# Agents in mr-moqui

MR Moqui is the Moqui framework in Rust. This repository is the framework; each application component under
`runtime/components/<set>/` (mr-boss, mr-mantle, mr-pass, mr-marble and the others in `addon/`) is a repository of its
own. Read the parts of this file your task touches, and the guides they point to.

## Before you start

- READMEs: before working in a directory, read the `README.md` in it and in each parent directory up to the repository root (for a component under `runtime/components/addon/`, its own repository's root and then mr-moqui's). Skip vendored and generated trees (`runtime/install`, `runtime/opensearch`, `webroot/libs`, `target`). Keep READMEs short: what is here, how to run and test it, and links to `docs/` for detail; no dated status or results.
- Building: read the [building skill](.agents/skills/building/SKILL.md) before building or working in a worktree.
- Applications: read [docs/dev/Practices-App-Dev.md](docs/dev/Practices-App-Dev.md) before working on MR Moqui applications (entities, services, screens, `.qvue` files and specs in a component such as mr-boss or mr-mantle).
- Rust: read [docs/dev/Practices-Rust.md](docs/dev/Practices-Rust.md) before working on Rust code (`crates/*`, a component's `src/`): where code goes, crate and module organization, tests, and idiom.
- JavaScript API: the references are `docs/dev/JS-*.md` ([docs/README.md](docs/README.md#dev-developing-on-mr-moqui)): [JS-Core-API](docs/dev/JS-Core-API.md) for `ec.*`, [JS-Globals](docs/dev/JS-Globals.md) for decimals, dates and the helper objects, [JS-Service-Scripts](docs/dev/JS-Service-Scripts.md), [JS-XML-Actions](docs/dev/JS-XML-Actions.md), [JS-Screen-Scripts](docs/dev/JS-Screen-Scripts.md) and [JS-Testkit](docs/dev/JS-Testkit.md). Look a member up there before assuming a Java one exists; when you add a host member, add it to the reference and to `crates/moqui-devkit/src/typegen/moqui-host.d.ts`, and rewrite the typegen golden (`UPDATE_GOLDEN=1 cargo test -p moqui-devkit --lib typegen`).
- Tests: read the [testing skill](.agents/skills/testing/SKILL.md) before writing or running tests.
- Harnesses: the repositories hold no harness's own files. A harness that does not find `AGENTS.md` and `.agents/skills` by itself has a setup task in `moq` that links or packages them where it looks (`./moq help` lists them on its "agent harnesses" line); add one in `scripts/moq/harness.sh` for a new harness.

## Rules

- Conf settings: a setting is an attribute of a conf element with its default written there, never a `default-property` or a `${name}` in a conf attribute (the boot refuses both): a component's on its own top-level element in its `MoquiConf.xml`, a framework one in `MoquiDefaultConf.xml` with its XSD attribute and conf schema entry. Code reads it by selector (`ec.factory.getConfValue("chat@view-once-days")`, `conf_env::setting`), specs set it with `setConf`/`withConf`, and the environment by `moqui_conf__...` ([Practices-App-Dev, Conf settings](docs/dev/Practices-App-Dev.md#conf-settings), [Run-Deploy](docs/Run-Deploy.md#settings-and-the-environment)).
- Failure tolerance: as Moqui Java does, when one independent piece fails (a DDL statement, a data file, a ServiceJob, a service file, a row that will not decrypt) log an error naming it and go on with the rest; do not `?` out of a loop over independent items. Stay strict only where it protects security or data (for example the legacy-schema check).
- Two test suites. The **regression suite** (`test/`, `test/client/`) is for development: it checks rules and fixed bugs, and runs while working (the specs of what you touched: `./moq test <component> --spec ...`) and before every commit. The **acceptance suite** (`test/acceptance/`, `test/acceptance/client/`) holds complete scenarios, access and isolation walks, screen sweeps, browser walks, load and media tests: `./moq accept [component...]` and `./moq accept-all`. **Run an acceptance test only when the user asks, or when you add or change one** (then that test, and its component's acceptance suite once it is written); never because code it uses changed, to check your own work, or as part of "done". See [docs/Build-Test.md](docs/Build-Test.md#the-two-suites). The **security proofs** (`test/proofs/`) are regression client specs filed by OWASP ASVS requirement, run by `./moq test-framework` and `./moq test-apps` and alone with `moqui test-client <component> --proofs`; a test belongs there only for an industry-standard requirement ([docs/security/proofs/README.md](docs/security/proofs/README.md)).
- Budgets: each component has a regression budget in `test/budget`; a regression spec over 15 seconds fails the run, so move it to acceptance or delete it (a Rust test over 15 seconds is `#[ignore = "..."]` or an opt-in `[[test]]`, which `./moq accept-all` runs). Do not raise a budget without the user's agreement.
- Rendering in tests: no regression test walks every screen of an app or of all apps, or every screen in every render mode (they have been deleted before and keep coming back; do not add one). Across the regression suite render a screen at most once in each mode, with all of its checks on that one render, and in a second mode only where the screen has its own qvt or tui template (`.qvue`, `.tui.json`, a `render-mode` section). A screen sweep belongs only in `test/acceptance/`, one per app per mode at most. See [docs/Build-Test.md](docs/Build-Test.md#rendering-screens-in-tests).
- `moqui test` and `moqui test-client` run specs directly. Node (22.13 or later) and npm build the libraries with `./moq build-js`. Use `./moq update-js` for dependency updates and `./moq verify-js` after changing JS build inputs.

## Validation

- Before a commit: run the [pre-commit skill](.agents/skills/pre-commit/SKILL.md), which picks the checks by what changed ([Build-Test, Before a commit](docs/Build-Test.md#before-a-commit)). For Rust, `cargo lint`, `cargo lint-min` and `./moq test-framework`, with `scripts/check-packages.sh` for a feature or dependency change: CI runs these on every push, and a commit that skips them fails there. For the framework's components, the conf, `moq` or `scripts/`, `./moq test-framework`. For application work (components under `runtime/components/addon` and `runtime/components/test`), `./moq test-apps`; never `cargo test`, the framework specs or `./moq test-all` for application work unless asked.
- Before a release or a production deploy: the [pre-production skill](.agents/skills/pre-production/SKILL.md): the lints, `./moq test-all`, `./moq accept-all`, the client apps, optionally load, the release build and the upgrade's conf check. `./moq test-all` and `./moq accept-all` are for a release, or when asked.
- Report what ran and what failed, with the output. A test that fails only in a full run is called flaky only after it passed alone; one that fails alone is a regression ([Reading the results](docs/Build-Test.md#reading-the-results)).

## Repositories and git

- The component repositories under `runtime/components/<set>/` follow the framework in lockstep: when mr-moqui is pulled, pull them too (`./moq git pull`, or `git pull --ff-only` in each), and commit in each repository the work changed.
- Merging upstream: check for conflicts without touching the tree (`git merge-tree --write-tree HEAD @{u}`), read the incoming commits for what the rules above refuse (a setting added as a property, a name the conf renamed, a slow or sweeping regression test), and run the pre-commit checks on the merge.
- Pull requests: before merging, cherry-picking or porting one, check that every author of its commits has signed the repository's `AUTHORS.md` ([docs/dev/Contributions.md](docs/dev/Contributions.md)). For an unsigned one work from its description, never from its diff.
