- Default building skill: read [.agents/skills/building/SKILL.md](.agents/skills/building/SKILL.md) before building or working in a worktree.
- Application development: read [docs/dev/Practices-App-Dev.md](docs/dev/Practices-App-Dev.md) before working on MR Moqui applications (entities, services, screens, `.qvue` files and specs in a component such as mr-boss or mr-mantle).
- Rust: read [docs/dev/Practices-Rust.md](docs/dev/Practices-Rust.md) before working on Rust code (`crates/*`, a component's `src/`): where code goes, crate and module organization, tests, and idiom.
- READMEs: before working in a directory, read the `README.md` in it and in each parent directory up to the repository root (for a component under `runtime/component/`, its own repository's root and then mr-moqui's). Skip vendored and generated trees (`runtime/install`, `runtime/opensearch`, `webroot/libs`, `target`). Keep READMEs short: what is here, how to run and test it, and links to `docs/` for detail; no dated status or results.
- Slow tests: **NEVER run a slow test without the user's explicit permission**, and ask for it only when the output of that test is needed for the task (a specific scenario or case the user wants checked), never because code it uses changed. Slow tests are NOT a tool for code coverage or for checking code quality at the unit level; they test specific scenarios or cases when needed. A test over about 15 seconds is slow and only for such special cases; write tests to run in well under that. One over 30 seconds must be marked slow: `slow: true` on a spec's `spec()` or `feature()`, `#[ignore = "slow: ..."]` in Rust, or an opt-in `[[test]]` that `./moq test-all` runs only with `--slow`. No test command runs a marked test without `--slow`, also when it is named (`moqui test`, `moqui test-client`, `./moq test-all`); do not pass `--slow` without that permission. See [docs/Build-Test.md](docs/Build-Test.md#slow-tests). A slow test is banned from normal runs and every slow test is a candidate for deletion: delete one rather than mark it when its scenario need not stay checkable; the end of a `moqui test` or `moqui test-client` run names any unmarked spec over 30 seconds.
- Rendering in tests: no test walks every screen of an app or of all apps, or every screen in every render mode (they have been deleted before and keep coming back; do not add one). Across the suite render a screen at most once in each mode, with all of its checks on that one render, and in a second mode only where the screen has its own qvt or tui template (`.qvue`, `.tui.json`, a `render-mode` section). See [docs/Build-Test.md](docs/Build-Test.md#rendering-screens-in-tests).
- Node is not a test dependency. `moqui test` and `moqui test-client` run the JavaScript specs. `libs/refresh.mjs` and `scripts/wasm-smoke.mjs` still use Node.
- Failure tolerance: as Moqui Java does, when one independent piece fails (a DDL statement, a data file, a ServiceJob, a service file, a row that will not decrypt) log an error naming it and go on with the rest; do not `?` out of a loop over independent items. Stay strict only where it protects security or data (for example the legacy-schema check).
