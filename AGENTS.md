- Default building skill: read [.agents/skills/building/SKILL.md](.agents/skills/building/SKILL.md) before building or working in a worktree.
- Application development: read [docs/dev/Practices-App-Dev.md](docs/dev/Practices-App-Dev.md) before working on MR Moqui applications (entities, services, screens, `.qvue` files and specs in a component such as mr-boss or mr-mantle).
- JavaScript API: the references are `docs/dev/JS-*.md` ([docs/README.md](docs/README.md#dev-developing-on-mr-moqui)): [JS-Core-API](docs/dev/JS-Core-API.md) for `ec.*`, [JS-Globals](docs/dev/JS-Globals.md) for decimals, dates and the helper objects, [JS-Service-Scripts](docs/dev/JS-Service-Scripts.md), [JS-XML-Actions](docs/dev/JS-XML-Actions.md), [JS-Screen-Scripts](docs/dev/JS-Screen-Scripts.md) and [JS-Testkit](docs/dev/JS-Testkit.md). Look a member up there before assuming a Java one exists; when you add a host member, add it to the reference and to `crates/moqui-devkit/src/typegen/moqui-host.d.ts`.
- Rust: read [docs/dev/Practices-Rust.md](docs/dev/Practices-Rust.md) before working on Rust code (`crates/*`, a component's `src/`): where code goes, crate and module organization, tests, and idiom.
- READMEs: before working in a directory, read the `README.md` in it and in each parent directory up to the repository root (for a component under `runtime/components/addon/`, its own repository's root and then mr-moqui's). Skip vendored and generated trees (`runtime/install`, `runtime/opensearch`, `webroot/libs`, `target`). Keep READMEs short: what is here, how to run and test it, and links to `docs/` for detail; no dated status or results.
- Testing: read [.agents/skills/testing/SKILL.md](.agents/skills/testing/SKILL.md) before writing or running tests. There are two suites. The **regression suite** (`test/`, `test/client/`) is for development: it checks rules and fixed bugs, and runs while working (the specs of what you touched: `./moq test <component> --spec ...`) and before every commit. The **acceptance suite** (`test/acceptance/`, `test/acceptance/client/`) holds complete scenarios, access and isolation walks, screen sweeps, browser walks, load and media tests: `./moq accept [component...]` and `./moq accept-all`. **Run an acceptance test only when the user asks, or when you add or change one** (then that test, and its component's acceptance suite once it is written); never because code it uses changed, to check your own work, or as part of "done". Each component has a regression budget in `test/budget`; a regression spec over 15 seconds fails the run, so move it to acceptance or delete it (a Rust test over 15 seconds is `#[ignore = "..."]` or an opt-in `[[test]]`, which `./moq accept-all` runs). Do not raise a budget without the user's agreement. See [docs/Build-Test.md](docs/Build-Test.md#the-two-suites).
- Before a commit: `./moq test-apps` for application work (components under `runtime/components/addon` and `runtime/components/test`), `./moq test-framework` for framework work (`crates/`, `runtime/components/base`, `runtime/components/dev`, `moq`, `scripts/`). Never run `cargo test`, the framework specs or `./moq test-all` for application work unless asked; `test-all` is for a release or when asked.
- Rendering in tests: no regression test walks every screen of an app or of all apps, or every screen in every render mode (they have been deleted before and keep coming back; do not add one). Across the regression suite render a screen at most once in each mode, with all of its checks on that one render, and in a second mode only where the screen has its own qvt or tui template (`.qvue`, `.tui.json`, a `render-mode` section). A screen sweep belongs only in `test/acceptance/`, one per app per mode at most. See [docs/Build-Test.md](docs/Build-Test.md#rendering-screens-in-tests).
- Node is not a test dependency. `moqui test` and `moqui test-client` run the JavaScript specs. `libs/refresh.mjs` and `scripts/wasm-smoke.mjs` still use Node.
- Failure tolerance: as Moqui Java does, when one independent piece fails (a DDL statement, a data file, a ServiceJob, a service file, a row that will not decrypt) log an error naming it and go on with the rest; do not `?` out of a loop over independent items. Stay strict only where it protects security or data (for example the legacy-schema check).
- Pull requests: before merging, cherry-picking or porting one, check that every author of its commits has signed the repository's `AUTHORS.md` ([docs/dev/Contributions.md](docs/dev/Contributions.md)). For an unsigned one work from its description, never from its diff.
