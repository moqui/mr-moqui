# Security review: Low and Info findings

The Low and Info findings of the [security review](Security-Review.md), by area, in short form: what happens, where, and the suggested fix. The evidence each reviewer quoted is in the reports (`plans/security-review-evidence/slice-N.md`).


## Web authentication and controls

- **SEC-WEB-05 (Low; reported (confirmed in code)). Several sign-ins keep the session id; the forced password change flow never changes it.** `login_user` rotates only when `password_login` returns `Ok`; an account with `requirePasswordChange` or an expired password returns the error before the rotation, and `Login/changePassword` then signs the user in with `internalLoginUser`, which does not rotate. The id the attacker planted is then a signed-in session. The cookie name has no `__Host-` prefix, and the first `moqui.session` pair of the header wins. Where: `crates/moqui-core/src/user/login.rs:54-61`, `:403-416`, `:514-516`; `Login.xml:105-114`. Fix: Rotate the session id in `finish_login` whenever a bound web session's user changes from none or from another user, whatever the caller.
- **SEC-WEB-06 (Low; reported (confirmed in code)). Logout keeps the session and its attributes; a password change ends nothing.** `logout` clears the user but keeps the session id and every attribute, and the next sign-in's new session is a copy of it, so attributes of the earlier user (the map's one-time values such as `newAccessToken`, `newAppPassword`, `singleUseCodes`, and application state) are in the next user's session. The `hasLoggedOut` flag that ends other sessions is cleared by the next person sign-in, including any request with the user's `api_key`, so a session that made no request in between stays signed in. `change_password` and `update#PasswordInternal` end no session and revoke no key. Where: `crates/moqui-core/src/user/login.rs:1042-1071`, `:1227-1245`; `crates/moqui-core/src/user/session.rs:1490-1506`, `:2763-2781`. Fix: At logout drop the session (retire the id and its attributes) and send a new anonymous one. At a password change end the user's other sessions and offer to end the keys.
- **SEC-WEB-07 (Low; reported (confirmed in code); fixed). The `login` rate limit covers part of the password checks and is passed by a dot segment.** The limit's globs are matched against the path as sent; the screen path drops `.`, `..` and `~` segments, so the same transition is reached on a path the glob does not match. The same holds for any `path-rule` deny and any path-scoped limit a component adds. The listed other paths check a password or code and are not in the limit at all; only `all` (50 a second, burst 500) and the `auth-failure` ban apply to them. Where: `crates/moqui-host/src/guard.rs:295-300`, `:1010-1035`; `crates/moqui-core/src/screen/url.rs:645-672`; `MoquiDefaultConf.xml:869-870`. Fix: Normalize the path in `Guard::check` the way `cleanup_path_names` does before matching, or refuse a request path with `.`, `..` or `~` segments at the listener. Fixed 2026-11-16: each `rate-limit` and `path-rule` applies when it matches the path as sent (escapes decoded) or the screen path it resolves to (`guard.rs` `screen_path`, in `check` and `check_served_path`); test `guard_tests.rs` `a_limit_and_a_path_rule_match_the_screen_path_a_request_reaches`.
- **SEC-WEB-09 (Low; reported (confirmed in code); fixed). `reset#Password` rewrites `requirePasswordChange` for any account.** With the default `email-require-change="false"` the service sets `requirePasswordChange = N`, which removes an administrator's "must change at first sign-in" from a new account. With `true` it sets `Y`, which makes any user's next sign-in fail until they change their password. The unknown-user branch logs the caller's text and returns before the hash, so timing tells whether the account exists. Where: `UserServices.xml:404-462`. Fix: Leave `requirePasswordChange` alone at reset; set it when the reset password is used in `update#Password`. Fixed 2026-11-16: `reset#Password` leaves `requirePasswordChange` alone and makes its random password and hash before the lookup, so an unknown, closed or recently reset account answers after the same work; test `framework/test/PasswordChangeGate.spec.js`.
- **SEC-WEB-10 (Low; reported (confirmed in code)). Dev conf: every origin is allowed with credentials.** With `*` the origin check passes every `Origin`, and the response echoes it with `Access-Control-Allow-Credentials: true` and exposes `X-CSRF-Token`, so that page reads responses and the session token and can post as the signed-in developer. A dev instance with Dev AIDE runs code as the server's user for such a session. Where: `runtime/conf/MoquiDevConf.xml:9`; `crates/moqui-core/src/web/origin.rs` `origin_allowed_by`; `crates/moqui-core/src/web/mod.rs:2318-2327`. Fix: In the dev conf allow `localhost` and `127.0.0.1` origins of the server's own port only, or do not send `Access-Control-Allow-Credentials` when the match was `*`.
- **SEC-WEB-11 (Low; reported (confirmed in code)). `/health` and `/metrics` trust a loopback TCP peer.** Both routes allow a peer that is loopback or in `status-ips`, by the TCP peer, so every request the local proxy forwards is allowed. `/metrics` answers pool, queue, statement and web protection counts. Where: `crates/moqui-host/src/http.rs:957-963`, `:1679-1684`. Fix: When `client-ip-header` is believed for the peer, test the resolved client address as well as the peer.
- **SEC-WEB-12 (Low; reported (confirmed in code); fixed). Second factor details: a TOTP code works more than once; code sends are not limited in the login flow.** Nothing records a TOTP step as used, so a code is accepted again for its step and the one after. Each `sendOtp` creates a new single-use row and sends an email or SMS; only the re-authentication path has the 30 second gap. Where: `crates/moqui-core/src/user/totp.rs:89-106`; `UserServices.xml:688-694`, `:772-814`. Fix: Store the last accepted TOTP step on the factor and refuse a step not after it. Apply the send gap in `send#ExternalAuthcCode`. Fixed 2026-11-16: `validate#UserAuthcFactorCode` takes an authenticator code only for a step after the factor's last one (`UserAuthcFactor.lastTotpStep`, `user::totp_code_step`), and `send#ExternalAuthcCode` refuses a second code to a factor within 30 seconds; tests `user::totp` `a_code_is_taken_for_a_step_after_the_last_one`, `framework/test/CredentialGuards.spec.js`.
- **SEC-WEB-13 (Low; reported (confirmed in code)). A `session_cookie_key` set by the operator is not checked.** A value from the environment is never replaced. `CHANGEME` is valid base64 and decodes to six known bytes, and any length is accepted as the HMAC key. A forged MAC still needs a live session id (160 random bits), which is in `HttpSession`, `Visit.sessionId` and the telemetry attribute `session.id`. Where: `crates/moqui-core/src/user/session.rs:3057-3065`; `crates/moqui-core/src/context/factory.rs:1812-1816`. Fix: Refuse to start with a decoded key under 32 bytes or one ending in `CHANGEME`.
- **SEC-WEB-14 (Low; reported (confirmed in code); fixed). An anonymous tarpit lock is everyone's.** The count key and the lock row use an empty user id for every caller with nobody signed in, so one client that passes the limit on `/Login` locks the screen for every signed-out visitor for the lock time, and can repeat it. Where: `crates/moqui-core/src/user/authz.rs:703-704`, `:753-758`. Fix: Key the anonymous count by the client address or the visitor. Fixed 2026-11-16: with nobody signed in the tarpit's count and lock are keyed by `_ANON_` and a digest of the client address (an IPv6 one by its /64; `authz.rs` `anonymous_tarpit_subject`); test `authz_tests.rs` `an_anonymous_tarpit_lock_is_the_client_addresss`.

## Routes, screens and REST

- **SEC-RTE-08 (Low; reported (confirmed in code); fixed). State changes on `GET` with no token.** A `GET` is never token-checked. A `read-only` transition takes URL parameters, and a transition that is not `read-only` still runs on a `GET` with no query, its `path-parameter` values included. So these change state from a link: `/apps/setPrefGoLast?preferenceKey=..&preferenceValue=..` (any user preference; `mantle.content.root` is the default root of `/resources`), `/Login/logout`, `/rest/logout`, `/sso/logout`, `/Login/removePreAuth`, and any application transition without `method="post"` that takes only path parameters. Where: `crates/moqui-core/src/screen/render.rs:2667` (`csrf_rejected`), `:2070` (`insecure_transition`). Fix: Refuse a `GET` for a transition that is not `read-only` and has actions; make `setPrefGoLast` and the logouts `POST`. Partly fixed 2026-11-16 with SEC-WEB-04: a GET another site started is refused for a transition that runs actions and is not `read-only` (`/Login/logout`, `/rest/logout`, `/Login/removePreAuth`, path-parameter transitions); the `read-only` ones (`setPrefGoLast`, `/sso/logout`, SEC-ADM-09) still change state on such a GET. Fixed 2026-11-16 (rest): `apps/setPrefGoLast` is `method="post"`, `/sso/logout` is neither `read-only` nor without the session token (a cross-site GET is 403), and Tools' and Marble's `createFieldDynamic` are not `read-only`: the field tree sends it as a POST with the token (`screen/tree.rs` `loadMethod` "post", qvt `loadContainer`, html `postThenLoad`), and a GET with its parameters in the URL is refused. Tests `forms.rs` `a_tree_link_that_loads_through_a_writing_transition_is_a_post`, `SecurityScreens.spec.js` "a GET of sso/logout, setPrefGoLast or createFieldDynamic changes nothing". The terminal client still opens the field tree's links by GET, which are now refused there.
- **SEC-RTE-09 (Low; reported (confirmed in code)). `lastStandalone` takes the parents out of the user check.** A screen marked `require-authentication="false"` or `anonymous-*` under a parent that requires a user is reachable with no user, and so are its transitions, which then need no authorization record. The always-actions of every parent still run. In the base and dev components the only such screen is `ScreenTreeNested`, whose actions fail without `ScreenTree`'s; an application screen written on the assumption that its parent protects it has no such luck. Where: `crates/moqui-core/src/screen/url.rs:373`; `crates/moqui-core/src/screen/render.rs:1513`. Fix: Check authentication against every screen of the path (`path_defs`), as the transition path already pushes them all, and keep `render_defs` for what is drawn.
- **SEC-RTE-10 (Low; reported (to check)). `/health` and `/metrics` trust the TCP peer.** Both routes allow any loopback peer and do not use the client address a trusted proxy names. The map says the server is meant to run behind a proxy; with the proxy on the same host every request has a loopback peer, so `/metrics` (pool, guard, telemetry counters, Prometheus text) and `/health` answer the internet unless the proxy blocks the two paths. `/status` uses the proxy-named client and does not have this. Where: `crates/moqui-host/src/http.rs:957`, `:977`, `:1679`. Fix: When `trusted-proxies` names the peer, decide by the resolved client address, as `/status` does; say so in the map row either way.
- **SEC-RTE-11 (Low; reported (likely)). A restricted host still serves some framework paths.** The refusal is by the reserved first-segment list. The token routes `i` (staff invitation) and `call` are not in it and are dispatched before the site's own routing, so they run on the restricted host. Where the site has no mount at `/`, the root transitions (`/menuData`, `/shellData`, `/resources`, `/find/rank`, `/email/..`) and a `//name` search path (`//tools` is `/apps/tools`) also reach the framework there; a request with a key or Basic header is signed in for them. The map says nobody reaches the apps or the token routes on such a host. Where: `crates/moqui-core/src/screen/public_site.rs:96`-`102`; `crates/moqui-core/src/web/reserved.rs:114`. Fix: On a restricted host refuse every path the site's own mounts do not take (and every token route), instead of refusing a list.
- **SEC-RTE-12 (Low; reported (confirmed in code)). Anonymous reads through `/listViewColumns` and `/statusBar`.** With no user and no authorization the caller reads any `StatusItem` and `Enumeration` description by id (500 ids a request for `values`; `stages` is not capped), every status of a type, and the flow transitions. Enumerations include what applications and customers define. Each id is a cached find, so unknown ids also add finds and cache entries. Where: `runtime/components/base/webroot/screen/webroot.xml:83`, `:104`; `runtime/components/base/framework/service/org/moqui/ui/StatusServices.xml:62`, `:171`. Fix: Answer 401 without a user, as the neighbouring transitions do; a public page that needs a board can name its values server-side.
- **SEC-RTE-13 (Low; reported (confirmed in code)). Answers that tell an anonymous caller what exists.** A missing screen path is 404 with the component location of the last screen found, while an existing protected one is a redirect or 401, so the screen tree under `/apps` can be mapped. `/rest/s1/<root>/<bad>` lists the resource names at that level before any user check. `/rest/sm/<type>/<remote>` says whether a message type and a remote exist, names the remote's HMAC header, and on a failure returns the error text (`Error receiving message: {err}`) whatever the instance purpose. Where: `crates/moqui-core/src/screen/url.rs:499`; `crates/moqui-core/src/service/rest.rs:480`; `crates/moqui-core/src/service/system_sync/message.rs:231`, `:248`, `:252`, `:290`. Fix: Answer an anonymous caller a plain 404 (no location, no names), one 403 text for every `/rest/sm` refusal, and an error id for its 500.
- **SEC-RTE-14 (Low; reported (confirmed in code); fixed). Service REST entity lists have no upper bound.** `pageNoLimit=true` removes the 100-row default and `rest-max-page-size` is not applied here, so one request reads a whole table into memory and one response. Generic entity REST removes the parameter for this reason. Where: `crates/moqui-core/src/service/rest.rs:731`. Fix: Apply the same removal and `rest-max-page-size` cap in `find_entity`. Fixed 2026-11-16: Service REST `find_entity` drops `pageNoLimit` from the request and caps a page at `rest-max-page-size`, 100 when no page is asked for; test `rest_tests.rs` `entity_resources_answer_encrypted_fields_as_set_and_read_a_page_at_most`.
- **SEC-RTE-15 (Low; reported (to check)). `getPreferences` builds a JavaScript regular expression from the request.** The pattern is compiled by the script engine and tested against each of the user's preference keys, which the same user sets. A backtracking pattern against a long key of their own holds a request worker. Where: `crates/moqui-core/src/script/host/user.rs:120`; `runtime/components/base/webroot/screen/webroot/apps.xml:58`. Fix: Match with a prefix or a fixed set of keys, or cap the pattern's length and the script's time.
- **SEC-RTE-16 (Low; reported (to check)). A refused token-route token is not counted.** The dispatch answers 404 and does not call `web::note_auth_failure`, which is what per-client web protection counts for sign-ins, device codes, git and CI tokens. Guess limits are then whatever each token service does itself. Where: `crates/moqui-core/src/screen/token_route.rs:300`-`365`. Fix: Call `note_auth_failure` in `dispatch` when `check_token` refuses a well-formed token.
- **SEC-RTE-17 (Low; reported (confirmed in code)). The Login page verifies a password on every render and offers a one-click admin sign-in.** When `EX_JOHN_DOE` exists the page runs a password verification for each anonymous render (the stored hash is rehashed at login, so it may be the configured slow hash), and when the password is still `moqui` it shows a form that signs in as that `ADMIN` user. Nothing ties this to the instance purpose; it depends only on whether demo data was loaded. Where: `runtime/components/base/webroot/screen/webroot/Login.xml:191`-`193`, `:249`-`256`. Fix: Run the section only when `instance_purpose` is `dev` or `test`.
- **SEC-RTE-18 (Info; reported (to check)). `/PublicShell` takes `tokenRoute` from a JSON body.** The map says no request parameter sets the token route's context. For a request to `/PublicShell` itself the screen reads `tokenRoute` from the context, where a JSON object parameter of that name lands, and builds the page's config (base path, title, context, the session token) from it. The page then loads `<basePath>.qvt` as a template with the compiler build of Vue. Where: `runtime/components/base/webroot/screen/webroot/PublicShell.xml:24`. Fix: Have the token-route dispatch put `tokenRoute` in a request attribute the screen reads, and ignore a parameter of that name.

## Administration, identity and sign-in

- **SEC-ADM-07 (Low; reported (confirmed in code); fixed). Long-lived credentials are minted from a session with no recent sign-in.** A session holder gets an API key (no second factor at use, A2), an app password or an SSH key for the account without the password. `expireDays` has no upper bound. Where: `crates/moqui-core/src/service/user_keys.rs:216-229, 382-401, 137-176`. Fix: Ask `check#RecentAuth` in the three create services and cap `expireDays`. Fixed 2026-11-16: `create#UserSshKey`, `create#UserAccessToken` and `create#UserAppPassword` need a sign-in in the last five minutes (`require_recent_auth`), and a token's `expireDays` is at most 366; `create#UserScopedKey` (the gateway key, narrower than the key that makes it) is left without the rule; test `service::user_keys_tests` `credentials_need_a_recent_sign_in_and_an_access_token_is_for_git_alone`. Follow-up 2026-11-16 (commit 67c0856f3): an administrator acting on another account needs a recent sign-in too, for its password, codes, factors, email and provider link, Login as, and the revoke of its keys, tokens, app passwords, SSH keys and phones (`revoke#AccountAccess`, every kind, and `revoke#Sessions` for another account's sessions); test `framework/test/AdminSessions.spec.js`.
- **SEC-ADM-08 (Low; reported (confirmed in code); fixed). Login-as leaves no evidence and has no bound.** `internal_login_user` calls `internal_login` and not `recorded_login`, so no `UserLoginHistory` row is written, no audit row is written by the transition, and the session id is kept. The target is not compared with the caller (`heldBeyond`), and may be the caller's own or any account that is not a display account. Where: `base/tools/screen/System/Security/UserAccount/UserAccountDetail.xml:31-43`; `crates/moqui-core/src/user/login.rs:403-415`. Fix: Write an audit row (actor, target, visit) and apply `heldBeyond`. Fixed 2026-11-16: Tools' `loginAs` refuses the caller's own account and an account that holds access the caller lacks, and writes an `EntityAuditLog` row (`changedFieldName` `loginAs`, the administrator's user and visit) and a warning before the login; `UserLoginHistory` is still not written. Follow-up 2026-11-16 (commit 67c0856f3, and mr-boss Admin's `UserDetail.xml` `loginAs`): Login as, in Tools and in mr-boss Admin, also needs the administrator's sign-in in the last five minutes (`require#RecentAuth`), and logs in only when it is recent.
- **SEC-ADM-09 (Low; reported (confirmed in code); fixed). `/sso/logout` signs the browser out on a GET.** The transition is `read-only` with no session token and `logout#User` is `anonymous-all`; it calls `crate::user::logout()` for any session, SSO or not. Where: `base/webroot/screen/webroot/sso.xml:40-45`; `crates/moqui-core/src/service/sso.rs:551-580`. Fix: Take the logout by POST with the session token, as `/Login/logout`. Fixed 2026-11-16 with SEC-RTE-08: `/sso/logout` is neither `read-only` nor `require-session-token="false"`, as `/Login/logout`; a cross-site GET is 403.
- **SEC-ADM-10 (Low; reported (confirmed in code)). Owner services run below `OperationServices` with inherited authorization.** See B4. An owner's registered service that relies on its artifact authorization, as the map warns for import targets below an app screen, is open to every holder of the operation permission. The transfer, audit and readiness families have a non-inheritable call step; this one does not. Where: `admin/OperationLib.js:59-72`; `base/framework/data/AdminConfigurationData.xml:204, 353, 367`. Fix: Call owners through a non-inheritable `call#OwnerService`, as `call#TargetService`.
- **SEC-ADM-11 (Low; reported (likely)). The SSO sync writes an unverified `email` claim to `UserAccount.emailAddress`.** `map_fields` copies the claim whatever `email_verified` says, and the account is created or updated with it, authorization off. Anything that treats `UserAccount.emailAddress` as proof of a mailbox (`reset#Password` finds an account by it, `UserServices.xml:420`) reads an address its owner never confirmed. For an existing account `update#UserAccount` refuses a duplicate with "Email X is already in use. Login with username Y", which names another account and fails the sign-in. Where: `crates/moqui-core/src/service/sso.rs:601-650, 762-777`. Fix: Map `email` only when `email_verified` is true, and give one generic refusal.
- **SEC-ADM-12 (Low; reported (confirmed in code); fixed). An anonymous reset can force a password change.** The reset sets `requirePasswordChange` Y on the account named. Every login of it, by password, key, app password or provider, then fails in `post_password` until the password is changed. Where: `UserServices.xml:404-462`. Fix: Require the change only when the reset password is used, not when it is requested. Fixed 2026-11-16 with SEC-WEB-09: `reset#Password` leaves `requirePasswordChange` alone.
- **SEC-ADM-13 (Info; reported (confirmed in code); fixed). `create#InitialAdminAccount` on a fresh instance.** The first caller becomes `ADMIN`. The check and the create are not under one lock, so two requests at once can both pass. An account made first by a provider sign-in or a registration turns the path off. Where: `UserServices.xml:464-505`. Fix: None needed beyond the documented rule; a unique marker row would close the race. Fixed 2026-11-16 with SEC-WEB-08: the first administrator is made only from this machine or with the startup log's setup secret, under a row lock.

## Tools, System, Monitor and Dashboards

- **SEC-TLS-07 (Low; reported (confirmed in code); fixed). `export#EntityDataSnapshot` joins `baseFilename` into a path.** The zip is written to `runtime/db/snapshot/<baseFilename>.zip` with parent directories made, so a snapshot (every field of the chosen entities) lands in any directory the server can write, for example one a static route serves. The other snapshot transitions check `isSafeSinglePathSegment`; this one does not. The file is never replaced (`create_new`). Where: `runtime/components/base/framework/service/org/moqui/impl/EntityServices.xml:276-284`. Fix: Refuse a `baseFilename` that fails `isSafeSinglePathSegment` in the service. Fixed 2026-11-16: `export#EntityDataSnapshot` refuses a `baseFilename` that is not one safe path segment (`WebUtilities.isSafeSinglePathSegment`); test `tools/test/EntityExport.spec.js`.
- **SEC-TLS-08 (Low; reported (confirmed in code); partly fixed). The production internal-address check of a deploy URL is bypassed by user info, and fails open.** `check_url` takes the authority as the text before the first `/` or `:`, so with `user:password@host` it tests `user`, which does not resolve; a resolution error counts as not internal. The fetch then goes to the internal host. The check also resolves once, before the fetch resolves again. Where: `crates/moqui-devkit/src/deploy/git.rs:210-234`. Fix: Parse the URL with the `url` crate, treat a host that does not resolve as refused, and pass `deny_internal` to the fetch so the address used is the address checked. Fixed 2026-11-16 in part: `check_url` parses with the `url` crate, and on production a host that does not resolve, or has any internal address, is refused (test `deploy::git::tests::on_production_an_internal_or_unknown_deploy_host_is_refused`); left: the fetch resolves the host again (gix resolves itself and offers no hook to connect to the checked address).
- **SEC-TLS-09 (Low; reported (confirmed in code); fixed). Secrets written to the server log by Tools and Instance.** Service Run logs every result value at INFO. `init#InstanceDocker` logs the whole container request, with each `Env` value (`entity_ds_password` among them, stored encrypted in `AppInstanceEnv.envValue`). The log is read in Monitor by any `SYSTEM_APP` holder and kept by retention. Where: `runtime/components/base/tools/screen/Tools/Service/ServiceRun.xml:26-29`; `runtime/components/base/framework/service/org/moqui/dev/InstanceServices.xml:439`. Fix: Drop both log lines, or log the names only. Fixed 2026-11-16: `init#InstanceDocker` logs the image and the names of the env and host settings, and Service Run logs the result names only.
- **SEC-TLS-10 (Low; reported (to check); fixed). `create#DatabaseMySQL` quotes the password for standard SQL only.** The password is put in a string literal with `'` doubled. MySQL's default mode also takes `\` as an escape, so a value with `\'` ends the literal early and the rest is read as SQL, with the database host's admin login. The seed's claim of interpolated identifiers is refuted: names must match `^[A-Za-z0-9_]+$` (`:812-814`). Where: `runtime/components/base/framework/service/org/moqui/dev/InstanceServices.xml:816`, `:842`. Fix: Refuse a password with `\` or a quote, or send it as a bound parameter. Fixed 2026-11-16: `create#DatabaseMySQL` refuses a password holding `'`, `"` or `\`.
- **SEC-TLS-14 (Low; reported (likely)). (telemetry reader) An ingest key's sender can pose as this server's own service and move the regression detector and recovery.** The receiver fixes only `source.id` and `source.name`. A sender sets `service.name`, `service.version` and `service.instance.id` to this server's own, and may post a `release` annotation for a version. `detect#Regressions` (every five minutes) and the release list select by `service.name` and never by source, so forged request metrics open a regression and an incident for the local service, which the seed `DEFAULT` policy escalates to the `ADMIN` group. Where an `automatic` policy and `allow-automatic="true"` are set, the incident can run the ladder (pause a job, deny an artifact group, drain an instance). Forged healthy data can equally hide a regression or let a verification pass. Spans can also carry any `user.id`. Where: `crates/moqui-core/src/telemetry/ingest.rs:878-891`, `crates/moqui-report/src/regression/mod.rs:144-157`, `:276-281`, `crates/moqui-report/src/annotations.rs:60-75`. Fix: Have the detector, the release list and verification read the local service only from records with no `source.id`, and treat a received service of the same name as another service (or refuse the local `service.name` from a key).
- **SEC-TLS-15 (Low; reported (likely)). (telemetry reader) An ingest key owned by an administrator writes business annotations for any organization.** The receiver calls `create_annotation` as the key's owner. For `business` the check is the owner's own grant of `org.moqui.report.annotation.business`, which `ADMIN` holds, so a telemetry credential placed on another machine writes a business event marker (255 bytes of text and a path on this server as its link) into the dashboards of any organization. The code's comment says the technical sources write no business event. Where: `crates/moqui-report/src/annotations.rs:19-31`, `crates/moqui-host/src/monitor/receiver.rs:224-243`. Fix: In the receiver path refuse `source` `business` (the shared map already carries `monitor.ingest.source`).
- **SEC-TLS-16 (Low; reported (confirmed in code); fixed). (telemetry reader) `Settings/revertAll` runs on a GET with no token.** The transition has no `method`, so it accepts GET; a GET is never token-checked, and a transition with actions is refused on GET only when the URL carries parameters, which this one does not need. Every runtime override on every instance is reverted (a raised log level, a receiver turned off for an incident, a sample ratio). The change is logged with the victim as the user. Where: `runtime/components/base/tools/screen/System/Monitor/Settings.xml:17-20`.
