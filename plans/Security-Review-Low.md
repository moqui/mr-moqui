# Security review: Low and Info findings

The Low and Info findings of the [security review](Security-Review.md), by area, in short form: what happens, where, and the suggested fix. The evidence each reviewer quoted is in the reports (`plans/security-review-evidence/slice-N.md`).


## Web authentication and controls

- **SEC-WEB-05 (Low; reported (confirmed in code); fixed). Several sign-ins keep the session id; the forced password change flow never changes it.** `login_user` rotates only when `password_login` returns `Ok`; an account with `requirePasswordChange` or an expired password returns the error before the rotation, and `Login/changePassword` then signs the user in with `internalLoginUser`, which does not rotate. The id the attacker planted is then a signed-in session. The cookie name has no `__Host-` prefix, and the first `moqui.session` pair of the header wins. Where: `crates/moqui-core/src/user/login.rs:54-61`, `:403-416`, `:514-516`; `Login.xml:105-114`. Fix: Rotate the session id in `finish_login` whenever a bound web session's user changes from none or from another user, whatever the caller. Fixed 2026-11-16 in part (commit 8a271bf02): every sign-in moves a session the client brought to a new id when it held another user or none (`login.rs` `internal_login`: the forced password change's `internalLoginUser`, a second factor's code, a key, an app password, an identity provider; `rotate_on_password_login` unless the session was made for this request), so a planted id is never the signed-in one; an SSO sign-in for the user the session already holds keeps the id. Test `user::session` `every_sign_in_moves_a_brought_session_to_a_new_id`. Fixed 2026-11-16 (the rest; commits 23a478718 and 833f6b5ad, mr-pass 6a23ff8), the owner's call: rename the cookie over https, keep the name over plain http, and have users sign in once again at the upgrade. Over https the session cookie is `__Host-moqui.session` (`Secure`, `Path=/`, no `Domain`), so no other host of the domain and no plain-http page can plant or shadow it, and an https request reads only that name, a plain `moqui.session` there being no session (`user::session_cookie_name`, `format_session_cookie`, `web::session_cookie_of`, the host's `notws::session_cookie` for `/notws`, `/termws`, the Assist event stream and the upload check); plain http keeps `moqui.session`, and the edge's sticky cookie reads `__Host-moqui.session` first. PASS keeps and counts the authority's https cookie by its new name (`Transport.js`, `Headers.js`, `ShopCart.js`). Tests `user::session` `a_bad_mac_is_an_unknown_session`, `web` `an_https_request_reads_only_the_host_prefixed_session_cookie`, `edge_link::web` `the_sticky_cookie_is_read_from_every_cookie_header`.
- **SEC-WEB-06 (Low; reported (confirmed in code); fixed). Logout keeps the session and its attributes; a password change ends nothing.** `logout` clears the user but keeps the session id and every attribute, and the next sign-in's new session is a copy of it, so attributes of the earlier user (the map's one-time values such as `newAccessToken`, `newAppPassword`, `singleUseCodes`, and application state) are in the next user's session. The `hasLoggedOut` flag that ends other sessions is cleared by the next person sign-in, including any request with the user's `api_key`, so a session that made no request in between stays signed in. `change_password` and `update#PasswordInternal` end no session and revoke no key. Where: `crates/moqui-core/src/user/login.rs:1042-1071`, `:1227-1245`; `crates/moqui-core/src/user/session.rs:1490-1506`, `:2763-2781`. Fix: At logout drop the session (retire the id and its attributes) and send a new anonymous one. At a password change end the user's other sessions and offer to end the keys. Fixed 2026-11-16 in part (commit 8a271bf02): logout ends the bound session with its attributes (`session::renew_after_logout`: the id retired, its row deleted and the end published to the cluster, a new empty session of no user and no visit), and `update#PasswordInternal` ends the account's other sessions on every server (`UserSecurityChecks.endUserSessions`; the current one stays). Tests `user::session` `a_logout_ends_the_session_and_its_attributes`, `PasswordChangeGate.spec.js` "a new password ends the account's other sessions". Fixed 2026-11-16 (the rest; commit 806142bca, mr-boss e32064e3), the owner's call: only an interactive sign-in clears `hasLoggedOut`, so a key or app password request never undoes a logout; logout is not changed, and the account gets "sign out everywhere and end my keys and app passwords". A login key, `api_key` header or app password signs its request in and leaves `UserAccount.hasLoggedOut` set; a password, a second factor's code, SSO or an SSH key sign-in at the host clears it (`login.rs` `recorded_login`). `IdentityServices.revoke#OwnAccess` (the caller's own account, no permission but `require#RecentAuth`) ends every session of the account on every server (the current one at its next request), its login keys and app passwords, through `revoke#AccountAccess`'s path with its evidence row, and leaves SSH keys and phones; Commons Account's "Sign out everywhere and end my keys and app passwords" calls it. Tests `user::login` `a_key_or_app_password_login_leaves_has_logged_out_set`, AdminSessions "revoke#OwnAccess signs the account out everywhere and ends its keys and app passwords after a recent sign-in", mr-boss CommonsSettings "Sign out everywhere ends my own keys and app passwords, after a recent sign-in".
- **SEC-WEB-07 (Low; reported (confirmed in code); fixed). The `login` rate limit covers part of the password checks and is passed by a dot segment.** The limit's globs are matched against the path as sent; the screen path drops `.`, `..` and `~` segments, so the same transition is reached on a path the glob does not match. The same holds for any `path-rule` deny and any path-scoped limit a component adds. The listed other paths check a password or code and are not in the limit at all; only `all` (50 a second, burst 500) and the `auth-failure` ban apply to them. Where: `crates/moqui-host/src/guard.rs:295-300`, `:1010-1035`; `crates/moqui-core/src/screen/url.rs:645-672`; `MoquiDefaultConf.xml:869-870`. Fix: Normalize the path in `Guard::check` the way `cleanup_path_names` does before matching, or refuse a request path with `.`, `..` or `~` segments at the listener. Fixed 2026-11-16: each `rate-limit` and `path-rule` applies when it matches the path as sent (escapes decoded) or the screen path it resolves to (`guard.rs` `screen_path`, in `check` and `check_served_path`); test `guard_tests.rs` `a_limit_and_a_path_rule_match_the_screen_path_a_request_reaches`.
- **SEC-WEB-09 (Low; reported (confirmed in code); fixed). `reset#Password` rewrites `requirePasswordChange` for any account.** With the default `email-require-change="false"` the service sets `requirePasswordChange = N`, which removes an administrator's "must change at first sign-in" from a new account. With `true` it sets `Y`, which makes any user's next sign-in fail until they change their password. The unknown-user branch logs the caller's text and returns before the hash, so timing tells whether the account exists. Where: `UserServices.xml:404-462`. Fix: Leave `requirePasswordChange` alone at reset; set it when the reset password is used in `update#Password`. Fixed 2026-11-16: `reset#Password` leaves `requirePasswordChange` alone and makes its random password and hash before the lookup, so an unknown, closed or recently reset account answers after the same work; test `framework/test/PasswordChangeGate.spec.js`.
- **SEC-WEB-10 (Low; reported (confirmed in code); fixed). Dev conf: every origin is allowed with credentials.** With `*` the origin check passes every `Origin`, and the response echoes it with `Access-Control-Allow-Credentials: true` and exposes `X-CSRF-Token`, so that page reads responses and the session token and can post as the signed-in developer. A dev instance with Dev AIDE runs code as the server's user for such a session. Where: `runtime/conf/MoquiDevConf.xml:9`; `crates/moqui-core/src/web/origin.rs` `origin_allowed_by`; `crates/moqui-core/src/web/mod.rs:2318-2327`. Fix: In the dev conf allow `localhost` and `127.0.0.1` origins of the server's own port only, or do not send `Access-Control-Allow-Credentials` when the match was `*`. Fixed 2026-11-16 (commit 4591ccf8c), the owner's call: the dev conf allows only this machine's origins, and `*` never comes with credentials on any conf. `MoquiDevConf.xml` allows only `localhost` and `127.0.0.1` origins, any port and scheme (`webapp_allow_origins=localhost,127.0.0.1`; an IP address entry no longer allows hosts under it), and `Access-Control-Allow-Credentials` is sent only for an origin the allow list names other than by `*` (`web::origin::origin_credentialed_by`, in `apply_cors` and the sockets' origin check `notws::origin_allowed` for `/notws`, `/termws` and the Assist stream), so a conf on `*` gives cross-site reads without cookies only. Tests `web::origin` `a_wildcard_origin_carries_no_credentials_and_the_dev_conf_allows_only_this_machine`, `screen::tests` `redirect_json_list_security_headers_and_cors`.
- **SEC-WEB-11 (Low; reported (confirmed in code); fixed). `/health` and `/metrics` trust a loopback TCP peer.** Both routes allow a peer that is loopback or in `status-ips`, by the TCP peer, so every request the local proxy forwards is allowed. `/metrics` answers pool, queue, statement and web protection counts. Where: `crates/moqui-host/src/http.rs:957-963`, `:1679-1684`. Fix: When `client-ip-header` is believed for the peer, test the resolved client address as well as the peer. Fixed 2026-11-16 (commit b490313fb, beside SEC-CLU-01's edge rule): `/health` and `/metrics` answer only when the peer passes `status_allowed` and, when a believed `client-ip-header` names another client, that client is listed in `status-ips`; a loopback address a header names is not this machine (`http::status_request_allowed`). Test `http_tests::status_routes_check_the_client_a_proxy_names`. A monitor that probes through such a proxy must be listed in `webapp_status_ips`.
- **SEC-WEB-12 (Low; reported (confirmed in code); fixed). Second factor details: a TOTP code works more than once; code sends are not limited in the login flow.** Nothing records a TOTP step as used, so a code is accepted again for its step and the one after. Each `sendOtp` creates a new single-use row and sends an email or SMS; only the re-authentication path has the 30 second gap. Where: `crates/moqui-core/src/user/totp.rs:89-106`; `UserServices.xml:688-694`, `:772-814`. Fix: Store the last accepted TOTP step on the factor and refuse a step not after it. Apply the send gap in `send#ExternalAuthcCode`. Fixed 2026-11-16: `validate#UserAuthcFactorCode` takes an authenticator code only for a step after the factor's last one (`UserAuthcFactor.lastTotpStep`, `user::totp_code_step`), and `send#ExternalAuthcCode` refuses a second code to a factor within 30 seconds; tests `user::totp` `a_code_is_taken_for_a_step_after_the_last_one`, `framework/test/CredentialGuards.spec.js`.
- **SEC-WEB-13 (Low; reported (confirmed in code); fixed). A `session_cookie_key` set by the operator is not checked.** A value from the environment is never replaced. `CHANGEME` is valid base64 and decodes to six known bytes, and any length is accepted as the HMAC key. A forged MAC still needs a live session id (160 random bits), which is in `HttpSession`, `Visit.sessionId` and the telemetry attribute `session.id`. Where: `crates/moqui-core/src/user/session.rs:3057-3065`; `crates/moqui-core/src/context/factory.rs:1812-1816`. Fix: Refuse to start with a decoded key under 32 bytes or one ending in `CHANGEME`. Fixed 2026-11-16 (commit 68a63d939): the server does not start with a `session_cookie_key` that still ends in `CHANGEME`, is not standard base64 or decodes to under 32 bytes (`context/factory.rs` `check_session_cookie_key`, at boot and on a conf reload); the message names the property, not the value. Test `context::tests` `a_weak_session_cookie_key_stops_the_boot`.
- **SEC-WEB-14 (Low; reported (confirmed in code); fixed). An anonymous tarpit lock is everyone's.** The count key and the lock row use an empty user id for every caller with nobody signed in, so one client that passes the limit on `/Login` locks the screen for every signed-out visitor for the lock time, and can repeat it. Where: `crates/moqui-core/src/user/authz.rs:703-704`, `:753-758`. Fix: Key the anonymous count by the client address or the visitor. Fixed 2026-11-16: with nobody signed in the tarpit's count and lock are keyed by `_ANON_` and a digest of the client address (an IPv6 one by its /64; `authz.rs` `anonymous_tarpit_subject`); test `authz_tests.rs` `an_anonymous_tarpit_lock_is_the_client_addresss`.
- **SEC-WEB-81 (Low; reported (confirmed in code)). A path-scoped rate limit or path rule is passed by another path to the same transition or screen (SEC-WEB-07's fix does not cover these).** The guard matches a limit's globs against the decoded request path and against `screen_path(path)`, which only drops empty, `.` and `~` names and pops `..`. The screens reach the same transition by paths neither form matches: an extra path after the transition (`POST /r/<token>/submit/x` runs `submit`, and `/r/*/submit` does not match four segments; the same for `/call/<token>/joinGuest/x` and `/i/<token>/<step>/x`), the FOP servlet (`POST /fop/Login/login`, `/fop/rest/login`, `/fop/SecondFactor/...`, `/fop/ChangePassword/...`, and `/fop/apps/tools/...` past an operator's `deny /apps/tools/**`), a `//name` search path (`//tools/x` is `/apps/tools/x`; this passes only a rule that names a path below the root), a `ScreenPathAlias` row, which rewrites the path after the guard has run, and a render-mode extension (`POST /rest/login.<mode>`; this form is likely, not confirmed). The limits are `login`, mr-boss `request-form` and `invitation-accept`, basic-comms `call-guest`, and any `path-rule` or path limit an operator adds. The `all` limit, the `auth-failure` ban and the account lockout still apply, so for the login paths this is the residue SEC-WEB-07 recorded; for `request-form` (5 a minute) what is left is `all` (50 a second) and whatever the intake service counts itself. `/ReAuth/password` checks a password and is in no path limit. Not confirmed: which `screen-text-output` types the conf declares, whether `create#IntakeRequest`, the invitation steps and `joinGuest` have limits of their own, and who may write `ScreenPathAlias` rows. Where: `crates/moqui-host/src/guard.rs:338-344`, `:1015-1019`, `:1034-1035`; `crates/moqui-core/src/screen/public_site.rs:123-136`; `crates/moqui-core/src/screen/url.rs:272-275`, `:301-307`, `:548`, `:567-585`; `crates/moqui-core/src/screen/mod.rs:585-598`, `:739`; `crates/moqui-core/src/screen/render.rs:868`; `runtime/components/addon/mr-boss/MoquiConf.xml:30`, `:32`; `runtime/components/base/basic-comms/MoquiConf.xml:14`. Fix: Refuse extra path names after a transition that declares no `path-parameter` for them (404), and a transition through the FOP servlet. For the guard, match a limit against the path with a leading servlet prefix (`/fop`) removed and with trailing names dropped one at a time, or let a limit name a transition (screen location and name) and count it in the worker where the path is resolved. Add `/ReAuth/password` to the `login` limit.
- **SEC-WEB-82 (Low; reported (likely)). A per-host web protection rule is passed by a `Host` header with a port that is not a number.** The guard cuts a port from `Host` only when it is all digits, so `Host: shop.example:x` is `shop.example:x` to it and no `rate-limit`, `path-rule`, `user-agent-rule` or deny `client-rule` with `host="shop.example"` applies. The screens cut the header at its first colon, so the root screen and the `public-site` of `shop.example` serve the request. A stricter per-site limit or deny rule is passed by an anonymous client that comes straight to a listener (not through an edge node's forward); the rules without `host` still apply. Not confirmed: that hyper passes a `Host` value with a non-numeric port to the service on HTTP/1.1 and HTTP/2; no shipped conf has a rule with `host`. Where: `crates/moqui-host/src/guard.rs:162-173`; `crates/moqui-core/src/web/mod.rs:2532-2537`; `crates/moqui-core/src/screen/public_site.rs:196-203`; `crates/moqui-core/src/screen/info.rs:148-150`; `crates/moqui-host/src/http/serve.rs:619-627`, `:642-650`. Fix: One function for the host name of a request, used by the guard, `root_for_host` and the public-site routing; answer 400 for a `Host` whose port is not digits.
- **SEC-WEB-83 (Low; reported (confirmed in code)). Once 100,000 clients are tracked, a new client is not rate limited, banned or connection-capped.** `with_client` returns `None` for an address not in the table when `max_tracked` (`max-tracked-clients`, 100,000) entries exist; `admit` then admits the connection uncounted, `check` returns `Ok` with no rate limit applied, and `record_key` counts no event, so no ban starts. An entry stays while it has a connection, a ban, or was seen within the longest ban window (600 s by the default conf), so 100,000 addresses (an IPv4 botnet, or IPv6 /64s out of a routed /47 or larger) that each send one request every ten minutes keep the table full, and every other client, the attacker's fresh addresses included, has only the global limits. Nothing evicts an entry but the 30 second `sweep`, and only the counter `untracked` shows it. The account lockout and the tarpit still apply. Where: `crates/moqui-host/src/guard.rs:863-872`, `:935-944`, `:1029`, `:1054-1056`, `:1117`, `:1336-1345`; `runtime/components/base/framework/conf/MoquiDefaultConf.xml:915`. Fix: When the table is full, drop the entry seen longest ago that has no connection and no ban, and log once a minute while `untracked` rises. Consider counting an untracked IPv6 client under a shorter prefix (/48).
- **SEC-WEB-84 (Low; reported (confirmed in code)). With an OAuth 2 provider the recent sign-in check is met by a redirect any site can start and the provider may answer without asking.** `/sso/login` is `read-only` with `require-session-token="false"`, so `GET /sso/login?authFlowId=<an OAuth flow>&reauth=true` runs for whoever moves a signed-in browser to it: another site by a top-level navigation or a link, a person at an unattended browser, a script in the page. For an OpenID flow the callback asks for an `auth_time` after the request; for an OAuth 2 flow (`AftOauth`) there is no such proof and the callback takes `now`. A provider that already has the user's session and consent redirects straight back, so the session's `LAST_AUTH` is fresh with no credential typed, and the five-minute gate of `require#RecentAuth` (new keys and tokens, factor and code changes, the email address, Login as) is open to whatever holds the session. A stolen cookie alone does not get this: the thief's browser has no provider session. Not confirmed: which providers answer a repeated authorization without a prompt. Where: `runtime/components/base/webroot/screen/webroot/sso.xml:19-27`; `crates/moqui-core/src/service/sso.rs:309-318`, `:522-530`; `crates/moqui-core/src/user/login.rs:603-610`. Fix: Start a re-authentication only by a POST with the session token (keep the plain login a GET), and do not count an OAuth 2 round trip as a recent sign-in unless the flow's row says its provider prompts; otherwise ask for the account's password or second factor.
- **SEC-WEB-85 (Low; reported (confirmed in code)). The new-device notice is not sent for a sign-in that passes a second factor, or one made within a minute of any other login attempt on the account.** `notify#NewDeviceSignIn` runs only when a `UserLoginHistory` row with `successfulLogin` Y and a visit is created. The password step of an account with a second factor is recorded as not logged in and the step that finishes the factor (`internal_login_user`) records nothing, so such an account never gets a Y row for a password sign-in and never a notice. One row a minute is written for a user, failed or successful, so a wrong password sent first claims the minute and the right one within 60 seconds writes no row; for the same reason an account whose key or automation logs in every minute never has a free minute. `user/factor.rs` was read only by a grep for `save_history`, and `Identity.js` `clientSummary` was not read. Where: `crates/moqui-core/src/user/login.rs:158-163`, `:307-336`, `:359-364`, `:486-498`; `runtime/components/base/framework/entity/Security.eecas.xml:154-155`; `runtime/components/base/framework/service/org/moqui/admin/IdentityNewDevice.js:63-99`. Fix: Write the successful row when the second factor finishes, and keep the minute's claim apart for failed and successful logins (or let a successful login always write when the last row of the minute was a failure or from another visit).
- **SEC-WEB-86 (Low; reported (confirmed in code)). User info claims are merged into the profile without comparing the user info `sub` with the ID token's.** After the ID token is validated its claims are the profile; every user info member the ID token lacks is then added (`email`, `email_verified`, `preferred_username`, `roles`, `groups`), and these decide the username, the verified-email link and the role maps. OpenID Connect Core 5.3.2 has the client refuse a user info answer whose `sub` differs from the ID token's; here the ID token's `sub` wins silently and the other user's claims are used. It needs a provider that answers user info for another subject; none is known. Where: `crates/moqui-host/src/sso.rs:557-565`. Fix: For an OIDC flow refuse a user info answer with no `sub` or one unequal to the ID token's.

## Routes, screens and REST

- **SEC-RTE-08 (Low; reported (confirmed in code); fixed). State changes on `GET` with no token.** A `GET` is never token-checked. A `read-only` transition takes URL parameters, and a transition that is not `read-only` still runs on a `GET` with no query, its `path-parameter` values included. So these change state from a link: `/apps/setPrefGoLast?preferenceKey=..&preferenceValue=..` (any user preference; `mantle.content.root` is the default root of `/resources`), `/Login/logout`, `/rest/logout`, `/sso/logout`, `/Login/removePreAuth`, and any application transition without `method="post"` that takes only path parameters. Where: `crates/moqui-core/src/screen/render.rs:2667` (`csrf_rejected`), `:2070` (`insecure_transition`). Fix: Refuse a `GET` for a transition that is not `read-only` and has actions; make `setPrefGoLast` and the logouts `POST`. Partly fixed 2026-11-16 with SEC-WEB-04: a GET another site started is refused for a transition that runs actions and is not `read-only` (`/Login/logout`, `/rest/logout`, `/Login/removePreAuth`, path-parameter transitions); the `read-only` ones (`setPrefGoLast`, `/sso/logout`, SEC-ADM-09) still change state on such a GET. Fixed 2026-11-16 (rest): `apps/setPrefGoLast` is `method="post"`, `/sso/logout` is neither `read-only` nor without the session token (a cross-site GET is 403), and Tools' and Marble's `createFieldDynamic` are not `read-only`: the field tree sends it as a POST with the token (`screen/tree.rs` `loadMethod` "post", qvt `loadContainer`, html `postThenLoad`), and a GET with its parameters in the URL is refused. Tests `forms.rs` `a_tree_link_that_loads_through_a_writing_transition_is_a_post`, `SecurityScreens.spec.js` "a GET of sso/logout, setPrefGoLast or createFieldDynamic changes nothing". The terminal client posts such a tree link too (`moqui-tui` `follow_tree_row`; test `a_tree_link_that_changes_data_is_posted_with_its_parameters`).
- **SEC-RTE-09 (Low; reported (confirmed in code); fixed). `lastStandalone` takes the parents out of the user check.** A screen marked `require-authentication="false"` or `anonymous-*` under a parent that requires a user is reachable with no user, and so are its transitions, which then need no authorization record. The always-actions of every parent still run. In the base and dev components the only such screen is `ScreenTreeNested`, whose actions fail without `ScreenTree`'s; an application screen written on the assumption that its parent protects it has no such luck. Where: `crates/moqui-core/src/screen/url.rs:373`; `crates/moqui-core/src/screen/render.rs:1513`. Fix: Check authentication against every screen of the path (`path_defs`), as the transition path already pushes them all, and keep `render_defs` for what is drawn. Fixed 2026-11-16 (commits 19ae280ce, 94ae325b4): `check_authentication` and the login redirect ask `path_requires_authentication` of every screen of the path, so a screen under a parent that requires a user needs one as a `lastStandalone` fragment and for its transitions (`ScreenTreeNested` now needs a user); a parent's `allow-web-request="false"` refuses a fragment below it (`check_web_settings` reads `path_defs`), and a device's route check exempts a file only when no screen of the whole path needs a user (`device.rs` `check_route`). Tests `a_screen_under_a_parent_that_needs_a_user_needs_one_as_a_fragment`, `a_parent_that_allows_no_web_request_refuses_a_fragment_below_it`, `a_file_below_a_parent_that_needs_a_user_is_in_the_device_route_check`. The `require-encryption` redirect to https still reads the rendered screens only.
- **SEC-RTE-10 (Low; reported (to check); fixed). `/health` and `/metrics` trust the TCP peer.** Both routes allow any loopback peer and do not use the client address a trusted proxy names. The map says the server is meant to run behind a proxy; with the proxy on the same host every request has a loopback peer, so `/metrics` (pool, guard, telemetry counters, Prometheus text) and `/health` answer the internet unless the proxy blocks the two paths. `/status` uses the proxy-named client and does not have this. Where: `crates/moqui-host/src/http.rs:957`, `:977`, `:1679`. Fix: When `trusted-proxies` names the peer, decide by the resolved client address, as `/status` does; say so in the map row either way. Fixed 2026-11-16 with SEC-WEB-11 (commit b490313fb), of which this is a second report: `/health` and `/metrics` answer only when the peer passes `status_allowed` and, when a believed `client-ip-header` names another client, that client is listed in `status-ips` (`http::status_request_allowed`). Test `http_tests::status_routes_check_the_client_a_proxy_names`. Checked against the code 2026-11-17.
- **SEC-RTE-11 (Low; reported (likely)). A restricted host still serves some framework paths.** The refusal is by the reserved first-segment list. The token routes `i` (staff invitation) and `call` are not in it and are dispatched before the site's own routing, so they run on the restricted host. Where the site has no mount at `/`, the root transitions (`/menuData`, `/shellData`, `/resources`, `/find/rank`, `/email/..`) and a `//name` search path (`//tools` is `/apps/tools`) also reach the framework there; a request with a key or Basic header is signed in for them. The map says nobody reaches the apps or the token routes on such a host. Where: `crates/moqui-core/src/screen/public_site.rs:96`-`102`; `crates/moqui-core/src/web/reserved.rs:114`. Fix: On a restricted host refuse every path the site's own mounts do not take (and every token route), instead of refusing a list.
