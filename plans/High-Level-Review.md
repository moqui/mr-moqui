## Pass 1. Data and storage

The list path enters entity authorization, checks the cache and sim overlay, then executes a SQL plan and decodes rows. Writes invalidate caches immediately and again at frame end to cover intervening readers. Feed keys are registered before commit, and pending delivery is scheduled afterward. XML, JSON arrays and CSV already read data incrementally, and the PostgreSQL loader batches compatible upserts. Keep the datasource and transaction boundaries and the two feed phases. Cached read contention and nested XML load costs already have follow-ups in Profiling. [Entity find](../crates/moqui-entity/src/entity/find.rs#L299), [transaction commit](../crates/moqui-entity/src/transaction/manager.rs#L1415), [feed hooks](../crates/moqui-entity/src/entity/load_feed/feed.rs#L197), [load buffer](../crates/moqui-entity/src/entity/load_feed/pull.rs#L152), [PostgreSQL batching](../crates/moqui-drivers/src/postgres.rs#L571), [Profiling follow-ups](Profiling.md#next-steps).

#### HL-001. Index child matching during DataDocument assembly

**High · Supported by source.** A feed rebuild pages by primary key and queries a joined view for each page. Page size limits primary records, while related rows can still multiply within a page. For each joined row, assembly linearly searches each type-many child list using the child's direct projected fields. One parent with N distinct children can take O(N²) child comparisons, and sibling to-many joins can further multiply input rows. The same assembler serves document export and delivery by ID. Start with an assembly-local index for each parent and relationship keyed by the existing field equality, retaining insertion order, missing/null equivalence, and the current treatment of expression fields. Keep the SQL shape initially. Compare joined rows, comparisons, assembly time and peak memory for one large child list and for two sibling lists before considering separate relation fetches. [Feed rebuild](../crates/moqui-core/src/search/feed.rs#L575), [document paging and view query](../crates/moqui-entity/src/entity/document.rs#L405), [child merge](../crates/moqui-entity/src/entity/document.rs#L995).

#### HL-002. Batch entity cache invalidation at frame end

**High · Needs measurement.** A write sweeps its entity's cached lists. For updates and deletes it can scan the rows in each list for the primary key. Frame end can repeat that sweep per retained write until the existing threshold switches to a whole-cache clear. The cost can grow with both writes per frame and cached query variants, even when few cached lists contain the written rows. Compare the current strategy with a single sweep per entity that reuses a set of changed keys, or with an earlier whole-cache clear when selective eviction costs more than warming the cache. Preserve immediate invalidation, the frame-end pass for intervening readers, and conservative matching for incomplete values and views. Measure write and commit latency, entries and rows inspected, and subsequent cache miss rates in a mixed workload. This is distinct from Profiling's existing cached-read lock work. [Write hooks](../crates/moqui-entity/src/entity/cache.rs#L1002), [frame replay](../crates/moqui-entity/src/entity/cache.rs#L622), [eviction and matching](../crates/moqui-entity/src/entity/cache.rs#L677), [cache removal](../crates/moqui-lib/src/cache.rs#L449).

#### HL-003. Make bounded iteration an explicit driver capability

**Medium · Needs measurement.** Entity iteration opens the same driver stream API across targets. PostgreSQL fetches through a cursor and MySQL reads from an active result. Browser SQLite gathers all matching rows before returning the first one, so an early stop still pays for the entire result. First measure an uncached browser export or iterator consumer over growing data sets, including a consumer that reads only the first few rows. Compare time to first row and peak worker memory. If material, expose or document the buffering distinction and evaluate bounded SQLite iteration that preserves the statement lifetime, ordering and snapshot contract. The cached and sim-view paths intentionally use memory as well. [Entity iterator](../crates/moqui-entity/src/entity/find.rs#L553), [PostgreSQL cursor](../crates/moqui-drivers/src/postgres.rs#L640), [MySQL stream](../crates/moqui-drivers/src/mysql.rs#L391), [browser SQLite stream](../crates/moqui-browser/src/sqlite.rs#L208).

#### HL-006. Give async request adapters one completion path

**High · Supported by source.** The common host worker adapter and the notification socket adapter each start a Tokio blocking task that waits on a synchronous reply from a framework worker. The blocking task is occupied for queue wait plus execution. The bounded framework queue is reached only once that task runs. Screen HTTP, DAV, and MCP instead allocate an async oneshot inside each handler and pass a separate synchronous result through the same pool. Screen HTTP has queue-age, abandonment and overload handling that the simpler adapters do not share. Expose a completion hook at the pool boundary and use it from one host async adapter. Keep job context setup and completion after cleanup in the synchronous pool. Preserve each protocol's deadlines, auth-failure accounting, and treatment of started writes when a caller disconnects. Start with the two waiting adapters, then migrate HTTP adapters when their policies can be expressed explicitly. Under mixed HTTP and protocol traffic, compare blocking threads occupied, queue wait, overload response and shutdown completion. #### HL-008. Isolate SFU packet work to the peers it affects

**High · Supported by source.** A UDP or TCP media packet reaches `Sfu::handle_receive`, which searches peers on the whole media node for an RTC session that accepts it. Each accepted packet then calls `drive`, which polls every peer and scans for dead peers on each propagation pass, even across unrelated rooms. This adds O(P) node-wide work per accepted packet for P peers before necessary room fan-out. First instrument peer polls and accept checks with increasing numbers of independent rooms at fixed per-room traffic. Use CPU per packet, output latency and packet loss to size the work. If the poll cost dominates, drive peers with pending work and track their deadlines. Treat transport demultiplexing as a separate change and keep RTC's acceptance check authoritative during ICE migration and relay changes. Preserve per-peer ordering, timers, and generation fences. [Host media driver](../crates/moqui-host/src/rtc/driver.rs#L133), [SFU receive and timeout](../crates/moqui-rtc/src/sfu/mod.rs#L752), [all-peer drive](../crates/moqui-rtc/src/sfu/mod.rs#L899), [room fan-out](../crates/moqui-rtc/src/sfu/mod.rs#L930).

#### HL-009. Route targeted pushes through user indexes

**Medium · Supported by source.** Notification WebSocket fan-out snapshots all S sockets and linearly tests the recipient list of size U for each one, O(S × U) in the worst case. XMPP uses a recipient set and still scans every registered session. Both have user-specific presence or lookup operations that also scan. Start with a user-to-connection index in the WebSocket registry and retain the ID lookup for direct call signaling. Apply the same indexing approach to XMPP if warranted, keeping topic filtering, per-session queues, overflow closure and stream resumption with their existing owners. Measure registry work and enqueue latency with many idle connections and small recipient lists, then with a large broadcast. [WebSocket fan-out](../crates/moqui-host/src/notws.rs#L597), [direct and presence lookup](../crates/moqui-host/src/notws.rs#L530), [XMPP registry](../crates/moqui-xmpp/src/registry.rs#L82).

#### HL-010. Put drive file service calls behind one adapter

**Medium · Supported by source.** WebDAV and the SFTP-facing tree already share drive lookup and some metadata helpers. Both still call the same resource-info service, open storage under a scoped authorization bypass after the access check, and translate uploads through the same upload service and result shape. Extract the authorized open and upload operations into the existing drive adapter. Keep WebDAV lock tokens, conditional requests, range responses and SFTP handle semantics in their callers. A shared open operation gives a later range or streaming change a common place to use a byte source, since WebDAV currently reads the whole file before slicing a range. Verify access denial and version creation on both paths before changing transfer behavior. [WebDAV read and range](../crates/moqui-dav/src/dav/files.rs#L405), [WebDAV upload](../crates/moqui-dav/src/dav/files.rs#L520), [SFTP tree read and upload](../crates/moqui-dav/src/dav/files.rs#L861), [host SFTP adapter](../crates/moqui-host/src/ssh/sftp_fs.rs#L18).

#### HL-011. Bound mailbox import by a message window

**Medium · Supported by source.** Import reads a resource as a byte vector, collects an mbox into separate message buffers, and loads every existing message ID in the destination folder before processing any new messages. Working memory grows with archive bytes and existing folder size, even for a small import into a large folder. Start by iterating the mbox parser over the source without collecting messages. Then use a reader where the resource supports it and check IDs in bounded batches, retaining duplicate handling within the import and independent per-message commits. Measure peak resident memory, time to first stored message and database queries as archive size and pre-existing folder size vary independently. [Resource read and mbox split](../crates/moqui-mail/src/import.rs#L70), [folder dedupe and import loop](../crates/moqui-mail/src/import.rs#L183).

## Pass 7. Independent review of coherence, deadlines and shared runtime work

This targeted pass followed interactions between subsystems where a local optimization or concurrency limit can change another subsystem's guarantees. The findings below distinguish source-established behavior from impact that still requires measurement.

#### HL-017. Preserve invalidation coverage when coalescing

**High · Supported by source.** When one outgoing cluster batch contains writes to distinct rows of an entity, coalescing keeps only the first invalidation, including its primary key. The receiver passes that key to selective cache eviction. A batch changing rows A and B can therefore invalidate A while leaving a cached lookup for B stale indefinitely, until some separate eviction or invalidation happens to remove it. The existing batching test counts deliveries; it does not establish remote cache freshness. This is a correctness issue distinct from the local invalidation cost in HL-002. [Batch coalescing](../crates/moqui-core/src/cluster/mod.rs#L724), [remote application](../crates/moqui-core/src/cluster/mod.rs#L279), [selective eviction](../crates/moqui-entity/src/entity/cache.rs#L1029), [batching test](../crates/moqui-core/src/cluster/tests.rs#L658).

Start by preserving every affected key or promoting a combined message to whole-entity invalidation, which the receiver already supports when no usable key is supplied. Preserve publication after commit. Verify with two distinct cached keys changed in one batch and assert both remote reads are fresh, including a previously cached missing row that is then inserted. A deterministic coalescing and receiver test should check coverage, not just reduced message counts.

#### HL-018. Recover cache coherence after lost cluster messages

**High · Supported by source.** A full outgoing queue drops new messages. Exhausted delivery retries discard the batch, and subsequent batches skip peers during backoff without retaining a reconciliation obligation. Entity list and count caches have no expiry, so a missed invalidation can leave a peer stale after connectivity returns; later writes to unrelated keys do not guarantee repair, and there may be no later write. PostgreSQL LISTEN reconnect already clears entity caches, but that transport-specific recovery does not cover every gap in the common sender, including overflow while the listener stays connected. [Queue overflow and peer skipping](../crates/moqui-core/src/cluster/mod.rs#L617), [retry exhaustion](../crates/moqui-core/src/cluster/mod.rs#L843), [cache configuration](../crates/moqui-entity/src/entity/cache.rs#L2211), [LISTEN reconnect recovery](../crates/moqui-host/src/cluster_notify.rs#L268).

Start with a bounded recovery mechanism that records delivery gaps, such as a dirty-peer or generation marker, and forces conservative invalidation before treating that peer as synchronized. The recovery obligation must survive the failed delivery and must not require another entity write to trigger it. Define this guarantee specifically for cache invalidations rather than assuming all cluster topics have the same delivery contract. Verify overflow, exhausted retries and writes during peer backoff, then restore delivery without another write and check remote cache freshness.

#### HL-019. Keep blocking network operations off the deadline timer

**High · Supported by source.** The single transaction deadline thread collects due cancellations and invokes each synchronously. PostgreSQL cancellation opens a separate connection; TCP connection establishment, TLS negotiation and cancellation I/O have no application deadline on this path. One stalled cancellation can delay the other cancellations already due and every subsequent timer pass. Pool acquisition timeouts also govern waiting for a returned connection, not the connection establishment branch. Database statement timeouts do not bound these transport operations. [Deadline thread and dispatch](../crates/moqui-entity/src/transaction/manager.rs#L1540), [synchronous cancellation loop](../crates/moqui-entity/src/transaction/manager.rs#L1590), [connection setup](../crates/moqui-drivers/src/pgwire.rs#L196), [TLS negotiation](../crates/moqui-drivers/src/pgwire.rs#L321), [cancellation](../crates/moqui-drivers/src/pgwire.rs#L1138), [pool connection acquisition](../crates/moqui-entity/src/transaction/pool.rs#L410).

Start by bounding driver connection, handshake and cancellation operations and isolating cancellation dispatch from the timer with bounded execution capacity. Preserve rollback, connection-discard and database timeout behavior. Verify a stalled cancellation alongside an independent expiring transaction: the second cancellation and later timer passes must still proceed. Separately exercise a connection that accepts TCP but stalls during handshake, checking that connection and cancellation attempts finish within their application deadlines.

#### HL-020. Separate cluster heartbeats from workload-sized maintenance

**Medium · Supported by source.** Scheduled-job discovery and maintenance hooks run sequentially on one scheduler thread. Discovery reads the entire job list and performs per-job readiness queries before checking whether execution slots remain. Session flushing also runs as a maintenance hook. A large job set, slow readiness queries or many dirty sessions can delay the cluster heartbeat hook beyond the three-interval liveness window, allowing a healthy but busy member to appear unavailable. The scheduling dependency is established by source; its frequency and impact under load remain unmeasured. [Scheduler](../crates/moqui-core/src/service/schedule.rs#L36), [job discovery and capacity check](../crates/moqui-core/src/service/jobs.rs#L138), [readiness queries](../crates/moqui-core/src/service/jobs.rs#L219), [session hook registration](../crates/moqui-core/src/context/factory.rs#L1439), [session flushing](../crates/moqui-core/src/user/session.rs#L475), [liveness window and heartbeat hook](../crates/moqui-core/src/cluster/mod.rs#L547).

Start by scheduling heartbeats independently and making maintenance passes bounded and resumable. Preserve job priority, locking and failure isolation between independent jobs or sessions. Verify a saturated job queue with many dirty sessions while checking that heartbeats continue on schedule. Measure job-count growth, readiness query counts, maintenance duration and heartbeat delay; use controlled blocking hooks or a test clock for a small deterministic regression proof.

#### HL-021. Make run-event delivery proportional to interested streams

**Medium · Supported by source.** Each published LLM run event notifies all hub waiters, including streams following unrelated runs. Each awakened waiter scans its retained ring under the same hub mutex, and matching event payloads are cloned while holding that mutex. Work can approach O(waiters × retained events) per notification even when only one run is active. The bounded ring limits retained history but does not remove work caused by unrelated watchers. This is separate from sharing the surrounding stream lifecycle in HL-014. [Hub publication and reads](../crates/moqui-llm/src/run/hub.rs#L125), [gap-recovering follower](../crates/moqui-llm/src/run/hub.rs#L275).

Start with per-run wakeups and cursor-based access to the unread ring suffix, reducing the work performed under the shared registry lock. Preserve replay ordering, live-only events, ring wrap and stored gap recovery. Verify one active run among many unrelated stream watchers, then force ring wrap and a replay gap. Count awakened waiters and inspected events and measure lock hold time and delivery latency before claiming an improvement.

#### HL-022. Include database transfers in connection admission budgeting

**Medium · Supported by source.** Startup validates ordinary connection capacity against request and service workers and leaves the remaining allowance for agent work. Streamed database downloads independently admit up to 16 readers by default. Those readers perform database reads using the same ordinary connection capacity outside the request worker budget. A configuration can therefore pass startup validation while admitted transfers, request transactions and agent work together exceed the concurrency allowance that validation intends to protect. The transfer limit and short reads bound part of the demand, but neither accounts for it in the shared budget; actual pool waits and timeout frequency remain workload-dependent. [Transfer admission and reads](../crates/moqui-host/src/source_body.rs#L29), [startup capacity calculation](../crates/moqui-core/src/service/request_pool.rs#L174), [agent capacity](../crates/moqui-llm/src/run/pool.rs#L36), [database chunk reads](../crates/moqui-entity/src/resource/blob.rs#L260).

Start by including database transfer demand in the shared capacity model for the default and linked pools it can use. Preserve streaming backpressure, short connection lifetimes and reserved capacity. Verify concurrent database downloads, request transactions and agent work near pool capacity; record ordinary connection high-water marks, pool waits, request latency and reserve availability. Include slow download consumers so the test also checks that backpressure does not turn into long-held database connections.

## Verification follow-ups

The independent review and its planning stage were read-only; no files were changed in Plan Mode. Consolidation changes only this document. No benchmarks or test suites were run. The scenarios above are proposed follow-up proofs, not reported test results.

Use small deterministic regression tests for invalidation coverage and recovery, independent deadline progress, heartbeat progress, and event ordering across ring wrap and replay gaps. Sustained load, prolonged delivery failures and combined download/request/agent saturation belong in opt-in acceptance tests. Follow the repository's [testing rules](../docs/Build-Test.md#the-two-suites): run acceptance tests only when requested or when adding or changing them, and keep regression tests within their existing budgets. Measure representative workloads before claiming any performance improvement.
