#### HL-001. Index child matching during DataDocument assembly

**Status: fixed** in `69663eca` (assembly-local hash index per to-many list; same equality, null handling and order; SQL unchanged). Opt-in timing: 8,000 children 41 ms against 8.3 s.

**High · Supported by source.** A feed rebuild pages by primary key and queries a joined view for each page. Page size limits primary records, while related rows can still multiply within a page. For each joined row, assembly linearly searches each type-many child list using the child's direct projected fields. One parent with N distinct children can take O(N²) child comparisons, and sibling to-many joins can further multiply input rows. The same assembler serves document export and delivery by ID. Start with an assembly-local index for each parent and relationship keyed by the existing field equality, retaining insertion order, missing/null equivalence, and the current treatment of expression fields. Keep the SQL shape initially. Compare joined rows, comparisons, assembly time and peak memory for one large child list and for two sibling lists before considering separate relation fetches. [Feed rebuild](../crates/moqui-core/src/search/feed.rs#L575), [document paging and view query](../crates/moqui-entity/src/entity/document.rs#L405), [child merge](../crates/moqui-entity/src/entity/document.rs#L995).

#### HL-002. Batch entity cache invalidation at frame end

**Status: partly fixed** in `41262597` (same-type key comparison without strings; opt-in measurement `eviction_sweep_cost_per_write_and_per_entity`: at 200 lists × 50 rows and 200 writes, per-write sweeps inspect 2.0M rows with 220 ms lock held per pass, one sweep per entity 10k rows and 8 ms). One frame-end sweep per entity in `5621f748` (at 200 lists × 20 rows and 200 writes, cache overhead 400 → 103 ms).

**Medium · Needs measurement.** A write sweeps its entity's cached lists. For updates and deletes it can scan the rows in each list for the primary key. Frame end can repeat that sweep per retained write until the existing threshold switches to a whole-cache clear. The cost can grow with both writes per frame and cached query variants, even when few cached lists contain the written rows. Each sweep holds the cache's write lock, so cached reads of the entity wait while it runs, and comparing a cached row's key with the written one falls back to converting both values to strings: two allocations for each row that does not match. Compare the current strategy with a single sweep per entity that reuses a set of changed keys, or with an earlier whole-cache clear when selective eviction costs more than warming the cache. Preserve immediate invalidation, the frame-end pass for intervening readers, and conservative matching for incomplete values and views. Measure write and commit latency, entries and rows inspected, lock hold time, and subsequent cache miss rates in a mixed workload. This is distinct from Profiling's existing cached-read lock work. HL-023 changes the same eviction code; make this change after it. [Write hooks](../crates/moqui-entity/src/entity/cache.rs#L1002), [frame replay](../crates/moqui-entity/src/entity/cache.rs#L622), [eviction and matching](../crates/moqui-entity/src/entity/cache.rs#L677), [key comparison](../crates/moqui-entity/src/entity/cache.rs#L719), [cache removal](../crates/moqui-lib/src/cache.rs#L449).

#### HL-003. Make bounded iteration an explicit driver capability

**Status: fixed** for correctness in `fa47c908` (the iterator begins its own transaction, records its frame token, and the pool discards a connection returned with an open stream; buffering documented). Bounded SQLite iteration deferred: native measurement shows about 400 B per row buffered and the first row at about 80% of a full read.

**Medium · Needs measurement.** Entity iteration opens the same driver stream API across targets. PostgreSQL fetches through a cursor and MySQL reads from an active result. Browser SQLite gathers all matching rows before returning the first one, so an early stop still pays for the entire result. The SQLite driver documents this, but the shared stream contract and the iterator's documentation do not. Every production iterator caller reads to the end, and export keeps all rows when dependents exist, so peak memory on a full read matters more than time to first row. First measure an uncached browser export or iterator consumer over growing data sets, and compare peak worker memory and time to first row. If material, document the buffering in the shared contract and evaluate bounded SQLite iteration. Every logical SQLite connection shares one handle, so a statement kept open across `next_row` would coexist with sequence refills and savepoints on that handle, and a rollback drops the stream; bounded iteration has to preserve ordering and the snapshot under those writes. The cached and sim-view paths intentionally use memory as well. [Entity iterator](../crates/moqui-entity/src/entity/find.rs#L552), [stream contract](../crates/moqui-entity/src/driver.rs#L88), [PostgreSQL cursor](../crates/moqui-drivers/src/postgres.rs#L640), [MySQL stream](../crates/moqui-drivers/src/mysql.rs#L391), [browser SQLite stream](../crates/moqui-browser/src/sqlite.rs#L208), [SQLite buffering note](../crates/moqui-browser/src/sqlite.rs#L31).

The iterator also opens its stream without requiring a transaction, although its documentation says it needs one. Outside a transaction the connection goes back to the pool while the iterator still reads from it. PostgreSQL refuses such a stream; MySQL opens it, and the pool does not check for an open stream, so later borrowers fail and the iterator can end early. The iterator keeps no frame token, so closing a stale one closes the current transaction's cursor. Current callers open a transaction first, so this is latent. Have `iterator()` begin a transaction when none is in place or require one, record the frame token, and discard a connection that comes back with an open stream.

#### HL-006. Give async request adapters one completion path

**Status: fixed** for the common worker and notification adapters in `2453fa42` (`RequestPool::try_submit_then` completion hook; no blocking task waits). Screen HTTP, DAV and MCP moved in `1d9821ef` to one admission path (`http/admission.rs`) with shared overload, queue-age and abandonment checks.

**High · Supported by source.** The common host worker adapter and the notification socket adapter each start a Tokio blocking task that waits on a synchronous reply from a framework worker. The blocking task is occupied for queue wait plus execution. The bounded framework queue is reached only once that task runs. The common adapter has 61 call sites across SSH, SMTP, XMPP and the edge link, and the host does not size Tokio's blocking pool, so its default of 512 threads is what bounds these waits. Screen HTTP, DAV, and MCP instead allocate an async oneshot inside each handler and pass a separate synchronous result through the same pool. Screen HTTP has queue-age, abandonment and overload handling that the simpler adapters, DAV and MCP included, do not share. Expose a completion hook at the pool boundary and use it from one host async adapter. Keep job context setup and completion after cleanup in the synchronous pool. The common adapter holds the factory weakly so that a stopped server's database clients are never dropped on a runtime thread; submitting from async code must keep that. Preserve each protocol's deadlines, auth-failure accounting, and treatment of started writes when a caller disconnects. Start with the two waiting adapters, then migrate HTTP adapters when their policies can be expressed explicitly. Under mixed HTTP and protocol traffic, compare blocking threads occupied, queue wait, overload response and shutdown completion. [Pool admission and completion](../crates/moqui-core/src/service/request_pool.rs#L101), [common worker adapter](../crates/moqui-host/src/worker.rs#L15), [notification worker adapter](../crates/moqui-host/src/notws.rs#L576), [screen HTTP admission](../crates/moqui-host/src/http.rs#L898), [DAV adapter](../crates/moqui-host/src/dav_http.rs#L83), [MCP adapter](../crates/moqui-host/src/llm/mcp.rs#L88).

#### HL-007. Share remote login and OTP protocol code

**Status: fixed** in `bce52ed5` (shared `moqui-lib` `remote_login` for the TUI and desktop client; one empty-key refusal; the TUI sends a device name, so its key is listed and lasts the device expiry; jittered `reconnect::Backoff` for both socket loops).

**Low · Supported by source.** The remote TUI and desktop client implement the same login-key and second-factor handshake. Both post credentials, decode challenge fields and replay the pre-authentication cookie and CSRF token to request an OTP. Changes to this server contract require edits in both, and the challenge types exist in three copies (moqui-tui, moqui-client and the host's TUI link), about 100 duplicated lines. moqui-host does not depend on moqui-client, which brings rusqlite and the platform certificate verifier, so put a small shared protocol layer in a crate both already use, with a caller-supplied HTTP client and optional device name. Resolve the differences first: the client rejects a sign-in with an empty key and the TUI falls through to a generic reason; the TUI sends no device name; the client's decoding is tested and the TUI's sign-in is not. Preserve TUI key storage and errors, desktop device registration, and each caller's TLS policy. #### HL-017. Preserve invalidation coverage when coalescing

**Status: fixed** in `cde425ae` (invalidations joined at enqueue with every key, whole entity past 100 keys; own bound of 2,000 entities collapsing to a clear-all; never-cached entities not posted).

**High · Supported by source.** When one outgoing cluster batch contains writes to distinct rows of an entity, coalescing keeps only the first invalidation, including its primary key. The receiver passes that key to selective cache eviction. A batch changing rows A and B can therefore invalidate A while leaving a cached lookup for B stale indefinitely, until some separate eviction or invalidation happens to remove it. The existing batching test asserts that 200 distinct writes reach a peer as one or two posts; it does not establish remote cache freshness. #### HL-019. Keep blocking network operations off the deadline timer

**Status: fixed** in `fd5aa01d` and `6861e313` (cancel workers off the timer with panic guards; a connection whose canceller was taken is closed; connect/handshake/cancel deadlines; Postgres read deadline from remaining time plus 15 s; keepalive; MySQL `read-timeout` datasource setting, default 600 s). Checked against MySQL 8.4 and MariaDB 11.4 behind a relay that stops forwarding (`mysql/driver/network_tests.rs`), which found a read past the read timeout waiting a second time on a ROLLBACK over the dead connection, now fixed; keepalive against a silent host is not checked: [MySQL issues](archive/MySQL-Issues.md).

**High · Supported by source.** The single transaction deadline thread collects due cancellations and invokes each synchronously. PostgreSQL cancellation opens a separate connection; TCP connection establishment, TLS negotiation and cancellation I/O have no application deadline on this path. One stalled cancellation can delay the other cancellations already due and every subsequent timer pass. Pool acquisition timeouts also govern waiting for a returned connection, not the connection establishment branch. Database statement timeouts do not bound these transport operations. [Deadline thread and dispatch](../crates/moqui-entity/src/transaction/manager.rs#L1540), [synchronous cancellation loop](../crates/moqui-entity/src/transaction/manager.rs#L1590), [connection setup](../crates/moqui-drivers/src/pgwire.rs#L196), [TLS negotiation](../crates/moqui-drivers/src/pgwire.rs#L321), [cancellation](../crates/moqui-drivers/src/pgwire.rs#L1138), [pool connection acquisition](../crates/moqui-entity/src/transaction/pool.rs#L410).

Statement reads on an ordinary connection have no client read deadline either, and nothing in the drivers sets TCP keepalive. When the database host stops answering without a reset, the worker waits until the kernel gives up, and the cancel, a new connection to the same host, cannot reach it. MySQL is the same: its connection options set no connect, read, write or keepalive timeout, and its cancel opens a fully authenticated connection before sending `KILL QUERY`. A cancel can also reach the wrong statement. The timer takes the canceller out of its slot before connecting; meanwhile the owner can roll back, remove the slot and return the connection, and the idle list is last-in first-out, so the next borrower gets it and the late cancel kills that borrower's statement. Nothing discards a connection whose canceller was taken. The timer thread also has no panic guard and is started once, so a panic in a driver's cancel would end deadline enforcement for the process. [MySQL options](../crates/moqui-drivers/src/mysql.rs#L52), [MySQL cancel](../crates/moqui-drivers/src/mysql.rs#L468), [slot removed before return](../crates/moqui-entity/src/transaction/manager.rs#L793), [last-in first-out idle list](../crates/moqui-entity/src/transaction/pool.rs#L720).

Start by bounding driver connection, handshake and cancellation operations and isolating cancellation dispatch from the timer with bounded execution capacity. Moving cancellation off the timer widens the wrong-statement window, so in the same change discard, or wait for, a connection whose canceller was taken. Give statement reads a deadline from the transaction's remaining time plus a margin, and enable keepalive on both drivers. Preserve rollback, connection-discard and database timeout behavior, and the single-threaded path, which starts no timer thread. Verify a stalled cancellation alongside an independent expiring transaction: the second cancellation and later timer passes must still proceed. Separately exercise a connection that accepts TCP but stalls during handshake, checking that connection and cancellation attempts finish within their application deadlines, and a one-connection pool where a late cancel must not reach the next borrower's statement.

After ten windows (30 minutes) peers delete its row, and the heartbeat is an update that ignores a zero row count, so the member never rejoins until it restarts. The scheduling dependency is established by source; its frequency and impact under load remain unmeasured. #### HL-023. Fence entity cache stores against concurrent commits

**Status: fixed** in `156dce1d` (per-entity store fence; replica and snapshot-read frames not stored). Open: the opt-in revocation-under-load acceptance test.

**High · Supported by source.** A cached find or count runs its query, then stores the rows with a plain put that replaces whatever is there; nothing records whether the entity was written meanwhile. [TURN accept](../crates/moqui-host/src/rtc/turn.rs#L443), [ICE-TCP cap](../crates/moqui-host/src/rtc/tcp.rs#L61), [defaults](../runtime/base-component/framework/conf/MoquiDefaultConf.xml#L233).

Start with a total and per-/64 cap in TURN, handshake and idle deadlines, and bounded output that closes on overflow. For SIP, accept TLS in moqui-sip, or patch rsipstack, with a handshake deadline, counting connections before the handshake. Keep allocation lifetimes and the registrar's cleanup when a connection closes. Verify that idle connections to each port close by the deadline and that one over the per-source cap is refused.

#### HL-032. Give pre-auth pools a per-source share

**Status: fixed** in `24a95de5` (per-/64 `SourceSlots` in moqui-lib for the cluster listener with reserved member slots, SSH, XMPP, edge pairing and ICE-TCP).

**Medium · Supported by source.** The cluster listener, on all addresses by default, takes one of 64 global slots before the mutual-TLS handshake and holds it for up to 10 seconds, so about six connections a second from one source keep it full; peer posts are then refused and go into HL-018's retry-and-discard path, so delivery gaps can be caused from outside. SSH has 16 global pre-authentication slots held for 30 seconds with no per-source share, and SFTP, Git, edge tunnels and the SSH cluster transport all share them. XMPP's 20-per-source cap keys the raw address, while the web guard, SMTP, SIP and XMPP's own sign-in block group IPv6 by /64, so one host on a /64 can fill all 10,000 XMPP connections from 500 addresses. The edge pairing-attempt map uses the raw address too and rescans the whole map on every call, and ICE-TCP's cap has no per-source share. [Cluster slots](../crates/moqui-host/src/cluster_edge/listen.rs#L163), [handshake under a slot](../crates/moqui-host/src/cluster_edge/listen.rs#L204), [SSH slots](../crates/moqui-host/src/ssh/server.rs#L67), [XMPP per-source cap](../crates/moqui-host/src/xmpp/mod.rs#L54), [/64 key](../crates/moqui-host/src/guard.rs#L545), [edge pairing attempts](../crates/moqui-host/src/edge_link/accept.rs#L597).

Start with per-source pre-auth caps keyed by /64, treating IPv4-mapped addresses as IPv4, and reserve slots for, or allow before the handshake, the addresses of `ClusterMember` rows. Keep mutual TLS, sender retries and the client addresses edge tunnels pass on. Verify by holding every slot from one address, then checking that a peer post and an SSH key login from another address still succeed, and that the 21st XMPP address in one /64 is refused.

#### HL-028. Commit the mail send claim before the SMTP session

**Status: fixed** in `e03bda0b` (claim committed, SMTP outside a transaction with a 120 s session limit, result recorded against the claim; "send now" is deferred to after commit; per-run budget). Open: messages created and sent in one transaction (rule forwards, out-of-office) keep the one-transaction path.

**High · Supported by source.** `deliver#DraftMessage` claims a message, sends it and records the result in one transaction, and the mail client's Sent status is written inside it too. The SMTP session has only the library's per-command timeouts and a retry, with no overall limit, while the transaction has the 60-second default deadline. A send slower than that, or any failure recording the result after the server accepted the message, delivers the mail and then rolls the claim back: a scheduled or undo-held message is scheduled again with a past date, and `send#DueDrafts` sends it again on its next one-minute run, and the next. `fail#StoppedSend` cannot catch this, because the claim it looks for never committed. The job also works through every account one message at a time, holding a pooled connection and the row lock during each session, so one unreachable server delays every account's scheduled mail. The chat bridge already does this right: it commits its lease before calling the provider. [Claim, send and record](../runtime/base-component/framework/service/org/moqui/impl/EmailClientServices.xml#L3529), [due drafts](../runtime/base-component/framework/service/org/moqui/impl/EmailClientServices.xml#L3635), [stopped sends](../runtime/base-component/framework/service/org/moqui/impl/EmailClientServices.xml#L3609), [Sent status in the transaction](../crates/moqui-mail/src/implementation.rs#L232), [SMTP retry](../crates/moqui-mail/src/implementation.rs#L1458), [default deadline](../crates/moqui-entity/src/transaction/manager.rs#L36), [chat bridge lease](../crates/moqui-core/src/service/chat_bridge.rs#L1105).

Start by committing the claim in its own transaction, then running SMTP with no transaction or connection held and an overall session deadline, then recording the result in a new transaction that checks the claim is still there. Preserve the uncertain outcome, which is shown to the user and never resent automatically, template messages, and `send#Draft` sending a draft saved earlier in the caller's transaction, by deferring the send until after that commit. Give each run a time budget so one account cannot hold up the others. Verify with the fake SMTP server delaying its final DATA reply past a short transaction timeout: run `send#DueDrafts` twice and check that exactly one message arrived and the row is sent, or ready with a send error, never scheduled again; a second case makes recording the result fail after the send.

#### HL-029. Count an IMAP change attempt that loses the connection

**Status: fixed** in `7c2c6a95` (attempt counted before the command; reconnect and go on to the fetch).

**High · Supported by source.** Every IMAP session, the IDLE inbox syncs included, applies the account's queued changes oldest first, before listing folders or fetching anything. When a change loses the connection (an I/O timeout, BYE or tag mismatch), the queue returns before the attempt is counted, and a panic becomes a connection failure. The 10-attempt limit therefore never applies: the same change runs first in every session and fails the same way, and the account fetches no new mail and pushes no later change, indefinitely. Appending a large sent copy that passes the 60-second socket timeout, or that the server answers by disconnecting, is enough. One message blocking a whole account goes against the rule of logging a failed piece and going on. [Changes first](../crates/moqui-mail/src/sync.rs#L1501), [return before counting](../crates/moqui-mail/src/remote.rs#L359), [attempt limit](../crates/moqui-mail/src/remote.rs#L50), [lost connection](../crates/moqui-mail/src/sync.rs#L562), [socket timeout](../crates/moqui-mail/src/inbound.rs#L1029).

Start by writing the attempt count and time in its own transaction before sending the IMAP command, so a lost connection or panic still counts, and after a lost connection in this phase reconnect and go on to the folder fetch. Preserve change order per message and leaving the remaining changes queued after a lost connection. Verify with a fake IMAP server that disconnects on APPEND, a queued sent change and new Inbox mail: the mail must arrive within two sessions, and the change must be dropped and logged after 10 attempts.

#### HL-037. Stop a mail sync whose lease lapsed

**Status: fixed** in `9c4c06fb` (per-session holder, renewal by elapsed time at every write step, stop on refusal, release only an own lease).

**Medium · Supported by source.** A sync holds its account for 15 minutes and renews only between folders, so the change phase and the first folder run on the first lease, and a bulk move queues one change per message. A renewal that another session refused is ignored, since only an error is checked, and the session carries on while a second one claims the expired lease. Each works from its own snapshot of local rows, the match does not treat a row with the same UID in the same folder as the message, and nothing is unique on the remote folder and UID, so both store the same messages and run email ECA rules, mail rules and out-of-office replies twice, and both append the queued sent copies. Release then clears the lease without checking who holds it. [Lease length](../crates/moqui-mail/src/sync.rs#L70), [renewal](../crates/moqui-mail/src/sync.rs#L1540), [release](../crates/moqui-mail/src/sync.rs#L928), [message match](../crates/moqui-mail/src/sync.rs#L1878).

Start by renewing by elapsed time inside the change and folder loops, ending the session when a renewal is refused, and releasing only a lease this session holds; consider a uniqueness guard on the remote UID. Keep the conditional claim under a row lock. Verify with an injectable lease length: stall a fake IMAP fetch past the lease, start a second sync, and check that the first stops at its next renewal and its release leaves the second's lock.

#### HL-038. Bound mail sync by bytes fetched and rows read

**Status: fixed** in `75f0e236` (25-message or 8 MiB fetch batches, no body copy, 5-session cap on failing stores, rows read only for the UIDs involved). Open: the cap is in memory.

**Medium · Supported by source.** New mail is fetched 25 whole messages per request; the IMAP client buffers the response and each body is copied again before the buffer is freed, so a session can hold about twice the size of 25 messages, and up to 8 IDLE workers and the job syncs can do so at once. Each message's size is already fetched but sizes neither the batch nor a cap. A message whose store keeps failing moves the next start UID back to itself with no attempt limit, so it is downloaded again every session. On the local side, whenever the folder status shows any change, the sync loads every row of the folder that has a UID, even with CONDSTORE or QRESYNC, where only new, changed and expunged UIDs need rows. With CONDSTORE one flag change moves the highest mod-sequence and defeats the unchanged shortcut, and IDLE syncs the Inbox on every notice, including the echo of this client's own flag changes, so the rows read follow the whole Inbox on every server event. [Fetch chunks](../crates/moqui-mail/src/sync.rs#L72), [body fetch](../crates/moqui-mail/src/sync.rs#L2163), [all local rows](../crates/moqui-mail/src/sync.rs#L1832), [unchanged shortcut](../crates/moqui-mail/src/sync.rs#L1977), [IDLE syncs](../crates/moqui-mail/src/idle.rs#L15).

Start by splitting fetches by a byte budget from the known sizes, fetching an oversized message alone, taking the bodies without copying them, and capping re-reads of a store that keeps failing. Query local rows only for the UIDs involved, plus the lowest UID for the range, keeping the full load for the flag scan without CONDSTORE and for the expunge count check. Preserve de-duplication after an interrupted first sync and the handling of moved and vanished messages. Verify with a unit test of the byte-budget batching, by counting rows read for one flag change and one new message in a 100,000-row Inbox, and with an opt-in load test of 25 messages of 20 MiB that records peak memory.

#### HL-039. Stop the MX delivery round rescanning every pending delivery

**Status: fixed** in `4392abd8` (one query for rows of unpaired nodes).

**Medium · Supported by source.** On the edge node, each delivery round starts by listing every pending delivery row, with no limit, to fail those whose node is no longer paired. A round runs after every finished session and at least every 30 seconds, so a backlog of P rows (a bulk mailing, or a recipient outage kept for up to five days) costs P row reads per finished session even when every node is paired. [Unpaired check](../crates/moqui-mail/src/mx.rs#L496), [round after each session](../crates/moqui-mail/src/mx.rs#L445), [round interval](../crates/moqui-mail/src/mx.rs#L88).

Start with one conditional update for rows whose node is no longer paired, or run the check only when pairing changes and in the hourly cleanup. Keep bouncing those rows and removing their stored message. Verify with a regression test of rows read per round with many pending rows for an active node, and an opt-in load test with 50,000 pending rows.

### Agents

#### HL-030. Count in-flight model calls against quotas

**Status: fixed** in `32d643b2` (row-locked admission with a reservation counted in totals; agent attempts reserve before each call; endpoint slots documented as per node).

**High · Supported by source.** The quota check counts only finished calls, and a call's row is written after the call ends. The gateway tests usage plus the most this call may use, but never records that reserve, and the API client's daily limit has the same race. Agent steps check with no reserve, only whether usage has reached the limit, and one step can then make several attempts, a retry with a large output allowance and side calls without checking again. Concurrent calls for one user, bounded only by worker and stream caps, therefore all pass against the same total, overshooting by about (concurrent calls − 1) × reserve per node. The endpoint `max-concurrent` and model `max-concurrency` limits are counted in memory on each node, so N nodes give a single-slot server N calls at once, and unlike requests per minute this is not documented as per node. [Finished calls only](../crates/moqui-llm/src/usage.rs#L788), [row after the call](../crates/moqui-llm/src/gateway.rs#L1310), [reserve test](../crates/moqui-llm/src/usage.rs#L834), [agent check](../crates/moqui-llm/src/run/step.rs#L1063), [endpoint slots](../crates/moqui-llm/src/provider/mod.rs#L1554), [per-node rate note](../crates/moqui-llm/src/usage.rs#L22).

Start by admitting calls under a per-user and per-client row lock and writing a reservation in the same short transaction. Count open reservations in the totals, replace each with real usage when the call is recorded, and expire reservations left past their deadline; design this together with HL-012's aggregate read. Keep no transaction open across the call, and keep the timezone, month and estimated-usage behavior. Document the endpoint slots as per node, or add a cluster-wide slot. Verify with a fake provider held at a barrier: start N concurrent admissions for a user whose remaining quota fits one reserve and check that only one is admitted, for the gateway and for agent steps; an opt-in two-node acceptance test can check the slots.

#### HL-040. Record in-flight tool writes as unknown outcome on every recovery path

**Status: fixed** in `b103b88e` (resumed call marked running with its decision by approval ID; unknown outcome on every end path; `UnknownOutcome` approval status; a tool panic counts too).

**Medium · Supported by source.** Only a pending tool call is marked running before it runs, so after a takeover a running write is reported as unknown outcome and not run again. A resumed, approved write skips that step: its decision input is consumed and committed, then the tool runs while the call is still awaiting, and the approval moves to executing. If the node dies during that write, the next owner finds an awaiting call with no decision and stores it as failed with "No answer came for this call." If the user has a message queued, the message can be used up as the tool's input and never reach the conversation. Runs that end by takeover with cancel requested, by running out of recovery attempts, by a cancel at step start or by a step error or panic record a running write as not run, and the run's approval expiry skips executing approvals, which stay executing forever. The model and the audit trail are told that a write which may have committed did not run. [Resumed call](../crates/moqui-llm/src/run/step.rs#L2000), [move to executing](../crates/moqui-llm/src/approval/mod.rs#L838), [approval expiry](../crates/moqui-llm/src/approval/mod.rs#L1354), [end-path record](../crates/moqui-llm/src/run/step.rs#L511).

Start by marking the resumed call running in the same transaction that consumes its decision, selecting the decision by approval ID, and closing running and executing work as unknown outcome on every end path. Keep the conditional move from approved to executing, which is what guarantees a write runs at most once. Verify by blocking or panicking a resumed write after it begins, then taking the run over, and checking for unknown outcome, an approval no longer executing, and the queued message folded into the conversation; repeat for cancel on takeover and for running out of attempts.

#### HL-041. Keep model calls out of a caller's open transaction

**Status: fixed** in `98096ae5` (model calls refused while any transaction frame is open unless `allowInTransaction`; opted-in calls cut to the remaining time). Open: no opt-in for `ec.llm.summarize`, `classify`, `extract`.

**Medium · Supported by source.** A model call suspends any transaction already open, and its documentation says no transaction stays open while a model answers. Suspension, though, parks the connection, which still counts against the pool maximum, and the database transaction stays begun with its locks. `ec.llm.complete` and the AI task services allow 300 seconds per call, the AI task services are `transaction="ignore"` and so join the caller's transaction, and screen transitions begin one by default with the 60-second deadline, which keeps running while the transaction is suspended and marks it rollback-only. A call that outlasts the caller's remaining time is paid for and recorded, then the caller's work rolls back; recording the call takes a second connection. [Suspension](../crates/moqui-llm/src/provider/mod.rs#L960), [documentation](../crates/moqui-llm/src/provider/mod.rs#L900), [parked connections count](../crates/moqui-entity/src/transaction/pool.rs#L20), [deadline while suspended](../crates/moqui-entity/src/transaction/manager.rs#L1252), [AI task service](../runtime/base-component/framework/service/org/moqui/agent/AiTaskServices.xml#L25), [transition transaction](../crates/moqui-core/src/screen/definition.rs#L435).

Start by refusing a model call while a transaction is open, or handing it to an async task, unless the caller opts in; at least cut the call's deadline to the transaction's remaining time and correct the documentation. Keep usage rows surviving a rollback and the agent step's no-transaction assertion. Verify by calling `ec.llm.complete` inside a transaction against a slow fake model and checking the pool's parked count and that the call is refused or cut short; an opt-in load test can drive transitions that call AI tasks.

#### HL-042. Fence a run's writes by lease generation

**Status: fixed** in `71685cb6` (`leaseGeneration` checked with the owner on every run write). Clock skew documented rather than moved to database time.

**Medium · Supported by source.** Every run write checks only that the lease owner is this node, and a node learns it lost a run only when its keeper next reads the row; a failed renewal is just logged. If node A's keeper cannot renew for longer than the lease while a step is still running, node B takes the run over and pauses it, and the user's answer can then reach A: A's resume claims the lease again, its local run state hands back the old entry, which is not marked lost, and the old step's stale writes pass the owner check. They store a second result for a call B already closed, or reuse a step number, which fails the run. Lease expiry is computed from each node's own clock, so a node whose clock runs ahead by the lease margin takes over healthy runs. [Owner check](../crates/moqui-llm/src/run/mod.rs#L1261), [loss noticed by the keeper](../crates/moqui-llm/src/run/lease.rs#L167), [claim on local time](../crates/moqui-llm/src/run/lease.rs#L48), [resume claim](../crates/moqui-llm/src/run/mod.rs#L1090), [local run state](../crates/moqui-llm/src/run/mod.rs#L120).

Start with a lease generation that every claim other than a renewal increments, carried in the node's local run state and checked with the owner. Use database time for expiry, or document the clock-skew bound. Verify with a deterministic test with two node IDs that follows the sequence above.

- **Deferred calls checked against an empty stack.** `registerOnCommit` and tx-commit rule runs were authorized after the commit, when the screen or service frames were gone, so Compose "Send now" never sent for a normal user, and spilled rule runs ran with authorization disabled. ### Checked and not recorded

These candidates were traced and dropped because a guard already covers them. They are listed so a later pass does not repeat the work.

- **Data layer:** sequenced IDs refill with one atomic upsert under a per-name lock in a reserve transaction, so a crash or rollback only leaves gaps; a frame's uncommitted rows never reach the shared cache; an open transaction returned to the pool is rolled back or the connection dropped; statement timeouts are cleared on return; the sim overlay sets its schema path per statement on its own pool; pipelined failures are discarded by the rollback; a decode error still reads the reply to its end; nested and suspended transactions are repaired and marked rollback-only; a data file that fails is logged and skipped; blob garbage collection waits at least a day against a one-hour freshen (a narrow window remains where `finish` ignores a failed freshen, which the foreign key turns into a failed write).
- **Core runtime:** feed rows are inserted with the write and claimed by delete; QuickJS has a 64 MiB heap limit, a stack budget and an interrupt on the deadline; pooled threads are cleaned up after an error or panic, and tested; a panicking or abandoned job run releases its lock; ECA, include, extends, service-include and entity-auto nesting are bounded; remote invalidations move the screen-config generation; screen loading marks clean up on drop; per-call coverage counting is gated by a flag; read-your-writes waits are bounded; login history is documented as best effort; notification email failures are isolated per recipient; a lost `session-end` message or a logout on another member converges at the peer's next flush, which retires a session whose row is gone, so the delay is bounded; the scheduler pass, tick hooks, cluster sender and pool workers all catch panics.
- **Hosts:** hyper's header timeout covers idle keep-alive connections and the TLS handshake; request bodies and uploads have body and idle timeouts; the web guard's client table is capped and swept; HTTP/2 stream and reset floods are limited; a slow notification or XMPP client cannot stall fan-out, since a full queue unregisters it; XMPP caps unacknowledged stanzas, detached sessions and handshake time; inbound SMTP has read, write and session deadlines and global and per-/64 caps, and answers 451 when it cannot store; SIP over UDP and TCP has rate, transaction and per-/64 gates; the edge link has handshake timeouts, a hello limit and a tunnel semaphore; the opt-in gRPC listener has admission and a TLS deadline but no total cap (the same family as HL-027 and HL-031); no standard-library lock is held across `.await` on the traced paths; HTTP connections drain at shutdown; telemetry queues, buffers and series are capped; outbound HTTP has 30-second total and 10-second connect defaults and refuses internal addresses.
- **Communications:** edge MX claims are conditional on the attempt count with a lease longer than the session, answers commit before the report, and each row runs on its own thread with panics caught; the edge relay checks for an earlier relay and commits its status right after; SMS commits its lease before the provider call and marks a lost answer uncertain; inbound SMTP checks Message-ID with a store transaction per account; the OAuth refresh under the server row lock is deliberate and bounded; Git pushes stream to a disk quarantine with a per-object limit and fetches stream their pack; Git ref rows are locked in name order and compared before writing; the post-push commit walk is capped; two syncs cannot start at once (only the lease lapse in HL-037 remains); XMPP caps stanza size and depth and archive pages; the SIP registrar caps and expires bindings; elFinder archive, extract and search are disabled; mail IDLE reconciliation does no network I/O on the scheduler thread.
- **Agents:** trigger limits hold a row lock until the run is created and events are claimed conditionally; takeover is a conditional claim; event flushes check the lease owner under a row lock; a crashed running write becomes unknown outcome; approvals are decided and run at most once; agent steps assert that no transaction is open during a model call; provider attempts have a 30-minute cap, an idle limit and a run deadline, and a cancel reaches the reader within one heartbeat; A2A delegation, the MCP client and push delivery have deadlines and output caps; MCP approval waits are capped; async AI task records expire after a day; embedding callers run outside transactions; requests per minute are documented as per node.

## Verification follow-ups

All three passes were static and read-only: no benchmarks, builds or test suites were run, and no file but this document changed. The scenarios above are proposed follow-up proofs, not reported test results.

Use small deterministic regression tests for invalidation coverage and recovery (HL-017, HL-018), a reader straddling a commit (HL-023), the authorization generation after a remote invalidation (HL-024, through the remote path itself, since the generation is a process static), heartbeat progress and rejoining (HL-020), independent deadline progress and a late cancel (HL-019), the tx-commit spill and job lock claim and reclaim (HL-025, HL-026), a stalled write and upgraded-socket caps (HL-027), a single delivery for a slow SMTP send and an IMAP change that drops the connection (HL-028, HL-029, with the fake servers), concurrent quota admissions (HL-030, with a barrier), recovery of an in-flight tool write and a stale lease holder (HL-040, HL-042), and event ordering across ring wrap and replay gaps (HL-021). Sustained load, prolonged delivery failures, a two-member kill mid-job, group revocation under load, TURN and SIP connection floods, combined download/request/agent saturation and two-node endpoint slots belong in opt-in acceptance tests. Follow the repository's [testing rules](../docs/Build-Test.md#the-two-suites): run acceptance tests only when requested or when adding or changing them, and keep regression tests within their existing budgets. Measure representative workloads before claiming any performance improvement.
