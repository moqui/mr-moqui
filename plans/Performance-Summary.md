# Performance summary

Digest of [Performance.md](Performance.md), [Performance-Implementation.md](Performance-Implementation.md), [MantleUSL-Performance-Audit.md](MantleUSL-Performance-Audit.md) and [MantleUSL-Execution-Benchmark-Plan.md](MantleUSL-Execution-Benchmark-Plan.md). The first two are self-contained plans with recorded numbers; the audit is a static source review of mr-mantle; the benchmark plan defines the proofs.

## Target
**100,000 durable commits / completed reads of transactional business data per second**, one-node first, then a maximum-scale split (writing, processing and optional batch app servers; a write database and a read database). Reference point: TPC-C record ~142,542 New-Order/s (128 cores, 2013). **Not demonstrated.** Never substitute generated statements or row counts for it; use a declared read/write mix, durable acknowledgments, full framework semantics and tail latency.

## Recorded so far (local experiments, not full acceptance)
- Durable-WAL follow-ups: ~26k/s faithful extracted 100-line invoice path, 35.8k/s over 15 min on a reduced mixed fused-SQL path, median 53.5k/s on a lighter one-line diagnostic.
- XML parse/tree: 156.77 MB/s resident (21.1 MB corpus, 134.8 ms median); real framework entity model (217 entities) 4.856 ms median; warm read+parse of 21 MB ≈ 32% of a 500 ms startup budget.
- SQL text generation: 0.18–0.60 µs per statement (insert, update, delete, upsert, PK select). Excludes execution, auth, commit.
- Search, 50,000 generated documents (`tests/search_bench.rs`, [Performance.md, Search](Performance.md)): Postgres indexes 3,190 docs/s (3.75 KB per document) and answers selective queries in about 1 ms p50, but broad ones in 80–580 ms p50; OpenSearch indexes 490 docs/s with about 1 s to visibility and answers everything in 1–5 ms p50.

## Profiling rounds ([Profiling](Profiling.md))
Entity, service, data load and XML/definition work profiled and optimized against embedded Postgres, with five opt-in speed tests. Round 14 (the transaction cache, [TX-Cache](TX-Cache.md)): held writes go out as one commit batch and a frame reads a row once; with 200 µs to the database `update#WikiPage` goes from 33.5 to 9.9 ms a call (117 waited round trips to 17) and `heartbeat#UserStatus` from 2.3 to 1.6 ms, while over a local socket the cache's own cost (SQL text built per read, rows copied) still makes some calls a little slower; Round 15 tuned it (SQL text cached, kept rows shared, regular expressions compiled once a thread, a secondary sequence read of one field): over a local socket the cache is now as fast or faster for most calls, and with the delay `update#WikiPage` is 7.7 ms against 30.9 ms off. Round 16 timed the rows with the async workers quiet (every call but `mark#Read` is now as fast or faster with the cache on), sent savepoints, releases and a commit behind unanswered writes, cached the mail-change count every message write read, made resource references read size and children only when asked (a wiki save read every page of its space), and moved service results instead of copying them (4-9% fewer allocations a call). Round 17 tuned the shared layers under them: script property names read without a copy, a script's service parameters validated in place, and a commit that sends a transaction-cache batch behind its `COMMIT` (no check needed for rows a locking find read): `heartbeat#UserStatus` 1.36 ms with the delay (2.17 off), 6-11% fewer allocations a call. Round 18: a find by keys the transaction cache knows answered in memory, the update's changed-row check made on the server so the `COMMIT` goes with the batch, and cold deferred statements prepared as they are sent: `heartbeat#UserStatus` 1.07 ms with the delay. Round 19 applied the cache beyond the first set (mail stored with its attachments 15.8 to 10.2 ms with the delay, notifications marked viewed 2.6 to 1.2 ms, chat reactions and edits), kept select-field finds in a cache frame, sent the feed's savepoint behind the batch, and cut a service call's allocations 9-16% (the authorization regex matcher). Round 20: files written into a new directory without the extra transactions (mail store 9.3 ms with the delay), artifact metric attributes made once per artifact, agent step bookkeeping in cache frames (a run's round trips 14% fewer), and `send#WebPush` no longer holding a transaction across its HTTP calls. Round 21: span ids kept as bytes, a write's lock check answered from a cached count, and `save#Draft` and the chat bridge's inbound item on the cache (an autosave 5.4 to 4.1 ms with the delay). Round 22: the census of mr-boss and mr-mantle under the cache found five ways a frame's read differed from the database's (fixed: 2,822 to 3,062 of 3,067 features pass with every transaction holding), and presence expiry and delivered mail with its rules went to batches. Round 23: the census measures per service what holding saves, and 45 services it picked (order placement and approval, invoices, the Shop checkout, BOM and routing releases, production orders) are on the cache: 34% fewer waited round trips across them in the specs. Round 24: a view read sees the held rows of its members through shadowed tables instead of writing them (view early flushes in the census 3,652 to 34), and Mantle's asset services hold: 36% fewer round trips across the 45, each in one batch. Round 25: distinct reads and encrypted members shadowed too, and the shared payment and shipment services on the cache (`apply#Settlement` 242 to 122 round trips a call, `create#Payment` 48 to 28). Round 26: views built in code shadowed too, 13 more services, and the Mantle operations timed against a Postgres 200 µs away: 32% less time a call across them (`pack#Shipment` 68 to 45 ms, `create#Payment` 37 to 25 ms, `place#Order` 30 to 22 ms). Data load records about 8x faster than at the start (one pipelined upsert each), PK finds about 30% faster, allocations down 2.5–9x across the rows; a blocking wire-protocol Postgres client replaces `tokio_postgres`. Next: the same tests against an external Postgres.

## Mantle USL audit findings
Avoidable work amplification comes before engine speed: per-item total recalculation on orders/invoices (triangular), synchronous ECA/service cascades, historical summary scans, duplicate reads, quadratic collection loops, and JS host-boundary/decimal costs. QuickJS may stay but is unproven for financial arithmetic and collection-heavy paths. Recommended: fix workload shape, add indexed algorithms, then build a real generated-JS + facade spike (party create, bounded order import, invoice finalization, reservation, payment) and compare native orchestration vs QuickJS through the same facades and commit boundaries. Optional ahead-of-time Rust backend from a shared validated action IR is a proposal only.
