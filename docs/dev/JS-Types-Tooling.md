# Types and tooling for JavaScript

The tools around application JavaScript: TypeScript declarations generated from the loaded definitions (`moqui types`), checks of XML files and the expressions in them (`moqui check`, `moqui lint`), a language server (`moqui lsp`), which services a test run never called (`moqui test --coverage`), and the mechanical part of converting a Groovy component (`moqui convert --groovy`). None of them changes how code runs.

They are commands of the `moqui` binary. In a clone, `./moq run <command> ...` runs the built binary with the repository's runtime and the dev conf, so `./moq run types --out /tmp/types` is `moqui types --out /tmp/types`. `moqui help <command>` prints each command's own text.

| Command | |
|---|---|
| `moqui types [--out dir]` | TypeScript declarations for entities, services, screens and tools |
| `moqui check [paths] [--extensions] [--json]` | Schema, references and expressions of Moqui XML files; for a hook |
| `moqui lint [file]` | Service files: every expression and action script parses |
| `moqui lint --screens [report-file]` | Screen and form XML: expressions parse; idioms and hazards counted |
| `moqui lint --groovy [--all] <dir> ...` | Groovy left in a component, and run-time hazards of ported scripts |
| `moqui convert --groovy [--write] <dir> ...` | Mechanical Groovy-to-JavaScript rewrites |
| `moqui lsp` | A language server for Moqui XML files |
| `moqui refs <name> [--in \| --out]` | What uses an artifact, or what it uses |
| `moqui test [component] --coverage` | The services no spec called |

## `moqui types`

`moqui types` loads the definitions as a server does, against an entity model with no database, and writes declaration files. The default directory is `types/` in the runtime directory (`runtime/types`, which the repository ignores); `--out dir` or `--out=dir` names another. It prints the number of files and of notes, and logs each note: a screen that did not load, an `auto-parameters` whose entity is not loaded.

```sh
./moq run types                       # into runtime/types
moqui types --out my-component/types  # to commit beside a component's scripts
```

| File | |
|---|---|
| `moqui-host.d.ts` | The fixed host types: `Decimal`, `Timestamp`, `EntityValue`, `EntityList`, `EntityFind`, the server `ec` (`MoquiServerEc`) and its facades, `sri`, the service call builders, the static helpers, the plain projection sent to JSON and the browser, and the browser `ec` |
| `moqui-globals.d.ts` | The names a server script sees without declaring them: `ec`, `context`, `result`, `sri`, `ObjectUtilities`, `StringUtilities`, `toDecimal`, `compare`, `SftpClient`, ... ([JS-Globals](JS-Globals.md)) |
| `entities.d.ts` | A shape for each entity and view entity, and `MoquiEntityMap` from every name to its shape |
| `services.d.ts` | `MoquiServiceIn` and `MoquiServiceOut`: the input and output map of each service by name |
| `screens.d.ts` | A partial context type for each screen, and the package type of each server-static qvt screen |
| `tools.d.ts` | `MoquiToolMap`: the type of each tool whose factory declares one |
| `shape.ts` | The server-static qvt package keys as values, for client code |
| `tsconfig.json` | Strict, `noEmit`, including the directory's `*.d.ts` and `*.ts`, so `tsc --noEmit -p <dir>` checks the declarations themselves |

Each generated file starts with "Generated by `moqui types` from the loaded definitions. Do not edit." Only loaded definitions are there: a component's entities and services appear when the runtime that runs the command loads the component. Run it again after changing an entity or a service definition.

### Pointing an editor at them

The declarations are ambient: no `import` is needed, and any project that includes the directory sees `ec`, `context` and the maps. For JavaScript checked in place, add a `jsconfig.json` (or a `tsconfig.json` with `allowJs`) that includes the declarations and the scripts. For a component in `runtime/component/<name>` with the declarations in `runtime/types`, for example:

```json
{
    "compilerOptions": { "target": "ES2022", "lib": ["ES2022"], "checkJs": true, "noEmit": true, "types": [] },
    "include": ["../../types/*.d.ts", "service/**/*.js", "script/**/*.js", "test/**/*.js"]
}
```

`lib` without `DOM` keeps browser names out of server scripts, and `"types": []` keeps `@types` packages out. With that, `tsc --noEmit -p <component>` checks the scripts, and an editor completes entity names, field names, service names and their parameters. Only `.js` and `.ts` files are covered. A `<script>` body or an expression attribute inside an XML file is checked by `moqui check` and `moqui lint`, which parse it and do not type it.

### How definitions become types

**Entities.** Each entity is an interface in the `MoquiEntity` namespace, named from its full name with dots as underscores (`MoquiEntity.moqui_basic_Enumeration`), with `fields` (each field's type as a script reads it), `pk` (the primary key field names) and `rel` (each relationship name, short alias or untitled related entity name to the related entity). `MoquiEntityMap` maps every name the entity facade resolves to that shape: the full name, the entity name when it is unique, and the short alias. The generic host types take the name:

```js
const row = ec.entity.find("moqui.basic.Enumeration").condition("enumId", id).one();
row.get("sequenceNum");             // number | null
row.description = "Changed";        // fields are properties too
row.get("noSuchField");             // an error under tsc
```

A name that is not loaded is a plain map: nothing is refused and nothing is known.

| Field or parameter type | As a script reads it | As a service input |
|---|---|---|
| `String` and text | `string` | `string` |
| `BigDecimal` | `Decimal` | `Decimal \| number \| string` |
| `Timestamp` | `Timestamp` (branded ISO-8601 text) | `Timestamp \| string \| number` |
| `Date`, `Time` | `string` | `string` |
| `Long`, `Integer`, `Double`, ... | `number` | `number \| string` |
| `Boolean` | `boolean` | `boolean \| string` |
| `Map` | `MoquiMap` | `MoquiMap` |
| `List`, `Set`, `Collection` | `unknown[]` | `unknown[]` |
| `EntityValue`, `EntityList` | the host types | the host types |
| Binary | `never` | `unknown` |
| Anything else, or no type | `unknown` | `unknown` |

`Decimal` is an object type with the host value's methods (`add`, `subtract`, `multiply`, `divide`, `compare`, `toNumber`, ...), so `amount + tax` is an error in checked code.

**Services.** `MoquiServiceIn` has one entry for each defined service. A key is required when the validation rejects the call without it: `required="true"` and no `default` or `default-value`. Every other key is optional and may be null. `auto-parameters` expand against the entity model as the validation expands them. A service with `validate="false"` accepts other keys too. `MoquiServiceOut` lists the declared out-parameters, all optional, since nothing checks an output; a service that declares none returns a plain map. Each entry's comment names the implementation (inline, script, rust, entity-auto, interface).

The implicit entity-auto names are not listed. They are mapped types over `MoquiEntityMap`, so `create#`, `store#`, `update#` and `delete#` with any loaded entity name are typed: the entity's fields and its relationship names as input, the primary key required for `update#` and `delete#`, and the primary key fields as output.

```js
const out = ec.service.sync().name("org.moqui.impl.UserServices.create#UserAccount")
    .parameters({ username: "jo", newPassword: pw, newPasswordVerify: pw }).call();
out.userId;                          // string | null | undefined
ec.service.sync().name("update#moqui.basic.Enumeration").parameters({ description: "x" });   // an error: enumId is required
ec.service.sync().name("my.Unknown.do#Thing").parameters({ any: "thing" });                 // a name not loaded: a plain map
```

**Screens.** A screen's actions are dynamic, so `screens.d.ts` lists only the context keys the definition proves: the screen's parameters, form maps and form-list lists with their pagination keys, `section-iterate` lists, and the names that `<set>`, the entity finds and `service-call` out-maps write. `MoquiScreenContexts` maps each screen location to those keys plus any other name, for a script that narrows the context:

```ts
const ctx = context as MoquiScreenContexts["component://my-app/screen/MyApp/Order/OrderDetail.xml"];
```

For a server-static qvt screen, `MoquiScreenPackages` and `MoquiFormListPackages` give the package its template receives ([Qvt-Client](../ui/Qvt-Client.md)). A screen that did not load is a `// not loaded:` line at the top of the file.

**Tools.** A native tool factory gives its instance a type with `ToolFactory::type_declaration()` ([Native-Components](Native-Components.md#tools)): the text of a TypeScript object type.

```rust
fn type_declaration(&self) -> Option<&'static str> {
    Some("{ greet(name: string): string; readonly greeting: string }")
}
```

`tools.d.ts` writes it into `MoquiToolMap` under the factory's name, and `ec.getTool("Example")`, `ec.factory.getTool("Example")` and `ec.factory.getToolFactory("Example").getInstance()` return that type. A tool with no declaration is a `MoquiTool`: any member is a function of unknown arguments and result.

### Declarations are advisory

Nothing at run time reads these files. The script host does not check a call against `services.d.ts`; the service's own validation does that from the XML definition, at the call. A script that passes `tsc` can still fail validation (a value out of range, a name chosen at run time), and one that `tsc` rejects still runs. The declarations describe what the definitions say: a context key a script sets, or a result a service returns without declaring it, is not there. There is no transpile step either; a script is the JavaScript the host runs.

The generator is `crates/moqui-devkit/src/typegen/` (`entities.rs`, `services.rs`, `screens.rs`, and the fixed `moqui-host.d.ts` and `moqui-globals.d.ts`). Its fixtures in `testdata/` include `usage-fixture.ts`, authored code with `@ts-expect-error` lines that shows what is and is not an error. The design record is [TypeGeneration](../../plans/archive/TypeGeneration.md).

## `moqui check`

`moqui check` checks Moqui XML files (a directory: the XML files in it) three ways: against the framework's XSDs, the names they use against the loaded definitions (entities, fields, services, service parameters, locations), and their JavaScript expressions and scripts, which must parse. It opens no database. With no paths it checks the XML files git shows as changed under the current directory.

```sh
moqui check                                                         # the changed XML files
moqui check runtime/component/my-site/service/my/MyServices.xml
moqui check --extensions --json
```

| Option | |
|---|---|
| `--extensions` | Also check every extension against what it extends: a `screen-extend` file's base screen and the forms, sections and transitions it names, an `extend-entity`'s entity, an ECA rule's service or entity |
| `--json` | One JSON object per problem per line, instead of `path:line:col: severity: message [rule, skill#section]` |
| `--server URL` | Ask a running dev instance (its MCP `check` tool), with the login key `moqui tui --server` keeps or `MOQUI_LOGIN_KEY` ([MCP](../ai/MCP.md)) |
| `--project DIR`, `--java DIR` | Read another Moqui project: an MR Moqui clone or runtime, or a Java Moqui checkout |

It exits 1 when there is an error, so it runs as a git or agent hook. A reference that does not resolve, an expression that does not parse and XML that does not parse are errors. Schema problems are warnings and do not fail it.

## `moqui lint`

Three lints, by the first argument.

**`moqui lint [file]`** registers the service files (one file, or with no file those the framework conf names) without changing the registered services, and prints each registration failure, such as an expression or a generated action script that does not parse. It boots a factory with no database so that the `type="rust"` locations of linked components resolve. Any failure exits 1.

**`moqui lint --screens [report-file]`** scans the screen, form and widget-template XML under the runtime's components. Every expression site must parse as JavaScript, and so must the script generated from each `actions` block. The argument is the file the report is written to, not a screen to check; with none the report goes to stdout. The report has the files and expression sites scanned, the parse failures, idiom totals by sites and files, and a TUI worklist (browser-only parts with no `tui` text). Parse failures exit 1; idioms do not.

**`moqui lint --screens --qvt-static [report-file]`** is a compatibility report of each screen for server-static qvt. It never fails the process.

**`moqui lint --groovy [--all] <dir> ...`** reports what is left of Groovy under the directories, for a component being converted, and adds the hazards a typed scan can find. It needs at least one directory.

The idioms fall in three groups:

| Group | |
|---|---|
| Groovy | Not JavaScript, or not the same in it: Elvis `?:`, map literals `[a: 1]`, `as` casts, closures, GStrings, ranges, the regex operators, `def`, `new` of a Java type, static Java classes, `catch (Exception e)`, `context + [..]`, Java collection methods |
| Hazard | Parses and runs, and behaves differently: a host decimal under `<`, `==`, `+` or a truth test; an empty collection in a condition (true in JavaScript); `push`, `add` or `each` on an `entity-find` result, which is a read-only host list; `x in list` on an array; a `const` or `let` declared twice across the `<script>` elements of one service; `.replaceAll('[^a-z]+', '')`, where JavaScript reads the pattern as text |
| Valid | Also JavaScript (`new Date`, `.add(` on a decimal, `catch (e)`, `1.5`): counted in the totals and not flagged; `--all` flags them too |

The hazard scan is by name within one service: the names it declares as `BigDecimal`, sets from a decimal call, or fills from an `entity-find`. It has no types, so it knows only what the service text says. The scanners are `crates/moqui-devkit/src/screen_lint.rs` and `lint_hazards.rs`. The rules for writing the JavaScript these lints want are in [Practices-App-Dev](Practices-App-Dev.md) and [JS-XML-Actions](JS-XML-Actions.md).

## `moqui lsp`

`moqui lsp` is a Language Server Protocol server over stdin and stdout for editors and coding agents. It serves Moqui XML files, not JavaScript files; for those use TypeScript's own language server with the generated declarations. Logs go to stderr. It is in the Dev and Debug packages; another build answers that it is not built into this host.

| Feature | |
|---|---|
| Diagnostics | The checks of `moqui check`, on each open file's text as it changes |
| Go to definition, references | From the artifact index, read into memory and kept current with the open files |
| Hover | An artifact's summary; an element's or attribute's documentation from the XSDs |
| Completion | Elements, attributes and enumerated values from the XSDs; entity and service names in the attributes that take them |
| Symbols | Document and workspace symbols |

`--server URL` answers from a running dev instance instead of this checkout, and `--project DIR` (or `--java DIR`) reads another Moqui project, both as `moqui check` does.

```sh
moqui lsp
moqui lsp --server https://dev.example.com
```

`moqui refs <name>` is the same index from the command line: `--in` (the default) lists the references to an artifact in every component's files, `--out` those made inside its definition, `--kind k` keeps one kind, `--json` prints one object per line. The name is an artifact id (`service:a.B.run#Thing`, `entity:moqui.example.Example`), a full or short name (`place#Order`, `OrderHeader`), or a file.

## Service coverage

`moqui test --coverage` records, during the run, the name of every service a call resolved: direct calls, nested calls, ECA and SECA calls, entity-auto calls and the calls of `parallel` threads. After the run it lists, for each component tested, the services of its `service/*.xml` files that no spec called, with the total. A call whose name does not resolve is not counted.

```sh
./moq test mr-mantle --coverage
./moq test mr-mantle --coverage-report /tmp/mantle-coverage.txt
```

`--coverage-report file` writes the report to the file with the call counts and prints only the total. It is a list of services nothing exercised, not line coverage: a service that was called once counts as covered whatever its branches. The rest of `moqui test` is in [JS-Testkit](JS-Testkit.md) and [Build-Test](../Build-Test.md#component-specs).

## Converting Groovy

A component written for Java Moqui has Groovy in its expression attributes, `<script>` bodies and `.groovy` files. A `.groovy` service script does not run here. The conversion is a mechanical pass, then a lint that lists what is left, then hand ports.

```sh
moqui convert --groovy runtime/component/my-component            # print the changes
moqui convert --groovy --write runtime/component/my-component    # write them to the files
moqui lint --groovy runtime/component/my-component               # what is left
```

`moqui convert --groovy` makes only rewrites whose meaning is the same in JavaScript, and only in the expression places of XML (the expression attributes, `${}` in other attributes and text, `<script>` and `<expression>` bodies). Without `--write` it prints the changes and writes nothing. Running it again on converted files changes nothing more.

| Groovy | Becomes |
|---|---|
| `[a: 1, (k): v]`, `[:]` | `{a: 1, [k]: v}`, `{}` |
| `context + [a: 1]` | `Object.assign({}, context, {a: 1})` |
| `a ?: b` | `a \|\| b` (left alone before a ternary at the same depth) |
| A found list in a `condition`: `orderList`, `!orderList` | `(orderList?.length > 0)`, `!orderList?.length` |
| `'lit'.equals(x)`, `x.equals('lit')` | `('lit' === x)`, `(x === 'lit')` |
| `x as String` | `x?.toString()` |
| `x as BigDecimal`, `x as int` | `toDecimal(x)` forms that keep null as null |
| `x in [..]` | `[..].includes(x)` |
| `.contains(` on a string literal or a found list | `.includes(` |
| `new ArrayList()`, `new HashMap()` | `[]`, `{}` |
| An EDI grammar `.groovy` file (one list literal) | A `.js` copy, and the XML locations that name it |

Everything else is left for a person or an agent: closures, GStrings, Java classes, decimal arithmetic with operators, and whole `.groovy` scripts. `moqui lint --groovy` lists it by file and site, and `moqui lint` and `moqui check` then confirm that what was ported parses. The converter is `crates/moqui-devkit/src/groovy_convert.rs`. The process used on Mantle, with the kinds of hand port it needed, is in [ConvertProcess](../../plans/archive/ConvertProcess.md), and the wider migration in [Moqui-Java-Migration](Moqui-Java-Migration.md).
