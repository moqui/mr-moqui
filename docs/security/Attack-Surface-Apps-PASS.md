# Attack surface: public applications (mr-pass and Mantle)

The public applications: mr-pass and the Mantle (mr-mantle) services its operations reach. This file holds what all of them share: how the frontend reaches the authority, public accounts, and sites with their members. The applications themselves are in two more files: Shop, Billing, Supplier, Support, PASS Sales and PASS Marketing in [Attack-Surface-Apps-PASS-Commerce.md](Attack-Surface-Apps-PASS-Commerce.md), and Forum and Smithy in [Attack-Surface-Apps-PASS-Forum-Smithy.md](Attack-Surface-Apps-PASS-Forum-Smithy.md). The PASS authority's gRPC service is a row under [Host routes and servlets](Attack-Surface-Routes.md#host-routes-and-servlets), and its edge link form is under [Edge node](Attack-Surface-Cluster-Edge.md#edge-node). The staff applications are in [Attack-Surface-Apps-BOSS.md](Attack-Surface-Apps-BOSS.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## How PASS reaches the authority

mr-pass (`runtime/components/addon/mr-pass`) is the public frontend and holds no business data. Every page calls a named operation through `pass.Facade.call#Operation` (`authenticate="anonymous-all"`, `service/pass/Facade.js`). The name must be a key of `service/pass/Schema.js` or `SmithySchema.js`, and every top-level key of the input must be one of that operation's `fields`; nested values are not checked there. `siteId` is the site the runtime conf binds to the host (`<public-site>`), never a request value. The authority is the node that runs mr-mantle. It maps an operation to one Mantle service through `script/PassRoutes.js` and `service/mantle/forum/ForumSchema.js` or `service/mantle/smithy/SmithySchema.js`; mr-pass's `Schema.js`, `SmithySchema.js` and `Routes.js` are copies of those three files. Every such service is `authenticate="anonymous-all"`, takes one `input` map and finds its caller itself. Nothing reads a service's `allow-remote` attribute ([Services and allow-remote](Attack-Surface-Web.md#services-and-allow-remote)): the route table and the two schemas are what bound the set a request reaches.

**The route resolver.** `pass.RouteServices.resolve#Route` (`authenticate="anonymous-all"`) is the `resolver-service` of a PASS `<public-site>`. The framework calls it with the conf's site id, the request's host and the path. It reads the site's mounts from the authority (`getSiteInfo`) and takes the longest mount whose prefix the path starts with; with none the answer is Not Found. For every app but Smithy a path that contains `..` is Not Found. The mount's app names a root screen from `service/pass/Apps.js` (`forum`, `account`, `members`, `sites`, `billing`, `supplier`, `support`, `sales`, `marketing`, `shop`, `smithy`). Named path forms are checked by pattern and become screen parameters that replace request parameters of the same name (Forum: `t/{id}/{slug}`, `p/{id}`, `held-mail/{token}` and its `/claim`; Marketing: `pages/...`; Shop: `products/{id}/{slug}`, `categories/{id}/{slug}`, `pages/...`, `Orders/{id}`, `Subscriptions/{id}`, `robots.txt`, `sitemap.xml`, `feeds/{key}.{xml|csv|json}`, `theme/{64 hex}/{path}`). Any other path is the app's root screen name followed by the rest of the path as written, so every subscreen and transition of a mounted app is reachable by its own name with its own request parameters. The framework refuses a resolver answer that does not start with `/`, starts with `//` or contains `..` (`crates/moqui-core/src/screen/public_site.rs`).

**Local mode.** With `pass_backend_url` empty the facade calls the operation's Mantle service in process with `{input}`, as the request's own user. These checks of the authority's `run()` (`mr-mantle/script/PassAuthority.js`) do not run in that mode: the registered client and its sites, the delegation, the rule for writes below, the rule that an operation has a route (`createSite` and `findModerationScopes` have a schema entry and no route), `CLIENT_READS`, and the removal of `location` from a download's answer. What holds in local mode is the frontend's login-key rule (below), its schema check, the screen transition's session token ([CSRF](Attack-Surface-Web.md#csrf)) and each Mantle service's own checks.

**Remote mode.** With `pass_backend_url` set, `service/pass/Transport.js` sends each operation to the authority over REST (`{pass_backend_url}/rest/s1/pass/v1/sites/{siteId}/{route}`) or gRPC (`pass_backend_grpc_url`, or `edge:` for the edge link). Each REST call carries `x-pass-client` (`pass_client_id`), `x-pass-client-secret` (`pass_client_secret`, which the script never reads: `RestClient.addPropertyHeader` adds it only to a URL under `pass_backend_url`) and `x-pass-client-ip` (the visitor's address as the frontend sees it); a signed-in visitor's delegation goes as `Authorization: Bearer`. The REST client has a 30 second timeout and follows no redirect. An `http://` `pass_backend_url`, or a `grpc://` gRPC endpoint, to a host other than loopback is refused (each call Unavailable) unless `pass_backend_insecure=true` (`Transport.js` `select`, `authorityClient`; SEC-PSF-05, fixed). A file goes as multipart after a 10 MiB check. Before it sends a write with no delegation the frontend refuses it unless the operation is `applyOptOut`, `addCartItem`, `getCart`, `requestSubscription`, `submitMarketingForm`, `recordTrackingEvent`, `reserveRegistration`, or a `TOKEN_WRITES` name with a `token`, `key` or `orderToken` in its input.

**The authority's rule for writes.** `run()` takes the client as registered only when `clientRegistered` accepts the client id, the secret and the site. A delegation from an unregistered client is refused; a delegation is checked for the client and site it was issued to (`authenticateDelegation`) and signs its account in for the call. When the servlet has not already checked the session token, a write (an account action, or a route whose method is not `GET`) is refused unless it is an account action from a registered client, `applyOptOut`, a `TOKEN_WRITES` operation from a registered client, or carries a delegation. `CLIENT_READS` (`getShopThemeRelease`, `getShopThemeFiles`, `getShopThemeAsset`) answer NotFound without a registered client. A registered client (a right secret, or verified by the transport) calling for a site not in its `pass_client_<id>_sites` is NotFound, not an anonymous caller (SEC-PSA-05, fixed). A registered client's `visitorAddress` becomes the requester key (`client:{id}:{address}`, 64 characters of the address) of every Mantle limit keyed by `requesterKey()`.

**Who the caller is.** The caller of an operation's service is `ec.user`: the account a delegation names, in local mode the frontend session's user, or over REST the business-host session's user. No service trusts a user or party id from the input. The site is the path's `{siteId}` and an app's organization or store is the site's mount of that app (`PublicApps.js` `mount`), never an input. The operations fall into classes: public reads of a published site (`getSiteInfo`, the Shop catalog, Marketing's pages) that name no caller; member and account operations that need a signed-in user and use its party; link operations that take a `token`, `orderToken`, `downloadToken`, or a reference with its `key` or `returnKey`; site administration that needs the site's owner or the `ADMIN` group; and Smithy, which takes its actor from `ec.user`. Link operations that are `GET` carry the token in the query string to the authority.

**Public accounts and delegations.** A public account is a framework user account. Signing in through `account/session` calls `org.moqui.impl.UserServices.login#UserAccount`, which asks no group or flag, so the same name and password sign in on the business host, and `POST .../account/session` with the session token signs a business-host session in. In remote mode an answered credential rotates the frontend's session and is kept there as `passDelegation`. The frontend's session also holds the other bearer values a visitor has: the authority's session (`passAuthorityCookie` over REST, `passAuthoritySession` over gRPC), a Shop cart capability (`passShopCart:{site}`), checkout return keys (`passShopCheckout:{site}`), guest order tokens (`passShopOrders:`, `passSalesOrders:`), an invoice pay token per attempt (`passPayToken.{attemptId}`), a card setup reference and form (`passShopMethodSetup:{site}`), a cart recovery token, a registration capability, the state, verifier and handoff id of a remote single sign-on (`passSsoState` and `passSsoHandoffId` among them) and, for two minutes, a Smithy access token just made (`passSmithyFlash`).

**Bearer links.** A PASS bearer link is a `mantle.party.ExternalAccessCapability` row, checked by `check()` of `service/mantle/party/ExternalAccess.js`. A token is 48 random characters (`ec.user.randomString(48)`); only its digest (`ec.user.singleUseCodeHash`) is stored. A lookup accepts a text of 32 to 128 characters and finds the row by digest. Each lookup first counts against the requester's limit, 100 in ten minutes (`org.moqui.public.AccountServices.record#Attempt`, key `access-token:{requester}`), and a requester over it is refused (`Tarpit`, `RATE_LIMITED`) whether the token is good or not. A row must be unrevoked and in its dates, of the record type asked, of the record id when the request gives one, hold the scope asked, and be of the organization the page serves when the caller of `check()` gives one. The record is resolved again and must still have the row's organization and party. Every failure is the same NotFound. The record types and scopes are `Invoice` (`InvoicePay`), `Order` (`BillUpload`, `OrderAcknowledgement`), `Quote` (`QuoteResponse`), `RequestCategory` (`CaseIntake`, reached by its token only), `Request` (`CaseView`), `ReturnHeader` (`ReturnRma`), `FormInvitation` (`CaseFeedback`, `MarketingSurvey`), `EventRegistration` (`RegistrationView`, `RegistrationCancel`) and `SalesOrder` (`OrderView`, `Download`, `RenewalAction`, `QuoteView`, `QuoteRespond`). A link lasts `validDays` (60 by default) or to `thruDate`, at most 366 days. With no token the caller must be signed in and the page must name its organization: either the account's own party is the record's party (`selfOf`, for the kinds marked `self`: the same party, not internal, not disabled, no employee, agent, member or representative relationship to an internal organization, the account's current email address verified), or the account holds a contact grant (`ExternalAccessContact`) for the app, the organization and the record's party.

**Bearer writes and downloads.** `TOKEN_WRITES` is a list of 57 operation names kept in three copies (`mr-mantle/script/PassAuthority.js`, `mr-mantle/script/PassApi.js`, `mr-pass/service/pass/Transport.js`): Billing 1, Supplier 5, Support 10, Shop's cart 6, checkout 13, account and downloads 5, email preferences 3, cart recovery 1, Sales 1, Marketing 12. A name in it is a write the authority takes with no session and no delegation from a registered client; over REST it also takes the write from any caller that sends its own business-host session's token, and the limits are then keyed by that caller's address. The service behind it checks the link, capability or limit itself. A download operation answers a `location` that the transport streams with authorization off: `getShopProductImage`, `getShopReviewImage`, `getShopDownload`, `getShopThemeAsset`, `getSalesQuoteDocument`, `getSalesOrderDocument`, `getCaseFile`, `getReturnLabel` and Smithy's `downloadArchive`, `downloadReleaseAsset` and `downloadArtifact`. In each of the Shop and Support ones the location is a stored column of a row the service has matched to the store, the release, the case or the return; no request value is put into a location. Over REST and gRPC the authority removes `location` from the answer; in local mode `Facade.js` reads it. Each download answer has `X-Content-Type-Options: nosniff` and a `Content-Disposition` of `attachment` unless the service marks it inline.

**Response headers.** `Pass.xml` sets headers on every page before it renders (`screen/Shared/Headers.js`): `Cache-Control: no-store`, `Referrer-Policy: same-origin` and `Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; font-src 'self' data:; connect-src 'self'; img-src 'self' data: [the brand logo's https origin]; media-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'` (default-src and the rest since SEC-PSF-04; `'unsafe-eval'` stays while the islands compile in the browser). `frame-ancestors 'none'` is on every route. `form-action` also allows `https://accept.authorize.net` and `https://test.authorize.net` on three routes only: Shop's `/PaymentRelay` and `/MethodRelay` and Marketing's `/RegistrationRelay`. Shop's catalog routes and Smithy's read pages answer `Cache-Control: public, max-age=60` with `Vary: Cookie` only for a request with no signed-in user and no `moqui.session`, `moquiSession` or `JSESSIONID` cookie; any other request to them is `no-store`.

## The frontend

This section adds to the summary under [How PASS reaches the authority](#how-pass-reaches-the-authority); a fact stated there is not repeated.

**The public site.** mr-pass has 171 screens and each is `require-authentication="false"`. A PASS site exists only where the runtime conf declares it; the example confs are `runtime/conf/MoquiSitesConf.xml`, `runtime/conf/pass/MoquiPassConf.xml` and `runtime/conf/full-stack/MoquiEdgeConf.xml`. The framework writes the conf's site id into the request's parameters as `siteId` and as the bound site (`crates/moqui-core/src/screen/public_site.rs`). `Pass.xml` calls `getSiteInfo` with that site and the request's host. The framework's request logins are read by `authenticate` (`crates/moqui-core/src/screen/mod.rs`) before the public-site routing and before the check that refuses framework routes on a host. So a request to a site page that carries an `api_key` or `login_key` header, Basic credentials, or `authUsername` and `authPassword` is signed in as that framework user on the site's host, also where `/Login` is 404.

**The resolver in detail.** The framework calls the resolver for every path under one of the `<public-site>`'s mounts that is not a reserved framework path. `ShopPreview` is a subscreen of `Pass.xml` that `service/pass/Apps.js` does not list; it is reached only on a preview host. A forum `held-mail` token must match `[A-Za-z0-9._~-]{8,200}`. The patterns hold only for the named path forms: a request that names the screen itself (`/shop/themeAsset?themeDigest=...`, `/forum/HeldMail?token=...`) gives the same values as request parameters, and the resolver checks none of them. Smithy paths go through their own grammar (`service/pass/SmithyRoutes.js`), which checks names by segment, asks the authority (`resolveSmithyPath`) and answers only the screens of its `BUILT` list. When the resolver ends Not Found it asks the site's table of old paths (`screen/Smithy/Smithy.js` `movedPath`) and answers a 301 through `Smithy/redirect`. The resolver and `Pass.xml` ask `isPreviewHost` (`screen/Shop/ShopPreview.js`), which calls `mantle.public.ThemeServices.get#PreviewHost`; when that call throws, the error is logged and the answer is false, so the host is served as a live host of the site, the Account pages included. The framework's own `host-check-service` call for the same host refuses the route when the check fails ([Host routes and servlets](Attack-Surface-Routes.md#host-routes-and-servlets)).

**The facade in detail.** The two schemas hold 422 operations and 420 of them have a route. `Schema.js`, `SmithySchema.js` and `Routes.js` are byte-identical to Mantle's three files. An operation name is a literal in the page that calls it. A request chooses the operation in two places only: among the forms of the page it posts to (`formAction`, `screen/Shared/View.js` `save`), and among `storeDraft`, `updatePost` and `publishPost` on `Forum/Compose/publish`. A page copies from the request only the fields the operation's schema lists (`View.js`).

**Login keys in local mode.** Before a local-mode call the facade applies the authority's login-key rule (`mr-pass` `Facade.js` `checkLoginKey`): a request with an `api_key` or `login_key` header, a user signed in by a login key (`ec.user.loginKeyKind`) or a session a header login started (`moquiHeaderLogin`) is refused, with the authority's access-denied text, unless the key is a device's and the operation is one of `PassAuthority.js` `APP_KEY_OPERATIONS` (SEC-PSF-01, fixed). An access token is scope `git` and signs in to no PASS page at all (SEC-PFS-61). A header-authenticated request still skips the transition's session token check (`crates/moqui-core/src/screen/render.rs`, `header_authenticated`), so the only header-login writes on a PASS page are an installed app's operations with a device key. On the authority's servlet the same rule holds ([The authority](#the-authority)).

**The remote transports.** `pass_backend_transport` chooses REST or gRPC; when it is empty the frontend uses gRPC only where the host has it and an endpoint is set. Over REST path values are percent-encoded, a `GET`'s fields go as query parameters and any other method's as a JSON body. A 401 clears the session's delegation, and a `GET` is then asked again without it. A visitor sees an error's own text only for 409 and 422 (its first line, 300 characters); any other failure shows a fixed text. A REST download forwards the authority's status and headers except the hop-by-hop ones, `Content-Length`, `Set-Cookie`, `x-csrf-token` and `moquisessiontoken`. A spec (`test/Marketing/MarketingAccess.spec.js`) compares the three `TOKEN_WRITES` copies. A remote frontend keeps the answers to fourteen anonymous catalog reads (`CACHED_READS`, `getSiteInfo` among them) in a 512-slot cache for 60 seconds, keyed by site, operation, input, locale, currency, the site's generation and its theme release. It does so only for a request with no framework user, no delegation and no `token` input, and it does not keep an answer that says `authenticated`.

**Downloads.** In local mode a page streams a file from the `location` the operation's Mantle service answers; each operation name is a literal in the page. `Facade.downloadFile` reads the location with authorization disabled for `getShopReviewImage` and `getShopProductImage` (`/shop/media`), `getSalesQuoteDocument`, `getSalesOrderDocument`, `getCaseFile`, `getReturnLabel`, `downloadArchive`, `downloadReleaseAsset` and `downloadArtifact`. `Facade.downloadRanged` does so for `getShopDownload`, and passes the request's `Range` header only when it matches `bytes=\d*-\d*`. `screen/Shop/ShopTheme.js` does so for `getShopThemeAsset`, and answers Not Found unless the answered type and the byte count equal the release manifest's. `Facade.download` (`getAttachment`) and `Facade.downloadExport` (`getExport`) read the location with the request's own authorization. The content type is the one the service answers when it is inert (an image, a font, audio or video, a PDF, plain text or CSV, an archive), else `application/octet-stream`, with `Content-Security-Policy: default-src 'none'; sandbox`, an inline PDF aside (browsers do not show one in a sandbox) (`Facade.js` `servedType`, `sandboxed`; Mantle's `PassAuthority.js` does the same for the remote transports, `PassApi.js` adds the policy; SEC-PSF-08, fixed). In the `Content-Disposition` file name `"`, `\`, CR and LF are replaced; a forum thumbnail is `inline`, and Smithy sets its own. `Cache-Control` is `no-store`, except `public, max-age=60` when the service names exactly that value and the theme asset's own value. A Smithy release file, whose type Mantle takes from its name, is so answered as an octet stream unless inert (`x.js` is no script of the site). A run artifact the engine sends itself (`send#RunArtifact`) and a download the frontend forwards from the authority over gRPC are answered the same way by the framework (`web::is_inert_content_type`, the same list; `web::USER_FILE_SANDBOX`). Smithy's raw file route answers `text/plain`, one of four image types or `application/octet-stream`, with `Content-Security-Policy: default-src 'none'; sandbox`. In remote mode the same page code forwards the authority's download.

**Page caching and the session token.** The Shop routes that may answer `public, max-age=60` are Home, Categories, Search, a product, a category, a page, `sitemap.xml` and `robots.txt`. Smithy's are its read pages; `/-/issues`, merge requests, pipelines, the forum and the other sections `Headers.js` lists stay `no-store`. A page that answers `public` carries no session token (`passPublicPage`: the `moquiSessionToken` meta tag is left out of `screen/Shared/Header.html.fancy`). The framework sends no session cookie with a public answer to an anonymous request that brought none (`crates/moqui-core/src/screen/mod.rs` `session_choice`). The tracking servlets (`script/TrackingLib.js`) set `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow` and `X-Content-Type-Options: nosniff`.

**Transitions.** The 171 screens declare 231 transitions. 137 are `method="post"`. Two of those have `require-session-token="false"`: `Account/Unsubscribe/oneClick`, which calls `applyOptOut`, and `Account/EmailPreferences/oneClick`, which calls `applyOneClickUnsubscribe`; each acts only on the `token` it is given. 37 are `method="get" read-only="true"` (downloads, feeds, redirects, island state). 57 declare no `method` and are not read-only: every `save` of the Account, Forum, Members and Sites pages; `Forum/Compose` `publish`, `preview`, `upload` and `removeAttachment`; `Forum/HeldMail/claim`; the `read` of a topic and of a conversation; Shop's `Cart` (`add`, `quote`, `update`, `remove`, `applyCode`, `removeCode`), `Checkout` (`begin`, `contact`, `addresses`, `delivery`, `payment`, `submit`, `resume`), `Downloads/file` and `PaymentMethods/return`. The rule for such a transition is in [CSRF](Attack-Surface-Web.md#csrf): the session token is checked on POST, PUT, PATCH and DELETE, a request with URL parameters is refused, and a `GET` with none runs with no token check. A parameter the resolver takes from the path is not a URL parameter to that rule. So `GET /forum/held-mail/{token}/claim` calls `claimHeldMail` as the signed-in account, `GET /shop/Checkout/begin` calls `beginCheckout` on the session's cart, and `GET /forum/t/{id}/{slug}/read` calls `markRead`; the rest of the 57 read request parameters. Two page loads write on a `GET`: `Account/Sso` completes a remote single sign-on in its `pre-actions`, and `Marketing/Page` with `?tc=` records a visit (`recordTrackingEvent`). Since SEC-WEB-04 was fixed (2026-11-16), such a GET that another site started is refused with 403 ([CSRF](Attack-Surface-Web.md#csrf)); the app's own links still run them.

**Credentials in URLs.** PASS links carry bearer values in three ways.

- **A query parameter named `token`, `orderToken`, `downloadToken` or `invitationToken`**: invoice pay links, supplier, sales, support and feedback links, registration and subscription links, list unsubscribe, the tracking links and the pixel. The framework's secret-name rule (`crates/moqui-core/src/context/identity.rs`) leaves these out of the request span's `url.query`, the logged `Referer` and a Visit's `initialRequest`.
- **A query parameter named `returnToken`, `recoveryToken` or `confirmToken`** (since SEC-PSF-03, SEC-PSS-02 and SEC-PSS-27): a payment return key on `Billing/InvoicePay`, `Shop/Checkout/return` and `marketing/Register`, a one-time cart recovery token on `shop/Recover`, a receipt's confirmation on `account/EmailPreferences`; the authority's `getPaymentResult` (a `GET`) takes `returnToken`. The secret-name rule leaves these out. The pages still read the old names (`key`, `r`, `confirm`; `returnKey` on the authority) for links sent before; `returnKey` is a secret name too, the others are recorded as sent.
- **The path**: `forum/held-mail/{token}` and its `/claim`, the same under a Smithy group's or repository's `/-/forum/`, Smithy's `/-/held-report/{token}`, and a preview host's `/preview/{token}` (20 to 80 letters and digits). mr-pass's `MoquiConf.xml` declares them as `token-path`s (`/**/held-mail/{token}`, `/**/-/held-report/{token}`, `/preview/{token}`), so the request log, log lines, a Visit and browser telemetry record the token as `:token`, as for the framework's token routes ([Routes](Attack-Surface-Routes.md); `crates/moqui-core/src/screen/token_route.rs`). The held-mail page's sign-in link puts its own path, token included, in `returnTo`, which is redacted where it is recorded.

Billing, Sales and Support pages keep a link's `token` in the page address for the whole visit. Shop, Marketing's Registration and cart recovery move it to the session and redirect to an address without it. `Referrer-Policy: same-origin` keeps all of these from another origin's `Referer`.

**Test-only services.** `service/pass/test/` is loaded with the component: `pass.test.MediaServices.scan#File` and `pass.test.ClassifierServices.classify#Post`, both `authenticate="false"`. No code of the component calls them unless the conf names one in `pass_scanner_service` or `pass_classifier_service`. `scan#File` throws unless `pass_test_scanner` is `true`; when it runs it answers `clean` for every `image/*` type and for any file whose text is not `quarantine fixture`. What else can call a service by name is in [Services and allow-remote](Attack-Surface-Web.md#services-and-allow-remote).

## Account pages and the session

`Account/Login`, `Register`, `SecondFactor`, `Invitation` and `Settings` post to a `save` transition. Its `formAction` picks one of `startSession`, `completeSession`, `beginRegistration`, `verifyRegistration`, `requestRecovery`, `endSession`, `manageAccount` and `startSso`, and `service/pass/Account.js` passes only a fixed list of fields for each (its `allowed` map). In local mode the action calls the matching service of the framework's `org.moqui.public.AccountServices` in process ([Public accounts](#public-accounts)). Before `begin#Registration` the frontend itself checks that the site is published and that its registration mode is `open`, or `invitation` with a token `inspectInvitation` accepts. In remote mode the action goes to the authority's `account/*` routes.

**Single sign-on.** In local mode it starts only for a flow id listed in `pass_sso_flows` and calls `org.moqui.sso.AuthServices.login#User` with the forum mount as the return path. In remote mode the frontend keeps a 32-character state and a 64-character verifier in the session and sends the browser to the authority's `account/sso`. `Account/Sso` (a `GET`) completes the sign-in only when the request's `state` and `handoffId` equal the session's. The authority's side is under [Public accounts](#public-accounts).

**Return paths.** A `returnTo` is kept only when it is a local path: one leading `/` not followed by `/` or `\`, and no white space, backslash or control character.

**What the session holds.** The bearer values of a visitor are listed under Public accounts and delegations above. Each is a session attribute of the frontend, written as the page received it: `passDelegation` by `service/pass/Account.js`, `passAuthorityCookie` and `passAuthoritySession` by `service/pass/Transport.js`, `passPayToken.{attemptId}` by `screen/Billing/InvoicePay.xml`, the checkout keys by `screen/Shop/ShopCheckout.js`, the registration capability by `screen/Marketing/Registrations.js`, and `passSmithyFlash` by `screen/Smithy/SmithyForms.js`. On a remote frontend a signed-in visitor has a delegation and no framework user.

## The authority

The REST servlet's row and the rule for writes are under [How PASS reaches the authority](#how-pass-reaches-the-authority). This section adds what they leave out.

**The REST servlet in detail.** `script/PassRoutes.js` holds 422 routes for 420 operations, and each operation is one Mantle service. `PassApi.js` reads the bearer from `Authorization: Bearer`, the client from `x-pass-client` and `x-pass-client-secret`, and counts a write as a token write only when the client is registered and the method and path match a route of a `TOKEN_WRITES` operation. The session token the `x-csrf-token` header is compared with is never empty: the framework makes one when the session has none (`crates/moqui-core/src/user/session.rs` `csrf_token`). A session and its token are had from any page of the business host. A JSON list or JSON that does not parse is 422. A download is read with authorization off from the location the service answered. It is read whole (`readAllBytes`) and written once, except a ranged Shop download, which is streamed in windows. It is sent with the stored content type, as `attachment` unless the service marks it inline, with the file's `cacheControl` or `no-store`. A refusal is `{code, reason, message, fieldErrors, correlationId}` with status 401, 403, 404, 405, 409, 422, 429 (with `Retry-After: 10`) or else 503. The message is the refusal's own text (300 characters) only for 422 and 409, and only when it matches none of the internal-text patterns of `PassAuthority.js`; any other message is fixed. Each refusal is logged at warn with the correlation id and the error's first line. The servlet sets no CORS header.

**The caller in detail.** Over gRPC the site is the message's `site_id`. A public read (`resolveTrackingLink` is one more) needs a published site. Member and account operations (`findInvoices`, `getShopAccount`, `getAccountHub`, the forum's writes) use the party of `ec.user`. A link operation looks its token up by digest for the site's organization, the record and the scope ([Bearer links](#how-pass-reaches-the-authority)). Site administration (`findSites`, `findMembers`, `findDeliveries`, `checkReadiness`) calls `site(id, true)`. An anonymous caller of Smithy sees what its rules show to nobody in particular. A `customerPartyId` input only narrows the caller's own customers. 21 `GET` operations take a `token` (`getInvoice`, `getPaymentResult`, `getCustomerCase`, `getSalesQuote`, `getMarketingForm`, `inspectOptOut` among them), and `getShopDownload` takes a `downloadToken`.

**Client registration.** A PASS client is three properties on the authority: `pass_client_<id>_secret`, `pass_client_<id>_sites` (a comma list of site ids, matched exactly) and `pass_client_<id>_callback`. The example conf (`runtime/conf/pass/MoquiAuthorityConf.xml`) keeps the secret in `runtime/.env`, not in the conf file. `pass_sso_flows` lists the flows any client may start. `pass_edge_client` (default `edge`) names the client the edge link is. There is no client row in the database and no screen. The client id comes from the request (`x-pass-client`) and names the property that is read. The given and the stored secret are compared as two digests (`singleUseCodeHash`, `org/moqui/public/Account.js` `secretMatches`); a client with no `_secret` property is never registered by a secret. The REST servlet counts a present and wrong secret per address and logs it (`PassApi.js` `checkSecret`, `record#Attempt`, 10 in 10 minutes as the gRPC listener's limit, [Host routes and servlets](Attack-Surface-Routes.md#host-routes-and-servlets)); an address that has used them up is answered 429 for every call naming a secret, right or wrong, until its window ends (SEC-PSA-03). It also counts toward the web protection's `auth-failure` ban of the address, as a wrong password does (`ec.web.noteAuthFailure()`). `GET shop/theme/release` is 404 without a registered client, so its answer tells a right secret from a wrong one.

**A site outside the client's list.** A registered client (a right secret, or a client the transport verified) that names a site not in its `pass_client_<id>_sites` is answered Not Found for every operation of that site, reads included, never as an anonymous caller (`PassAuthority.js` `run`, SEC-PSA-05); the edge link's `pass_client_edge_sites` likewise. The gRPC check of the secret (`crates/moqui-core/src/pass_authority.rs`) looks at no site.

**Login keys.** A request to the servlet whose user came by an `api_key` or `login_key` header, Basic or `authUsername` skips the session token check. `run()` then holds it to the 18 `APP_KEY_OPERATIONS`, all Smithy's (merge requests, fork, the agreement, review comments, threads and reviews, pipeline and job runs, their re-run and retry, issues), and only when `ec.user.loginKeyKind` is `device`. An access token, a session's key and a scoped key call no PASS operation, account actions included. The SSO front channel (`account/sso`, `account/sso-complete`) refuses such a request too. Within those operations the key's account has its normal rights on any site.

**The in-process entry.** The gRPC transport and the edge link call `mantle.pass.PassAuthorityServices.handle#Call` (`authenticate="anonymous-all"`) with `clientVerified` true once they have checked the client themselves. `clientVerified` is a parameter of the service: a caller that can run a service by name with `clientVerified: true` and a `clientId` is that registered client with no secret. What can call a service by name is in [Services and allow-remote](Attack-Surface-Web.md#services-and-allow-remote).

## Public accounts

**Account actions.** `POST account/{session,challenge,registration,verification,recovery,logout,security}` on the servlet (`account.<action>` over gRPC) call `org.moqui.public.AccountServices` `start#Session`, `complete#Session`, `begin#Registration`, `verify#Registration`, `request#Recovery`, `end#Session` and `manage#Account`. All are `authenticate="anonymous-all"`; their bodies are in `runtime/components/base/framework/service/org/moqui/public/Account.js` and run with authorization off. The fields are `username`, `password`, `code`, `emailAddress`, `token`, `action`, `oldPassword`, `newPassword`, `newPasswordVerify`, `visitId` and `invitationToken`; any other is 422.

- **The account.** A public account is a `moqui.security.UserAccount` whose username is its address. It has no group but `ALL_USERS`, and no party until an application makes one (`deferIdentityLink`).
- **Sign-in.** `start#Session` and `complete#Session` are the framework's `login#UserAccount`: the password, then the second factor from the session. A wrong one answers `Sign-in failed` and counts as a failed login of the account ([Login lockout and passwords](Attack-Surface-Web.md#login-lockout-and-passwords)).
- **Registration.** `begin#Registration` needs `pass_verification_template` and a published site whose `registrationMode` is `open`, or `invitation` with a token the site's `inspect#Invitation` accepts for the address. It makes a disabled account with a random password and a `RegistrationChallenge`: a 64-character token, kept as its digest, good for one hour, the earlier ones consumed. The answer is the same sentence whether or not the address has an account. The work differs: for an address with no account the service makes one and sends the verification mail in the call, and for a claimed address it does nothing. An address that is another account's user name and not its `emailAddress` is answered 503, `Registration is temporarily unavailable`. `verify#Registration` takes the token once, writes `VerifiedAddress`, and for a new account sets the password under the password rules and enables it.
- **Recovery.** `request#Recovery` is `org.moqui.impl.UserServices.reset#Password` for any account, staff included, by user name or address, with one answer. For a known account it hashes a reset password before it answers; for an unknown one it returns at once.
- **Account settings.** `manage#Account` changes the signed-in user's password (`update#Password`, the old one required) or ends one of the user's own other visits.

**Limits.** `record#Attempt` counts in `AccountAttempt` rows of fixed windows. Registration and recovery allow 10 per requester in 10 minutes and 3 per address in an hour; verification allows 20 per requester in 10 minutes. Sign-in (`startSession` and `completeSession` of `public/Account.js`, `throttle('session', userName)`) allows 20 per requester and 10 per user name in 10 minutes, refused with "Wait before signing in again" before any password is checked, besides the account's failed-login count (SEC-PSA-01, fixed). The web protection's `login` rule names `account/session` and `account/challenge` too ([Web protection](Attack-Surface-Web.md#web-protection)), and the example authority conf exempts the PASS servers' addresses from web protection (`<client-rule name="pass-servers" action="exempt">`). The requester is the address a registered client names in `x-pass-client-ip`, else the request's.

**Delegations.** When an account action signs in and the call names a client, `issue#Delegation` answers a 64-character credential for that client and site. Its digest is kept in a `DelegatedSession` row. It is good for 15 minutes; a use in its last 5 minutes extends it, up to 12 hours from issue. It is refused once revoked (`account/logout`), once the account is closed, once the account's password hash or salt changes, or once the issuing visit ends. A closed account is the framework's own test: gone, `disabled` with no `disabledDateTime`, or past its `terminateDate`; a lock set by failed logins (`disabled` with a `disabledDateTime`) does not end a delegation, an SSO completion or an SSO exchange, as the framework keeps a session through such a lock (`authenticateDelegation`, `completeSso`, `exchangeSso`). A call with a delegation runs `ec.user.internalLoginUser` for its account.

**Single sign-on through the authority.** A registered client starts a provider sign-in with `POST account/sso-prepare` (`prepare#Sso`). The flow must be in `pass_sso_flows`, enabled, outbound, and OIDC or OAuth. The callback is the client's `pass_client_<id>_callback` (an `http` or `https` URL with a path, no `#`, CR or LF), never a value of the request. The client gives a `state` (16 to 80 characters) and a `verifier` (64); the verifier's digest is kept in a `SsoHandoff` row good for 10 minutes. The browser then makes two `GET`s on the business host that need no client. `account/sso?handoffId=` (`start#Sso`) stores the handoff id in the business-host session and starts the framework's SSO login (`org.moqui.sso.AuthServices.login#User`) with a `returnTo` of the second. `account/sso-complete?handoffId=` (`complete#Sso`) needs that session attribute and a signed-in user, writes a 64-character code (its digest, good for one minute) and redirects to the stored callback with `handoffId`, `state` and `code`. `handoffId` is the only parameter either takes. A request signed in by a header is refused, and a session waiting for its second factor is sent to `/Login?returnTo=` first. `POST account/sso-exchange` (`exchange#Sso`, registered client only) takes the code and the verifier once, for the client that prepared the handoff, and answers a delegation.

**On the business host.** A public account signs in on the business host with the same user name and password as on a PASS site, at `/Login` or at `account/session`; a Smithy access token (`createAccessToken`) is a login key of scope `git`, which git over HTTP and the git REST take and nothing else. Nothing marks a public account apart from a staff account with no group, so each grant to `ALL_USERS` is a grant to every public account. BOSS grants no app to `ALL_USERS` (`mr-boss/data/BossSetupData.xml`). An app password (DAV, SFTP, XMPP) is made only from `BasicComms/Settings/ChatApps.xml` and `Commons/Settings/Sync.xml`. The seed data grants `ALL_USERS`:

- **Screens**: `apps/ScreenTree.xml`, `apps/AppList.xml` and `apps/Terminal.xml` (`SCREEN_TREE`, view; `webroot/data/WebrootSecurityData.xml`).
- **REST paths**: `/moqui/git` and `/moqui/hosting` (`tools/data/ToolsSecurityData.xml`), and `/mantle/my` (`MANTLE_MY_API`, inherited: `userOrgInfo`, `noticeCounts`, `tasks`, `payments/{paymentId}/authorizeNet` and `payTrace`).
- **Git**: `AT_GIT_REPOSITORY` through the authorization service `mantle.work.GitServices.check#GitRepositoryAuthz`.
- **Framework services**: `TerminalServices`; `DriveDeviceServices`, `ConstitutionServices`, `XmppClientServices` and `MantleDavServices` (each `AUTHZT_ALWAYS`); `ExpressionServices`, `ResourceOwnerServices`, `OwnedResourceCall`; the `Admin*Services` groups (access, device, audit, configuration, identity provider, connection, protocol, operation, message type, transfer, backup, readiness).
- **Application services**: `mantle.party.IdentityServices.*`; the owned-resource, import-row, readiness and transfer services of Sales, Marketing, People, Maintenance and the payment gateway; BOSS's `ironstone.admin.LifecycleServices.request#Provisioning` and `request#AccessEnd`.

The seed data's comments say each of those services checks its own permission or owner.

## Sites, members and the account hub

`mantle.public.SiteServices` runs each operation through `service/mantle/forum/Forum.js` `execute` (or `SitePages.js`), which runs the method with authorization disabled after the schema check. The caller is the delegation's or session's user; no input names it.

- **Site configuration.** A staff operation calls `site(id, true)` (`service/mantle/forum/ForumCore.js`), which needs the site's owner (an active `PublicSiteParty` row of the user's party with role `owner`, in state `active`, not suspended) or an operator. An operator is a member of the framework's `ADMIN` group (`ec.user.isInGroup('ADMIN')`). A site that is not published is NotFound except to its owner, an operator or an internal party. `createSite` needs an operator and has no PASS route. Host bindings and the target of an app mount (an organization or a store) are written by an operator only. `updateSite` accepts a subscription page only as an `https://` address or a local path of one leading `/`.
- **Membership.** `joinSite` needs an open registration mode or a current access grant of the site (`An invitation is required` otherwise). `setSiteRole` signs the caller in again with the password and code of the input (`org.moqui.impl.UserServices.login#UserAccount`) before it changes a role. A profile's bio is passed through `StringUtilities.cleanHtml`. `getProfile` answers a profile to anyone when its discoverability is `public`, to active members when `members`, else to its owner only.
- **Invitations.** `createInvitation` needs the site's owner or an operator; the token is two generated ids joined; the row keeps a hash of the token and of the lower-cased address, and its scopes are empty. `inspectInvitation` is a `GET` (`invitations/inspect`) that needs no sign-in: the row is found by site and token hash, and a revoked, redeemed or expired one, and a wrong address beside a good token, are NotFound. `redeemInvitation` is a `POST` for a signed-in account whose verified current address has the invitation's hash, refused (as `joinSite`) when the account's membership is suspended or was ended by someone other than the member (SEC-PSS-43); it gives the party a contact grant (`ExternalAccessContact`, `bindContact`) for each scope the invitation holds. An invitation with scopes is made by `ExternalAccess.js` `invite`, which asks the app's permission in the organization (Billing `RECEIVABLE_EDIT`; Supplier `PAYABLE_EDIT`, `PURCHASE_ORDER_EDIT`; Support `SUPPORT_CONTACT_INVITE`; Sales `SALES_CUSTOMER_INVITE`).
- **Site pages.** `get#SitePage` is the site page services' (`SitePages.js`) for a `sitePageId`, a `routePath` or the roles `delivery`, `returns`, `privacy` and `terms`, and Forum's for the other roles. `publish#SitePage` with a `sitePageId` is the site page services'; without one it is Forum's role page publication (`Forum.js` `publishSitePage`), which needs the site's owner or an operator, the wiki's update right to the page, and the page in the site's `publishingWikiSpaceId` or in a space the caller administers (`get#WikiPageAccess` `canAdmin`), with one refusal for a missing page, another space, no update access or another revision. `updateSite` takes a new `publishingWikiSpaceId` only of a space the caller administers (SEC-PSS-42, fixed).
- **Access grants.** `setAccessGrant` needs staff of the grant's scope (`staff(siteId, scope)`), and a caller cannot grant itself. A grant's target is the site, a category of that site, or an article, which is any existing `moqui.resource.wiki.WikiPage` id. Binding a subscription resource needs the site's owner and an operator.
- **Account hub and email preferences.** `mantle.public.AccountHubServices` `get#AccountHub`, `get#EmailPreferences`, `store#EmailPreferences` and `apply#OneClickUnsubscribe` (`service/mantle/public/AccountHub.js`) run with authorization disabled after their own checks; the last three are in `TOKEN_WRITES`. The site must be published. `getAccountHub` needs a signed-in account with a party. Email preferences take one of three callers. A list link's token (`mantle.party.ConsentServices` `create#UnsubscribeToken`: `ec.user.randomString(32)`, kept as a hash; the service's description says it does not expire unless its maker gives a date or days) reads the organization's name, the address masked and the token party's lists, and changes only through `apply#UnsubscribePreferences` with that token; each lookup (`resolve#UnsubscribeToken`, `apply#UnsubscribePreferences`) counts first against the requester, 100 in ten minutes (SEC-PSS-44). The token still has no default expiry and can subscribe the party again to that organization's lists it left (decision open). A receipt's confirmation code (`{checkoutId}.{32 random characters}`, its digest on the `StoreCheckout`, bound to the site, valid `limits.confirmDays` days) reads and confirms that checkout's pending choices. A signed-in account changes its own party's. `applyOneClickUnsubscribe` unsubscribes the token's list. `apply#CheckoutOptIn` and `make#OptInConfirmLink` in the same service file are `anonymous-all` and take plain ids; whether a PASS route names them was not checked.
