# Attack surface: public applications (mr-pass and Mantle)

The public applications: mr-pass and the Mantle (mr-mantle) services its operations reach. The PASS authority's gRPC service is a row under [Host routes and servlets](Attack-Surface-Routes.md#host-routes-and-servlets), and its edge link form is under [Edge node](Attack-Surface-Cluster-Edge.md#edge-node). The staff applications are in [Attack-Surface-Apps-BOSS.md](Attack-Surface-Apps-BOSS.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## How PASS reaches the authority

mr-pass (`runtime/components/addon/mr-pass`) is the public frontend and holds no business data. Every page calls a named operation through `pass.Facade.call#Operation` (`authenticate="anonymous-all"`, `service/pass/Facade.js`). The name must be a key of `service/pass/Schema.js` or `SmithySchema.js`, and every top-level key of the input must be one of that operation's `fields`; nested values are not checked there. `siteId` is the site the runtime conf binds to the host (`<public-site>`), never a request value. The authority is the node that runs mr-mantle. It maps an operation to one Mantle service through `script/PassRoutes.js` and `service/mantle/forum/ForumSchema.js` or `service/mantle/smithy/SmithySchema.js`; mr-pass's `Schema.js`, `SmithySchema.js` and `Routes.js` are copies of those three files. Every such service is `authenticate="anonymous-all"`, takes one `input` map and finds its caller itself. Nothing reads a service's `allow-remote` attribute ([Services and allow-remote](Attack-Surface-Web.md#services-and-allow-remote)): the route table and the two schemas are what bound the set a request reaches.

**The route resolver.** `pass.RouteServices.resolve#Route` (`authenticate="anonymous-all"`) is the `resolver-service` of a PASS `<public-site>`. The framework calls it with the conf's site id, the request's host and the path. It reads the site's mounts from the authority (`getSiteInfo`) and takes the longest mount whose prefix the path starts with; with none the answer is Not Found. For every app but Smithy a path that contains `..` is Not Found. The mount's app names a root screen from `service/pass/Apps.js` (`forum`, `account`, `members`, `sites`, `billing`, `supplier`, `support`, `sales`, `marketing`, `shop`, `smithy`). Named path forms are checked by pattern and become screen parameters that replace request parameters of the same name (Shop: `products/{id}/{slug}`, `categories/{id}/{slug}`, `pages/...`, `Orders/{id}`, `Subscriptions/{id}`, `robots.txt`, `sitemap.xml`, `feeds/{key}.{xml|csv|json}`, `theme/{64 hex}/{path}`). Any other path is the app's root screen name followed by the rest of the path as written, so every subscreen and transition of a mounted app is reachable by its own name with its own request parameters. The framework refuses a resolver answer that does not start with `/`, starts with `//` or contains `..` (`crates/moqui-core/src/screen/public_site.rs`).

**Local mode.** With `pass_backend_url` empty the facade calls the operation's Mantle service in process with `{input}`, as the request's own user. These checks of the authority's `run()` (`mr-mantle/script/PassAuthority.js`) do not run in that mode: the registered client and its sites, the delegation, the rule for writes below, the rule that an operation has a route (`createSite` and `findModerationScopes` have a schema entry and no route), `CLIENT_READS`, the login-key rule (`APP_KEY_OPERATIONS`), and the removal of `location` from a download's answer. What holds in local mode is the frontend's schema check, the screen transition's session token ([CSRF](Attack-Surface-Web.md#csrf)) and each Mantle service's own checks.

**Remote mode.** With `pass_backend_url` set, `service/pass/Transport.js` sends each operation to the authority over REST (`{pass_backend_url}/rest/s1/pass/v1/sites/{siteId}/{route}`) or gRPC (`pass_backend_grpc_url`, or `edge:` for the edge link). Each REST call carries `x-pass-client` (`pass_client_id`), `x-pass-client-secret` (`pass_client_secret`) and `x-pass-client-ip` (the visitor's address as the frontend sees it); a signed-in visitor's delegation goes as `Authorization: Bearer`. The REST client has a 30 second timeout and follows no redirect; the code does not require an `https` URL. A file goes as multipart after a 10 MiB check. Before it sends a write with no delegation the frontend refuses it unless the operation is `applyOptOut`, `addCartItem`, `getCart`, `requestSubscription`, `submitMarketingForm`, `recordTrackingEvent`, `reserveRegistration`, or a `TOKEN_WRITES` name with a `token`, `key` or `orderToken` in its input.

**The authority's rule for writes.** `run()` takes the client as registered only when `clientRegistered` accepts the client id, the secret and the site. A delegation from an unregistered client is refused; a delegation is checked for the client and site it was issued to (`authenticateDelegation`) and signs its account in for the call. When the servlet has not already checked the session token, a write (an account action, or a route whose method is not `GET`) is refused unless it is an account action from a registered client, `applyOptOut`, a `TOKEN_WRITES` operation from a registered client, or carries a delegation. `CLIENT_READS` (`getShopThemeRelease`, `getShopThemeFiles`, `getShopThemeAsset`) answer NotFound without a registered client. A registered client's `visitorAddress` becomes the requester key (`client:{id}:{address}`, 64 characters of the address) of every Mantle limit keyed by `requesterKey()`.

**Who the caller is.** The caller of an operation's service is `ec.user`: the account a delegation names, in local mode the frontend session's user, or over REST the business-host session's user. No service trusts a user or party id from the input. The site is the path's `{siteId}` and an app's organization or store is the site's mount of that app (`PublicApps.js` `mount`), never an input. The operations fall into classes: public reads of a published site (`getSiteInfo`, the Shop catalog, Marketing's pages) that name no caller; member and account operations that need a signed-in user and use its party; link operations that take a `token`, `orderToken`, `downloadToken`, or a reference with its `key` or `returnKey`; site administration that needs the site's owner or the `ADMIN` group; and Smithy, which takes its actor from `ec.user`. Link operations that are `GET` carry the token in the query string to the authority.

**Public accounts and delegations.** A public account is a framework user account. Signing in through `account/session` calls `org.moqui.impl.UserServices.login#UserAccount`, which asks no group or flag, so the same name and password sign in on the business host, and `POST .../account/session` with the session token signs a business-host session in. In remote mode an answered credential rotates the frontend's session and is kept there as `passDelegation`. The frontend's session also holds the other bearer values a visitor has: the authority's session (`passAuthorityCookie` over REST, `passAuthoritySession` over gRPC), a Shop cart capability (`passShopCart:{site}`), checkout return keys (`passShopCheckout:{site}`), guest order tokens (`passShopOrders:`, `passSalesOrders:`), an invoice pay token per attempt (`passPayToken.{attemptId}`), a card setup reference and form (`passShopMethodSetup:{site}`), a cart recovery token and a registration capability.

**Bearer links.** A PASS bearer link is a `mantle.party.ExternalAccessCapability` row, checked by `check()` of `service/mantle/party/ExternalAccess.js`. A token is 48 random characters (`ec.user.randomString(48)`); only its digest (`ec.user.singleUseCodeHash`) is stored. A lookup accepts a text of 32 to 128 characters and finds the row by digest. Each lookup first counts against the requester's limit, 100 in ten minutes (`org.moqui.public.AccountServices.record#Attempt`, key `access-token:{requester}`), and a requester over it is refused (`Tarpit`, `RATE_LIMITED`) whether the token is good or not. A row must be unrevoked and in its dates, of the record type asked, of the record id when the request gives one, hold the scope asked, and be of the organization the page serves when the caller of `check()` gives one. The record is resolved again and must still have the row's organization and party. Every failure is the same NotFound. The record types and scopes are `Invoice` (`InvoicePay`), `Order` (`BillUpload`, `OrderAcknowledgement`), `Quote` (`QuoteResponse`), `RequestCategory` (`CaseIntake`, reached by its token only), `Request` (`CaseView`), `ReturnHeader` (`ReturnRma`), `FormInvitation` (`CaseFeedback`, `MarketingSurvey`), `EventRegistration` (`RegistrationView`, `RegistrationCancel`) and `SalesOrder` (`OrderView`, `Download`, `RenewalAction`, `QuoteView`, `QuoteRespond`). A link lasts `validDays` (60 by default) or to `thruDate`, at most 366 days. With no token the caller must be signed in and the page must name its organization: either the account's own party is the record's party (`selfOf`, for the kinds marked `self`: the same party, not internal, not disabled, no employee, agent, member or representative relationship to an internal organization, the account's current email address verified), or the account holds a contact grant (`ExternalAccessContact`) for the app, the organization and the record's party.

**Bearer writes and downloads.** `TOKEN_WRITES` is a list of 57 operation names kept in three copies (`mr-mantle/script/PassAuthority.js`, `mr-mantle/script/PassApi.js`, `mr-pass/service/pass/Transport.js`): Billing 1, Supplier 5, Support 10, Shop's cart 6, checkout 13, account and downloads 5, email preferences 3, cart recovery 1, Sales 1, Marketing 12. A name in it is a write the authority takes from a registered client with no session and no delegation; the service behind it checks the link, capability or limit itself. A download operation answers a `location` that the transport streams with authorization off: `getShopProductImage`, `getShopReviewImage`, `getShopDownload`, `getShopThemeAsset`, `getSalesQuoteDocument`, `getSalesOrderDocument`, `getCaseFile`, `getReturnLabel` and Smithy's `downloadArchive`, `downloadReleaseAsset` and `downloadArtifact`. In each of the Shop and Support ones the location is a stored column of a row the service has matched to the store, the release, the case or the return; no request value is put into a location. Over REST and gRPC the authority removes `location` from the answer; in local mode `Facade.js` reads it. Each download answer has `X-Content-Type-Options: nosniff` and a `Content-Disposition` of `attachment` unless the service marks it inline.

**Response headers.** `Pass.xml` sets headers on every page before it renders (`screen/Shared/Headers.js`): `Cache-Control: no-store`, and `Content-Security-Policy: script-src 'self' 'unsafe-eval'; img-src 'self' data: [the brand logo's https origin]; media-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`. The policy has no `default-src`, `style-src`, `connect-src` or `frame-src`. `frame-ancestors 'none'` is on every route. `form-action` also allows `https://accept.authorize.net` and `https://test.authorize.net` on three routes only: Shop's `/PaymentRelay` and `/MethodRelay` and Marketing's `/RegistrationRelay`. Shop's catalog routes and Smithy's read pages answer `Cache-Control: public, max-age=60` only for a request with no signed-in user and no `moqui.session`, `moquiSession` or `JSESSIONID` cookie.

## Shop

PASS Shop is `mantle.order.ShopCartServices`, `mantle.order.ShopCheckoutServices`, `mantle.party.ShopCustomerServices`, `mantle.product.ShopFulfillmentServices`, `mantle.product.ShopSubscriptionServices`, the review services of `service/mantle/product/StoreReviews.js` and the theme reads of `mantle.public.ThemeServices`, each service `authenticate="anonymous-all"`. The store comes from the site's enabled `shop` mount (`service/mantle/product/ShopContext.js` `shopOf`: a published site, a store of an internal organization), never from the request.

### Cart

`mantle.order.ShopCartServices` (PASS operations `getCart`, `addCartItem`, `updateCartItem`, `removeCartItem`, `applyPromoCode`, `removePromoCode`, `attachCart`, `releaseCart` and `recoverCart`; `service/mantle/order/ShopCart.js`). A cart is an open `OrderHeader` with a `StoreCartAccess` row. The caller is the holder of the cart capability (`input.token`, 48 random characters, only its digest stored, kept by the frontend in its server session) or the signed-in account, whose own cart is found by its party. No operation takes an order id. A capability reaches a cart only on the same site, store and currency, while the row is unrevoked and unexpired and the order open; a cart attached to an account is reached only by that account. Each capability lookup counts against the requester (600 in ten minutes). The first `addCartItem` with no cart makes one: a guest `Party`, `Person` and `PartyRole`, an order and the access row, limited to 30 carts a requester in ten minutes. The request gives a product, an option, a quantity (1 to 999), a line id, a code, the revision seen and an operation id. The unit price is the authority's (`offersOf`) at each add and change. A cart holds 50 lines. A promo code is tried at most 20 times a requester in ten minutes and every refusal reads the same. `attachCart` needs a sign-in, attaches or merges the session's guest cart and rotates the capability. `releaseCart` rotates the capability of every open cart of the account on the site. `recoverCart` (`service/mantle/order/CartRecovery.js`) takes a one-time token (48 characters, its digest on the access row) and needs the signed-in account whose cart it is; a visitor is answered 401 and the token is kept; lookups are limited to 120 a requester in ten minutes. A cart with a payment in progress or a submitted checkout is not changed.

### Checkout and payment

`mantle.order.ShopCheckoutServices` (thirteen PASS operations, `beginCheckout` to `getOrderConfirmation`, all in `TOKEN_WRITES`; `service/mantle/order/ShopCheckout.js`). One `StoreCheckout` row coordinates a cart to one placement. Every write needs the cart's holder; a call reached any other way is NotFound. After submission the checkout is also read by its reference (the `checkoutId`) with a return key (40 random characters, made at each submit, only its digest kept, valid while the checkout is open and for a day after it completes), by the capability of a cart placed less than a day ago, or by the signed-in customer with the reference. The reference and key read a minimal view (the state, the amount due, the attempt's state and provider address) and the order's id, date and status; they are given no contact, address, line or order link. The request gives contact fields, address fields or one of the account's own addresses, a delivery option of the current quote, a payment option, the revision and terms version seen, opt-ins and an operation id. No price, total, tax, delivery charge, customer or status is read from the request. `submitCheckout` re-quotes delivery, then under the order's lock checks every line's price and availability, the promotion limits, the quote, the tax and the terms; a change answers `REVIEW_REQUIRED` and nothing is charged. The payment's amount is the order's total. A total of zero or less skips the gateway. The gateway is called through `authorize#SinglePayment` with a return address on the site's canonical host and Shop mount (`/Checkout/return?ref=…&key=…`), never a caller's origin. The payment's state is read from the `Payment` row's status, which only the gateway lookup (`get#SinglePaymentGatewayDetails`), the provider's webhook and the reconciliation job change; nothing the browser's return brings back is read. A result read asks the provider at most once a second. `place#Order` runs once the payment is approved, only when the order's revision and total are still the frozen ones. `getCheckoutPaymentForm` (fields `siteId`, `reference`, `key`) answers a fresh Authorize.Net Accept Hosted form address and token for a pending attempt whose amount equals the frozen amount; the token is not stored. A guest's order link (`orderToken`, the `SalesOrder` kind's `OrderView`, with `Download` for a digital order, 366 days) is issued once, only to a call that came by the cart's own capability. Stored operation results leave out the return key, the order token and the cart token.

### Relay and result pages of mr-pass

`screen/Shop/PaymentRelay.xml`, `MethodRelay.xml` and `PaymentResult.xml` are `require-authentication="false"` and run their script in `pre-actions`. `PaymentRelay` (`ShopCheckout.js` `relayPage`) reads `ref` (cut to 40 characters of `[A-Za-z0-9_-]`), calls `getCheckoutPaymentForm` with that reference and the key the session keeps for it, and writes a form whose `action` is the answered `formUrl` and whose hidden fields are the answered fields, each escaped; the page's same-origin script (`Checkout/enhance`) submits it. The checkout relay does not itself check the host of `formUrl`; the route's CSP `form-action` does. `MethodRelay` (`ShopAccount.js` `relayPage`) reads the form the session kept from `beginPaymentMethodSetup`, removes it from the session, and writes it only when its `formUrl` starts `https://accept.authorize.net/` or `https://test.authorize.net/`; otherwise it redirects to `PaymentMethods`. `PaymentResult` has one transition, `state` (`method="get"`, `read-only="true"`), which answers the checkout's state for the reference and the session's key. The pages are `no-store` and cannot be framed (`frame-ancestors 'none'`, see the headers above). `PaymentMethods/add` and `PaymentMethods/end` are `method="post"`; `PaymentMethods/return` has no `method`.

### Orders and the guest order link

`mantle.party.ShopCustomerServices` (fourteen services; `service/mantle/party/ShopCustomer.js`). An order is reached by a guest's order link (`input.orderToken`, the `SalesOrder` `OrderView` capability, its one order, which must be of the site's store; an `orderId` beside it must be its own) or by the signed-in account in the self relationship, for an order of the store whose every part has the account's party as customer and the store's organization as vendor. Another's order and an unknown one are the same NotFound. `findShopOrders`, `getShopOrder` and `getShopOrderDocument` are the link's reads; `getShopOrderDocument` answers only an invoice that is one of the reached order's. `previewReorder` and `reorder` drop the link and need the account. A verified account's first read merges into its party each guest party of a completed guest checkout of the store whose typed contact email equals the account's email (`mantle.party.DuplicateServices.merge#Parties`), when that party is still only the guest of that one cart.

### Addresses and payment methods

`get#Addresses`, `store#Address`, `end#Address`, `get#PaymentMethods`, `begin#PaymentMethodSetup`, `finish#PaymentMethodSetup` and `end#PaymentMethod` each need a signed-in account in the self relationship (`requireSelf`); a signed-in account outside it is `Unauthorized`. `store#Address` takes a name, two address lines, a city, a postal code, a country and a state (`address1` at most 255 characters, `city` 100, `postalCode` 60; the country must be a `moqui.basic.Geo` of type `GEOT_COUNTRY`, the state any existing `Geo`) and a purpose of billing or shipping. A change names a `contactMechId`, which must be a postal address with a current `PartyContactMech` of the caller's party, and the revision shown. An account keeps at most `limits.addresses` addresses. The store's carrier validation (`mantle.shipment.CarrierServices.validate#PostalAddress`) is called when the store has a shipping gateway with one; its suggestion is answered and not applied. `end#Address` ends only the caller's party's own purposes of that address. `begin#PaymentMethodSetup` calls the store gateway's hosted setup service with the caller's party, a 20-character reference and a return address made from the site's Shop mount (`/PaymentMethods/return?setup=…`), and answers the provider's redirect address or form. `finish#PaymentMethodSetup` calls the gateway's setup sync service with the caller's party and the request's `setupReference`. `end#PaymentMethod` ends only a method whose `ownerPartyId` is the caller's party and that is not ended; when recurring orders use it the call needs `confirm`, and each contract that renewed with it loses its consent. A card is entered on the gateway's hosted page; the list shows the brand, last four digits and expiry. These functions make no rate-limit call of their own.

### Subscriptions

`mantle.product.ShopSubscriptionServices` `get#Subscriptions`, `get#Subscription`, `begin#SubscriptionPurchase`, `change#SubscriptionMethod`, `cancel#Subscription` and `resume#Renewal` each need a signed-in account in the self relationship and a contract whose store is the site's and whose `customerPartyId` is the account's party; anything else is NotFound. A write names the contract's revision. A new card for renewals must be one of the account's own.

### Digital downloads

`mantle.product.ShopFulfillmentServices` `get#Downloads`, `issue#Download` and `get#DownloadFile` (PASS operations `getDownloads`, `issueDownload`, `getShopDownload`). A grant (`StoreDownloadGrant`) is reached by an order link with the `Download` scope (its one order, with a completed checkout on this site) or by the signed-in verified account (its own grants in the store). `issueDownload` is limited to 60 a requester in ten minutes and makes a `SalesOrder` capability of scope `Download` for the grant's order that lasts ten minutes. `getShopDownload` takes the grant id and that token, checks the capability against the grant's order and the store's organization, checks the grant again (unrevoked, in its dates, its fulfillment completed), counts the download and answers the file's location, which is the `contentLocation` of the grant's `ProductContent` row (type `PcntDownload`). The frontend streams it with authorization off, as an attachment with `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`, a 1 MiB window at a time, honouring one `bytes=start-end` range. The bundled frontend issues the token and streams in one request, so the token is not sent to the browser.

### Product images and reviews

`getShopProductImage` answers a `ProductContent` image of a product public in the store now, only when its `contentLocation` starts `dbresource://` or `component://`, has no `..`, backslash or encoded dot or slash, and ends in png, jpg, jpeg, gif or webp; the content type is the extension's. It is `public, max-age=60` only when the request names the site's current generation. `getShopReviewImage` answers a review image by a digest (16 to 128 characters) only while its review is approved, of the site's store, and its product public; the content type is the stored `image/png` or `image/jpeg`. `submitProductReview` counts against the requester first (30 in ten minutes), then needs a signed-in account with a verified email and, for a first review, a delivered order line of the product; an edit must name the caller's own review. The rating is 1 to 5 and the body at most 5,000 characters of plain text. A photo is staged only after those checks. It must be declared `image/png` or `image/jpeg`, at most three a review, and goes through `service/mantle/party/PortalMedia.js` `stage` (the rules under [Supplier](#supplier)): at most 10,485,760 bytes, the leading bytes must be the declared type's, and the scanner must answer clean. It is kept under the content root at `productReview/{store}/{review}/{seq}.{png|jpg}`, a path made from ids. A new or edited review is `PrvwPending` until staff approve it.

### Themes

A store's theme is a package a Commerce user writes (`COMMERCE_THEME_EDIT`) and publishes (`COMMERCE_THEME_PUBLISH`) in the stores of the user's scope. It is rendered on the public Shop pages of the site (the page kinds home, not-found, category, product, search, page, cart and checkout).

- **The package.** `service/mantle/public/Themes.js` takes paths that match `^[A-Za-z0-9_-][A-Za-z0-9_.-]*(/[A-Za-z0-9_-][A-Za-z0-9_.-]*)*$`, text files ending `.json`, `.html.fancy-locked`, `.css` or `.svg`, and binary files ending `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp` or `.woff2`: at most 300 files, 512 KiB a file and 8 MiB in all. The renderer's own bounds (`crates/moqui-core/src/script/theme/package.rs`) are 2,000 files, 1 MiB a text file, 1 MiB an assembled template and 16 MiB a binary asset named by reference. The renderer takes the package as text; a binary asset is only a reference (`{digest, size, contentType}`) and its bytes are not part of a render. The layout is the whole HTML document (the starter's `layouts/store.html.fancy-locked` begins `<html>` and `<head>`).
- **Expressions.** Each `${}` expression is parsed and checked before any runs (`expr.rs`). A denied name is refused as a variable or a property: `ec`, `sri`, `context`, `raw`, `globalThis`, `eval`, `Function`, `AsyncFunction`, `GeneratorFunction`, `constructor`, `__proto__`, `prototype`, the `__define*__` and `__lookup*__` names, `defineProperty`, `defineProperties`, `setPrototypeOf`, `getPrototypeOf`, `Reflect`, `Proxy`, `Symbol`, `arguments`, `require`, `import`, `fetch`, `XMLHttpRequest`, `WebSocket`, `setTimeout`, `setInterval`, `queueMicrotask`, `Atomics`, `SharedArrayBuffer`, `WebAssembly`, and any name that starts with `$`. A computed property is checked only when it is a string literal or a template literal with no expression; a property name built at run time (`x["con" + "structor"]`) is not seen by this check. `this`, `new`, a function, a class, an assignment, `++` and `--`, `import`, `yield`, `await`, a tagged template, `super`, `delete` and an arrow function with a block body are refused. Each layout, section and block runs through `template::render_locked_bounded` (`compose.rs`), with the view as a JSON snapshot whose values are the template's names, a global object frozen with everything reachable from it (`crates/moqui-core/src/script/template.rs` `SANDBOX_LOCKDOWN`), and that renderer's own ceilings of 5 seconds and 32 MiB.
- **Markup.** Template source is checked before it runs and each render's output is checked again (`markup.rs`, modes `Source` and `Output`). Refused elements: `script`, `iframe`, `frame`, `frameset`, `object`, `embed`, `applet`, `form`, `base`, `portal`, `noscript`, `xmp`, `plaintext`, `noembed`, `noframes`, `math`, `isindex`, `keygen`, `fencedframe`, and the SVG elements `foreignobject`, `animate`, `animatemotion`, `animatetransform`, `set`, `discard`, `handler`, `listener`, and a `style` inside an SVG. Refused attributes: any whose name starts with `on`, and `srcdoc`, `formaction`, `formmethod`, `formenctype`, `formtarget`, `formnovalidate`, `form`, `action`, `ping`, `http-equiv` and `is`. A `<link>` must have a `rel` of `stylesheet`, `icon`, `apple-touch-icon`, `preload`, `canonical`, `alternate`, `next`, `prev`, `author` or `license`. A tag inside `<title>` or `<textarea>`, an unclosed `<style>`, `<title>` or `<textarea>`, an `<svg>` left open in a render's output, and markup that ends inside a tag are refused. The deny lists do not hold `meta`, `link`, `style`, `input`, `button`, `select`, `img`, `video` or `audio`.
- **URLs and CSS.** The `href` of `a` and `area` (and of a `link` with a navigation `rel`) may be a relative address or an `http`, `https`, `mailto` or `tel` address of any host. A resource address (`src`, `poster`, `data`, `background`, `cite`, `manifest`, `srcset`, a stylesheet's `href`) may be relative, on an approved origin, or a `data:` PNG, GIF, JPEG, WebP or AVIF image; any other scheme is refused. A `style` attribute, a `<style>` element and SVG paint attributes that hold `url` are checked as CSS, which refuses `@import`, `expression(`, `javascript:`, `vbscript:`, `-moz-binding`, `</style`, `<!--`, `-->`, `image-set(`, `src(` and the `behavior` properties. The approved origins are the render request's `allowedOrigins`; mr-pass's render call (`screen/Shop/ShopTheme.js` `renderView`) passes none.
- **Limits.** A page is bounded to 100 sections, 100 blocks, composition depth 8, include depth 8, 2 MiB of output, one second a render (a layout, a section or a block), and the locked renderer's page time and memory. The `theme-limits` element of the conf can lower each value, never raise it.
- **What a theme sees.** `get#ShopPage` answers the theme an allow-listed view (`service/mantle/public/ThemeView.js` `contract()`: the fields its `shapes` name, dropping any name that is or ends in secret, token, password, partyid or userid). The cart's and checkout's views carry the store's data only. The frontend makes trusted component HTML from the page's view (`ShopTheme.js` `COMPONENTS`), which the renderer places by placeholder; a placeholder that is not one of the render's own, or that stands in an attribute, a comment, a `<style>` or an `<svg>`, is refused. The components given are those of the page kind, and when the release's `theme.json` has a `requiredComponents` list only the ones it names. A render that fails answers a fixed 503 page; diagnostics go to the log.
- **Reads and assets.** `mantle.public.ThemeServices` `get#ShopThemeRelease`, `get#ShopThemeFiles` and `get#ShopThemeAsset` (`CLIENT_READS`) answer only the release that is the site's Shop mount's active one (`RELEASE_NOT_ACTIVE`, NotFound, for another id). `getShopThemeFiles` takes 1 to 50 paths and answers only files the release pins. `getShopThemeAsset` answers only a binary path the release pins, named with the digest it pins; the bytes at the pinned version are checked against that digest before the location is answered; the type is the extension's (`image/png`, `image/jpeg`, `image/gif`, `image/webp`, `font/woff2`). The frontend serves an asset at `{mount}/theme/{manifestDigest}/{path}` (`sendAsset`): the digest must be the active release's, the path must match `^assets/[A-Za-z0-9_-]+(/[A-Za-z0-9_.-]+)*\.[A-Za-z0-9]+$` with no `..`, and the extension must be one of its asset types, so template source is never served. An SVG is passed through `ec.resource.theme.sanitizeSvg` when served. An asset answer carries `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; img-src 'self' data:`.
- **Previews.** A draft preview (`create#ThemePreview`) lasts twenty minutes; its token is 40 letters and digits and only its digest is stored. `get#ThemePreviewPage` (`anonymous-all`, `service/mantle/public/ThemeAuthoring.js`) answers the draft's files and view only for a token of 20 to 80 letters and digits that is unexpired, of the request's site, on a host of kind `PshkPreview` of that site, whose maker's account exists and is not disabled; anything else is NotFound. The function makes no rate-limit call of its own.

## Forum

The Forum is the PASS app `forum`: pages under `mr-pass/screen/Forum/`, operations under `mr-mantle/service/mantle/forum/`.

**The pattern shared with Smithy.** Every Forum and Smithy operation is a Mantle service that is `authenticate="anonymous-all"`, takes one `input` map and calls `Forum.js` or `Smithy.js` `execute(operation, input)`. `execute` refuses a field that the operation's entry in `ForumSchema.js` or `SmithySchema.js` does not list, checks each value's type (Smithy: a string of at most 4,096 characters, 200,000 for a text field, 8 MiB for a file's text, a list of at most 100 strings), and runs the operation with authorization disabled. The caller is `ec.user`; no input field names the caller, and each operation decides access from that user. A user in the `ADMIN` group is an operator (`ForumCore.js` `isOperator`): on a page an operator counts as the owner of every site and as an Owner of every Smithy group and repository, confidential issues included. A write that takes an `operationId` keeps a `ForumOperationReceipt` row by site, party, operation id and action, with a hash of the input and the answer as JSON without its `token` and `credential` keys; a retry answers the stored result (`ForumCore.js` `receipt`).

**Sites, categories and topics.** `ForumCore.js` `site(id)` answers Not Found for a site that is not published unless the caller is its owner, an operator or internal staff. `site(id, true)` also needs the site's owner (active, not suspended) or an operator; it guards the settings operations (members and roles, categories, mail settings and routes, invitations, `storePolicy`, `storeRule`, `setTrust`, `manageRun`, `startOperation`). `createSite` needs an operator. A category is read when the caller moderates it, or when site and category are published and the category is `public`, or the caller is an active member and the category is `members`, or the caller is on its list or holds a grant. A category bound to a Smithy group or repository is read by no more than view of that scope, and a child category only when its parent is. A private conversation is read through an active participant row and current membership only; staff have no access to it.

**Moderation.** `staff(siteId, contactListId)` with a category needs `canModerate` in that category of that site; with none it needs an operator, or an active, unsuspended member of the site with the role owner or moderator. `getReview`, `decideReview`, `decideReviews` and `escalateReview` find a review item by `reviewId` and the path's `siteId` together, then ask `reviewStaff` with the item's own category. `applyTopicAction` needs `canModerate` on the topic, found in the path's site. `setSanction` needs staff of the site or of the category named, a target that is a member of the site, and a rank above the target's (operator, site owner, site moderator, list owner or the bound scope's Owner, list moderator). `endSanction` finds the sanction by site and id and needs staff of its category.

**Attachments.** `stageAttachment` needs a signed-in user who may upload in the topic or category. A file is 1 byte to `mediaMaxBytes` (at most 10 MiB); its type is the upload's declared content type and must be PNG, JPEG, WebP, GIF, PDF or plain text. The upload is refused unless `pass_scanner_service` and `pass_media_root` are set; the file is written to `<pass_media_root>/<attachmentId>`, scanned and marked `clean` or `quarantined`. No count or total size of one party's staged files is checked; a staged file that no post takes expires after 7 days. `getAttachment` serves only a clean file of the site attached to a post the caller reads, or an avatar of a profile the caller is shown.

**Exports.** `requestPersonalDataAction` (a signed-in member; `export` or `erasure`) and `startOperation` with `export-site` (the site's owner or an operator) make a `ForumExport` row whose file is `<pass_media_root>/exports/<exportId>.zip` and which expires after 7 days. `getExport` answers only a complete, unexpired export of the path's site whose `partyId` is the caller, and asks again for the site's owner or an operator when it is a site export. It answers the row's `location`; `getExport` is in the authority's `DOWNLOADS` list.

**The delivery opt-out.** `inspectOptOut` and `applyOptOut` need no sign-in and no session; the authority takes `applyOptOut` as a write with no delegation. The token is looked up by its hash and the site and is refused after `expiresAt`. Its `ForumOptOut` row names one party and one scope (a category, a topic or the site); applying it writes that party's `ForumDeliveryPreference` for that scope, or for the whole site when asked, and nothing else.

**Inbound list mail and reply by email.** `mantle.forum.DeliveryServices.process#Inbound` (`anonymous-all`) takes a message's `headers`, `fields` and body parts as parameters and gives them to `Forum.js` `processInbound`. The route is the enabled `ForumMailRoute` whose address equals a `Delivered-To` or `Original-Recipient` address with its `+tag` taken off (the `To` and `Cc` addresses when neither field is there). A message stored in a mail account is read only when that account is hosted or shared, its server has no store host, and it holds the route's address (`forumAccount`). The sender is the `From` address. A post needs all of: exactly one enabled `UserAccount` with that email address, a `VerifiedAddress` row for it, and an `Authentication-Results` field of an authserv-id listed in `smtp_authserv_id` that says DMARC passed for the `From` domain, or DKIM passed for a `header.d` (or `header.i`) that is that domain or any parent of it (`gatewayAuthenticated`). With `smtp_authserv_id` empty nothing is taken as authenticated. The listener's own field and its removal of forged ones are in [Mail](Attack-Surface-Mail.md). A reply address is `<local>+<token>@<domain>` of a route. The token is 32 random characters, stored as a hash in `ForumReplyToken` with the site, the topic, the party and 90 days. A tag that is unknown, of another site, revoked or expired is rejected; one issued to another party than the sender's account is held. With no tag the topic is found from `In-Reply-To` and `References` among the `ForumDelivery` rows of the sender's own party. A route whose `targetType` is not `category` (a report address) ignores the tag and files the message through the service the bound app names (`mailReportService`), with the account's `username` as a parameter.

**Held list mail.** A message from an address that is no verified account's is not posted. It is kept as a `ForumHeldMail` row for 30 days when the gateway authenticated the sender's domain, it has no spam verdict and no reply tag, and the route holds mail; its sender is mailed a link `<forum>/held-mail/<token>` at most once a day, and the token is stored as a hash. `claimHeldMail` (`POST .../held-mail/<token>/claim`) needs a signed-in user whose account has a `VerifiedAddress` row for its current email address, equal to the held message's sender; the message is then posted as that account through `publishPost`.

**User text.** A post's source is HTML or Markdown. Markdown is rendered by `ec.resource.markdownHtml`, and either is cleaned by `StringUtilities.cleanHtml` before it is stored (`ForumCore.js` `renderSource`) and again when a post is read. The cleaner is `crates/moqui-lib/src/safe_html.rs`: ammonia's default list, with `data-mention-id`, `data-record-entity` and `data-record-id` added on a `span`.

## Smithy

Smithy is the PASS app `smithy`: pages under `mr-pass/screen/Smithy/`, operations under `mr-mantle/service/mantle/smithy/`, in the pattern described under [Forum](#forum). The git server, its REST, webhooks, mirrors and the pipeline engine are the framework's ([Git](Attack-Surface-Git.md)).

**Who views a group or a repository.** A read starts with `SmithyCore.js` `repository(repositoryId, siteId)` or `group(groupId, siteId)`. Each answers Not Found when the site is not open to the caller or has no enabled Smithy mount, when the row is of another site, or when the caller may not view it. The effective visibility is the narrowest of the repository's, its groups' and, for a fork, its parents'. Public is anyone's. Members-only is an active, unsuspended member of the site. Private needs a role of Guest or higher. A hidden repository or group is viewed by its Owners and the site's owners and moderators only. A fork of a parent that is not public also needs view of the parent. A write then calls `requireRole`, and most writes first call `writer(siteId)`: a signed-in user with a confirmed address (an operator excepted) who is not suspended on the site.

**Members and roles.** `setGroupMember` and `setRepositoryMember` need Owner of the group or repository; no lower role changes a role, its own included. A group, with the groups above it, keeps one Owner whose role has no end. Creating a subgroup, and changing, renaming, deleting, transferring or archiving a group or repository or changing its visibility, ask for Owner. A repository is no wider than its group, and a fork no wider than its parent.

**Issues and conversations.** An issue is read by a viewer of a repository whose issues are on, when its task is public or the caller is a Reporter. A confidential issue is read by the repository's Owners and its reporter only; `findIssues` builds the same rule into its query and its counts, and `searchSite` asks `issueAccess` for each row. An issue's or a merge request's conversation is a `ForumTopic` of kind `record`: `ForumCore.js` `topic()` asks `SmithyScope.js` `recordAccess` for it and refuses the Forum's own operations on it.

**Code reads, raw files and archives.** `getTree`, `getBlob`, `getBlame`, `findCommits`, `getCommit`, `getCompare` and `findRefs` call `repository()` first and then the framework's `get#Git*` services with authorization disabled. Raw (`<repository>/-/raw/<refPath>`) answers text as `text/plain`, a PNG, JPEG, GIF or WebP by its extension, and any other binary file as `application/octet-stream`, with `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, and `Content-Disposition: attachment` for anything but plain text and those images. An SVG or HTML file is sent as `text/plain`. An archive of a branch or tag of a public repository that is not hidden needs no sign-in; any other archive, and one by commit id, needs a signed-in user. No limit of archive builds by client is in Smithy. A README, a docs page, a landing page and release notes are Markdown, rendered and cleaned as under [Forum](#forum).

**Forks and merge requests.** `forkRepository` needs `writer`, and Developer when the repository is not public. A fork into a group needs Maintainer of that group. The site's `forkCreateEnumId` must be `ScpVerified` unless the caller is the site's owner. `createMergeRequest` needs `writer` and Developer in the source repository; a source in another repository is found by `repository()` in the same site, and the framework's refusal of a source outside the fork network is passed on. Naming reviewers needs Developer in the target. A merge request whose text the post gate holds is opened hidden.

**Pipelines.** A pipeline run, its jobs, a job's log (`getJobLog`) and its artifacts (`downloadArtifact`) are read by whoever views the repository, a visitor of a public repository included. Run, re-run and retry need Developer; `approvePipelineRun` needs Maintainer. The run check (`check#Run`, `git-ci` `run-check-service`) lowers trust and never raises it: a run is untrusted when its commits come from a fork, a push for review or a detached merge request, or when the account that caused it, the merge request's author or the head's pusher is below Developer. An untrusted run waits for a Maintainer by `outsideRunApproval` (`first`, `always`, `never`), is refused above `outsideRunMaxJobs` jobs, and counts against the account's daily runs. `storeCiSecret`, `deleteCiSecret` and `storeCiEnvironment` need `writer` and Maintainer. `findCiSecrets` answers names, scopes and dates; no read answers a secret's value, and the receipt is made without it. An environment's `allowedRefs` made only of wildcards is refused, as is a `targetUrl` or `cloneUrl` with a user or password in it; its token is write-only (`hasToken`). `requestDeploy` needs Developer. `decideDeploy` needs Maintainer and refuses the account that asked for the deployment.

**Git access (`Account/GitAccess`).** `findGitAccess`, `addSshKey`, `removeSshKey`, `createAccessToken` and `revokeAccessToken` (`SmithyGit.js`) act on the caller's own account through the framework's `create#UserSshKey`, `create#UserAccessToken` and their find, delete and revoke services. Adding a key or a token needs `writer` and a fresh proof: the account's password (and second factor code) checked by `login#UserAccount`, or, for an account with no password, any successful sign-in of the account in `UserLoginHistory` within 15 minutes. An account has at most 20 keys and 20 tokens. An access token is a framework login key (`moqui.security.UserLoginKey` with a `description` and an empty `scope`, `crates/moqui-core/src/service/user_keys.rs` `create_access_token`): it carries no scope of its own and is the account's key wherever a login key is read. It lasts until the date asked (at most 366 days), else 90 days. Only its hash is stored; the token is answered once and is not in the receipt. The authority refuses every PASS operation to a request signed in by an access token or a session's key, and all but `APP_KEY_OPERATIONS` to a device's key (`PassAuthority.js` `run`); that rule does not run in local mode.

**Webhooks and push mirrors.** The webhook and mirror operations need Maintainer, and an id must be of the repository in the request. A repository has at most 10 webhooks. The URL and the secret go to the framework's `store#GitWebhook`; `findWebhooks` answers the URL whole and `hasSecret`, never the secret. On a create, `storeWebhook`'s receipt row holds a hash of the input, the secret included. `testWebhook` is limited to 3 a minute for a repository and answers the status code and delivered or not. A mirror's URL must match `https://<host>[:port]/<path>` with no `@`; the credential is a field of its own and only `hasCredential` is answered. A changed URL of a mirror with a stored credential needs the credential again or its removal, and `lastError` is scrubbed of credentials. The address rules (no loopback, private or link-local address) are the framework's ([Git](Attack-Surface-Git.md)). Smithy's `check#Outbound` (`git-server` `outbound-check-service`) refuses webhook deliveries and mirror pushes of a repository whose site has no Smithy mount, of a hidden repository and of one whose owner is suspended, and refuses when the check itself fails.

**The GitHub import.** `startGitHubImport` needs `writer` and Owner of the target group; an existing target repository must be in that group and needs Owner. The source is a name `owner/name`, never a URL. The API base is the property `smithy_github_api` (default `https://api.github.com`), not an input. The caller's token is sent as `Authorization: Bearer` to that base, is kept for the run in the encrypted `password` of a `SystemMessageRemote` row, and is not in the receipt. A clone address that GitHub answers is refused unless it is `https` on the API's host. Pull request heads are fetched by the framework's `fetch#GitRefs` with that address and the token as the password; no file under `service/mantle/smithy/` names `import#GitRepository`. A private source into a wider group or repository is refused without `publishPrivate`.

**The GitHub identity claim at SSO sign-in.** Mantle sets `user-facade` `login` `sso-linked-service` to `mantle.smithy.SmithyImportServices.handle#SsoLinked` (`authenticate="false"`). It claims nothing unless the flow is an `OauthFlow` of type `OctGitHub` whose endpoints are empty or exactly github.com's (or one Enterprise Server host's), `providerHost` is `api.github.com` (or that host), and the account holds that `externalUserId` and `externalAuthFlowId`. It then moves, in each site where the account is an active, unsuspended member, the records of the import's placeholder with the same numeric GitHub id and host to the account (posts, issues, merge requests, assignments, reactions). No role or repository ownership is moved.

**Smithy and the framework's git REST.** For a repository Smithy keeps, `check#RestWrite` (`git-server` `rest-write-check-service`) refuses every write of the framework's git REST and allows `read` and `commitStatus.create`. Mantle's `MoquiConf.xml` sets `reserved-status-contexts="agreement/,ci/,deploy/"` and `review-start-hidden="true"`. The review threads of the framework's REST are answered by `mantle.work.GitServices.handle#GitReviewThread`: the caller must be signed in and view the repository, and a hidden merge request is its author's alone. Each comment in that answer carries `fromPartyId` and an `authorName` built from `PartyDetail`. The hook services (`check#Push`, `check#LfsUpload`, `check#Outbound`, `check#RestWrite`, `check#Run` and others) are `anonymous-all`, take `repositoryId` and a user id as parameters, and are not in `PassRoutes.js`.

**Redirects.** The `redirect` transition of `mr-pass/screen/Smithy.xml` (`method="get"`, `read-only="true"`) takes a `location` parameter and calls `redirectRoute` (`screen/Smithy/Smithy.js`). It answers 301 to the location with the request's query added when the location is a path on the site (`siteLocal`: one leading `/` not followed by `/` or `\`, no backslash or control character), or an `https` address whose host `getSiteInfo` finds among the site's `PublicSiteHost` rows and that is not the site's theme preview host. Any other location fails.
