# Attack surface: mail

Inbound and outbound mail. This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## Mail

There is no open SMTP receiver by default. `smtp-server@listen-port` empty does not start one. The host default is `127.0.0.1`. There is no default port (the doc example is 2525). Only internet mode (`moqui_conf__smtp_server__internet=true`, or `internet="true"` on the `smtp-server`, which MoquiEdgeConf.xml sets) takes mail from anyone, on port 25 of an edge node; see [Edge node](Attack-Surface-Cluster-Edge.md#edge-node) below. `inbound-smtp` is an Enterprise and Maximal feature. Dev and Lite omit it. If the port is set on a build without the feature, startup logs an error and does not listen.

The listener is the last hop behind an operator-run gateway (`docs/interfaces/Mail-Inbound.md`). There is no SMTP `AUTH` and no client certificate. The allow-list is the gateway. A peer outside `smtp-server@allowed-addresses` gets `554` at connect and the connection closes. An empty allow-list refuses to start the listener. `proxy-protocol`, `starttls`, and `require-tls` default to false. STARTTLS with no certificate does not start the listener. `dsn` defaults to false. The message cap is 25 MiB (`max-message-size` 26214400), 100 recipients, 20 connections. In internet mode an empty allow-list takes mail from any address, and a non-empty one still refuses every other address with `554`. In internet mode STARTTLS is on by default, each address is limited (`max-connections-per-ip` 5, `connections-per-minute` 30; IPv6 by its /64), and SPF, DKIM, DMARC and ARC are checked after the data within 45 seconds, with the listener's own `Authentication-Results` written and any claiming its authserv-id removed; a message whose DMARC result is a failure under a reject policy is refused (550) and under a quarantine policy goes to Junk, and every other result is accepted (the authentication decision, below). Rspamd's verdict, when `smtp-server@rspamd-url` is set, fails open ([Mail-Inbound](../interfaces/Mail-Inbound.md)).

The authentication decision (`crates/moqui-mail/src/auth.rs` `verify`, `verify_with`; internet mode only). The checks are DKIM (the first ten signatures), ARC, SPF (the HELO name and `MAIL FROM`), then DMARC with the `MAIL FROM` domain, or the HELO name for a null path. The action is reject when the DMARC result is `Fail` and the policy `reject`, quarantine when `Fail` and `quarantine`, and accept otherwise: `none`, `temperror`, `permerror` and no record all accept, and so does a message whose `From` addresses are of more than one domain (one field with two mailboxes, or two `From` fields) or that has no `From` address, for which `mail-auth` gives no DMARC result; such a message is stored with the first mailbox of its last `From` field as its sender (`store.rs`) and a verdict of `dmarc=none`. `t=y` lowers the policy one level inside `mail-auth`; there is no `pct`. With no resolver the message is accepted with `none (no resolver)`. The whole check runs within 45 seconds; a timeout or a panic is a temporary error, answered 451. `smtp-server@arc-trusted-sealers` (domains, comma or space separated; empty in the default conf, which means no exception) turns a reject or quarantine into accept when the message's ARC chain passes and the `d=` of its last seal is listed; the sealer's own `ARC-Authentication-Results` is not read, so any sender who can pass a message through a listed sealer reaches the Inbox. `mail-delivery@dns-offline` true (read at the resolver's first use; nothing ties it to the instance purpose) makes no DNS query, every name is "not found", so SPF, DKIM and DMARC of every inbound message are `none` and nothing is refused. `rewrite_head` writes the listener's fields first and leaves out every `Authentication-Results` field whose authserv-id (the first word before the first `;`, lower case) is the node's, and the spam verdict fields; the delivery's trust test reads the authserv-id with the same function, so a field written to dodge the removal is also not trusted. With an empty authserv-id nothing is removed. What the client wrote cannot extend the listener's own field: `mail-auth` writes `header.d`, `header.s`, `header.from` and `smtp.helo` without `; ( ) = " \` or white space.

Mail DNS (`crates/moqui-mail/src/dns.rs`). One resolver serves the inbound checks and MX delivery: Hickory's, from the system's configuration, else Cloudflare's servers, 5 seconds an attempt, no DNSSEC validation asked for, on a runtime of four threads. Answers are kept to their TTL in one cache of 20,000 entries for each record type; when a type's cache is full of live entries the whole map is cleared. Inbound mail fills it (the names in `MAIL FROM`, a signature's `d=` and SPF `include`), and so do recipient domains. An internet sender makes the node run SPF's bounded lookups, one key lookup for each DKIM signature (ten at most), the lookups of each ARC set and DMARC's tree walk; none of them makes a connection other than DNS.

A permitted gateway can `RCPT TO` a hosted (`EakHosted`) or shared (`EakShared`) address that has no incoming IMAP or POP server. Other recipients are `550`. After `DATA`, the message is stored in that account's Inbox, or Junk when a configured spam header starts with yes or true. That store runs with authorization disabled, including the app `EmailMessage` ECA when Mantle is loaded. `RCPT TO` takes no address of another domain, so nothing is relayed. A stored message can still make the server send mail: the "delivered" notice, an out-of-office reply and a rule's forward (the paragraph on mail sent because a message arrived, below). `VRFY` answers `252`. Empty `smtp-server@authserv-id` keeps every `Authentication-Results` header, including a forged one; it warns at startup on a node whose listener takes mail from a gateway, on a local node paired with an edge node and on a node that syncs mail by IMAP or POP3, not on an edge node in internet mode, whose listener's own fields are under `smtp-server@hostname` then. A reverse path with a quoted local part (`"a; dmarc=pass header.from=bank.example"@evil.example`, valid SMTP) cannot add results to the listener's own field: its `smtp.mailfrom` is written as the domain alone (RFC 8601 allows it), and the delivery's reading of trusted fields splits them on `;` outside quoted strings and comments only. Out of internet mode the listener does not check SPF, DKIM, or DMARC; the gateway does.

Only a mail administrator makes an account the listener delivers to. The MailAccounts wizard (`BasicComms/Settings/MailAccounts/Add`) offers every user of the app a "Hosted here" account and a "Shared, delivered here" account at an address the user types. `org.moqui.comms.MailSettingsServices` saves it with `gatewayDelivery` through `create#EmailAccount` with kind `EakHosted` or `EakShared`, no server and status `EasPaused`. `create#EmailAccount` refuses a hosted or shared account with no incoming server, and `update#EmailAccount` refuses to give such an account another address or to make an account one, unless the caller has the permission `EMAIL_ACCOUNT_HOSTED` (granted to `ADMIN`) or authorization is disabled (plans/Security-Review.md SEC-MAIL-01, fixed); the wizard shows the refusal. The domain of the address is not checked. A recipient of the listener is an account of kind `EakHosted` or `EakShared` that is not `EasRemoved` (a paused one counts) and has no incoming server, matched on `EmailAccount.emailAddress` and then `EmailIdentity.emailAddress` without regard to case, then again without the plus tag (`crates/moqui-mail/src/delivery.rs`). When several accounts have the address, the one with the lowest id gets the mail.

Listener limits. A command line is at most 4096 bytes (`500`, then the connection closes). Twenty commands answered with a syntax or sequence error close the connection (`421`); in internet mode an unknown recipient (`550`) counts as one of them (`RSET` does not clear the count), behind a gateway it does not. `command-timeout` is 300 seconds for each line or data chunk and `session-timeout` 1800 seconds for a connection. In internet mode a connection brings at most 100 messages and 256 MiB (`MAX_INTERNET_MESSAGES`, `MAX_INTERNET_BYTES`), after which the next `MAIL` is `421` "connect again"; behind a gateway a session has no limit on the number of messages. In internet mode the messages stored in an hour are limited per client address (IPv6 by its /64) and per envelope sender, whichever is reached first (`internet-messages-per-hour` 1000, `internet-bytes-per-hour` 1 GiB, a `MAIL`'s `SIZE` counted; `451 4.7.1` past them; a message counts once, a bounce only against its address). An account keeps at most its `quotaBytes` of mail, else `email-client` `mailbox-quota` (10 GiB; the sum of `messageSize`, view `EmailAccountBytes`): past it `RCPT TO` is `452 4.2.2` (not an error), and mail an edge node queued is held at delivery (`delivery::over_quota`). Each check keeps `EmailAccount.quotaFullDate` (set when found over, cleared when found under; the job `check#FullMailboxes` checks the marked accounts every 15 minutes), which is replicated in `mailRecipients`, so an edge node answers `452` for a full account too; the account's owner and members get an `EmailMailboxFull` notice when it fills. Only a mail administrator (`EMAIL_ACCOUNT_HOSTED`) sets `quotaBytes` (`update#EmailAccount`, the account page), which clears the mark (SEC-MAIL-07). A message over `max-message-size` is read to its end, not kept, and answered `552`. A message is answered as stored and not stored again only when a received message of the account has its `Message-ID`, the same envelope sender (its `Return-Path`) and the same subject, From address, body and text (`delivery::same_message`); another message with a known id is stored beside the first. That rule is the store's: on an edge node, and for a paired node's accounts on an all-in-one node, the listener answers stored for a queue item of the same `Message-ID` and recipient addresses, whatever the content or the sender ([The edge node's mail queue](#the-edge-nodes-mail-queue)). A message with no header fields is `554`. Each message is held in memory once per connection (at most `max-connections` times `max-message-size`). In internet mode with `smtp-server@rspamd-url` set the whole message is posted to `{url}/checkv2` with the client address, EHLO name, envelope sender and recipients as headers, within 20 seconds.

Mail sent because a message arrived. Three things send mail after a message is stored in an Inbox. (1) With `smtp-server` `dsn` on (off by default), a recipient with `NOTIFY=SUCCESS` gets one "delivered" `multipart/report` sent to the envelope sender from `MAILER-DAEMON@` the listener's name, through the outgoing server of the first such account; it carries the message's header fields up to 4 KiB, whole fields only (`MAX_RETURNED_HEAD`), and is sent only when `smtp-server@authserv-id` is set and the kept `Authentication-Results` show `spf=pass` or `dmarc=pass` with `header.from` aligned with the envelope sender's domain (`delivery::notice_authenticated`); none is sent to an empty sender or one without `@`, or when no such account has a server. (2) `send#OutOfOfficeReplies` sends the account's automatic reply to the message's `From` address, once per sender in `replyOncePerDays` (4), not to list, bulk, automatic or bounce mail, a system sender, the account itself, mail the rules moved to Junk or Trash, or a sender the kept `Authentication-Results` say failed DMARC, and at most 30 an hour from the account (SEC-MAIL-05); the subject is the reply's own, else `Automatic reply: ` and the mail's subject. (3) A rule's `forwardTo` action sends the message, with copies of its files, to the addresses the rule's author entered, from the account's default identity; it is skipped when the mail's `From` is one of the account's own addresses, when the mail is automatic (`Auto-Submitted` other than `no`), when it has more than 25 `Received` fields (a loop), and past 50 forwards from the account in an hour; a forward carries `Auto-Submitted: auto-generated`, so another account's rule does not send it back (SEC-MAIL-05). The delivery report (1) has no count limit per account or per hour. Rules run with authorization disabled, and an `EmailRuleAction` enumeration with an `optionValue` names a service that is called with authorization disabled and `emailMessageId`, `emailAccountId`, `emailRuleId`, `ruleOwnerUserId` and `value`.

An application's mail rule actions run on stored mail with authorization disabled, so mail from anyone reaches them. IronStone
Sales' lead intake address (`createLead`, Mantle `create#LeadFromEmail`) takes the team from the rule's value or the plus tag of a `To` or `Cc` address (`sales+leads@`), only a team
of an organization the rule's owner works for; the message makes a `SalesLeadIntake` row and a lead in that team's queue,
never a party, the sender's name and address held on the intake until the lead is qualified and blanked after the retention
days if it never is (`purge#LeadIntakes`); its `Message-ID` is the intake's identity, so the same mail again makes no second
lead. The mail text decides only the lead's name and description. The request for quote address (`createQuoteRequest`, Mantle `create#QuoteRequestFromEmail`) takes the team the same way, its rule's owner holding `SALES_QUOTE_EDIT` when the rule is saved and each time it runs, and makes an `RqtQuote` request in that team's queue with the message and its files on it, never a party (the sender is matched to an account or to the contact of exactly one account of the organization); the same `Message-ID` again makes no second request. A decline is mailed as the system only from such an intake mailbox, or one the rep may send from, to the address the rep previewed, once per request. The acknowledgement of such a request (off unless the organization's SalesPolicy turns `rfqAcknowledge` on) is a transactional delivery-ledger message from the organization, so its suppressions apply, queued at most once per request, only when the sender matched a contact or account of the organization and only to the mail's From address (an unknown or forged sender gets nothing back), never to automatic, list, bulk or system mail, marked `Auto-Submitted: auto-replied`; its locked text sees only the request's reference and the seller's name, nothing of the mail's content.

`send#EmailTemplate` (and `send#Email`) take a call's own `subject`, `fromAddress`, `fromName`, `bounceAddress` and `emailServerId` over the template's (mr-boss impl-marketing P6, F17). The service has `authenticate="anonymous-view"`. One screen path passes request parameters to it: the `emailScreenAsync` transition, through `send#ScreenRenderEmail`, which hands on only its own declared parameters ([Send services](#send-services)). The tools REST `email/templates/{id}/send` reaches `send#Email`, whose caller can already make a template with any sender and relay. The checks are the caller's: only Mantle's delivery ledger passes a sender, relay and bounce address, from the sending profile its delivery names, which `queue#Delivery` requires to be the delivery's organization's; a profile is stored only by a holder of `MESSAGE_SENDING_CONFIGURE` for an organization they work for, and names a relay that is an `EmailServer` no mail account owns, never a mail account's server or credentials; no profile answer carries a host, port, user or credential. A value with a CR or LF is left out (the subject's line breaks become spaces), an address must have an `@`, and the transport parses the addresses again, so a call cannot add a header or a recipient. A call's subject is used as given, never expanded with `bodyParameters`, so text a person wrote never runs as an expression.

`org.moqui.mail.EmailServices.read#DeliveryReport` reads a stored message as a delivery status notification (RFC 3464) or an abuse report (ARF, RFC 5965) from its stored report part and returned message (at most 256 KiB of each, 100 recipients), never its body text, and changes nothing; it is internal. The parsers (`report.rs`, `edge_mail::parse_dsn`) read hostile text without panicking (lossy UTF-8, no indexing past a part).

Mantle's bounce intake (`process#DeliveryReport`, the email ECA `DeliveryReportIntake` and the job `run_DeliveryReports`, as the system) reads only the messages of a bounce account (a hosted or shared account `bounces@` a sending profile's bounce domain); a report in any other mailbox is its owner's mail, left alone and not recorded. Anyone can mail a bounce address, and delivery ids are a sequence, so a report names its delivery only by the VERP address `bounces+(deliveryId).(bounceKey)@` the domain with the delivery's own random key (the address it came to, or an ARF's `Original-Mail-From`), or by the returned message's random `Message-ID`; a DSN counts only the recipients that are the delivery's own address. What a report can do is fixed by its delivery, never by the report: a hard bounce suppresses the delivery's address for every organization (a hard bounce stops all mail, the user's call), a complaint for the delivery's organization (promotional mail only), a soft bounce or a delivery nothing; each message is read once. A forger who has the key or the `Message-ID` (the recipient, or who saw the message) can only suppress that recipient's own address. The edge relay's bounce (`ES_BOUNCED` on a sent message) is matched by the attempt that sent it. `find#DeliveryReceipts` answers a delivery reviewer (`MESSAGE_DELIVERY_REVIEW`), a suppression reviewer or a contact administrator only the deliveries of the organizations they work for (every one for a system administrator or a holder of MARKETING_ALL_ORGANIZATIONS; another organization's delivery answers as missing), with any address in a diagnostic struck out.

`poll#EmailServer` (job `poll_EmailServer_frequent`) is paused. If unpaused, the cron is every 15 minutes, `emailServerId=SYSTEM`, `authenticate="anonymous-all"`. It connects out to the configured IMAP or POP server. `sync#DueEmailAccounts` (job `sync_EmailAccounts_frequent`) is running, every minute, `authenticate="anonymous-all"`; the job is its caller. IMAP IDLE is on by default (`idle-enabled="true"`, `idle-max` 8) and dials the account's server. It does not listen. Both jobs use the scheduler's authorization-off path. `sync#DueEmailAccounts` syncs the due accounts one after another on the job's thread (`sync.rs` `sync_due_accounts`); a session has no deadline of its own, only a 60 second timeout on each socket read and write, and it renews its account's 15 minute lease as it goes, so a slow server holds the pass over the other accounts. An IDLE worker runs an Inbox sync each time the server reports a change, with no interval between them (`idle.rs`); the server decides how often. `poll#EmailServer` fetches every id the server lists, with no count limit, and answers an account-owned server as not found. What a sync reads and stores is under [Mail account servers](#mail-account-servers-and-other-outbound-requests).

OAuth mail sign-in is not a listen port. It stays off until the operator sets a Google or Microsoft client id and secret. The browser session, PKCE, and server-side state (10 minutes, single use) protect the callback `/emailOAuth/callback`. The redirect URI is the deployment's and is never taken from the request. A server with no field encryption refuses to store the refresh token. The `callback` transition (`webroot/emailOAuth.xml`, `read-only="true"`, `require-session-token="false"`) passes `state`, `code`, `error` and `error_description` from the request, and the constant `sendPage: true`, to `complete#OAuthSignIn` (`anonymous-all`) and nothing else. The state is compared in constant time with the sign-ins kept in the caller's session (at most 8), taken once, and refused for another user, a signed-out caller or after ten minutes. The page it sends has a nonce CSP (`default-src 'none'`), `no-store`, the outcome text HTML-escaped and no token; it posts the outcome to `window.opener` on its own origin and on the BroadcastChannel `moqui-email-oauth`. The ID token comes from the token endpoint; its audience, issuer, expiry and nonce are checked, its signature is not. An `email_verified` of false is refused, and the signed-in address must be the account's unless the user allowed a change.

The OAuth exchange and where a token goes (`crates/moqui-mail/src/oauth.rs`). The exchange is a POST of the code, the redirect URI, the client id and secret and the PKCE verifier to the `tokenUrl` of the `EmailOAuthProvider` row (`{tenant}` filled from a property or the row), within 20 seconds. A missing refresh token and a missing mail scope are refused; a response with no `scope` field skips the scope check. The refresh token is stored in `EmailServer.oauthRefreshToken` (encrypted), the access token in memory and encrypted in `moqui.basic.email.EmailServerAccessToken`. The refresh token is sent to the provider row's `tokenUrl` and `revokeUrl`. The access token is sent to its `userInfoUrl` and, as XOAUTH2, to the `storeHost` and `smtpHost` of the account's `EmailServer` row, which the account's managers set and which are not tied to the provider ([Mail account servers](#mail-account-servers-and-other-outbound-requests)). A refresh runs a minute before expiry, one at a time for a server with the row locked; `invalid_grant` marks the accounts `EasAuthFailed`; the provider's `expires_in` is trusted. No token is logged or answered. `complete#OAuthSignIn` makes a new account by calling `create#EmailAccount` with authorization disabled, of kind `EakExternal` or `EakShared` as `start#OAuthSignIn` was asked, with the server fields of the provider row; any mail client user reaches it through `start#MailSignIn`. A provider row with no `storeHost` gives an IMAP account no incoming server, and only the POP3 case is refused for an empty host. For an existing account the user must manage it at the start and again at the store, a server the account does not own is refused, and a sign-in keeps the hosts already on the server row. `get#OAuthStatus` answers only a sign-in of this session and user, or an account the caller reaches; `revoke#OAuthToken` and `push#RemoteChanges` refuse a call with authorization on. `find#OAuthProvider` with `lookupMx` makes the same MX query as discovery for a domain the caller gives; no screen passes `lookupMx`.

## Send services

`org.moqui.mail.EmailServices.send#EmailTemplate` (`authenticate="anonymous-view"`) and `send#Email` (default authentication) are one implementation, `moqui_mail::send_template` (`crates/moqui-mail/src/implementation.rs`). The recipients are the call's `toAddresses`, `ccAddresses` and `bccAddresses`, with the template's cc and bcc added. The sender, the subject and the relay are the template's, or the call's over them. The body is the template's `bodyScreenLocation` rendered with the call's parameters and its `bodyParameters` in the script context, or the call's `body` and `bodyText`. When both are present the call's part wins, each part alone (`render_bodies`): the HTML is the call's `body` when it is not empty, else the screen rendered in `html`; the text is the call's `bodyText` when not empty, else the screen rendered in `text` when the screen allows it. So a caller who passes `body` and not `bodyText` sends its own HTML beside the template's rendered text. The template's `fromAddress`, `fromName` and `subject` are expanded as `${expression}` text. An attachment's `fileName` is expanded the same way, a call's `attachments[].fileName` included (`push_parameter_attachment`, `render_attachment`); `moqui_core::script::expand` runs each `${expression}` in the script runtime. An attachment is a call's `contentText` or `contentBytes`, a screen rendered in `screenRenderMode` (`attachmentLocation` or `screenPath`), or the bytes at `attachmentLocation`. `extraHeaders` adds a field only when its name is at most 76 ASCII letters, digits or `-`, is not a field the message writes itself, and its value is under 998 bytes with no line break. `inReplyTo` is kept only when it is one message id. Each address is parsed by lettre (`mailbox`). Of a stored message's `headersString` only a fixed list of names (`CLIENT_HEADERS`) is sent, each a single line under 998 bytes. Links in a template's body start with `https://` and the template's `webHostName`, else the `EmailServer`'s `webBaseUrl`, else the conf webapp's root URL; a request's host is not used (`RenderEnv::new`). When `createEmailMessage` is not false (the interface default is true) the rendered body is stored in `EmailMessage.body` and `bodyText`, with authorization disabled. The instance fence (`fence::check_effect`, `Effect::Mail`) is checked first.

`send#ScreenRenderEmail` (default authentication) takes `screenLocation`, `screenRenderMode`, `fileName`, `toAddresses`, `ccAddresses`, `bccAddresses`, `emailTemplateId` (default `SCREEN_RENDER`), `createEmailMessage` (default false), `bodyParameters` and `title`. It makes one attachment `{fileName, attachmentLocation: screenLocation, screenRenderMode}`, sets `pageNoLimit` and `lastStandalone` in `bodyParameters`, and calls `send#EmailTemplate` with its context. A call's attachment file name is taken as written; only an `EmailTemplateAttachment` row's own is expanded (SEC-MAIL-61, fixed). The `SCREEN_RENDER` template's subject is `${title}` and its relay is the `SYSTEM` server.

`send#EmailMessage` (`send_message`, default authentication) takes an `emailMessageId` and, with authorization on, answers a message the caller may not send as one that does not exist (`may_send`): system mail (no `emailAccountId`) only when `ES_READY` or `ES_BOUNCED`, or any for an `ADMIN` (the message page's Resend), and an account's message only when `ES_READY` or `ES_BOUNCED` and the caller has send level on that account (`get#EmailAccountAccess` `canSend`). Internal work (authorization disabled: the queue, its retries, the client's delivery) is not checked (plans/Security-Review.md SEC-MAIL-64, fixed). It refuses a message in `ES_DRAFT` or `ES_CANCELLED` and one with no body, no from address or no to address; a message in any other status is sent through its own `emailServerId`, else its mail account's server. The server's `allowedToDomains` drops recipients outside it. Only a message in `ES_READY` or `ES_BOUNCED` changes status (to `ES_SENT`) after the send.

## System mail with passwords, codes and links

- `org.moqui.impl.UserServices.reset#Password` is `authenticate="anonymous-all"`. It finds the account by `userId`, then `username`, then `username` as an email address, and answers the same public message whether or not one is found. One reset is made per `loginRules.disableMinutes` after `resetPasswordSetDate`. The reset password is 12 random characters, stored hashed in `UserAccount.resetPassword`; the current password stays valid. The mail (`PASSWORD_RESET`, body screen `PasswordReset.xml`) carries the reset password as text ("Your reset password has been set to: ..."). The call passes `createEmailMessage: false`, so no `EmailMessage` row keeps the password (a failed send is not retried by the queue). `password/@email-expire-hours` is 48 in the default conf.
- The single-use code mail (`SINGLE_USE_CODE`) carries the code and its `thruDate` to the factor's address; a second mail (`ADDED_EMAIL_AUTHC_FACTOR`) goes to the account's main address when the two differ. The code's send passes `createEmailMessage: false`, so no `EmailMessage` row keeps the code.
- The public account registration (`org/moqui/public/Account.js`) mails a 64-character random `verificationToken`. Its hash is stored (`RegistrationChallenge.tokenHash`), it expires after one hour, earlier challenges of the user are consumed when one is made, and a consumed or expired one is refused. The call passes `createEmailMessage: false`, so no `EmailMessage` row keeps the token.
- A Mantle invitation (`mantle/party/Invitations.js`) mails a link `{base}/i/{token}` with a 43-character random token whose hash is stored and which has an `expiresDate`; a resend makes a new token. The call passes `createEmailMessage: false`. The base is the caller's `baseUrl`, else the template's `webHostName`, else the `EmailServer`'s `webBaseUrl`. The mr-boss screens pass `ec.web.getWebappRootUrl()`, which takes a request's `Host` header only when a `root-screen` of the webapp names that host (`crates/moqui-core/src/web/mod.rs` `webapp_root_url`), and else the conf's host.

## Mail client

The mail client (`org.moqui.mail.EmailClientServices`, screens under `BasicComms/Inbox` and `BasicComms/Settings/MailAccounts`) is reached by members of `BASIC_COMMS_USERS`, `BASIC_COMMS_ADMIN` and `ADMIN` through the `BASIC_COMMS` artifact group (`inheritAuthz` Y from `BasicComms.xml`). The services check the account, not the screen: `get#EmailAccountAccess` answers the accounts a user owns (`ownerUserId`) or has a current `EmailAccountUser` row on, with level 1 (`EapRead`), 2 (`EapSend`) or 3 (`EapManage`). A `userId` other than the caller's is taken only with authorization disabled. `get#Thread` and `resolve#MessageTargets` find messages only with `emailAccountId` in the caller's accounts; another account's message is "not found". `find#Messages` refuses a named account that is not in the caller's access map. `export#EmailMessage` needs level 1 on the message's account, or authorization disabled for a message with no account. `InboxServices.get#MessageDetail` answers a message with no account (system mail) only to a member of `ADMIN`. The screens call `org.moqui.comms.InboxServices.run#Operation`, which takes an operation name from a fixed list and hands it to an app's `inbox-source` provider when one is declared, else to the framework service.

Drafts and sending. `save#Draft` changes a draft only at level 2 on the draft's account. The identity it names must be of an account the caller reaches and of the named account, and the account must be one the caller may send from (`canSend`). The draft's `fromAddress` is the identity's address, else the account's; the request cannot set it. An attachment location must be on the draft already or start with `dbresource://email/{emailAccountId}/` with no `..` segment, unless authorization is disabled. A `parentEmailMessageId` must be a message of an account the caller reaches. `send#Draft` asks the same access and `canSend`, an identity of the draft's account, and an `EmailServer` with an `smtpHost`; it sends a message in `ES_DRAFT`, or in `ES_READY` with a `sendError`. `deliver#DraftMessage` and `claim#DraftSend` refuse a call unless authorization is disabled. `send#DueDrafts` (`anonymous-all`) with an `emailMessageId` and authorization not disabled asks level 2 on the message's account. `create#EmailIdentity` asks level 3 on the account and an address that contains `@`; the address is not checked further. `create#EmailAccount` takes an existing `emailServerId` only with authorization disabled, so a user sends through a server whose host and sign-in the user gave.

Owners and members. An account's owner has level 3 (`get#EmailAccountAccess`). `add#EmailAccountUser` (`BasicComms/Settings/MailAccounts/Account.xml`, `MailSettingsServices.save#AccountOptions`) asks level 3 on the account, so an `EapManage` member adds others at `EapManage`, takes an account of any kind but Internal and a permission from a fixed list, and requires only that the user added exists: not that the user is enabled, internal or a member of a mail client group. Its answer tells an existing `userId` from a missing one ("User ... not found"). `remove#EmailAccountUser` lets a member remove only themselves. `transfer#EmailAccountOwner` (`allow-remote="false"`; reached through mr-boss's owned-resource contract, `transferService` with `requiredPermission` `EMAIL_ACCOUNT_OWNER_CHANGE`) asks that the caller is the current owner or holds `EMAIL_ACCOUNT_OWNER_CHANGE` (granted to `ADMIN`, `BOSS_ADMIN_IDENTITY`, `BOSS_ADMIN_ADMIN`), moves only a shared account that is not removed, and requires a new owner who exists, is not disabled without a date, is not ended and is not an external user; a user disabled by failed sign-ins (`disabled` Y with a `disabledDateTime`) is accepted, and the new owner is not asked. The new owner gains level 3: all the account's mail, sending as it, its members, rules and server settings. The stored server password or refresh token stays the account's and is not answered. The old owner keeps no access unless a member row exists. `find#OwnedEmailAccounts` is the contract's list of a user's accounts. A member at level 3, like the owner, changes the account's server (`update#EmailAccount`, [Mail account servers](#mail-account-servers-and-other-outbound-requests)). Removing an account clears the stored password and tokens of its server. No application replaces the MailAccounts wizard: mr-boss mounts the framework's settings screen unchanged (`mr-boss/screen/Comms.xml`), and no file under `runtime/components/addon` (tests, plans and l10n aside) calls `create#EmailAccount`, `save#AccountConnection` or `start#OAuthSignIn` except `MailDemoServices.xml`, so the kinds and domains a user may choose are the framework's.

## Message display and files

A message's HTML is never put in the application's document by the mail client. In the qvt client `m-html-view` cleans it in the browser with DOMPurify (HTML profile only; no `style`, `form`, `iframe`, `object`, `embed`, `base`, `link`, `meta`, `script`, media tags; no `srcset`, `poster`, `ping`, `action`, `srcdoc`), rewrites images, links and CSS, and shows it in an `iframe` with `sandbox="allow-same-origin allow-popups allow-popups-to-escape-sandbox"` (no `allow-scripts`) whose `srcdoc` has a CSP of `default-src 'none'; img-src data:` (plus `https: http:` when remote images are allowed), `style-src 'unsafe-inline'`, and `referrerpolicy="no-referrer"`. If DOMPurify does not load, the text is shown. The server does not clean the HTML for the qvt client. In `html` render mode the server cleans it (`StringUtilities.cleanHtml`) and writes an `iframe` with `sandbox="allow-popups allow-popups-to-escape-sandbox"` and `img-src data:`. In `html-print` mode the text is escaped. Remote images are loaded by the browser, never by the server: they are hidden until "Show images", and shown at once when the user's `remoteImages` preference is `always`, the `From` address is in the user's trusted senders, or the `From` address is one of the user's own (`Mail.qvue`); the stored authentication verdict is not part of that test. `cid:` images are fetched by the page from the `attachment` transition with the session and put in the frame as `data:` URLs. `Inbox/MessageDetail/attachment` (GET, read-only) serves an `EmailMessageAttachment` only when `get#Thread` shows its message to the caller, through `ec.web.sendResourceResponse`, which sends a type that can run script (HTML, SVG, XML, JavaScript) as an attachment whatever `inline` says. `Inbox/MessageDetail/downloadEml` (read-only) sends `export#EmailMessage`'s text as `message/rfc822`; for system mail it disables authorization after `get#MessageDetail` has answered the message. The mr-marble `PartyEmails.xml` `EmailMessage` transition is a second display path, with none of the above ([Send services](#send-services)).

## Mail account servers and other outbound requests

A user who adds a mail account names its incoming host and port (`storeHost`, `storePort`, IMAP or POP3) and outgoing host and port (`smtpHost`, `smtpPort`); `create#EmailAccount` writes them to an `EmailServer` the account owns. The server connects to them on the wizard's test (`test#EmailServer`), on `sync#EmailAccount`, from the job `sync_EmailAccounts_frequent` every minute, from the IDLE workers and on each send. `email-client` `allowed-hosts` limits the hosts and is empty by default, which allows any host (`implementation.rs` `require_host`). SMTP, IMAP and POP connect through `inbound::connect_tcp`: one lookup, every address checked, the connect to one of them; an internal address is refused when the row is denied the private network (`implementation::private_network_denied`: `N`, or anything but `Y` on a production instance), and the account services never give an account-owned server `Y`, and a link-local or metadata address is refused always (plans/Security-Review.md SEC-MAIL-02, fixed). The wizard's host pattern takes a name or an IPv4 literal. A test answers a fixed kind of failure (`implementation::test_failure_kind`: address not allowed, host not found, TLS failed, connection refused, timed out, sign-in refused, not a mail server) and logs the client's text at info; this server's own refusal of a plain store is shown as written. A sync does not use that mapping: `sync#EmailAccount` (level 1 on the account, the Inbox's "Sync now") answers as a service error the remote server's own text (the first line a non-TLS port sent, up to 16 KiB; a command's tagged answer; the connect error with host and port; the server's refusal) and writes it to `EmailAccount.lastSyncError` (4,000 characters), which `get#EmailAccountAccess` answers to every member of the account. On an instance that is not production an account-owned server's empty `allowPrivateNetwork` allows the private network (`outbound.rs` `deny_private_network`), so there that text can come from an internal host.

Changing an account's server. `update#EmailAccount` (level 3: the owner and every `EapManage` member; `BasicComms/Settings/MailAccounts/Account.xml`, `MailSettingsServices.save#AccountConnection`) writes each server field given to the account-owned `EmailServer`: host, port, TLS setting, protocol, user and sign-in kind, and `oauthProviderEnumId`. An empty `mailPassword` or `smtpPassword` keeps the one stored, and the wizard service asks for a password only when it makes a new account. The relay servers' endpoint-change rule holds here too, side by side (SEC-MAIL-84): a change of the store's host, port, protocol, `storeAllowPlain` or user clears `mailPassword` unless it is given again in the same change; a change of the SMTP host, port or TLS setting clears `smtpPassword` (and `mailPassword` when SMTP signs in as the store does), and of the SMTP user `smtpPassword`; a change of the sign-in kind or the OAuth provider clears both; any of these revokes and clears the OAuth refresh token. A sign-in so cleared marks the account `EasAuthFailed` until it is entered again. Values posted back as stored (a host in other capitals, a flag as the form sends it) change nothing. An `EatOAuth2` server takes only the provider row's `storeHost`, `popHost` or `smtpHost` or a host under its `hostSuffixes` (`update#EmailAccount`), and `oauth.rs` `access_token` gives no token, kept or refreshed, for a server row whose `storeHost` or `smtpHost` is another (`Provider::serves`).

What a sync reads and stores (`sync.rs`, `inbound.rs`, the `imap` crate). A plain IMAP or POP3 sign-in is refused without STARTTLS or STLS unless `storeAllowPlain` or loopback; TLS uses the web PKI roots plus the conf's CA file, with the host name checked. Counts: at most `email-client` `sync-batch` (500) new messages a folder a session, headers 100 and bodies 25 at a time. Bytes: `FETCH_BYTES` (8 MiB) groups messages by the sizes the server reported and is not a limit; a larger message is fetched alone. There is no maximum size for one message on IMAP or POP3. The POP3 client reads a line (the greeting before any sign-in included) and a multi-line answer with no length limit; the IMAP client holds a whole response; a line is limited (16 KiB) only on plain IMAP before STARTTLS, and there the number of lines is not. The socket's 60 second read and write timeouts are the only time limit. Every message a sync fetches is stored with its files: the mailbox quota of the listener is not read by the sync, and no rule limits the number of accounts a user adds.

- `discover#EmailServer` takes an address, checks its domain (`valid_domain`), and fetches `https://autoconfig.{domain}/mail/config-v1.1.xml`, the domain's `/.well-known/autoconfig/mail/config-v1.1.xml` and the Thunderbird ISPDB within 3.5 seconds; the domain's own URLs are fetched only to public addresses (`deny_internal_addresses`), not when `email-client` `autoconfig-urls` replaces the list. The two URLs on the address's own domain carry the whole address in the query string (`?emailaddress={email}`), and the Thunderbird ISPDB URL the domain. The domain must be a DNS name (no address literal, no single label). The guard is in the resolver and covers each redirect hop, and redirects stay on the same host; the ISPDB, a fixed host, is fetched without the guard. The autoconfig body is at most 16 MiB, a DOCTYPE is refused and nesting stops at 256. Its SRV and MX queries go by UDP, on a connected socket with a random id, to the first nameserver of `/etc/resolv.conf` or `email-client` `dns-server`, within 1.5 seconds. Discovery connects to none of the servers it suggests; the test and the sync do, through `connect_tcp`. Its one caller is `MailSettingsServices.suggest#MailServer` (`Add/Address.xml`, `Add/Connect.xml`), any mail client user, with no rate limit; a call starts three threads for at most 3.5 seconds. The fence and a sim session turn the fetches off.
- `unsubscribe#Message` (send level on the message's account) posts `List-Unsubscribe=One-Click` to the first `https` address of the message's `List-Unsubscribe` header when `List-Unsubscribe-Post` allows it, only to a host the script takes as public and with `denyInternal()` on the call, within 20 seconds; else it sends a message from the account to the header's `mailto` address with that address's subject and body.
- `import#EmailMessages` takes uploads (`file`, `fileList`), `messageText`, and `location` or `locationList`, which are read through `ResourceFacade::open` with no check of the location; the one screen that calls it (`Settings/MailAccounts/Account.xml`) passes `emailFolderId` and `file` only.
- The mail capture (`MailCaptureToolFactory`, in the default conf; `service/mail_capture.rs`) captures only in a `moqui test` run (`mail_capture::allowed()`, a process flag the test runner sets and no server sets): there `moqui_conf__email_client__capture_sends=true` or `ec.factory.getTool('MailCapture').enable()` turns it on, and `send#EmailMessage` then marks the message sent, connects to nothing and keeps the last 500 messages in memory. On a server `enable()` returns an error and the property is ignored with a warning (plans/Security-Review.md SEC-DEV-05, fixed).

## Tracking pixel

`GET /email/{key}` has no authentication ([Routes](Attack-Surface-Routes.md)). The key is the message's view key, `{emailMessageId}.{tag}`, the tag 128 bits of an HMAC-SHA256 of the id under a key derived from `webapp-list/webapp[webroot]/session-config@cookie-key` (`web::email_view_key`); the mail render puts it in a template's context as `emailViewKey` (mr-marble's `EmailLayout.html.fancy` is the one template with the image). A bare id or a wrong tag changes nothing. Only a message in `ES_SENT` is updated to `ES_VIEWED`, with `receivedDate` set to the time of the request and authorization disabled; queued (`ES_READY`) and received mail is left alone (plans/Security-Review.md SEC-RTE-01, fixed).

## MX delivery on an edge node

`crates/moqui-mail/src/mx.rs` delivers outbound mail straight to recipient domains when `mail-delivery@mta` is `moqui` (`conf/edge/MoquiEdgeConf.xml` sets it). At most 8 deliveries run at once and 40 rows are taken a round; a try's deadline is 10 minutes, tested when a command starts, and each socket read is given at most 60 seconds, so neither ends a session whose server keeps sending bytes of one reply line with no line feed: lettre reads a reply with `read_line` and tests its size limits only after a line ends, and a row leaves the in-flight set only when its thread ends. The wait after try `n` is `mail-delivery@retry-seconds` (default 300, any positive number) times `2^(n-1)`, capped at the larger of 4 hours and that first interval. A row is given up when a try ends `mail-delivery@days` (default 5, fractions allowed) or more after the row was made, and the recipients still waiting are refused with the last reply; the age is tested only at the end of a try. A row being tried is leased 15 minutes, taken by a conditional update on its attempt count, so one thread tries it. A refusal for good (5xx, a null MX, no public address) is not retried; a lookup failure waits. Rows of a node no longer paired fail at the next round with no report. Whoever makes the node send to a domain reaches that domain's server with these sessions: a mail user of a paired node, and an anonymous sender through an automatic reply, a rule's forward or the "delivered" notice.

| Outbound request | To | Limits and checks |
|---|---|---|
| SMTP, port 25 | Each MX host of the recipient domain by preference, each of its addresses in turn; the domain's own address when it has no MX. A null MX is refused (`556`). | An MX host's internal addresses are dropped, and a domain with only internal ones is refused, unless `mail-delivery@mx-override` names it ([Outbound](Attack-Surface-Outbound.md)). The instance fence is checked per host. The session connects to the address that was tested, not to the name again, and never to another port. With an MTA-STS policy in `enforce` mode only the hosts the policy names are tried. |
| STARTTLS on that session | The MX host | Opportunistic unless the domain has an MTA-STS `enforce` policy or is in `mail-delivery@mx-require-tls` (recipient domains, comma-separated, `*` for all; `mx.rs` `tls_required`): otherwise used when the host offers it, any certificate and any host name accepted (`dangerous_accept_invalid_certs(true)`, `dangerous_accept_invalid_hostnames(true)`), a host that does not offer it gets the message in clear, and when STARTTLS fails the session is opened again and the message is sent without TLS. With an `enforce` policy or a listed domain the certificate must be valid for the host, and no STARTTLS, a failed handshake or an invalid certificate ends that host's try: the message waits and bounces after `mail-delivery@days` rather than go in clear text. `mail-delivery@mx-require-tls` applies with `mail-delivery@mx-override` too. |
| `GET https://mta-sts.{domain}/.well-known/mta-sts.txt` | The recipient domain's policy host | 30 seconds in all, no redirects followed, no proxy, public addresses only, at most 64 KiB read. The `_mta-sts` TXT record's id decides when it is fetched again; a kept policy is used when the record or the fetch fails. The policy cache has no size limit and is never pruned: one entry for each recipient domain that published a policy, each up to 64 KiB, for the life of the process. |
| `mail-delivery@mx-override` (`domain=host:port`, `*` for any) | The named host and port | Skips the MX lookup and MTA-STS. No instance purpose is checked in `override_for`. |

A host's failure text is kept as `{host} [{ip}]: {reason}` with the remote's reply in it, and is the answer every recipient of the try gets; the reply sent back to the local node in the `mailStatus` report is cut to 16 KiB (`MAX_REPORT`), a recipient's reply to 500 characters and the last reply to 4,000; the local node keeps 4,000 characters.

When `mail-delivery@mta` is not `moqui`, `deliver#EdgeOutboundMail` relays to Postfix instead: to `mail-delivery@relay-host` (default `127.0.0.1`) port `mail-delivery@relay-port` (default 10025) with no TLS and no sign-in (`edge_mail.rs`, `lettre::SmtpTransport::builder_dangerous`). The instance fence is checked.

`org.moqui.edge.EdgeServices.check#EdgeDns` (`crates/moqui-mail/src/edge_dns.rs`) makes MX, TXT, A, AAAA and SRV lookups of names the caller gives, with no count limit; DNS queries only, no connection. It is called from a system administrator's screen (`tools/screen/System/EdgeNode/Pair/Apply.xml`).

## The edge node's mail queue

On an edge node the listener stores nothing: `crates/moqui-host/src/smtp_queue.rs` queues each message for the local node of its recipients ([Edge node](Attack-Surface-Cluster-Edge.md#edge-node)). `RCPT TO` is answered from the replicated copies and never by a call to the local node; an address two pairings hold, a node not paired now and a node not yet copied are `451`. Each `RCPT` and each message takes one lock (`Copies`), held across two queries for a `RCPT` and across the write of the item and its content for a message.

What a remote sender makes the queue hold. One `mail` item for each paired node that has a recipient of the message, with the whole message as content (at most `max-message-size`, 25 MiB) and a payload of the envelope and recipients, answered `250` once the item commits. The item's id is a hash of the `Message-ID` field and the sorted recipient addresses (of the message when it has no `Message-ID`), so the same message again is no new item, and neither is another message with that id for the same recipients, whoever sent it: the listener answers stored for both, and the row stays `queue-retention-days` (14) after delivery. The rate is the listener's internet limits (Listener limits above). `enqueue` tests the size of one item only (1 MiB payload, 64 MiB content). The total is `queue-max-megabytes` (1024) of pending items for each pairing, enforced only by the retention pass (every 40th maintenance round of 15 seconds), which fails the oldest pending items of that pairing, of every kind, until it is under: mail already answered `250` is among them, and the kind `mail` has no failed-service, so only a log line records it. A pending item waits up to 14 days and then fails. The mailbox quota is known to the edge node only as the local node's replicated mark, so it does not hold while the local node is away.

Bounces of relayed mail. A relayed message's `Return-Path` is `bounce+<mailOut item id>@<edge_mail_bounce_domain>`, the id a UUID with no keyed tag. Mail to such an address is not stored as mail: the address is taken only for a `mailOut` receipt of a node paired now, and a message with the text `message/delivery-status` and an `Action: failed` field (`edge_mail::parse_dsn`) is queued as a `mailStatus` item, one for each different report text. The local node (`note_edge_mail_status`, `back_to_outbox`) finds its own `mailOut` item by id and direction and changes a message only while it is still `ES_SENT` with the same `Message-ID`: a client message goes back to `ES_READY` with `sendError` set to the report's text (up to 4,000 characters), a template's message to `ES_BOUNCED`. Anyone on the internet who knows the item id reaches this: every recipient of the message and whoever saw its `Return-Path`. The report is not required to come from the MX the message went to.

What the local node takes from an item. `deliver#EdgeMail` resolves the recipient addresses again from its own accounts. The item's `authservId` replaces the local node's `smtp-server@authserv-id` for that message, and its `spamHeaders` are added to the local node's; only a paired edge node writes them. Each handler tests the node's role. A `mailOut` item is relayed once (the answer's idempotency key marks it).

A paired node's outbound mail on an all-in-one node. `refused_sender` refuses a `mailOut` item whose envelope sender or `From` is the server's own address or domain; it is not called on a dedicated edge node. The rule and the signing decision read the sender with `auth::from_address` (the first `From` field, the text after its last `<`), while the mailbox stores the first mailbox of the last `From` field as `mail-parser` reads it. `deliver_own` delivers such mail to the server's own accounts through `rewrite_head` with an internal `Authentication-Results` on top; `queue_back`, which queues it back to a local node, puts the internal field on top without `rewrite_head` and names the edge node's host name as the authserv-id that node trusts.

## DKIM signing and internal verification

The DKIM key is the property `mail-delivery/dkim@key` (an RSA key, PKCS#8 in base64 or PEM); a node set to make one generates RSA 2048 and writes it to `runtime/.env` (`crates/moqui-mail/src/auth.rs`). The selector is `mail-delivery/dkim@selector` (default `moqui`). A message is signed for its `From` domain when that domain is in `mail-delivery/dkim@domains`, or, when that list is empty, when it is the domain of a hosted or shared account (`signing_domain`). That is the domain test. A send by SMTP reaches it only when `mail-delivery/dkim@key` is set or the server is the node's own listener (`implementation.rs` `lettre_send`, which `deliver` calls for every send that is not through `edge:`, system mail and mail client mail alike), and then through any `EmailServer`, a mail account's own included: the account that sends, its own address and the server the message goes to are not tested, so a mail user's outgoing server receives the signed message. Through `edge:` the local node does not sign; the edge node does, testing the `From` domain against that paired node's replicated domains (`edge_mail.rs`), or, when `mail-delivery/dkim@domains` is set, against that list alone, whichever pairing the mail is from. Other mail of a paired node goes out unsigned. `org.moqui.mail.EmailServices.get#DkimRecord` answers the public key record, the selector and every hosted domain, and makes and writes the key when none is set and the host named `runtime/.env`. A message whose key cannot be had goes unsigned and is still sent. `verify_internal` (called from `delivery.rs` and `edge_mail.rs`) reads a stored message's DKIM signatures of the node's own selector, verifies them against the node's own key with no DNS query, and writes an `Authentication-Results` field under the node's authserv-id when one passes; it keeps only signatures of the node's selector and those domains. Inbound verification (`verify`) reads at most 10 signatures and ends within 45 seconds; a check that does not finish is a `temperror` verdict.

## Message parsing and storage

`crates/moqui-mail/src/store.rs` `parse_message` parses with `mail_parser::MessageParser::default()`; `store.rs` sets no limit of its own on parts or nesting. The defaults of `mail-parser` 1.0.1 are a nesting depth of 64, 10,000 parts and 3 levels of encoded nesting; `inbound.rs` `parse_rfc822` uses the same parser, and its walk for the ECA fields stops at depth 32. The size of a message is what is not limited on the sync path: each attachment's decoded bytes are held in memory beside the raw message, and `parse_rfc822` copies each part and the whole raw text again, so a message costs a few times its size in memory. An empty message and one with no header fields are refused. The stored header block is at most 65,536 bytes (`HEADERS_MAX`). An attachment is written to `dbresource://email/{account}/{message}/{n}-{name}`; in the name control characters and `/ \ ? # % :` become `_`, leading and trailing dots are cut, and at most 120 characters are kept (`safe_segment`). A hosted or shared account keeps at most its mailbox quota of mail (Listener limits above).
