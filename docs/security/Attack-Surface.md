# Attack surface of mr-moqui

This is a map of the HTTP routes, screens, REST, WebSockets, and the other listeners in this repository. It is for operators, security researchers, and review of this repository. It records what can be reached. It is not a vulnerability report, and it is not a WAF. Proof of the controls lives in [Proof-Tests.md](Proof-Tests.md).

Application components (Mantle, Marble, IronStone, and the mr-boss screens beyond the framework's token-route mount) add their own screens and services. Those are out of scope here, except where the framework mounts a route they plug into.

To report an issue that should stay private until it is fixed, write to [moqui-board@googlegroups.com](mailto:moqui-board@googlegroups.com). The policy is in [SECURITY.md](../../SECURITY.md).

## How to read this

A request goes from the client, through a reverse proxy or TLS, to hyper and axum in `crates/moqui-host/src/http.rs`, then screen dispatch, artifact authorization, and on to the database, search, mail, and jobs.

This server terminates TLS itself with rustls (`crates/moqui-host/src/tls.rs`) when the HTTPS listener is started. It is still meant to run behind a proxy. `webapp_https_enabled` defaults to false and is the flag generated URLs use when they pick https. Starting the listener is the separate rule in [HTTP container](#http-container).

**Defaults** are `runtime/components/base/framework/conf/MoquiDefaultConf.xml`. **On** and **off** mean those defaults. Rows say what untrusted input can reach, and what to keep in mind during a review. Designed admin tools are privileged on purpose.

`./moq run` merges `runtime/conf/MoquiDevConf.xml` on top of that file. The dev file sets `instance_purpose` to `dev`, `webapp_allow_origins` to `*`, and `ssh_port` to `2222`, and it sets `tarpit-enabled` false for screens, screen transitions, and services. It does not declare an H2 console. The Jackrabbit repository element in it is commented out. The tables below stay on the default conf unless a row says otherwise.

## HTTP authentication and authorization

A servlet request is signed in from the session cookie, HTTP Basic, an `api_key` or `login_key` header, or `authUsername` and `authPassword` (`docs/interfaces/Web-Scripts.md`). A key header is checked on every request, ahead of the cookie and Basic. A key for a user other than the session's, or a rejected key while a session is signed in, is a 401. A rejected key with nobody signed in leaves the request anonymous with the login error. `/notws` accepts the session cookie and, failing that, a `login_key` header. `/termws` accepts the session cookie only. Notification sockets revalidate the original session or hashed login key every 60 seconds and close on logout, a changed user, key revocation or expiry, or a failed credential lookup. Revalidation does not log in again or write login history. Protocol Ping/Pong traffic cannot extend authentication.

A node the desktop app runs in its own process may have no HTTP or cluster port (`moqui_host::start_embedded_with`, `crates/moqui-host/src/in_process.rs`). Its window's requests and sockets reach the router in process, through the same checks as a listener's, from the loopback address, as a sidecar window's do over loopback HTTP. The app keeps the node's session cookie for the window and sets `Host`, `Cookie` and the forwarded and edge link headers itself, never from the page (`crates/moqui-desktop/src/node/scheme.rs`). Nothing outside the app's process reaches that path.

Screens carry `require-authentication`. The parser maps `false`, `anonymous-view`, and `anonymous-all` to those modes, and it maps a missing attribute to required. A render requires a user when any screen in the chain is required. An anonymous login counts as a user.

Artifact authorization runs as each screen, transition, service, REST path, entity, git repository, and LLM call is pushed. Inheritable allow and always records cover children on that stack unless a more specific deny wins.

### Parent frames

A render checks only the last screen of its path; the screens above it are entered without their own check (Java's `pushInternal` with authorization required of the target alone), so their always- and pre-actions run for a user who may open the target. The qvt shell loads each level of a page as its own request, and the terminal client each level between the app root and the leaf (`Party.tui`), which checks that level as a target. A level the user may not open alone answers, only when the request names in `X-Moqui-Page-Path` a page strictly below it on the same screens that the user may open (the page's screen permitted with its parents on the stack, its subscreens items' user groups, and a shared device's route group), as the page's frame (`screen/frame.rs`): a GET in qvt or tui, written from the level's widgets as its subscreens placeholders alone (up to the first active level), `private, no-store`. Nothing of the level runs: no always-, pre- or widget actions, no section, no form, no label, no transition; its shell providers are not gathered for it (the shell gathers them only from roots the user may open). Its tabs list only the subscreens the user may open: in qvt the shell's menu data fills them, in tui the frame carries them, as the menu data makes each entry of that level for the page (each subscreen authorized below the level, its `menu-include` and `disable-when` evaluated, its title expanded; nothing of the level itself runs, where the menu data also runs the levels' pre-actions). What the frame tells the user is that the level exists, its title (tui) and that it has a subscreens placeholder or a tab bar, which the page's own menu data and breadcrumb titles already showed them. The level asked for without the header, in another mode (an html page), as a transition, for a page the user may not open, that does not resolve, or is not below it, or a level with a screen on its path that grants anonymous access (whose own render may apply that grant where the check does not), is refused or rendered as before; the launcher lists only roots the user may open. Checking the page is one path resolution and one permission check of its screens, as its own request would be.

Monitor is a section of System with no group of its own, so a `SYSTEM_APP` holder reads the telemetry: traces with their users, logs and errors, in Monitor and, with `DASHBOARDS_APP`, in Explore. The `MONITOR_*` permissions (`MONITOR_INGEST`, `MONITOR_REPLAY`, `MONITOR_INCIDENT`, `MONITOR_RECOVER`, `MONITOR_RECOVER_ADMIN`, `MONITOR_SETTINGS`, `MONITOR_EVAL`, `MONITOR_EVAL_RUN`) each gate one thing inside it. A database seeded before Monitor moved keeps its `MONITOR_APP` group, which still grants those datasets and `MonitorServices` to its holders but no screen ([Monitoring, Upgrading](../tools/Monitoring.md#upgrading)).

`user-facade` `authz` sets the privileged groups to `ADMIN`, `ADMIN_ADV` and `SYSMSG_RECEIVE`. Creating, updating, or deleting membership in those groups is allowed only when the caller is already a member. Seed and install, and a call with authorization disabled, skip that check. `SYSMSG_RECEIVE` is there because its members call `receive#IncomingSystemMessage` as a remote system, and a party screen that adds memberships by posted `userGroupId` would otherwise let a user join it. The sealed permissions are `GROOVY_SHELL_WEB`, `SQL_RUNNER_WEB`, `SSH_SHELL`, `TERMINAL_HOST`, `LOAD_RUNNER`, `ADMIN_LOGIN_AS`, `ADMIN_PASSWORD`, `SearchRemote`, `DashboardRemote`, `REST_SCHEMA`, `LlmGatewayUse`, `COMPONENT_DEPLOY`, `DATABASE_ADMIN`, `DATABASE_EXTERNAL`, `ADMIN_CONSTITUTION_GLOBAL`, and the delegated-administration grants that widen access, `ADMIN_IDENTITY_GLOBAL`, `ADMIN_ACCESS_MANAGE` and `ADMIN_BACKUP_DOWNLOAD`. A `UserGroupPermission` row for one of those can be written only by a caller who already has that permission, and a `UserGroupMember` row in a group that grants one (not ended) only by a caller who has each such permission, so a sealed grant is not passed on through a group that is not privileged; an update that only ends a membership sooner passes (`Security.eecas.xml` `UserGroupMemberSealed`, `assert_sealed_group_membership`). A component adds to either list with `authz` child elements, `<privileged-group name="..."/>` and `<sealed-permission name="..."/>`, which the conf merge adds to every other component's and never replaces; setting the attribute in a component's conf replaces the framework's list, so it is not done (mr-boss adds its privileged Admin groups this way). The check reads the attribute, or the framework's default list when it is empty, joined with every element (`security_checks.rs`). A DataDocument field expression (a `fieldPath` with `(`) is JavaScript run as whoever reads the document (the grid, exports, feeds, reports), so creating or updating one needs `DATABASE_ADMIN`, which already allows data changes that end in code running on the server (`Security.eecas.xml` `DataDocumentFieldExpression`, `assert_document_expression` in `crates/moqui-core/src/service/security_checks.rs`). Seed and install, and a call with authorization disabled, skip that check too. Its context holds no encrypted or password fields (`expression_hidden`, `crates/moqui-entity/src/entity/field_rw.rs`). A decimal formula (a payroll component's) is not script: `org.moqui.impl.ExpressionServices` parses it into a tree of numbers, input names, operators and an allowlist of functions and computes it over a map of decimals (`moqui_lib::decimal_expr`), with no context, entity, service or I/O behind it, so writing one needs only the application's own permission ([ExpressionServices](../dev/JS-Framework-Services.md#expressionservices-decimal-formulas)).

Delegated access administration goes through `org.moqui.admin.AccessServices` (`find#Groups`, `get#Group`, `create#Group`, `store#Group`, `store#Membership`, `end#Membership`, `preview#Grants`, `apply#Grants`, `store#GroupPreference`; bodies in `framework/service/org/moqui/admin/Access.js`) and `IdentityServices.check#AdministrationPath` (`Identity.js`). `ALL_USERS` may call them (`AdminAccessServices`, an inheritable `AUTHZT_ALLOW`, so an app's deny of the package still applies); each checks `ADMIN_ACCESS_VIEW` or the sealed `ADMIN_ACCESS_MANAGE` with `ec.user.hasPermission` and refuses without it. They write the security rows through the entity facade with authorization on, so the privileged-group and sealed-permission EECAs decide each row as for any other writer, and each write moves the authorization caches here and on every live cluster member. Before writing they refuse, with a reason code rather than an error: a membership outside a registered bundle (`moqui.security.CapabilityBundle`, seeded by each component) or a custom group of a registered purpose (a `UserGroupType` with `optionIndicator` Y); a grant that is not a registered bundle's permission or artifact binding (so no deny can be removed and no unregistered `ArtifactAuthz` added; a binding carries the bundle's filter sets), counting a privileged group's bundle only for a member of that group, so its permissions are not copied to another group; a sealed permission the caller does not hold, granted, ended, or carried by a group whose membership is given (no sealed grant smuggled through a group); a privileged group, or its members, changed by a non-member; a custom group named after a privileged or framework group; a stale revision; and any membership, group-flag or grant change that would leave no usable instance administrator where there was one. A usable administrator is a date-valid member of `ADMIN` who is not permanently disabled or terminated, can authenticate (a password, or an external identity with an enabled sign-in flow), holds a date-valid factor when any of its groups requires one, and is admitted by its own and its groups' `ipAllowed` from the caller's address, checked now and at each later date the change names. Memberships and grants are ended, never deleted; `UserGroupMember`'s and `UserGroupPermission`'s dates, `ArtifactAuthz`'s type, `UserGroup`'s `requireAuthcFactor` and `ipAllowed` and `UserGroupPreference`'s value are audit-logged with the caller's reason, and a removed binding or default gets an explicit audit row. `UserSecurityChecks.privilegedGroups()` and `sealedPermissions()` give scripts the effective lists the EECAs read, for markers and reasons; they grant nothing. An app adds organization scope above these services (IronStone Admin checks each member against the organizations its administrator works for); the framework services know no organization.

The same services read the registry as a capability matrix, the row rules and a review (Admin P9: `get#Capabilities`, `get#ScopeRules`, `get#GrantReview`; `AccessCapabilities.js`), each under `ADMIN_ACCESS_VIEW`, writing nothing and evaluating nothing: the matrix shows a launcher binding and each permission by its kind as rows of their own (a launcher is never read as a view or a change) and lists what a group holds that no registered bundle describes read only; the scope rules name each `EntityFilterSet` bound to an `ArtifactAuthz` with its source and never return a filter's `filterMap` or an `applyCond`; the review leaves sealed permissions out, counted, and holds no allowed IPs, preference values or filter expressions. A grant request may bind a row rule: a filter set a registered bundle the caller may assign names for that artifact group, added to the group's binding of the registered type (`UNREGISTERED_SCOPE`, `SCOPE_UNBOUND`), never to a binding that carries a filter set of its own (`SCOPE_CONFIGURED`: an administrator group's active-organization rule is not "completed") and never removed (`SCOPE_REMOVAL`: removing one widens what members read). The grant revision covers each binding's filter sets, and a bound rule gets an explicit audit row. Arbitrary filter sets and expressions, removing a filter and raw `ArtifactAuthz` rows stay Tools' (`ADMIN`).

Sessions and an account's credentials (Admin P4) are `IdentityServices.find#Sessions`, `revoke#Sessions`, `get#AccountCredentials` and `revoke#AccountAccess`, under the same `AdminAccessServices` grant. A user reads and ends their own sessions with no permission (Commons Account's "Where you are signed in"; never the current session, and a visit of another account is refused and counted); another user's need `ADMIN_IDENTITY_VIEW` to read and `ADMIN_IDENTITY_MANAGE` to end. A session is named by its visit, never by its cookie, token, user agent or contents, and credentials are metadata only (no secret, hash, verifier, factor option or recovery code). Ending a session deletes its web session on this server, retires the live copy and publishes the session end to every live cluster member, as `end#UserVisit` does, through `UserSecurityChecks.endUserSessions(userId, visitIds)` (`user::end_user_sessions`), which decides no authority. `revoke#AccountAccess` (another user only, `ADMIN_IDENTITY_MANAGE`) ends every session and sets the account's `hasLoggedOut` (so a session no row names yet signs out at its next request), ends the login keys (access tokens, device and sign-in keys, so a notification socket on a key closes at its next check), app passwords (XMPP's sign-in), SSH keys and SIP phones (each live SIP engine drops the phone), pauses the agent triggers that run as the user with their cron jobs and asks the user's open agent runs to cancel; it leaves the account enabled. Ending another user's sessions or access is refused for an account in a privileged group the caller is not in or holding a sealed permission the caller lacks (`Identity.js` `heldBeyond`, which Mantle's account-wide changes and IronStone's Login as also apply). The per-request session refresh and the notification socket's 60-second check sign out an account disabled for good (`disabled` with no `disabledDateTime`) or past its `terminateDate`, as login refuses it; a tarpit lock (disabled with a time) stops new logins only, so failed logins by someone else cannot sign the owner out. A ServiceJob whose run-as user is disabled for good, past its end date or gone does not run: the run is recorded with the refusal. `UserAccount`'s `ipAllowed` and `requirePasswordChange` are audit-logged. The framework knows no organization: an app checks the target first and asks for `ADMIN_IDENTITY_GLOBAL` for an account-wide change of an identity shared with an organization outside the caller's scope (IronStone Admin's `check#Record` with `accountWide`; Mantle's `IdentityServices`). `AccessServices.check#GrantProposal` and `apply#GrantProposal` take a grant proposal of registered bundles for an account an app provisions, by the same delegation rules as `store#Membership` (`ADMIN_ACCESS_MANAGE` or `ADMIN_IDENTITY_MANAGE` to apply), written with authorization on so the EECAs decide each membership.

Shared devices (Admin P18; [Shared devices](Shared-Devices.md)). A browser registered as a device opens one route group with no person signed in: `org.moqui.admin.DeviceServices` registers (`register#Device`, `issue#DeviceCode`), lists and revokes devices for a holder of `ADMIN_ACCESS_VIEW` or `ADMIN_ACCESS_MANAGE` (the `AdminDeviceServices` grant for `ALL_USERS`; each service checks its permission), and `/Device` redeems a registration code for whoever posts it (`redeem#Device`, no sign-in, the page's session token). The code is about 99 bits, returned once, kept only as its hash, good once and for 5 to 60 minutes; a wrong, used or expired one gets one answer and is counted by the web protection. Redeeming sets the cookie `moqui.device` (`HttpOnly`, `SameSite=Strict`, `Secure` on https), whose secret is kept only as its SHA-256 and is given to no script. A request with that cookie runs as the registration's display account for that request alone: the account is never written to the web session, so no session row, live session, notification or terminal socket or Assistant stream holds it, and there is no session of it to take over. Such a request reads no `api_key`, `login_key`, Basic credentials or `authUsername`, no login succeeds in it, and it is refused (403) every screen, transition, REST and service path and script servlet outside its route group's artifact group, before anything of the target runs (`user::device::check_route`); what the group admits is still authorized as the display account. A refusal or failure answered to a device's browser page is a fixed plain page with no error text, never the instance's error screen. A display account (`UserAccount.displayAccount`) is never signed in by a password, a key, an app password, an SSH key, an identity provider, a factor, a reset or `Login as`, may hold no privileged group or sealed permission, and is checked on every request of its devices, as are revocation, the end date, the idle timeout and `ipAllowed`, with no cache, so each holds from the next request on every server. The cookie is a bearer secret: it is replaced daily, and the one before it stops the device ten minutes later (a copy is the only thing left presenting it), which does not detect a copy used within the day; the device list shows the last address and client. A registrar gives a device nothing they could not give a person: every group of the display account must be one they could assign. The framework knows no organization: an app scopes the display account first (Mantle's `register#SharedDevice`, which refuses another organization's). Evidence (registered, code shown, redeemed, refused, stopped, revoked) is on the display account in the audit log, never with a code or a secret. A compromised device browser reads what its display account may read through the route group's screens until it is revoked.

Delegated configuration (Admin P8) is `org.moqui.admin.ConfigurationServices` (`get#EffectiveSettings`, `get#InstancePreference`, `store#InstancePreference`, `find#LocalizedMessages`, `store#LocalizedMessage`, `find#LocalizedEntityFields`, `store#LocalizedEntityField`; bodies in `ConfigurationSettings.js` and `ConfigurationLocalization.js`), which `ALL_USERS` may call (`AdminConfigurationServices` in `data/AdminConfigurationData.xml`, an inheritable `AUTHZT_ALLOW` that names each service, never the whole file): reads check `ADMIN_SETTINGS_VIEW` and changes `ADMIN_SETTINGS_MANAGE`, none remote. A setting is a seed row of `moqui.server.InstanceSetting`; only a registered preference is written, typed and within its allowed values and limits, and a setting marked secret or whose property name reads as one (pass, pw, key, secret, token, credential) is never returned and never a preference. `get#InstancePreference` answers any caller one registered, nonsecret preference. A translation must have exactly its original's `${...}` placeholders, so a translator cannot add an expression the server would evaluate, and carries no markup; a label is translated only for a `moqui.basic.LocalizedLabelTarget` that is an `enable-localization`, unencrypted field of a configuration entity with one key. The conf's own view (`get#ConfView`, file and line of each value) stays `ADMIN`'s.

Sign-in providers and sign-in policy (Admin P10). `ConfigurationServices.find#IdentityProviders`, `store#IdentityProvider` and `test#IdentityProvider` (bodies in `ConfigurationProviders.js`; the `AdminIdentityProviderServices` grant, ALL_USERS, each checking its own permission) administer `moqui.security.sso.AuthFlow` with its OpenID Connect, OAuth and SAML row, `AuthFlowFieldMap` and `AuthFlowRoleMap`. Whoever configures a provider decides who signs in as the accounts linked to it, so the parts are held apart: reading needs `ADMIN_CONNECTION_VIEW` or `ADMIN_ACCESS_VIEW`; the configuration `ADMIN_CONNECTION_MANAGE`; the role mappings, the default group, the rule that links existing accounts and enabling `ADMIN_ACCESS_MANAGE` (sealed). A mapped or default group is one the actor may assign by the grant proposal's rules and is never a privileged group or one that grants a sealed permission, whoever asks. Enabling needs a passing test of the configuration as it is now and is refused while a linked account holds access beyond the actor's (`HELD_BEYOND`); disabling keeps the administration path. A change of the client type, client id, issuer or discovery URL, realm, an endpoint, the Apple team or key (SAML: the metadata location or entity id) needs the secret entered again in the same save, else the stored one is cleared; either way the provider is saved disabled with its test mark cleared, so nothing reaches the new endpoint with the old secret. A secret is write-only (`secretSet` on a read), never logged, and its replacement or clearing is an audit row with no value. Identity mappings are a claim name onto the full name, email address, locale or time zone, never an expression; a provider whose rows carry an expression or a mapping service (an `ADMIN`'s, in Tools) keeps them, read only. A change of what a sign-in is verified by (the token signature, the nonce) disables the provider the same way, the secret kept. URLs are `https` (`http` only for the server's own machine, and only when `instance_purpose` is not `production`), with no credentials or fragment; on a production instance a provider started here is saved with `AuthFlow.allowPrivateNetwork` `N`, which the service never changes: the sign-in's own HTTP client (`crates/moqui-host/src/sso.rs`: no redirect followed, 1 MiB, 30 seconds) then sends no request of that flow (discovery, token, keys, user info) to a loopback, private or link-local address, by name (the resolver `moqui_lib::http::PublicOnly`) or written out. A flow without the flag (an `ADMIN`'s in Tools, or one of an instance that is not production) may be on the instance's own network. `test#IdentityProvider` calls `org.moqui.sso.AuthServices.check#Flow` (Rust, `service/sso.rs`; `ADMIN_CONNECTION_MANAGE` or `ADMIN_ACCESS_MANAGE`), which starts a login as `login#User` does and keeps nothing: the server reads an OpenID provider's discovery document (the same outbound request a sign-in makes, to the URL an integration administrator configured), no token is asked for, nobody is redirected and no account is made; its failure text names URLs and never the secret, and a discovery document that does not parse is reported by the kind of error and its position, never by the parser's text, which quotes the body.

The sign-in itself obeys the same bounds whoever wrote the rows (`service/sso.rs`; the account sync writes with authorization off, which the security EECAs skip): an existing account with no provider id is linked only under the flow's `accountLinkEnumId` `AflVerifiedEmail` rule (an `email_verified` claim and an `email` equal to the account's address), never by the provider's username alone, and never an account in a privileged group or in a group granting a sealed permission (an administrator links it); a role map or default group naming such a group is logged and passed over; and the sync ends only memberships in the groups the flow's role maps name, so an administrator's membership and one given by hand stay. A provider's id is linked with the provider it is of (`UserAccount.externalAuthFlowId`, set when a sign-in makes or links the account): an account another provider is named on is never found by this one, whatever id it asserts, so a second provider (with other users, or run or configured by somebody else) signs in only its own accounts. An account with an id and no provider named (linked by hand, or before providers were told apart) is taken by the provider that first signs in with the id; with several providers enabled, never an account in a privileged group or in a group granting a sealed permission, where an administrator names the provider. Under the same `AflVerifiedEmail` rule a sign-in whose `email_verified` claim is true and whose `email` equals the account's address (as it is after the flow's field maps) writes a `moqui.security.public.VerifiedAddress` row for that account and address when there is none, as the registration's mail link does (after the account's transaction, in one of its own: a failure to record it is logged and never fails the sign-in): the flow's rule is the statement that the provider's verified address is trusted, so whoever may set it on a flow decides which providers confirm an address for what an application gates on one (Smithy's writes and pushes). A flow without the rule writes none. A closed account (disabled for good, or past its `terminateDate`) is refused before the sync writes anything. An `AuthFlowFieldMap.srcFieldName` that is a plain name is read as the claim of that name, never evaluated; only a `dstFieldExpression` or a source that is not a plain name (an `ADMIN`'s, in Tools) is an expression. The `HELD_BEYOND` rule above counts the accounts the provider signs in: those it is named on and those that name none.

`ConfigurationServices.get#SignInPolicyValues` (Rust, `service/sign_in_policy.rs`) answers a fixed list of nonsecret `user-facade` `password`, `login-key` and `login` attributes and the web session's timeout, as the server runs with them, to a holder of `ADMIN_SETTINGS_VIEW` or `ADMIN_ACCESS_VIEW`; `get#EffectiveSettings` shows them through the settings that name one as `confAttribute` (to an access administrator the sign-in settings only). `AccessServices.preview#GroupSignInRules` (`ADMIN_ACCESS_VIEW`) previews a group's factor and address rules as counts, naming no member.

Connections and mail relays (Admin P11). `ConfigurationServices.find#Connections`, `get#Connection`, `store#Connection`, `test#Connection` and `find#ConnectionConsumers` (bodies in `ConfigurationConnections.js`; the `AdminConnectionServices` grant, ALL_USERS, each checking `ADMIN_CONNECTION_VIEW` or `ADMIN_CONNECTION_MANAGE`) administer the native connection records through registered adapters (`moqui.server.ConnectionAdapter`, seed data, never a name an administrator enters): `SystemMessageRemote` (kind remote), an `EmailServer` no `EmailAccount` owns (relay), `EmailOAuthProvider` (mailOAuth) and `NetworkPrinter` (printer) here, and a component's kinds through its adapter service (Mantle's gateways), which no group may call directly and which is built with the same engine. What they hold to:

- A secret is write-only (a read answers whether one is set), is never logged or put in a test's text, and its replacement or clearing is an audit row with no value. Only the fields a kind declares change, each validated; a send service, a gateway's service names, `disabled` and `allowPrivateNetwork` are never among them.
- The endpoint-change rule: a change of a host, port, URL, user or kind of sign-in needs the secrets entered again in the same save, else every stored secret of the connection is cleared; either way the record is saved `disabled` Y and its test mark (`moqui.server.ConnectionCheck`: a fingerprint of the endpoint fields, never a secret) is cleared, and a passing `test#Connection` of it as it is then enables it (not one an administrator had disabled before the change). The services write the audit rows the entity audit log does not (a first value, `disabled` and `allowPrivateNetwork` among them). A value saved as it was read is no change; a URL is read without credentials written into it. `disabled` is enforced by the senders, not by Admin: the SMTP transport (`moqui-mail` `smtp_transport`), `send#ProducedSystemMessage` and `send#SystemMessageRest`, the print service, and Mantle's gateways for their connection. While a cleared secret has not been entered again a test sends nothing.
- Server-side requests: a test makes the server contact an address its administrator chose (one HEAD with no credentials and no body, an SMTP connect and sign-in, a test page). On a production instance a connection started or repointed through these services is saved `allowPrivateNetwork` N, never set back by them, and its sender then reaches no loopback, private or link-local address: the HTTP client by its resolver and redirect checks, SMTP by one lookup (`moqui_lib::net::public_addresses`) and a connection to the address found, the IPP client by the `PublicOnly` resolver with no redirect followed. An instance administrator allows a connection on the instance's own network (Tools). A test's answer is a host, a status code and one of a fixed list of failure kinds, never a response body or the remote's own words, within the clients' time limits.
- An address the server expands (`SystemMessageRemote.sendUrl`) may hold the three names the sender gives and no other `${}`; URLs are `https` (`http` only for the server's own machine on an instance that is not production).

A scheduled job is an administrator's stored text that a service later runs with, and a subscription is how a notification reaches a person, so both are closed lists.

- Nothing is changed without a registration. `store#Job` writes only a job that has a `moqui.server.JobRegistration` (its owner's seed row), and only the controls that row names: the schedule (a cron expression of its own characters that the scheduler parses and that comes due no more often than the row's minimum interval; never cleared, never given to a job that has none), the pause, the priority and the wait after an error. The service has no parameter for the job's service, the identity it runs as, its topic, its time limits, its lock expiry or its dates, so no request names one. - A run outside the schedule is a registered recovery (`RecoveryDescriptor`, `targetKind` `ServiceJob`) through `execute#Recovery`. The native action starts nothing itself: in a transaction of its own, with the job's row and its lock row locked, at the revision read and only while no run holds the lock, it marks the job due (the step, `apply#JobRecovery`, checks the registration again itself, so it marks no unregistered job due whoever calls it), and the scheduler's next pass claims the lock and runs the job as it runs every run. A paused job, one outside its dates and one with no schedule are not started this way. A lock is never cleared or deleted here; a run whose server stopped is ended by the scheduler, which takes the lock over when its lease lapsed (`leaseExpireDate`, renewed by the running instance until the run ends or passes its job timeout), when the instance is gone, or after `expireLockTime`.
- A job run carries no organization, so a holder of `ADMIN_OPERATION_VIEW` reads the runs of every organization's jobs: their times, where they ran, the class of an error and up to five lines of it with addresses, URL paths, credentials and long tokens struck out, the numbers among a run's results, and the names of its parameters with a value only where it is a number, a yes or no, or a registered parameter (a stored text counts as a number only up to nine digits, so not an account, card or phone number, and nothing named like a secret is shown as a value, a result neither). Never a run's messages, a result's text or another parameter's value; a queued call (`ASYNC_QUEUE_`, which stores its caller's parameters) is never listed. A run that ended without an error while its results or its owner's items count failures is answered as ended with failed items, never as a success. `get#JobRunItems` calls the service the job's owner registered (`itemsService`) as the caller, so the owner's permission and scope decide, and reads its answer as data (cut, masked, states of a fixed set).
- A job's notification carries the run's errors, parameters and results unmasked, so a recipient is added only where the registration names the permission a recipient must hold, and only an account that signs in and holds it; an unknown name and an outsider get one answer.
- `store#TopicDefaults` (`ADMIN_SETTINGS_MANAGE`) writes only the delivery settings a `moqui.server.TopicRegistration` names; whether a topic is private, its title, error title and link templates (each expanded as a script when a notification is sent), its email template, its approval services and its inbox are never written, and none is returned by a read. `store#TopicSubscription` (`ADMIN_OPERATION_MANAGE`) sets a user's choices only for a topic whose owner registered an audience, and only for an account that signs in and holds that permission, the caller's own too: nobody is subscribed to a private topic, or to any other, outside the audience its owner registered. `allNotifications` (a user who has it receives every message of a topic, a private topic's too: the notification resolution adds such users to every message that is not direct-only, which the framework's own job error and web error topics rely on; a message whose content is its named recipients' alone is sent direct-only, `NotificationMessage::direct_only` or a script's `directOnly()`, as a business alert's and IronStone People's confidential notices are) is never set by this service, only ended; setting it stays an instance administrator's, in Tools. Subscriptions are listed by name only within the registered audience and only for a holder of `ADMIN_OPERATION_VIEW`; the others are counted.

The screen escapes them, and the CSV render guards a cell that begins like a formula.
- Whose changes. A projection with no `sourceService` is a record of the whole instance (a group's grants, a connection, a job, a setting): a holder of `ADMIN_AUDIT_VIEW` reads it. A record that belongs to an organization (a user's account, a membership, an invitation, a lifecycle operation, an export a person made) is registered by the component that knows organizations, with its `sourceService`: that service (the contract `find#OwnedChanges`) finds the audit rows within the caller's own scope and answers their ids only, and the rows are read and masked here, each checked to be of a projection of that source. It is called through `call#ChangeSource`, whose `ALL_USERS` ALLOW is not inheritable, so the owner's service is authorized as a direct call of it is. Mantle's source (`mantle.party.IdentityServices.find#IdentityChanges`) reads views that join the audit log's rows back to an internal organization, under the organization entity filters of the authorization the call runs under. Without such a component (a framework-only instance) a user's account and memberships are not in `find#Changes` at all.
- Bounds. A find reads at most the 2,000 newest rows across its sources (a deeper page is refused with a notice), a page is at most 100 rows, an export one page of 1,000 marked truncated when more match. A source that fails is named and the others are answered.
- What is written. An administrative action that changes no audit-logged field leaves a row of its own, with the actor, the session (`changedInVisitId`) and the reason: another user's sessions ended and access revoked (`IdentityServices`, on the account; the kinds and counts, never a credential), an import applied (`TransferBatch`, counts), a mail message closed or sent again from the queue (`EmailMessage`; a message's own state rows are every send of every user and are not registered).
- Access evidence is log lines, read through a dataset. A dataset that aliases a telemetry index (`indexName`) needs a row filter in its definition, but a dataset has no field list: whoever holds its artifact reads each matching line whole (a scheduled export's recipient addresses and a runtime setting's value are attributes of the audit lines). So an application that shows such lines to a delegated reader grants the alias's artifact to no group and reads it in its own service after its own check, with authorization off, answering named fields only (mr-boss `admin-access-log`, `ironstone.admin.AuditServices.get#AccessLog`). The row filter of an alias is whatever its definition says, so the engine asks for the index's own artifact (`org.moqui.report.dataset.otel_logs`), not only the alias's: of whoever saves the definition (`save#Definition`, a copy, a restore, an import, a git pull), and at each read of the reader or of the saved definition's owner, asked as the owner then, while the owner's account is open (`crates/moqui-report/src/alias.rs`; [Monitoring](../tools/Monitoring.md#dataset-aliases)). A holder of `org.moqui.report.dataset` update who is granted the datasets they name by a pattern (mr-boss's dataset steward, `insights-.*`) is refused the save of an alias of a log index, and a row written past the save is refused when read; the same holds for a business dataset's document read without its signal, or under the signal with no registered scope policy bound, which needs the document's own update artifact of every reader. A shipped alias (a component's `report/*.json`) is its component's code and is read by its own artifact: grant it as narrowly as its filter deserves, or to no group as here.

The new-device sign-in notice (Admin P10). `IdentityServices.notify#NewDeviceSignIn` is called by the EECA `UserLoginHistoryNewDevice` when a successful sign-in's history row is written (after the sign-in, by a worker; at most one row a minute for a user), with authorization off and in a transaction of its own; no group is authorized to call it. An account's first sign-in sends none.

Owned resources (Admin P6). A shared drive (`FileServices.transfer#DriveOwner`) and a shared mail account (`EmailClientServices.transfer#EmailAccountOwner`) change owner by their owner, or for another user with `DRIVE_OWNER_CHANGE` or `EMAIL_ACCOUNT_OWNER_CHANGE` (granted to `ADMIN`); the new owner must be an enabled account that is not ended and not an external user (`EXTERNAL_USER`), and only a shared drive (not personal, records or mirror, not archived) or a shared mail account (`EakShared`) moves: a personal account keeps its owner's own sign-in. `find#OwnedDrives` and `find#OwnedEmailAccounts` list names only, the caller's own or another's with the same permission. ## Cross-cutting controls

These apply unless a row says otherwise.

### Session cookie

The session row is `moqui.server.HttpSession`. The cookie is `moqui.session={id}.{mac}`, then `HttpOnly`, `SameSite=Lax`, and `Path=/`. `Secure` is added only when the request is https: the TLS listener, or `X-Forwarded-Proto: https` from a peer `ClientAddressing` believes. A client that is not that peer cannot turn the flag on by sending the header. The visitor cookie is `moqui.visitor`, with `Max-Age` of one year. The session cookie itself has no `Max-Age`.

The MAC is HMAC-SHA256 of the session id under `session_cookie_key`, base64 URL-safe without padding. A bad MAC is treated as no session. The session id and the session token are 20 random bytes, hex, 40 characters. `session-config` is `timeout="60"` (minutes), `flush="eventual"`, `max="10000"`.

`session_cookie_key` ships as `CHANGEME` with `is-secret="true"`. Startup generates a value into `runtime/.env` when the property still ends in `CHANGEME`. See [Secrets](#secrets).

#### Pages without a session

A request that comes with no session cookie starts no Visit until the cookie comes back or a user signs in. Two kinds of page send no session at all, so no cookie comes back:

- A page a shared cache may keep (`Cache-Control` with `public`), for a request with no live session (no verified session cookie, or one naming a session that is gone) and nobody signed in: no `Set-Cookie`, `moquiSessionToken` or `X-CSRF-Token`, and the session made for the request is discarded unwritten, so a cache never keeps a new session's cookie to hand to others.
- A page whose screen or servlet calls `ec.web.declineSession()`, whatever its caching (a preview frame on its own host, an embed, a beacon). For a request with no session of its own and nobody signed in it is the same as the public page. A request that has a session keeps it and is sent nothing new: no cookie and no token. Either way a Visit the request started at the bind (a returning `moqui.visitor` or a session cookie with no visit yet) is deleted, with a Visitor made for it, and the session forgets it, so no Visit has a declined request as its `initialRequest`. A Visit a sign-in in the request started stays. A page that signs a user in should not decline.

```js
ec.web.declineSession()   // e.g. mr-pass Shop/ShopPreview.js, before it writes the preview
```

A public island's component is the first kind too (impl-shop F72): the `.qvue` or `.qjs` answer of a screen that says `server-static` for that mode itself (not a placeholder screen's automatic one) or declines its session is sent with the `screen-server-static` `Cache-Control` (public by default), so it makes no session, but only for a request that brought no session of its own and has nobody signed in (`render.rs` `is_public_island`). A signed-in user, a request with a session, and any other screen's component get `private, no-store`, and keep their session. A `Cache-Control` the screen set itself stands. A screen that says `server-static` for qvue or qjs must send the same component to everyone; data for one visitor comes by a later request (a transition), which keeps its session.

### The system scope

`ec.artifactExecution.runAsSystem(body)` runs `body` with no user and authorization off, in a fresh execution context that shares the caller's transaction, effective time and agent origin (`user/system.rs` `as_system`; Commerce F72). It is for a service that has already checked its caller and must write what that caller has no right to write directly, such as Mantle's site page saves into a page space with `restrictUpdate` (a rule like `get#WikiPageAccess`'s `!userId && authzOff` then admits it). The caller's user, authorization and artifact stack come back when `body` returns, throws or panics; the messages and errors `body` added are moved to the caller's context. Records written inside have no `changedByUserId` or `lastUpdatedByUserId` of a user. A wiki save can still say whom it was for: `update#WikiPage` reads `historyUserId` only with no user and authorization off, for its `WikiPageHistory` row and a new page's creator (Mantle's site page saves pass the acting user), and `get#WikiPageHistory` names that user for a version that has none of its own.

Only a service's own code may call it: the top artifact frame must be a service's (`AT_SERVICE`), pushed after any screen render in progress on the thread began (`ExecutionContext::in_service_body`). Anything else is refused with an error: a screen's actions, widget expressions and transitions, a screen a service renders (the render began after its frame), a REST resource, a web script, a webapp action and a script with no frame. A remote or REST caller has no way to name it; it reaches the scope only through a service whose own code calls it, so the service decides what runs. Rust code calls `crate::user::as_system` directly. There is no XML action for it.

### CSRF

`webapp_require_session_token` is `true`. POST, PUT, PATCH, and DELETE on a transition that runs actions must send `moquiSessionToken`, or a header `moquisessiontoken`, `sessiontoken`, or `x-csrf-token`. The compare is constant time. A missing or wrong token is 401 `Session token is missing or is not valid`. A transition may set `require-session-token="false"`. Header authentication skips the check: Basic, `api_key`, `login_key`, or `authUsername`. A new session skips it too. Responses set `moquiSessionToken` and `X-CSRF-Token` when the cookie is new or the token changed.

### Login lockout and passwords

`login` is `max-failures="3"` `disable-minutes="5"` `history-store="true"`. The account is disabled when `successiveFailedLogins + 1` is greater than `max-failures`, so the fourth failure starts the five-minute window. That window is not a substitute for an edge limit on the login URL. The per-client login rate limit in [Web protection](#web-protection) is off until per-client rules are on.

New password hashes are argon2id. Legacy hashes still verify, including the conf type `SHA-256`. The password element also sets `min-length="8"`, `min-digits="1"`, `min-others="1"`, `history-limit="5"`, `change-weeks="104"`, and `email-expire-hours="48"`. A login key is hashed with `login-key` `encrypt-hash-type`, which is SHA-256, and it is not hashed with argon2id. `login-key` `expire-hours` is 144.

A sensitive action can ask for a recent sign-in (`check#RecentAuth`, five minutes): a password login, a second factor's code,
an SSO login with a recent `auth_time` or a re-authentication counts; a key, an app password or an internal login does
not, and another user's login in the session drops it. `reauthenticate#User`
checks the signed-in user's password and code under the same lockout rules as the login form ([Recent sign-in](Recent-Auth.md)).
`/ReAuth/check`, `/ReAuth/password` and `/ReAuth/sendCode` are 401 without a user; the posts need the CSRF token.

`update#Password` is `authenticate="anonymous-all"` and `allow-remote="false"`. `reset#Password` is `authenticate="anonymous-all"` and `allow-remote="true"` (`UserServices.xml`). `create#InitialAdminAccount` is `authenticate="anonymous-all"`. It returns an error when more than one `UserAccount` row exists (the seed row `_NA_` is the one that may already be there), then creates the account and adds it to `ADMIN` with authorization disabled.

### HTML and uploads

A service parameter `allow-html` defaults to none, which rejects text that contains `<`. There is no webapp attribute of that name. `safe` cleans with ammonia and allows the span attributes `data-mention-id`, `data-record-entity`, and `data-record-id`. `any` leaves the markup.

`webapp_upload_executable_allow` is `false`. An upload is refused unless that setting is `true`. The check matches a `#!` shebang and the magics `MZ`, ELF, a Java class file, and four Mach-O values. A ZIP (`PK`) is not treated as a program. `webapp_max_upload` is 2147483648 bytes. A file over 256 KiB is written under `runtime/tmp/upload`.

A body that is not multipart stops at `webapp_max_body`. This repository has no `default-property` of that name (`MoquiDefaultConf.xml` only interpolates `${webapp_max_body}`, and `MoquiDevConf.xml` does not set it). The code fallback is 10 MiB (`crates/moqui-core/src/web/mod.rs`). A runtime override in the environment or in `runtime/.env` was not confirmed.

Screen JSON removes credential fields at any depth, case-insensitive: `password`, `oldPassword`, `newPassword`, `newPasswordVerify`, `currentPassword`, `resetPassword`, `authPassword`, `api_key`, `login_key`, `passwordSalt`, `passwordHashType`, `passwordBase64`, `passwordVerify`.

### Response headers

Screen renders send `Content-Security-Policy: frame-ancestors 'none'; form-action 'self';`, `X-Frame-Options: sameorigin`, `X-XSS-Protection: 1; mode=block`, and `X-Content-Type-Options: nosniff`. `Strict-Transport-Security: max-age=31536000` is on type `screen-secure`. A stricter CSP in the conf comment is commented out. The Assist sandbox frame uses its own policy, under [Assist](#assist).

### CORS

`webapp_handle_cors` is `true`. `webapp_allow_origins` is empty. An origin is its scheme, host, and port, all three. The server's own origin is allowed: https over TLS or from a believed proxy, with the host and port of `Host` or of a believed proxy's forwarded host and port, and the webapp URLs from the conf. A foreign origin is 401 `Origin not allowed`, before the servlet. An `allow-origins` entry that includes a scheme is matched the same way. A bare domain allows that host and the hosts under it on any scheme and port. `*` allows every origin. The dev conf sets `*`.

An `OPTIONS` preflight is 204 with an empty body, before the servlet chain (`crates/moqui-core/src/screen/mod.rs`). Preflight and actual responses send `Access-Control-Allow-Credentials: true`. Preflight also sends the conf allow-headers (including `api_key`, `login_key`, `moquiSessionToken`, `X-CSRF-Token`, `Authorization`, `A2A-Version`, `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`), allow-methods `GET, PUT, POST, PATCH, DELETE, OPTIONS`, and `Access-Control-Max-Age: 3600`.

`/notws`, `/termws`, and the Assist event stream use the same origin list and answer 403 `origin not allowed`.

### Client IP

`webapp_client_ip_header` and `webapp_trusted_proxies` are empty, so `X-Forwarded-For` is not trusted. `ClientAddressing` believes a peer only when a header is configured. If a header is set and the trusted-proxy list is still empty, the first hop is believed from any peer, and `X-Forwarded-Proto` uses that same gate. The comment above the property still names Jetty's `ForwardedRequestCustomizer`. The listener uses `ClientAddressing`.

On an edge node (`node_role=edge`) and an all-in-one node (`node_role=all-in-one`) a header with an empty trusted-proxy list is ignored, with an error at startup: the edge node faces the internet and passes the client address to its local nodes ([Edge node](../Run-Deploy.md#a-local-server-with-an-edge-node)).

`/health` and `/metrics` use the TCP peer, not this header. `/status` uses `ec.user.getClientIp()`, which can differ.

### Field encryption

`entity_ds_crypt_pass` ships as `MoquiDefaultPassword:CHANGEME` with `is-secret="true"`. It is the `entity-facade` `crypt-pass`. The same secret encrypts an OAuth refresh token and a client secret stored on `EmailOAuthProvider`, the SSO client secrets (`OauthFlow.secret`, `OidcFlow.secret`), the SAML keystore and private key passwords, and a calendar publish link's token (`CalendarShare.publishToken`, still found by value since the encryption is deterministic). What this encryption protects, and its known gaps, are in [Threat model: stored secrets](#threat-model-stored-secrets).

`entity_ds_user` and `entity_ds_password` default to `sa` and `sa`. Those are the old datasource properties. The embedded Postgres client does not connect with them.

## HTTP container

The listener is hyper and axum. `webapp_http_bind` empty binds every address. `webapp_http_port` empty is port 8080. The plain HTTP listener is HTTP/1.1. The HTTPS listener offers `h2` and `http/1.1` by ALPN (`webapp_http2=false` offers only `http/1.1`). An HTTP/2 connection takes at most `http2-max-streams` (100) open streams, a request head of at most `max-header-bytes`, h2's bounds on streams a client resets before they are taken (20) and on streams reset for its protocol errors (1,024), PINGs every 30 seconds, and is closed with a GOAWAY after `header-timeout` with no request, or when web protection refuses its client with a closing refusal (HTTP/1.1's `Connection: close`). An HTTP/2 request is given `Host` from `:authority`; a WebSocket over extended CONNECT is checked by web protection as the GET of an HTTP/1.1 upgrade. Over HTTP/2 a `content-type: application/grpc` call goes to the gRPC services that are on (OTLP ingest, PASS authority; the rows below) before web protection's per-request rules and the router, as on their own port, except a call for an edge node's terminate host, which is forwarded as any request. There is no separate servlet descriptor: filters and servlets are the webroot `<webapp>` children in `MoquiDefaultConf.xml`, run by the screen chain. The session is the database row above.

`webapp_https_enabled` is `false`. `webapp_https_listen_port` empty is 8443 when the listener is used. The value `off` starts none. With no usable certificate in `runtime/cert` the listener does not bind, whether or not the port was set, until a name is set up with ACME ([ACME](#acme)), a certificate is added, or while a set-up check runs; it then answers only the challenges of names set up and refuses every other handshake until a certificate is there. An edge node that started so takes no links (`edge_link` is not given the listener's certificates) until it restarts with one. `instance_purpose=dev` tries to generate a development certificate first. `webapp_https_port` is the port clients see in generated URLs, which can differ behind a proxy.

### ACME

Certificates from an ACME authority, only for a name an administrator sets up on System › Certificates (`moqui.server.AcmeName`, `org.moqui.admin.CertificateServices`, `crates/moqui-host/src/acme/`, [plan](../../plans/Edge-Node2.md) §4.8). Nothing is requested for any other name, and nothing a client sends starts an order.

- **The challenge** (TLS-ALPN-01, RFC 8737) is answered on the HTTPS listener: a ClientHello that offers ALPN `acme-tls/1` gets a self-signed certificate carrying the SHA-256 of the order's key authorization, only when its server name has a challenge open (`moqui.server.AcmeChallenge`, at most ten minutes, closed when the order ends), and is refused otherwise; it is never served HTTP. The open challenges are read from their rows again when the last read is a second old, and at most once a second per process, so `acme-tls/1` handshakes cost at most that; an order waits past that second before the authority looks, so every member answers the challenge as it is now. On an edge node the passthrough check comes first, so a local node's passthrough name's challenge goes down its tunnel and the local node answers it; the edge node answers only for names it ends TLS for itself.
- **The set-up check** opens a challenge of its own with a random digest, for at most a minute and closed when the check ends, and connects to the name on 443 as the authority would, taking any certificate (it checks no signature, only that its digest is in the certificate), for at most 20 seconds. It reaches whatever address the name's DNS has; an administrator chooses the name. On a node with no certificate the listener binds for the check and closes after it.
- **Calls to the authority** have a time limit (a minute for the account and the order, three for the validation and the certificate), well under the 15-minute order lock.
- **The account key** is a P-256 key derived from `acme_account_key`, a secret generated into `runtime/.env` ([Secrets](#secrets)). Cluster members share it in their shared `.env`, or each is a separate account. Whoever has it can act as the account at the authority: revoke its certificates, and order for a name whose challenge they can answer.
- **The certificate's key** is new for each order. It is kept in `moqui.server.AcmeCertificate` (`privateKeyPem` encrypted at rest) so every member of a cluster writes it, and in `runtime/cert/<name>/privkey.pem` (mode `0600`). A `runtime/cert/<name>/` directory without the `.moqui-acme` marker is another tool's and is never written over or removed.
- **The authority** is reached over HTTPS checked by the operating system's trust store (`instant-acme` on hyper-rustls), or by the one root `acme_directory_ca` names for a company's own authority; the directory URL is the administrator's choice (`acme_directory_url` by default).

The request deadline is `request-timeout`, code default 300 seconds, and the answer is 504. Exempt paths are `/notws`, `/termws`, paths starting with `/git/` (and git at a page's URL on a public-site host, which is served as its `/git/` request: [Git hosting](../interfaces/Git-Hosting.md#repository-paths)), `/ci/runner/`, `/dav/`, and `/llm/v1`, and multipart uploads. A screen response past the `screen-facade` `stream-threshold` (64 KiB) is sent as it renders ([Screen output](../ui/Screen-Output.md)): the deadline covers it up to its head, and after that it holds its request worker and its transaction while the client reads. A client that takes nothing for `write-timeout` ends the render, so one that stops reading holds a worker for at most that long.

Default Cargo features are `maximal` and `devtools` (`crates/moqui-host/Cargo.toml`). `maximal` includes `enterprise`, which includes `git`, `llm`, `tui`, and `ssh`. `lite` includes `llm` and `tui`. `git` and `ssh` are on the `dev`, `enterprise`, and `maximal` sets. A default `cargo build` therefore compiles `/git`, `/termws`, and the LLM routes. `inbound-smtp` is on Enterprise and Maximal. `embedded-postgres` is on Dev, Lite, and Maximal. Enterprise leaves that feature out and uses an external database.

`<terminal max-sessions="16" max-sessions-per-user="4"/>` limits terminal sessions. The browser socket is `/termws`. The screen is `/qapps/Terminal`, which requires authentication. SSH is a separate listener, under [SSH and the TUI](#ssh-and-the-tui).

HTTP request spans are recorded by the factory-scoped telemetry middleware.

A `<public-site>` may name a `host-check-service`, called with the site, host and path for a request to a framework route (the `FRAMEWORK_ROUTES` of `screen/public_site.rs`: `/apps`, `/qapps`, `/rest`, `/Login`, `/sso`, the token routes, the servlets, `/status`...) on its host. When it answers `restricted` true the route is 404 there, before any servlet, token route, screen or `before-request` action runs, so nobody signs in to the framework or reaches its apps on that host (a site's theme preview host, Commerce F87; mr-pass points it at Mantle's `get#PreviewHost`). A path another servlet takes (`/fop`, `/search`, `/dashboard`, an app's own) is refused the same way, and the refusal makes no session. The static routes a page there loads (`/js`, `/css`, `/libs`, `/images`, `/static`, `/assets`) are not checked while the screen path stays under them: `/libs/../apps` is the apps, and is checked. A check that fails refuses the route and is logged. The host routes above (`/health`, `/metrics`, `/notws`, `/termws` and the others) are answered before this check: the probes keep their IP list, and the sockets need a session cookie, which a host where nobody can sign in never issues.

Root screens by host name ([Run-Deploy](../Run-Deploy.md#several-sites-by-host-name), plans/Edge-Node2.md §4.2): a `root-screen` whose host pattern matches the `Host` header (its port left off, lower case) gives that host its own root screen; any other host gets the `.*` root, `webroot.xml`. A host is not trusted by being sent: an unknown one is the default root's. With `framework-routes="refuse"` the host serves its root's screens and the shared static files only: the token routes and the servlets are 404 there before they run, as on a public site's restricted host but with no service call, and so are the host routes above (`/health`, `/metrics`, the sockets, `/dav`, the LLM and channel routes), by a layer on them, and the gRPC services of the HTTPS listener (the OTLP receiver, the PASS authority), whose calls go to the router instead. Git at a public site's page URL is the one host route left to such a host, when it is also a `public-site` host: only a request marked where it was rewritten to `/git/`, never a request to `/git/` itself. The gRPC listener on its own port (`grpc-port`, `pass_authority_grpc_port`) is not by host and is not affected. A `root-screen` conf that cannot be read (an invalid host pattern) refuses the framework's routes on every host. With `include` the host gets `webroot.xml`'s screens and routes beside its own. A link made in a request (`ec.web.getWebappRootUrl`) uses the request's host only when the whole `Host` header is a plain host name (letters, digits, `-` and `.`) with at most a numeric port, a `root-screen` pattern other than `.*` names it and that root does not refuse the framework's routes; the one normalized value is checked and written, with the conf's scheme and port. Else the conf's `webapp_http_host`, as always outside a request. A public site whose root is also its host's root screen is still routed and bound by its `public-site`, and a request that no public-site route takes has no bound site: a `resolvedSiteId` parameter it sends is dropped.

There is no axum route for `/groovysh`, `/rpc`, `/elastic`, `/kibana`, `/htmlr`, `/vapps`, or `/h2`. `/fop`, `/search`, and `/dashboard` are servlet patterns on the fallback. `/status` is a screen transition. The conf has no `/groovysh` endpoint, and the obsolete Groovy Shell screen has been removed. The browser's Terminal UI runs the applications; the privileged SSH admin shell provides the JavaScript executor ([SSH and the TUI](#ssh-and-the-tui)).

## Screen tree

The root screen `component://webroot/screen/webroot.xml` sets `require-authentication="false"` so subscreens decide. The default subscreen item is `qapps`. There is no `vapps` item. Schema documents are the REST transitions, which require a user and `REST_SCHEMA`.

Because the root screen does not require a user, static files served as that screen's content are reachable without a login. The shell references `/js` and `/libs`, and the root names `/favicon.ico`. A full listing of those files was not made.

`qapps` is `require-authentication="false"` with extra path allowed, and its pre-actions redirect to `/Login` when there is no `userId`. The Assist drawer flag is `ec.llm.isEnabled()` and `hasPermission('AgentUse')`. `terminalUrl` is `/qapps/Terminal` only when `webapp_terminal_endpoint` is set.

Screens another app shows ([Admin-Screens-Down](../../plans/archive/Admin-Screens-Down.md)). System's administration areas (Access, Security, Settings, Operations, Data, Audit, Integrations, Mail and protocols) and the Dashboards screens are also shown by another app under its own root: by location, in a wrapper, or inside a screen of the app's own ([Mounting the administration screens](../../runtime/components/base/tools/README.md#mounting-the-administration-screens), [Mounting the report screens](../tools/Monitoring.md#mounting-the-report-screens)). The rules a request meets there:

- Mount context is data. The mounting root sets `adminMount`, or `reportLinks` and `reportPolicy`, in its `always-actions`, and `System.xml`, `Dashboards.xml` and `System/Monitor.xml` set them to null, so a request parameter of those names is never read as one under either root. A value that is not a map is a mount with nothing in it: no route, no link, no feature and nothing of the instance administrator's. The map says where links go and carries the app's policy values; it opens no screen and authorizes no call.
- The instance administrator's parts (a job's, a group's, a remote's, a message type's or a message's record changed directly, a group of any id and type, the stored translation rows, artifact authorization, the whole audit log, the visits by user) are shown only with no mount, and only to a user whose own authorization records open System: `ec.artifactExecution.isPermittedOwn` (`moqui_core::user::permitted_own`) reads the user's own records and nothing from the stack, counts no hit and records no failure. The stack's question would not do: an app's inheritable always-allow on its area answers it for every user below it, and skips the transition, service and entity checks there as well. Every transition of such a part carries that question (`raw()` of `tools/template/AdminMount.js`) as its `condition`, so a post of one under a mount is refused, for a delegate and for `ADMIN` alike. A screen with such a transition is never mounted by location: an app's wrapper takes in transitions by name, and one that is not taken in does not exist on the app's route. `tools/test/AdminMounts.spec.js` fails on a transition of the areas that acts and neither calls only `org.moqui.admin` services nor carries `raw()`.
- No group of an app is granted a tools location: a grant there would open the screen under `/apps/system` or `/apps/dashboards` too.
- A policy value is enforced by the transition that reads the map, never a parameter, or by the service called. Setting an alert rule and sharing are refused first where the policy's feature is off (`ReportAlerts.requireSet`, `ReportShare.requireShare`), and making a playlist where the mount gives no editor (`createPlaylist` refuses when `reportLinks.definition` is null): the cases the engine cannot hold alone, since a holder of `save#Definition` need not be an author of the app. The people and groups a schedule or an alert rule names are asked of `find#ReportRecipients` under the policy's permission before the save. The email template, the alert topic and link and the recipient cap are written from the policy into every save, and the engine holds the cap under the instance ceiling. The wall display's `data` takes no range from the request. What a screen offers gives no right: the service asked decides.
- The report engine's own rules hold for a direct call too ([Business datasets](../tools/Monitoring.md#business-datasets), [Sharing](../tools/Monitoring.md#sharing), [Report delivery](../tools/Monitoring.md#report-delivery)). `create#BusinessDataset` asks the update artifact of the dataset named (`org.moqui.report.dataset.<id>`) beside the dataset-save artifact, so an id prefix a screen adds gives no right. `save#Definition`, and with it a copy, a restore, an import and a pull, takes a group only from a saver who belongs to it by a membership of their own (never `ALL_USERS`) or whose own grant holds `org.moqui.report.share.<userGroupId>` (update), and refuses any other (`SHARE_GROUP_UNAVAILABLE`); a group kept as stored is not asked again. `find#ShareGroups` names only such groups. `find#ReportRecipients` answers an account or a group only to a holder of the group delivery artifact, and accepts the caller always. `find#ScreenSchedules` and `store#ScreenSchedule` reach only the caller's own screen schedules. `get#BusinessDataset` answers a dataset the caller does not read as it answers one that does not exist.

The Tools database sections ([Database](../tools/Database.md), `crates/moqui-tools/`) add these rules:

- **Audit entities.** `DatabaseAudit`, `SqlRunToken`, `DatabaseConnection` and the `moqui.etl` mapping, value map and
  run entities are read and written only by their own services. The generic tools, entity REST and Service REST,
  request loads, ETL targets and every entity-auto service refuse them (`AUDIT_ENTITY_KEYS` and `run_entity`'s check,
  `crates/moqui-entity/src/entity/sensitive.rs`, `crates/moqui-core/src/service/call.rs`). An ETL `expression` runs as
  the mapping's user, so a generic write to a mapping would plant a script.
- **Views by origin.** `sensitive::is_restricted_entity_or_view` treats a view as restricted when any member is
  (`UserAccountAndGroup`, `UserGroupMemberUser`). `sensitive::secret_fields` follows each view alias to its member
  field, so an alias that renames a `UserAccount` password field is a secret too. The grid, ETL sources and lookups,
  entity REST finds and results, Service REST entity results and the JS `isRestrictedGenericEntity` use both.
- **No dummy parents in restricted entities.** A load with dummy foreign keys fails rather than create one.
- **External databases** keep the password encrypted, never return it, and clear it when the host, port, user, type or
  TLS settings change. An empty `sslMode` is `verify-full` for a host that is not loopback.

### Load runs

Tools › Load runs a load script on threads of the server (`crates/moqui-host/src/load_runner`, plans/archive/LoadRunner.md
§10; the guide is [Load-Runner](../tools/Load-Runner.md)):

- **Targets.** A run reaches this server (its own https URL, and its http URL only on a loopback host), loopback, and
  the URL prefixes of the `load_runner_targets` property; a dev instance reaches any URL. Plain `http` to another
  machine is refused unless `load_runner_targets` names it, since a login crosses in the clear; a prefix carries its
  scheme, and is matched on the path a request is sent to after `..` and `.` segments are resolved (`targets.rs`).
  `insecure` (an invalid certificate accepted) is a run setting shown on the run.
- **SSH.** A script whose plan uses `ssh` connects (`ssh.connect`, `test_client/ssh.rs`) only to this server's own SSH
  listener, loopback, and the `ssh://host:port` entries of `load_runner_targets`; a dev instance to any host. A host
  key not pinned by the script is taken only from loopback, or from any host when the run is `insecure`. It logs in
  with the account and password or key the script gives, so it can do over SSH only what that account may.
- **In-process service calls.** A script whose plan uses `service` calls this server's services through
  `service.call` as the user who started the run, with authorization required and the tarpit off for the run's
  contexts; a service that user is not authorized for is counted as an error and not run (D10; Java ran them as
  anonymous with authorization off). A load script's `service.call` goes straight to the service facade, so a
  service's `allow-remote="false"` does not refuse it: allow-remote is about calls from outside the server (REST,
  JSON-RPC), and this call runs in process as the user who started the run, with authorization required, the way the
  user's own screens call services. A script's user threads have no `ec` and none of the server's own functions.
- **Secrets and files.** A `secret` param is held in memory for the run, never in the result, the snapshot or a log
  line, and is asked again on Run again. The terminal form names its field `password_<name>`, so a refused form's
  parameters, which the session keeps for the form shown again, leave it out. Run again of an imported run fills only
  the target kind, not the file's URL, params or settings. A run is read, deleted and imported only by its `runId`, a directory name
  under `runtime/tmp/test-load/`; an import is checked to be a result (16 MiB at most) before it is kept.
- **Limits.** One running load per instance (`load_runner_max_runs`) and 1,000 users a run (`load_runner_max_users`).
- **Demo.** The demo lock-down replaces `Tools/Load` with its Disabled screen.

### Component deploy and conf reload

System › Components and System › Conf ([Component-Deploy](../tools/Component-Deploy.md)), with the services in `org.moqui.dev.ComponentServices` (`crates/moqui-devkit/src/deploy/`). Each is `allow-remote="false"`, under the `SYSTEM_APP` screen authorization, and each checks the `ADMIN` group itself.

- **What a load can do.** Loading a component, from a component directory or from git, runs its code on the server: its services, ECA rules, screens, REST APIs, templates and scripts are loaded, its data is loaded with authorization off, its tables are made, and its `MoquiConf.xml` is merged into the running conf. Treat a load as a code deploy. A component with Rust code (a `Cargo.toml`, or `.rs` files in `src/`) is refused: native code loads only at a start, when the binary links it.
- **Deploy from git** (`preview#ComponentDeploy`, `deploy#Component`, `update#Component`) also needs the sealed `COMPONENT_DEPLOY` permission. On a production instance it needs `component_deploy_enabled=true` too, and without that it is refused with a vague error.
- **URLs.** The URL must be `https` or `ssh` (also `user@host:path`), never `file://` or a local path. On a production instance a host that resolves to a loopback, private or link-local address is refused.
- **Fetching.** The database and bare storages fetch in-process (`moqui-git`). A working clone runs the system `git` command, with no prompt and the access token sent as an HTTP header rather than kept in the clone's conf. Both paths are refused in sim mode and by the `RemoteCall` fence. Credentials are stored encrypted (`GitRepository.accessToken`, or the `DeployedComponent` row for a clone).
- **Files written.** Fetched files go to a dot-prefixed staging directory that discovery skips, then into `runtime/components/addon/<name>` or the clone's component directory. Remove moves the directory to `.removed/` beside it; a working clone with changes asks again first.
- **Restart.** "Deploy and restart", "Update and restart" and System › Conf's Restart Now go through `restart#Server`: a dev instance only, `DEV_AIDE` or `ADMIN`, and a server that can restart itself.
- **Conf edit** (System › Conf › Edit: `get#ConfFile`, `check#ConfFile`, `save#ConfFile`) needs the sealed `CONF_EDIT` permission as well as `ADMIN`, since the conf names the code the server runs. A file is named only by its place in the merge, never by a path, and the default conf is never written. A save checks the file's hash from when it was read, writes the file whole and logs the user on `moqui.monitor.audit`. The merged-conf view (`get#ConfView`, `ADMIN`) masks secret values.
- **Conf reload** (`reload#Conf`, System › Conf, the dev file watcher, and `SIGHUP` when stdin is not a terminal) applies only the units the catalog marks live or apply. Ports, datasources, keys, `instance_purpose` and the other restart-class units wait for a restart. A property that the environment set is not overridden.
- **Cluster.** Only the database storage is fanned out, on the `component-deploy` topic (see Cluster below), and each member writes the tree from the shared database repository. The other storages, and a load from a local directory, are refused while the server has live cluster members.
- **Audit.** Each load, deploy, update and remove writes a `DeployedComponentHistory` row and a WARN on `moqui.monitor.audit`, as does a data load again (its history row only for a component a load recorded) and each conf reload request.

mr-boss also adds per-client rate limits: `request-form` on `POST /r/*/submit`, 5 requests in 60 seconds, burst 5; and
`invitation-accept` on `POST /i/*/*` (an invitation's account and factor steps), 10 requests in 60 seconds, burst 5.
They apply when per-client web protection is on.

A route's token is its credential, so it is kept out of what the server records. The request log (each request's SERVER
span) has `/i/:token/...` for `url.path`, and for a path or URL under a token route in the `Referer` header and in a
query value such as a sign-in step's `returnTo` (`screen::token_route::redact_url`). The log lines that name a request
path (a refused origin, the public-site host check) are redacted the same way, and so are a Visit's `initialRequest`
and `initialReferrer`. Browser telemetry (`/rum/traces`, `/rum/logs`, `/rum/replay`) has every string redacted before
it is stored, a replay's `url` and the links its rrweb snapshot holds included (`token_route::redact_json`). The routes
are read per conf generation, so a route a conf reload adds is redacted from then on. The route name and the rest of
the path stay (`/u/:token/oneClick`). `http.route` is the screen's location, which holds no token. The session keeps a
sign-in step's `returnTo` with its token (it is where the user goes next); a session is not a record.

While a token route's screen renders it is the root of its links (`web::set_link_prefix`): a form's action, a link and a
transition's redirect to a screen go to `/<name>/<token>/...`, not to `/<transition>` outside the route. A plain URL
(`/Login`) is not prefixed, and no request parameter or header sets the prefix: only the token route's dispatch does,
after its token check. A server-static qvt template is cached for every visitor, so it is made with no prefix
(`screen::statics::serve_template`) and its paths, an alias transition's target included, are still from the screen; a
token route's screen that needs links under the route should not be server-static. A `screen-last` path the session
saves (the page before a login) is from the screen as well.

`/call/<token>` is a call link's guest page. Its token is 32 random characters; only its hash is stored. The token is
refused once the link is revoked or expired. The page's transitions are `joinGuest`, `guestState` and `leaveGuest`,
without the session token. `joinGuest` takes a name of up to 60 characters and gives a 40-character credential that
lasts 4 hours (hash kept). basic-comms rate-limits it per client (`call-guest`: 10 a minute, burst 5).

- A guest's credential reaches only that call's signaling, on `GET /callws`. It is never in a URL.
- `guestState` shows a waiting guest nothing but their admission. Once admitted, a guest sees the names of those in the
  call. They never see the room, its members or its history.
- A guest leg can negotiate media only once admitted (`bind#GuestConnection`).
- Revoking the link, or removing or denying the guest, ends the credential and closes the guest's legs.
- A link made end-to-end encrypted (W8) takes no guest (`encryptedNoGuests`): a guest has no crypto device. The page says
  so from the token's route context (`encrypted`).

Call captions (W6, [WebRTC](../interfaces/WebRTC.md#captions)) send call audio out to a speech provider, so they are off
unless `call_captions_enabled` is `true`. `start#Captions` and `stop#Captions` (the Calls screen's `startCaptions`,
`stopCaptions`) need a signed-in user with an answered leg in the call; anyone else gets `notFound`. An end-to-end
encrypted call is refused. Every leg, a late joiner's and a guest's too, gets the notice naming the provider before its
audio is captioned. The provider is the `transcribe` model binding, reached through `moqui-llm`'s address guard (a
private address needs `allow-private-network`), counted against the quota of the user who turned captions on, and kept
as an `LlmCall`. `org.moqui.call.SpeechServices.transcribe#Audio` and `get#SpeechProvider` are `allow-remote="false"`:
`transcribe#Audio` reads any `audioLocation` it is given, so its caller decides what may be sent out. Captions are not
stored unless `call_captions_store` is `true`.

## LLM, A2A, MCP, Assist, git, and DAV

Routes exist when the `llm` feature is compiled. While a protocol is off, its handlers answer 404. `llm-facade` `enabled` is `true`. That element is the model facade. It is not the A2A server, the MCP server, or the gateway. Assist answers 503 when the facade is disabled; `bootstrap` still answers (`docs/ai/Assist.md`).

A user with `EXTERNAL_USER` never holds `A2aServerUse` or `AgentUse`. The Assist contract says that permission also blocks the other agent permissions, so that user starts no run and gets no model call.

### A2A

Off. `a2a_enabled` is `false`, and `trust-forwarded-headers` is `false`. While it is off, `/a2a` and `GET /.well-known/agent-card.json` answer 404.

From `docs/ai/A2A.md`: a caller needs `A2aServerUse` and `AgentUse`. Credentials are a Bearer login key, an `api_key` or `login_key` header, or Basic with an app password or a login key as the password. The account password is refused (401). Credentials are taken only over TLS, a believed proxy's https, or loopback. Missing credentials are 401 `WWW-Authenticate: Bearer realm="a2a", Basic realm="a2a"`. No permission is 403. The body max is 4 MiB. Waits and streams are at most 256 on a node (503) and 16 per user (429). Every request except the public card needs `A2A-Version: 1.0`. OIDC is not built. An agent is reached only when `exposeA2a="Y"` and the surface includes `a2a`. The seed `assist` agent does not. Writes wait for the human owner.

### MCP

Off. `mcp_enabled` is `false`, and `trust-forwarded-headers` is `false`. While it is off, `/mcp` and its documents answer 404.

From `docs/ai/MCP.md`: a caller needs `McpServerUse` and `AgentUse`. Credential shapes match A2A, with realm `mcp`. No credentials is 401 JSON-RPC `-31401`. No permission is 403 `-31403`. `server/discover` needs no credentials. The body max is 4 MiB. The transport is `POST /mcp` only; GET and DELETE are 405. The seed agent `mcp` serves `mcp` with `exposeMcp="Y"`. The MCP client cannot approve a write. Public when on, and cached for an hour: `GET /mcp/server-card`, `/mcp/setup`, `/.well-known/mcp.json`, `/.well-known/ai-catalog.json`.

### Gateway

Off. `llm_gateway_enabled` is `false`. The live element is `<gateway enabled="${llm_gateway_enabled}" require-client="true" timeout="300"/>`. An `enabled="true"` example above it in the conf is inside a comment.

From `docs/ai/Gateway.md`: Bearer login key or app password, or Basic with those. The account password is refused. TLS, a believed proxy's https, or loopback. Missing or bad credentials are 401 `invalid_api_key`. The caller needs `LlmGatewayUse` and an `LlmApiClient` row. An app password always needs a client. A login key needs one because `require-client` defaults to true. The body max is 16 MiB. The path is exempt from the webapp request deadline. The gateway `timeout` of 300 seconds answers 504. ### Git

`ANY /git/{*rest}` when `git` is compiled; on a `<public-site>` host, git's smart HTTP and LFS requests at a page's URL (`/<path>/info/refs?service=...`, `/<path>/git-upload-pack`, `/<path>/git-receive-pack`, `/<path>.git/info/lfs/...`, the first segment not a framework route) are served as the same request under `/git/`. Web protection checks such a request by the path it came with (client rules, methods, path rules, rate limits) and its path rules again by the `/git/...` path it is served at, so `<path-rule action="deny" path="/git/**"/>` stops git at page URLs too; a rate limit whose path is only `/git/**` does not count them, which is why `git-anonymous` names the page forms. `git-server` defaults: `allow-http="false"`, `max-concurrent="4"`, `max-queued="16"`, `max-request="67108864"`, `max-push-size="2147483648"`, `max-object-size="536870912"`, `idle-timeout="120"`, `lfs-max-object-size="5368709120"`, `webhook-private-network="false"`. The route is exempt from the webapp request timeout.

From `docs/interfaces/Git-Hosting.md`: HTTP Basic with the username and the password, or an access token or an app password as the password. An account with a second factor needs the token or the app password. The account password cannot finish that login. `Authorization: Bearer` and the `api_key` header also work. A request with no credentials is checked as no user: it reads (clone, fetch, LFS download) only a repository an `ALL_USERS` authorization record lets anyone view, which the framework's own data never does (Mantle's check does, for a public repository), and is 401 for everything else: a repository that is not there, a path that is not one, a push (refused before any record is asked), an LFS upload or verify, and every LFS locks request. The 401 is the same, status, headers and body, whatever the reason. It is not an `auth-failure` event; a header that is there and is not usable credentials (another `Authorization` scheme, Basic that does not decode, an empty `api_key`, a bad LFS token) is one, and is 401 on a public repository too, so a made-up header does not pass the `git-anonymous` limit for free. Requests with no credentials run at most `git-server` `anonymous-max-concurrent` git jobs at once (half of `max-concurrent`, at least 1); one more is 503 with `Retry-After`. Credentials are accepted only over HTTPS (the TLS listener, or `X-Forwarded-Proto: https` from a believed proxy), from loopback, or when `allow-http="true"`.

Authorization is artifact type `AT_GIT_REPOSITORY`, name `repositoryId`; a URL names a repository by its id (one segment, exact), its `repositoryPath` (segments of letters, digits, `.`, `_`, `-`, none starting with `.` or `-`; unique and looked up without case, by `repositoryPathKey`), or a path it had before a rename, until another repository takes that path. A path of one segment is only ever a repository's own id, so no path shadows an id. The framework has no namespace ownership: `set#GitRepositoryPath` needs the update right on the repository and nothing more, and the application decides who may rename and when a left path may be retaken. The server refuses to serve when that type's authorization is not enabled. VIEW is clone and fetch. CREATE is a new branch or tag. UPDATE is a fast-forward. DELETE is a force-push, a deleted ref, or settings. No view is 404 with credentials (401 without). View without push pushes only `refs/for/<branch>` (below), each other ref refused; it is 403 for the whole push with `review-push="false"`, and for a drive's viewer. Only `refs/heads/`, `refs/tags/` and `refs/for/` can be pushed. The default branch cannot be deleted. Seed `GitRepositories` is always-all for `ADMIN`. A `remote` repository is a read-only mirror. LFS is under `/git/<path>.git/info/lfs`; with `git-server` `lfs-upload-check-service` set, that service is asked before objects new to a repository are accepted (an application's quota) by the batch, by each upload and by a write of an LFS-tracked file through Moqui, and its errors refuse with 403; it is asked again once an object is stored, and a refusal then takes the object back, so uploads that run at once do not pass a limit together. Webhooks are not sent to loopback, private, or link-local addresses unless `webhook-private-network="true"`.

The services an application's code pages call check the same type: `get#GitBlame` and `get#GitArchive` need view, read trees and history that whoever may push made, and are refused past their `git-server` limits. Blame: `blame-max-bytes` (1 MiB), `blame-max-lines` (50,000), `blame-max-commits` (10,000), `blame-max-diffs` (2,000 comparisons, each parent of a merge one) and `blame-max-seconds` (10, which cuts each comparison off). Archive: `archive-max-bytes` (256 MiB of content), `archive-max-files` (50,000 entries, every tree read counted, so a tree naming one subtree many times ends), 64 directories deep with no recursion, `archive-max-concurrent` (2 at once on a node) and `archive-max-disk-bytes` (2 GiB kept). An archive is one file for each (repository, commit, path, format) under `runtime/tmp/git-archive`, written under another name and renamed, shared by the callers that ask for it, kept six hours from its last use. A pushed tree's names are not trusted: an entry named `.`, `..`, `.git` (any case), empty, with `/`, `\` or NUL, or not UTF-8, and a name twice in one directory, refuses the archive; a link is stored as a link entry and never followed, and one whose target is absolute or climbs out of the archive is left out. Neither service is capped by client: a page that offers them to visitors rate limits its route. `get#GitRepositoryUsage` needs view, leaves out what the caller may not view, and is for an application's quota code (it reads object rows or walks a directory per repository). `delete#GitRepository` needs delete, the right that also forces a push, so an application wraps it in its own rule; with authorization off it deletes for any caller. It marks the repository as going in a committed step that every push and write reads again before storing, deletes the rows in its transaction, and after the commit removes the directory and deletes the id's rows once more. The directory goes only when, with links followed, it is under the runtime directory, is a bare repository (`HEAD` and `objects/`) and is no other repository's directory, parent or child. It cannot be undone. `find#UserSshKeys` and `find#UserAccessTokens` answer the current user's rows only, with no public key, token or stored hash.

Push to review, forks and reads by id (`docs/interfaces/Git-Hosting.md`): with `git-server` `review-push` (default `true`) an account that may only view a repository pushes `refs/for/<branch>`, which stores its commits in that repository and opens or updates its own merge request; it writes no ref a reader reads but the merge request's head (`refs/merge-requests/<n>/head`), uploads no LFS object, and is capped by `review-max-push-bytes` (50 MiB a push; no more than that is read from such an account's connection) and `review-max-account-bytes` (200 MiB an account a day over all repositories, from `GitUpdate.packBytes`). A pre-receive gitECA rule sees `forReview`, the target branch, the user and `packBytes`, and is where an application puts its own gate (a confirmed address, a daily count); `commit#GitFiles` with `asProposal` is the same by a service, under the same caps and the same pre-receive rules. With authorization disabled only: `fileLocationMap` (reads a resource location as the server), `authorName` and `authorEmail`, `bypassBranchRules`, `propose#MergeRequest`, `sync#MergeRequestHead`, and the `mergeRequestNum`, `pushedForReview`, `headCommitId`, `reviewTopic` and `hidden` of `create#MergeRequest`, the `localPath` of `fork#GitRepository`. A fork (`fork#GitRepository`, view of the source) shares its network's objects: one set of `GitObject` rows for a `db` network, the parent's directory through `objects/info/alternates` for a `local` one. Because a store then holds what its repository's readers may not read (another fork's commits, a merge request held for moderation, hidden by `set#MergeRequestHidden` or from the start with `review-start-hidden`), no read goes by what the store has. A commit is read by id through the `get#Git*` services, wanted by id in a fetch, restored or checked out by id, only when a branch, a tag or the head of a merge request that is not hidden reaches it; the start of an id is looked up among those commits alone. The one exception is a repository in no fork network, none of whose merge requests is or ever was hidden (`GitRepository.reviewHiddenDate`, kept from the first one on), on a server without `review-start-hidden`: there a user with the update right (or a service with authorization disabled) also reads the commits its refs have left. The row is read when asked, so a first fork or a first hidden merge request made on another node counts at once. A push is checked for everything it names and does not bring: a ref's new value, a parent (also one a client declares shallow, which must be there), a tag's target must be such a commit, or a tag object a readable tag names; a tree, a blob (also as a ref's new value, for an account with a push right) and the base of a thin pack's delta must be a file of a commit the pusher reads (for an account with no push right: of the branch the review is for, of its own review heads, or of a commit the push builds on). An id that is not in the store and one that is another's are refused alike (the same words, report and push log row, before the ref's name and the account's rights are looked at), and a fetch acknowledges a `have` only for a commit the readable refs reach, so neither tells which ids a store holds. For an account with no push right the server's work is bounded: `review-max-commands` (8) commands, shallow lines and options in `review-max-request-bytes` (64 KiB), `review-max-built-on` (8) commits built on, `review-max-trees` (20,000) trees read, and `review-max-refused` (30) refused pushes for review or proposals an hour per node before the next are refused unread (`GitReviewRefusals`); an account that may push sends at most `push-max-commands` (100,000) commands in `push-max-request-bytes` (16 MiB). `commit#GitFiles` builds its objects in memory and stores them only once the change may be made, so a refused proposal stores nothing. The heads are not advertised and a hidden one is not fetched. `find#GitUpdates` gives an account without the update right no remote address, no object id that no ref reaches, no rule error, no text of a refusal, and no count of the log. A hidden merge request is changed and reviewed (`update#`, `close#`, `reopen#MergeRequest`, `set#MergeRequestReviewers`, `submit#MergeRequestReview`, `get#MergeRequestApprovals`) by its author or with authorization disabled only, and a repository's webhooks are sent nothing of it until it is shown (then `opened`). `get#GitCommitStatuses` and `create#GitCommitStatus` (the two git services under `/rest`) answer for a commit only when the caller reads it by id; `includeHidden` is honoured with authorization disabled only. The reached commits are a set in memory per repository and node (`reach-max-commits`, 1,000,000; at most 128 repositories, least recently used first out), read from the refs again at most every two seconds for a hit and always for a miss. A merge request from a fork needs the update right on the fork, follows its branch only while its author has that right, and is detached by the fork's owner (`detach#MergeRequestSource`) or by the fork's deletion; the LFS objects it brings pass the target's upload check. `create#GitCommitStatus` refuses the contexts under `reserved-status-contexts` (none by default; a hosting application sets `agreement/,ci/`) unless called with authorization disabled. `merge#MergeRequest` needs the update right and merges exactly the commit whose approvals and checks it counted, by its id (not a branch or tag of that name; `expectedHeadCommitId` refuses a head the caller did not see), and deletes a fork's source branch only for a caller with the delete right on the fork (or `forceDeleteSourceBranch` with authorization disabled). The gitECA pre events run, with the new commits, their authors and the calling user, for every way a branch moves (a push, a merge, `commit#GitFiles`, `create#GitRef`, a `git://` write, an import, a mirror's fetch), so an application's rule on them cannot be passed by choosing another way in; a rule names `source="push,fetch,import,write"` to hold for all. `queue#GitWebhookEvent` and `queue#MergeRequestEvent`, whose events are signed with the webhooks' secrets, need the update right on the repository or authorization disabled. A repository with forks is not deleted. The head ref of a merge request closed unmerged is deleted after `review-ref-retention-days` (30). `get#GitCommitRefs` reads at most `contains-max-commits` (200,000) commits a call, and `get#GitCommitPushers` at most 500 ids by key, of commits the caller reads.

SSH git is a channel on the SSH server, not this route. See [SSH and the TUI](#ssh-and-the-tui).

### Pipelines

From `docs/interfaces/Pipelines.md`. The CI engine never runs a step on the server: a job is a container the server starts on another machine through an `InstanceHost` (the Docker Engine API over a Unix socket, HTTP, or HTTPS with a client certificate whose key is an encrypted field), or a registered runner's. What it adds to the surface:

- **The pipeline file** (`ci.xml`) is read from a pushed commit, by whoever may push or open a merge request. The reader is strict and bounded (`git-ci` `max-file-bytes`, `max-pipelines`, `max-jobs`, `max-matrix`, `max-steps`, `max-timeout-minutes`); names are letters, digits, dot, dash and underscore; paths cannot leave the checkout. Nothing of the file is run or expanded on the server: a step's command, an image name and a cache key are text handed to the runner. The image must match a pattern of the pool's `allowedImages` (none by default).
- **The runner REST**, `ANY /ci/runner/{*rest}` when `git` is compiled. No session, cookie or user credential: a bearer token, taken only where git takes credentials (HTTPS, a believed proxy's, loopback, or `git-server` `allow-http`). A **job token** (32 random bytes, stored as its SHA-256, good while its job run is `running` and until the job's time limit, cleared when the job ends) reaches only `jobs/<its job run>/...`: the job, log lines, step results, uploads, cache downloads and the result. The job run in the path must be the token's (403), and a job that ended is 401, counted as an authentication failure for web protection. A **pool token** only registers a runner and a **runner token** only asks for a job of its pool. Requests are counted per job and per runner (`runner-max-requests-per-minute`); a JSON body is at most `max-log-batch-bytes`; an upload streams to a content blob and is cut at its kind's limit (`max-artifact-bytes`, `max-report-bytes`, `max-cache-bytes`), at most `max-artifacts` of a job. Exempt from the request deadline, as git is. A host whose root screen refuses the framework's routes answers 404 here too.
- **A job token on the git server** reads its job's repository at its job's commit and nothing else: upload-pack only, one advertised ref at that commit, every `want` that commit, a shallow fetch of at most `max-fetch-depth`. The repository is the run's (the target of a fork's merge request, never the fork), and the commit must still be the repository's to give: one the head ref of the run's merge request reaches (`refs/merge-requests/<n>/head`; a hidden merge request's head is fetched by its job's token and by nothing else), or for another run one a ref the repository's readers read reaches. A commit its ref has left (a forced branch, an amended push for review, a released head) is refused in a fork network and in a repository that has had a hidden merge request (elsewhere every commit of the store was once a reader's), and the only `have` acknowledged is that commit, so the token is no way to read, or to probe for, what else a fork network's store or a store with a hidden merge request holds. It logs no user in, so it reaches no service, screen or other route, and it cannot push. A step runs as the runner's user and could read the token from the runner's process: it gives the step nothing the job did not have.
- **What queues a run.** The framework's post-receive gitECA rule (a branch or a tag moved by a push or a write; a push to `refs/for/<branch>` and a merge request's head ref queue no push pipeline) and its service ECA rule on `queue#MergeRequestEvent`, which does not run after a refused event (a caller without the update right). `queue#PushRuns` and `queue#MergeRequestRuns` are refused without authorization disabled, so no caller names the user or the commit of a run. The file is read at the event's commit as the system reads, a hidden merge request's head too; in a fork network, and in a repository that has had a hidden merge request, a commit no ref of the repository reaches any more has no pipeline, so a run (or a re-run of an old one) is no way to read it.
- **Hidden runs.** The run of a hidden merge request's head is hidden (`GitPipelineRun.hidden`): its log, artifacts and reports, which are that head's files, are read by the user who pushed it and with authorization disabled and `includeHidden`, not by a user with the update right, who therefore does not approve it either (the application does). `set#MergeRequestHidden` hides and shows a merge request's runs with it.
- **Untrusted code.** A run for a merge request from a fork, one pushed for review or one detached from its source, whoever opened it, or caused by an account without the update right, is untrusted: no secrets, caches read and never written (so it cannot poison a later trusted run), only a pool marked for untrusted runs (a trusted run never shares its hosts), and it waits for `approve#PipelineRun` unless the application's `run-check-service` allows it. That service may lower a run's trust and never raise it. A re-run of an untrusted run stays untrusted whoever asks for it.
- **Secrets** (`GitCiSecret.secretValue`, encrypted) are given only to a job of a trusted run whose scope is met (a protected branch or tag, or the job's environment), only over the runner REST and never in a container's definition, and are masked in the log as it is stored. No service reads a value back. A step that has a secret can still send it elsewhere: the protection is that only reviewed files run with one.
- **The container** has no privilege, no capabilities, `no-new-privileges`, no host path or socket, no published port, a non-root user, a read-only root, and the pool's CPU, memory, pid and disk limits and network mode. What it may reach on the network is the host's to limit (`egressRule` names a network; the engine makes no rules): it must reach the server's URL, and should reach nothing else of the server's network. The server holds the host's API credentials, which are root on that host: a compromised server owns its runner hosts, not the other way round, as long as runners are other machines.
- **Statuses** `ci/<pipeline>/<job>` are written by the engine through `create#GitCommitStatus`, with authorization disabled and `includeHidden` (so a service ECA rule on it runs for them, and a hidden head has its checks); their description is plain text, with `<` and `>` left out of what a pipeline file's error, a runner or the application's check said. A user with a push right can still post a status of any context unless the application reserves `ci/` (`git-server` `reserved-status-contexts`), which a branch rule that requires a `ci/` check needs.
- **Delete.** `delete#GitRepository` removes the engine's rows of the repository with it (runs, jobs, logs, uploads, secrets, environments, schedules) and stops its running jobs, so no job token or secret outlives its repository; a fork's runs are its own.
- **Services** (`org.moqui.git.GitCiServices`): reads follow view of the repository, and a hidden merge request's run only with authorization disabled; cancel, retry, run and approve need update; a repository's secrets and environments need update; an owner's, and `includeHidden`, need authorization disabled. The runner pool services have no repository to check: they are an operator's, behind the caller's own service authorization.

### DAV

The routes are always registered. There is no `<dav-server>` element in `MoquiDefaultConf.xml`. The defaults are the Rust fallbacks, and `docs/interfaces/Sync.md` states the same numbers.

| Flag | Default | Effect |
| --- | --- | --- |
| `enabled` | true | `false` is 404 `the DAV server is off` |
| `allow-http` | false | otherwise credentials need a secure request: HTTPS, a believed proxy's https, or loopback |
| `account-password` | false | app password only. `true` also accepts the account password |
| `max-file` | 268435456 (256 MiB) | 413 over that body |
| `sftp-drives` | true | SFTP to drives for a user without `SSH_SFTP` |

OPTIONS is answered with no login: `DAV: 1, 2, 3, calendar-access, addressbook, extended-mkcol`, and `Allow` lists `OPTIONS, GET, HEAD, PUT, DELETE, PROPFIND, PROPPATCH, MKCOL, COPY, MOVE, LOCK, UNLOCK, REPORT`.

Every other method is HTTP Basic. No credentials is 401 `WWW-Authenticate: Basic realm="Moqui", charset="UTF-8"`. Plain HTTP while `allow-http` is false is 403 `credentials over plain HTTP are refused; use HTTPS`. A path whose user segment is not the signed-in username (case-insensitive) is 404. Writes go through the file and adapter services as that user. `docs/interfaces/Sync.md` paths: `/dav/`, `/dav/principals/<user>/`, `/dav/files/<user>/<drive>/<path>`, `/dav/calendars/...`, `/dav/addressbooks/...`. The framework keeps no calendar or contact of its own. An application serves them through adapter services, and Mantle sets those adapters.

Projected address books (Mantle's `ContactProjection`, IronStone Sales' My accounts) are read-only collections
`projected-<id>` computed per request by their owner service as the signed-in user: the collection is listed only when the
owner admits the user, its cards are the parties the owner answers for that user (Sales: the contacts of the accounts the
user manages or has deals with, in their Sales scope), and `PUT` and `DELETE` on them answer 403. No `ContactBook` row is
copied.

`login_user` does not call `finish_login` when a second factor is required. DAV requires that login to succeed and requires a non-empty current user id. The wrapper that maps a second-factor result onto the current user was not read.

## Non-HTTP listeners

`/metrics` is on the public HTTP listener. It is not its own port. `port_check` probes HTTP, HTTPS, cluster, and SSH before the database opens. It does not probe SMTP.

### Mail

There is no open SMTP receiver by default. `smtp_listen_port` empty does not start one. The host default is `127.0.0.1`. There is no default port (the doc example is 2525). Only internet mode (`smtp_internet=true`, or `internet="true"` on the `smtp-server`, which MoquiEdgeConf.xml sets) takes mail from anyone, on port 25 of an edge node; see [Edge node](#edge-node) below. `inbound-smtp` is an Enterprise and Maximal feature. Dev and Lite omit it. If the port is set on a build without the feature, startup logs an error and does not listen.

The listener is the last hop behind an operator-run gateway (`docs/interfaces/Mail-Inbound.md`). There is no SMTP `AUTH` and no client certificate. The allow-list is the gateway. A peer outside `smtp_allowed_addresses` gets `554` at connect and the connection closes. An empty allow-list refuses to start the listener. `proxy-protocol`, `starttls`, and `require-tls` default to false. STARTTLS with no certificate does not start the listener. `dsn` defaults to false. The message cap is 25 MiB (`max-message-size` 26214400), 100 recipients, 20 connections. In internet mode no allow-list is needed: STARTTLS is on by default, each address is limited (`max-connections-per-ip` 5, `connections-per-minute` 30; IPv6 by its /64), and SPF, DKIM, DMARC and ARC are checked after the data within 45 seconds, with the listener's own `Authentication-Results` written and any claiming its authserv-id removed; a DMARC reject policy is refused (550). Rspamd's verdict, when `mail_rspamd_url` is set, fails open ([Mail-Inbound](../interfaces/Mail-Inbound.md)).

A permitted gateway can `RCPT TO` a hosted (`EakHosted`) or shared (`EakShared`) address that has no incoming IMAP or POP server. Other recipients are `550`. After `DATA`, the message is stored in that account's Inbox, or Junk when a configured spam header starts with yes or true. That store runs with authorization disabled, including the app `EmailMessage` ECA when Mantle is loaded. There is no relaying. `VRFY` answers `252`. Empty `smtp_authserv_id` keeps every `Authentication-Results` header, including a forged one, and warns at startup. Out of internet mode the listener does not check SPF, DKIM, or DMARC; the gateway does.

An application's mail rule actions run on stored mail with authorization disabled, so mail from anyone reaches them. IronStone
Sales' lead intake address (`createLead`, Mantle `create#LeadFromEmail`; the request for quote address `createQuoteRequest`
follows in Sales P8) takes the team from the rule's value or the plus tag of a `To` or `Cc` address (`sales+leads@`), only a team
of an organization the rule's owner works for; the message makes a `SalesLeadIntake` row and a lead in that team's queue,
never a party, the sender's name and address held on the intake until the lead is qualified and blanked after the retention
days if it never is (`purge#LeadIntakes`); its `Message-ID` is the intake's identity, so the same mail again makes no second
lead. The mail text decides only the lead's name and description.

`poll#EmailServer` (job `poll_EmailServer_frequent`) is paused. If unpaused, the cron is every 15 minutes, `emailServerId=SYSTEM`, `authenticate="anonymous-all"`. It connects out to the configured IMAP or POP server. `sync#DueEmailAccounts` (job `sync_EmailAccounts_frequent`) is running, every minute, `authenticate="anonymous-all"`, `allow-remote="false"`. IMAP IDLE is on by default (`idle-enabled="true"`, `idle-max` 8) and dials the account's server. It does not listen. Both jobs use the scheduler's authorization-off path.

OAuth mail sign-in is not a listen port. It stays off until the operator sets a Google or Microsoft client id and secret. The browser session, PKCE, and server-side state (10 minutes, single use) protect the callback `/emailOAuth/callback`. The redirect URI is the deployment's and is never taken from the request. A server with no field encryption refuses to store the refresh token. The ID token signature is not checked. The callback transition's body was not fully read.

### SSH and the TUI

The SSH server is one `TcpListener`. SFTP, git, the admin shell, `apps`, `agent-apps`, and the SSH cluster channel are channels on it. `moqui tui` with no `--serve` and no `--server` opens no port (`docs/ui/TUI.md`).

Off in the default conf: `ssh_port` empty, `ssh_host` `127.0.0.1`. `0` binds an ephemeral port. `./moq run` merges the dev conf, which sets `ssh_port` to `2222`, still on loopback unless `ssh_host` changes. `MoquiProductionConf.xml` does not set `ssh_port`. The `ssh` feature is in Dev, Enterprise, and Maximal. Lite leaves it out. `moqui tui --serve` starts this listener together with HTTP and the cluster listener.

Password login uses `login_user` (lockout counts, `ipAllowed` of the account and its groups). An account that needs a second factor is refused at the SSH password step. An app password is tried first when the secret has that shape. A public key must match an active `UserSshKey` by SHA-256 fingerprint, then `internal_login_user` with no password. Keyboard-interactive (`login-dialog` default true, and only if `tui` is built) asks no questions: the session has no user until the apps login dialog, the same username, password, and second factor as `moqui tui`. That dialog checks `ipAllowed` and closes after 2 minutes without a login or 5 refused logins. Pre-auth timeout is 30 seconds, and at most 16 connections have not logged in. The host key is `ssh_host_key`, generated into `runtime/.env`.

`SSH_SHELL` is seeded on `ADMIN_ADV` and is sealed, so the ordinary permission UI cannot grant it. A login with `SSH_SHELL` gets the admin shell (`help`, `status`, `service`, `entity` up to 100 rows, `cache clear`, `js` with `ec`, `apps`; on a dev instance `sh`, `profiles`, `sessions` and `attach`, [Terminal](../ui/Terminal.md)). Those commands run as that user. `service`, `entity`, and `js` also need Tools-app artifact authorization. Without `SSH_SHELL`, or after a dialog login, the session is only `apps`. `agent-apps` needs a key or password login and no pty. It drives the same client with that user's credentials. A dialog login gets no shell commands, no `agent-apps`, no SFTP, and no git. Git over SSH needs `SSH_GIT` (seeded on `ADMIN`) and a key, unless `git-password-auth` (default false). With `ssh-server` `git-any-account="true"` (default false) any account that logs in by key gets the git commands (`git-upload-pack`, `git-receive-pack`, `git-lfs-authenticate`) without `SSH_GIT`, so on a site with public registration every account that adds a `UserSshKey` reaches the git server over SSH; each repository's `AT_GIT_REPOSITORY` check still decides, a repository it may not view is "not found", and a password login is never let in by it. It opens no shell and no SFTP root; SFTP to the drives an account may open is `dav-server` `sftp-drives`, as before. One user logged in by key or password holds at most `max-sessions-per-user` (4) of the sessions and one address (an IPv6 /64) `max-sessions-per-source` (8), so one account or host cannot hold all of `max-sessions`; a cluster peer is counted by neither, and 0 is no share. At most `max-sessions` 8 SSH connections, 4 of one user (`max-sessions-per-user`) and 8 from one address (`max-sessions-per-source`). Terminal sessions also count against the terminal limits. Idle time is 10 minutes.

**The browser terminal's command line and host sessions** ([Terminal](../ui/Terminal.md#who-may-open-what-and-from-where), plans/Terminal-Fancy.md §8). On a dev instance only (`instance_purpose` dev; `terminal` `command-line` and `host-sessions` are `dev` by default) and only in a build with the dev tools (Maximal, Debug; not Lite or Enterprise), a user with `SSH_SHELL` gets the same `moqui>` prompt in the browser, and a user with `TERMINAL_HOST` (sealed, on `ADMIN_ADV`) programs on the server's operating system on a pty: a shell as the server's OS user, with its files, keys, processes, the runtime's `.env` and the database's files. With the dev AIDE (its D15) these are the exceptions to "no code from outside runs on the server", with its limits: dev only, a permission, an audit. From the server's own machine (a loopback peer, no forwarding header, the server's own loopback origin; or the Desktop app's node in process) nothing more is asked. From anywhere else (a LAN, a VPN, the edge node, a tunnel or a proxy on the machine) they need `terminal` `remote="true"` (off by default; `terminal_remote`), a secure request and a sign-in within `remote-reauth-minutes` (60), asked when a session is opened and again when a socket attaches to one; a device key's requests keep no session, so its user confirms the password (and code) in one request for a short ticket (`confirm#TerminalUser`). They take only the server's own origin, whatever `allow-origins` says (a device key's socket, which sends none, excepted). Everything else is one vague `notAvailable`. Each one is a `moqui.terminal.TerminalSession` audit row (who, what program, where from, edge or not, when, how it ended; never what is typed or shown), kept 90 days. The program's environment is the server's less every variable that names a conf property, and holds no credential of the Moqui user. `sh` at the SSH prompt takes the same permission and purpose, and the rule above by the peer's address; `attach <id>` at the SSH prompt takes one of the user's own sessions only (another user's id is no such session) and, for a command line or a host session, the attach-time checks above by the peer's address. Host sessions are held by `moqui term-hold`, a process of the server's OS user that outlives the server, on a Unix socket in `runtime/tmp/term-hold` (`0700` directory, `0600` socket) that trusts its owner only. A dev instance with remote on logs a WARN at start. An administrator (the System app's update) may end any user's session, which is an audit row (`EntityAuditLog`, `endedBy`).

The SSH cluster channel is not a separate port. It is used when a peer's base URL is `ssh://`. The default transport is HTTPS, so the channel is off unless a member advertises SSH, and the SSH server must be listening. The login user is `moqui-cluster` with an Ed25519 key derived from `cluster_tls_key`. Any other key for that user is rejected. The channel carries the same cluster topics. It is not a shell.

### SFTP

SFTP is the SSH `sftp` subsystem. Nothing listens for it unless the SSH server is up. `docs/interfaces/Sync.md` "SFTP to the drives" is this subsystem. The outbound SFTP client dials other hosts.

`sftp-drives` defaults to true. `sftp-root` defaults to `runtime://sftp`. `sftp-max-file` defaults to 256 MiB. The user must already be logged in by key, password, or app password. A dialog login is refused. `SSH_SFTP` (seeded on `ADMIN`) selects the root: one resource location (`runtime://`, `file:`, `component://`, or `dbresource://`), paths normalized against `/`, and `..` that leaves the root is refused. Those calls run with authorization off. The permission checked at login is the gate. A user without `SSH_SFTP` gets the drives that user may open, when `sftp-drives` is true. `sftp-drives="false"` gives that user no SFTP. A write is an upload and a new version. A removal goes to the trash. At most 64 handles per channel.

### Cluster

The cluster listener is separate from the public HTTP and HTTPS listeners. Public routes do not ask for a client certificate.

On whenever the process starts listeners (a normal `moqui` with no command, and `moqui tui --serve`). Empty `cluster_https_port` is **8444**. Empty `cluster_bind_address` is **0.0.0.0**. `0` is ephemeral. Commands that do not serve do not start it. The default is 8444 (`crates/moqui-host/src/cluster_edge/mod.rs`).

A TLS client certificate is mandatory. The verifier accepts only a certificate whose SHA-256 matches this member's `cluster_tls_cert`. The server presents that same certificate. The handshake must finish within 10 seconds. There is no HTTP login and no public app routing. ALPN picks the protocol: `h2` (offered unless `cluster_protocol=rest`) serves only the gRPC `moqui.cluster.v1.Cluster.Post`, a batch of the same messages with a status for each, decoded up to 17 MiB, at most 64 streams per connection, with HTTP/2 PINGs and a connection idle for 60 seconds closed; `http/1.1`, or no ALPN, serves only `POST /cluster/{topic}` for one of the bus topics (`moqui_core::notify::TOPICS`): `entity-cache-invalidate`, `notification-message`, `collab-update`, `session-end`, `rtc-signal`, `runtime-settings` or `component-deploy`. The body must be JSON with `origin_id` and `message_id`, or the answer is 400. An unknown topic or method is 404. The serialized JSON envelope limit is 16 MiB on HTTPS, SSH and Postgres NOTIFY (including payloads kept in `ClusterMessage`). Oversized messages are refused before fan-out. A 4xx response refuses that message without retrying or marking the peer down. At most 64 connections. Cache clears that entity's one-cache. `session-end` drops this process's live copies of the named session ids. Notification and collab messages are published on the local bus and are not fanned out again. `rtc-signal` is sent to one member (`cluster::send_to`, one try from a queue of 1,024 that refuses when full): a call's signaling frames for the node holding its media, its replies for the node holding a leg's socket, the call services' close messages, and the voice services' SIP control (kind `sip`, for the node's SIP engine); a receiver drops one whose `target` is not its instance id (the notify transport reaches every notify member).

Postgres `LISTEN moqui_cluster` is off unless `cluster_transport=notify`. It needs a Postgres entity database. MySQL refuses startup. It is one connection outside the pool, not a new TCP port. The payload is not authenticated on its own. A payload over 7,900 bytes is a `ClusterMessage` row id. A notification missed while `LISTEN` is down is lost. Reconnect then clears entity caches. The default `cluster_transport` is empty, which means the cluster port at `cluster_base_url` (gRPC, or the HTTP/1.1 POST).

### Edge node

Off unless `node_role` is `edge` or `all-in-one` and the HTTPS listener runs, and only in a binary with the `edge` feature (Maximal, Enterprise). It is not a port of its own: the edge link shares the public HTTPS listener and tells its connections apart by the ClientHello, which the listener reads before it picks TLS settings (`crates/moqui-host/src/edge_link/`, [plan](../../plans/archive/Edge-Node.md) §5.1, §5.3, §5.8). A local node opens no port; it dials out.

- **`moqui-edge/1`** (the up and down connections): the edge node presents a certificate from its own link key (`edge_link_key`) and asks for a client certificate without requiring it. After the handshake the key's SHA-256 must match an active `moqui.edge.EdgeClient`; a role byte follows, and a down connection must name the live link generation. The handshake to the role byte has 10 s. On up the local node calls the edge node's `Link` gRPC service; on down the edge node calls the local node, which serves only the link's own gRPC and the PASS authority's (on `/moqui.edge.v1.LocalLink/` and `/moqui.pass.v1.PassAuthority/`, with no client named), forwarded requests and tunnels. A revoked key, a stale generation and a version more than one apart are refused.
- **`moqui-edge-pair/1`** (checking and pairing): the web certificate, which the local node checks by WebPKI. A check connection (no client certificate) can only Probe; a pairing connection presents the new key and can Pair with a one-use code (kept as a hash, an hour by default, at most a day). Each connection stays at most 30 s, with at most 4 calls and 2 streams; Pair is limited to 10 tries per address in 10 minutes. A code does not take over a node that is active with another key.
- **Any other ALPN** gets the web certificate and is never asked for a client certificate.
- **Terminate hosts** (`moqui.edge.EdgeHost`, mode `EdgeHostTerminate`): a request whose `Host` is one goes down its node's link after the edge node's own web protection; only configured names go, and only to their own node. The edge node removes hop-by-hop headers and every forwarding header a client sent (`Forwarded`, `X-Forwarded-*`, `X-Real-IP`, its client-IP header, `x-moqui-edge-*`), then names the client in `x-moqui-edge-client`. The local node believes that header only on the down connection, removes it and the forwarding headers, and runs its own web protection on that client. A client's `CONNECT` is answered 405; only a WebSocket, an HTTP/1.1 upgrade or an HTTP/2 extended CONNECT with `:protocol` `websocket`, becomes an extended CONNECT down the link, and the edge node answers the browser 101 or 200 as its protocol has it. While the link is down the edge node answers 503 with an offline page. The edge node sees the content of these requests.
- **Passthrough hosts** (mode `EdgeHostPassthrough`): a ClientHello whose server name is one goes down the link unopened, with a PROXY v2 header naming the client; the local node ends TLS with its own certificate, so the edge node sees no content. A ClientHello is at most 64 KiB. While the link is down the connection is closed. A local node reads a PROXY header only on a tunnel from its link, never on a socket, and its web protection admits that address before the TLS handshake. A tunnel names a kind (`https`, `ssh`); the local node picks its own listener and the edge node never names an address. At most 768 tunnels and forwarded WebSockets at once per node.
- **Delegated calls, queue and replication** (the link's gRPC, [plan](../../plans/archive/Edge-Node.md) §5.2): the edge node calls `LocalLink.Delegate` and `LocalLink.Deliver` on the down connection, and the local node calls `Link.Deliver` and `Link.Replicate` on the up connection; each is fenced by the link generation, and none is reachable by a forwarded request (the down connection takes gRPC only under `/moqui.edge.v1.LocalLink/` and `/moqui.pass.v1.PassAuthority/`, and only with no client named, which a forwarded request always has). Every message is at most 16 MiB both ways (tonic's decode and encode limits on both servers and clients); a queued item's payload is at most 1 MiB, refused at enqueue, and a replication batch at most 500 records and 4 MiB. On the edge node a delegated call is checked first: with the service's definition there, its authorization and `authenticate`; without one, a caller with no user is refused unless the `delegate` entry has `allow-anonymous="true"`. A delegated call runs on the local node only when the service is in the local node's own `<edge><delegate>` list (a compromised edge node could ask for anything), as the user `_EDGE_` (no password, so no login; group `EDGE_DELEGATE`, `UgtRemoteSystems`), with authorization: the `EDGE_DELEGATE` artifact group, which starts with only the diagnostic `echo#Delegate`, must grant it. No parameter the edge node sends changes that user: the local node drops `authUsername`, `authPassword`, `authUserAccount`, `authTenantId`, any other `auth` + capital name, every `_` name, and an `edgeCaller` the edge node wrote, then sets `edgeCaller` from the call's caller data (never a login). A queued item runs its kind's handler from the receiver's own `queue-kind` conf, also as `_EDGE_` with authorization, once per item id (`moqui.edge.EdgeReceipt`, inserted before the handler runs); a node enqueues only the kinds it lists. Replication writes only `moqui.edge.EdgeReplicaValue` and `EdgeReplicaCursor` rows of the sending node on the edge node, with the copied fields encrypted at rest; what a compromised local node sends there is data for its own node only.
- **PASS authority on the link** ([plan](../../plans/archive/Edge-Node.md) §5.5): an edge node's mr-pass (`pass_backend_url=edge:`) calls `moqui.pass.v1.PassAuthority` on the down connection; a forwarded request never reaches it (the same rule as `LocalLink`). With several pairings the call goes to the pairing whose Configure names the call's site (each site has one pairing, the first to name it; one two name is refused), and a site no pairing names goes only to the only active pairing: with more than one paired it is refused, also while one is away, so a pairing's authority never sees the calls of another's sites. The link's mutual TLS is the client's identity, so no secret is sent: the local node names it `pass_edge_client` (default `edge`) and serves only the sites in `pass_client_<id>_sites`, with its SSO callback `pass_client_<id>_callback`. Everything else is the direct listener's (the row in Host routes): routed operations only, schema-checked input, a delegation per call, session handles bound to the client and site, the visitor's address as rate-limit data. A compromised edge node can do what a registered PASS server of those sites can: any routed operation and account action, as an anonymous visitor or with the delegations of the visitors who sign in through it (it is their frontend, so it sees their passwords and second-factor codes too), and it can name any visitor address for the rate limits. It cannot use a delegation or session handle made for another client or site, and it reaches no operation the routes do not list.
- **Port 25** (the MTA in moqui, E5b; `conf/edge/MoquiEdgeConf.xml` turns internet mode on, and `smtp_listen_port` in `.env` starts it): the [Mail](#mail) listener's internet mode. `RCPT TO` is answered from the paired nodes' replicated accounts (`mailRecipients`), never by calling a local node, so an unknown address is refused while a node is away, and a node not yet replicated answers 451. A message is queued for its node, not stored on the edge node beyond the queue's retention. There is no relaying: the edge node sends only what a paired node queued (`mailOut`), DKIM-signed with `mail_dkim_key`, to each recipient domain's MX. A VERP bounce address is taken only for a `mailOut` item the edge node holds the receipt of.
- **LMTP from a gateway beside it** (E5a, instead of port 25): the listener out of internet mode with `protocol="lmtp"` and an allow-list of the gateway's addresses (`127.0.0.1,::1`), as in [Mail](#mail). Mail out is relayed to the gateway on `edge_mail_relay_port`, on loopback.
- **Chat webhooks and media on the edge node** (E6): the [Host routes](#host-routes-and-servlets) rows for `/channels/{chatBridgeId}/webhook` and `/media/{token}`. The webhook's signature is checked with the bridge's replicated public key (never its API key, which stays on the local node), and the raw request goes in the queue, applied on the local node without a second check. The bridge is found by its id within the request's host name: at a pairing's own terminate host (where the edge node answers `/channels/{id}/webhook` and `/media/{token}` itself for the bridges that pairing's Configure routes through it, when it takes webhooks) only that pairing's copy and files, and at the edge node's own names the one pairing that has the id; a bridge two pairings have there, or one with no key, is 401. A media address names a file the local node put there (`moqui.edge.EdgeMedia`, by the token's hash), only for that bridge of an active paired node, until its expiry; a file over `channels_edge_media_max_bytes` (5 MiB) or past `channels_edge_media_node_megabytes` (256) of a node's files is refused.
- **Offer and Configure** (the Edge Node wizard, [plan](../../plans/archive/Edge-Node.md) §5.7): on the up connection, fenced by the link generation like the others, a local node asks `Link.GetOffer` (what the edge node offers it, with its own host names; no secret: the DKIM key's public record, public names and addresses) and sends `Link.Configure`. The edge node checks a Configure as input from any client before it changes anything: at most 64 host names, mail domains, bridges and sites each; domains and ids by their syntax; a mode other than passthrough or terminate refuses the whole request. Host names go through the same code as Edge Clients: only the asking node's names change (a name of the node not listed is removed), a name another node holds is refused without naming that node, and the node comes from the link's key, never the request. A local node cannot claim the edge node's own names, which the host table would otherwise route before the edge node's own handling (its admin UI, PASS sites, webhooks, or a certificate for its name): Configure refuses the edge node's public names and `webapp_http_host`, its `smtp_hostname`, `edge_mail_bounce_domain`, the host of its `channels_public_url`, its `public-site` hosts, and the subdomains of each, and any IP address, `localhost` (and its subdomains) and a name with one label. A name the operator adds on Edge Clients is the operator's choice and is not checked against these. Errors other than a refusal of the input go back as one generic message, with the detail in the edge node's log. The rest is kept on its `EdgeClient` row (refused for a node that is not active) for the operator to see. The Test step's checks on the edge node are limited to 20 a minute per node, as each mail-in check reads the node's replicated recipients.
- **Calls** (E7, [plan](../../plans/archive/Edge-Node.md) §5.4): the edge node's media socket and TURN are the [Call media](#call-media) and [TURN](#turn) listeners, with the same rules (a relay reaches only the media port). Call signaling crosses the link as `Link.Signal` and `LocalLink.Signal` streams, fenced by the link generation like the other calls, on `rtc-signal` only. Each end takes only what the other may send. A local node takes from its edge node only `reply` messages, and delivers one only to a socket of its own that bound that leg of that call with its media on that edge node (the frame's `callSessionId`, its topic `rtc:<call>`, and `to` or `callLegId`); a frame, control, relay or room frame from the edge node is dropped, so a compromised edge node reaches no other socket and no other call. An edge node takes from a local node only `frame` (whose `origin`, where replies go, must be that node), `control` and `sip`; the link stamps each with the sending node (`linkNode`) and refuses one that already has the field, and the rooms of a paired node's calls are keyed by that node and the call (E12), so a node reaches only its own calls' rooms; the media driver checks a frame's leg and generation as a cluster message's. The edge node's instance id, which these checks and the routes trust, is pinned at pairing (`edge_node_id`, beside its key): a link naming another id, this node's own or a live cluster member's is refused, and the link never takes over a `CallMediaNode` row a media node registered. Each pairing has its own TURN secret (E16, [plan](../../plans/Edge-Node2.md) §4.1), derived from the edge node's `turn_auth_secret`, the pairing's id, its key's fingerprint and when it paired, so a node paired again under the same id gets a new secret and the credentials from before are refused (a node id may not hold `@`, the username's separator); it goes to that local node only in the answer to Hello on an up connection whose key it pinned (not in Probe's Hello), and the local node keeps it in memory. Its credentials name the pairing (`<expiry>:<leg>@<pairing>`) and the TURN server checks them with that pairing's secret only while the pairing is active, so revoking a local node ends its TURN access within a second or two, relays included, with no new `turn_auth_secret`; a pairing's secret makes no credential for another pairing or the server's own legs, and a pairing's leg never has an XMPP user's public relaying ([TURN](../interfaces/TURN.md#on-an-edge-node)). One local node has at most `edge_call_legs_per_pairing` (200) legs on the media node at once. Delegated to the local node: `note#MediaEvent`, `get#CaptionSpeaker`, `store#CallTranscript` (only for a leg of the named call) and `transcribe#CaptionAudio` (only for a participant of the call, `userId` required, a chunk at most 4 MiB); queued: `callRecording`, stored only from the queue's own copy of the item's content and only as `_EDGE_`. Run as `_EDGE_`, each refuses a call whose media node is not the local node's edge node (its `CallMediaNode` row `edgeLinked`). A compromised edge node can see and record the media of calls that are not end-to-end encrypted, write captions, media events and recordings of the calls whose media it holds, and spend their participants' transcription quota.
- **SIP** (E8, [plan](../../plans/archive/Edge-Node.md) §5.4 "Voice (SIP)"): the edge node's SIP listeners, RTP range and registrar are the [SIP](#sip) ones, with the same flood caps and failed-digest blocks, on the edge node's own; the calls it routes through the local node get the local node's fraud controls there, and the forwards its fallback makes while the local node is away get only the engine's own checks (the destination's class, the deployment's international and premium switches, the calls at once) and the number's limits at once and a day that its replicated fallback row carries; they start only when `.env` sets `sip_port` or `sip_tls_port`. Its trunks come from the replicated set `voiceTrunks` (their `authJson`, encrypted at rest); no phone's verifier is on it: each digest answer goes to the local node's `check#SipDeviceDigest` (the edge node keeps the nonces and their counts, the local node says whether the response is right for its HA1), so a stolen edge database holds no phone's credentials and outside phones sign in only while the local node is reachable. The local node takes such an answer only for the realm the edge node's registrar challenges with, only while its nonce is at most 330 seconds old by the local clock (the time is inside the nonce, which the phone's response covers, so the edge node cannot change it afterwards), and each (phone, nonce, nonce count) once, so an answer the edge node kept cannot be sent again. Delegated to the local node: the routing, leg and trunk notes, the digest check, bindings and device calls, IVR, queue and transfer services, voicemail's begin, PIN, keys and saved audio, and greeting and prompt audio (`get#CallAudio`, only under the greeting and prompt roots); queued: `voicemail` (edge to local, stored only from the queue's own copy, as `_EDGE_`) and `callAudio` (local to edge, kept only under those roots). Run as `_EDGE_`, `receive#PhoneCall` takes calls only for the edge node's own instance id, the call services only calls whose media is on it, the registrar's binding and call services only its own node and a phone whose fresh answer the local node checked within a minute, and voicemail's keys and saved audio only on a call that gave that box's PIN. A message the edge node queues goes in the box the local node chose for the call, or the called number's own, never one the edge node names. While the local node is away the edge node answers from the replicated `voiceFallbacks` (each number's outside number, which a call may be forwarded to through the engine's own fraud checks, and whether it takes a message). A compromised edge node can answer and record calls to the numbers, take messages for them, forward a number's calls to its replicated outside number, and route calls into the local node as from the trunks. Each delegated call carries how long the edge node waits; the local node starts nothing past it and rolls back a call that ran past it. It cannot sign a phone in or place a call as a user without a fresh answer of that phone, nor read a box's messages without its PIN. With several pairings (E16) each pairing's trunks, calls, legs and phones are keyed by its node: a call goes to the pairing whose copies have the number dialled and a phone to the pairing whose `sip_domain` its realm is, a number or a realm two pairings claim is refused (logged with both), a fallback is read from its owner's copy only, a message is queued to the pairing whose call it was (after a restart too), and each pairing's offer lists only its own trunks.
- **SSH tunnel port**: off unless `edge_ssh_tunnel_port` is set (`edge_ssh_tunnel_host`, empty for every address). The edge node's web protection admits each connection (deny, bans, per-client limit), at most 64 at once; each goes down the link to the local node's SSH server, which serves it in process as a connection from the client's address, with its usual logins and limits. It goes to the one active pairing, counted from the pairings, never from the links up: refused while none or several are paired, while that one is away, or when its local node runs no SSH server, so one pairing away never sends its users' SSH connections (and passwords) to another.
- **Ports of one pairing** (E16, [plan](../../plans/Edge-Node2.md) §4.1, §4.10): each `moqui.edge.EdgePort` row is a TCP port the edge node listens on (on `edge_ssh_tunnel_host` for SSH, `edge_xmpp_host` for XMPP) whose connections go down that one pairing's link as an SSH, STARTTLS or direct TLS XMPP tunnel, admitted by web protection, at most 64 (SSH) or 256 (XMPP) at once each, and counted with the link's other tunnels. `add#EdgePort` (`allow-remote="false"`, System › Edge Clients › Ports) refuses a port of the node's own listeners (set, or unset with that service's usual port; its conf's tunnel ports and the mail relay included), the mail and XMPP federation ports, the SIP RTP and TURN relay ranges, one another row has and a pairing that is not active; a removed row, or one of a revoked pairing (the row stays), closes its port and its connections within seconds. A row names the pairing, never an address, so the edge node is no open proxy.
- **XMPP ports of every domain** (E16): `edge_xmpp_port` and `edge_xmpp_tls_port` take every pairing's XMPP domain. Before a connection goes anywhere the edge node reads its domain: the TLS ClientHello's server name on the direct TLS port, the `to` of the stream header the client sends in the clear on the STARTTLS port (at most 16 KB, within 10 seconds; a start that is neither is dropped). The connection goes down the link of the one pairing whose Configure named that domain, with the bytes read first, and the local node ends the TLS; the edge node reads no stanza and no credential. A domain two pairings name, or a connection naming no pairing's domain (or none) while several are paired, is refused; with one pairing it goes to it, and is refused while it is away, never to another. A client names the domain it wants, so it reaches only that pairing's server, whose TLS and sign-in it must pass.
- **An all-in-one node** (`node_role=all-in-one`, `conf/all-in-one/MoquiAllInOneConf.xml`, [plan](../../plans/archive/Edge-Node.md) §10): a full server with its own users and data that also takes one local node's link, with every rule above. What the paired node's traffic can reach on it:
  - **Delegated calls.** A listed service is sent to the paired node only inside that node's owner scope (`moqui_core::edge::owner::with`, set by the engine that took the item), and to that node; outside it the service runs on the server for the server's own item.
  - **The queue.** A paired node's items run only its kind's handler from the server's own `queue-kind` conf, once per item id, as on an edge node.
  - **Replica rows** are `EdgeReplicaValue` rows of that node, encrypted at rest, read by the engines to route its items. They are never shown to the server's own users: only System › Edge Clients shows them, with the records held back for a claim (`moqui.edge.EdgeReplicaConflict`).
  - **Claims.** The server's own items win: Configure refuses the node's bridges, XMPP and SIP domains, numbers and a mail domain the server holds whole (its bounce domain), naming each, and a replicated record that claims a server's mail address, bridge or number is not applied (kept as a conflict, logged). The server's own setup refuses an item the replica holds (`EdgeClaims.secas.xml`). So a paired node cannot take the server's mail, webhooks, numbers or phones' realm. An address both sides hold gets 451 at `RCPT TO`, and a bridge both hold 409 at its webhook, naming the id; neither side gets it until an operator fixes it.
  - **Calls and SIP.** Each signaling message from the link carries the stamped `linkNode`, and a paired node's rooms, call, leg, trunk and phone ids are keyed by that node (`sip/owners.rs`), so its messages never reach the server's own calls, whose ids come from another database. A phone of the server's `sip_domain` is checked on the server; one of the paired node's domain is delegated to it. The paired node's greetings are kept under `dbresource://moqui/edge-node/<node>/`, apart from the server's.
  - **XMPP.** The server's own XMPP ports read each connection's domain as the tunnel ports do (E16): a paired node's domain goes down its link, any other is the server's own. The tunnel ports, when set, take the server's own domain to its own server too; one equal to one of the server's own XMPP ports is not opened again.
  - **Trust.** The paired node's owner trusts the server's operators as an edge node's: queued mail, messages and recordings are stored on the server until delivered. A compromised paired node can do on the server what it can on an edge node, for its own items only.
- **Several pairings on one edge node** ([plan](../../plans/Edge-Node2.md) §4.1, E16): a dedicated edge node is an all-in-one node with no items of its own, and the pairings are kept apart as the server and its pairing are above. Reasonable isolation for pairings of one organization or related ones, not a defense against a hostile pairing.
  - **Rows.** Every edge row is keyed by its pairing, and each engine takes an item for one pairing: a request by its host name, mail by the recipient's address in that pairing's copies, a webhook by the bridge id within the host name, a PASS call by its site, a delegated call by the owner scope the engine set (outside one, refused while several are paired, linked or not), a queued item by the node it names or the owner scope (else refused, logged). No call made for one pairing reads another's copies.
  - **Claims.** Each host name, mail address, number, XMPP or SIP domain and PASS site has one pairing: the first claim holds. A later Configure is refused the item with only "another node has this name", and a later pairing's replicated record that claims an address or number another pairing holds is not applied, kept as a conflict Edge Clients shows (with the holder), and applied once the first lets it go. An address two pairings' copies still both have (a race, or copies from before) gets 451 at `RCPT TO`. A chat bridge id may be both's: ids come from separate databases, and the host name tells them apart. A mail domain is split between pairings by address, and each pairing's mail out is DKIM-signed only for the domains of its own accounts.
  - **Limits per pairing.** The queue's size cap (`queue-max-megabytes`, or the pairing's `EdgeClient.queueMaxMegabytes`) holds for each pairing alone, so one pairing's backlog fails only its own oldest items; the MX delivery gives each pairing with mail due an even share of its sessions, holding one back for another pairing, and reads each pairing's rows apart; tunnels and streams per link and MMS files per node were already per pairing.
  - **Shared on purpose:** the edge node's addresses and their mail reputation, the DKIM key and selector, the media and TURN ports, web protection's counts, CPU and bandwidth. A pairing that floods mail through the edge node can hurt the others' reputation; there is no operator per pairing.
  - **The screens** (System › Edge Clients: Clients, Domains, Ports, [plan](../../plans/Edge-Node2.md) §4.10): the System app's, so only its administrators (`SYSTEM_APP`, which the screens' service calls inherit); every `org.moqui.edge.EdgeServices` service is `allow-remote="false"`, and a direct call without that inheritance is refused. The menu lists Edge Clients only on a node that takes links (`default-menu-include` reads `node_role`), and the host name, domain, port and queue cap services refuse on any other node. They read and write the rows without the link, so they work while the HTTPS listener is off; a host name change then loads the link's table again. A host name another pairing has is refused with "another node has this name", as in Configure; the operator sees which pairing has it on Domains. What Domains shows of a pairing's setup (its domains, bridges, sites) and its numbers came from that local node and is shown as text, escaped like any other value. A pairing's queue cap is a number of megabytes above 0, or empty for the conf's.
- **The example confs** (`runtime/conf/<topology>/`, E13): they hold no secrets, and each says which go in `.env`.
  `conf/edge/MoquiEdgeConf.xml` and `conf/all-in-one/MoquiAllInOneConf.xml` turn on web protection and the nightly
  backup (`embedded_db_backup_scheduled`), whose archives hold the queued items (mail, messages, recordings) until
  delivered: a mirror off the host should seal them (`mirrorEncrypt`). `conf/pass/MoquiAuthorityConf.xml` exempts the
  PASS servers from web protection by an example private range (`10.0.2.0/24`), to be replaced by theirs.

### Call media

Off unless `rtc_media_port` is set, and only in a binary with the `rtc` feature (Maximal, Enterprise, Debug). One UDP socket on `rtc_media_host` (127.0.0.1 by default); browsers are told `rtc_public_address` (the bound address by default; a wildcard bind without it does not start). It carries ICE (STUN) and DTLS-SRTP for every browser leg (`crates/moqui-rtc`, on str0m, ICE-lite). A datagram goes to the peer whose ICE session (its ufrag and password from the SDP exchange over the authenticated socket) accepts it; anything else is dropped. A peer exists only after its leg's `join` was bound by the call services and reached the media node; leaving, a newer generation of the leg, the call's end (`send#MediaControl`) and ICE consent loss remove it. At most 200 rooms and 50 legs a room on a node; SDP over 64 KiB is refused. Media is hop by hop: the SFU decrypts and re-encrypts each stream, except the frames of an end-to-end encrypted call (below), which it forwards as they come. The node registers itself (`CallMediaNode`) every 20 seconds; a call whose node stops registering ends.

Cascading media nodes (`rtc_cascade_enabled`, off by default) add relay links between the media nodes of a call on the
same UDP sockets: one str0m peer a room on each side, DTLS-SRTP like a browser leg, negotiated only by `rtc-signal`
messages on the cluster's client-certificate HTTPS transport (kind `relay`), so only a cluster member opens one. The
origin takes at most 8 links a room and 64 in all, and refuses more (`tooManyRelays`); a message of an older link is
dropped, a room that ended takes no new link, and a link not connected within 10 seconds is dropped. A leg node forwards
to the origin only its own legs' tracks; the origin decides nothing a leg node asks beyond the layers it sends it. Any
cluster member may open a link for any room id: the cluster's members are trusted alike.

ICE-TCP (`rtc_media_tcp_port`, off unless set) takes TCP connections on the same address: at most 1,000. Each carries
RFC 4571 frames of up to 2,048 bytes into the same SFU, which accepts only what a peer's ICE session takes.

End-to-end encrypted calls (W8, [WebRTC, Encrypted calls](../interfaces/WebRTC.md#encrypted-calls)) open nothing new.
Each browser SFrame-encrypts its frames (RFC 9605, AES-128-GCM on WebCrypto, in an `RTCRtpScriptTransform` worker) with
a key of its own per call and epoch. It sends that key to the other browsers' crypto devices as Olm to-device messages
over the `/ChatKeys` endpoints (C7 core), so the server holds and relays only Olm ciphertext; no chat Megolm session is
used. What the server and the media nodes still see: the RTP headers and header extensions (the audio level for the
active speaker), each frame's size and timing, the first 10 bytes of a VP8 keyframe and the first 3 of other VP8 frames
(kept in the clear so the SFU finds keyframes and sizes; authenticated as SFrame metadata), the SFrame header (the
sender's key index and epoch, the counter), and who is in the call with which device. The roster the browsers send keys
to is the server's (`get#Call`): a server that adds a device of a user in the call gets that leg's keys. A browser takes a
key only from the device the roster names for its leg (the Olm sender, which the server cannot forge), with that leg's key
index in its KID (refused while another leg has that index), and decrypts a track only with the keys of the leg it comes
from, each counter once (a replay window); a frame that does not decrypt is dropped, never played. A sender sends only
with keys it made, so a server-made roster cannot make two senders share a key and its nonces. A call page shows each
device as unverified (emoji and QR verification are in My devices, C7, but the call does not read their trust yet). The mode is set at the start (`requireE2ee`, a room's or a link's policy) and never lowered, and a
leg of such a call binds only with a crypto device of its user (`noCryptoDevice`); recording, captions, phone legs, desk
phones, forwarded numbers, guests and merges are refused. The browser's crypto store is encrypted at rest with a store
key the server gives only to its signed-in user (see Chat keys).

### Call recording

Off unless `call_recording_enabled` is true ([Call recording](../interfaces/Call-Recording.md)). It opens no port. Only a
host of the call starts, pauses, resumes or stops it (`org.moqui.call.CallRecordingServices`). The recorder runs on the
media node, takes frames from a bounded queue and spools under `runtime/tmp/call-recording/`. `store#RecordingFile`
(internal, `allow-remote="false"`) refuses a spool path outside that directory and a location outside
`dbresource://moqui/call/recording/`. The files are read only through `get#RecordingFile` by segment id, from the
BasicComms Calls `Recordings` screen's `recordingFile` transition: the one who recorded it and the call's hosts get the
file, anyone else "not found" (an empty JSON answer) for the same id. No route serves those `dbresource://` locations
to users, and an app's record links (BOSS) go through the same services. The guest page's `ackRecording` and
`withdrawRecording` take the guest's credential and act on its own leg only. Every leg gets the notice, and each is
logged (`CallRecordingConsent`, with every earlier acknowledgement and withdrawal in `CallRecordingConsentHistory`).
The files count toward the owner's personal drive quota: a full drive refuses a start, and a recording that fills it
stops, so recording cannot fill the database past the quota by more than a segment. Retention deletes the files and
rows (`expire_Recordings_hourly`).

### TURN

The embedded TURN server (`crates/moqui-rtc` `turn/`, host `rtc/turn.rs`) runs on the media node. Each listener is off
unless set: `turn_port` (UDP and TCP), `turn_tls_port` (TLS), and 443 on `turn_tls443_host`. TLS uses the
`runtime/cert` certificates. Relays are UDP sockets in `turn_relay_ports`. Its rules:

- **Credentials** are short-lived TURN REST ones: `<expiry>:<legId>`, HMAC-SHA1 with `turn_auth_secret` (generated
  when unset; is-secret). They go only to an admitted leg (`get#IceServers`, `get#GuestIceServers`). An expired one
  is refused, and so is one of a leg that left (revoked by the media node). On an edge node a local node's are
  `<expiry>:<legId>@<pairing>`, signed with that pairing's secret and taken only while it is active (E16).
- **Relay peers** are only the media nodes' media ports (and `turn_allowed_peers`, by address and port). A permission
  to any other address, or a channel to any other address or port, is dropped before the server sees it, and nothing
  is relayed to or from one, another port of a media node's address included. The exception is an XMPP user's own
  credential (`xmpp.<userId>`, from `XmppServices.get#IceServers`, XEP-0215), for calls between XMPP clients: it may
  relay to public unicast addresses too, never to loopback, private (RFC 1918, unique-local), link-local, shared
  (100.64/10), multicast or documentation ranges, nor an IPv6 address that carries an inside IPv4 one (6to4 of one,
  IPv4-compatible, NAT64, Teredo), nor another port of a media node's address or of the TURN listeners' own address
  (a relay there would come from the server itself, past a firewall that keeps the outside off those ports).
- **Limits:** two allocations per credential, `turn_max_allocations` in all, and `turn_max_kbps` each way per
  allocation; excess data is dropped. A stream buffers at most 64 KiB without a whole message. No TCP relays to
  peers are offered.

coturn can take its place ([TURN](../interfaces/TURN.md)), with the same secret and a deny-all, allow-media-node
peer rule.

### SIP

The SIP engine (`crates/moqui-sip` on rsipstack, host `src/sip/`) runs beside a media node, only in a binary with the
`sip` feature (Maximal, Enterprise, Debug). Each listener is off unless set: `sip_port` (UDP and TCP on `sip_host`),
`sip_tls_port` (TLS on `sip_tls_host`, the `runtime/cert` certificates). Each phone leg has a UDP RTP socket in
`sip_rtp_ports` on `sip_rtp_host`. An exposed SIP listener is scanned within hours, so its rules are release gates
([SIP](../interfaces/SIP.md) "Fraud controls"):

- **Who is answered.** An INVITE from a trunk's host (each address of its SRV targets, for a trunk set up by name
  with no port, looked up again at each registration and ping) or listed signaling addresses is a trunk's call; any other
  INVITE or REGISTER is challenged with SIP Digest (SHA-256 and MD5, nonces that expire after 5 minutes and carry
  random bytes and a MAC under a per-process key, nonce counts that must go up). Only a PBX trunk's credentials
  (profile "PBX on a private network") answer it: a provider trunk's are the provider account's password, so a digest
  with them is refused and counted as a failure, and a provider's calls come only from its addresses. A listed address
  range is at most a /8 (IPv4) or a /32 (IPv6); the services refuse a wider one and the engine ignores it. Other requests from addresses that
  are not a trunk's are not answered. Without the registrar, REGISTER is refused (403) without a
  challenge, so it counts no failures. Over UDP a
  source address can be forged, so a trunk taken by its address is best on TLS (the default) or TCP.
- **The registrar (V4).** Off unless `sip_registrar_enabled` is true, even with the listeners on. With it, a REGISTER
  and a phone's INVITE answer the same challenge with a desk or soft phone's credentials: a generated username and a
  22-character random password that is shown to its user once and never stored. Only its digest verifiers are kept
  (`SipDeviceVerifier.ha1`, encrypted, per algorithm and realm): SHA-256, and MD5 only for a device of the legacy
  profile, so an MD5 answer for a standard device fails. A failed or replayed answer counts against its source as any
  failed digest; no device or account is locked. Each REGISTER or signed INVITE looks the username up once
  (`get#SipDeviceAuth`), within the per-source rate. Rotation deletes the old verifiers and revocation the device's,
  and either ends its bindings and its calls on every engine. A binding is the flow the phone opened (its transport
  and source address and port); calls to the phone go back over it only, never to the address its Contact names, and
  a stream connection that closes ends its bindings. A device has at most 10 bindings, and expiry is held to
  `sip_registrar_min_expires`..`sip_registrar_max_expires`. A phone's own call is placed as its user through the same
  checks as the browser's (`place#PhoneCall`: outbound permission, caller ID, international and premium, limits,
  emergency first), so a phone's credentials give no more than its user has. Plain RTP from a phone is taken from its
  SDP's address or the address it signals from (its NAT's), on any port until the first packet latches.
- **Failed digests block the source.** `authFailureLimit` failures in `authFailureWindowSeconds` from one address
  block it for `authBlockSeconds` (5 in 10 minutes, for an hour, by default): its datagrams and stream messages are
  dropped before a transaction is made, nothing is answered, and the block is kept in `VoiceAuthFailure` across
  restarts (the engine counts failures in memory and writes only the block). An IPv6 source counts as its /64. The
  engine tracks at most 50,000 sources; when full, the ones not blocked go first, so rotating addresses does not lift
  the blocks. No account is locked or counted.
- **What an incoming call reaches.** Only a number in `PhoneNumber` rings anyone, through the call services'
  ringing; the SDP must be audio with a codec in common, and SRTP when the trunk's profile requires it (488
  otherwise).
- **Outbound.** Calls go out only from `send#SipControl` (the `rtc-signal` cluster topic, kind `sip`, to that node),
  which only the voice services send, after their checks (caller ID grant, outbound enabled, international and
  premium off by default, concurrency and daily limits, the emergency path). With home country 1, the area codes of
  the plan's other countries (the Caribbean's, Bermuda's) are international. The engine checks the number's class,
  the emergency trunk and the concurrency limit again before an INVITE goes out. A display name or extra header with
  a line break or a quote is cleaned or left out, so it cannot add headers (a `P-Asserted-Identity`) to the INVITE.
- **Forwards to outside numbers (V3).** A call that comes in can make the server dial out: a user's forwarding rules,
  their simultaneous ring to a mobile, and a ring group's fallback number. That is toll fraud's other door (a caller
  rings in to be bridged to a premium or foreign number), so a forward is a phone leg under the same checks as a call
  the user places (`VoiceServices` `forwardCheck` and `dialForward`): the user needs outbound calls and
  `VoiceUserSetting.forwardEnabled` (off by default, set only by a voice admin); international and premium need the
  deployment's and the user's permission; emergency numbers are never a target; the user's limits at once and per day
  count their forwards with the calls they place, and the deployment's calls in a day count every forward; and the
  engine checks the class and its calls at once again before the INVITE. A ring group's fallback number is set by a
  voice admin and checked against the deployment's policy. The caller ID of a forward is the number the call came in
  on, never one the caller supplied. A forward to one of this deployment's numbers is routed inside (no hairpin through
  the trunk), a forward back to the caller's number is skipped, and a call takes at most `call_forward_max_hops`
  forwards, with a user or group already in its plan skipped, so rules cannot loop a call or fan it out without bound.
  Caller lists and rules are the user's own (another user's are "not found"); the rule's target is checked when it is
  saved and again when a call uses it.
- **Transfers and adds to outside numbers (V5).** A user in a call can make the server dial out by transferring the
  call's outside party to a number, or adding a number to the call; a desk phone can ask for a transfer with REFER.
  Each is a call the user places, under the same checks (`CallTransfers.js`, `VoiceServices` `forwardCheck` with
  `transfer` and `dialForward`): outbound calls enabled for the user, international and premium only with the
  deployment's and the user's permission, emergency numbers refused (they are dialed directly), the user's limits at
  once and per day (which count every number they added or transferred to, `CallLeg.dialedByUserId`, so adding numbers
  one by one does not get past them), the deployment's calls in a day, and the engine's own check of the class and its calls at once
  before the INVITE. The limits are counted under one lock (`CallLimitLock`), so calls placed at once cannot pass them
  together. A REFER is taken only from a registered phone's answered leg in a call, as its user; its target is
  a username or a number under those checks, checked before the phone is answered (403 when refused, so it keeps the
  call); an attended REFER (Replaces) is refused. A person called, transferred to or added must pass the apps'
  `call-target` providers (IronStone: someone of the user's organizations), answered as a user that does not exist when
  refused. Only someone in the call (an
  answered leg of theirs) may transfer, add or merge; a call that still rings is not transferred; a stale revision or
  a second open transfer is refused. An external user (`EXTERNAL_USER`) neither transfers nor adds. An end-to-end encrypted call adds no phone legs. An IVR option, a menu's or a
  queue's fallback to a number is set by a voice admin and checked against the deployment's policy when it is saved
  and when a call uses it; a menu loop ends after 20 menus, and a queue's fallback chain after 10.
- **Credentials.** Trunk credentials are `VoiceTrunk.authJson`, encrypted; they answer only the trunk's realm and
  allowed algorithms. TLS to a trunk verifies its certificate against `sip_tls_ca_file` (the system bundle by default),
  for the trunk's host as set up, never an SRV target's name, so a changed SRV record cannot point a trunk at a server
  that does not hold the provider's certificate.
- **Media.** SRTP (AES_CM_128_HMAC_SHA1_80, SDES keys over TLS) unless the trunk's profile is a private-network PBX;
  a packet that fails its tag or replay window is dropped. RTP goes back where the leg's authenticated packets come
  from. Plain RTP is taken only from the SDP's address and, once the first packet latched, only from that source;
  anything else is dropped, so a guessed port neither injects audio nor takes the call's audio. RTCP is dropped.
  rsipstack logs whole SIP messages (SDES keys, digest answers) at INFO, so the host keeps only its warnings.
- **Floods.** rsipstack has no caps of its own, so the engine's transport inspector holds new requests (outside a
  dialog) to `sip_request_rate` a second per source (`sip_request_burst` at once; 20 and 100 by default, an IPv6
  source as its /64), drops them while `sip_max_transactions` (2,000) run, and closes TCP and TLS connections past
  `sip_max_connections` (500), or past `sip_max_connections_per_source` (100) from one source, so one source cannot
  hold the connections the registrar's phones keep open. What is over is dropped unanswered; requests in a dialog and responses pass, so calls
  going on are not cut. Answers sent before an incoming call's decision expire after 30 seconds (1,000 at most).
- **Limits.** A leg's jitter buffer holds 10 packets; a leg's consumer queue a second of frames; datagrams over 2 KiB
  are cut. The engine registers its node (`SipNode`) every 20 seconds.

### XMPP

The XMPP server (`crates/moqui-xmpp`, host `src/xmpp/`, [XMPP](../interfaces/XMPP.md)) runs only in a binary with the
`xmpp` feature (Maximal, Enterprise, Debug) and only when `xmpp_domain` is set. Each listener is off unless set:
`xmpp_port` (STARTTLS, required before anything else) on `xmpp_host`, `xmpp_tls_port` (direct TLS) on
`xmpp_tls_host`, and `/xmpp-websocket` with `xmpp_websocket_enabled`. Local users only: no server-to-server.

- **Sign-in** takes app passwords only, never the account password (which would count toward the account's lockout
  and cannot carry a second factor): SCRAM-SHA-256 and SCRAM-SHA-256-PLUS against the verifiers stored when the
  app password was made (salted, 10,000 iterations), with tls-exporter channel binding where the connection has its
  own TLS session and a downgrade (`y` where the server binds) refused; PLAIN over TLS only; FAST tokens (XEP-0484)
  bound to the client's user-agent id, kept encrypted, expiring (`xmpp_fast_token_days`), and without channel binding
  refused unless their count grows; a token goes with the app password it was issued under. An unknown user gets a salt
  derived from the name and `xmpp_scram_decoy_key` (is-secret, generated when unset), so the exchange does not tell it
  apart, and its salt stays the same across restarts and nodes. A disabled account cannot sign in, and each service
  call logs the user in again by name. A session checks every minute that its app password is not revoked and the
  account may sign in, and ends when not.
- **Failures** are counted per source address (moqui-lib `source_guard.rs`, as the SIP engine counts failed digests):
  5 in 10 minutes block the address for an hour, a /64 for IPv6; the account is never locked. Over WebSocket the
  address is the client a trusted proxy names. At most 20 connections from one address at once and 10,000 in all
  (TCP and WebSocket); a connection not signed in within a minute is closed; a stanza or stream header over 256 KiB,
  or nested over 32 deep, ends the stream; a session whose pushes back up (512) is closed. Stream management keeps at
  most 1,000 unacknowledged stanzas and 10 detached sessions a user; PEP 200 nodes a user and 256 items a node;
  uploads 60 slots a user an hour.
- **Authorization** is the user's: each stanza becomes a service call as the signed-in user, through
  `XmppClientServices` (granted to `ALL_USERS`), and every service checks the room (`get#RoomAccess`) or works on the
  user's own rows. An external user (`EXTERNAL_USER`) learns only the usernames of the people of their own rooms.
- **XML** is parsed by rxml, which refuses DTDs, entity declarations and processing instructions.
- **End-to-end encrypted Moqui rooms** (C7) are not served; OMEMO messages are kept as they came, unreadable to Moqui,
  never in a bridged room, with no text in snippets, search, notifications or agents. PEP items (OMEMO bundles hold
  public keys) are read by access model: `open` any local user, `presence` the people the owner shares a room with,
  `whitelist` the owner.
- **TURN for XMPP calls** (XEP-0215): off unless `xmpp_turn_enabled` is true; while off, external services are not
  advertised and a request gets an empty list. On, a credential keyed to the user (`xmpp.<userId>`) may relay to public
  unicast addresses only, never loopback, private, link-local, shared or documentation ranges ([TURN](#turn)); it is a
  relay to the internet within the TURN quotas, as a public TURN service's is. An external user (`EXTERNAL_USER`) never
  gets one, and a user at most `xmpp_turn_per_hour` (30) an hour (counted on the distributed cache
  `moqui.xmpp.turn.issued`); a refusal is the same empty list.
- **Push** (XEP-0357) registrations are stored, with their app server's secret encrypted; a notification has the message
  count only, and goes nowhere until federation (C3b).

### Voicemail

Voicemail ([Voicemail](../interfaces/Voicemail.md)) opens no port: it runs on the SIP engine above, for calls to a
user's number that nobody answers, and on the access number (`PnrVoicemail`) when an administrator sets one.

- **The PIN over the phone.** A caller who presses `*` in a greeting, or calls the access number, can enter a box
  number and a PIN. `check#VoicemailPin` (internal) checks it against the box's argon2 hash and limits failures per
  box (5 in 15 minutes, then 15 minutes refused from any caller) and per source (the caller's number, 10 in an hour,
  then an hour). The source is a caller ID the caller can fake, so the box's limit is the one that holds: about 240
  guesses a day, which tries every four-digit PIN in six weeks and every six-digit one in eleven years, so a new PIN
  has at least `voicemail_pin_min_digits` (6 by default) digits. A box that does not exist, has no PIN, or is blocked is refused in
  the same words after the same hash work and is counted the same way, so the answers say nothing of which boxes
  exist. Three refusals end the call. The PIN is never logged, and weak ones (one digit repeated, a run) are refused
  when set. Accepted, the caller hears only that box's new messages, and its keys act only on them (`act#PhoneVoicemail`
  checks the box).
- **The audio route.** Messages and greetings are under `dbresource://moqui/call/voicemail/`, which no route serves.
  The audio is read only through `get#VoicemailAudio` and `get#VoicemailGreeting`, from the Calls `Voicemail` and
  Settings `Phone` screens' transitions: the box's owner gets the file, anyone else "not found" (an empty JSON answer),
  the same as for an id that does not exist. The engine writes only through `store#VoicemailFile` (internal), which
  takes a spool path only under `runtime/tmp/voicemail` and a location only under the voicemail root.
- **Uploads.** A greeting upload is at most 10 MB, checked as WAV or Ogg Opus by its first bytes, then decoded and
  re-encoded by the server (`convert#GreetingAudio`, internal, which reads and writes only under the greetings' root);
  a minute is kept.
- **Mail out.** The email notice carries only a link unless the owner turns on the audio or the transcript in it; the
  screen warns that mail cannot be recalled. Transcription sends the audio to the speech provider only when
  `voicemail_transcribe` is on.
- **Limits.** A message is at most `voicemail_max_seconds` (120; at most 600), spooled to disk as it is recorded; one
  under a second is dropped.

### Chat bridges

The bridge layer ([Chat bridges](../interfaces/Chat-Bridges.md), C1) opens no port and routes no endpoint: a network
adapter (C4 on) brings its own transport, and C1 ships none.

- **Input.** `ChatBridgeServices.ingest#Event` is `allow-remote="false"`: only code in the server (an adapter, after its
  own checks of a webhook's signature or a gateway's session) calls it. It authenticates the bridge by its inbound token
  (`check#BridgeToken`: the SHA-256 against `ChatBridge.inboundTokenHash`, in constant time; a bridge with no hash takes
  none) and refuses the whole batch, storing nothing, for an unknown or disabled bridge, a wrong token, a malformed
  transaction id, more than 200 items or 1 MB, or an item that names a local user. An item posts only as an external
  actor (no login, no `UserAccount`) into a room an administrator mapped to that bridge (`noMapping` otherwise), as a
  member a moderator has not taken out, edits and deletes only its own messages, and carries plain text only (escaped to
  HTML; files are refused). A puppet link to a local user is provenance, never authority. Its messages fetch no link
  previews, reach a room's agents only under the room's `agentsReadExternal`, and never start the framework's agents.
- **Output.** A room's messages go only to the networks an administrator mapped it to; a link to an external room grants
  no rights. Delivery rows keep no message text.
- **Administration.** `find#Bridges`, `store#Bridge`, `store#RoomBridge` and `end#RoomBridge` need `ChatBridgeAdmin`.
  `ChatBridge.configJson` is an encrypted field and never returned; the inbound token is kept only as its hash.
  `retry#Delivery`: the message's sender, a moderator of the room, or `ChatBridgeAdmin`; anyone else is told "not found"
  or "not allowed" with the same parameters.
- **Internal services.** `send#Message`, `edit#Message`, `react#Message` and `redact#Message` take `senderActorId` only
  with authorization disabled. `get#LocalActors`, `get#ActorNames`, `get#RoomBridges`, `check#BridgeSupport`,
  `get#BridgeCapabilities`, `wake#BridgeDelivery`, `run#BridgeDeliveries` and the
  `ChatBridgeServices` internals are `allow-remote="false"`.

### Database

`entity_ds_db_conf` default `h2` (and an empty name) selects the embedded Postgres cluster. There is no H2 driver and no H2 TCP server.

Embedded Postgres is on when the entity datasource is embedded and the build has `embedded-postgres` (Dev, Lite, Maximal). The data directory is `runtime/db/embedded`. On Unix there is no TCP: `listen_addresses` is empty, and the socket directory is the data directory. `PORT` 5432 names the socket file `.s.PGSQL.5432`. A second postmaster (search, or the sim overlay) uses the same socket recipe. The client uses the bootstrap superuser, the password in the cluster `pgpass` file, and `NoTls`. This tree does not set `unix_socket_permissions` or `pg_hba.conf`. On Windows the same default listens on `127.0.0.1` and an ephemeral port.

External Postgres or MySQL is off unless `entity_ds_db_conf` is `postgres`, `mysql`, or `mysql8`. This process is a client. Omitted ports default to 5432 and 3306. TLS is on unless `entity_ds_sslmode=disable`.

### Jobs

The scheduler is a thread in this process. `scheduled_job_check_time` is 60 seconds. The first job pass waits 120 seconds, then every 60. `0` starts no job runner. Tick hooks such as the cluster heartbeat still run.

Scheduled cron jobs do not log in a user and do not run with artifact authorization. That is the scheduler's default. `dispatch` leaves `user_name` empty unless the row is an overflow queue (`ASYNC_QUEUE_`). `run_job` calls `internal_login_user` only when that name is set, then calls the service with authorization disabled. `ServiceJobUser` is who gets the completion or error notification. It is not the identity the job runs as. An explicit run-now logs in as the caller, and a queued fire-and-forget call logs in as the original caller, and both still disable authorization for the call. The tx-commit rules the scheduler runs from the outbox (`ServiceOutbox`, written in the committing transaction) log in as the user who made the call and run under the authorization the call had when it registered them, as on the commit hook; no service or screen reads the outbox, whose rows hold the call's parameters and results. One job's error is logged and recorded. It does not stop the scheduler.

Two worker paths turn authorization back on as the user. `run#EtlMapping` calls `etl::access::run_as_user` (`crates/moqui-tools/src/etl/access.rs`): it requires authorization again and pushes the Tools screen, checked for all actions as the user, so the run's writes and service calls run the entity ECAs and the privileged-group and sealed-permission rules. The `DatabaseLoadWrap` job does the same from script with `ec.artifactExecution.runAsUser(location, body)` (`tools_host.rs`). A cron run has no user: `run#EtlMapping` then signs in as the saved mapping's owner for that one run, so the owner's own permissions decide. The owner must be a `ServiceJobUser` of the job. An `ADMIN`, who may write both `ServiceJob` and `ServiceJobUser`, may therefore schedule another user's saved mapping to run as that user; that is allowed on purpose. Either way the job's `location` and `contentBytes` are ignored, so the run reads only the mapping's own source. The owner's login gate applies (a disabled or terminated account, or a password that must change or has expired, refuses the run), and an inline mapping is refused; the load wrap refuses a cron run. `run#DatabaseJob` on a worker re-checks `DATABASE_ADMIN` and runs only server-made plans as raw SQL, with authorization off.

### Secrets

Startup, before listeners, replaces each secret `default-property` that still ends in `CHANGEME` after the environment and `runtime/.env` are read. The value is 32 CSPRNG bytes, base64, written into `runtime/.env`. A new file is mode `0600`. An unwritable `.env` fails startup. `entity_ds_crypt_pass_old` is the exception: the sentinel is kept. `cluster_tls_cert` and `cluster_tls_key` are generated as a pair when `cluster-tls` is on, which it is in every server package. The same path fills `ssh_host_key`, `session_cookie_key`, `git_lfs_token_key` and `acme_account_key`. The key is then on the same host as the data it protects; see [Threat model: stored secrets](#threat-model-stored-secrets).

### Other local processes

The `pdf` feature, which every server package includes, starts headless Chromium when a binary is found, with `--remote-debugging-address=127.0.0.1` and `--remote-debugging-port=0`. This tree does not add its own authentication on that socket. If no Chromium binary is found, the server still starts and PDF is unavailable.

An OpenSearch child starts only when `search_backend` is opensearch, `elasticsearch_url` is loopback (the property default is `http://127.0.0.1:9200`), nothing is already answering, `runtime/opensearch/bin` exists, `opensearch_run` is not `false` (default `true`), and there is no pid file. The default `search_backend` is `postgres`, so the child stays off. User and password properties default to empty.

IPP printing and the SFTP client are outbound. Git, DAV, `/termws`, and `/notws` are routes on the public HTTP server. Web Push (the `web-push` feature) posts to the push service named by each subscription a browser stored, with a VAPID token; internal addresses are refused, no redirect is followed, and the payload is encrypted to the browser and holds no message body. FCM (`service/fcm.rs`) posts only to the token endpoint of the configured service account (`fcm_service_account`, is-secret, never generated) and to `fcm_base_url` (FCM by default), both from the conf, through the framework's outbound HTTP; the data message holds what a Web Push holds, plus a ring's call id, room id, caller name, video flag and expiry (and a ring's end, its call id and reason), and no message body.

## Threat model: stored secrets

This section says what a stored secret is protected from, and what it is not protected from. Each claim names its test; [Proof-Tests, Stored secrets](Proof-Tests.md#stored-secrets) lists them all. A test whose name starts with `known_gap_` pins a weakness: when the weakness is fixed, the test fails, and this section must change with it.

The short answer: field encryption keeps secrets out of a stolen database dump or a database backup that does not include `runtime/.env`. It does not protect them from anyone who has that file, the host, or code that runs in the server. It is not suitable as a personal password manager.

### Assets

| Asset | Where | Protection |
| --- | --- | --- |
| Encrypted fields | Entity fields with `encrypt="true"` (46 in `runtime/` here: OAuth refresh and access tokens, client secrets, mail and SMTP passwords, private keys and their passwords, API keys, bearer tokens, shared secrets, auth JSON) | AES-128-CBC under `entity_ds_crypt_pass` ([Field encryption](#field-encryption)) |
| Generated secrets | `runtime/.env`: `entity_ds_crypt_pass`, `session_cookie_key`, `ssh_host_key`, the cluster TLS key, `git_lfs_token_key` | Mode `0600` on Unix ([Secrets](#secrets)) |
| Session key | `session_cookie_key`; other signing keys derive from it as HMAC-SHA256 of a label (`derived_cookie_key`, `crates/moqui-core/src/user/session.rs:2955`) | Kept only in `.env` and process memory |
| Password and login-key hashes | `UserAccount.currentPassword`, `UserLoginKey` | argon2id for passwords; SHA-256 for login keys ([Login lockout and passwords](#login-lockout-and-passwords)) |
| Client device keys | Desktop and terminal clients | OS key store, else `FileKeyStore` files mode `0600` (`crates/moqui-desktop/src/client/keystore.rs:101`, `crates/moqui-client/src/keys.rs:48`) |

### Controls that hold

- Field encryption with the wrong pass, salt or iteration count does not give the plaintext (`wrong_or_empty_pass_fails`, `only_the_same_pass_salt_and_iterations_decrypt`).
- An empty pass is refused by `encrypt` and `decrypt`, and a pass that is not printable ASCII is refused (`crates/moqui-entity/src/entity/crypto.rs:104`; `wrong_or_empty_pass_fails`, `a_pass_phrase_that_is_not_ascii_is_an_error`).
- `CryptConfig`'s `Debug` does not show the pass (`crypto.rs:50`; `debug_leaves_out_the_pass`).
- Every bound value of an encrypted field in a query is encrypted before SQL (`every_bound_value_of_an_encrypted_field_is_sealed`).
- Startup replaces each secret `CHANGEME` default with 32 CSPRNG bytes, a new value each time, written to `.env` with mode `0600` (`crates/moqui-core/src/context/factory.rs:1823`, `:1974`; `crates/moqui-lib/src/env.rs:147`). A `default-property` is a secret by `is-secret="true"`, or by `pass`, `pw` or `key` in its name (`factory.rs:1954`). Tests: `generated_secrets_are_32_random_bytes_and_secret_names_are_known`, `generated_secret_is_stable_and_unwritable_env_fails`, `update_dotenv_file_replaces_in_place_appends_and_removes`.
- Password hashes are argon2id, and a legacy hash becomes argon2id at the next sign-in (`a_legacy_hash_verifies_and_the_stored_value_becomes_an_argon2_string`).

### Inspiration

Two designs show what MR Moqui does not do yet.

**HashiCorp Vault** (server-side secrets):

- A barrier encrypts all storage with AES-256-GCM. A random nonce on each write gives different ciphertext for equal values, and the GCM tag detects a change.
- The keyring is versioned. `vault operator rotate` adds a key term; old terms still decrypt, and new writes use the new term.
- A root key encrypts the keyring. Shamir's secret sharing (k of n unseal keys) or a KMS or HSM (auto-unseal) seals the root key. The key is not on the disk beside the data.
- Leases and dynamic secrets: Vault makes a short-lived credential on request and revokes it when its lease ends.
- Transit encrypts as a service: the application never holds the key. A rewrap moves ciphertext to the newest key version without exposing the plaintext. Convergent encryption is an opt-in for lookup by value.
- Response wrapping hands a secret over through a single-use token.
- Audit devices log each request with secret values as HMAC-SHA256. A request fails when no audit device can write it (fail closed).
- `mlock` keeps secret memory out of swap.

**Bitwarden** (client-side, zero-knowledge):

- The client derives a master key from the master password with PBKDF2-SHA256 (600,000 iterations by default) or Argon2id.
- HKDF stretches the master key into an encryption key and a MAC key.
- A random user key encrypts the vault. The stretched master key wraps the user key, so a password change rewraps one key, not every item.
- Each field is AES-256-CBC with HMAC-SHA256, encrypt-then-MAC, with a random IV.
- An organization key is shared by encrypting it to each member's RSA public key.
- The client sends only a hash of the master key, and the server hashes it again with a random salt. The server never sees the master password or a plaintext item.

**What MR Moqui can take from them** (also in [Remaining-Work](../../plans/Remaining-Work.md#sessions-notifications-and-security)):

## Heavy lock-down

A production install keeps the default conf's closed switches and does not publish the listeners that are on.

- Do not publish the HTTP port. Empty `webapp_http_bind` is every address, and empty `webapp_http_port` is 8080.
- Do not leave `entity_ds_crypt_pass` or `session_cookie_key` as `CHANGEME`. Startup writes generated values into `runtime/.env` when they still end in `CHANGEME`. Keep that file private (mode `0600`). The same generator fills `ssh_host_key`, the cluster certificate and key, and `git_lfs_token_key`. `entity_ds_crypt_pass_old` stays the sentinel on purpose.
- Do not load demo users.
- Leave tarpits on. The dev conf turns them off for screens, transitions, and services.
- Leave `webapp_allow_origins` empty. The dev conf sets `*`. A foreign origin is then refused. Own origin stays allowed.
- Leave SSH off unless you want it. The default port is empty. The dev conf sets `2222` on `127.0.0.1`.
- Leave A2A, MCP, and the gateway off unless a client is configured. The model facade can stay on without those servers.
- Leave git `allow-http` false, and DAV `account-password` false.
- The cluster listener binds every interface on 8444 and requires a client certificate. Keep it on a private network.
- Leave inbound SMTP off unless a gateway and a non-empty allow-list are in place. An empty allow-list does not start the listener.
- Per-client web protection is off until `webapp_trusted_proxies` is set or `webapp_web_protection` is `true`. Set the proxy list when a reverse proxy is in front, so the client address and the per-client rules see the client rather than the proxy.

## Public demo server

A public demo breaks one rule above on purpose: it loads the demo users, and anyone can log in as `john.doe`, an
`ADMIN`. The demo component (`runtime/components/dev/demo`, loaded by `runtime/conf/MoquiDemoConf.xml`) narrows what
that login reaches:

- Tools' SQL, Data Load, Export and Snapshots, Database Speed Test, Activity, Queries and Connections, Service Run
  and Load testing (`Tools/Load`) are replaced by a screen that says they are disabled. Activity and Queries show every
  session's statements. Plans, jobs, maintenance and resets are refused by the VIEW-only authorization and the missing
  `DATABASE_ADMIN`.
- `ADMIN` is VIEW-only on Tools, System (Monitor with it), `/moqui`, EntitySync and SystemMessage receive, `/resources` (so refused: `run` is not a view verb), git repositories,
  report git sync and report webhooks. It loses `SearchRemote`, `DashboardRemote`, `ADMIN_PASSWORD`, `SSH_SFTP`,
  `SSH_GIT`, `MONITOR_INGEST` and `REPORT_SAVE_LOCATION`. `john.doe` leaves `ADMIN_ADV`.
- SSH (`ssh-server enabled="false"`), DAV, the MCP server and client, A2A both ways and the gateway are off, and mail
  connects only to `localhost`.
- Password changes and resets, sign-in factors, and username, disabled and require-password-change changes are refused
  for the shared login, so one visitor cannot lock the others out.

Visitors can still change any business data, and `john.doe` can view every entity in Tools. Restore the database on a
schedule, and keep real keys out of it. Its README has the rest.

### Integration-fix cluster rollout

The compact `collab-update` envelope carries the update once, in `body.frame.update`. Receivers apply that update before broadcasting the frame to local editors. Incoming notification socket messages are capped at 16 MiB, and a collaboration update whose complete cluster envelope exceeds that limit is refused before local application or acknowledgement.

Upgrade and restart every member together, with collaborative editing stopped until all members run the new version. Mixed versions are unsupported for this wire-format change; older receivers expect a second top-level update and HTTPS receivers still enforce 1 MiB. No database migration is required.
