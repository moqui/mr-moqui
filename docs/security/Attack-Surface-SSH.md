# Attack surface: SSH and the terminal

The SSH listener, the admin shell, the terminal UI and terminal sessions. `/termws` is a row in [Attack-Surface-Routes.md](Attack-Surface-Routes.md); SFTP is in [Attack-Surface-Files.md](Attack-Surface-Files.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## SSH and the TUI

The SSH server is one `TcpListener`. SFTP, git, the admin shell, `apps`, `agent-apps`, and the SSH cluster channel are channels on it. `moqui tui` with no `--serve` and no `--server` opens no port (`docs/ui/TUI.md`).

Off in the default conf: `ssh_port` empty, `ssh_host` `127.0.0.1`. `0` binds an ephemeral port. `./moq run` merges the dev conf, which sets `ssh_port` to `2222`, still on loopback unless `ssh_host` changes. `MoquiProductionConf.xml` does not set `ssh_port`. The `ssh` feature is in Dev, Enterprise, and Maximal. Lite leaves it out. `moqui tui --serve` starts this listener together with HTTP and the cluster listener.

Password login uses `login_user` (lockout counts, `ipAllowed` of the account and its groups). An account that needs a second factor is refused at the SSH password step when the secret is its account password. An app password is tried first when the secret has that shape, and it logs in an account that needs a second factor. A login by app password gets the same channels as one by account password: the admin shell with `SSH_SHELL`, the SFTP root with `SSH_SFTP`, and git only with `git-password-auth`. A public key must match an active `UserSshKey` by SHA-256 fingerprint, then `internal_login_user` with no password. Keyboard-interactive (`login-dialog` default true, and only if `tui` is built) asks no questions: the session has no user until the apps login dialog, the same username, password, and second factor as `moqui tui`. That dialog checks `ipAllowed` and closes after 2 minutes without a login or 5 refused logins. On a system with no accounts the dialog creates the first administrator before it logs in (`get#InitialAdminNeeded`, then `create#InitialAdminAccount` with no user, as the browser's anonymous Login form posts it): no wider than that form, since the service refuses once any account exists; a refused creation counts toward the 5, and the 2 minutes still hold. Pre-auth timeout is 30 seconds, and at most 16 connections have not logged in. The host key is `ssh_host_key`, generated into `runtime/.env`.

`SSH_SHELL` is seeded on `ADMIN_ADV` and is sealed, so the ordinary permission UI cannot grant it. A login with `SSH_SHELL` gets the admin shell (`help`, `status`, `service`, `entity` up to 100 rows, `cache clear`, `js` with `ec`, `apps`; on a dev instance `sh`, `profiles`, `sessions` and `attach`, [Terminal](../ui/Terminal.md)). Those commands run as that user. `service`, `entity`, and `js` also need Tools-app artifact authorization. Without `SSH_SHELL`, or after a dialog login, the session is only `apps`. `agent-apps` needs a key or password login and no pty. It drives the same client with that user's credentials. A dialog login gets no shell commands, no `agent-apps`, no SFTP, and no git. Git over SSH needs `SSH_GIT` (seeded on `ADMIN`) and a key, unless `git-password-auth` (default false). With `ssh-server` `git-any-account="true"` (default false) any account that logs in by key gets the git commands (`git-upload-pack`, `git-receive-pack`, `git-lfs-authenticate`) without `SSH_GIT`, so on a site with public registration every account that adds a `UserSshKey` reaches the git server over SSH; each repository's `AT_GIT_REPOSITORY` check still decides, a repository it may not view is "not found", and a password login is never let in by it. It opens no shell and no SFTP root; SFTP to the drives an account may open is `dav-server` `sftp-drives`, as before. One user logged in by key or password holds at most `max-sessions-per-user` (4) of the sessions and one address (an IPv6 /64) `max-sessions-per-source` (8), so one account or host cannot hold all of `max-sessions`; a cluster peer is counted by neither, and 0 is no share. At most `max-sessions` 8 SSH connections, 4 of one user (`max-sessions-per-user`) and 8 from one address (`max-sessions-per-source`). Terminal sessions also count against the terminal limits. Idle time is 10 minutes.

**The browser terminal's command line and host sessions** ([Terminal](../ui/Terminal.md#who-may-open-what-and-from-where), plans/Terminal-Fancy.md §8). On a dev instance only by default (`instance_purpose` dev; `terminal` `command-line` and `host-sessions` are `dev` by default, and a value other than `dev` or `false` turns one on whatever the purpose) and only in a build with the dev tools (Maximal, Debug; not Lite or Enterprise), a user with `SSH_SHELL` gets the same `moqui>` prompt in the browser, and a user with `TERMINAL_HOST` (sealed, on `ADMIN_ADV`) programs on the server's operating system on a pty: a shell as the server's OS user, with its files, keys, processes, the runtime's `.env` and the database's files. With the dev AIDE (its D15) these are the exceptions to "no code from outside runs on the server", with its limits: dev only, a permission, an audit. From the server's own machine (a loopback peer, no forwarding header, the server's own loopback origin; or the Desktop app's node in process) nothing more is asked. From anywhere else (a LAN, a VPN, the edge node, a tunnel or a proxy on the machine) they need `terminal` `remote="true"` (off by default; `terminal_remote`), a secure request and a sign-in within `remote-reauth-minutes` (60), asked when a session is opened and again when a socket attaches to one; a device key's requests keep no session, so its user confirms the password (and code) in one request for a short ticket (`confirm#TerminalUser`). They take only the server's own origin, whatever `allow-origins` says (a device key's socket, which sends none, excepted). Everything else is one vague `notAvailable`. Each one is a `moqui.terminal.TerminalSession` audit row (who, what program, where from, edge or not, when, how it ended; never what is typed or shown), kept 90 days. The program's environment is the server's less every variable that names a conf property, and holds no credential of the Moqui user. `sh` at the SSH prompt takes the same permission and purpose, and the rule above by the peer's address; `attach <id>` at the SSH prompt takes one of the user's own sessions only (another user's id is no such session) and, for a command line or a host session, the attach-time checks above by the peer's address. Host sessions are held by `moqui term-hold`, a process of the server's OS user that outlives the server, on a Unix socket in `runtime/tmp/term-hold` (`0700` directory, `0600` socket) that trusts its owner only. A dev instance with remote on logs a WARN at start. An administrator (the System app's update) may end any user's session, which is an audit row (`EntityAuditLog`, `endedBy`). `open#TerminalSession`'s `input` is typed into a new host session's program as the user would type it (the Dev AIDE's Run locally types `sh <script>`, a script it wrote under `runtime/tmp/dev-aide-run` from the working tree's `ci.xml`: the job's steps and variables, its secrets' variables unset); it is at most 4096 bytes with no NUL, gives nothing a host session's user could not type, and a command or host session is never opened under a fence or in a sim (`fence::check_effect` Process; `try_service` refuses every Terminal service). Run locally (`start#LocalRun`) is refused under a fence, in a sim and from a header login, runs only the script the page showed (its digest), writes it `0600` in a `0700` directory, removes it when it ends, and types it into the server user's shell profile.

### Channels and permissions

The SSH handler implements session channels only. It has no handler for `direct-tcpip`, `tcpip-forward`, X11 or agent forwarding (`crates/moqui-host/src/ssh/server.rs`). `SSH_SFTP`, `SSH_SHELL` and `SSH_GIT` are read once, when the password or key login succeeds, and kept for the connection. The `sftp` subsystem is the only subsystem. An exec request is, in order: `cluster <topic>` for the cluster user, a git or git-lfs command, `agent-apps`, `apps`, and otherwise one admin shell line for a user with `SSH_SHELL`. A failed login is answered after 500 ms (`auth_rejection_time`).

### The admin shell

The commands are in `crates/moqui-host/src/command/shell.rs`. An exec request and each line at the prompt run on a request worker after `internal_login_user` of the SSH user. The gate is the `SSH_SHELL` value read at login and a username; the shell does not ask how the user logged in (key, account password or app password). `service`, `entity` and `js` push `component://tools/screen/Tools.xml` with action `view` and `Authz::Required`, and a user without authorization for that screen is refused. `status` and `cache clear` push no screen and ask nothing past `SSH_SHELL`. None of these five commands asks the instance purpose; they answer in production.

`service <name> [json]` calls any service by name with `moqui_core::service::sync` under the Tools frame. `entity <name> [json]` finds up to 100 rows with equality conditions. `js <code>` evaluates the text with `moqui_core::script::eval_value` as that user; what `ec` gives a script is in [Attack-Surface-Scripts.md](Attack-Surface-Scripts.md). A value is printed as JSON (`serde_json::to_string_pretty`). Error text (the message facade's errors, a service's error message) is written to the channel as it is, with `\n` made `\r\n` on a pty.

`shell.rs` writes no log line and no audit row for a command. The login is logged (`SSH login of <user> from <peer>`). `sh` at the prompt writes a log line with its command line and a `moqui.terminal.TerminalSession` audit row (`crates/moqui-host/src/command/host.rs`), and an SSH `attach` is logged.

The SSH cluster channel is not a separate port. It is used when a peer's base URL is `ssh://`. The default transport is HTTPS, so a member sends over SSH only to a peer whose base URL is `ssh://`. The receiving side is not conditional: whenever the SSH server listens, on its port and on an edge node's SSH tunnel to it, it accepts the `moqui-cluster` login and applies its `cluster <topic>` channels, whatever `cluster_transport` is ([Where a member sends, and the SSH channel](Attack-Surface-Cluster-Edge.md#where-a-member-sends-and-the-ssh-channel)). The login user is `moqui-cluster` with an Ed25519 key derived from `cluster_tls_key`. Any other key for that user is rejected. The channel carries the same cluster topics. It is not a shell.

## Terminal session limits

`<terminal max-sessions="16" max-sessions-per-user="4"/>` limits terminal sessions. The browser socket is `/termws`. The screen is `/qapps/Terminal`, which requires authentication. SSH is a separate listener, under [SSH and the TUI](#ssh-and-the-tui).

## Terminal services and `/termws`

The eight services of `org.moqui.terminal.TerminalServices` are Rust functions in `crates/moqui-host/src/term/services.rs`. The `TerminalServices` artifact group grants `org\.moqui\.terminal\.TerminalServices\..*` to `ALL_USERS` (`AUTHZT_ALLOW`, `inheritAuthz` `N`, `runtime/components/base/framework/data/TerminalTypeData.xml`), so each service checks its caller itself. The find, update and close services list or look up sessions by the current username (`Registry::list`, `Registry::find`), so another user's id is "No such terminal session". The two administrator services (every user's sessions, `end#TerminalSessionOf`) call `authorize_own` on `component://tools/screen/System.xml` with `view` or `update`. A session id and a ticket are `random_string(22)`.

`open#TerminalSession` with kind `apps` is open to any signed-in user, within the session limits. For a command line or a host session `access::check` (`crates/moqui-host/src/term/access.rs`) asks, in order:

- The build: the `devtools` feature, and for a host session also unix.
- The switch: `terminal` `command-line` or `host-sessions`. Unset or `dev` is on only on a dev instance. `false` is off. Any other value is on whatever the instance purpose.
- The permission: `SSH_SHELL` or `TERMINAL_HOST`.
- The origin: the `Origin` header equals the request's own scheme, host and port. A request with a `login_key` header and no `Origin`, an SSH session and an in-process request are excepted. A request with no `Origin` header is otherwise refused.
- The place. Local is an in-process request; an SSH peer on loopback; or an HTTP request with a loopback peer, none of the headers `forwarded`, `x-forwarded-for`, `x-forwarded-host`, `x-forwarded-proto`, `x-forwarded-port`, `x-real-ip` or the configured client-address header, a direct request (`RequestVia::Direct`), its own origin, and a `Host` that is `localhost`, `*.localhost` or a loopback address. Anything else is remote and needs `remote` true, a secure request, and a sign-in within `remote-reauth-minutes` or a ticket. An SSH peer that is not on loopback counts as a secure remote request.

`confirm#TerminalUser` checks the password (and code) again and answers a ticket bound to the username. A ticket lives 300 seconds and is not used up by a use. `/termws` reads it from the `ticket` query parameter.

`/termws` (`crates/moqui-host/src/termws.rs`) checks `origin_allowed` for `terminal` (403), then takes a verified session cookie or, with no cookie, a `login_key` header (401 without a user). With a `session` id in the query it attaches to that session, found by id and username, and for a command line or a host session it runs `access::check` again. With no session id it runs an apps session for the user (`run_ephemeral`).

A host session's profile is found by name among the conf's profiles and the user's own (a user preference). `directory`, `resume` and `input` come from the request. `attach <id>` at the prompt works over SSH only and finds the session by id and username.

### The `term-hold` socket

`moqui term-hold` listens on a Unix socket in `runtime/tmp/term-hold` (`crates/moqui-host/src/term/hold.rs`). The directory is made `0700` and set to `0700` at each start; the socket is bound and then set to `0600`. The holder does not read the peer's credentials: the file modes are the only check. A connection sends one JSON line of at most 1 MiB. The operations include `hello`, `list`, `status`, `resize` and `open`; `open` starts the `argv` the request names, with the `env` it names, through the `helper` program it names. A process that can open the socket (the server's OS user, or root) lists the held sessions and starts programs as that user.

## Escape sequences from application data

The TUI (`crates/moqui-tui`) drops, from every string and key of a screen model as it is parsed, the C0 controls other than tab and newline, DEL, the C1 controls and the bidirectional overrides and isolates (`clean_value` in `src/model.rs`). The markdown reader does the same for a link's text and URL. The painter skips a zero-width character, and the encoder writes a space for a control character in a cell (`src/ui/encode.rs`). The encoder writes an OSC 8 hyperlink with its URL as given; `safe_link` admits a URL that starts with `http://`, `https://` or `mailto:`, and the one caller (`src/ui/draw.rs`) takes the URL from the cleaned model. OSC 52 (clipboard) carries Base64 of the copied text. The TUI source writes no title sequence (OSC 0 or 2).

The admin shell and a host session are not drawn by the TUI. A host session's program output goes to the terminal as it is, and so does the admin shell's error text (see [The admin shell](#the-admin-shell)).
