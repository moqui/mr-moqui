# Attack surface: SSH and the terminal

The SSH listener, the admin shell, the terminal UI and terminal sessions. `/termws` is a row in [Attack-Surface-Routes.md](Attack-Surface-Routes.md); SFTP is in [Attack-Surface-Files.md](Attack-Surface-Files.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## SSH and the TUI

The SSH server is one `TcpListener`. SFTP, git, the admin shell, `apps`, `agent-apps`, and the SSH cluster channel are channels on it. `moqui tui` with no `--serve` and no `--server` opens no port (`docs/ui/TUI.md`).

Off in the default conf: `ssh-server@enabled` `false`, `ssh-server@port` `2222`, `ssh-server@host` `127.0.0.1`. `0` binds an ephemeral port; an empty port is refused at the boot (the switch turns it off). `./moq run` merges the dev conf, which sets `ssh-server@enabled` to `true`, still on loopback unless `ssh-server@host` changes. `MoquiProductionConf.xml` does not turn it on, and `MoquiDemoConf.xml` keeps it off. The `ssh` feature is in Dev, Enterprise, and Maximal. Lite leaves it out. `moqui tui --serve` starts this listener together with HTTP and the cluster listener.

The methods offered are public key, password, and keyboard-interactive (only with `login-dialog` and a build with the TUI); "none" is not offered and russh's default refuses it. Password login uses `login_user` under the peer's address (lockout counts, `ipAllowed` of the account and its groups). An account that needs a second factor is refused at the SSH password step when the secret is its account password. An app password is tried first when the secret has that shape, and it logs in an account that needs a second factor. A login by app password (`LoginBy::AppPassword`, `Connection::by_app_password`) gets the drives over SFTP (`dav-server` `sftp-drives`) and nothing else: no admin shell, no SFTP root and no git, whatever the user holds, and `apps` and `agent-apps` answer "an app password opens the drives over SFTP only" (plans/archive/Security-Review.md SEC-FIL-02, fixed). A public key must match an active `UserSshKey` of the named account by SHA-256 fingerprint (`fromDate`, `thruDate`), then `login_ssh_key_user` with the peer's address: no password and no second factor, but `ipAllowed` of the account and its groups is checked against the SSH peer and a `UserLoginHistory` row is written (`recorded_login` inside `with_client_ip`). The logins each later SFTP operation or terminal call borrows (`sftp_fs.rs`, term) run without an address; the session's sign-in passed the check. russh accepts every offered key before the signature, so the answer to an offer does not tell which keys exist. A disabled, terminated or display account, one locked by failed logins and one that must change its password are refused at a key or password login, and again at each later shell line, `apps` or `agent-apps` call, `sh` and `attach`, which log in again (`gate_account`). A failed password or key login is logged with the username the client sent cut to 64 characters and quoted with its control characters escaped (`for_log`, SEC-FIL-92). Keyboard-interactive (`login-dialog` default true, and only if `tui` is built) asks no questions and lets in any name but `moqui-cluster`: the session has no user until the apps login dialog, the same username, password, and second factor as `moqui tui`. That dialog checks `ipAllowed` and closes after 2 minutes without a login or 5 refused logins; a dialog connection that opens no `apps` within 30 seconds is closed (`dialog_expired`). Before its password check the dialog takes the user's `max-sessions-per-user` share, as a key or password login does, and is refused when the user's sessions are all open; a failed login gives the share back, and a login gives back the dialog place (`DialogLogin`, `SlotLogin`). On a system with no accounts the dialog creates the first administrator before it logs in (`get#InitialAdminNeeded`, then `create#InitialAdminAccount` with no user, as the browser's anonymous Login form posts it): no wider than that form, since the service refuses once any account exists; a refused creation counts toward the 5, and the 2 minutes still hold. Over SSH the dialog asks the setup secret unless the peer is on loopback (`initial_admin_local`), and the service is off unless `user-facade/login@initial-admin-enabled` is true (false in the default conf, true in the dev conf). Pre-auth timeout is 30 seconds, and at most 16 connections have not logged in, 4 of them from one source (`PREAUTH_PER_SOURCE`); both limits end at the accepted login, keyboard-interactive included. The host key is `ssh-server@host-key`, generated into `runtime/.env`: an OpenSSH private key or the Base64 of a 32-byte Ed25519 seed, refused when empty or ending `CHANGEME`. The algorithms are russh's defaults.

`SSH_SHELL` is seeded on `ADMIN_ADV` and is sealed, so the ordinary permission UI cannot grant it. A login with `SSH_SHELL` gets the admin shell (`help`, `status`, `service`, `entity` up to 100 rows, `cache clear`, `js` with `ec`, `apps`; on a dev instance `sh`, `profiles` and `attach`, and in any build with the dev tools `sessions`, which asks neither the instance purpose nor `TERMINAL_HOST` and lists the user's own kept sessions, [Terminal](../ui/Terminal.md)). Those commands run as that user. `service`, `entity`, and `js` also need Tools-app artifact authorization. Without `SSH_SHELL`, or after a dialog login, the session is only `apps`. `agent-apps` needs a key or password login and no pty. It drives the same client with that user's credentials and asks no permission. `agent-apps open` leaves a session in a map of the process, found later by an 8-character random id and the username and dropped after 10 minutes unused (`ssh/agent.rs`); these sessions count against the terminal limits, and a size outside 40 to 500 columns and 10 to 500 rows is not taken. A dialog login gets no shell commands, no `agent-apps`, no SFTP, and no git. Git over SSH needs `SSH_GIT` (seeded on `ADMIN`) and a key, unless `git-password-auth` (default false). With `ssh-server` `git-any-account="true"` (default false) any account that logs in by key gets the git commands (`git-upload-pack`, `git-receive-pack`, `git-lfs-authenticate`) without `SSH_GIT`, so on a site with public registration every account that adds a `UserSshKey` reaches the git server over SSH; each repository's `AT_GIT_REPOSITORY` check still decides, a repository it may not view is "not found", and a password login is never let in by it. It opens no shell and no SFTP root; SFTP to the drives an account may open is `dav-server` `sftp-drives`, as before. One user logged in by key or password holds at most `max-sessions-per-user` (4) of the sessions and one address (an IPv6 /64) `max-sessions-per-source` (4), so neither one account nor one host holds all of `max-sessions`. A connection let in by keyboard-interactive takes a session with no user (`Who::Dialog`), counted against the total and its source's share and also against `max-dialog-sessions` (4) and `max-dialog-sessions-per-source` (2); it is closed when it opens no `apps` within 30 seconds, or after `LOGIN_WAIT` (120 seconds) without a login. A cluster peer is counted against the total only, and 0 is no share. At most `max-sessions` 8 SSH connections, 4 of one user (`max-sessions-per-user`) and 4 from one address (`max-sessions-per-source`). Terminal sessions also count against the terminal limits. Idle time is 10 minutes (`inactivity_timeout`); a connection has no maximum age.

**The browser terminal's command line and host sessions** ([Terminal](../ui/Terminal.md#who-may-open-what-and-from-where), plans/archive/Terminal-Fancy.md §8). On a dev instance only by default (`instance@purpose` dev; `terminal` `command-line` and `host-sessions` are `dev` by default, and a value other than `dev` or `false` turns one on whatever the purpose) and only in a build with the dev tools (Maximal, Debug; not Lite or Enterprise), a user with `SSH_SHELL` gets the same `moqui>` prompt in the browser, and a user with `TERMINAL_HOST` (sealed, on `ADMIN_ADV`) programs on the server's operating system on a pty: a shell as the server's OS user, with its files, keys, processes, the runtime's `.env` and the database's files. With the dev AIDE (its D15) these are the exceptions to "no code from outside runs on the server", with its limits: dev only, a permission, an audit. From the server's own machine (a loopback peer, no forwarding header, the server's own loopback origin; or the Desktop app's node in process) nothing more is asked. From anywhere else (a LAN, a VPN, the edge node, a tunnel or a proxy on the machine) they need `terminal` `remote="true"` (off by default; `terminal@remote`), a secure request and a sign-in within `remote-reauth-minutes` (60), asked when a session is opened and again when a socket attaches to one; a device key's requests keep no session, so its user confirms the password (and code) in one request for a short ticket (`confirm#TerminalUser`). They take only the server's own origin, whatever `allow-origins` says (a device key's socket, which sends none, excepted). Everything else is one vague `notAvailable`. Each one is a `moqui.terminal.TerminalSession` audit row (who, what program, where from, edge or not, when, how it ended; never what is typed or shown), kept 90 days. The program's environment (`term/host.rs` `Launch::of`, `environment`) is the server's OS environment less every variable whose name is a `default-property` name of the merged conf (as written, with `.` as `_`, or in upper case), every `MOQUI_*` variable and `MOQUI_TERM_EXEC`; then `TERM`, `COLORTERM`, `LANG` when no locale is set, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION`, `MOQUI_TERMINAL_SESSION`, `MOQUI_RUNTIME`, `MOQUI_USER` and the profile's own `env` are set, and `exec::start` runs the helper with `env_clear()` and that list. It holds no credential of the Moqui user and no value of `runtime/.env` (the dotenv store is read by `get_prop_or_env`, never put in the process environment). A variable an operator passes to the server under a name no `default-property` has (a cloud provider's key, `PGPASSWORD`) is inherited. A user's own profile (the `TERMINAL_PROFILES` preference) names any program and environment. Every host session is started through the program the `terminal_exec_helper` property or environment variable names (`term/exec.rs`), and a session with `integration` writes a script under `runtime/tmp/term-integration` at each start, with no mode of its own, and has bash or zsh read it. `sh` at the SSH prompt takes the same permission and purpose, and the rule above by the peer's address; `attach <id>` at the SSH prompt takes one of the user's own sessions only (another user's id is no such session; a prefix of an id matches only among the user's own) and, for a command line or a host session, the attach-time checks above by the peer's address. Two parts of the rule differ over SSH. The recent sign-in is the connection's login: `sh` and `attach` hold its time to `remote-reauth-minutes` (`HostAccess::signed_in`, SEC-FIL-97), so an older remote connection is refused them. And an SSH peer on loopback is local with no forwarding signal to say otherwise, so the clients of a TCP forwarder on the server's machine (a tunnel tool, an OpenSSH `-L` or a jump through the host's own sshd) are local; an edge tunnel is not (`via_edge`). Host sessions are held by `moqui term-hold`, a process of the server's OS user that outlives the server, on a Unix socket in `runtime/tmp/term-hold` (`0700` directory, `0600` socket) that trusts its owner only, and takes a connection only from a peer of its own uid (`peer_is_own_user`, SEC-FIL-66). A dev instance with remote on logs a WARN at start. An administrator (the System app's update) may end any user's session, which is an audit row (`EntityAuditLog`, `endedBy`). `open#TerminalSession`'s `input` is typed into a new host session's program as the user would type it (the Dev AIDE's Run locally types `sh <script>`, a script it wrote under `runtime/tmp/dev-aide-run` from the working tree's `ci.xml`: the job's steps and variables, its secrets' variables unset); it is at most 4096 bytes with no NUL, gives nothing a host session's user could not type, and a command or host session is never opened under a fence or in a sim (`fence::check_effect` Process; `try_service` refuses every Terminal service). Run locally (`start#LocalRun`) is refused under a fence, in a sim and from a header login, runs only the script the page showed (its digest), writes it `0600` in a `0700` directory, removes it when it ends, and types it into the server user's shell profile.

### Channels and permissions

The SSH handler implements session channels only, at most 8 a connection waiting for a request or running `sftp` (`MAX_SESSION_CHANNELS`; one more is refused with resource-shortage; SEC-FIL-61). A channel that got an exec or shell request is no longer counted, russh 0.65.1 has no limit of its own on the channels of a connection (each takes the next id of a wrapping counter), and each exec runs as its own task. It has no handler for `direct-tcpip`, `tcpip-forward`, X11 or agent forwarding (`crates/moqui-host/src/ssh/server.rs`): russh answers an unknown channel type `unknown_type` and forwarded-streamlocal and agent forwarding "administratively prohibited", and its default handlers reject `direct-tcpip`, `forwarded-tcpip`, X11 and `direct-streamlocal`. The russh `Config` is the default but for the window (2,097,152 bytes), the maximum packet (32,768), `max_auth_attempts` 6, the rejection time and the inactivity time; an incoming packet is at most 256 KiB plus headroom, and there is no keepalive. `SSH_SFTP`, `SSH_SHELL` and `SSH_GIT` are read when the password or key login succeeds, and read again before each `sftp` subsystem, exec or shell request is answered (`refresh_permissions`, SEC-FIL-11), so a permission taken away, or an account that may no longer sign in (disabled, terminated, gone; app-password logins too), refuses what an open connection asks for next. The `sftp` subsystem is the only subsystem. An exec request is, in order: `cluster <topic>` for the cluster user, a git or git-lfs command, `agent-apps`, `apps`, and otherwise one admin shell line for a user with `SSH_SHELL`. A failed login is answered after 500 ms (`auth_rejection_time`).

A `pty-req` gives a `TERM` string of at most 256 bytes (a longer one is refused) and a size; `window` takes the columns and rows of `pty-req` and `window-change` up to 65535 each, and an `apps` session applies a minimum (20 by 10). The session loop draws at most 500 by 500 (`MAX_SIDE` in `crates/moqui-tui/src/ui/session_loop.rs`, logged when a larger size is asked), whatever the transport gives at the start or on a resize and whatever the input asks with `ESC [ 8 ; rows ; cols t` (`Decoded::Resize` in `src/decode.rs`), so SSH, `/termws` and `agent-apps` hold the same bound (SEC-FIL-81, SEC-FIL-100). An `env` value over 256 bytes is refused, and a request is kept for two cases: `GIT_PROTOCOL` for a logged-in user, and `COLORTERM`, `NO_COLOR`, `COLORFGBG`, `LANG`, `LC_ALL` and `LC_CTYPE` for any connection let in (`MAX_CHANNEL_TEXT`). The handler keeps the channel, the pty, the terminal variables and `GIT_PROTOCOL` in maps by channel id, and `channel_close` removes a closed channel from all four (`Connection::forget_channel`).

An `apps` session's input, over SSH and `/termws` alike, is read 4096 bytes at a time and sent to the session thread; the pump counts the bytes sent and not yet taken (`SessionOptions::input_queued`) and stops reading while 1 MiB is queued, so SSH and socket flow control hold the sender back (`term/apps.rs` `INPUT_QUEUED`). The decoder drops an OSC past 512 bytes and a CSI past 64, and keeps at most 1 MiB of a bracketed paste (`MAX_PASTE`), from `ESC [ 200 ~` to `ESC [ 201 ~`: past it the rest is read to the end marker and dropped, the paste is its first 1 MiB, cut back to a whole UTF-8 character, and the cut is logged; each read searches only its own bytes for the marker (`crates/moqui-tui/src/decode.rs`, SEC-FIL-99). A paste has no deadline; a connection let in by keyboard-interactive reaches this before its login, for its login wait. The decoder takes input in time linear in its bytes.

### The admin shell

The commands are in `crates/moqui-host/src/command/shell.rs`. An exec request and each line at the prompt run on a request worker after `internal_login_user` of the SSH user. The gate is the `SSH_SHELL` value read at login and a username; a login by app password gets no shell. `service`, `entity` and `js` push `component://tools/screen/Tools.xml` with action `view` and `Authz::Required`, and a user without authorization for that screen is refused. `status` and `cache clear` push no screen and ask nothing past `SSH_SHELL`. None of these five commands asks the instance purpose; they answer in production.

`service <name> [json]` calls any service by name with `moqui_core::service::sync` under the Tools frame. `entity <name> [json]` finds up to 100 rows with equality conditions. `js <code>` evaluates the text with `moqui_core::script::eval_value` as that user; what `ec` gives a script is in [Attack-Surface-Scripts.md](Attack-Surface-Scripts.md). A value is printed as JSON (`serde_json::to_string_pretty`). Error text (the message facade's errors, a service's error message) is written to the channel as it is, with `\n` made `\r\n` on a pty.

`shell.rs` writes an INFO line and a `moqui.terminal.TerminalSession` row of kind `command` for each `service`, `entity`, `cache` and `js` line that ran, over SSH and at the browser terminal's prompt: the user, the client's address, the command word with the service or entity name (for `js` a SHA-256 digest of the code, never the code or a call's parameters) and its exit status (SEC-FIL-62). The login is logged (`SSH login of <user> from <peer>`). `sh` at the prompt writes a log line with its command line and a `moqui.terminal.TerminalSession` audit row (`crates/moqui-host/src/command/host.rs`), and an SSH `attach` is logged.

The interactive prompt (`crates/moqui-host/src/command/mod.rs` `interactive`, `line.rs`) reads the stream in 4096-byte reads; a line is at most 1 MiB and a `js` block the same. The editor drops C0 input other than its keys. With a pty the history is loaded from and saved to the user's `TERMINAL_HISTORY` preference as a JSON list in plain text: every non-empty command line of at most 4096 bytes that differs from the one before, the last 500, through `shell::history_text` and `kept_history` (`crates/moqui-host/src/command/`): a `service` or `entity` line keeps its name only, nothing of `js` is kept, nor a line that is not a command (a line of a `js` block), and an older value is cleaned at the next save. Up-arrow within the session still recalls whole lines. A recalled line is written to the terminal as stored. With no pty nothing is loaded or saved. The browser command line (`Registry::open_command`) runs the same `interactive` with a pty on an in-memory pipe, with the facts of the request that opened it. The prompt writes a terminal title (OSC 2 `moqui>`) after `sh` and `attach`.

The SSH cluster channel is not a separate port. It is used when a peer's base URL is `ssh://`. The default transport is HTTPS, so a member sends over SSH only to a peer whose base URL is `ssh://`. The receiving side takes the `moqui-cluster` login and applies its `cluster <topic>` channels only when this member takes the SSH channel (`moqui_conf__cluster_member__transport=ssh` or an `ssh://` `cluster-member@base-url`), not through an edge node's SSH tunnel, and from an address a member's `clusterBaseUrl` resolves to ([Where a member sends, and the SSH channel](Attack-Surface-Cluster-Edge.md#where-a-member-sends-and-the-ssh-channel)). The login user is `moqui-cluster` with an Ed25519 key derived from `cluster-member@tls-key`. Any other key for that user is rejected. Each `cluster <topic>` channel then starts with a proof both ways: the server sends a challenge, the member signs it and a nonce of its own, and the server signs both back, with a second key derived from `cluster-member@tls-key`, bound to this server's host key fingerprint; no frame is read before the member's proof, and a sender sends none to a host that does not prove the key (SEC-CLU-04). The host key stays the one git and SFTP clients pin. The channel carries the same cluster topics. It is not a shell.

## Terminal session limits

`<terminal max-sessions="16" max-sessions-per-user="4"/>` limits terminal sessions. The browser socket is `/termws`. The screen is `/qapps/Terminal`, which requires authentication. SSH is a separate listener, under [SSH and the TUI](#ssh-and-the-tui).

## Terminal services and `/termws`

The eight services of `org.moqui.terminal.TerminalServices` are Rust functions in `crates/moqui-host/src/term/services.rs`. The `TerminalServices` artifact group grants `org\.moqui\.terminal\.TerminalServices\..*` to `ALL_USERS` (`AUTHZT_ALLOW`, `inheritAuthz` `N`, `runtime/components/base/framework/data/TerminalTypeData.xml`), so each service checks its caller itself. The find, update and close services list or look up sessions by the current username (`Registry::list`, `Registry::find`), so another user's id is "No such terminal session". The two administrator services (every user's sessions, `end#TerminalSessionOf`) call `authorize_own` on `component://tools/screen/System.xml` with `view` or `update`. A session id and a ticket are `random_string(22)`.

`open#TerminalSession` with kind `apps` is open to any signed-in user, within the session limits. For a command line or a host session `access::check` (`crates/moqui-host/src/term/access.rs`) asks, in order:

- The build: the `devtools` feature, and for a host session also unix.
- The switch: `terminal` `command-line` or `host-sessions`. Unset or `dev` is on only on a dev instance. `true` is on whatever the instance purpose, a warning in the log on a production instance. `false`, and any other value (logged as an error), is off (SEC-FIL-65).
- The permission: `SSH_SHELL` or `TERMINAL_HOST`.
- The origin: the `Origin` header equals the request's own scheme, host and port. A request with a `login_key` header and no `Origin`, an SSH session and an in-process request are excepted. A request with no `Origin` header is otherwise refused.
- The place. Local is an in-process request; an SSH peer on loopback that no edge tunnel handed over; or an HTTP request with a loopback peer, none of the headers `forwarded`, `x-forwarded-for`, `x-forwarded-host`, `x-forwarded-proto`, `x-forwarded-port`, `x-real-ip` or the configured client-address header, a direct request (`RequestVia::Direct`), its own origin, and a `Host` that is `localhost`, `*.localhost` or a loopback address. Anything else is remote and needs `remote` true, a secure request, and a sign-in within `remote-reauth-minutes` or a ticket. An SSH peer that is not on loopback counts as a secure remote request.

`confirm#TerminalUser` checks the password (and code) again and answers a ticket bound to the username. A ticket lives 300 seconds and is not used up by a use. `/termws` reads it from the `ticket` query parameter.

`/termws` (`crates/moqui-host/src/termws.rs`) checks `origin_allowed` for `terminal` (403), then takes a verified session cookie or, with no cookie, a `login_key` header (401 without a user). With a `session` id in the query it attaches to that session, found by id and username, and for a command line or a host session it runs `access::check` again. With no session id it runs an apps session for the user (`run_ephemeral`).

A host session's profile is found by name among the conf's profiles and the user's own (a user preference). `directory`, `resume` and `input` come from the request. `attach <id>` at the prompt works over SSH only and finds the session by id and username.

### The `term-hold` socket

`moqui term-hold` listens on a Unix socket in `runtime/tmp/term-hold` (`crates/moqui-host/src/term/hold.rs`). The directory is made `0700` and set to `0700` at each start; the socket is bound and then set to `0600`. The holder does not read the peer's credentials: the file modes are the only check. A connection sends one JSON line of at most 1 MiB. The operations include `hello`, `list`, `status`, `resize` and `open`; `open` starts the `argv` the request names, with the `env` it names, through the `helper` program it names. A process that can open the socket (the server's OS user, or root) lists the held sessions and starts programs as that user.

## The `moqui tui` command

`moqui tui` with no `--server` renders in process as a logged-in user (`crates/moqui-host/src/tui.rs`, `tui_cmd.rs`). On a dev instance `--user <name>` logs in as that user with no password; it is refused for any other instance purpose, and whoever can run the binary on the runtime (the server's OS user) reaches it. The in-process link keeps what a screen put in `ec.web.sessionAttributes` (names not starting `moqui.`) for the session's next renders, as a browser session does. A terminal session opened through the in-process link cannot be a command line or a host session: its request has no `Origin`, no `login_key` header and is not `RequestVia::InProcess`.

`moqui tui --server <base>` (`tui_remote.rs`) is a client on the user's machine. It signs in through the REST login for a device login key, keeps the key in `<config>/moqui/tui/<name>.toml` (`0600`), sends it as the `login_key` header to the configured base only, follows no HTTP redirect by itself and takes a redirect's path only, and refuses plain `http` except to `localhost`, `127.0.0.1` and `::1`.

The first-administrator mode over HTTP asks `/Login/initialAdminNeeded` with no key and posts `/Login/createInitialAdminAccount` with the session token it got, the two requests the browser's Login page makes. In process (the SSH dialog, `moqui tui`) it calls `get#InitialAdminNeeded` and `create#InitialAdminAccount` with no user, under the SSH peer's address.

## Escape sequences from application data

The TUI (`crates/moqui-tui`) drops, from every string and key of a screen model as it is parsed, the C0 controls other than tab and newline, DEL, the C1 controls and the bidirectional overrides and isolates (`clean_value` in `src/model.rs`). The markdown reader does the same for a link's text and URL. The painter skips a zero-width character. On the SSH and browser-terminal loop the encoder writes a space for a control character in a cell (`src/ui/encode.rs`); `moqui tui`, `moqui tui --server`, the agent answers and `--snapshot` draw through Revue's writer or plain text, where nothing replaces one ([Clients](Attack-Surface-Clients.md)). An OSC 8 hyperlink's URL comes from Revue's registry, which percent-encodes C0, DEL and C1; `safe_link` admits a URL that starts with `http://`, `https://` or `mailto:`, and the one caller (`src/ui/draw.rs`) takes the URL from the cleaned model. OSC 52 (clipboard) carries Base64 of the copied text, and is written only when `Session::copy` is set, which only `copy_text` does, from a mouse drag or double or triple click, the Copy key, Ctrl+C or Ctrl+X in a field, and the code editor's key handler (`Act::Copy`); a component's `tick`, the one path with no user action, does not copy. What is copied is server text the user selected. The TUI source writes no title sequence (OSC 0 or 2); the `moqui>` prompt writes OSC 2 (see [The admin shell](#the-admin-shell)).

Data that reaches the TUI outside a screen model is not cleaned by `clean_value`: the JSON a component receives (`Link::json`), transition messages, menu titles, shell data and option labels. On the SSH and browser-terminal loop the encoder still writes a space for every C0, DEL and C1 character in a cell; the bidirectional overrides and isolates are not control characters and pass from these sources. No call that registers a hyperlink was found in `components/` by search.

A user who may view `component://tools/screen/System.xml` and the `otel_logs` dataset gets the server's WARN and ERROR log lines forwarded into the `apps` session's log pane, over SSH too (`term/apps.rs`); over SSH the pane draws through the encoder, and in `moqui tui` through Revue's writer (`tui_cmd.rs`, `ui/run.rs`). The console log writer splits a message at newlines and passes every other character.

The admin shell and a host session are not drawn by the TUI. A host session's program output goes to the terminal as it is. The admin shell's output and error text (each outcome, the SSH exec answer and the `error:` line) pass through `with_newlines` (`crates/moqui-host/src/command/mod.rs`), which drops the same controls as the TUI: C0 other than tab and newline, DEL, C1 and the bidirectional overrides and isolates (SEC-FIL-63; see [The admin shell](#the-admin-shell)).
