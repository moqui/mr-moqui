# Attack surface: SSH and the terminal

The SSH listener, the admin shell, the terminal UI and terminal sessions. `/termws` is a row in [Attack-Surface-Routes.md](Attack-Surface-Routes.md); SFTP is in [Attack-Surface-Files.md](Attack-Surface-Files.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## SSH and the TUI

The SSH server is one `TcpListener`. SFTP, git, the admin shell, `apps`, `agent-apps`, and the SSH cluster channel are channels on it. `moqui tui` with no `--serve` and no `--server` opens no port (`docs/ui/TUI.md`).

Off in the default conf: `ssh_port` empty, `ssh_host` `127.0.0.1`. `0` binds an ephemeral port. `./moq run` merges the dev conf, which sets `ssh_port` to `2222`, still on loopback unless `ssh_host` changes. `MoquiProductionConf.xml` does not set `ssh_port`. The `ssh` feature is in Dev, Enterprise, and Maximal. Lite leaves it out. `moqui tui --serve` starts this listener together with HTTP and the cluster listener.

Password login uses `login_user` (lockout counts, `ipAllowed` of the account and its groups). An account that needs a second factor is refused at the SSH password step. An app password is tried first when the secret has that shape. A public key must match an active `UserSshKey` by SHA-256 fingerprint, then `internal_login_user` with no password. Keyboard-interactive (`login-dialog` default true, and only if `tui` is built) asks no questions: the session has no user until the apps login dialog, the same username, password, and second factor as `moqui tui`. That dialog checks `ipAllowed` and closes after 2 minutes without a login or 5 refused logins. On a system with no accounts the dialog creates the first administrator before it logs in (`get#InitialAdminNeeded`, then `create#InitialAdminAccount` with no user, as the browser's anonymous Login form posts it): no wider than that form, since the service refuses once any account exists; a refused creation counts toward the 5, and the 2 minutes still hold. Pre-auth timeout is 30 seconds, and at most 16 connections have not logged in. The host key is `ssh_host_key`, generated into `runtime/.env`.

`SSH_SHELL` is seeded on `ADMIN_ADV` and is sealed, so the ordinary permission UI cannot grant it. A login with `SSH_SHELL` gets the admin shell (`help`, `status`, `service`, `entity` up to 100 rows, `cache clear`, `js` with `ec`, `apps`; on a dev instance `sh`, `profiles`, `sessions` and `attach`, [Terminal](../ui/Terminal.md)). Those commands run as that user. `service`, `entity`, and `js` also need Tools-app artifact authorization. Without `SSH_SHELL`, or after a dialog login, the session is only `apps`. `agent-apps` needs a key or password login and no pty. It drives the same client with that user's credentials. A dialog login gets no shell commands, no `agent-apps`, no SFTP, and no git. Git over SSH needs `SSH_GIT` (seeded on `ADMIN`) and a key, unless `git-password-auth` (default false). With `ssh-server` `git-any-account="true"` (default false) any account that logs in by key gets the git commands (`git-upload-pack`, `git-receive-pack`, `git-lfs-authenticate`) without `SSH_GIT`, so on a site with public registration every account that adds a `UserSshKey` reaches the git server over SSH; each repository's `AT_GIT_REPOSITORY` check still decides, a repository it may not view is "not found", and a password login is never let in by it. It opens no shell and no SFTP root; SFTP to the drives an account may open is `dav-server` `sftp-drives`, as before. One user logged in by key or password holds at most `max-sessions-per-user` (4) of the sessions and one address (an IPv6 /64) `max-sessions-per-source` (8), so one account or host cannot hold all of `max-sessions`; a cluster peer is counted by neither, and 0 is no share. At most `max-sessions` 8 SSH connections, 4 of one user (`max-sessions-per-user`) and 8 from one address (`max-sessions-per-source`). Terminal sessions also count against the terminal limits. Idle time is 10 minutes.

**The browser terminal's command line and host sessions** ([Terminal](../ui/Terminal.md#who-may-open-what-and-from-where), plans/Terminal-Fancy.md §8). On a dev instance only (`instance_purpose` dev; `terminal` `command-line` and `host-sessions` are `dev` by default) and only in a build with the dev tools (Maximal, Debug; not Lite or Enterprise), a user with `SSH_SHELL` gets the same `moqui>` prompt in the browser, and a user with `TERMINAL_HOST` (sealed, on `ADMIN_ADV`) programs on the server's operating system on a pty: a shell as the server's OS user, with its files, keys, processes, the runtime's `.env` and the database's files. With the dev AIDE (its D15) these are the exceptions to "no code from outside runs on the server", with its limits: dev only, a permission, an audit. From the server's own machine (a loopback peer, no forwarding header, the server's own loopback origin; or the Desktop app's node in process) nothing more is asked. From anywhere else (a LAN, a VPN, the edge node, a tunnel or a proxy on the machine) they need `terminal` `remote="true"` (off by default; `terminal_remote`), a secure request and a sign-in within `remote-reauth-minutes` (60), asked when a session is opened and again when a socket attaches to one; a device key's requests keep no session, so its user confirms the password (and code) in one request for a short ticket (`confirm#TerminalUser`). They take only the server's own origin, whatever `allow-origins` says (a device key's socket, which sends none, excepted). Everything else is one vague `notAvailable`. Each one is a `moqui.terminal.TerminalSession` audit row (who, what program, where from, edge or not, when, how it ended; never what is typed or shown), kept 90 days. The program's environment is the server's less every variable that names a conf property, and holds no credential of the Moqui user. `sh` at the SSH prompt takes the same permission and purpose, and the rule above by the peer's address; `attach <id>` at the SSH prompt takes one of the user's own sessions only (another user's id is no such session) and, for a command line or a host session, the attach-time checks above by the peer's address. Host sessions are held by `moqui term-hold`, a process of the server's OS user that outlives the server, on a Unix socket in `runtime/tmp/term-hold` (`0700` directory, `0600` socket) that trusts its owner only. A dev instance with remote on logs a WARN at start. An administrator (the System app's update) may end any user's session, which is an audit row (`EntityAuditLog`, `endedBy`). `open#TerminalSession`'s `input` is typed into a new host session's program as the user would type it (the Dev AIDE's Run locally types `sh <script>`, a script it wrote under `runtime/tmp/dev-aide-run` from the working tree's `ci.xml`: the job's steps and variables, its secrets' variables unset); it is at most 4096 bytes with no NUL, gives nothing a host session's user could not type, and a command or host session is never opened under a fence or in a sim (`fence::check_effect` Process; `try_service` refuses every Terminal service). Run locally (`start#LocalRun`) is refused under a fence, in a sim and from a header login, runs only the script the page showed (its digest), writes it `0600` in a `0700` directory, removes it when it ends, and types it into the server user's shell profile.

The SSH cluster channel is not a separate port. It is used when a peer's base URL is `ssh://`. The default transport is HTTPS, so the channel is off unless a member advertises SSH, and the SSH server must be listening. The login user is `moqui-cluster` with an Ed25519 key derived from `cluster_tls_key`. Any other key for that user is rejected. The channel carries the same cluster topics. It is not a shell.

## Terminal session limits

`<terminal max-sessions="16" max-sessions-per-user="4"/>` limits terminal sessions. The browser socket is `/termws`. The screen is `/qapps/Terminal`, which requires authentication. SSH is a separate listener, under [SSH and the TUI](#ssh-and-the-tui).
