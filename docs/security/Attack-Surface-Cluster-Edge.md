# Attack surface: cluster and edge node

The cluster transport between members, and the edge node with its link. The gRPC listener and the PASS authority's gRPC service are rows in [Attack-Surface-Routes.md](Attack-Surface-Routes.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## Cluster

The cluster listener is separate from the public HTTP and HTTPS listeners. Public routes do not ask for a client certificate.

On whenever the process starts listeners (a normal `moqui` with no command, and `moqui tui --serve`). Empty `cluster-member@https-port` is **8444**. Empty `cluster-member@bind-address` is **0.0.0.0**. `0` is ephemeral. Commands that do not serve do not start it. The default is 8444 (`crates/moqui-host/src/cluster_edge/mod.rs`). No example conf under `runtime/conf` sets `cluster-member@bind-address`, and `MoquiDevConf.xml` does not, so `./moq run` binds 8444 on every interface.

A TLS client certificate is mandatory. The verifier accepts only a certificate whose SHA-256 matches this member's `cluster-member@tls-cert`, and the handshake signature must verify, so the certificate without `cluster-member@tls-key` is not enough. The verifier does not check the certificate's validity dates or the host name (`crates/moqui-host/src/tls_pin.rs`). The server presents that same certificate. The handshake must finish within 10 seconds. There is no HTTP login and no public app routing. ALPN picks the protocol: `h2` (offered unless `moqui_conf__cluster_member__protocol=rest`) serves only the gRPC `moqui.cluster.v1.Cluster.Post`, a batch of the same messages with a status for each, decoded up to 17 MiB, at most 64 streams per connection, with HTTP/2 PINGs and a connection idle for 60 seconds closed; `http/1.1`, or no ALPN, serves only `POST /cluster/{topic}` for one of the twelve bus topics (`moqui_core::notify::TOPICS`): `entity-cache-invalidate`, `notification-message`, `collab-update`, `calc-update`, `calc-presence`, `session-end`, `rtc-signal`, `runtime-settings`, `component-deploy`, `edge-replica-note`, `web-ban` or `edge-state`. `edge-replica-note` carries a member's replication notes (entity names and record keys only), which only the member holding the sender lock keeps; `web-ban` is in [Web protection](Attack-Surface-Web.md#web-protection). The body must be JSON with `origin_id` and `message_id`, or the answer is 400. An unknown topic or method is 404. The serialized JSON envelope limit is 16 MiB on HTTPS, SSH and Postgres NOTIFY (including payloads kept in `ClusterMessage`). Oversized messages are refused before fan-out. A 4xx response refuses that message without retrying or marking the peer down. At most 64 connections from addresses that are not members', at most 8 of them from one source (an IPv6 /64 is one), and 64 more for the members' addresses: those the hosts of the `ClusterMember` rows' `clusterBaseUrl` resolve to, read every 30 seconds. A connection past its slot is closed. Cache clears that entity's one-cache. `session-end` drops this process's live copies of the named session ids. Notification and collab messages are published on the local bus and are not fanned out again. `rtc-signal` is sent to one member (`cluster::send_to`, one try from a queue of 1,024 that refuses when full): a call's signaling frames for the node holding its media, its replies for the node holding a leg's socket, the call services' close messages, and the voice services' SIP control (kind `sip`, for the node's SIP engine); a receiver drops one whose `target` is not its instance id (the notify transport reaches every notify member).

An unauthenticated connection to the cluster port reaches the TCP accept, a connection slot and the TLS handshake, nothing else. No HTTP is read before the certificate check. After the handshake the limits are an HTTP/1.1 head of at most 16 KiB, a body of at most 16 MiB (413 above it) read within 10 seconds, and on HTTP/2 a header list of at most 16 KiB (`crates/moqui-host/src/cluster_edge/listen.rs`). The 10 seconds are the HTTP/1.1 branch's only: a gRPC call has no read timeout, and a stream in flight keeps the connection from the idle close, so a holder of the cluster certificate can hold 64 streams of up to 17 MiB each on each of its connections.

The gRPC listener (its rows are in [Attack-Surface-Routes.md](Attack-Surface-Routes.md)) sets limits of its own (`crates/moqui-host/src/grpc_listen.rs`): HTTP/2 keepalive (a ping every 30 seconds, 20 seconds to answer), `max_concurrent_streams` 64 and a call timeout of 300 seconds, with hyper's 16 KiB header list. The decoded message size is each service's: 4 MiB by default, with the PASS authority and the OTLP receiver setting their own. A TLS connection has 10 seconds for its handshake; then a connection, h2c or TLS, closes when it has sent no byte within 10 seconds of being handed over, or has had no call in flight for 60 seconds (`Idle`, `Track`, which counts a call until its answer's body ends), so a connection that sends nothing frees its web protection slot.

Postgres `LISTEN moqui_cluster` is off unless `moqui_conf__cluster_member__transport=notify`. It needs a Postgres entity database. MySQL refuses startup. It is one connection outside the pool, not a new TCP port. The payload is not authenticated on its own. A payload over 7,900 bytes is a `ClusterMessage` row id. A payload of the form `@id` applies any `ClusterMessage` row under the topic the `NOTIFY` names: the row's own topic is read and dropped (`crates/moqui-host/src/cluster_notify.rs`), so any session of the database can have a stored message applied on a topic of its choice. A notification missed while `LISTEN` is down is lost. Reconnect then clears entity caches. The default `cluster-member@transport` is empty, which means the cluster port at `cluster-member@base-url` (gRPC, or the HTTP/1.1 POST).

### The cluster certificate and key

`cluster-member@tls-cert` and `cluster-member@tls-key` ship as `CHANGEME`. With both still `CHANGEME`, the first member to need them makes one self-signed pair (common name `moqui-cluster`, valid 10 years) and keeps both as `SecretValue` rows in one transaction, which every member of the cluster reads through the database; a member that lost the race takes the winner's pair (`seal::secrets`, [Secrets](Attack-Surface-Data.md#secrets)). One set without the other stops the start.

`cluster::start` (`crates/moqui-core/src/cluster/mod.rs`) writes this member's `moqui.server.ClusterMember` row with `sessionKeyFingerprint` (SHA-256 hex of `webapp-list/webapp[webroot]/session-config@cookie-key`, no salt), `certFingerprint` (SHA-256 hex of the certificate) and, on a node that dials an edge or front node, `edgeMemberKey`, the fingerprint of its own edge member key, set before the start so the row is never live without it (`MemberKey::publish_before_start`, `set_edge_member_key`). It refuses to start when a live member's row has another value of either of the first two. The comparison runs at start only, against rows whose heartbeat is live. An empty `cluster-member@base-url` is `https://127.0.0.1:8444`.

Two members that start at the same moment with different `webapp-list/webapp[webroot]/session-config@cookie-key` values each see no live row, and both start. After that neither sends to the other, as each leaves out a row of other material (below, with a warning at each read of the peers), so the two run as two clusters on one database: no cache invalidation, `session-end`, notification, co-editing or call signaling crosses, each serves stale cached rows of the other's writes, and a session cookie of one is not valid on the other. Nothing stops either member.

The `ClusterMember` row is written only by the cluster's own SQL, with authorization off: `write_member` at start and on rejoin, `touch_member` each heartbeat, `delete_dead_members` for rows dead ten windows. No service or screen in the framework writes it. The entity is in none of the lists that keep the generic entity tools out (`crates/moqui-entity/src/entity/sensitive.rs`; `InstanceDrain` of the same package is in one), so whoever holds those tools for it may write it; the tools' own write path was not read. A row is live when `now - heartbeat` is within the window, so a row whose heartbeat is in the future is live, and the cleanup, which deletes only rows whose heartbeat is before its cutoff, never removes it. A live row is what the code asks for wherever it asks for a member: a destination of cluster messages (below), an address with member slots on the cluster port and allowed the SSH cluster login, a live member in the list a local node sends its edge node with its `edgeMemberKey` (Pools below), and on an edge cluster an `edgeLinkUrl` every local node dials. A live row with another fingerprint makes every member refuse to start.

### Where a member sends, and the SSH channel

A sender posts every topic to the `clusterBaseUrl` of each live `ClusterMember` row other than its own (`live_peer_urls`), and `send_to` likewise (`direct::member_url`), only when the row's `certFingerprint` and `sessionKeyFingerprint` are its own (`cluster::same_material`); a row with others is left out with a warning. Whoever can write a `ClusterMember` row can copy the fingerprints, so this keeps out a row of another cluster's material, not a writer of the table. For an `https://` row the receiver must present the pinned cluster certificate. For an `ssh://` row the host key the sender pins is the `sshHostKeyFingerprint` of that same row, which a writer of the table chooses; so before any frame on a `cluster <topic>` channel each side proves the cluster material: the server challenges, the connecting member signs the challenge and a nonce of its own, and the server signs both back, each with an Ed25519 key derived from `cluster-member@tls-key`, bound to the server's host key fingerprint (`ssh::cluster::prove_server`, `prove_client`). A host named by a row without the cluster material gets no message, and a peer that cannot sign is refused (`403`, logged) before its first frame is read. The host key is unchanged (`crates/moqui-host/src/ssh/cluster.rs`).

A member sends over SSH only to a peer whose base URL is `ssh://`. The receiving side takes a login as `moqui-cluster` with the key derived from `cluster-member@tls-key`, and applies its `cluster <topic>` channels, only when this member takes the SSH channel (`moqui_conf__cluster_member__transport=ssh` or a `cluster-member@base-url` of `ssh://`), not through an edge node's SSH tunnel, and from an address a member's `clusterBaseUrl` resolves to (`ssh::cluster::login_refused`, `cluster_edge::member_addresses`; a refusal is logged). The SSH server itself is in [Attack-Surface-SSH.md](Attack-Surface-SSH.md).

### What a holder of the cluster certificate can do

A holder of the cluster certificate and its key can post on any of the twelve topics by the cluster port, and with the key alone by the SSH channel. With `moqui_conf__cluster_member__transport=notify` the same messages arrive by `NOTIFY` on the shared database, which asks for no certificate. A peer's message is applied by `moqui_core::cluster::apply_remote`, which clears caches for `entity-cache-invalidate` and publishes the message on the local bus. The transport itself calls no service and no script. What follows is each topic's subscriber:

- `entity-cache-invalidate`: that entity's caches are cleared. A body with `clearAll` clears every list cache and retires sessions whose rows are gone.
- `notification-message`: the body, less `routeUserIds`, is sent as JSON text to the open `/notws` sockets of the users the body names that follow its `topic`, and to a TUI link of such a user (`fan_out_notice` in `crates/moqui-host/src/notws.rs`). The web shell shows `title` as text in a toast and in the notification history, and as the title of a desktop notification. `link` is followed when the user clicks, by `moqui.openLink` or `window.open` with `noopener`, only when `moqui.followableLink` takes it: a path, a relative link, or an `http`, `https`, `mailto` or `tel` URL (`WebrootVue.qvt.js`, `MoquiLib.js`). On a TUI the link makes a push from the body with no cleaning (`push_of` in `crates/moqui-host/src/tui.rs`), the session sets `title` as its message line (`on_push` in `crates/moqui-tui/src/session/shell.rs`), and the painter writes a cell for every character whose width is not zero, which a control character's is not: a title's control characters are not removed, though every other text the TUI draws goes through `clean_text`. The same holds for any notification whose sender puts outside text in its title. A page's own listener for a topic (`registerListener`) gets the whole body as data. Three were read: the shell's takes `shellCounts` as numbers and otherwise reloads a tray tab, mr-marble's `MyAccountNav.js` adds one to a count, and `DevAide.js` reloads open files the report names and shows file names and summaries as text; none of the three writes HTML or follows a URL from the body.
- `collab-update`, `calc-update`, `calc-presence`: the co-editing rooms take them.
- `session-end`: this process's live copies of the named sessions are dropped.
- `rtc-signal`: the call media driver, and for kind `sip` the SIP engine.
- `runtime-settings`: a timed override of a logging or telemetry setting from the catalog, for at most 24 hours (`crates/moqui-core/src/live_settings/mod.rs`).
- `component-deploy`: the member writes the files of the commit the message names (`to`) of a component kept in a database repository, and loads or reloads the component (`apply_remote` in `crates/moqui-devkit/src/deploy/git.rs`). `gate_remote` is the only check. With `component-deploy`'s `require-passed-run` false (the default) it asks for no attestation, so any commit of that repository is taken. This is the one topic that leads to code being run ([who can author code that runs](Attack-Surface-Scripts.md#who-can-author-code-that-runs)).
- `web-ban`: a ban or a lift of a client address, taken only when the body's `from` is a live member row (`crates/moqui-host/src/guard_share.rs`).
- `edge-state`: the host table and the replicated copies are read again, or links are closed (Edge clusters below).
- `edge-replica-note`: replication notes, as above.

## Edge node

Off unless `instance@node-role` is set (`front`, `front_edge`, `edge` or `all-in-one`) and the HTTPS listener runs, and only in a binary with the `edge` feature (Maximal, Enterprise). It is not a port of its own: the edge link shares the public HTTPS listener and tells its connections apart by the ClientHello, which the listener reads before it picks TLS settings (`crates/moqui-host/src/edge_link/`, [plan](../../plans/archive/Edge-Node.md) §5.1, §5.3, §5.8). A local node opens no port; it dials out.

- **`moqui-edge/1`** (the up and down connections): the edge node presents a certificate from its own link key (`edge@link-key`) and asks for a client certificate without requiring it. After the handshake the key's SHA-256 must match an active `moqui.edge.EdgeClient`; a role byte follows, and a down connection must name the live link generation. The handshake to the role byte has 10 s. On up the local node calls the edge node's `Link` gRPC service; on down the edge node calls the local node, which serves only the link's own gRPC and the PASS authority's (on `/moqui.edge.v1.LocalLink/` and `/moqui.pass.v1.PassAuthority/`, with no client named), forwarded requests and tunnels. A revoked key, a stale generation and a version more than one apart are refused. An up connection with a client certificate runs `store::link_up` on a request worker: a transaction that reads `EdgeClient` for update by the fingerprint (`accept.rs`, `store.rs`). An unknown key matches no row, so nothing is locked or written. `serve_up` counts each refused unpaired key by source (`PairAttempts`, in Pair's window): a source that reached `edge@up-refusals` (30) is refused before `link_up`, except for a key in `known_keys` (at most 10,000: the active pairings' keys read at the member's start, and the keys this process pairs or links), so a busy address does not block a real node; only the first three refusals of a window are logged at info. Another edge member's new pairings reach this member's set only through that node's own link. Web protection's request limits never see a link connection. An up connection has no stream limit of its own (`Limits` with `streams: None`), and is closed 10 s after it opened if no Hello was admitted. Each Hello on it, from any holder of the pairing's key, admitted or not, reads the pairing's row and the other edge members' rows, may Ping the linked member (1 s) and asks every linked member for its list (3 s).
- **`moqui-edge-pair/1`** (checking and pairing): the web certificate, which the local node checks by WebPKI. A check connection (no client certificate) can only Probe; a pairing connection presents the new key and can Pair with a one-use code (kept as a hash, an hour by default, at most a day). Each connection stays at most 30 s, with at most 4 calls and 2 streams; Pair is limited to 10 tries per source address in 10 minutes (an IPv6 /64 is one source; the table holds at most 10,000 sources). A code does not take over a node that is active with another key. The Probe answer, the code and what each side checks are in [Pairing](#pairing-the-code-and-what-each-side-checks).
- **Any other ALPN** gets the web certificate and is never asked for a client certificate.
- **Terminate hosts** (`moqui.edge.EdgeHost`, mode `EdgeHostTerminate`): a request whose `Host` is one goes down its node's link after the edge node's own web protection; only configured names go, and only to their own node. The edge node removes hop-by-hop headers and every forwarding header a client sent (`Forwarded`, `X-Forwarded-*`, `X-Real-IP`, its client-IP header, `x-moqui-edge-*`), then names the client in `x-moqui-edge-client`. The local node believes that header only on the down connection, removes it and the forwarding headers, and runs its own web protection on that client (each header by name is in [Forwarded requests](#forwarded-requests-the-headers-removed-and-set)). A client's `CONNECT` is answered 405; only a WebSocket, an HTTP/1.1 upgrade or an HTTP/2 extended CONNECT with `:protocol` `websocket`, becomes an extended CONNECT down the link, and the edge node answers the browser 101 or 200 as its protocol has it. While the link is down the edge node answers 503 with an offline page. The member must take the request within 10 seconds; then the request body may not stop moving for `<edge forward-idle-seconds>` (120) and its answer's head must come within `forward-head-seconds` (3600) after the body is all sent, or within `forward-first-byte-seconds` (30) for a GET or HEAD with no body, else 504: an upload answered once it is stored is not cut off, a client that stops sending is, and a GET held by a hung member goes once more to another member and counts toward setting the hung one aside (a first-byte timeout that goes to no other member is not counted; a POST is never sent twice and waits the head wait). The edge node's own `request-timeout` does not apply to a forwarded request: the member applies its own (with git's exemption at a public site's page URL, which the edge node cannot tell). Each wait is at most a day. The edge node sees the content of these requests, which includes the session cookies, passwords and second-factor codes of everyone who signs in through a terminate host, staff included.
- **Passthrough hosts** (mode `EdgeHostPassthrough`): a ClientHello whose server name is one goes down the link unopened, with a PROXY v2 header naming the client; the local node ends TLS with its own certificate, so the edge node sees no content. A ClientHello is at most 64 KiB. While the link is down the connection is closed. A local node reads a PROXY header only on a tunnel from its link, never on a socket, and its web protection admits that address before the TLS handshake. A tunnel names a kind (`https`, `ssh`); the local node picks its own listener and the edge node never names an address. At most 768 tunnels and forwarded WebSockets at once per node.
- **Delegated calls, queue and replication** (the link's gRPC, [plan](../../plans/archive/Edge-Node.md) §5.2): the edge node calls `LocalLink.Delegate` and `LocalLink.Deliver` on the down connection, and the local node calls `Link.Deliver` and `Link.Replicate` on the up connection; each is fenced by the link generation, and none is reachable by a forwarded request (the down connection takes gRPC only under `/moqui.edge.v1.LocalLink/` and `/moqui.pass.v1.PassAuthority/`, and only with no client named, which a forwarded request always has). Every message is at most 16 MiB both ways (tonic's decode and encode limits on both servers and clients); a queued item's payload is at most 1 MiB, refused at enqueue on the sender, and a sender splits a replication batch at 500 records and 4 MiB. The receiving edge node refuses a batch of more than 500 records, of a set its own `<replicate>` conf does not name, or with an entity that set does not have (`edge::replica::batch_refused`), and keeps at most `replica-max-rows` replicated records per pairing (1,000,000, all its sets; or the pairing's `EdgeClient.replicaMaxRows`). The content a pairing's link sends before its deliveries (`PutContent`, kept under `CONTENT_IN<node>/` until each delivery is answered) counts against the pairing's queue cap, and in files against `queue-max-content-files` (10,000, empty ones too). At any cap the pairing pauses (`edge::caps`, `EdgeClient.capPausedDate`): its `Replicate` and `PutContent` are refused as unavailable, which the sender tries again (a delivery takes it as the receiver's pause, uncounted), so nothing is dropped, and the administrators get an `EdgePairingPaused` notice; it stays paused until Resume on Edge Clients (`resume#EdgeClient`) or new caps (`update#EdgeClient`). A local node refuses, for now and logged, content its edge node sends past its own caps, and its administrators get an `EdgeContentRefused` notice when it starts refusing and when it takes content again. On the edge node a delegated call is checked first: with the service's definition there, its authorization and `authenticate`; without one, a caller with no user is refused unless the `delegate` entry has `allow-anonymous="true"`. A delegated call runs on the local node only when the service is in the local node's own `<edge><delegate>` list (a compromised edge node could ask for anything), as the user `_EDGE_` (no password, so no login; group `EDGE_DELEGATE`, `UgtRemoteSystems`), with authorization: the `EDGE_DELEGATE` artifact group must grant it; the seed data puts 30 services in it (`echo#Delegate`, the 9 queue handlers and the 20 delegated call and SIP services), each with `inheritAuthz="Y"`. No parameter the edge node sends changes that user: the local node drops `authUsername`, `authPassword`, `authUserAccount`, `authTenantId`, any other `auth` + capital name, every `_` name, and an `edgeCaller` the edge node wrote, then sets `edgeCaller` from the call's caller data (never a login). A delegated call runs on the local node's request pool, in a transaction whose timeout is the `timeout_ms` the edge node sends (`dial.rs`, `edge/delegate.rs`); no cap on it was found in those lines. `enqueue#Item` sends to the other end any `dbresource://` location its caller names (the prefix is the only check, `service/edge.rs`), for a caller authorized for the service; no screen or REST resource names it. A queued item runs its kind's handler from the receiver's own `queue-kind` conf, also as `_EDGE_` with authorization, once per item id (`moqui.edge.EdgeReceipt`, inserted before the handler runs); a node enqueues only the kinds it lists. Replication writes only `moqui.edge.EdgeReplicaValue` and `EdgeReplicaCursor` rows of the sending node on the edge node, with the copied fields encrypted at rest; what a compromised local node sends there is data for its own node only. The shipped lists are in [The delegate list](#the-delegate-list-the-queue-kinds-and-what-_edge_-is-granted), the replicated fields in [What is replicated](#what-is-replicated-to-an-edge-node).
- **PASS authority on the link** ([plan](../../plans/archive/Edge-Node.md) §5.5): an edge node's mr-pass (`moqui_conf__pass__backend_url=edge:`) calls `moqui.pass.v1.PassAuthority` on the down connection; a forwarded request never reaches it (the same rule as `LocalLink`). With several pairings the call goes to the pairing whose Configure names the call's site (each site has one pairing, the first to name it; one two name is refused), and a site no pairing names goes only to the only active pairing: with more than one paired it is refused, also while one is away, so a pairing's authority never sees the calls of another's sites. The link's mutual TLS is the client's identity, so no secret is sent: the local node names it `edge/node@pass-client` (default `edge`) and counts it as registered only for the sites in `pass-authority/client[<id>]@sites` (for another site it is an unregistered caller: [The authority](Attack-Surface-Apps-PASS.md#the-authority)), with its SSO callback `pass-authority/client[<id>]@callback`. Everything else is the direct listener's (the row in Host routes): routed operations only, schema-checked input, a delegation per call, session handles bound to the client and site, the visitor's address as rate-limit data. A compromised edge node can do what a registered PASS server of those sites can: any routed operation and account action, as an anonymous visitor or with the delegations of the visitors who sign in through it (it is their frontend, so it sees their passwords and second-factor codes too), and it can name any visitor address for the rate limits. It cannot use a delegation or session handle made for another client or site, and it reaches no operation the routes do not list. Which client it is comes from its own offer, though: the wizard's Apply writes the offer's client id as `edge/node@pass-client` with no look at an existing client of that id ([What a local node takes](#what-a-local-node-takes-from-its-edge-node-besides-requests)).
- **Port 25** (the MTA in moqui, E5b; `conf/edge/MoquiEdgeConf.xml` turns internet mode on, and `smtp-server@listen-port` in `.env` starts it): the [Mail](Attack-Surface-Mail.md#mail) listener's internet mode. `RCPT TO` is answered from the paired nodes' replicated accounts (`mailRecipients`), never by calling a local node, so an unknown address is refused while a node is away, and a node not yet replicated answers 451. A message is queued for its node, not stored on the edge node beyond the queue's retention. There is no relaying: the edge node sends only what a paired node queued (`mailOut`) to each recipient domain's MX, DKIM-signed with `mail-delivery/dkim@key` when the `From` domain is one of that paired node's replicated domains (and, when `mail-delivery/dkim@domains` is set, one of that list too); its other mail goes out unsigned, and a sender of another pairing's domain is refused ([Mail](Attack-Surface-Mail.md)). A VERP bounce address is taken only for a `mailOut` item the edge node holds the receipt of.
- **LMTP from a gateway beside it** (E5a, instead of port 25): the listener out of internet mode with `protocol="lmtp"` and an allow-list of the gateway's addresses (`127.0.0.1,::1`), as in [Mail](Attack-Surface-Mail.md#mail). Mail out is relayed to the gateway on `mail-delivery@relay-port`, on loopback.
- **Chat webhooks and media on the edge node** (E6): the [Host routes](Attack-Surface-Routes.md#host-routes-and-servlets) rows for `/channels/{chatBridgeId}/webhook` and `/media/{token}`. The webhook's signature is checked with the bridge's replicated public key (never its API key, which stays on the local node), and the raw request goes in the queue, applied on the local node without a second check. The local node checks every queued request's signature again with the bridge's whole configuration (at the time it came, `receivedMillis`, and over its public URL: `webhookUrl`, else `channels@public-url` and the path and query) before anything is parsed, whichever way the edge node queued it, so a bridge whose adapter changed after the edge node queued its request is never applied unchecked. A provider that signs with a secret instead (Twilio's auth token, Sinch's webhook secret; the adapter's `WebhookVerification::Core`) cannot be checked on the edge node, and no secret is replicated: the edge node checks only the method, the size (`channels/edge-limits@unverified-max-bytes`, 32 KiB, within `channels@webhook-max-bytes`), that the provider's signature header is there (else 401, counted as for a bad signature), a rate per client address (`channels/edge-limits@webhooks-per-client-minute`, 120) and per bridge (`channels/edge-limits@webhooks-per-minute`, 600; token buckets on each edge node member, at most 10,000 kept), and how many of the bridge's items wait unverified (`channels/edge-limits@unverified-waiting`, 500, so at most 16 MiB of bodies); over a rate or the cap it answers 429. It then parses the unverified body for the event key only (the adapter's `webhook_event_id`, bounded by the size cap) and queues the request, its idempotency key including a hash of the signature header, so a forged item naming a real event's id cannot take that event's key and make the provider's own copy a duplicate. On the local node a request whose signature is not the network's is refused: kept as `moqui.chat.ChatBridgeWebhookRefused` (at most 1,000 a bridge, 30 days; `replay#RefusedWebhooks` after a configuration fix), counted (`find#Bridges`, System › Chat Bridges) and logged once per bridge every ten minutes (also once refusals stop), and the item answered done so it holds nothing behind it; one the local node cannot check (the bridge has no secret, or its configuration did not read) waits (`retryLater`), named by its bridge. So a flood of forged requests at one bridge costs at most its rates in queue items and checks on the local node, and at most 500 items and 16 MiB waiting on the edge node. - **Offer and Configure** (the Edge Node wizard, [plan](../../plans/archive/Edge-Node.md) §5.7): on the up connection, fenced by the link generation like the others, a local node asks `Link.GetOffer` (what the edge node offers it, with its own host names; no secret: the DKIM key's public record, public names and addresses) and sends `Link.Configure`. - **Calls** (E7, [plan](../../plans/archive/Edge-Node.md) §5.4): the edge node's media socket and TURN are the [Call media](Attack-Surface-Comms.md#call-media) and [TURN](Attack-Surface-Comms.md#turn) listeners, with the same rules (a relay reaches only the media port). One local node has at most `edge@call-legs-per-pairing` (200) legs on the media node at once. Delegated to the local node: `note#MediaEvent`, `get#CaptionSpeaker`, `store#CallTranscript` (only for a leg of the named call) and `transcribe#CaptionAudio` (only for a participant of the call, `userId` required, a chunk at most 4 MiB); queued: `callRecording`, stored only from the queue's own copy of the item's content and only as `_EDGE_`. Run as `_EDGE_`, each refuses a call whose media node is not the local node's edge node (its `CallMediaNode` row `edgeLinked`). A compromised edge node can see and record the media of calls that are not end-to-end encrypted, write captions, media events and recordings of the calls whose media it holds, and spend their participants' transcription quota. `transcribe#CaptionAudio` and `store#CallTranscript` do not ask whether the call's captions are on, so this holds for a call with captions off too; the user charged is any participant the edge node names, a transcription's `timeoutSeconds` is the edge node's up to 300, and `store#CallTranscript` takes `text` with `allow-html="any"`.
- **SIP** (E8, [plan](../../plans/archive/Edge-Node.md) §5.4 "Voice (SIP)"): the edge node's SIP listeners, RTP range and registrar are the [SIP](Attack-Surface-Comms.md#sip) ones, with the same flood caps and failed-digest blocks, on the edge node's own; the calls it routes through the local node get the local node's fraud controls there, and the forwards its fallback makes while the local node is away get only the engine's own checks (the destination's class, the deployment's international and premium switches, the calls at once) and the number's limits at once and a day that its replicated fallback row carries; they start only when `.env` sets `sip-server@port` or `sip-server@tls-port`. As `_EDGE_`, `record#AuthFailure` and `note#TrunkStatus` take a report only as the edge node's own engine (`edgeAllowed`, with the `instanceId` the SIP engine sends) (`Voice.js`). The edge node's blocks are kept as `edge:<address>`, never handed to the local cluster's own SIP engines by `get#EngineConfig`, removed once ended, and capped by `sip-server/limits@edge-blocks-per-hour` (200) and `@edge-alerts-per-hour` (10); `find#AuthBlocks` lists local rows (200) and edge rows (100) each in its own share. A trunk status is taken only for an enabled trunk and only while no engine of the local node is up, so the edge node's report never overrides the local engines' status or emergency readiness, and its trunk alerts count against `VoiceTrunk.alertedDate`; each local engine reports every trunk it holds on its first outcome at start and reload. The local node also uses as given some values the edge node names: `atMs`, the time the call handling rules, an IVR menu and a queue are read at, so the edge node picks which schedule's route a call takes; `ivrMenuId`, any menu, not the one the call is in; a binding's `expiresDate`, so one fresh digest answer makes a binding that lasts while the edge node's SIP row is live; and the `fromNumber` that is the source of `check#VoicemailPin`'s per-source failure limit, so only the per-box limit binds it. A message the edge node queues goes in the box the local node chose for the call, or the called number's own, never one the edge node names. While the local node is away the edge node answers from the replicated `voiceFallbacks` (each number's outside number, which a call may be forwarded to through the engine's own fraud checks, and whether it takes a message). A compromised edge node can answer and record calls to the numbers, take messages for them, forward a number's calls to its replicated outside number, and route calls into the local node as from the trunks. It holds the trunks' `authJson`, so it can also register and place calls on the trunks with their credentials. Each delegated call carries how long the edge node waits; the local node starts nothing past it and rolls back a call that ran past it. It cannot sign a phone in (`store#SipRegistration`) or start a call from a phone (`receive#DeviceCall`) without a fresh answer of that phone, nor read a box's messages without its PIN. The fresh answer guards those two services only: when a call rings a user whose phone has a binding at the edge node, the edge node's own `note#PhoneLeg` with `answered` makes that device leg the user's answered leg, and `refer#Call` on it signs in as that user and blind-transfers the call to any number the user's own outbound permissions allow (`CallTransfers.js`), and the edge node can start the ringing call itself. So it can answer in a user's name any call that rings them, and place a call in that user's name and against that user's limits. With several pairings (E16) each pairing's trunks, calls, legs and phones are keyed by its node: a call goes to the pairing whose copies have the number dialled and a phone to the pairing whose `sip-server@domain` its realm is, a number or a realm two pairings claim is refused (logged with both), a fallback is read from its owner's copy only, a message is queued to the pairing whose call it was (after a restart too), and each pairing's offer lists only its own trunks.
- **SSH tunnel port**: off unless `edge@ssh-tunnel-port` is set (`edge@ssh-tunnel-host`, empty for every address). - **XMPP ports of every domain** (E16): `edge@xmpp-port` and `edge@xmpp-tls-port` take every pairing's XMPP domain. - **An all-in-one node** (`moqui_conf__instance__node_role=all-in-one`, `conf/all-in-one/MoquiAllInOneConf.xml`, [plan](../../plans/archive/Edge-Node.md) §10): a full server with its own users and data that also takes one local node's link, with every rule above. What the paired node's traffic can reach on it:
  - **Delegated calls.** A listed service is sent to the paired node only inside that node's owner scope (`moqui_core::edge::owner::with`, set by the engine that took the item), and to that node; outside it the service runs on the server for the server's own item.
  - **The queue.** A paired node's items run only its kind's handler from the server's own `queue-kind` conf, once per item id, as on an edge node.
  - **Replica rows** are `EdgeReplicaValue` rows of that node, encrypted at rest, read by the engines to route its items. They are never shown to the server's own users: only System › Edge Clients shows them, with the records held back for a claim (`moqui.edge.EdgeReplicaConflict`).
  - **Claims.** The server's own items win: Configure refuses the node's bridges, XMPP and SIP domains, numbers and a mail domain the server holds whole (its bounce domain), naming each, and a replicated record that claims a server's mail address, bridge or number is not applied (kept as a conflict, logged). The server's own setup refuses an item the replica holds (`EdgeClaims.secas.xml`). So a paired node cannot take the server's mail, webhooks, numbers or phones' realm. An address both sides hold gets 451 at `RCPT TO`, and a bridge both hold 409 at its webhook, naming the id; neither side gets it until an operator fixes it.
  - **Calls and SIP.** Each signaling message from the link carries the stamped `linkNode`, and a paired node's rooms, call, leg, trunk and phone ids are keyed by that node (`sip/owners.rs`), so its messages never reach the server's own calls, whose ids come from another database. A phone of the server's `sip-server@domain` is checked on the server; one of the paired node's domain is delegated to it. Each paired node's greetings are kept under `dbresource://moqui/edge-node/<node>/`, apart from the server's and from another pairing's.
  - **XMPP.** The server's own XMPP ports read each connection's domain as the tunnel ports do (E16): a paired node's domain goes down its link, any other is the server's own. The tunnel ports, when set, take the server's own domain to its own server too; one equal to one of the server's own XMPP ports is not opened again.
  - **Trust.** The paired node's owner trusts the server's operators as an edge node's: queued mail, messages and recordings are stored on the server until delivered. A compromised paired node can do on the server what it can on an edge node, for its own items only.
- **Several pairings on one edge node** ([plan](../../plans/Edge-Node2.md) §4.1, E16): a dedicated edge node is an all-in-one node with no items of its own, and the pairings are kept apart as the server and its pairing are above. Reasonable isolation for pairings of one organization or related ones, not a defense against a hostile pairing.
  - **Rows.** Every edge row is keyed by its pairing, and each engine takes an item for one pairing: a request by its host name, mail by the recipient's address in that pairing's copies, a webhook by the bridge id within the host name, a PASS call by its site, a delegated call by the owner scope the engine set (outside one, refused while several are paired, linked or not), a queued item by the node it names or the owner scope (else refused, logged). No call made for one pairing reads another's copies. Kept greeting and prompt audio is keyed by its pairing: on every node that takes links `kept_audio_location(node, location)` keeps it under `dbresource://moqui/edge-node/<node>/` (`crates/moqui-core/src/edge/media.rs`), so one pairing's item never stands at a location another pairing's calls read. `check_kept_audio` refuses a file over 8 MiB or one that would pass the pairing's queue cap; at the cap it first removes kept files none of the pairing's replicated fallbacks name (`prune_kept_audio`; nothing when the fallbacks cannot be read), in `store#EdgeCallAudio` and when the SIP engine keeps fetched audio. A new greeting whose `callAudio` item arrives before its fallback row replicates can be pruned at the cap.
  - **Claims.** Each host name, mail address, number, XMPP or SIP domain and PASS site has one pairing: the first claim holds. A later Configure is refused the item with only "another node has this name", and a later pairing's replicated record that claims an address or number another pairing holds is not applied, kept as a conflict Edge Clients shows (with the holder), and applied once the first lets it go. An address two pairings' copies still both have (a race, or copies from before) gets 451 at `RCPT TO`. A chat bridge id may be both's: ids come from separate databases, and the host name tells them apart. A mail domain is split between pairings by address, and each pairing's mail out is DKIM-signed only for the domains of its own accounts.
  - **Limits per pairing.** The queue's size cap (`queue-max-megabytes`, or the pairing's `EdgeClient.queueMaxMegabytes`) holds for each pairing alone, so one pairing's backlog fails only its own oldest items; the content it sends and its replicated records (`replica-max-rows`) are capped per pairing too, and a pairing at a cap pauses alone; the MX delivery gives each pairing with mail due an even share of its sessions, holding one back for another pairing, and reads each pairing's rows apart; tunnels and streams per link and MMS files per node were already per pairing.
  - **Shared on purpose:** the edge node's addresses and their mail reputation, the DKIM key and selector, the media and TURN ports, web protection's counts, CPU and bandwidth. A pairing that floods mail through the edge node can hurt the others' reputation; there is no operator per pairing.
  - **The screens** (System › Edge Clients: Clients, Domains, Ports, [plan](../../plans/Edge-Node2.md) §4.10): the System app's, so only its administrators (`SYSTEM_APP`, which the screens' service calls inherit); a direct call to an `org.moqui.edge.EdgeServices` service without that inheritance is refused. The services' `allow-remote="false"` is not the control, as nothing reads that attribute ([services and allow-remote](Attack-Surface-Web.md#services-and-allow-remote)). The menu lists Edge Clients only on a node that takes links (`default-menu-include` reads `instance@node-role`), and the host name, domain, port and queue cap services refuse on any other node. They read and write the rows without the link, so they work while the HTTPS listener is off; a host name change then loads the link's table again. A host name another pairing has is refused with "another node has this name", as in Configure; the operator sees which pairing has it on Domains. What Domains shows of a pairing's setup (its domains, bridges, sites) and its numbers came from that local node and is shown as text, escaped like any other value. A pairing's queue cap is a number of megabytes above 0, or empty for the conf's.
- **Roles** ([plan](../../plans/Edge-Node2.md) §4.3, E17): `instance@node-role` names the option sets. `front_edge` is the edge node as built; `front` (the front set: web access, ports, balancing) and `edge` (the edge set: delegate, queue, replicate, mail, chat, calls, SIP, PASS) take links too. - **Pools: every member of a local cluster links** ([plan](../../plans/Edge-Node2.md) §4.4, E17). A pairing is one local node or one cluster of them; each member presents the pairing's key and names its own instance id in its Hello, and the edge node keeps each member's link apart (a member that dials again replaces only its own). What the key is for, the rows and the work, stays the pairing's: the member id is used only to tell the links apart and in Clients.
  - **Admission** is the new trust decision. A member not linked is admitted only when a linked member's cluster member list, asked for down that member's link at that moment (else the latest it sent with its Ping), has it as a live member; otherwise it is refused with "join the cluster first" and the dialer backs off as for any refusal. So a stolen copy of the pairing's key, or a staging copy on another database with it, does not take a pairing's traffic while a real member is linked. The list carries each member's id, liveness, version and the fingerprint of its own key from its `ClusterMember` row (`ClusterMemberInfo.key_fingerprint`, `edge.proto` field 5, checked as hex), and a listed or kept row admits the Hello as that member only with that key (`admission` in `crates/moqui-core/src/edge/pool.rs`). A row that names no key (a member that publishes none) admits as before, the Hello's own key pinned for the id, and the administrators are told of that first pin, on the linked branch and through the kept list alike (`admitted_unkeyed`, `notify_first_pin`). With no member linked the key alone admits, which is what lets a standby in; the notice and the approval hold below are its guard. The kept list is in memory, so after an edge node restart only the last member and the pins decide.
  - **A member's own key.** The shared key says only which pairing a link is for. Each member also keeps an Ed25519 key of its own, a bootstrap secret of its own `runtime/db/seal.json` (`edge-member-key`; a `runtime/db/edge_member_key` an earlier build wrote is moved there; not in the database, which a standby restores, and not in the recovery bundle, so a member restored from one makes its own), and its Hello signs the TLS connection's exporter value with it. The edge node pins the key's fingerprint for the member's id on its first link (`EdgeClient.memberKeys`, at most 64), claimed in one transaction committed before the link is registered: pinned when none is, kept when it matches, pinned again only on a decided takeover, else refused, so two first links of one id cannot both pin. Past the cap a forgotten marker goes first, then the oldest member that is not linked, the last linked or in the kept member list. A linked id with no key pinned is not replaced within 5 s of its link. The last member with a new key is a takeover from itself: told (or held) as such, displacing no one. `forget#EdgeMember` reads the pins for update and closes that member's link once committed. The key file is written whole to a part file (owner only) and linked into place only where none is; a bad one names itself and what to do. An id named with another key is a new node: refused while a member is linked, a takeover (notice or hold) while none is; `forget#EdgeMember` unpins one. A member that dials again while its link still answers a Ping (1 s) is refused, retryable, so a copy cannot make two links trade places.
  - **The down connection** names the live generation and a 16-byte random token from its up connection's Hello answer (compared in constant time), and is refused while that link's down connection is open: a node that knows a generation cannot take a member's queue, calls, web requests or tunnels.
  - **The node a takeover displaced** (`takeoverFromId`) is refused "taken over", whether or not a member is linked, until `clear#EdgeTakeover`, so a blip of the standby's link or an edge node restart never hands the pairing back to the old copy of the data. Admission is re-checked as the link is registered: two new nodes at once with none linked get one link, the other a retryable refusal.
  - **The member list** (`Link.Hello`, `Link.Ping`, `LocalLink.Members`) is input from a paired node: at most 64 members, each id at most 40 characters with no space, control character or `@`, each named once, a version of at most 40 printable characters, a key fingerprint of hex; a list that fails is not taken whole, and it is used only for that pairing's admission and report. It is kept in memory only, never in the database. A member's state (starting, live, draining, stopping) comes the same way; an unknown one is logged and ignored. Only a live member gets new work (`EdgeServer::link_of`, and the queue answers an item for a member that is not live "unavailable", not counted).
  - **Drain from the edge node** (`drain#EdgeMember`): `LocalLink.Drain` on the member's own down connection, fenced by its generation; the member sets its own `InstanceDrain` row, so `/health` answers 503 as for the recovery action's drain. An administrator's service, as the rest of Edge Clients.
  - **Balancing** ([plan](../../plans/Edge-Node2.md) §4.4, 17B): each piece of work goes to one member that is linked and live, never outside the pairing it is for. The sticky cookie of a terminate host (the session cookie, `__Host-moqui.session` or else `moqui.session`, or the host's `EdgeHost.stickyCookie`) is client input to the hash: rendezvous hashing (SHA-256 of the member id and the value) only picks among that pairing's own members, so a forged or chosen value can at most aim its own requests at one member, which any client with no cookie reaches in turn anyway; a value over 4 KiB is not hashed (the request goes in turn); the value is never stored or logged, and the cookie is passed on unchanged. The same holds for a PASS sign-in's session handle and a delegated call's conversation, and for the client's address (IPv6 by its /64) on passthrough hosts and tunnels. A member whose work fails or times out `set-aside-failures` times in a row (3) is set aside for `set-aside-seconds` (30); with every member set aside all are tried, so a member cannot be kept from work by failures alone longer than that. A request that fails before any byte of an answer goes once more to another member only when it is a GET or HEAD with no body, or was never sent, so a write is never applied twice. Call signaling: each member's down connection has its own route, `<member>@<pairing>` (`@` is in no node id), and a member's frame must name the member as its origin, so the replies for a leg go only to the member whose socket bound it, never to another member or pairing with an id of the same name. The counts per member (`get#EdgeBalancing`, `moqui.edgelink.*` with the pairing and member) are in memory, bounded by the members.
  - **The takeover notice** ([plan](../../plans/Edge-Node2.md) §4.5): a node with a new instance id admitted with no member linked, that is neither the member last linked nor in the latest member list, takes the pairing over: logged as a warning, noted on the pairing's row (`takeoverDate`, `takeoverFromId`, `takeoverToId`) and sent as a notification (topic `EdgeMemberTakeover`) to the `ADMIN` group. With `holdNewMember=Y` (`hold#NewMembers`) such a node is refused "held for approval" until `approve#EdgeMember` names it (one use), with one notice. The approval stores the instance id (`approvedMemberId`), not the member key the held node showed, which the record of the held node does not keep: the next link of the pairing's key that names that id, with any member key, is the takeover. A pairing sends at most four takeover or hold notices an hour; more are only logged, so cycling ids does not flood the administrators. Clients shows the nodes refused or held lately (in memory, eight per pairing).
  - **Replication and the outbox from a pool** (17C): one member sends replication and keeps the link's own rows, the holder of `moqui.edge.EdgeSenderLock` (a 30-second lease by the database's clock; a holder whose claim does not come back within two thirds of the lease stops sending by its own clock, and a new link sends nothing before its first claim). Each batch carries when its sender took the lock, and the edge node refuses a batch of a set whose cursor a later sender wrote, so a member that lost the lock cannot cross the new sender's batches. The queue's claim, its answer and its failing passes read each row `FOR UPDATE`, so two members never both deliver one item.
  - **Deliver again since** (`deliver#ItemsAgain`): an administrator's service on the edge node that sets a pairing's delivered items back to pending, from a time on; delivered items are kept for the retention period only, and the local node's receipts, keyed by the pairing (`edge/node@pairing`, the same in every member's `.env`), make an item it has applied do nothing.
  - **The pool's screens** (System › Edge Clients › Clients, Members and Takeovers; System › Edge Node on a member, This node's cluster): the System app's, as the rest of Edge Clients. Members shows what the links and the member lists said (ids, versions, addresses, a refusal's text), escaped as any value. Ping on a member row (`ping#EdgeClient` with `instanceId`) is a Ping down that member's own down connection, fenced by its generation. Approve, Forget key, Let it link again (`clear#EdgeTakeover`), New nodes (`hold#NewMembers`) and Deliver again write the pairing's row or queue, and refuse a pairing that is not one and on a node that takes no links (`instance@node-role` as it is now); Forget key, the hold and Deliver again are logged. A forgotten key is kept as forgotten for its id (`pool::forget_key`), so the id's next link is a new node's: never the last member or a kept list's member coming back, so a takeover with its notice, or held for approval. With the HTTPS listener off, the screens show the rows and the defaults, and what is in memory (members, balancing) is read in probes of its own. On a member, `get#LocalCluster` reads its own cluster's rows and `drain#EdgeMember` with no pairing drains itself (its `InstanceDrain` row); neither reaches the edge node beyond the state its links already tell.
- **Edge clusters: a local node links to every edge member** ([plan](../../plans/Edge-Node2.md) §4.6, E18). The members of an edge cluster share one database, and with it the `SecretValue` row of `edge@link-key`, so they present the one link key a local node pinned at pairing (`edge/node@pin`, the SHA-256 of the public key, checked on every connection with the handshake's signature). Each member's answer to Hello and to every Ping lists the cluster's live members (`HelloReply.edge_members`, `PingReply.edge_members`: instance id and `edge@link-url`, from the `ClusterMember` rows by the heartbeat's liveness window, in id order; read at most every 2 seconds), and the local node dials each one.
  - **The list is input** from a linked edge member: at most 64 members, each id a node id (at most 40 characters, no space, control character or `@`) named once, each address empty or an `https` URL with a host of at most 512 characters; a list that fails is not taken whole, and an empty one changes nothing. A member with no address is reached only at the URL the node paired with. An edge member that is not trusted can therefore make its local nodes open a TLS connection to at most 64 addresses of its choosing, where nothing past the ClientHello is sent unless the far end proves the pinned link key (TLS 1.3 sends the client certificate only after the server's is verified); it can already do more with the link itself.
  - **Each member's identity.** A link dialed for a member of the list must reach that member: a Hello naming another id fails the link ("its edge@link-url reaches another member", tried again with the usual backoff, at once when a list changes the address), so a stale or wrong address cannot put one member's link on another. On a link to the URL the node paired with, any id is taken, as every member holds the pinned key, and is learned then: `edge/node@id` becomes the set of the edge members' ids (in memory, beside the one pairing wrote to `runtime/.env`), which is what a web protection ban goes up to (one ban to each edge member, as each keeps its own). An id the local node has a use for is refused on any link: its own, any member of its own cluster (a `ClusterMember` row, live or not, so an offline member's call signaling cannot be routed to the edge node), and a media node of its own (a `CallMediaNode` row the edge link did not write). Lists are compared by instance id, and a member is in its own list only while its own row is live, so every member answers the same list.
  - **What is kept** (`runtime/db/edge_members`, this machine's file, as `edge_member_key` is): the latest list and the ids learned, with the pairing's URL and pin; a file for another pairing is not used, one that fails the list's checks is dropped, and unpairing or pairing again removes it. It holds no secret.
  - **Work.** The edge members' calls (requests, delegate, queue delivery, PASS) are taken on each link, fenced by that link's generation, and items are claimed by lease in the edge cluster's database, so each is applied once. The local node's own work goes up one link at a time (its outbox, its replicated sets with the sender lock, the edge node's call rows), so nothing is sent once per edge member; call signaling has a route per edge member, to the member whose media holds the call.
  - **Admission across the edge cluster** (E18 part B). Each edge member keeps the links it holds in memory, so "a member is linked" would mean linked to that edge member only: a copy of the pairing's shared key dialing an edge member that has no link of the pairing (one just restarted) would be taken as a takeover by the key alone while a real member is linked to another edge member, and could displace it. Each edge member therefore keeps one row (`moqui.edge.EdgeMemberLinks`: its id, the local members it holds links of by pairing, a heartbeat by the database's clock), written in the transaction that locks the pairing's row as it admits a link, and every 5 seconds while another member of its cluster is live (by the heartbeat, else by the member rows), removed when it stops and pruned after a day; admission reads the rows at every admission and counts a local member as linked when another edge member's row naming it is under 20 seconds old. A member linked elsewhere is admitted as another of its links only with the key pinned for its id; with another key, or a forgotten pin, it is refused while that member is linked (forgetting a key closes that member's links everywhere). A node linked nowhere while another is linked anywhere needs a linked member's list as before (asked down a link of that edge member, else its latest list; none there refuses it, and it links once another member's link brings a list). While a live edge member with an `edge@link-url` has no fresh row (it has not written since another member came up), no node takes the pairing over (refused, retryable), so it cannot displace a member linked there. Two edge members admitting at once are ordered by the pairing's row lock: the second reads the first's row again within that lock, so a node dialing both is one takeover, and a takeover decided before another member linked elsewhere is refused to dial again. A failure to read the rows refuses the link (it retries).
  - **Revocation and the in-memory state on every member** (E18 part B). What one edge member does to a pairing's links reaches the others on the cluster topic `edge-state` (`moqui_core::edge::cluster_state`): a revoke (System › Edge Clients) or a node's Unpair closes its links on every member and refuses them there, pairing again lifts that and closes the old key's links, and a forgotten member key closes that member's link everywhere. Two checks stand behind it, for a member that missed the notice: every link checks that its key is active when it opens, and every 5 seconds, while another member of its cluster is live, each edge member reads the pairings it holds links of and closes the links of one no longer active and of a member whose pinned key is forgotten or another (also at once after its cluster transport reconnected). The same topic carries a change of the host table (host names, pairings, a Configure's PASS sites, chat bridges and XMPP domains) and of the replicated copies (a batch applied, a conflict recheck), so each member answers what the database says within moments; a member that may have missed notices (its cluster transport reconnected) loads both again. The body is `{"from", "hosts", "sets", "links"}`, from a cluster member only (the cluster transport's own authentication), at most 64 sets and 64 link operations, each name at most 255 characters; it only makes a member read the shared rows again or close links, never carries data to trust.
  - **Per member, as in any cluster:** pairing tries (`Pair` by source), web protection's counts (bans are shared since E17), the SIP registrar's nonces and their counts, and the voicemail fallback's forward counts, so each limit holds per member and an edge cluster of n members allows up to n times it. The nonce's MAC key is each member's own, random at start: a nonce from another member is challenged again (one failed answer counted at the phone's source), as sharing the key would let an answer captured at one member be replayed at another, whose counts never saw it. A chat webhook repeated to another member is one queue item by its event's idempotency key, and a replay there by the `moqui.security.SignatureReplay` rows every member shares.
  - **SIP trunks** register from one member at a time, the holder of the lock row `EdgeSenderLock` `sipTrunks` (30-second lease by the database's clock), so a provider's account is not registered from two contacts; a holder whose claims fail stops registering after two thirds of its lease. The local node keeps a `CallMediaNode` and `SipNode` row and the TURN secret for each edge member from its own link (at most 64), forgotten for a member gone from the edge cluster's list and all at unpairing.
  - **The screens** (E18 part C, [plan](../../plans/Edge-Node2.md) §4.10): System › Edge Clients › Edge cluster on a node that takes links, and the Edge cluster box of System › Edge Node on a local node, the System app's as the rest of Edge Clients. Both are read only. Edge cluster lists this node's own cluster from its `ClusterMember` rows (`get#EdgeCluster`, refused on a node that takes no links; with the HTTPS listener off it reads the rows and this node's `edge@link-url` itself), with each member's id, link address (and whether it is one the Hello answer sends, by the one check `moqui_core::edge::cluster_list::usable_link_url` the answer uses), heartbeat and version, and the member that holds the `sipTrunks` lock row; nothing there is secret, and each value is escaped. The box on a local node shows `get#LinkStatus`'s `edgeMemberList`: each edge member's id and address as its list said, the link's state, round trip and last error, which link carries the work. A member's address is the `edgeLinkUrl` of its `ClusterMember` row, which the member writes from its own `edge@link-url`; no Edge screen sets it, and a writer of that row can ([The cluster certificate and key](#the-cluster-certificate-and-key)).
- **Front nodes** ([plan](../../plans/Edge-Node2.md) §4.3, §4.7, E19): the front option set alone (`moqui_conf__instance__node_role=front`), before a local cluster (`conf/front`) or an edge cluster (`conf/full-stack`), and the nodes that dial it. What a front can see: in terminate mode the sites' content and their certificates, never a passthrough name's or a link name's content, and none of the mail it passes when the sender uses STARTTLS (it relays the bytes: plain SMTP passes in clear, and a compromised front could strip the STARTTLS offer, which MTA-STS for the domains guards against); it holds no business data.
  - **The front node** ([plan](../../plans/Edge-Node2.md) §4.7, E19, `moqui_conf__instance__node_role=front`): the front set alone. It starts no call media, TURN, SIP, SMTP listener, MX delivery or XMPP server, even with their ports set (each logged and shown off in the startup report), keeps no queue, and dials no other node. Its Hello names its role and offers web access and ports only; on its links it refuses a queued item, its content, a replication batch and call signaling (`Link.Deliver`, `Link.PutContent`, `Link.Replicate` answer "this is a front node"; `Link.Signal` takes a web protection ban only), sends no queued item or delegated call down, gives no PASS call to a pairing, and refuses a Configure's mail domains, chat bridges, PASS sites and SIP domain by name. In terminate mode it sees the content of the sites it ends, and holds their certificates; it holds no business data.
  - **A node's front pairing** ([plan](../../plans/Edge-Node2.md) §4.7, E19): a second pairing, `edge/front-node@url`, `edge/front-node@pin` and `edge/front-node@id` in `runtime/.env` and `edge/front-node@key` in the seal's store (a secret, `conf_env::keep_in_env`), beside any `edge_node_*`, with the same key pinning both ways, member key and member list (kept apart in `runtime/db/front_members`). Pairing keeps it there when the node's Hello names the role `front`; a link whose node names another role than its pairing expects is refused, so a front cannot be reached on an edge pairing or the reverse. A front pairing's links carry web access and ports only: no outbox, replicated set, call or SIP row or TURN secret goes up them, and the down connection takes no queued item, delegated call or PASS call (its `LocalLink` calls of the queue, content, delegation and signal answer unavailable, and the PASS authority is not served on it; `LocalLink.Drain`, `Members` and `Ping` are served on it as on an edge pairing's, so a front node can drain the members linked to it); the queue's pairing id is the edge pairing's. A web protection ban goes up to the front's ids too. With both pairings each hears every Configure, both sent at once: the host names and XMPP domain to the front, the rest to the edge pairing, and a part one did not take is answered item by item with why. A Configure that sets the host names clears them on the edge pairing, so an edge node with the front set does not forward them to the same front as well. The Pair screens show the node's role before pairing, since the pairing goes where it says.
  - **An edge node that dials** (`front_edge`, `edge`, `all-in-one`) pairs with a front node only: its role is read from the front's Probe answer before the code is spent, and anything else is refused. Its own `webapp-list/webapp[webroot]@http-host` and link address are not given (an all-in-one node gives its `webapp-list/webapp[webroot]@http-host` too, as a terminate host: it is a full server's app). ### Pairing: the code and what each side checks

**Probe is anonymous.** Any client that offers ALPN `moqui-edge-pair/1` to an edge node's HTTPS port and sends the role byte `C` may call `Link.Probe` with no certificate. The answer is the node's Hello and its link key fingerprint: the binary version, the link version, the built features, the capabilities, the public names, the instance id, the node name, `instance@node-role`, the media address and TURN URLs, and the SIP addresses, domain and registrar flag (`hello()` in `crates/moqui-host/src/edge_link/accept.rs`). The connection holds a web protection connection slot, within the 30 seconds, 4 calls and 2 streams of the `moqui-edge-pair/1` item above.

**The code.** A pairing code is 12 letters of a 32-letter alphabet (60 bits; no `0`, `O`, `1` or `I`) from the TLS provider's random source, shown as three groups of four (`crates/moqui-host/src/edge_link/store.rs`). Dashes, spaces and case are ignored. Only `single_use_hash` of it is kept: the conf's simple hash with the fixed single-use salt. `org.moqui.edge.EdgeServices.create#PairingCode` takes `validMinutes` from 1 to 1440, default 60. `create#PairingCode` takes `pairedNodeId`, kept as `EdgePairingCode.forNodeId` (the Clients dialog's "For local node"), and `pair_client` pairs only that code's node. `re_pair_refusal` refuses an id active with another key; an id that is revoked, whatever key it brings (its own revoked one too), or that was paired before with another key, pairs only with a code made for it. A new node id with no row is paired by any valid code. A re-pair with a new key clears `setupJson` (PASS sites, chat bridges, XMPP and SIP domain); the id's `EdgeHost` and `EdgePort` rows, replicated copies and queued items are keyed by the id and kept for a re-pair (whether the queued items are then delivered was not read). Every refusal of a code is one message ("the pairing code is unknown, used or expired"). The attempt limit is in the `moqui-edge-pair/1` item above. The wizards keep the code in a session attribute, and session attributes are written to the session row as JSON, not encrypted (`HttpSession.attributes`). On the edge node `newEdgePairingCode` is removed at the next render, so it is in the row only if a flush falls between. On the local node `edgePairingCode` is removed only when pairing succeeds, so after a failed or abandoned pairing it stays in the row until the session ends, for a reader of that table or of a backup within the code's life.

**What the local node checks on the first connection.** The local node checks the edge node's web certificate against the built-in WebPKI roots and the host name of the URL (`crates/moqui-host/src/edge_link/pair.rs`). No switch turns that check off. The link key fingerprint the local node pins is the one the edge node tells inside that connection. An operator may give the fingerprint to expect (`expectFingerprint`), and any other fingerprint then fails the pairing. With none given, whoever holds a valid certificate for that host name receives the code and is pinned. Every later link connection checks the pinned key (`edge/node@pin`, Edge clusters above).

**Revoking.** A pairing is revoked by `revoke#EdgeClient` or by the node's own `Link.Unpair`, which any one admitted member of the pairing (or a node that took it over) may call for the whole pairing. The row turns `EdgeClientRevoked` and its links close. An up connection is admitted only for a key whose row is `EdgeClientActive` (`link_up` in `store.rs`).

### Forwarded requests: the headers removed and set

On the edge node `forward` (`crates/moqui-host/src/edge_link/web.rs`) changes the headers of a request for a terminate host in this order:

1. It removes the hop-by-hop headers and the ones `Connection` names.
2. It removes `forwarded`, `x-forwarded-for`, `x-forwarded-host`, `x-forwarded-port`, `x-forwarded-proto`, `x-real-ip`, `x-moqui-edge-client`, `x-moqui-edge-proto`, `x-moqui-tunnel` and the node's own client-IP header.
3. It removes `Host`.
4. It sets `x-moqui-edge-client` to the client's `ip:port` and `x-moqui-edge-proto` to `https` or `http`.

The client is the edge node's own view (`guard.client_of`): the TCP peer, or a trusted proxy's header. `X-Moqui-Test-Peer` is removed earlier, in `serve_request` (`crates/moqui-host/src/http/serve.rs`), on every server. `x-pass-client-ip` is not removed by any host code. It reaches the member's scripts, which believe it only with a registered PASS client's secret (`org/moqui/public/Account.js`): mr-mantle's `PassApi.js` reads it into `visitorAddress` for every request, and `PassAuthority.js` uses that only for a registered client; otherwise the socket's address is the key. It is a rate-limit key only, and no Rust code reads the header. Only a WebSocket's extended CONNECT (`:protocol` `websocket`) is marked and made again as a CONNECT with that fixed protocol, so a client cannot open a `moqui-tunnel`.

On the member the down connection is the only reader of `x-moqui-edge-*` (`crates/moqui-host/src/edge_link/down.rs`). A request with `x-moqui-edge-client` goes to the app whatever its path. The forwarding headers are removed again. The address the header names becomes both the request's TCP peer (`ConnectInfo`) and its client (`ClientAddr`), with `RequestVia::Edge`. A direct listener neither reads nor removes `x-moqui-edge-*`.

So an edge node names the client address of every forwarded request and tunnel. The member's web protection, limits and logs use that address. The member's rules that treat a loopback peer as this machine do not take one that came through an edge link (the host's `local_peer(peer, via)`, `RequestVia::Edge`): the loopback rule of `/health` and `/metrics`, the rule that takes git and DAV credentials from a loopback client as if over TLS, and the terminal's place; an SSH connection an edge tunnel hands over is marked (`Connection.via_edge`) and placed remote (`Facts::over_ssh(peer, via_edge)`). Web protection's exempt rules and limits still take the address the edge node names: an edge node is trusted to name the client.

A `voicemail` item goes in the box this node's own `PhoneNumber` row routes the item's number to, so one naming a number of the server's is stored in that user's box, with the sender number and name the paired node gives; on a dedicated edge node there is no number and the item is dropped. A `callRecording` item for a recording that exists is refused unless the call's media node is an edge-linked one, which the server's own are not; a recording id that does not exist passes that check and goes to `store#RecordingSegment`. None of these four is named by a screen, a REST resource or a script. `deliver#EdgeMail` runs the delivery with authorization off and takes the `authservId` and `spamHeaders` the item's payload names (`crates/moqui-mail/src/edge_mail.rs`).

### What is replicated to an edge node

Four sets are replicated by default (`<edge><replicate>` in `MoquiDefaultConf.xml`). These are all the fields that cross:

| Set | Entity | Fields |
|---|---|---|
| `mailRecipients` | `moqui.basic.email.EmailAccount` | `emailAddress`, `accountKindEnumId`, `statusId`, `emailServerId`, `quotaFullDate` |
| `mailRecipients` | `moqui.basic.email.EmailIdentity` | `emailAddress`, `emailAccountId` |
| `mailRecipients` | `moqui.basic.email.EmailServer` | `storeHost` |
| `chatBridges` | `moqui.chat.ChatBridge` | `typeEnumId`, `adapterName`, `statusId`, `webhookPublicKey`, `webhookToleranceSeconds` |
| `voiceTrunks` | `moqui.call.VoiceTrunk` | `name`, `host`, `port`, `transportEnumId`, `mediaEncryptionEnumId`, `providerProfileEnumId`, `authJson`, `registerFlag`, `emergencyCapable`, `inboundAddresses`, `fromDomain`, `disabled` |
| `voiceTrunks` | `moqui.call.VoicePolicy` | `internationalEnabled`, `premiumEnabled`, `maxConcurrentCalls`, `authFailureLimit`, `authFailureWindowSeconds`, `authBlockSeconds`, `homeCountryCode`, `emergencyNumbers`, `premiumPrefixes` |
| `voiceTrunks` | `moqui.call.PhoneNumber` | `voiceTrunkId` |
| `voiceFallbacks` | `moqui.call.PhoneNumberFallback` | `voiceTrunkId`, `voicemailFlag`, `greetingLocation`, `forwardNumber`, `forwardSeconds`, `forwardMaxConcurrent`, `forwardMaxPerDay` |

The only credential among them is `VoiceTrunk.authJson`. It is encrypted on the local node (`encrypt="true"`), sent as the entity facade reads it, which is decrypted (the sender serializes what an ordinary find with authorization off returns), so it crosses in clear inside the link's TLS, and kept on the edge node in `EdgeReplicaValue.fieldsJson` (`encrypt="true"`, as `pkJson` is). No chat bridge secret, API key or inbound token is replicated.

Replication is one way. There is no call by which an edge node writes a replicated record back, and the edge node's copies are read only there. `get#ReplicaValues` on the edge node returns each record's fields decrypted, `authJson` included, to a caller authorized for it; it has no check in its body. No screen, REST resource or data grant names it.

The receiving side of `Link.Replicate` has these bounds only: the link's key and generation, the 16 MiB message, and the pool's sender-lock check on the set's cursor. Before it applies a batch the edge node refuses one with more than 500 records (where the sender splits), a set its own `<replicate>` conf does not name, or an entity that set does not have (`replica::batch_refused`, SEC-CLU-02). `apply_batch_rows` (`crates/moqui-core/src/edge/replica.rs`) then writes one `EdgeReplicaValue` row for each change, held to `replica-max-rows` for the pairing (`caps::admit_batch`). The cap is a count of rows: neither check looks at the size of a record's `fieldsJson` or at its field names, so a record may be as large as the 16 MiB message allows (`apply_batch_rows` past its head was not read). The count is read before the batch is applied, outside its transaction, so batches sent at once each pass against the same count.

### Received queue content and receipts

`PutContent` (`Link.PutContent` and `LocalLink.PutContent`) keeps each upload at `dbresource://moqui/edge/content/in/<node>/<item id>.<uuid>`, at most 64 MiB a call, in a transaction of its own (`crates/moqui-core/src/edge/queue.rs`). The node and the item id are one path segment each (letters, digits, `-`, `_`, `.`). Each call gets a new name. `read_content` takes a call in this order (`crates/moqui-host/src/edge_link/queue.rs`): a permit, at most `edge@content-calls` (4) calls of a pairing at once (`content_permit`; past them `unavailable`, which the sender takes as no answer, not counted); the first chunk; the pairing's cap asked about the size it names (`caps::admit_content`); then the chunks, none of another item and none past the named size, with at most 1 MiB reserved ahead. Each chunk must come within `edge@forward-idle-seconds` and the whole call within `edge@content-call-seconds` (900). A delivery may name only a location under its own item's prefix. The content is removed when its delivery is answered. Content with no delivery stays until the retention pass (`queue-retention-days`, 14). Received content counts against the pairing's queue cap and `queue-max-content-files` on the edge node, which pauses the pairing at a cap (Delegated calls, queue and replication above); a local node refuses, logged and told to its administrators, content past its own caps. Each applied item leaves one `EdgeReceipt` row for the same period. The receiver does not check a delivered item's payload size: the 1 MiB limit is the sender's at enqueue, and the message limit is 16 MiB. `EdgeQueueItem.payload` and an item's content under `dbresource://moqui/edge/content/` are not field-encrypted.

### What a local node takes from its edge node besides requests

Beyond forwarded requests, tunnels, delegated calls and queued items, a local node acts on these values an edge node sends:

- `LocalLink.Drain` sets or clears the member's own drain, so `/health` answers 503 (Pools above). An edge node can therefore drain the members linked to it, and so can a front node on a front pairing's link, which serves `Drain`, `Members` and `Ping` too.
- `LocalLink.PutContent` stores content as in the section above.
- The Hello's instance id is written to `runtime/.env` as `edge/node@id`. Its media address, TURN URLs, SIP addresses and TURN secret go into the `CallMediaNode` and `SipNode` rows and memory.
- The edge member list names up to 64 addresses the node dials (Edge clusters above).
- At the wizard's Apply (`apply#EdgeSetup`, an administrator's step) the offer's chat address is written to `.env` as `channels@public-url` (an `http` or `https` URL), and the offer's PASS client id names the properties `edge/node@pass-client`, `pass-authority/client[<id>]@sites` and `pass-authority/client[<id>]@callback` written there (`crates/moqui-core/src/edge/setup.rs`). The id is checked for its syntax (1 to 63 letters, digits, `_` and `-`, no `.`; empty is `edge`), and Apply refuses an id whose `pass-authority/client[<id>]@secret` is set, since the link never has a secret (a direct client named `edge` while `edge/node@pass-client` is unset included), and an id with sites unless it is already the edge node's client (`client_taken`); the review step names the id with the sites and the callback. The names written always end in `_sites` or `_callback`, so no other property is hit. This code's own edge node always offers `edge`. The `.env` writer refuses a value with a line break (`crates/moqui-lib/src/env.rs`).

## Manager link

A manager's HTTPS listener takes ALPN `moqui-manage/1` in a binary with the `manage` and `instances` features (Maximal,
Enterprise), when it is not an edge node (an edge node's listener reads the ClientHello for the edge link and takes no
manager link). Every build with `manage` (all packages) dials it as a managed instance when `manage@url` is set or it
paired. `crates/moqui-host/src/manage_link/`, [Run-Deploy, The manager link](../Run-Deploy.md#the-manager-link),
plans/Vault-Instances.md §4.4.

- **`moqui-manage/1`** on the manager: the manager presents a certificate from its link key (`runtime/db/manage_link_key`,
  mode 0600, or a `systemd-creds` credential) and requires a client certificate; any key passes the handshake, which
  proves its possession, and is looked up after it. The listener reads each ClientHello before choosing settings
  (`link::read_hello`, at most 64 KiB); any other ALPN gets the listener's own settings and is never asked for a
  certificate, and `acme-tls/1` its challenge answer. The role byte has 10 s.
  - Role `P` (pairing): `Manager.Pair` alone, for 30 s with at most 2 streams; Pair is limited to 10 tries per source
    address in 10 minutes. The secret is a provision's token or a System › Instances code (32 letters and digits from
    the OS's randomness, about 190 bits), kept only as its SHA-256 on the `AppInstance` row with a 15-minute end; the row
    is found by that hash and compared again in constant time, and the hash is cleared at its one use, an expired one
    too. Every refusal is one message. Pairing pins the presented key and the instance's X25519 bundle key on the row,
    replacing a key pinned before (a code is made only by INSTANCE_ADMIN, in the environment's group when it names one).
  - Role `U` (link): the key's SHA-256 must be an `AppInstance.linkKeyFingerprint`, read on a request worker by an
    indexed equality find; an unknown key is refused before any call, and nothing is written. Hello must come within
    10 s. While the instance's last Hello or Status says sealed, only Hello, Status, Bootstrap and Unseal are answered
    (Unseal: "not built", M6); Event and the Serve stream need it unsealed. Each new link of an instance has a higher
    generation and closes the one before. Pair is refused on a link connection.
  - What a holder of a pinned key (a stolen instance disk) can do: report a status and events for that instance, take
    its bootstrap bundle if one is still held (the manager holds it in memory only, until taken, a restart or 15
    minutes), and answer the manager's commands. Under the plan's automatic unseal policy (M6) it would get the root
    key: the limit of the link key the plan names (§4.4). Revoke (`revoke#InstanceLink`) unpins it and closes the link.
- **On the instance** the link opens no listener. It pins the manager's key from `manage@pin` (a provision's setting, or
  what a code is shown with); a manager that presents another key is refused before any secret is sent. The manager's
  commands run as the link's one identity and only these: status, seal, restart, drain, undrain, put-secret (the
  operator's rules: the crypt pass only with force), deploy-component (`deploy#AttestedComponent`, whose attestation
  stands for `COMPONENT_DEPLOY`), export-seal (wrapped values only), surface-report (not built) and a changed approver
  set (taken only when signed by an approver the instance pinned, at a higher version); an unknown command is refused,
  and while sealed only status runs. The bootstrap bundle is HPKE to the pinned bundle key, its instance id as
  associated data, and goes into `seal.json`, never `.env`.
- **What a compromised manager can do** (§4.9): every command above on every instance it manages, including put-secret
  and seal; it cannot change a pinned approver set without an approver's signature, nor read a value an instance does
  not send it. A manager compromised at pairing chooses the approver set the instance pins.
- **SSH transport**: the manager runs `ssh` (`manage@ssh-command`) with `StrictHostKeyChecking=yes` against the host key
  pinned on the row, the key (an `ssh-key` vault item under a lease or machine access) in a file of mode 0600 in a
  directory of its own, removed after; the remote command is `moqui operator` with single-quoted words (a secret name
  with a quote, space or control character is refused), and a secret's value goes on standard input.

## Integration-fix cluster rollout

The compact `collab-update` envelope carries the update once, in `body.frame.update`. Receivers apply that update before broadcasting the frame to local editors. Incoming notification socket messages are capped at 16 MiB, and a collaboration update whose complete cluster envelope exceeds that limit is refused before local application or acknowledgement.

Upgrade and restart every member together, with collaborative editing stopped until all members run the new version. Mixed versions are unsupported for this wire-format change; older receivers expect a second top-level update and HTTPS receivers still enforce 1 MiB. No database migration is required.
