# Attack surface: cluster and edge node

The cluster transport between members, and the edge node with its link. The gRPC listener and the PASS authority's gRPC service are rows in [Attack-Surface-Routes.md](Attack-Surface-Routes.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## Cluster

The cluster listener is separate from the public HTTP and HTTPS listeners. Public routes do not ask for a client certificate.

On whenever the process starts listeners (a normal `moqui` with no command, and `moqui tui --serve`). Empty `cluster_https_port` is **8444**. Empty `cluster_bind_address` is **0.0.0.0**. `0` is ephemeral. Commands that do not serve do not start it. The default is 8444 (`crates/moqui-host/src/cluster_edge/mod.rs`). No example conf under `runtime/conf` sets `cluster_bind_address`, and `MoquiDevConf.xml` does not, so `./moq run` binds 8444 on every interface.

A TLS client certificate is mandatory. The verifier accepts only a certificate whose SHA-256 matches this member's `cluster_tls_cert`, and the handshake signature must verify, so the certificate without `cluster_tls_key` is not enough. The verifier does not check the certificate's validity dates or the host name (`crates/moqui-host/src/tls_pin.rs`). The server presents that same certificate. The handshake must finish within 10 seconds. There is no HTTP login and no public app routing. ALPN picks the protocol: `h2` (offered unless `cluster_protocol=rest`) serves only the gRPC `moqui.cluster.v1.Cluster.Post`, a batch of the same messages with a status for each, decoded up to 17 MiB, at most 64 streams per connection, with HTTP/2 PINGs and a connection idle for 60 seconds closed; `http/1.1`, or no ALPN, serves only `POST /cluster/{topic}` for one of the twelve bus topics (`moqui_core::notify::TOPICS`): `entity-cache-invalidate`, `notification-message`, `collab-update`, `calc-update`, `calc-presence`, `session-end`, `rtc-signal`, `runtime-settings`, `component-deploy`, `edge-replica-note`, `web-ban` or `edge-state`. `edge-replica-note` carries a member's replication notes (entity names and record keys only), which only the member holding the sender lock keeps; `web-ban` is in [Web protection](Attack-Surface-Web.md#web-protection). The body must be JSON with `origin_id` and `message_id`, or the answer is 400. An unknown topic or method is 404. The serialized JSON envelope limit is 16 MiB on HTTPS, SSH and Postgres NOTIFY (including payloads kept in `ClusterMessage`). Oversized messages are refused before fan-out. A 4xx response refuses that message without retrying or marking the peer down. At most 64 connections from addresses that are not members', at most 8 of them from one source (an IPv6 /64 is one), and 64 more for the members' addresses: those the hosts of the `ClusterMember` rows' `clusterBaseUrl` resolve to, read every 30 seconds. A connection past its slot is closed. Cache clears that entity's one-cache. `session-end` drops this process's live copies of the named session ids. Notification and collab messages are published on the local bus and are not fanned out again. `rtc-signal` is sent to one member (`cluster::send_to`, one try from a queue of 1,024 that refuses when full): a call's signaling frames for the node holding its media, its replies for the node holding a leg's socket, the call services' close messages, and the voice services' SIP control (kind `sip`, for the node's SIP engine); a receiver drops one whose `target` is not its instance id (the notify transport reaches every notify member).

An unauthenticated connection to the cluster port reaches the TCP accept, a connection slot and the TLS handshake, nothing else. No HTTP is read before the certificate check. After the handshake the limits are an HTTP/1.1 head of at most 16 KiB, a body of at most 16 MiB (413 above it) read within 10 seconds, and on HTTP/2 a header list of at most 16 KiB (`crates/moqui-host/src/cluster_edge/listen.rs`).

Postgres `LISTEN moqui_cluster` is off unless `cluster_transport=notify`. It needs a Postgres entity database. MySQL refuses startup. It is one connection outside the pool, not a new TCP port. The payload is not authenticated on its own. A payload over 7,900 bytes is a `ClusterMessage` row id. A notification missed while `LISTEN` is down is lost. Reconnect then clears entity caches. The default `cluster_transport` is empty, which means the cluster port at `cluster_base_url` (gRPC, or the HTTP/1.1 POST).

### The cluster certificate and key

`cluster_tls_cert` and `cluster_tls_key` ship as `CHANGEME`. With both still `CHANGEME`, startup makes one self-signed pair (common name `moqui-cluster`, valid 10 years) and appends both to `runtime/.env`. One set without the other stops the start. Members share the pair by copying `.env`.

`cluster::start` (`crates/moqui-core/src/cluster/mod.rs`) writes this member's `moqui.server.ClusterMember` row with `sessionKeyFingerprint` (SHA-256 hex of `session_cookie_key`, no salt) and `certFingerprint` (SHA-256 hex of the certificate). It refuses to start when a live member's row has another value of either. The comparison runs at start only, against rows whose heartbeat is live. An empty `cluster_base_url` is `https://127.0.0.1:8444`.

### Where a member sends, and the SSH channel

A sender posts every topic to the `clusterBaseUrl` of each live `ClusterMember` row other than its own (`live_peer_urls`), and `send_to` likewise (`direct::member_url`), only when the row's `certFingerprint` and `sessionKeyFingerprint` are its own (`cluster::same_material`); a row with others is left out with a warning. Whoever can write a `ClusterMember` row can copy the fingerprints, so this keeps out a row of another cluster's material, not a writer of the table. For an `https://` row the receiver must present the pinned cluster certificate. For an `ssh://` row the host key the sender pins is the `sshHostKeyFingerprint` of that same row, which a writer of the table chooses; so before any frame on a `cluster <topic>` channel each side proves the cluster material: the server challenges, the connecting member signs the challenge and a nonce of its own, and the server signs both back, each with an Ed25519 key derived from `cluster_tls_key`, bound to the server's host key fingerprint (`ssh::cluster::prove_server`, `prove_client`). A host named by a row without the cluster material gets no message, and a peer that cannot sign is refused (`403`, logged) before its first frame is read. The host key is unchanged (`crates/moqui-host/src/ssh/cluster.rs`).

A member sends over SSH only to a peer whose base URL is `ssh://`. The receiving side takes a login as `moqui-cluster` with the key derived from `cluster_tls_key`, and applies its `cluster <topic>` channels, only when this member takes the SSH channel (`cluster_transport=ssh` or a `cluster_base_url` of `ssh://`), not through an edge node's SSH tunnel, and from an address a member's `clusterBaseUrl` resolves to (`ssh::cluster::login_refused`, `cluster_edge::member_addresses`; a refusal is logged). The SSH server itself is in [Attack-Surface-SSH.md](Attack-Surface-SSH.md).

### What a holder of the cluster certificate can do

A holder of the cluster certificate and its key can post on any of the twelve topics by the cluster port, and with the key alone by the SSH channel. With `cluster_transport=notify` the same messages arrive by `NOTIFY` on the shared database, which asks for no certificate. A peer's message is applied by `moqui_core::cluster::apply_remote`, which clears caches for `entity-cache-invalidate` and publishes the message on the local bus. The transport itself calls no service and no script. What follows is each topic's subscriber:

- `entity-cache-invalidate`: that entity's caches are cleared. A body with `clearAll` clears every list cache and retires sessions whose rows are gone.
- `notification-message`: the body, less `routeUserIds`, is sent as JSON text to the open `/notws` sockets of the users the body names that follow its `topic`, and to a TUI link of such a user (`fan_out_notice` in `crates/moqui-host/src/notws.rs`). The web shell shows `title` as text in a toast and in the notification history, and as the title of a desktop notification. `link` is followed when the user clicks, by `moqui.openLink` or `window.open`, with no check of its scheme (`WebrootVue.qvt.js`, `MoquiLib.js`).
- `collab-update`, `calc-update`, `calc-presence`: the co-editing rooms take them.
- `session-end`: this process's live copies of the named sessions are dropped.
- `rtc-signal`: the call media driver, and for kind `sip` the SIP engine.
- `runtime-settings`: a timed override of a logging or telemetry setting from the catalog, for at most 24 hours (`crates/moqui-core/src/live_settings/mod.rs`).
- `component-deploy`: the member writes the files of the commit the message names (`to`) of a component kept in a database repository, and loads or reloads the component (`apply_remote` in `crates/moqui-devkit/src/deploy/git.rs`). `gate_remote` is the only check. With `component-deploy`'s `require-passed-run` false (the default) it asks for no attestation, so any commit of that repository is taken. This is the one topic that leads to code being run ([who can author code that runs](Attack-Surface-Scripts.md#who-can-author-code-that-runs)).
- `web-ban`: a ban or a lift of a client address, taken only when the body's `from` is a live member row (`crates/moqui-host/src/guard_share.rs`).
- `edge-state`: the host table and the replicated copies are read again, or links are closed (Edge clusters below).
- `edge-replica-note`: replication notes, as above.

## Edge node

Off unless `node_role` is set (`front`, `front_edge`, `edge` or `all-in-one`) and the HTTPS listener runs, and only in a binary with the `edge` feature (Maximal, Enterprise). It is not a port of its own: the edge link shares the public HTTPS listener and tells its connections apart by the ClientHello, which the listener reads before it picks TLS settings (`crates/moqui-host/src/edge_link/`, [plan](../../plans/archive/Edge-Node.md) §5.1, §5.3, §5.8). A local node opens no port; it dials out.

- **`moqui-edge/1`** (the up and down connections): the edge node presents a certificate from its own link key (`edge_link_key`) and asks for a client certificate without requiring it. After the handshake the key's SHA-256 must match an active `moqui.edge.EdgeClient`; a role byte follows, and a down connection must name the live link generation. The handshake to the role byte has 10 s. On up the local node calls the edge node's `Link` gRPC service; on down the edge node calls the local node, which serves only the link's own gRPC and the PASS authority's (on `/moqui.edge.v1.LocalLink/` and `/moqui.pass.v1.PassAuthority/`, with no client named), forwarded requests and tunnels. A revoked key, a stale generation and a version more than one apart are refused.
- **`moqui-edge-pair/1`** (checking and pairing): the web certificate, which the local node checks by WebPKI. A check connection (no client certificate) can only Probe; a pairing connection presents the new key and can Pair with a one-use code (kept as a hash, an hour by default, at most a day). Each connection stays at most 30 s, with at most 4 calls and 2 streams; Pair is limited to 10 tries per source address in 10 minutes (an IPv6 /64 is one source; the table holds at most 10,000 sources). A code does not take over a node that is active with another key. The Probe answer, the code and what each side checks are in [Pairing](#pairing-the-code-and-what-each-side-checks).
- **Any other ALPN** gets the web certificate and is never asked for a client certificate.
- **Terminate hosts** (`moqui.edge.EdgeHost`, mode `EdgeHostTerminate`): a request whose `Host` is one goes down its node's link after the edge node's own web protection; only configured names go, and only to their own node. The edge node removes hop-by-hop headers and every forwarding header a client sent (`Forwarded`, `X-Forwarded-*`, `X-Real-IP`, its client-IP header, `x-moqui-edge-*`), then names the client in `x-moqui-edge-client`. The local node believes that header only on the down connection, removes it and the forwarding headers, and runs its own web protection on that client (each header by name is in [Forwarded requests](#forwarded-requests-the-headers-removed-and-set)). A client's `CONNECT` is answered 405; only a WebSocket, an HTTP/1.1 upgrade or an HTTP/2 extended CONNECT with `:protocol` `websocket`, becomes an extended CONNECT down the link, and the edge node answers the browser 101 or 200 as its protocol has it. While the link is down the edge node answers 503 with an offline page. The member must take the request within 10 seconds; then the request body may not stop moving for `<edge forward-idle-seconds>` (120) and its answer's head must come within `forward-head-seconds` (3600) after the body is all sent, or within `forward-first-byte-seconds` (30) for a GET or HEAD with no body, else 504: an upload answered once it is stored is not cut off, a client that stops sending is, and a GET held by a hung member goes once more to another member and counts toward setting the hung one aside (a first-byte timeout that goes to no other member is not counted; a POST is never sent twice and waits the head wait). The edge node's own `request-timeout` does not apply to a forwarded request: the member applies its own (with git's exemption at a public site's page URL, which the edge node cannot tell). Each wait is at most a day. The edge node sees the content of these requests, which includes the session cookies, passwords and second-factor codes of everyone who signs in through a terminate host, staff included.
- **Passthrough hosts** (mode `EdgeHostPassthrough`): a ClientHello whose server name is one goes down the link unopened, with a PROXY v2 header naming the client; the local node ends TLS with its own certificate, so the edge node sees no content. A ClientHello is at most 64 KiB. While the link is down the connection is closed. A local node reads a PROXY header only on a tunnel from its link, never on a socket, and its web protection admits that address before the TLS handshake. A tunnel names a kind (`https`, `ssh`); the local node picks its own listener and the edge node never names an address. At most 768 tunnels and forwarded WebSockets at once per node.
- **Delegated calls, queue and replication** (the link's gRPC, [plan](../../plans/archive/Edge-Node.md) §5.2): the edge node calls `LocalLink.Delegate` and `LocalLink.Deliver` on the down connection, and the local node calls `Link.Deliver` and `Link.Replicate` on the up connection; each is fenced by the link generation, and none is reachable by a forwarded request (the down connection takes gRPC only under `/moqui.edge.v1.LocalLink/` and `/moqui.pass.v1.PassAuthority/`, and only with no client named, which a forwarded request always has). Every message is at most 16 MiB both ways (tonic's decode and encode limits on both servers and clients); a queued item's payload is at most 1 MiB, refused at enqueue on the sender, and a sender splits a replication batch at 500 records and 4 MiB. The receiving edge node refuses a batch of more than 500 records, of a set its own `<replicate>` conf does not name, or with an entity that set does not have (`edge::replica::batch_refused`), and keeps at most `replica-max-rows` replicated records per pairing (1,000,000, all its sets; or the pairing's `EdgeClient.replicaMaxRows`). The content a pairing's link sends before its deliveries (`PutContent`, kept under `CONTENT_IN<node>/` until each delivery is answered) counts against the pairing's queue cap. At either cap the pairing pauses (`edge::caps`, `EdgeClient.capPausedDate`): its `Replicate` and `PutContent` are refused as unavailable, which the sender tries again (a delivery takes it as the receiver's pause, uncounted), so nothing is dropped, and the administrators get an `EdgePairingPaused` notice; it stays paused until Resume on Edge Clients (`resume#EdgeClient`) or new caps (`update#EdgeClient`). A local node refuses, for now and logged, content its edge node sends past its own queue cap. On the edge node a delegated call is checked first: with the service's definition there, its authorization and `authenticate`; without one, a caller with no user is refused unless the `delegate` entry has `allow-anonymous="true"`. A delegated call runs on the local node only when the service is in the local node's own `<edge><delegate>` list (a compromised edge node could ask for anything), as the user `_EDGE_` (no password, so no login; group `EDGE_DELEGATE`, `UgtRemoteSystems`), with authorization: the `EDGE_DELEGATE` artifact group must grant it; the seed data puts 30 services in it (`echo#Delegate`, the 9 queue handlers and the 20 delegated call and SIP services), each with `inheritAuthz="Y"`. No parameter the edge node sends changes that user: the local node drops `authUsername`, `authPassword`, `authUserAccount`, `authTenantId`, any other `auth` + capital name, every `_` name, and an `edgeCaller` the edge node wrote, then sets `edgeCaller` from the call's caller data (never a login). A queued item runs its kind's handler from the receiver's own `queue-kind` conf, also as `_EDGE_` with authorization, once per item id (`moqui.edge.EdgeReceipt`, inserted before the handler runs); a node enqueues only the kinds it lists. Replication writes only `moqui.edge.EdgeReplicaValue` and `EdgeReplicaCursor` rows of the sending node on the edge node, with the copied fields encrypted at rest; what a compromised local node sends there is data for its own node only. The shipped lists are in [The delegate list](#the-delegate-list-the-queue-kinds-and-what-_edge_-is-granted), the replicated fields in [What is replicated](#what-is-replicated-to-an-edge-node).
- **PASS authority on the link** ([plan](../../plans/archive/Edge-Node.md) §5.5): an edge node's mr-pass (`pass_backend_url=edge:`) calls `moqui.pass.v1.PassAuthority` on the down connection; a forwarded request never reaches it (the same rule as `LocalLink`). With several pairings the call goes to the pairing whose Configure names the call's site (each site has one pairing, the first to name it; one two name is refused), and a site no pairing names goes only to the only active pairing: with more than one paired it is refused, also while one is away, so a pairing's authority never sees the calls of another's sites. The link's mutual TLS is the client's identity, so no secret is sent: the local node names it `pass_edge_client` (default `edge`) and counts it as registered only for the sites in `pass_client_<id>_sites` (for another site it is an unregistered caller: [The authority](Attack-Surface-Apps-PASS.md#the-authority)), with its SSO callback `pass_client_<id>_callback`. Everything else is the direct listener's (the row in Host routes): routed operations only, schema-checked input, a delegation per call, session handles bound to the client and site, the visitor's address as rate-limit data. A compromised edge node can do what a registered PASS server of those sites can: any routed operation and account action, as an anonymous visitor or with the delegations of the visitors who sign in through it (it is their frontend, so it sees their passwords and second-factor codes too), and it can name any visitor address for the rate limits. It cannot use a delegation or session handle made for another client or site, and it reaches no operation the routes do not list.
- **Port 25** (the MTA in moqui, E5b; `conf/edge/MoquiEdgeConf.xml` turns internet mode on, and `smtp_listen_port` in `.env` starts it): the [Mail](Attack-Surface-Mail.md#mail) listener's internet mode. `RCPT TO` is answered from the paired nodes' replicated accounts (`mailRecipients`), never by calling a local node, so an unknown address is refused while a node is away, and a node not yet replicated answers 451. A message is queued for its node, not stored on the edge node beyond the queue's retention. There is no relaying: the edge node sends only what a paired node queued (`mailOut`), DKIM-signed with `mail_dkim_key`, to each recipient domain's MX. A VERP bounce address is taken only for a `mailOut` item the edge node holds the receipt of.
- **LMTP from a gateway beside it** (E5a, instead of port 25): the listener out of internet mode with `protocol="lmtp"` and an allow-list of the gateway's addresses (`127.0.0.1,::1`), as in [Mail](Attack-Surface-Mail.md#mail). Mail out is relayed to the gateway on `edge_mail_relay_port`, on loopback.
- **Chat webhooks and media on the edge node** (E6): the [Host routes](Attack-Surface-Routes.md#host-routes-and-servlets) rows for `/channels/{chatBridgeId}/webhook` and `/media/{token}`. The webhook's signature is checked with the bridge's replicated public key (never its API key, which stays on the local node), and the raw request goes in the queue, applied on the local node without a second check. The bridge is found by its id within the request's host name: at a pairing's own terminate host (where the edge node answers `/channels/{id}/webhook` and `/media/{token}` itself for the bridges that pairing's Configure routes through it, when it takes webhooks) only that pairing's copy and files, and at the edge node's own names the one pairing that has the id; a bridge two pairings have there, or one with no key, is 401. A media address names a file the local node put there (`moqui.edge.EdgeMedia`, by the token's hash), only for that bridge of an active paired node, until its expiry; a file over `channels_edge_media_max_bytes` (5 MiB) or past `channels_edge_media_node_megabytes` (256) of a node's files is refused.
- **Offer and Configure** (the Edge Node wizard, [plan](../../plans/archive/Edge-Node.md) §5.7): on the up connection, fenced by the link generation like the others, a local node asks `Link.GetOffer` (what the edge node offers it, with its own host names; no secret: the DKIM key's public record, public names and addresses) and sends `Link.Configure`. The edge node checks a Configure as input from any client before it changes anything: at most 64 host names, mail domains, bridges and sites each; domains and ids by their syntax; a mode other than passthrough or terminate refuses the whole request. Host names go through the same code as Edge Clients: only the asking node's names change (a name of the node not listed is removed), a name another node holds is refused without naming that node, and the node comes from the link's key, never the request. A local node cannot claim the edge node's own names, which the host table would otherwise route before the edge node's own handling (its admin UI, PASS sites, webhooks, or a certificate for its name): Configure refuses the edge node's public names and `webapp_http_host`, its `smtp_hostname`, `edge_mail_bounce_domain`, the host of its `channels_public_url`, its `public-site` hosts, and the subdomains of each, and any IP address, `localhost` (and its subdomains) and a name with one label. A name the operator adds on Edge Clients is the operator's choice and is not checked against these. Errors other than a refusal of the input go back as one generic message, with the detail in the edge node's log. The rest is kept on its `EdgeClient` row (refused for a node that is not active) for the operator to see. The Test step's checks on the edge node are limited to 20 a minute per node, as each mail-in check reads the node's replicated recipients.
- **Calls** (E7, [plan](../../plans/archive/Edge-Node.md) §5.4): the edge node's media socket and TURN are the [Call media](Attack-Surface-Comms.md#call-media) and [TURN](Attack-Surface-Comms.md#turn) listeners, with the same rules (a relay reaches only the media port). Call signaling crosses the link as `Link.Signal` and `LocalLink.Signal` streams, fenced by the link generation like the other calls, on `rtc-signal`, and a local node's web protection bans up the link on `web-ban` (kind `ban` or `lift`, stamped with the node by the edge node, [Web protection](Attack-Surface-Web.md#web-protection)). Each end takes only what the other may send. A local node takes from its edge node only `reply` messages, and delivers one only to a socket of its own that bound that leg of that call with its media on that edge node (the frame's `callSessionId`, its topic `rtc:<call>`, and `to` or `callLegId`); a frame, control, relay or room frame from the edge node is dropped, so a compromised edge node reaches no other socket and no other call. An edge node takes from a local node only `frame` (whose `origin`, where replies go, must be that node), `control` and `sip`; the link stamps each with the sending node (`linkNode`) and refuses one that already has the field, and the rooms of a paired node's calls are keyed by that node and the call (E12), so a node reaches only its own calls' rooms; the media driver checks a frame's leg and generation as a cluster message's. The edge node's instance id, which these checks and the routes trust, comes from a link whose key is pinned (`edge_node_id`, pinned at pairing, and since E18 the set of an edge cluster's members, each learned on such a link and on a link dialed for a member only that member's, Edge clusters below): a link naming this node's own id or a live member of its own cluster is refused, and the link never takes over a `CallMediaNode` row a media node registered. Each pairing has its own TURN secret (E16, [plan](../../plans/Edge-Node2.md) §4.1), derived from the edge node's `turn_auth_secret`, the pairing's id, its key's fingerprint and when it paired, so a node paired again under the same id gets a new secret and the credentials from before are refused (a node id may not hold `@`, the username's separator); it goes to that local node only in the answer to Hello on an up connection whose key it pinned (not in Probe's Hello), and the local node keeps it in memory. Its credentials name the pairing (`<expiry>:<leg>@<pairing>`) and the TURN server checks them with that pairing's secret only while the pairing is active, so revoking a local node ends its TURN access within a second or two, relays included, with no new `turn_auth_secret`; a pairing's secret makes no credential for another pairing or the server's own legs, and a pairing's leg never has an XMPP user's public relaying ([TURN](../interfaces/TURN.md#on-an-edge-node)). One local node has at most `edge_call_legs_per_pairing` (200) legs on the media node at once. Delegated to the local node: `note#MediaEvent`, `get#CaptionSpeaker`, `store#CallTranscript` (only for a leg of the named call) and `transcribe#CaptionAudio` (only for a participant of the call, `userId` required, a chunk at most 4 MiB); queued: `callRecording`, stored only from the queue's own copy of the item's content and only as `_EDGE_`. Run as `_EDGE_`, each refuses a call whose media node is not the local node's edge node (its `CallMediaNode` row `edgeLinked`). A compromised edge node can see and record the media of calls that are not end-to-end encrypted, write captions, media events and recordings of the calls whose media it holds, and spend their participants' transcription quota.
- **SIP** (E8, [plan](../../plans/archive/Edge-Node.md) §5.4 "Voice (SIP)"): the edge node's SIP listeners, RTP range and registrar are the [SIP](Attack-Surface-Comms.md#sip) ones, with the same flood caps and failed-digest blocks, on the edge node's own; the calls it routes through the local node get the local node's fraud controls there, and the forwards its fallback makes while the local node is away get only the engine's own checks (the destination's class, the deployment's international and premium switches, the calls at once) and the number's limits at once and a day that its replicated fallback row carries; they start only when `.env` sets `sip_port` or `sip_tls_port`. Its trunks come from the replicated set `voiceTrunks` (their `authJson`, encrypted at rest); no phone's verifier is on it: each digest answer goes to the local node's `check#SipDeviceDigest` (the edge node keeps the nonces and their counts, the local node says whether the response is right for its HA1), so a stolen edge database holds no phone's credentials and outside phones sign in only while the local node is reachable. The local node takes such an answer only for the realm the edge node's registrar challenges with, only while its nonce is at most 330 seconds old by the local clock (the time is inside the nonce, which the phone's response covers, so the edge node cannot change it afterwards), and each (phone, nonce, nonce count) once, so an answer the edge node kept cannot be sent again. Delegated to the local node: the routing, leg and trunk notes, the digest check, bindings and device calls, IVR, queue and transfer services, voicemail's begin, PIN, keys and saved audio, and greeting and prompt audio (`get#CallAudio`, only under the greeting and prompt roots); queued: `voicemail` (edge to local, stored only from the queue's own copy, as `_EDGE_`) and `callAudio` (local to edge, kept only under those roots). Run as `_EDGE_`, `receive#PhoneCall` takes calls only for the edge node's own instance id, the call services only calls whose media is on it, the registrar's binding and call services only its own node and a phone whose fresh answer the local node checked within a minute, and voicemail's keys and saved audio only on a call that gave that box's PIN. A message the edge node queues goes in the box the local node chose for the call, or the called number's own, never one the edge node names. While the local node is away the edge node answers from the replicated `voiceFallbacks` (each number's outside number, which a call may be forwarded to through the engine's own fraud checks, and whether it takes a message). A compromised edge node can answer and record calls to the numbers, take messages for them, forward a number's calls to its replicated outside number, and route calls into the local node as from the trunks. It holds the trunks' `authJson`, so it can also register and place calls on the trunks with their credentials. Each delegated call carries how long the edge node waits; the local node starts nothing past it and rolls back a call that ran past it. It cannot sign a phone in or place a call as a user without a fresh answer of that phone, nor read a box's messages without its PIN. With several pairings (E16) each pairing's trunks, calls, legs and phones are keyed by its node: a call goes to the pairing whose copies have the number dialled and a phone to the pairing whose `sip_domain` its realm is, a number or a realm two pairings claim is refused (logged with both), a fallback is read from its owner's copy only, a message is queued to the pairing whose call it was (after a restart too), and each pairing's offer lists only its own trunks.
- **SSH tunnel port**: off unless `edge_ssh_tunnel_port` is set (`edge_ssh_tunnel_host`, empty for every address). The edge node's web protection admits each connection (deny, bans, per-client limit), and refuses one from a client the pairing's own shared ban names once the pairing is known, at most `<edge ssh-tunnels>` (256) at once; each goes down the link to the local node's SSH server, which serves it in process as a connection from the client's address, with its usual logins and limits. It goes to the one active pairing, counted from the pairings, never from the links up: refused while none or several are paired, while that one is away, or when its local node runs no SSH server, so one pairing away never sends its users' SSH connections (and passwords) to another.
- **Ports of one pairing** (E16, [plan](../../plans/Edge-Node2.md) §4.1, §4.10): each `moqui.edge.EdgePort` row is a TCP port the edge node listens on (on `edge_ssh_tunnel_host` for SSH, `edge_smtp_tunnel_host` for SMTP, `edge_xmpp_host` for XMPP; every address while the property is empty) whose connections go down that one pairing's link as an SSH, STARTTLS or direct TLS XMPP tunnel, admitted by web protection (and refused for a client the pairing's shared ban names), at most `<edge ssh-tunnels>` (256, SSH) or 256 (XMPP) at once each, and counted with the link's other tunnels. `add#EdgePort` (System › Edge Clients › Ports) refuses a port of the node's own listeners (set, or unset with that service's usual port; its conf's tunnel ports and the mail relay included), the mail and XMPP federation ports, the SIP RTP and TURN relay ranges, one another row has and a pairing that is not active; a removed row, or one of a revoked pairing (the row stays), closes its port and its connections within seconds. A row names the pairing, never an address, so the edge node is no open proxy.
- **XMPP ports of every domain** (E16): `edge_xmpp_port` and `edge_xmpp_tls_port` take every pairing's XMPP domain. Before a connection goes anywhere the edge node reads its domain: the TLS ClientHello's server name on the direct TLS port, the `to` of the stream header the client sends in the clear on the STARTTLS port (at most 16 KB, within 10 seconds; a start that is neither is dropped). The connection goes down the link of the one pairing whose Configure named that domain, with the bytes read first, and the local node ends the TLS; the edge node reads no stanza and no credential. A domain two pairings name, or a connection naming no pairing's domain (or none) while several are paired, is refused; with one pairing it goes to it, and is refused while it is away, never to another. A client names the domain it wants, so it reaches only that pairing's server, whose TLS and sign-in it must pass.
- **An all-in-one node** (`node_role=all-in-one`, `conf/all-in-one/MoquiAllInOneConf.xml`, [plan](../../plans/archive/Edge-Node.md) §10): a full server with its own users and data that also takes one local node's link, with every rule above. What the paired node's traffic can reach on it:
  - **Delegated calls.** A listed service is sent to the paired node only inside that node's owner scope (`moqui_core::edge::owner::with`, set by the engine that took the item), and to that node; outside it the service runs on the server for the server's own item.
  - **The queue.** A paired node's items run only its kind's handler from the server's own `queue-kind` conf, once per item id, as on an edge node.
  - **Replica rows** are `EdgeReplicaValue` rows of that node, encrypted at rest, read by the engines to route its items. They are never shown to the server's own users: only System › Edge Clients shows them, with the records held back for a claim (`moqui.edge.EdgeReplicaConflict`).
  - **Claims.** The server's own items win: Configure refuses the node's bridges, XMPP and SIP domains, numbers and a mail domain the server holds whole (its bounce domain), naming each, and a replicated record that claims a server's mail address, bridge or number is not applied (kept as a conflict, logged). The server's own setup refuses an item the replica holds (`EdgeClaims.secas.xml`). So a paired node cannot take the server's mail, webhooks, numbers or phones' realm. An address both sides hold gets 451 at `RCPT TO`, and a bridge both hold 409 at its webhook, naming the id; neither side gets it until an operator fixes it.
  - **Calls and SIP.** Each signaling message from the link carries the stamped `linkNode`, and a paired node's rooms, call, leg, trunk and phone ids are keyed by that node (`sip/owners.rs`), so its messages never reach the server's own calls, whose ids come from another database. A phone of the server's `sip_domain` is checked on the server; one of the paired node's domain is delegated to it. The paired node's greetings are kept under `dbresource://moqui/edge-node/<node>/`, apart from the server's.
  - **XMPP.** The server's own XMPP ports read each connection's domain as the tunnel ports do (E16): a paired node's domain goes down its link, any other is the server's own. The tunnel ports, when set, take the server's own domain to its own server too; one equal to one of the server's own XMPP ports is not opened again.
  - **Trust.** The paired node's owner trusts the server's operators as an edge node's: queued mail, messages and recordings are stored on the server until delivered. A compromised paired node can do on the server what it can on an edge node, for its own items only.
- **Several pairings on one edge node** ([plan](../../plans/Edge-Node2.md) §4.1, E16): a dedicated edge node is an all-in-one node with no items of its own, and the pairings are kept apart as the server and its pairing are above. Reasonable isolation for pairings of one organization or related ones, not a defense against a hostile pairing.
  - **Rows.** Every edge row is keyed by its pairing, and each engine takes an item for one pairing: a request by its host name, mail by the recipient's address in that pairing's copies, a webhook by the bridge id within the host name, a PASS call by its site, a delegated call by the owner scope the engine set (outside one, refused while several are paired, linked or not), a queued item by the node it names or the owner scope (else refused, logged). No call made for one pairing reads another's copies.
  - **Claims.** Each host name, mail address, number, XMPP or SIP domain and PASS site has one pairing: the first claim holds. A later Configure is refused the item with only "another node has this name", and a later pairing's replicated record that claims an address or number another pairing holds is not applied, kept as a conflict Edge Clients shows (with the holder), and applied once the first lets it go. An address two pairings' copies still both have (a race, or copies from before) gets 451 at `RCPT TO`. A chat bridge id may be both's: ids come from separate databases, and the host name tells them apart. A mail domain is split between pairings by address, and each pairing's mail out is DKIM-signed only for the domains of its own accounts.
  - **Limits per pairing.** The queue's size cap (`queue-max-megabytes`, or the pairing's `EdgeClient.queueMaxMegabytes`) holds for each pairing alone, so one pairing's backlog fails only its own oldest items; the content it sends and its replicated records (`replica-max-rows`) are capped per pairing too, and a pairing at a cap pauses alone; the MX delivery gives each pairing with mail due an even share of its sessions, holding one back for another pairing, and reads each pairing's rows apart; tunnels and streams per link and MMS files per node were already per pairing.
  - **Shared on purpose:** the edge node's addresses and their mail reputation, the DKIM key and selector, the media and TURN ports, web protection's counts, CPU and bandwidth. A pairing that floods mail through the edge node can hurt the others' reputation; there is no operator per pairing.
  - **The screens** (System › Edge Clients: Clients, Domains, Ports, [plan](../../plans/Edge-Node2.md) §4.10): the System app's, so only its administrators (`SYSTEM_APP`, which the screens' service calls inherit); a direct call to an `org.moqui.edge.EdgeServices` service without that inheritance is refused. The services' `allow-remote="false"` is not the control, as nothing reads that attribute ([services and allow-remote](Attack-Surface-Web.md#services-and-allow-remote)). The menu lists Edge Clients only on a node that takes links (`default-menu-include` reads `node_role`), and the host name, domain, port and queue cap services refuse on any other node. They read and write the rows without the link, so they work while the HTTPS listener is off; a host name change then loads the link's table again. A host name another pairing has is refused with "another node has this name", as in Configure; the operator sees which pairing has it on Domains. What Domains shows of a pairing's setup (its domains, bridges, sites) and its numbers came from that local node and is shown as text, escaped like any other value. A pairing's queue cap is a number of megabytes above 0, or empty for the conf's.
- **Roles** ([plan](../../plans/Edge-Node2.md) §4.3, E17): `node_role` names the option sets. `front_edge` is the edge node as built; `front` (the front set: web access, ports, balancing) and `edge` (the edge set: delegate, queue, replicate, mail, chat, calls, SIP, PASS) take links too. A node offers in its Hello and offer only its own sets, and one without the front set forwards no web access and binds no tunnel port: a host name it holds gets no web front.
- **Pools: every member of a local cluster links** ([plan](../../plans/Edge-Node2.md) §4.4, E17). A pairing is one local node or one cluster of them; each member presents the pairing's key and names its own instance id in its Hello, and the edge node keeps each member's link apart (a member that dials again replaces only its own). What the key is for, the rows and the work, stays the pairing's: the member id is used only to tell the links apart and in Clients.
  - **Admission** is the new trust decision. A member not linked is admitted only when a linked member's cluster member list, asked for down that member's link at that moment (else the latest it sent with its Ping), has it as a live member; otherwise it is refused with "join the cluster first" and the dialer backs off as for any refusal. So a stolen `.env`, or a staging copy on another database with production's `.env`, does not take a pairing's traffic while a real member is linked. With no member linked the key alone admits, which is what lets a standby in; the notice and the approval hold below are its guard.
  - **A member's own key.** The shared key says only which pairing a link is for. Each member also keeps an Ed25519 key of its own in `runtime/db/edge_member_key` (owner-only; beside `runtime/db/instance_id`, not in `.env`, which members and a standby share, nor in the database, which a standby restores), and its Hello signs the TLS connection's exporter value with it. The edge node pins the key's fingerprint for the member's id on its first link (`EdgeClient.memberKeys`, at most 64), claimed in one transaction committed before the link is registered: pinned when none is, kept when it matches, pinned again only on a decided takeover, else refused, so two first links of one id cannot both pin. Past the cap a forgotten marker goes first, then the oldest member that is not linked, the last linked or in the kept member list. A linked id with no key pinned is not replaced within 5 s of its link. The last member with a new key is a takeover from itself: told (or held) as such, displacing no one. `forget#EdgeMember` reads the pins for update and closes that member's link once committed. The key file is written whole to a part file (owner only) and linked into place only where none is; a bad one names itself and what to do. An id named with another key is a new node: refused while a member is linked, a takeover (notice or hold) while none is; `forget#EdgeMember` unpins one. A member that dials again while its link still answers a Ping (1 s) is refused, retryable, so a copy cannot make two links trade places.
  - **The down connection** names the live generation and a 16-byte random token from its up connection's Hello answer (compared in constant time), and is refused while that link's down connection is open: a node that knows a generation cannot take a member's queue, calls, web requests or tunnels.
  - **The node a takeover displaced** (`takeoverFromId`) is refused "taken over", whether or not a member is linked, until `clear#EdgeTakeover`, so a blip of the standby's link or an edge node restart never hands the pairing back to the old copy of the data. Admission is re-checked as the link is registered: two new nodes at once with none linked get one link, the other a retryable refusal.
  - **The member list** (`Link.Hello`, `Link.Ping`, `LocalLink.Members`) is input from a paired node: at most 64 members, each id at most 40 characters with no space, control character or `@`, each named once, a version of at most 40 printable characters; a list that fails is not taken whole, and it is used only for that pairing's admission and report. It is kept in memory only, never in the database. A member's state (starting, live, draining, stopping) comes the same way; an unknown one is logged and ignored. Only a live member gets new work (`EdgeServer::link_of`, and the queue answers an item for a member that is not live "unavailable", not counted).
  - **Drain from the edge node** (`drain#EdgeMember`): `LocalLink.Drain` on the member's own down connection, fenced by its generation; the member sets its own `InstanceDrain` row, so `/health` answers 503 as for the recovery action's drain. An administrator's service, as the rest of Edge Clients.
  - **Balancing** ([plan](../../plans/Edge-Node2.md) §4.4, 17B): each piece of work goes to one member that is linked and live, never outside the pairing it is for. The sticky cookie of a terminate host (the session cookie, `__Host-moqui.session` or else `moqui.session`, or the host's `EdgeHost.stickyCookie`) is client input to the hash: rendezvous hashing (SHA-256 of the member id and the value) only picks among that pairing's own members, so a forged or chosen value can at most aim its own requests at one member, which any client with no cookie reaches in turn anyway; a value over 4 KiB is not hashed (the request goes in turn); the value is never stored or logged, and the cookie is passed on unchanged. The same holds for a PASS sign-in's session handle and a delegated call's conversation, and for the client's address (IPv6 by its /64) on passthrough hosts and tunnels. A member whose work fails or times out `set-aside-failures` times in a row (3) is set aside for `set-aside-seconds` (30); with every member set aside all are tried, so a member cannot be kept from work by failures alone longer than that. A request that fails before any byte of an answer goes once more to another member only when it is a GET or HEAD with no body, or was never sent, so a write is never applied twice. Call signaling: each member's down connection has its own route, `<member>@<pairing>` (`@` is in no node id), and a member's frame must name the member as its origin, so the replies for a leg go only to the member whose socket bound it, never to another member or pairing with an id of the same name. The counts per member (`get#EdgeBalancing`, `moqui.edgelink.*` with the pairing and member) are in memory, bounded by the members.
  - **The takeover notice** ([plan](../../plans/Edge-Node2.md) §4.5): a node with a new instance id admitted with no member linked, that is neither the member last linked nor in the latest member list, takes the pairing over: logged as a warning, noted on the pairing's row (`takeoverDate`, `takeoverFromId`, `takeoverToId`) and sent as a notification (topic `EdgeMemberTakeover`) to the `ADMIN` group. With `holdNewMember=Y` (`hold#NewMembers`) such a node is refused "held for approval" until `approve#EdgeMember` names it (one use), with one notice. A pairing sends at most four takeover or hold notices an hour; more are only logged, so cycling ids does not flood the administrators. Clients shows the nodes refused or held lately (in memory, eight per pairing).
  - **Replication and the outbox from a pool** (17C): one member sends replication and keeps the link's own rows, the holder of `moqui.edge.EdgeSenderLock` (a 30-second lease by the database's clock; a holder whose claim does not come back within two thirds of the lease stops sending by its own clock, and a new link sends nothing before its first claim). Each batch carries when its sender took the lock, and the edge node refuses a batch of a set whose cursor a later sender wrote, so a member that lost the lock cannot cross the new sender's batches. The queue's claim, its answer and its failing passes read each row `FOR UPDATE`, so two members never both deliver one item.
  - **Deliver again since** (`deliver#ItemsAgain`): an administrator's service on the edge node that sets a pairing's delivered items back to pending, from a time on; delivered items are kept for the retention period only, and the local node's receipts, keyed by the pairing (`edge_node_pairing`, the same in every member's `.env`), make an item it has applied do nothing.
  - **The pool's screens** (System › Edge Clients › Clients, Members and Takeovers; System › Edge Node on a member, This node's cluster): the System app's, as the rest of Edge Clients. Members shows what the links and the member lists said (ids, versions, addresses, a refusal's text), escaped as any value. Ping on a member row (`ping#EdgeClient` with `instanceId`) is a Ping down that member's own down connection, fenced by its generation. Approve, Forget key, Let it link again (`clear#EdgeTakeover`), New nodes (`hold#NewMembers`) and Deliver again write the pairing's row or queue, and refuse a pairing that is not one and on a node that takes no links (`node_role` as it is now); Forget key, the hold and Deliver again are logged. A forgotten key is kept as forgotten for its id (`pool::forget_key`), so the id's next link is a new node's: never the last member or a kept list's member coming back, so a takeover with its notice, or held for approval. With the HTTPS listener off, the screens show the rows and the defaults, and what is in memory (members, balancing) is read in probes of its own. On a member, `get#LocalCluster` reads its own cluster's rows and `drain#EdgeMember` with no pairing drains itself (its `InstanceDrain` row); neither reaches the edge node beyond the state its links already tell.
- **Edge clusters: a local node links to every edge member** ([plan](../../plans/Edge-Node2.md) §4.6, E18). The members of an edge cluster share one database and one `.env`, so they present the one link key a local node pinned at pairing (`edge_node_pin`, the SHA-256 of the public key, checked on every connection with the handshake's signature). Each member's answer to Hello and to every Ping lists the cluster's live members (`HelloReply.edge_members`, `PingReply.edge_members`: instance id and `edge_link_url`, from the `ClusterMember` rows by the heartbeat's liveness window, in id order; read at most every 2 seconds), and the local node dials each one.
  - **The list is input** from a linked edge member: at most 64 members, each id a node id (at most 40 characters, no space, control character or `@`) named once, each address empty or an `https` URL with a host of at most 512 characters; a list that fails is not taken whole, and an empty one changes nothing. A member with no address is reached only at the URL the node paired with. An edge member that is not trusted can therefore make its local nodes open a TLS connection to at most 64 addresses of its choosing, where nothing past the ClientHello is sent unless the far end proves the pinned link key (TLS 1.3 sends the client certificate only after the server's is verified); it can already do more with the link itself.
  - **Each member's identity.** A link dialed for a member of the list must reach that member: a Hello naming another id fails the link ("its edge_link_url reaches another member", tried again with the usual backoff, at once when a list changes the address), so a stale or wrong address cannot put one member's link on another. On a link to the URL the node paired with, any id is taken, as every member holds the pinned key, and is learned then: `edge_node_id` becomes the set of the edge members' ids (in memory, beside the one pairing wrote to `runtime/.env`), which is what a web protection ban goes up to (one ban to each edge member, as each keeps its own). An id the local node has a use for is refused on any link: its own, any member of its own cluster (a `ClusterMember` row, live or not, so an offline member's call signaling cannot be routed to the edge node), and a media node of its own (a `CallMediaNode` row the edge link did not write). Lists are compared by instance id, and a member is in its own list only while its own row is live, so every member answers the same list.
  - **What is kept** (`runtime/db/edge_members`, this machine's file, as `edge_member_key` is): the latest list and the ids learned, with the pairing's URL and pin; a file for another pairing is not used, one that fails the list's checks is dropped, and unpairing or pairing again removes it. It holds no secret.
  - **Work.** The edge members' calls (requests, delegate, queue delivery, PASS) are taken on each link, fenced by that link's generation, and items are claimed by lease in the edge cluster's database, so each is applied once. The local node's own work goes up one link at a time (its outbox, its replicated sets with the sender lock, the edge node's call rows), so nothing is sent once per edge member; call signaling has a route per edge member, to the member whose media holds the call.
  - **Admission across the edge cluster** (E18 part B). Each edge member keeps the links it holds in memory, so "a member is linked" would mean linked to that edge member only: a copied `.env` dialing an edge member that has no link of the pairing (one just restarted) would be taken as a takeover by the key alone while a real member is linked to another edge member, and could displace it. Each edge member therefore keeps one row (`moqui.edge.EdgeMemberLinks`: its id, the local members it holds links of by pairing, a heartbeat by the database's clock), written in the transaction that locks the pairing's row as it admits a link, and every 5 seconds while another member of its cluster is live (by the heartbeat, else by the member rows), removed when it stops and pruned after a day; admission reads the rows at every admission and counts a local member as linked when another edge member's row naming it is under 20 seconds old. A member linked elsewhere is admitted as another of its links only with the key pinned for its id; with another key, or a forgotten pin, it is refused while that member is linked (forgetting a key closes that member's links everywhere). A node linked nowhere while another is linked anywhere needs a linked member's list as before (asked down a link of that edge member, else its latest list; none there refuses it, and it links once another member's link brings a list). While a live edge member with an `edge_link_url` has no fresh row (it has not written since another member came up), no node takes the pairing over (refused, retryable), so it cannot displace a member linked there. Two edge members admitting at once are ordered by the pairing's row lock: the second reads the first's row again within that lock, so a node dialing both is one takeover, and a takeover decided before another member linked elsewhere is refused to dial again. A failure to read the rows refuses the link (it retries).
  - **Revocation and the in-memory state on every member** (E18 part B). What one edge member does to a pairing's links reaches the others on the cluster topic `edge-state` (`moqui_core::edge::cluster_state`): a revoke (System › Edge Clients) or a node's Unpair closes its links on every member and refuses them there, pairing again lifts that and closes the old key's links, and a forgotten member key closes that member's link everywhere. Two checks stand behind it, for a member that missed the notice: every link checks that its key is active when it opens, and every 5 seconds, while another member of its cluster is live, each edge member reads the pairings it holds links of and closes the links of one no longer active and of a member whose pinned key is forgotten or another (also at once after its cluster transport reconnected). The same topic carries a change of the host table (host names, pairings, a Configure's PASS sites, chat bridges and XMPP domains) and of the replicated copies (a batch applied, a conflict recheck), so each member answers what the database says within moments; a member that may have missed notices (its cluster transport reconnected) loads both again. The body is `{"from", "hosts", "sets", "links"}`, from a cluster member only (the cluster transport's own authentication), at most 64 sets and 64 link operations, each name at most 255 characters; it only makes a member read the shared rows again or close links, never carries data to trust.
  - **Per member, as in any cluster:** pairing tries (`Pair` by source), web protection's counts (bans are shared since E17), the SIP registrar's nonces and their counts, and the voicemail fallback's forward counts, so each limit holds per member and an edge cluster of n members allows up to n times it. The nonce's MAC key is each member's own, random at start: a nonce from another member is challenged again (one failed answer counted at the phone's source), as sharing the key would let an answer captured at one member be replayed at another, whose counts never saw it. A chat webhook repeated to another member is one queue item by its event's idempotency key (the replay cache is each member's own).
  - **SIP trunks** register from one member at a time, the holder of the lock row `EdgeSenderLock` `sipTrunks` (30-second lease by the database's clock), so a provider's account is not registered from two contacts; a holder whose claims fail stops registering after two thirds of its lease. The local node keeps a `CallMediaNode` and `SipNode` row and the TURN secret for each edge member from its own link (at most 64), forgotten for a member gone from the edge cluster's list and all at unpairing.
  - **The screens** (E18 part C, [plan](../../plans/Edge-Node2.md) §4.10): System › Edge Clients › Edge cluster on a node that takes links, and the Edge cluster box of System › Edge Node on a local node, the System app's as the rest of Edge Clients. Both are read only. Edge cluster lists this node's own cluster from its `ClusterMember` rows (`get#EdgeCluster`, refused on a node that takes no links; with the HTTPS listener off it reads the rows and this node's `edge_link_url` itself), with each member's id, link address (and whether it is one the Hello answer sends, by the one check `moqui_core::edge::cluster_list::usable_link_url` the answer uses), heartbeat and version, and the member that holds the `sipTrunks` lock row; nothing there is secret, and each value is escaped. The box on a local node shows `get#LinkStatus`'s `edgeMemberList`: each edge member's id and address as its list said, the link's state, round trip and last error, which link carries the work. A member's address is set only by that member's own `edge_link_url`, never from a screen.
- **Front nodes** ([plan](../../plans/Edge-Node2.md) §4.3, §4.7, E19): the front option set alone (`node_role=front`), before a local cluster (`conf/front`) or an edge cluster (`conf/full-stack`), and the nodes that dial it. What a front can see: in terminate mode the sites' content and their certificates, never a passthrough name's or a link name's content, and none of the mail it passes when the sender uses STARTTLS (it relays the bytes: plain SMTP passes in clear, and a compromised front could strip the STARTTLS offer, which MTA-STS for the domains guards against); it holds no business data.
  - **The front node** ([plan](../../plans/Edge-Node2.md) §4.7, E19, `node_role=front`): the front set alone. It starts no call media, TURN, SIP, SMTP listener, MX delivery or XMPP server, even with their ports set (each logged and shown off in the startup report), keeps no queue, and dials no other node. Its Hello names its role and offers web access and ports only; on its links it refuses a queued item, its content, a replication batch and call signaling (`Link.Deliver`, `Link.PutContent`, `Link.Replicate` answer "this is a front node"; `Link.Signal` takes a web protection ban only), sends no queued item or delegated call down, gives no PASS call to a pairing, and refuses a Configure's mail domains, chat bridges, PASS sites and SIP domain by name. In terminate mode it sees the content of the sites it ends, and holds their certificates; it holds no business data.
  - **A node's front pairing** ([plan](../../plans/Edge-Node2.md) §4.7, E19): a second pairing, `front_node_url`, `front_node_key`, `front_node_pin` and `front_node_id` in `runtime/.env`, beside any `edge_node_*`, with the same key pinning both ways, member key and member list (kept apart in `runtime/db/front_members`). Pairing keeps it there when the node's Hello names the role `front`; a link whose node names another role than its pairing expects is refused, so a front cannot be reached on an edge pairing or the reverse. A front pairing's links carry web access and ports only: no outbox, replicated set, call or SIP row or TURN secret goes up them, and the down connection takes no queued item, delegated call or PASS call (its `LocalLink` calls of the queue and delegation answer unavailable, and the PASS authority is not served on it); the queue's pairing id is the edge pairing's. A web protection ban goes up to the front's ids too. With both pairings each hears every Configure, both sent at once: the host names and XMPP domain to the front, the rest to the edge pairing, and a part one did not take is answered item by item with why. A Configure that sets the host names clears them on the edge pairing, so an edge node with the front set does not forward them to the same front as well. The Pair screens show the node's role before pairing, since the pairing goes where it says.
  - **An edge node that dials** (`front_edge`, `edge`, `all-in-one`) pairs with a front node only: its role is read from the front's Probe answer before the code is spent, and anything else is refused. Its down connection serves the front's forwarded requests with its own app and web front, so a request for one of its local nodes' terminate hosts goes on down that node's link, with the client the front named (believed only on the authenticated link, as on a local node); a passthrough tunnel from the front is read to its ClientHello, and one whose server name is a passthrough host of a node linked here goes on down that node's link with a new PROXY header naming the same client, after this node's web protection admitted the client; any other is this node's own TLS. It gives the front, by Configure, its sites' and chat address's hosts as terminate hosts and, with the front set, every active pairing's names in their modes; the front checks them as any Configure (claims between its pairings, its own names reserved). A name the front refused (another pairing's) is given again after a minute. Its own `webapp_http_host` and link address are not given (an all-in-one node gives its `webapp_http_host` too, as a terminate host: it is a full server's app). The edge cluster's members share one key, so they are one pairing on the front, admitted by the member list as any pool; and every local node behind a `front_edge` cluster is part of that one pairing there, so what the front holds per pairing (a ban told up for its hosts, rules per host, limits) holds for the edge cluster as a whole, not for each local node behind it.
  - **TCP ports on a front** (E19 part B): an `EdgePort` row of kind `smtp` (port 25 before an edge cluster) is taken only on a front node (`node_role=front`); a node with the edge set refuses one, as it takes mail on its own SMTP listener. On a front the usual ports of the edge set's listeners, which it never starts, are free for a row; its own web ports stay reserved. Each connection is admitted by the front's web protection, then goes down the pairing's link to a member chosen by the client's address, a PROXY v2 header naming the client first, at most 128 at once.
  - **PROXY trust** (E19 part B): the edge member's SMTP listener takes the client from a PROXY header only on a connection that came down its own front link (a link it dialed and pinned; a node without the edge set, a plain local node, takes no SMTP tunnel at all), and checks that client against its allow-list and per-address limits as a direct client's (with a LOCAL header, the client the front named); its own port reads no PROXY header unless `proxy-protocol` is on, so a direct client's header is a command not known. A compromised front can name any client address for that member's mail checks (SPF, limits), as a gateway in `smtp_allowed_addresses` can.
  - **Link names through a front** (E19 part B): each edge member names its own `edge_link_url` in its front link's Hello; the front keeps the host as an `EdgeHost` row in `EdgeHostLinkName` mode with the member's id, the first claim holding (another pairing's name, a host name of the pairing's own and the front's own names, its own `edge_link_url` among them, are refused; a Configure or the System app cannot set or change one). Only a front node (the front set without the edge set) keeps one, and only from a node whose Hello names a role with the edge set. A refused claim is logged on the front only; the member's link goes on without the name. Two members sending one `edge_link_url` take the name from each other, logged as a warning each time. A name no member sends any more stays until removed on Domains, the only cleanup. On a front the listener reads the server name before the ALPN for a link name only, so a local node's link (`moqui-edge/1`, its client certificate) or pairing to it passes through untouched to that member alone, never balanced to another, and is refused while that member is not linked; a connection to a link name that offers no link or ACME ALPN is refused. A link ALPN with any other server name, an ordinary passthrough host's too, is the front's own link, so a pairing that claims a name the front is dialed at cannot take other pairings' links. A link name's tunnels have their own budget of 768 beside the pairing's. The front sees only the ClientHello; the local node still pins the edge cluster's link key end to end, so a front that sent a link name elsewhere gets a failed handshake, not a link. On the edge member a link ALPN in a tunnel down its front link is served as a link to its own listener from the client the front named; any other node takes a link by its ALPN first, as before.
  - **Not through a front:** media, TURN and SIP go to each edge member's own address; nothing tunnels them.
  - **The screens and confs** (E19 part C): System › Edge Clients › Edge cluster's Front node box (`get#EdgeCluster` `frontList`: each front member's address, link state, last error, the front's name and the pinned fingerprint of its link key, no secret) and System › Edge Node's front pairing are read only and the System app's, as the rest of Edge Clients. Unpair front is the existing `unpair#EdgeNode`. `conf/front` and `conf/full-stack` hold no secrets and name the ones that go in `.env`; the front's nightly backup holds its pairings, host names and ACME certificates (their keys encrypted), so a mirror off the host should be sealed. A local cluster's mail through a front's port 25 is the same code as an edge cluster's, with no test of its own yet.
- **The example confs** (`runtime/conf/<topology>/`, E13): they hold no secrets, and each says which go in `.env`.
  `conf/edge/MoquiEdgeConf.xml` and `conf/all-in-one/MoquiAllInOneConf.xml` turn on web protection and the nightly
  backup (`embedded_db_backup_scheduled`), whose archives hold the queued items (mail, messages, recordings) until
  delivered: a mirror off the host should seal them (`mirrorEncrypt`). `conf/pass/MoquiAuthorityConf.xml` exempts the
  PASS servers from web protection by an example private range (`10.0.2.0/24`), to be replaced by theirs.

### Pairing: the code and what each side checks

**Probe is anonymous.** Any client that offers ALPN `moqui-edge-pair/1` to an edge node's HTTPS port and sends the role byte `C` may call `Link.Probe` with no certificate. The answer is the node's Hello and its link key fingerprint: the binary version, the link version, the built features, the capabilities, the public names, the instance id, the node name, `node_role`, the media address and TURN URLs, and the SIP addresses, domain and registrar flag (`hello()` in `crates/moqui-host/src/edge_link/accept.rs`). The connection holds a web protection connection slot, within the 30 seconds, 4 calls and 2 streams of the `moqui-edge-pair/1` item above.

**The code.** A pairing code is 12 letters of a 32-letter alphabet (60 bits; no `0`, `O`, `1` or `I`) from the TLS provider's random source, shown as three groups of four (`crates/moqui-host/src/edge_link/store.rs`). Dashes, spaces and case are ignored. Only `single_use_hash` of it is kept: the conf's simple hash with the fixed single-use salt. `org.moqui.edge.EdgeServices.create#PairingCode` takes `validMinutes` from 1 to 1440, default 60. A code is not bound to a node id: the node that uses it names its own id. A node id that is revoked, or that has no row, is paired by any valid code with any key. A node id that is active with another key is refused. Every refusal of a code is one message ("the pairing code is unknown, used or expired"). The attempt limit is in the `moqui-edge-pair/1` item above.

**What the local node checks on the first connection.** The local node checks the edge node's web certificate against the built-in WebPKI roots and the host name of the URL (`crates/moqui-host/src/edge_link/pair.rs`). No switch turns that check off. The link key fingerprint the local node pins is the one the edge node tells inside that connection. An operator may give the fingerprint to expect (`expectFingerprint`), and any other fingerprint then fails the pairing. With none given, whoever holds a valid certificate for that host name receives the code and is pinned. Every later link connection checks the pinned key (`edge_node_pin`, Edge clusters above).

**Revoking.** A pairing is revoked by `revoke#EdgeClient` or by the node's own `Link.Unpair`. The row turns `EdgeClientRevoked` and its links close. An up connection is admitted only for a key whose row is `EdgeClientActive` (`link_up` in `store.rs`).

### Forwarded requests: the headers removed and set

On the edge node `forward` (`crates/moqui-host/src/edge_link/web.rs`) changes the headers of a request for a terminate host in this order:

1. It removes the hop-by-hop headers and the ones `Connection` names.
2. It removes `forwarded`, `x-forwarded-for`, `x-forwarded-host`, `x-forwarded-port`, `x-forwarded-proto`, `x-real-ip`, `x-moqui-edge-client`, `x-moqui-edge-proto`, `x-moqui-tunnel` and the node's own client-IP header.
3. It removes `Host`.
4. It sets `x-moqui-edge-client` to the client's `ip:port` and `x-moqui-edge-proto` to `https` or `http`.

The client is the edge node's own view (`guard.client_of`): the TCP peer, or a trusted proxy's header. `X-Moqui-Test-Peer` is removed earlier, in `serve_request` (`crates/moqui-host/src/http/serve.rs`), on every server. `x-pass-client-ip` is not removed by any host code. It reaches the member's scripts, which believe it only with a registered PASS client's secret (`org/moqui/public/Account.js`). Only a WebSocket's extended CONNECT (`:protocol` `websocket`) is marked and made again as a CONNECT with that fixed protocol, so a client cannot open a `moqui-tunnel`.

On the member the down connection is the only reader of `x-moqui-edge-*` (`crates/moqui-host/src/edge_link/down.rs`). A request with `x-moqui-edge-client` goes to the app whatever its path. The forwarding headers are removed again. The address the header names becomes both the request's TCP peer (`ConnectInfo`) and its client (`ClientAddr`), with `RequestVia::Edge`. A direct listener neither reads nor removes `x-moqui-edge-*`.

So an edge node names the client address of every forwarded request and tunnel. The member's web protection, limits and logs use that address. The member's rules that treat a loopback peer as this machine do not take one that came through an edge link (`http::local_peer(peer, via)`, `RequestVia::Edge`): the loopback rule of `/health` and `/metrics`, the rule that takes git and DAV credentials from a loopback client as if over TLS, and the terminal's place; an SSH connection an edge tunnel hands over is marked (`Connection.via_edge`) and placed remote (`Facts::over_ssh(peer, via_edge)`). Web protection's exempt rules and limits still take the address the edge node names: an edge node is trusted to name the client.

Replication is one way. There is no call by which an edge node writes a replicated record back, and the edge node's copies are read only there. `get#ReplicaValues` on the edge node returns each record's fields as stored, `authJson` included, to a caller authorized for it. No screen calls it.

The receiving side of `Link.Replicate` has these bounds only: the link's key and generation, the 16 MiB message, and the pool's sender-lock check on the set's cursor. Before it applies a batch the edge node refuses one with more than 500 records (where the sender splits), a set its own `<replicate>` conf does not name, or an entity that set does not have (`replica::batch_refused`, SEC-CLU-02). `apply_batch_rows` (`crates/moqui-core/src/edge/replica.rs`) then writes one `EdgeReplicaValue` row for each change. There is no total of rows or bytes for a pairing.

### Received queue content and receipts

`PutContent` (`Link.PutContent` and `LocalLink.PutContent`) keeps each upload at `dbresource://moqui/edge/content/in/<node>/<item id>.<uuid>`, at most 64 MiB a call, in a transaction of its own (`crates/moqui-core/src/edge/queue.rs`). The node and the item id are one path segment each (letters, digits, `-`, `_`, `.`). Each call gets a new name. A delivery may name only a location under its own item's prefix. The content is removed when its delivery is answered. Content with no delivery stays until the retention pass (`queue-retention-days`, 14). Received content is not counted against the pairing's queue cap. Each applied item leaves one `EdgeReceipt` row for the same period. The receiver does not check a delivered item's payload size: the 1 MiB limit is the sender's at enqueue, and the message limit is 16 MiB. `EdgeQueueItem.payload` and an item's content under `dbresource://moqui/edge/content/` are not field-encrypted.

### What a local node takes from its edge node besides requests

Beyond forwarded requests, tunnels, delegated calls and queued items, a local node acts on these values an edge node sends:

- `LocalLink.Drain` sets or clears the member's own drain, so `/health` answers 503 (Pools above). An edge node can therefore drain the members linked to it.
- `LocalLink.PutContent` stores content as in the section above.
- The Hello's instance id is written to `runtime/.env` as `edge_node_id`. Its media address, TURN URLs, SIP addresses and TURN secret go into the `CallMediaNode` and `SipNode` rows and memory.
- The edge member list names up to 64 addresses the node dials (Edge clusters above).
- At the wizard's Apply (`apply#EdgeSetup`, an administrator's step) the offer's chat address is written to `.env` as `channels_public_url` (an `http` or `https` URL), and the offer's PASS client id names the properties `pass_edge_client`, `pass_client_<id>_sites` and `pass_client_<id>_callback` written there (`crates/moqui-core/src/edge/setup.rs`). The `.env` writer refuses a value with a line break (`crates/moqui-lib/src/env.rs`).

## Integration-fix cluster rollout

The compact `collab-update` envelope carries the update once, in `body.frame.update`. Receivers apply that update before broadcasting the frame to local editors. Incoming notification socket messages are capped at 16 MiB, and a collaboration update whose complete cluster envelope exceeds that limit is refused before local application or acknowledgement.

Upgrade and restart every member together, with collaborative editing stopped until all members run the new version. Mixed versions are unsupported for this wire-format change; older receivers expect a second top-level update and HTTPS receivers still enforce 1 MiB. No database migration is required.
