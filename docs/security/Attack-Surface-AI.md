# Attack surface: LLM, A2A, MCP and Assist

The model facade, A2A, MCP, the OpenAI-compatible gateway, Assist and the agent permissions. This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## LLM, A2A, MCP and Assist

Routes exist when the `llm` feature is compiled. While a protocol is off, its handlers answer 404. `llm-facade` `enabled` is `true`. That element is the model facade. It is not the A2A server, the MCP server, or the gateway. Assist answers 503 when the facade is disabled; `bootstrap` still answers (`docs/ai/Assist.md`).

A user with `EXTERNAL_USER` never holds `AgentUse`, `AgentAdmin`, `AgentAudit`, `LlmGatewayUse`, `A2aServerUse` or `McpServerUse` (`EXTERNAL_WITHHELD` in `crates/moqui-core/src/user/preference.rs`), so that user starts no run and gets no model call. `start_run` (`crates/moqui-llm/src/run/mod.rs`) and `LlmFacade::complete` (`crates/moqui-llm/src/lib.rs`) refuse that user again. `AgentSkillAuthor` is not in the list. The embedding path ([Semantic find](#semantic-find)) does not make the check.

### A2A

Off. `llm-facade/a2a@enabled` is `false`, and `trust-forwarded-headers` is `false`. While it is off, `/a2a` and `GET /.well-known/agent-card.json` answer 404.

From `docs/ai/A2A.md`, with the login in `crates/moqui-llm/src/a2a/mod.rs` `log_in` and the limits in `crates/moqui-host/src/llm/a2a.rs`: a caller needs `A2aServerUse` and `AgentUse`. Credentials are a Bearer login key, an `api_key` or `login_key` header, or Basic with an app password or a login key as the password. The account password is refused (401). Credentials are taken only over TLS, a believed proxy's https, or from a client on this machine (behind a believed proxy, the client it names in `client-ip-header`, never the socket peer). Missing credentials are 401 `WWW-Authenticate: Bearer realm="a2a", Basic realm="a2a"`. No permission is 403. The body max is 4 MiB; the host handler reads the body into memory before the job that authenticates is queued, and the bindings parse it only after the login. A message holds at most 32 parts of 65,536 bytes each (`crates/moqui-llm/src/conf.rs`), against the drawer's 16,000 characters. A message to a working task of the caller's is stored as an input of the run and counts no tarpit hit. Waits and streams are at most 256 on a node (503) and 16 per user (429); the gateway's model calls and the MCP waits count in the same counters (`Open::take(user_id)`). Every request except the public card needs `A2A-Version: 1.0`. OIDC is not built. A new context reaches an agent only when `exposeA2a="Y"` and the surface includes `a2a` (`crates/moqui-llm/src/a2a/ops.rs` `agent_of`). A message with the `contextId` of a conversation of the caller's on the `a2a` surface takes that conversation's agent, and a message to a task takes the task's; `start_task` and `continue_task` check that agent as `agent_of` does, so one that is not exposed, is disabled or no longer serves `a2a` gets the same error (`check_callable`). The seed `assist` agent does not. Writes wait for the human owner. An `LlmApiClient` row of the credential with the `a2a` scope limits what it reaches ([Gateway](#gateway)).

Each A2A, MCP and gateway request runs as a job in an execution context made for it (`crates/moqui-core/src/service/request_pool.rs` `run_work`: `factory.new_context()`, left when the job ends, also on a panic), so the login of `log_in` goes with the job and the next job on the thread starts with no user. The waits and streams that run later make a context of their own with authorization off and no user, and act only on a task or run chosen while the caller was checked.

Credentials over plain HTTP from a client that is not on this machine answer 403 before they are read. The secure test is the host's `http::secure_transport` (TLS, a believed proxy's `X-Forwarded-Proto: https`, or a client on this machine), which A2A, MCP and the gateway share. Behind a believed proxy the client is the address the proxy names in `client-ip-header`, never the loopback socket peer; a request the proxy passes without naming a client is not local. The public card is `Cache-Control: public, max-age=300` with `Vary: Host`. With `llm-facade/a2a@public-url` empty, the card's URLs are built from the request's `Host`, which is checked for its characters only (`crates/moqui-llm/src/a2a/card.rs` `base_url_of`). `X-Forwarded-Host` and `X-Forwarded-Proto` are read only from a believed proxy and only with `trust-forwarded-headers`. The card advertises `streaming`, `pushNotifications` and `extendedAgentCard`. Every task lookup is filtered by the caller's user id and the `a2a` surface (`a2a/ops.rs` `owned`, in front of every read, cancel, subscribe, message and push config); another user's task is "not found". `Part.url` takes only `dbresource://` and is never fetched.

**Push notifications.** An A2A caller may give a push URL on `SendMessage` or through the push config operations. `check_url` in `crates/moqui-llm/src/a2a/push.rs` takes an absolute `http` or `https` URL with no user info or fragment, at most 2000 characters. It is `https` unless `push allow-http` is true or `push allow-hosts` names the host (defaults: `false`, empty). An internal address written in the URL, `localhost` and `*.localhost` are refused unless `allow-hosts` names the host. The server POSTs each task update to the URL from an outbox, with `A2A-Version`, the caller's `token` in `X-A2A-Notification-Token`, the caller's `authentication` as `Authorization: <scheme> <credentials>`, and trace headers; no credential of the server's. A completed task's notification carries the whole answer. The client refuses internal addresses at connect time ([the guard](Attack-Surface-Outbound.md#the-internal-address-guard)), except for a host that `allow-hosts` names: for that host the connect-time guard is off too, on any port. It follows no redirect, connects within 3 seconds, and reads at most 16 KiB of the answer. `push timeout` is 15 seconds and `max-attempts` is 6. A task takes at most 10 configs and a caller at most 50. `token` and `authenticationJson` are encrypted fields of `AgentPushConfig`, and a config's wire object never carries them. A token and credentials are at most 4096 characters with no control character, and the scheme is one word. No operation returns a config's `lastError` or `lastStatus`. A config is read, listed and deleted by task, config id and user. A config lives 7 days (`CONFIG_DAYS`). The push thread runs with authorization off and reads no user: a config goes on delivering after the caller's key or `A2aServerUse` is withdrawn, until its task ends or the 7 days pass. A config stores the base URL of the request that made it, which comes from `Host` when `llm-facade/a2a@public-url` is empty; it is used for the links of later notifications, which go only to that caller's own push URL.

### MCP

Off. `llm-facade/mcp@server-enabled` is `false`, and `trust-forwarded-headers` is `false`. While it is off, `/mcp` and its documents answer 404.

From `docs/ai/MCP.md`, with the checks in `crates/moqui-llm/src/mcp/server.rs` and `crates/moqui-host/src/llm/mcp.rs`: a caller needs `McpServerUse` and `AgentUse`. Credential shapes match A2A, with realm `mcp`. No credentials is 401 JSON-RPC `-31401`. No permission is 403 `-31403`. `server/discover` needs no credentials. The body max is 4 MiB. The transport is `POST /mcp` only; GET and DELETE are 405. The seed agent `mcp` serves `mcp` with `exposeMcp="Y"`. The MCP client cannot approve a write. Public when on, and cached for an hour: `GET /mcp/server-card`, `/mcp/setup`, `/.well-known/mcp.json`, `/.well-known/ai-catalog.json`.

Before the body is read, a present `Origin` that is not this machine, the configured origin or an allowed origin answers 403; the request's own `Host` is not the test. Behind a believed proxy the origin made of `X-Forwarded-Host` is also taken as the server's own, whatever `mcp trust-forwarded-headers` says (`mcp/server.rs`, `crates/moqui-core/src/web/origin.rs` `request_site`), so a proxy that copies `Host` into `X-Forwarded-Host` makes the request's `Host` the test again. A content type other than `application/json` is 415. `MCP-Protocol-Version`, `Mcp-Method` and, for `tools/call`, `Mcp-Name` must match the body, or the answer is 400. Only `server/discover`, `tools/list` and `tools/call` are served. The four public documents carry `Access-Control-Allow-Origin: *` and `Vary: Host, X-Forwarded-Host, X-Forwarded-Proto` (`mcp::server::public_reply`). With `llm-facade/mcp@public-url` empty their URLs are built from the request's `Host` (`crates/moqui-llm/src/mcp/mod.rs` `base_url`). A write waits for its owner: the call answers `input_required` with a `requestState`, an HMAC-SHA256 over the approval, the user, the tool, the digest of the arguments and the expiry (`crates/moqui-llm/src/mcp/state.rs`). The key is `llm-facade/mcp@request-state-key` (base64, 32 bytes or more), else a key derived from `webapp-list/webapp[webroot]/session-config@cookie-key`, else a random key of the process. A state over 4096 bytes is refused. The MAC is compared in constant time, before the version, expiry, user, tool and digest are checked.

**Tools.** `tools/list` and `tools/call` (`crates/moqui-llm/src/mcp/tools.rs`) offer every tool of the MCP agent whose spec has `mcp` and is a read tool: `screen`, `data`, `search`, the exposed services through the lazy tools, and a component's own read tools. A caller who is a Dev AIDE user on a dev instance (`devtools::dev_aide_user`) also gets the dev tools (`artifact`, `source`, `check`; `caps::DEV`). The list is cached per user for `tools-ttl-ms` (300,000), and a call finds its tool in that list. The MCP agent's `AgentToolPolicy` is the server's allowlist. The agent that cannot be read refuses the request; so does a policy that cannot be read (an internal error, `mcp::tools::Ctx::new`), and a policy row whose classification or approval mode cannot be read is a `never` rule for its pattern (`crates/moqui-llm/src/tools/mod.rs` `policy_rule`); the lazy catalog answers "unavailable" when the policy cannot be read (`tools/lazy.rs` `policy_of`). `server/discover` needs no login; the body of the other two methods is parsed as JSON before the login. Each `tools/call` counts one `AT_LLM` hit `mcp:<name>` (`count_hit`: 120 a minute for each name, then 429 with `Retry-After`); the name is the caller's, and an unknown name is counted as any other. A read tool runs through `step::invoke` with no run, as the caller, under the read fence (`direct`); its approvals cannot ask, so a pause answers "did not run". A write needs a client that takes URL elicitations, and no key means no write. A retry with a `requestState` loads the approval for its owner and its run, replays the stored answer of an ended run, waits on a thread of its own for at most `approval-wait` (20 seconds) while the approval is pending, and else takes the run under its lease and runs the tool once with the decision (`retry`, `resume`). `run_tool` on the MCP surface uses the MCP exposures and checks the agent and the user again as it runs. A `screen` session is a conversation of the caller on the `mcp` surface. An `LlmApiClient` row of the credential with the `mcp` scope limits the server ([Gateway](#gateway)).

### Gateway

Off. `llm-facade/gateway@enabled` is `false`. The live element is `<gateway enabled="false" require-client="true" timeout="300"/>`. An `enabled="true"` example above it in the conf is inside a comment.

From `docs/ai/Gateway.md`, with the login in `crates/moqui-llm/src/gateway.rs` and the body limit in `crates/moqui-host/src/llm/gateway.rs`: Bearer login key or app password, or Basic with those. The account password is refused. TLS, a believed proxy's https, or a client on this machine (behind a believed proxy, the client it names). Missing or bad credentials are 401 `invalid_api_key`. The caller needs `LlmGatewayUse` and an `LlmApiClient` row, which must be the user's and not disabled (`client_of`). A2A and MCP read the rows of the credential they logged in with (`crates/moqui-llm/src/a2a/mod.rs` `protocol_client`): when no row has that protocol's scope (`a2a` or `mcp`), the rows do not limit it and the account's permissions alone apply; when one has, one of the user's rows with the scope must not be disabled (403), and its `allowedAgents` limit the agents. On A2A they bound a new task's agent, the old contexts and tasks found (`ops::owned`: get, subscribe, cancel, push configs), `ListTasks` and the extended card; on MCP a client whose `allowedAgents` leave out the MCP agent is refused. Each use updates `lastUsedDate`. `store#LlmApiClient` (`AgentAdmin`) writes the row for any user the admin names and takes a login key itself as `loginKey`, keeping its hash. An app password always needs a client. An account's login key needs one because `require-client` defaults to true; a key made for the gateway alone (`create#UserScopedKey`, `UserLoginKey.scope` `gateway`) is its own client, since it opens nothing else and its user's permission and quota still apply. The body max is 16 MiB. The host handler reads the whole body into memory and copies it before the job that authenticates is queued (`read_body`, with the body timeout), so an anonymous POST is buffered up to that size while the gateway is on. The path is exempt from the webapp request deadline. The gateway `timeout` of 300 seconds answers 504 for a whole call; a stream has already answered 200 and ends with an error frame. Paths: `GET /models`, `GET /models/{alias}`, `POST /chat/completions`, `POST /responses`, `POST /embeddings`. An unknown alias is 404. No tools run on the server: function-tool definitions pass through, and any other tool type is 400 `unsupported_tool`. Only allowlisted fields pass, with `n` 1, `store: false` and `model` set to the provider's name. `messages` and `input` pass as they are, so a content part that names a URL (an `image_url`, a file URL) reaches the model server. Upstream errors reach the caller as generic text. A stream caller that stops reading is dropped within the idle limit, and a caller that leaves cancels the call.

**Quotas.** Before a call runs, `admit` (`gateway.rs`, `usage.rs`) reserves its cost: the estimated prompt tokens plus the output limit, checked against the user's `LlmQuota` (own row, else the largest group row, else the conf's 2,000,000 tokens and 20 a day) and the client's daily limits, in one transaction under a lock row of the user and of the client, as an `LlmQuotaReservation` that goes when the call's row is written. Then come the host's room, the requests per minute of the user and the client (counted per node, in memory), and the `gateway:<alias>` tarpit. With no output limit in the request and no `max-output` on the model the reserve's output is 0, so a call may pass a limit by its own output. Today's use is from `LlmCall` plus open reservations; a month's earlier days are from `LlmUsageDaily`, which the rollup job writes.

### Assist

The drawer is screen transitions on `assist.xml` (`require-authentication="false"`), not host routes. Thirty-two of its 34 transitions call `AssistServices.call#Drawer` with authorization disabled. `constitution` and `constitutionReference` call the Constitution readers for any signed-in user, with no `AgentUse` ([Constitution services](#constitution-services)). `mentions` with `kind=records` calls `sri.getShellSearch` after its own `AgentUse` check. GET reads: `bootstrap`, `constitution`, `constitutionReference`, `conversations`, `conversation`, `tasks`, `prompts`, `mentions`, `attachment`, `memories`, `skills`, `events`, `read`. POST: `turn`, `cancel`, `archive` (the user's own conversation archived or restored; refused while its run is active), `retry`, `follow`, `context`, `submitted`, `decide`, `preview`, `answer`, `feedback`, `queued`, `attachments`, `transcribe`, `textAction`, `memory`, `skill`, `canvasState`, `canvasAction`, `canvasAdjust`, `canvasProblems`.

`docs/ai/Assist.md` is the contract for those calls. The browser session cookie is the login. Every call acts for the current user and needs `AgentUse`. Another user's conversation, run, approval, question, hand-off, or message is 404. A call from inside a run is 403. POST requires `X-CSRF-Token` or `moquiSessionToken`, and a missing token is 401 `Session token is missing or is not valid` before the call. The qapps shell always loads the drawer's script (`qapps.xml` `footer_scripts.add('/js/WebrootAssist.js')`). The script does nothing until `assist.start`, which returns unless the page setting `assist` is true; the server sets that only for a signed-in user with the llm feature enabled and `AgentUse` (`includes/QvtConfig.js`). Each drawer call checks again on the server.

Every drawer call goes through `Caller::current` in `crates/moqui-llm/src/assist/mod.rs`. It refuses a context that an agent's run works in (403), a request with no user (401), and a user without `AgentUse` (403). A conversation or a run is loaded with authorization off and then compared with the caller's user id; a mismatch is 404. Each write in `assist/write.rs` resolves its id through the caller, and a canvas is found through the caller's conversation (`assist/canvas.rs` `canvas_of`). `decide`, `canvasAction` `kind=arm` and `kind=mutation` also need `Decider::from_request` (`crates/moqui-llm/src/approval/mod.rs`): a browser render with its session token or the terminal, never a header login, an agent's context or internal code. `attachment` sends a file only when the stored `userId` is the caller's, as `Content-Disposition: attachment` with `X-Content-Type-Options: nosniff`. A message is at most 16,000 characters. A turn that starts a run counts one hit of the `AT_LLM` tarpit `agent:<agentId>` (30 a minute, then 300 seconds). `transcribe` and `textAction` count `assist:<call>` (60 a minute). The drawer's audio for `transcribe` is at most 10 MiB (`max-audio-bytes`); `transcribe` also checks the user's `api` quota. `textAction` puts the caller's `language` (one line, 40 characters) into the system text and the field text in the untrusted wrapper.

The reads in `assist/read.rs` and `assist/extras.rs` are keyed by the caller's user id or go through `caller.conversation` and `caller.run`. `conversations` and `tasks` find by `userId` only; the `search` text is a LIKE within those rows with `%` and `_` removed. The runs, approvals, questions and hand-offs of a conversation are filtered by the caller's `userId` again. A chat conversation is one sender's (found by room, thread, sender and agent), so another room member's drawer never lists it. Tool arguments and results in the thread are redacted and cut to 2000 characters; the cost shows only to an `AgentAdmin`. `bootstrap` lists every enabled drawer agent to any `AgentUse` user, with no role-group filter, and tells the client whether the user holds `AgentAdmin` and `AgentAudit`. `queued` edits only an unconsumed message input whose `userId` is the caller's, read for update. `events` checks the run's owner; `memories`, `memory` and the conversation setting check the conversation's owner. `skill` `op=draft`, `retire` and `share` act only on the caller's own rows ([Skills, memory and lessons](#skills-memory-and-lessons)).

The terminal Assist pane (`crates/moqui-tui/src/session/assist.rs`) posts the same `/assist/<call>` transitions through the in-process link. A decision there counts as the terminal's (`Channel::Tui`). Its approval card draws the summary and the change rows. The pane's encoder writes no control character from a cell, so model text sends no escape sequence to the user's terminal.

**Dev Assist's `hosting` tool** (the dev-aide crate, `src/agent/hosting.rs`; plans/design-dev-aide.md 21.8) reads a working tree's hosted repository on a connected group server as the connected user: merge requests, review threads, checks, a job's log and failed tests, an issue. It calls with the connection's keys, never the account's after an app sign-in (plans/design-dev-aide.md question 18): a key for git alone for the framework's git and hosting REST, and the key for tasks alone for an issue, so what the agent reads there is what those REST resources serve and no other (`key-scope`, docs/interfaces/Git-Hosting.md); for a repository Smithy keeps, the installed app's key that Smithy's REST takes, sent only under its `restBase`. Every text a successful answer returns is other people's (titles, descriptions, comments, logs, test messages): it reaches the model inside `<untrusted from="group-server">` with the wrapper's markers elided (`moqui_llm::prompt::untrusted`, called in `as_data`), so a comment that tells the agent to approve or push is data. A failed call's text is not wrapped: a non-2xx answer becomes a `ToolError` that holds up to 300 characters of the `errors` or `message` the remote server wrote (`hosting.rs` `service`, `src/hosting/client.rs`). Path parts the model names are validated or percent-encoded. It has no action that approves, merges, re-runs, resolves a thread, signs the contributor agreement or pushes. It gives an agent no diff (files, file texts, commits) of a merge request whose commits' authors have not all signed where the server requires it (`get#AuthorSigned` per author email, or the application's `diffRefused`), nor when the authors are not all known: no commit list, a cut one (`commitsTruncated`, fewer commits than `aheadBy`), a commit with no author email, more than 20 authors, or, for a repository an application keeps, an author the server did not decide (`known` false, which is also its answer when its agreement hook fails); the threads of such a merge request come without their line's text and without fenced or quoted code (a suggestion). `checks` and `job` (a log's last 20,000 characters) are not subject to that gate. A worktree of an agent's session is its maker's: it is made only for one of the caller's own conversations, only that user's session is rooted in it, only they or an administrator remove it (and only under `runtime/worktrees`), and a session with a worktree reaches neither another worktree nor a root inside the tree its worktree stands in for. When its conversation ends (archived or deleted; the dev-aide's `DevAide.eecas.xml`), a worktree seen clean is removed after the commit and one with uncommitted changes is kept, with its branch, and its maker told once (`end#ConversationWorktrees`, which does nothing for a conversation that is there and not archived). Its reads run under the read fence: the tool opens a remote permit for the hosted server's origin only (`fence::enter_remote`), and the Dev AIDE's client lifts the fence for that one GET after `check_remote` passes (never in a sim, never for another origin, never for a write); a read that would write (resolving a root's hosted repository) is refused under the fence instead. A comment, a reply or a new merge request is an EXTERNAL approval whose card shows the text, the merge request, file and line, the repository and the server; the approved write goes through the same HostingServices as the Workspace's, so a header login, a fence and a sim refuse it.

`GET /assist/runs/{run_id}/events` and `.../events.json` authenticate like `/notws` (origin, session cookie, else `login_key`). The stream is for the run's owner. The routes check the run's owner only (`crates/moqui-host/src/llm/sse.rs` `owns`); they do not check `AgentUse`. At most 256 streams on a node (`MAX_STREAMS`; one more is 503 with `Retry-After`, `docs/ai/Assist.md`) and 16 of one user (`MAX_STREAMS_PER_USER`; one more is 429 with `Retry-After`).

`GET /assist/sandbox` is public and has no session. The origin written into the policy is the scheme and the host of the request: `X-Forwarded-Host` from a believed proxy, its value at the client address's hop (`http::forwarded`), else `Host`, else the webroot's configured host (`crates/moqui-host/src/llm/sandbox.rs` `frame_host`). A host that is not a plain name and port is 400. Query `v` is a cache buster. `x=1` adds `https:` to `img-src` only. The iframe is `sandbox="allow-scripts"` without `allow-same-origin` (`docs/ai/Assist.md`). The policy is the frame document, separate from the screen CSP:

```
sandbox allow-scripts; default-src 'none';
script-src <origin>/libs/vue/ <origin>/libs/quasar/ <origin>/js/WebrootAssistSandbox.js 'unsafe-eval';
style-src <origin>/libs/ 'unsafe-inline'; font-src <origin>/libs/;
img-src data: <origin>/images/ <origin>/libs/;
connect-src 'none'; media-src 'none'; object-src 'none'; frame-src 'none'; child-src 'none'; worker-src 'none';
manifest-src 'none'; form-action 'none'; frame-ancestors 'self' <origin>; base-uri 'none'
```

Response headers from that doc: `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, a `Permissions-Policy` that turns features off, and no `X-Frame-Options`; the code also sends `cache-control: no-cache` and `cross-origin-resource-policy: same-origin` (`crates/moqui-llm/src/ui/vue_sfc.rs`). `v` is cleaned to 40 plain characters. `'unsafe-eval'` is in this frame policy. It is not in the default screen CSP.

Mantle's `user-facts` provider (`mantle.party.UserFactServices.get#OrganizationFacts`, named in Mantle's MoquiConf `llm-facade`) adds to a new conversation's prompt the names and ids of the user's internal organizations (at most twenty) and their active one; it reads only and answers nothing for another user. Mantle's conf is its one caller: no screen or rest-api file names it. A tool still takes and checks its organization: the facts are fixed when the conversation starts.

### Agent runs and tools

A run's step logs in as the run's user (`internal_login_user`, `crates/moqui-llm/src/run/step.rs`) on an agent pool thread, in a context made for that job with no user and an empty session (`request_pool.rs` `run_work`), which is left when the job ends. The independent reads of a step, up to 4 at a time, log in again as that user on threads of their own, each in a new context. The user is read from the run's row (`acting_user`), never from the model or a tool. No caller outside a test sets `StartRequest.run_as_agent_user`, so `AgentRun.runAsUserId` is never written and `acting_user` answers the run's `userId`: the caller's own, the sender of a room message, or a trigger's run-as user ([Triggers](#triggers)). A service becomes a tool only through an `AgentToolExposure` row, which `org.moqui.agent.AgentAdminServices.store#AgentToolExposure` (`AgentAdmin`) writes. One row is seeded: `get_constitution_references`, READ. Before a service tool runs, `user_permitted` (`crates/moqui-llm/src/tools/catalog.rs`) calls `authorize("AT_SERVICE", ...)` for the current user, and for an entity-auto service `authorize("AT_ENTITY", ...)`. That check is skipped for a service whose `authenticate` is `false` or anonymous: once such a service is exposed, the agent of every `AgentUse` user may run it, and an agent's role group is the only bound. The service then runs with default call options, so authorization is on. An agent's role group, when it has one, also has to permit the service (`group_permits`). A READ tool runs under the read fence. Any other class asks for an approval; DESTRUCTIVE needs the policy's `allowDestructive`. The `screen`, `data` list and `search` tools render screens as the run's user, fenced, with every write held by the transition gate. The `screen` tool's `go` and the `data` tool's `path` take any screen under the webroot root, not only `/apps`: `check_screen_path` (`crates/moqui-llm/src/screen.rs`) refuses a path that is not from the root, has a host, `..`, a backslash or a control character, names a transition, or names no screen. Only the canvas paths are held to `/apps`. `search` renders the two fixed root transitions `/shellData` and `/shellSearch`; the model gives `text`, `groups` and `limit`, no path, and the titles and subtitles of the hits reach the model unwrapped. The `data` tool also reads the entities of the conf's `data-entity` patterns with authorization off (`crates/moqui-llm/src/tools/data.rs`): by default the package `moqui.basic` (enumerations, statuses, units, geos, localized messages). Encrypted fields are never read, and fields named like secrets only with `secret-fields="true"`. An `ai-opt-out` field is never read either, and a `where`, `order` or `fields` argument that names a field outside the readable set is refused. For a list screen the tool refuses a `where` or an `order` argument that names an `ai-opt-out` field; that test reads those two arguments only, and find parameters written in the query of `path` go into the render's parameters untouched. `data artifact=A<n>` reads a spilled tool result and `artifact=F<n>` the text of a file attached to the conversation, wrapped as untrusted, each only for the run's own conversation. Screen sessions are at most 64 on a node and 4 for a user.

**The run loop.** A step (`run/step.rs`) claims the run's lease, ends a canceled run, logs in, fails the run when its agent is disabled, its user has become external or no longer holds `AgentUse` (`lost_standing`; a trigger's run whose user is an agent's own account is exempt from the `AgentUse` test, one set to run as a person is not), loads the agent, the model, the policy and the offered tools, folds in the waiting messages as user messages, checks the budget and the quota, calls the model with no transaction open, stores the reply and runs the calls in model order. The model can call only a tool offered to the run. A reply that is only a tool call written as text (the whole reply is `<tool_call>` blocks or one bare object naming an offered tool, `json_mode.rs` `leaked_calls`) is run as a call; a call quoted in prose or a fence is text. Anything that writes asks `approval::request` from inside the tool; the loop adds no approval. Limits: the steps, tool calls, tokens, cost and time of the run, the model's tool calls a run (12 or 30), a tool's `callsPerRun`, and the user's `agent` quota, against which each model call of a step is admitted. At a cap an interactive run asks whether to continue, and a background one fails. Any message, or a yes, is a continue, and `raise_caps` then adds the base amount to each cap reached, each time; the user's quota is the bound.

A new run is bounded by the `agent:<agentId>` tarpit and the user's daily quota. A message handed to an active run counts no tarpit hit, though the run makes a model call to answer it. One run for each conversation holds; conversations and a user's concurrent runs are not limited. The agent pool is one for the node: `max-concurrent-runs` (8) workers and `run-queue` (64) jobs for every user (`run/pool.rs`), and a step holds its worker for a whole model call; past the queue a step is refused and left to the recovery sweep. A run has no session, so it goes on after its user signs out. The step's login refuses a disabled or terminated account (`gate_account`), so such a run fails at its next step. A step does not check again that the agent is not disabled, that the user is not an `EXTERNAL_USER`, or that the user holds `AgentUse`; `start_run` and its callers check those once. The tool policy is read again each step.

A question's pause has no expiry: `ask`, the budget question and a remote's question or link pause with `expires: None`, and the sweep ends only a pause with a date, which only an approval has. Such a run holds its conversation's `activeRunId`, and a remote A2A task or an MCP `requestState` it waits on, until its user answers or cancels. `ask` stores one `AgentQuestion` for the run's user and checks the answer against the form's fields before the run takes it. After a takeover a READ call that was running runs again (for an MCP tool an admin marked READ, a second request to the remote server); a write, destructive or external call never does. A run is taken over at most 3 times (`MAX_ATTEMPTS`). An external harness's run is never worked by this engine.

When a step returns an error (a database error, a row that cannot be read, a failed login), its text goes unredacted into the stored `error` event, `AgentRun.errorText` and `statusReason`, and the `run.state` payload; for a run started in a room the chat adapter posts its first 300 characters as the agent's reply (`chat.rs`). A provider's error text is redacted before it is stored.

`org.moqui.agent.AgentServices.start#AgentRun` and `submit#AgentInput` act for the current user's own run; `submit#AgentInput` takes `inputKind` `message`, `answer` or `remote` and a free `data` map, and never a decision. `start#AgentRun` refuses the `job`, `a2a` and `mcp` surfaces without `AgentAdmin`. No screen, rest-api file or script in the tree names either. `ec.llm.startRun` (`crates/moqui-llm/src/script.rs`, `ai_task.rs`) lets a server script start a job-surface run as the current user, who needs `AgentUse` and `AgentAdmin`; `AgentEval.js` is its caller. `AgentAdminServices.cancel#AgentRun` stops any user's run for an `AgentAdmin`, from the `cancelRun` transition of System › LLM › Runs.

**The lazy tools.** `find_tools`, `describe_tools` and `run_tool` are in every surface (`crates/moqui-llm/src/tools/lazy.rs`). `run_tool` is the path by which an `AgentToolExposure` service runs: the parameters repaired and cleaned, the user's permission before the record is read, the agent's policy and role group, then a READ under a fence of its own or an approval. An entity-auto write needs the whole key and no pattern. An approved call is checked again for the exposure's lock version, the user's permission, the record's stamp, the exact arguments and the same record. An add-on tool of the catalog is called as itself, a non-read one with the fence lifted, so its approvals are its own code's. `store#AgentToolExposure` stores the classification the admin gives, with no floor from the service's own class.

**Spilled results.** A tool result over the model's result cap is written whole to `dbresource://agent/<runId>/<toolCallId>` (`tools/spill.rs`; `toolCallId` is a sequenced key the server makes) and kept as a database resource, unencrypted.

**Screen sessions.** In a screen session (`crates/moqui-host/src/llm/screens.rs`) the agent, as the user, opens any screen the user may open, sets fields and presses elements; a transition is held and becomes an approval. A session is found and used only by its owner; its id is 16 random characters. Every link gets the agent's render origin, the gate and the write fence before its first request, and never logs in. A drop-down's options, a dialog body and a JSON or raw lookup of a rendered screen run through a second link whose gate is open, under the read fence, as the user. An agent render is not interactive, so the session cannot decide an approval. An approved write runs only for the write's owner, with the approval id and the arguments' hash, and a second hold is a refusal.

### Approvals

A write waits as an `AgentApproval` row (128 random bits as its id) for at most `approval-ttl-minutes` (30). `approval::decide` (`crates/moqui-llm/src/approval/mod.rs`) takes a decision only from the approval's own user, with one exception: a chat run's card. A run started from a room message runs as the sender, and its approval card is a room message. A member who may post in the room (`get#RoomAccess` `canPost`) decides that card through `org.moqui.agent.AgentServices.decide#ChatCard` (the webroot `chatAssistCard` transition, a POST), other than an agent's chat or run-as user, a member with the role `CmrAgent`, or an `EXTERNAL_USER` (`crates/moqui-llm/src/chat.rs` `room_approval`). A member who is not the requester approves only a write that member may make, checked as that member (`approval::decide_in`, `decider_may_write` under `user::as_user`: a screen write's path, a service's own permission); a write of another system's tool, an add-on tool or a change set only its requester approves. Any such member may reject (plans/Security-Review.md SEC-AI-01, fixed). The write still runs as the user who asked, with that user's permissions; the approval keeps both users. Edit in screen and a question's answer stay the requester's. A decision needs a browser render with its session token or the terminal (`Decider::from_request`). A policy rule approves by itself only for a background agent: the run is on the `job` surface and every surface the agent serves is `job` (`is_background`). A click on a Button of an OpenUI canvas holds the write and shows it; the user's confirm of that held write is recorded as an approval through the channel `canvas`, with no card ([Canvases](#canvases)). A skill's `risk` (`reversible`, `confirm`, `irreversible`) is a label on the card where the card names the write the skill lists; it neither adds nor skips an approval. For a screen write it is never shown: the card names the write by its `component://` location and the skills list `/qapps` paths (`tools/screen.rs`, `skills/mod.rs`). A learned skill counts as `confirm` whatever it says.

### Canvases

An agent on the drawer may write a canvas. With no `canvasDialects` an agent writes only OpenUI Lang; the seed `assist` agent names none. Vue SFC is off unless an agent names `vue-sfc`. Two more dialects, `screen-xml` and `qvue-screen`, exist on a dev instance only ([below](#the-development-dialects)). The server parses an OpenUI program in a JavaScript runtime of its own with no `ec` and no host functions, a 64 MiB heap and a 5 second limit (`crates/moqui-llm/src/ui/openui.rs`). A Vue SFC script is compiled, not run, in one with 16 MiB and 2 seconds (`ui/vue_sfc.rs`). A program is at most 64 KiB. The OpenUI parse runs no model-written JavaScript: the program goes to lang-core's parser as a JSON string. The validator refuses, among others, a Query or Mutation whose tool is not `"request"`, an option outside `path, list, query, method` or `method, path, body`, a key starting `__`, a Query with a method other than GET, a Mutation with GET or a body that reads a Query, a literal path that is not a plain `/apps` path, and a Link whose literal path is not a screen of the apps. A path that is not a literal is checked where it is used: the read proxy, `hold`, and the client's `safePath` for a Link. The Vue SFC check is a text scan (banned tags, attributes, free names and property names, `import`, `@import`, a `url()` that is not `data:`); by its own comment it is a first layer and the boundary is the frame. It does not look at a banned name used as a property, so `x.location` passes, and a computed name passes. A canvas reads through `GET /assist/read`, as the user: the proxy makes no outbound request and renders an `/apps` path in-process from the agent's origin, fenced with writes held, after `check_read` (the agent's role groups for view, then the user's permission); a screen answers the rows of one form-list, a transition its own JSON, and a transition that writes 403 (`ui/proxy.rs`). Reads are 240 a minute a user and node, 100 rows by default and 500 at most; from a frame, 6 at once, 60 in 10 seconds and an answer of at most 1.5 MB. A Vue SFC canvas reads only the paths its `<reads>` list declares (at most 50 `/apps` paths, stored on the canvas; the model writes the list). With no `artifactId` the proxy reads any `/apps` path for the caller with the role groups of the conversation's agent, else of `assist`; the `<reads>` list and the "other sites" refusal apply only when a Vue SFC or qvue-screen canvas is named. A canvas never posts from the page (`ui/write.rs`). A Mutation names a transition under `/apps`. The model writes the Button's label and the Mutation behind it, and a Mutation's arguments may be literals in the program. The server evaluates the arguments from the stored program and the posted state, holds the request at the transition gate, checks the user and the agent's role group, and runs it as the user. A Mutation runs from two clicks: `canvasAction` `kind=arm` gives nonces (16 random bytes, 30 seconds, one use, 5 a click, 10 a session), and `kind=mutation` needs one, the `activation` flag, a browser session and a Mutation name that the stored canvas lists (`crates/moqui-llm/src/assist/canvas.rs` `mutation`). The first click holds the evaluated write and answers its method, path, transition, parameters and hash (`ui::write::hold`), running nothing; the client shows the transition, the path and every parameter in a dialog (`js/WebrootAssist.js` `canvasAction`, `confirmCanvasWrite`), and the write runs only when the user's Save, with a new nonce, posts `confirm` equal to that hash, so a write the model or the values changed has another hash (plans/Security-Review.md SEC-AI-02, fixed). The confirm is the approval: an `AgentApproval` row records it and no card is shown. A value named like a secret is never stored or posted. Beside the label, a Button that runs a Mutation shows "saves:" and the last segment of the transition's path (`js/WebrootAssistCanvas.js` `savesText`). A Mutation the agent proposes with `write_ui` `run`, with no click, is an approval card like any other write. A Vue SFC component runs in `<iframe sandbox="allow-scripts">`. It talks to the page over a `MessageChannel` port handed over with a nonce. A submit from the frame opens a confirm drawn outside the frame, and the Save there is the first click; it posts through the same `canvasAction`, so the server's held write is confirmed in its dialog as well. While the user's preference `ASSIST_CANVAS_EXTERNAL` is on (the `x=1` of `GET /assist/sandbox`), a Vue SFC canvas reads nothing; the component's source and initial values are still the model's. A Vue SFC action is a fixed list the server parses from the stored program (an `/apps` path with no query, a write method, no secret name, scalar parameters, at most 10 actions and 50 values), and the request is built from that list and the confirmed values only. The parent listens only on its channel port and validates each message; a link from the frame opens only from a gesture and only to a `safePath` or, with "Other sites", another site with `noopener,noreferrer`. The frame's runtime (`js/WebrootAssistSandbox.js`) evaluates the script with `new Function` and cannot stop the component's own code. The frame policy has no directive that governs navigation, so the drawer frames the sandbox through a holder document on this site's origin, `GET /assist/sandboxHost` (`vue_sfc::host_document`, `js/WebrootAssistSandboxHost.js`, framed `sandbox="allow-scripts allow-same-origin"`), whose policy lets its one frame load only `/assist/sandbox` (`frame-src`), and a browser holds a frame's own navigations to the policy of the document that frames it: a component cannot carry what it read to another site by setting its location (plans/Security-Review-Medium.md SEC-AI-81, fixed). The holder hands the drawer's port to the sandbox and reads nothing from it; a second load of the sandbox makes it leave, and the drawer's watchdog closes the canvas on that load. The app's pages keep their own policy. The runtime deletes the WebRTC constructors from the frame's window by name and both policies have `webrtc 'block'`; where a browser does not enforce that directive, a component can still send what it read out by WebRTC (a new frame of its own has the constructors), a known limit of Vue SFC canvases.

#### The development dialects

On an instance whose `instance@purpose` is `dev`, a user who holds a dev-aide permission (`devtools::dev_aide_user`; `ADMIN` holds `DEV_AIDE` by its seed) gets `ui.write:screen-xml` and `ui.write:qvue-screen` for an agent whose policy pins a dev tool (`run/mod.rs`). A `screen-xml` canvas is an XML screen file the model wrote, shown through `write_ui` with no approval. Its first line names the `component://` location it stands at (`at`) and the page that shows it (`path`). The server checks that `at` starts with `component://` and refuses a `path` that is not a plain path of the apps (`/apps/...` or `/qapps/...`, no scheme, host, `..`, `//` or backslash: `page_path_ok` in `crates/moqui-llm/src/ui/screen_xml.rs` `prepare`); the client holds `path` to the same rule (`plainAppPath`) and uses it plus the preview token as the `src` of an iframe with no `sandbox` attribute, framed only when the user presses Show the preview, again for each version (`js/WebrootAssistCanvas.js` `previewUrl`; plans/Security-Review-Medium.md SEC-AI-82), so a `javascript:` or another site's path never becomes the frame and text a run read does not open a preview by itself. A screen request with the parameter `moquiPreview` or the header `x-moqui-preview` equal to `canvas:<artifactId>` renders with the canvas's program standing at that location (`crates/moqui-core/src/screen/render.rs`, `screen/overlay.rs`): only on a dev instance, only for the user who owns the canvas's conversation, under the entity read fence, with the policy `PREVIEW_POLICY` (`default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; frame-ancestors 'self'; form-action 'self';`), so nothing it loads goes to another site; the response drops a `Refresh` header and turns a redirect to another site into a 403 (`screen/render.rs` `preview_response`). While the overlay is held, a screen that stands at its text (the overlaid file, or a screen-extend of it: `sri.isOverlaid()`, `screen::sri::active_overlaid`) writes a placeholder for its render-mode text, `.qvt` and templates, so script the model wrote there does not run in the application's origin (`renderTextCode` in `ScreenSupport.js`; SEC-AI-82). Its widgets render through the macros, which escape their values: its labels, displays, links, editables and button-menus are encoded even with `encode="false"` (`rawText` in `ScreenHtml.js` and `ScreenQvt.js`, which writes a qvt text's braces as character references too), it is not sent as a server-static template (`statics::serve_template`), and a label's or editable's `type` is one of the XSD's tags, preview or not (`labelTag`), and its `<actions>` run on the server under the read fence with authorization required: while the preview holds the runtime, `disableAuthz`, a login or logout, `runAsUser` and an artifact push or pop are refused, and the actions run on the preview's allow-list (`script/preview.rs`; [Attack-Surface-Scripts.md](Attack-Surface-Scripts.md#the-effect-fence); plans/Security-Review-Low.md SEC-AI-102).

### Assistant text in the browser

The drawer renders an assistant text as Markdown with Marked (`escapeHtml: true`, so raw HTML is text), then DOMPurify, then a walk of the cleaned DOM (`js/WebrootAssist.js` `assist.sanitize`, then `v-html`). `style`, `form`, `input`, `button`, `iframe`, `object`, `embed`, `svg`, `math`, `video` and `audio` are forbidden tags. An image is replaced by a text placeholder that names its host, unless its `src` is a static image path of this site or `/richTextImage/<id>` (`siteImage`: a path with an image extension, no query or fragment, not under `/apps`, `/qapps`, `/rest`, `/assist`, `/vapps`, `/s1`, `/e1` or `/m1`, no `//`, no `..`, no white space or backslash; the canvas rule). Such an image stays, and the browser fetches it with the user's cookies (SEC-AI-03, fixed). A link keeps its `href` only when it is a site path or an `http(s)` URL. An external link is kept as the model wrote it and opens in a new tab with `noopener,noreferrer`; its title is the host the browser goes to (after any `user:password@`). One that carries data past its host and path (a query, a fragment, or a user and password; `assist.externalCarries`) shows its whole address as its title and opens only after the user OKs a dialog that names the whole URL and its host (`assist.confirmExternal`). A link the server marked as invented is shown as text. The server marks a link in a run's final text (a step with no tool call) whose URL is in no tool result, no user message and not in the compaction summary of the active window (`run/step.rs` `seen_references`, `tools/format.rs` `check_answer`): an `/apps` or `/qapps` URL is known when its path was in that text and every query value is a word of it, any other URL only when that text held it whole. A URL planted whole in a record a tool read is therefore known. The marks go out as the event `answer.references` and into the run's `resultJson`. A text the model writes in a step that also calls a tool is not checked, and a conversation loaded from `GET conversation` is built from the stored messages without the marks; there the client rule above is what applies, and it does not look at a URL's path or host name for data. `moqui.markdown` sets `target="_blank" rel="noopener noreferrer"` on an external link (`js/WebrootVue.qvt.js`). A canvas's Markdown is strict: no image and no external link.

### Untrusted text

`moqui_llm::prompt::untrusted` wraps text as `<untrusted from="...">` with its markers elided. It wraps: a remote A2A agent's card, question and answer; an MCP server's descriptions and results; a chat thread's earlier messages; a document trigger's records; an AI task's input; a text attachment's lines; a learned skill's text; a lesson; a conversation summary; a canvas problem's message; an inline text action's field text; the dev-aide `hosting` tool's answers. The results of the `screen`, `data` (lists and entities), `search` and service tools are not wrapped. For those the controls are the core prompt's rule that tool text is data (`framework/prompt/core.md`) and the approval of every write.

### Skills, memory and lessons

A skill is text the model loads with the `skill` tool; the server runs none of its steps. File skills come from a component's `skill/` directory; those of mr-boss are in [Attack-Surface-Apps-BOSS.md](../../runtime/components/addon/mr-boss/docs/security/Attack-Surface-Apps-BOSS.md#agent-skills). A user's own skill is personal: `skill` `op=save` stores it for that user, and saving one an agent drafted needs `AgentSkillAuthor` (`crates/moqui-llm/src/assist/extras.rs`). `op=share` makes a site copy in Draft, which only an admin publishes in System › LLM › Skills (`crates/moqui-llm/src/skills/learn.rs`). A learned skill's text reaches the model inside `<untrusted from="learned-skill">`. The "learned" mark of a save is the client's flag, a `runId` parameter, or a match with a draft kept in the session attribute `moqui.assist.skillDrafts`; a user who retypes a draft stores it as their own `user` skill, which is trusted for that user only. `op=draft` takes only the caller's completed run and leaves out fields named like secrets. `save`, `retire` and `share` act only on a row whose `ownerUserId` is the caller's. The skill index takes only published rows that have no owner or the reader's; a learned row never takes a name a file or a site row has. `store#AgentSkill` needs `AgentAdmin` for a site skill and lets an owner with `AgentUse` change a personal one (`personal=Y`); its only callers are the System › LLM › Skills screens. `sync#AgentSkills`, `get#AgentSkill` and `get#SkillRetrieval` need `AgentAdmin`. `get#AgentSkill` returns another user's personal skill only to an `AgentAudit` holder, with the read written to `AgentAuditLog`; anyone else gets `contentHidden=Y` and no text, and SkillDetail hides the editor. `get#SkillRetrieval` refuses another user's `userId` on the same test (`assist::audit::may_read`, `crates/moqui-llm/src/skills/services.rs`), and SkillList's search leaves out the skill's text fields. `sync` reads only `skill/**/*.md` of the framework and component directories. Memory holds facts for one user, one line of 200 characters each, keyed by `userId`; they are in the prefix of every new conversation of that user. `memory::needs_confirmation` (`crates/moqui-llm/src/memory.rs`) decides whether the `remember` tool keeps a fact at once or asks with a confirm card. It asks on any surface but the drawer and the terminal, with no run, and when the messages cannot be read; otherwise it reads the conversation's newest 200 messages and asks only when a message of role `tool` comes after the last `user` message, so tool text read in an earlier turn does not make a card. The drawer shows "Remembered: … [Forget]". When a card is needed and a policy would approve by itself, nothing is kept. `save_skill` uses the same test and needs `AgentSkillAuthor`; its card shows the skill's name and description, and the body is in the approval's arguments. A lesson is Proposed and active for its author only until `review#AgentLesson` (`AgentAdmin`) approves it; it reaches the model wrapped. The compaction summary goes back in wrapped as untrusted (`window.rs`). User facts providers run under the read fence and are dropped on a write (`facts.rs`).

### Triggers

An `AgentTrigger` starts a run on the `job` surface as the trigger's `runAsUserId`, else the agent's. That user is the run's own `userId`, so the run, its conversation, its approvals and its quota are that user's. `org.moqui.agent.AgentTriggerServices.store#AgentTrigger` and `reset#AgentTriggerBreaker` need `AgentAdmin`. `store#AgentTrigger` takes as run-as user any user that some agent names as its `runAsUserId` or `chatUserId`. `fire#AgentTrigger`, `receive#TriggerDocuments` and `delete#TriggerDocument` are `authenticate="anonymous-all"` and check no permission in their bodies (`crates/moqui-llm/src/trigger.rs`). Their callers in this repository are the `ServiceJob` `agent_trigger_<triggerId>`, the `AgentTriggers` data feed, the scheduler's sweep, and the `fireTrigger` transition of System › LLM › Triggers (`AgentAdmin` on the screen). No rest-api file names an agent service ([how a service is reached](Attack-Surface-Web.md#services-and-allow-remote)). A firing is skipped while the trigger is paused, its breaker is open, or a limit is reached (defaults: 2 concurrent runs, 60 an hour). Three failures in a row open the breaker. A document trigger's changed records reach the model inside `<untrusted from="record">`, each cut to 1500 characters and 8000 in all. A record change the trigger's own agent made does not fire it.

### AI tasks and speech

`org.moqui.agent.AiTaskServices.run#Summarize`, `run#Classify`, `run#Extract`, `run#Translate`, `run#Generate` and `run#AiTask` run one completion for the current user. They need no `AgentUse`; `LlmFacade::complete` refuses an `EXTERNAL_USER` and checks the user's `api` quota. A task's input is at most 60,000 characters and is wrapped as untrusted. An async task may name a webhook in its `webhookUrl` parameter, so the service's caller chooses the address: `https` only, internal addresses refused at connect ([the guard](Attack-Surface-Outbound.md#the-internal-address-guard)), no redirect, 15 seconds. The POST carries the task's outcome and trace headers.

`org.moqui.call.SpeechServices.transcribe#Audio` is `authenticate="false"`. It reads the bytes at any `audioLocation` it is given and sends them to the model bound to `transcribe` ([Call captions](Attack-Surface-Comms.md#call-captions)). Its callers are the voicemail job, the Mantle voice note check and the drawer's `transcribe` call; each passes a stored location or the upload.

### Semantic find

`POST /find/rank` (webroot `find.xml`, `require-authentication="false"`, `track-artifact-hit="false"`) answers 401 without a signed-in user and checks no permission. It answers 503 on the default conf, which has no embedder (`search-facade` `semantic`). The body is JSON `{query, texts, limit}`, passed to `org.moqui.search.SearchServices.rank#Texts`. At most 5000 texts, each cut to 2000 characters, go to the embedding model in requests of 64 (`crates/moqui-core/src/search/rank.rs`, `crates/moqui-llm/src/embed.rs`). Every embedding call made for a user, this path's included, is refused for an `EXTERNAL_USER`, checked against the user's `api` quota and counted as an AT_LLM tarpit hit `embed:<modelId>` (`LlmFacade::embed_batches`; artifact group `LlmEmbedCalls`, 120 a minute); work with no user (the embedding worker, jobs) is not, and a call whose texts are all cached makes no check. Vectors are cached in memory (20,000). Each request to the model is an `LlmCall` of source `embed`.

### Model providers

Every model call is an outbound POST from the server to an endpoint's URL, with the endpoint's key and the model request (the prompt and the conversation) as its body. The default endpoint is `default`, protocol `chat-completions`, at `llm-facade/endpoint[default]@url` (`https://api.openai.com`). Its key is `llm-facade/endpoint[default]@api-key` (empty, `is-secret`). With an empty key no auth header is sent. The default model has no name until `llm-facade/model[default]@name` is set, so no call goes out on the default conf. The other endpoints in `MoquiDefaultConf.xml` (xAI, Anthropic, Gemini, GLM, DeepSeek) are inside XML comments. An endpoint is configured in the conf or by an `LlmEndpoint` row, which overrides a conf endpoint by id; `store#moqui.llm.LlmEndpoint` runs from System › LLM › Models, which needs `AgentAdmin`. `LlmEndpoint.apiKey` is an encrypted field. A row that moves an endpoint to another origin without a key of its own drops the conf's key (`crates/moqui-llm/src/registry.rs`), and a write of a row with a new address clears its stored `apiKey` unless a new key is written in the same save, on every write path but seed and install loads (the run-before entity ECA `LlmEndpointSecretMoves` in `Security.eecas.xml`, `admin/EndpointSecrets.js` `moved`). An endpoint's key may also come from the property or environment variable its conf `api-key-env` names; no entity field sets that name. A provider call follows no redirect. The address check reads only an address written in the URL (`crates/moqui-llm/src/provider/mod.rs` `check_address`; the row in [Attack-Surface-Outbound.md](Attack-Surface-Outbound.md#requests-the-server-makes)): a private or link-local address needs `allow-private-network` or `local`, loopback is always allowed, and a host name is not resolved for the check. `org.moqui.agent.AgentAdminServices.test#Endpoint` and `probe#Model` (`AgentAdmin`) make a call to the endpoint and return the reply text or the error text.

### Remote agents and MCP servers

The MCP client is on (`mcp client-enabled="true"`). It calls only the servers of `AgentMcpServer` rows, and the A2A client only the remote agents of `AgentRemoteA2a` rows. `org.moqui.agent.RemoteAgentServices.store#AgentRemoteA2a`, `store#AgentMcpServer`, `store#AgentMcpServerTool`, `test#AgentRemoteA2a` and `test#AgentMcpServer` need `AgentAdmin`, so an `AgentAdmin` chooses each address. A row's URL is `https` unless `allowPrivateNetwork` is `Y` and the host is internal (`crates/moqui-llm/src/remote.rs` `check_url`). Every call is checked to be on the row's origin, goes through a client that refuses internal addresses at connect time unless the row allows them ([the guard](Attack-Surface-Outbound.md#the-internal-address-guard)), and follows no redirect. A call carries the question or the tool arguments the model wrote, the row's credentials and trace headers. `authJson` is an encrypted field and is never returned; a store that moves the URL (or card URL) to another origin clears it unless it is given again, and an MCP server's users' tokens with it (`store_row`, `credentialCleared`; SEC-OUT-82). With `perUserAuth` a call uses the user's `AgentMcpUserToken` row (`tokenJson`, encrypted); no service, screen, REST resource, OAuth flow or Rust code in this repository or its add-on components writes that entity, and its one reader is `mcp/client.rs`. A `perUserAuth` server therefore answers every user that no token is set for them, unless a holder of the generic entity tools writes the row. The token used is that of the user the tools run as. Remote tools are EXTERNAL, so a call asks for an approval before anything goes out, unless an admin marks an MCP tool otherwise; with nobody to ask and no policy it is refused. A READ MCP tool runs at once under the read fence with a permit for its server's origin only, with the arguments the model chose. An approved remote call goes only to the origin the user approved. A call does not go out in a sim.

An MCP server's tool list is fetched when a run's catalog is built (`tools/mcp_client.rs`, from `find_tools`, `describe_tools` and `run_tool`), with the row's credential or the user's token and with no approval. The client keeps tool lists and sessions per server, address and credential, caps a list at 4 MiB, 10 pages and 1000 tools, answers no request of the server's own, and speaks a legacy protocol (`initialize` at 2025-11-25, the server's `Mcp-Session-Id` sent back) to a server that does not discover. A remote MCP schema is rebuilt from an allowlist. A remote's answer, error, card text and tool description reach the model inside `<untrusted>`; a remote's `structured` result does not reach the model. The A2A client calls a card's interface only on the card's origin.

A remote A2A task or an MCP server that needs the user pauses the run with a question that carries the remote's link and its host (`tools/delegate.rs`). The link is from an MCP elicitation or the first URL in an A2A status text. It is shown when it is `https` to any host, or `http` to an internal host of a row that allows a private network, with no user info or fragment (`remote.rs` `link_allowed`). The message beside it is the remote's text, cut to 600 characters. The user's answer goes to the same remote task, and Cancel cancels it.

### Constitution services

The artifact group `ConstitutionServices` is granted `AUTHZT_ALWAYS`, `AUTHZA_ALL`, inheritable, to `ALL_USERS` (`AgentTypeData.xml`). It covers eleven services of `org.moqui.admin.ConstitutionServices`. Each checks in its body (`crates/moqui-llm/src/constitution/services.rs`). `store#Constitution`, `create#ConstitutionCustomization`, `reset#Constitution` and `store#ReferenceOrigins` need the sealed permission `ADMIN_CONSTITUTION_GLOBAL`, which the seed grants to `ADMIN`. The readers need a signed-in user; a run's snapshot is for the run's user or an `AgentAdmin`. `validate#Constitution` and `edit#ConstitutionDocument` write nothing. `record#ConstitutionChange` is not in the group. The webroot transitions `GET /assist/constitution` and `GET /assist/constitutionReference` call the readers for any signed-in user and remove `instructions` and `documentText` from the answer.

### System › LLM, the content log and audit

Every screen under `System/Llm` returns an error without `AgentAdmin` (`always-actions` of `Llm.xml`; the row in [Attack-Surface-Tools.md](Attack-Surface-Tools.md)). The Rust services behind them check `AgentAdmin` again, except the entity-auto ones (`store#moqui.llm.LlmEndpoint`, `LlmModel`, `LlmFeatureBinding`, `LlmModelAlias`, `store#moqui.agent.AgentToolPolicy`, `delete#moqui.agent.AgentToolExposure`) and the eval services, which check `MONITOR_EVAL` or `MONITOR_EVAL_RUN` instead ([Evals](#evals)). `org.moqui.agent.AgentAdminServices.rollup#LlmUsage` and `clean#LlmCallContent` are `authenticate="false"` and run only with authorization disabled (the jobs) or for an `AgentAdmin`; `clean#LlmCallContent` takes `retentionDays`. Their callers are the jobs and the `rollupUsage` transition of System › LLM › Usage. `org.moqui.agent.AgentServices.record#AgentRunUsage` loads a run by id where it has an `externalHarnessId`, writes steps and cost to it and can request its cancel, only with authorization disabled or for the run's own user (anyone else is told the run is not found). Only its definition in `AgentServices.xml` names it: no screen, rest-api file or other code in this repository calls it.

`LlmCall.requestJson` and `responseJson` are kept only when `llm-facade/content-log@enabled` is true (default false), redacted by key name and token shape, not encrypted, and cleared after `retention-days` (14) by the job `clean_LlmCallContent_daily`. Conversations, messages, tool arguments and results, and run events are stored always, unencrypted. `get#LlmCallContent` and `get#AgentAuditView` show content to its own user, or to a user with `AgentAudit`, and write an `AgentAuditLog` row for each such read. From those two services `AgentAdmin` alone gets metadata. The Evals › Runs screen is another path to content, with `AgentAdmin` alone and no `AgentAuditLog` row ([Evals](#evals)). The four list screens (calls, conversations, runs, approvals) select metadata fields only; the content fields are plain columns of the same entities. A find's `search-form-inputs` takes the whole context, which holds the request's parameters, and tests every field of the entity against it except those in `skip-fields`, password fields and, for a generic find, encrypted ones; `orderByField` is filtered the same way (`crates/moqui-entity/src/entity/search_form.rs`). The four lists name their content fields in `skip-fields`, so a request puts a condition or an order only on the other columns (ids, dates, counts and names). A tool call's arguments are stored whole in `AgentToolCall.argumentsJson`, the message part and the `tool.call` event; a result in the tool message, its first 4000 characters in `resultSummary` and 2000 in the `tool.result` event. An approval card leaves out arguments named like secrets; the approval's stored `argumentsJson` does not.

### Evals

Seven screens under System › LLM › Evals have eleven POST transitions (`Scorers.xml`, `Runs.xml`, `Experiments.xml`, `ExperimentDetail.xml`, `DatasetDetail.xml`, `Datasets.xml`). The parent screen needs `AgentAdmin`; each write also needs `MONITOR_EVAL` or `MONITOR_EVAL_RUN`, checked in the script (`runtime/components/base/framework/service/org/moqui/agent/AgentEval.js` `need`). `advance#Experiments` and `score#LiveRuns` need `MONITOR_EVAL_RUN` when a user calls them (Check now in `ExperimentDetail.xml`). Nothing in the eval services or screens writes an audit row.

Evals › Runs reads `AgentRun`, `AgentMessage` and `AgentMessagePart` with authorization off for the 50 newest runs, or one run by `runId`, of any user, and lists the first 300 characters of the run's user message, 500 of its reply and the scores' reasons only for a run that `check#RunReadable` gives: the viewer's own, or another user's with `AgentAudit`, each such read written to `AgentAuditLog` (`readsRun` in `AgentEval.js`; plans/Security-Review-Medium.md SEC-AI-83, fixed); another user's run is listed with its status and scores only, and is not offered to the forms. `MONITOR_EVAL` gates the screen's two forms. `save#RunAsDatasetItem` copies a run's whole user message, and with `useOutput=Y` its whole reply, into a dataset item that Dataset detail and Experiment detail show, and `score#Run` with a judge scorer sends both to the model and stores the model's reasoning in `AgentScore.reason`; both refuse another user's run without `AgentAudit` and log it with it. Another user's run is listed without its scores too, which a judge's rubric or a Contains scorer's terms would make tell what it said. Live scoring (`score#LiveRuns`, a job) scores every user's runs of an agent a scorer is attached to, so attaching one (`Scorers.xml` `attachAgent`) needs `AgentAudit` and is written to `AgentAuditLog`; a service scorer of a service other than the evals' own (`score#ExactMatch`, `score#Contains`, `score#CalledTool`) is made only by an `AgentAudit` holder and runs with the caller's own authorization, never as the system (`check#ScorerChange`, `scoreOne` in `AgentEval.js`; SEC-AI-83).

An experiment runs each current item of a dataset `trials` times, at most 200 items times trials. Through an agent, each item's text is the user message of a job-surface run of the user who pressed Start (`ec.llm.startRun`; that user needs `AgentUse` and `AgentAdmin`). Those runs start without the `approval.policy` capability, so no policy rule approves a write by itself, unless the experiment's `policyWrites` is Y (`approval::is_background`; [Approvals](#approvals)); a dataset item saved from a run records the run's user (`runUserId`). Through a service, `asPerson` runs the service the experiment names with authorization on, as the current user (in the job, as the experiment's starter), with the parameters `input` and `metadata`, and stores its whole out-map as the result's `outputText`. A scorer of type `AgstService` names a service the same way, called with `input`, `output`, `groundTruth`, `runId`, `metadata` and `config`; a scorer of a service other than the evals' own runs as a person too. The name is free text; nothing checks that it is a scorer or a target.

Two jobs run with no user: `advance_AgentExperiments_frequent` each minute and `score_AgentLiveRuns_frequent` every five minutes (`AgentEvalData.xml`). The first runs each experiment as the user who started it (`asStarter`); the second runs a scorer of another service as the user who attached it (`AgentScorerAttach.attachedByUserId`, written by `attach#Scorer`), and an attach that names no one is logged once and not run. For a judge scorer they call the model on the content of users' runs.
