# Attack surface: PASS Forum and Smithy

The Forum and Smithy (public git hosting), as mr-pass pages and the Mantle services behind them. How every PASS page reaches the authority, public accounts and sites are in [Attack-Surface-Apps-PASS.md](Attack-Surface-Apps-PASS.md); the framework's git and pipeline layer is in [Attack-Surface-Git.md](Attack-Surface-Git.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## Forum

The Forum is the PASS app `forum`: pages under `mr-pass/screen/Forum/`, operations under `mr-mantle/service/mantle/forum/`.

**The pattern shared with Smithy.** Every Forum and Smithy operation is a Mantle service that is `authenticate="anonymous-all"`, takes one `input` map and calls `Forum.js` or `Smithy.js` `execute(operation, input)`. `execute` refuses a field that the operation's entry in `ForumSchema.js` or `SmithySchema.js` does not list, checks each value's type (Smithy: a string of at most 4,096 characters, 200,000 for a text field, 8 MiB for a file's text, a list of at most 100 strings), and runs the operation with authorization disabled. The caller is `ec.user`; no input field names the caller, and each operation decides access from that user. A user in the `ADMIN` group is an operator (`ForumCore.js` `isOperator`): on a page an operator counts as the owner of every site and as an Owner of every Smithy group and repository, confidential issues included. A write that takes an `operationId` keeps a `ForumOperationReceipt` row by site, party, operation id and action, with a hash of the input and the answer as JSON without its `token` and `credential` keys; a retry answers the stored result (`ForumCore.js` `receipt`).

**Sites, categories and topics.** `ForumCore.js` `site(id)` answers Not Found for a site that is not published unless the caller is its owner, an operator or internal staff. `site(id, true)` also needs the site's owner (active, not suspended) or an operator; it guards the settings operations (members and roles, categories, mail settings and routes, invitations, `storePolicy`, `storeRule`, `setTrust`, `manageRun`, `startOperation`). `createSite` needs an operator. A category is read when the caller moderates it, or when site and category are published and the category is `public`, or the caller is an active member and the category is `members`, or the caller is on its list or holds a grant. A category bound to a Smithy group or repository is read by no more than view of that scope, and a child category only when its parent is. A private conversation is read through an active participant row and current membership only; staff have no access to it.

**Moderation.** `staff(siteId, contactListId)` with a category needs `canModerate` in that category of that site; with none it needs an operator, or an active, unsuspended member of the site with the role owner or moderator. `getReview`, `decideReview`, `decideReviews` and `escalateReview` find a review item by `reviewId` and the path's `siteId` together, then ask `reviewStaff` with the item's own category. `applyTopicAction` needs `canModerate` on the topic, found in the path's site. `setSanction` needs staff of the site or of the category named, a target that is a member of the site, and a rank above the target's (operator, site owner, site moderator, list owner or the bound scope's Owner, list moderator). `endSanction` finds the sanction by site and id and needs staff of its category.

**Attachments.** `stageAttachment` needs a signed-in user who may upload in the topic or category. A file is 1 byte to `mediaMaxBytes` (at most 10 MiB); its type is the upload's declared content type and must be PNG, JPEG, WebP, GIF, PDF or plain text. The upload is refused unless `pass@scanner-service` and `pass@media-root` are set; the file is written to `<pass@media-root>/<attachmentId>`, scanned and marked `clean` or `quarantined`. A member with 20 files or 50 MiB staged in the site and not yet on a post is refused (`Tarpit`, `limitReached`), and each upload is counted against the day's `uploads` of the member's trust level (new 10, basic 50, member 200, regular 400), both before anything is written; a staged file that no post takes expires after 7 days. `getAttachment` serves only a clean file of the site attached to a post the caller reads, or an avatar of a profile the caller is shown.

**Exports.** `requestPersonalDataAction` (a signed-in member; `export` or `erasure`) and `startOperation` with `export-site` (the site's owner or an operator) make a `ForumExport` row whose file is `<pass@media-root>/exports/<exportId>.zip` and which expires after 7 days. `getExport` answers only a complete, unexpired export of the path's site whose `partyId` is the caller, and asks again for the site's owner or an operator when it is a site export. It answers the row's `location`; `getExport` is in the authority's `DOWNLOADS` list.

**The delivery opt-out.** `inspectOptOut` and `applyOptOut` need no sign-in and no session; the authority takes `applyOptOut` as a write with no delegation. The token is looked up by its hash and the site and is refused after `expiresAt`. Its `ForumOptOut` row names one party and one scope (a category, a topic or the site); applying it writes that party's `ForumDeliveryPreference` for that scope, or for the whole site when asked, and nothing else.

**Inbound list mail and reply by email.** `mantle.forum.DeliveryServices.process#Inbound` (`anonymous-all`) takes a message's `headers`, `fields` and body parts as parameters and gives them to `Forum.js` `processInbound`. The route is the enabled `ForumMailRoute` whose address equals a `Delivered-To` or `Original-Recipient` address with its `+tag` taken off (the `To` and `Cc` addresses when neither field is there). A message stored in a mail account is read only when that account is hosted or shared, its server has no store host, and it holds the route's address (`forumAccount`). The sender is the `From` address. A post needs all of: exactly one enabled `UserAccount` with that email address, a `VerifiedAddress` row for it, and an `Authentication-Results` field of an authserv-id listed in `smtp-server@authserv-id` that says DMARC passed for the `From` domain, or DKIM passed for a `header.d` (or `header.i`) that is that very domain (`gatewayAuthenticated`, strict alignment: a parent's signature is not the subdomain's). With `smtp-server@authserv-id` empty nothing is taken as authenticated. The listener's own field and its removal of forged ones are in [Mail](Attack-Surface-Mail.md). A reply address is `<local>+<token>@<domain>` of a route. The token is 32 random characters, stored as a hash in `ForumReplyToken` with the site, the topic, the party and 90 days. A tag that is unknown, of another site, revoked or expired is rejected; one issued to another party than the sender's account is held. With no tag the topic is found from `In-Reply-To` and `References` among the `ForumDelivery` rows of the sender's own party. A route whose `targetType` is not `category` (a report address) ignores the tag and files the message through the service the bound app names (`mailReportService`), with the account's `username` as a parameter.

**Held list mail.** A message from an address that is no verified account's is not posted. It is kept as a `ForumHeldMail` row for 30 days when the gateway authenticated the sender's domain, it has no spam verdict and no reply tag, and the route holds mail; its sender is mailed a link `<forum>/held-mail/<token>` at most once a day, and the token is stored as a hash. `claimHeldMail` (`POST .../held-mail/<token>/claim`) needs a signed-in user whose account has a `VerifiedAddress` row for its current email address, equal to the held message's sender; the message is then posted as that account through `publishPost`.

**User text.** A post's source is HTML or Markdown. Markdown is rendered by `ec.resource.markdownHtml`, and either is cleaned by `StringUtilities.cleanHtml` before it is stored (`ForumCore.js` `renderSource`) and again when a post is read. The cleaner is `crates/moqui-lib/src/safe_html.rs`: ammonia's default list, with `data-mention-id`, `data-record-entity` and `data-record-id` added on a `span`.

## Smithy

Smithy is the PASS app `smithy`: pages under `mr-pass/screen/Smithy/`, operations under `mr-mantle/service/mantle/smithy/`, in the pattern described under [Forum](#forum). The git server, its REST, webhooks, mirrors and the pipeline engine are the framework's ([Git](Attack-Surface-Git.md)).

**Who views a group or a repository.** A read starts with `SmithyCore.js` `repository(repositoryId, siteId)` or `group(groupId, siteId)`. Each answers Not Found when the site is not open to the caller or has no enabled Smithy mount, when the row is of another site, or when the caller may not view it. The effective visibility is the narrowest of the repository's, its groups' and, for a fork, its parents'. Public is anyone's. Members-only is an active, unsuspended member of the site. Private needs a role of Guest or higher. A hidden repository or group is viewed by its Owners and the site's owners and moderators only. A fork of a parent that is not public also needs view of the parent. A write then calls `requireRole`, and most writes first call `writer(siteId)`: a signed-in user with a confirmed address (an operator excepted) who is not suspended on the site.

**Members and roles.** `setGroupMember` and `setRepositoryMember` need Owner of the group or repository; no lower role changes a role, its own included. A group, with the groups above it, keeps one Owner whose role has no end. Creating a subgroup, and changing, renaming, deleting, transferring or archiving a group or repository or changing its visibility, ask for Owner. A repository is no wider than its group, and a fork no wider than its parent.

**Issues and conversations.** An issue is read by a viewer of a repository whose issues are on, when its task is public or the caller is a Reporter. A confidential issue is read by the repository's Owners and its reporter only; `findIssues` builds the same rule into its query and its counts, and `searchSite` asks `issueAccess` for each row. An issue's or a merge request's conversation is a `ForumTopic` of kind `record`: `ForumCore.js` `topic()` asks `SmithyScope.js` `recordAccess` for it and refuses the Forum's own operations on it.

**Code reads, raw files and archives.** `getTree`, `getBlob`, `getBlame`, `findCommits`, `getCommit`, `getCompare` and `findRefs` call `repository()` first and then the framework's `get#Git*` services with authorization disabled. Raw (`<repository>/-/raw/<refPath>`) answers text as `text/plain`, a PNG, JPEG, GIF or WebP by its extension, and any other binary file as `application/octet-stream`, with `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, and `Content-Disposition: attachment` for anything but plain text and those images. An SVG or HTML file is sent as `text/plain`. An archive of a branch or tag of a public repository that is not hidden needs no sign-in; any other archive, and one by commit id, needs a signed-in user. No limit of archive builds by client is in Smithy. A README, a docs page, a landing page and release notes are Markdown, rendered and cleaned as under [Forum](#forum).

**Forks and merge requests.** `forkRepository` needs `writer`, and Developer when the repository is not public. A fork into a group needs Maintainer of that group. The site's `forkCreateEnumId` must be `ScpVerified` unless the caller is the site's owner. `createMergeRequest` needs `writer` and Developer in the source repository; a source in another repository is found by `repository()` in the same site, and the framework's refusal of a source outside the fork network is passed on. Naming reviewers needs Developer in the target. A merge request whose text the post gate holds is opened hidden.

**Pipelines.** A pipeline run, its jobs, a job's log (`getJobLog`) and its artifacts (`downloadArtifact`) are read by whoever views the repository, a visitor of a public repository included. Run, re-run and retry need Developer; `approvePipelineRun` needs Maintainer. The run check (`check#Run`, `git-ci` `run-check-service`) lowers trust and never raises it: a run is untrusted when its commits come from a fork, a push for review or a detached merge request, or when the account that caused it, the merge request's author or the head's pusher is below Developer. An untrusted run waits for a Maintainer by `outsideRunApproval` (`first`, `always`, `never`), is refused above `outsideRunMaxJobs` jobs, and counts against the account's daily runs. `storeCiSecret`, `deleteCiSecret` and `storeCiEnvironment` need `writer` and Maintainer. `findCiSecrets` answers names, scopes and dates; no read answers a secret's value, and the receipt is made without it. An environment's `allowedRefs` made only of wildcards is refused, as is a `targetUrl` or `cloneUrl` with a user or password in it; its token is write-only (`hasToken`). `requestDeploy` needs Developer. `decideDeploy` needs Maintainer and refuses the account that asked for the deployment.

**Git access (`Account/GitAccess`).** `findGitAccess`, `addSshKey`, `removeSshKey`, `createAccessToken` and `revokeAccessToken` (`SmithyGit.js`) act on the caller's own account through the framework's `create#UserSshKey`, `create#UserAccessToken` and their find, delete and revoke services. Adding a key or a token needs `writer` and a fresh proof: the account's password (and second factor code) checked by `login#UserAccount`, or, for an account with no password, a sign-in within five minutes (`RECENT_SIGN_IN`, the window of `require#RecentAuth`): through a remote frontend the visitor's own, its delegation's issue (`PassAuthority.js` `passSignedInAt`, SEC-PFS-63); in local mode this session's own (`check#RecentAuth`, 300 seconds: a password, a second factor's code or a provider sign-in with its `auth_time`; never another session's or a login key's). With an account already signed in, `startSso` asks the provider to sign the user in again (`reauth: true`). An account has at most 20 keys and 20 tokens. An access token is a framework login key of scope `git` (`moqui.security.UserLoginKey` with a `description` and `scope` `git`, `crates/moqui-core/src/service/user_keys.rs` `create_access_token`): git over HTTP and the git REST take it, and the web, the rest of REST, sockets, A2A and PASS pages refuse it. It lasts until the date asked (at most 366 days), else 90 days. Only its hash is stored; the token is answered once and is not in the receipt. The authority refuses every PASS operation to a request signed in by an access token or a session's key, and all but `APP_KEY_OPERATIONS` to a device's key (`PassAuthority.js` `run`); in local mode the frontend applies the same rule (`Facade.js` `checkLoginKey`).

**Webhooks and push mirrors.** The webhook and mirror operations need Maintainer, and an id must be of the repository in the request. A repository has at most 10 webhooks. The URL and the secret go to the framework's `store#GitWebhook`; `findWebhooks` answers the URL whole and `hasSecret`, never the secret. On a create, `storeWebhook`'s receipt row holds a hash of the input without the secret, as `storeMirror`'s (SEC-PFS-62). `testWebhook` is limited to 3 a minute for a repository and answers the status code and delivered or not. A mirror's URL must match `https://<host>[:port]/<path>` with no `@`; the credential is a field of its own and only `hasCredential` is answered. A changed URL of a mirror with a stored credential needs the credential again or its removal, and `lastError` is scrubbed of credentials. The address rules (no loopback, private or link-local address) are the framework's ([Git](Attack-Surface-Git.md)). Smithy's `check#Outbound` (`git-server` `outbound-check-service`) refuses webhook deliveries and mirror pushes of a repository whose site has no Smithy mount, of a hidden repository and of one whose owner is suspended, and refuses when the check itself fails.

**The GitHub import.** `startGitHubImport` needs `writer` and Owner of the target group; an existing target repository must be in that group and needs Owner. The source is a name `owner/name`, never a URL. The API base is the property `mantle@smithy-github-api` (default `https://api.github.com`), not an input. The caller's token is sent as `Authorization: Bearer` to that base, is kept for the run in the encrypted `password` of a `SystemMessageRemote` row, and is not in the receipt. A clone address that GitHub answers is refused unless it is `https` on the API's host. Pull request heads are fetched by the framework's `fetch#GitRefs` with that address and the token as the password; no file under `service/mantle/smithy/` names `import#GitRepository`. A private source into a wider group or repository is refused without `publishPrivate`.

**The GitHub identity claim at SSO sign-in.** Mantle sets `user-facade` `login` `sso-linked-service` to `mantle.smithy.SmithyImportServices.handle#SsoLinked` (`authenticate="false"`). It claims nothing unless the flow is an `OauthFlow` of type `OctGitHub` whose endpoints are empty or exactly github.com's (or one Enterprise Server host's), `providerHost` is `api.github.com` (or that host), and the account holds that `externalUserId` and `externalAuthFlowId`. It then moves, in each site where the account is an active, unsuspended member, the records of the import's placeholder with the same numeric GitHub id and host to the account (posts, issues, merge requests, assignments, reactions). No role or repository ownership is moved.

**Smithy and the framework's git REST.** For a repository Smithy keeps, `check#RestWrite` (`git-server` `rest-write-check-service`) refuses every write of the framework's git REST and allows `read` and `commitStatus.create`. Mantle's `MoquiConf.xml` sets `reserved-status-contexts="agreement/,ci/,deploy/"` and `review-start-hidden="true"`. The review threads of the framework's REST are answered by `mantle.work.GitServices.handle#GitReviewThread`: the caller must be signed in and view the repository, and a hidden merge request is its author's alone. For a repository Smithy keeps, each comment in that answer carries no `fromPartyId`, and `authorName` and `authorHandle` from the site profile when `SmithyCore.authorShown` lets the caller see it, else empty (SEC-PFS-01); another repository's comments carry `fromPartyId` and an `authorName` built from `PartyDetail`. The hook services (`check#Push`, `check#LfsUpload`, `check#Outbound`, `check#RestWrite`, `check#Run` and others) are `anonymous-all`, take `repositoryId` and a user id as parameters, and are not in `PassRoutes.js`.

**Redirects.** The `redirect` transition of `mr-pass/screen/Smithy.xml` (`method="get"`, `read-only="true"`) takes a `location` parameter and calls `redirectRoute` (`screen/Smithy/Smithy.js`). It answers 301 to the location with the request's query added when the location is a path on the site (`siteLocal`: one leading `/` not followed by `/` or `\`, no backslash or control character), or an `https` address whose host `getSiteInfo` finds among the site's `PublicSiteHost` rows and that is not the site's theme preview host. Any other location fails.
