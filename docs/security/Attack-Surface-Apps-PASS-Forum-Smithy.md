# Attack surface: PASS Forum and Smithy

The Forum and Smithy (public git hosting), as mr-pass pages and the Mantle services behind them. How every PASS page reaches the authority, public accounts and sites are in [Attack-Surface-Apps-PASS.md](Attack-Surface-Apps-PASS.md); the framework's git and pipeline layer is in [Attack-Surface-Git.md](Attack-Surface-Git.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## Forum

The Forum is the PASS app `forum`: pages under `mr-pass/screen/Forum/`, operations under `mr-mantle/service/mantle/forum/`.

**The pattern shared with Smithy.** Every Forum and Smithy operation is a Mantle service that is `authenticate="anonymous-all"`, takes one `input` map and calls `Forum.js` or `Smithy.js` `execute(operation, input)`. `execute` refuses a field that the operation's entry in `ForumSchema.js` or `SmithySchema.js` does not list, checks each value's type (Smithy: a string of at most 4,096 characters, 200,000 for a text field, 8 MiB for a file's text, a list of at most 100 strings), and runs the operation with authorization disabled. The caller is `ec.user`; no input field names the caller, and each operation decides access from that user. A user in the `ADMIN` group is an operator (`ForumCore.js` `isOperator`): on a page an operator counts as the owner of every site and as an Owner of every Smithy group and repository, confidential issues included. A write that takes an `operationId` keeps a `ForumOperationReceipt` row by site, party, operation id and action, with a hash of the input and the answer as JSON without its `token` and `credential` keys; a retry answers the stored result (`ForumCore.js` `receipt`).

**Sites, categories and topics.** `ForumCore.js` `site(id)` answers Not Found for a site that is not published unless the caller is its owner, an operator or internal staff. `site(id, true)` also needs the site's owner (active, not suspended) or an operator; it guards the settings operations (members and roles, categories, mail settings and routes, invitations, `storePolicy`, `storeRule`, `setTrust`, `manageRun`, `startOperation`). `createSite` needs an operator. A category is read when the caller moderates it, or when site and category are published and the category is `public`, or the caller is an active member and the category is `members`, or the caller is on its list or holds a grant. A category bound to a Smithy group or repository is read by no more than view of that scope, and a child category only when its parent is. A private conversation is read through an active participant row and current membership only, with one exception, a review item: site staff read a private post with the approved post before and after it, and ten each side once an escalation is approved (`ForumModeration.js` `getReview`, `privateContext`). The item is filed by a member's report, or by a site rule whose action is `flag` or `approve` and that matches the post: `ForumCore.js` `gate` sets `flag` for a private post under such a rule, and `publishPost` and `updatePost` file the review with the conversation's category, which is null, so `reviewStaff` asks `staff(siteId, null)`, any site owner or moderator. The site's owner may both ask for an escalation and approve it.

**Moderation.** `staff(siteId, contactListId)` with a category needs `canModerate` in that category of that site; with none it needs an operator, or an active, unsuspended member of the site with the role owner or moderator. `getReview`, `decideReview`, `decideReviews` and `escalateReview` find a review item by `reviewId` and the path's `siteId` together, then ask `reviewStaff` with the item's own category. `applyTopicAction` needs `canModerate` on the topic, found in the path's site. `setSanction` needs staff of the site or of the category named, a target that is a member of the site, and a rank above the target's (operator, site owner, site moderator, list owner or the bound scope's Owner, list moderator). `endSanction` finds the sanction by site and id and needs staff of its category, and nothing more: no rank above the sanctioned member's and no test that the caller is not that member. `getMember` (`GET moderation/members/{id}`) needs staff of the site or of the category named; only a bound scope's Owner is narrowed to its scope, so a list's owner or moderator reads any site member's membership and member state (trust level, contributions, reading statistics). `storeRule` and `testRule` need the site's owner. `validRule` refuses a quantified group that holds `+`, `*` or `}`, and back references, and a pattern is at most 200 characters; `applyRules` runs up to 200 rules on a post's plain text plus its HTML, with the script engine's backtracking `RegExp`.

**Members, drafts, tags and invitations.** `setMembership` (`PATCH members/{targetPartyId}`, the site's owner) sets any state on any membership row, one its member ended with `leaveSite` included, and asks no re-authentication, where `setSiteRole` and a category role change ask the password and code again (`login#UserAccount`); `protectOwner` refuses only a change that would leave no other active, unsuspended owner. `joinCategory` writes one more `CLPT_PENDING` row on each call in a category that asks approval, and tests the member's state alone. `storeDraft` and `previewPost` need a signed-in account with a party, member of the site or not; they check no length and count nothing, and nothing expires a `ForumDraft`. `findTags` (anonymous on a published site) reads up to 100 tags and up to 1,000 topics of each through `topic()`. `inviteListMembers` takes 500 addresses a call, and site owners and operators skip its day's limits.

**Attachments.** `stageAttachment` needs a signed-in user who may upload in the topic or category. A file is 1 byte to `mediaMaxBytes` (at most 10 MiB); its type is the upload's declared content type and must be PNG, JPEG, WebP, GIF, PDF or plain text. The upload is refused unless `pass@scanner-service` and `pass@media-root` are set; the file is written to `<pass@media-root>/<attachmentId>`, scanned and marked `clean` or `quarantined`. A member with 20 files or 50 MiB staged in the site and not yet on a post is refused (`Tarpit`, `limitReached`), and each upload is counted against the day's `uploads` of the member's trust level (new 10, basic 50, member 200, regular 400), both before anything is written; a staged file that no post takes expires after 7 days. `getAttachment` serves only a clean file of the site attached to a post the caller reads, or an avatar of a profile the caller is shown; it writes the thumbnail file the first time one is asked (always a PNG, served inline; the full file goes out as `attachment` with `nosniff`). These upload rules are `stageAttachment`'s: the Discourse import makes `ForumAttachment` rows of any type, taken from the source file name, with the source's file name and the size the dump gives (`ForumImport.js`). Over the remote transports the authority answers a download's type through `servedType` with the sandbox policy; in local mode `mr-pass/service/pass/Facade.js` `download` (`getAttachment`) and `downloadExport` (`getExport`) set the stored type as it is, with no inert-type rule and no sandbox, where `downloadFile` and `downloadRanged` apply both.

**Exports.** `requestPersonalDataAction` (a signed-in member; `export` or `erasure`) and `startOperation` with `export-site` (the site's owner or an operator) make a `ForumExport` row whose file is `<pass@media-root>/exports/<exportId>.zip` and which expires after 7 days. `getExport` answers only a complete, unexpired export of the path's site whose `partyId` is the caller, and asks again for the site's owner or an operator when it is a site export, and `staff()` when it is a report export. It answers the row's `location`; `getExport` is in the authority's `DOWNLOADS` list. A site export writes every `kind: 'category'` topic of the site (or of the one category named) with every post of every visibility (pending, rejected and deleted included), each revision's `sourceText` and the author and editor ids, and `site.json`, `categories.json`, `tags.json`, `mail-routes.json`, `policy.json` and a manifest (`ForumOperations.js` `topicFind`, `exportTopic`). It asks no category access, so it holds the categories bound to a private Smithy scope, which the site's owner does not read. A personal export holds the member's profile, memberships, posts of every kind, drafts, bookmarks and preferences. `exportReport` (`POST reports/exports`, the category's staff) makes CSV exports. Only an erasure is limited to one open request; exports have no count, and the dispatcher takes the 50 oldest pending operation runs (`op-%`) of all sites each minute.

**The delivery opt-out.** `inspectOptOut` and `applyOptOut` need no sign-in and no session; the authority takes `applyOptOut` as a write with no delegation. The token is looked up by its hash and the site and is refused after `expiresAt`. Its `ForumOptOut` row names one party and one scope (a category, a topic or the site); applying it writes that party's `ForumDeliveryPreference` for that scope, or for the whole site when asked, and nothing else. The delivery worker mints one token for each mail: 64 random characters, the hash stored, good 365 days; the mail's `List-Unsubscribe` is `<origin><account>/Unsubscribe/oneClick?token=`, with `List-Unsubscribe-Post: List-Unsubscribe=One-Click`.

**The delivery worker.** The job `pass_dispatch_outbox` (every minute) runs `DeliveryWorker.js` `dispatch`; nobody reaches it directly, and posts make its outbox rows. Recipients come only from watchers, mailing-list subscribers, the parent post's author, mentioned handles (at most 20 a post) and a private conversation's participants, and each is decided again at send time with the recipient's own access (membership, sanctions, mutes, the source gate, the root post's review); no request value names an address. The address is the party's first enabled `UserAccount.emailAddress`, and it must be verified. A private conversation's mail has a fixed title and no text; a list's mail in Every-post mode carries the cleaned post (`StringUtilities.cleanHtml(event.body)`) as the template's `body`, which no page policy reaches, so its images load as the reader's mail client loads them. The sender and template are the site's `ForumMailSettings`: `storeMailSettings` (the site's owner) takes any sender of `pass@sender-addresses` with a template of `pass@mail-template-ids` whose `fromAddress` is that sender, both lists the deployment's and not the site's. Each mail also mints a reply token. One queue serves every site: a run prepares the 100 oldest pending outboxes and sends the 100 oldest due deliveries of all sites.

**Inbound list mail and reply by email.** `mantle.forum.DeliveryServices.process#Inbound` (`anonymous-all`) takes a message's `headers`, `fields` and body parts as parameters and gives them to `Forum.js` `processInbound`. Its only caller is the email rule `service/ForumInbound.emecas.xml` (`in-map="context"`), which the framework runs on each new Inbox message of every mail account: from the listener and from IMAP and POP3 sync with the account's `emailAccountId` and `emailMessageId`, and from `poll#EmailServer` with neither. `process#JunkInbound` (from `handle#StoredEmail`, the `ForumJunkInbound` rule on a message stored in Junk) and `retryInbound` (the site's owner, which re-reads the stored message) call `processInbound` with the stored message. `ForumSchema.js` routes no operation to `process#Inbound`, `process#JunkInbound`, `post#Inbound` or `release#HeldMail`, and no REST resource, transition or tool names `process#Inbound` or `post#Inbound`. The route is the enabled `ForumMailRoute` whose address equals a `Delivered-To` or `Original-Recipient` address with its `+tag` taken off (the `To` and `Cc` addresses when neither field is there). A message stored in a mail account is read only when that account is hosted or shared, its server has no store host, and it holds the route's address as its own or as an `EmailIdentity` (`forumAccount`). `forumAccount` does not ask that the account be the forum's own inbound account, so a person's hosted mailbox on a route domain is read as well; with no account and message id (a `poll#EmailServer` run) the check is skipped. `storeRoute` (the site's owner) takes any local part on a domain of `pass@route-domains` that no other route holds; `testRoute` mails the caller's own verified address. The sender is the first `<local@domain>` in the email rule's `fields.from` (`Forum.js` `bareAddress`). That field is the first From mailbox as the listener writes it, `"<name>" <address>` when the display name holds `<`, `>`, `@` or the like (`crates/moqui-mail/src/inbound.rs` `address_text`), so an address written inside the display name is taken before the real one; the stored message's `fromAddress`, which the retry and Junk paths use, is the bare address. A post needs all of: exactly one enabled `UserAccount` with that email address, a `VerifiedAddress` row for it, and an `Authentication-Results` field of an authserv-id listed in `smtp-server@authserv-id` that says DMARC passed with a `header.from` equal to the sender's domain, or DKIM passed for a `header.d` (or `header.i`) that is that very domain (`gatewayAuthenticated`, strict alignment: a parent's signature is not the subdomain's). Only the domain is compared, and the gateway's results are of the real From address. With `smtp-server@authserv-id` empty nothing is taken as authenticated. The listener's own field and its removal of forged ones are in [Mail](Attack-Surface-Mail.md). A reply address is `<local>+<token>@<domain>` of a route. The token is 32 random characters, stored as a hash in `ForumReplyToken` with the site, the topic, the party and 90 days. A tag that is unknown, of another site, revoked or expired is rejected; one issued to another party than the sender's account is held. With no tag the topic is found from `In-Reply-To` and `References` among the `ForumDelivery` rows of the sender's own party. When no topic is found, the message starts a new topic in the route's category, or is rejected. A route whose `targetType` is not `category` (a report address) ignores the tag and files the message through the service the bound app names (`mailReportService`), with the account's `username` as a parameter. Otherwise `post#Inbound` (`authenticate="false"`) signs in as the sender's `username` (`ForumCore.js` `asUser`), stages up to ten files through `stageAttachment` and calls `publishPost`, so the web's checks and gate apply as the sender; a reply to an Owners-only post is posted Owners only. The sender is mailed the outcome. A spam verdict or an unauthenticated sender is never posted or answered.

**Delivery reports.** A message to a route whose `Content-Type` is `multipart/report`, or whose sender is `mailer-daemon@` or `postmaster@`, is read as a bounce before any sender check: a `Status: 5.x.x` that names a delivery's Message-ID sets that member's mail on the whole site to `None`, suppressed (`Forum.js` `bounce`). Auto-replies are recorded, not posted. A Message-ID holds 96 random bits.

**Held list mail.** A message from an address that is no verified account's is not posted. It is kept as a `ForumHeldMail` row for 30 days when the gateway authenticated the sender's domain, it has no spam verdict and no reply tag, and the route holds mail; its sender is mailed a link `<forum>/held-mail/<token>` at most once a day, and the token is stored as a hash. `claimHeldMail` (`POST .../held-mail/<token>/claim`) needs a signed-in user whose account has a `VerifiedAddress` row for its current email address, equal to the held message's sender; the message is then posted as that account through `publishPost`. A held message is also posted with no claim when an account verifies the address: `claim#VerifiedAddress` (the `ForumVerifiedAddress` rule, `entity/ForumInbound.eecas.xml`) posts every held list message of that address as the account that verified it (`ForumLists.js` `claimVerified`). At most 20 messages wait for one address and 200 a day for one route, and the review item shows the scope's moderators the From, the Subject and 3,500 characters of the text.

**User text.** A post's source is HTML or Markdown. Markdown is rendered by `ec.resource.markdownHtml`, and either is cleaned by `StringUtilities.cleanHtml` before it is stored (`ForumCore.js` `renderSource`) and again when a post is read. The cleaner is `crates/moqui-lib/src/safe_html.rs`: ammonia's default list, with `data-mention-id`, `data-record-entity` and `data-record-id` added on a `span`; it keeps `<img src>` of any `http`, `https` or relative address. After cleaning, the gate runs the site's censor rules on the body and stores what `censor` returns; the rule test (`testRule`) answers its censored sample, HTML-encoded before the censor, in a page of its own. The text as typed is kept uncleaned in `ForumPostRevision.sourceText` and `ForumDraft.sourceText`: it is answered for a Markdown post or draft (to a wiki editor of a Markdown wiki post too) and is what `restorePostRevision` posts again, and it is shown only in a `textarea` or cleaned again. Every revision is written with `publicHistoryAllowed: 'Y'`, so `getPostHistory` and `comparePostRevisions` show every revision of a post to every reader of it, an anonymous visitor of a public category included; only the import and the retention purge of a deleted or rejected post set `N`, and nothing hides a revision of a live post. The diff is of plain text and escapes every character it writes.

**Pages.** Every Forum page under `mr-pass/screen/Forum/` renders `mr-pass/screen/Shared/Page.html.fancy` and the form macros; the templates escape `& < > " '`, and the inline `<text>` elements of the 33 Forum screens write no member value. The four `raw()` sites (`Page.html.fancy:8`, `:12`, `:20`, `:52`) write a post's or a reported conversation's body, a category's rules, a bio, the guidelines page, a reported post and the revision diff, each cleaned at the authority (at write and again at read) or escaped. The topic stream and the composer's preview show a post in `m-html-view`: DOMPurify, a frame with `default-src 'none'` and a sandbox without scripts, remote images hidden; no island uses `v-html`, and the islands run on Vue's runtime build, so `{{ }}` in a post is never compiled. The shell's CSP loads images only from `'self'`, `data:` and the brand logo's origin, so a same-site `<img src>` in a post loads with the reader's cookie as a same-origin request, which the rule against cross-site GETs lets through: the site's GET transitions that run with no query string run as each reader who loads the page. `View.js` `preview`, `caseReplyPreview`, `operationPreview` and `invitationResult` are whole documents written as `text/html` by the screens' `save`; each escapes what it takes from the request, and `caseReplyPreview` writes the reply's cleaned and censored body raw to internal staff with posting rights. Every Forum transition calls `pass.Facade.call#Operation` from a script with only the operation's schema fields and the bound site (`View.js` `inputFor`).

**Imports.** The Discourse import (`ForumImport.js`): `registerImport`, `stageImport`, `storeImportMappings`, `runImport`, `activateImport` and `cancelImport` need an operator; `findImports`, `getImport` and `reconcileImport` the site's owner; `approveImport` an operator and a site owner, two people, of the same reconciliation. The archive is a file of `pass@import-dir` named by pattern, with no `..`, and its SHA-256; expansion keeps regular files only, refuses absolute and parent paths and links, and stops at 4 GiB and a million entries, and a `.sql` dump is read into memory whole. The import writes only into the import row's site, fetches no URL, cleans imported text as a post's, makes no outbox rows and turns imported members' mail off. It creates a party, a membership, a profile and, for an active, confirmed source user whose address no account holds, an enabled `UserAccount` with no password and no `VerifiedAddress`, in no group; an identity is joined to an existing account only by the operator, and only to the account that holds that verified address. `resolvePermalink` (anonymous) maps an old path of the imported community and answers only what the reader may read. The mbox import (`importMbox`, `POST categories/{id}/mbox-imports`) is a list's staff's (operator, site owner, list owner or moderator, the bound scope's Owner): it names a file of the same shared `pass@import-dir` with its SHA-256, answers Not Found for a missing name and Conflict for a wrong checksum, and reads the whole file to hash it.

**Integrations.** In `ForumIntegration.js`, `createCaseFromTopic`, `previewCaseReply`, `publishCaseReply` and `draftArticleFromTopic` need internal staff who moderate the topic; a case reply is bound to its preview by hash, and an article draft goes to the site's publishing space. `linkDiscussion` and `detachDiscussion` need the site's owner; `linkDiscussion` takes any existing `productId` or `wikiPageId` of the host, and `getTopicLinks` answers its `productName` or `pagePath` to the topic's moderators, and to every reader when the page has a published version and no subscription binding. An access grant needs staff of its target, never the caller itself. `storeSubscriptionBinding` needs an operator alone; the subscription handlers (`EntitlementServices.xml`, `authenticate="false"`) are named on a `SubscriptionResource` and called by the subscription lifecycle. No Forum integration has an outbound URL, a secret or an inbound callback. `Tracking.js` is an account's read-state mode, changed by two entity rules (`entity/ForumTracking.eecas.xml`) and the job `pass_convert_tracking_modes`; it records nothing about visitors (visitor tracking, `/trk/*`, is Marketing's).

**Reads that write.** No Forum GET writes forum content, but `getAttachment` writes a thumbnail file the first time it is asked, `getReview` of a private post writes a `ForumModerationAction` audit row, and every paged read writes `ForumCursor` rows, an anonymous visitor's too. `site(id, true)` reads the `PublicSite` row `FOR UPDATE` before it checks the owner, so any caller of an operation that calls it locks the row for the length of the call; `setCategoryMember`, `endSanction` and `applyTopicAction` lock the same way.

## Smithy

Smithy is the PASS app `smithy`: pages under `mr-pass/screen/Smithy/`, operations under `mr-mantle/service/mantle/smithy/`, in the pattern described under [Forum](#forum). The git server, its REST, webhooks, mirrors and the pipeline engine are the framework's ([Git](Attack-Surface-Git.md)).

**Who views a group or a repository.** A read starts with `SmithyCore.js` `repository(repositoryId, siteId)` or `group(groupId, siteId)`. Each answers Not Found when the site is not open to the caller or has no enabled Smithy mount, when the row is of another site, or when the caller may not view it. The effective visibility is the narrowest of the repository's, its groups' and, for a fork, its parents'. Public is anyone's. Members-only is an active, unsuspended member of the site. Private needs a role of Guest or higher. A hidden repository or group is viewed by its Owners and the site's owners and moderators only. A fork of a parent that is not public also needs view of the parent. A write then calls `requireRole`, and most writes first call `writer(siteId)`: a signed-in user with a confirmed address (an operator excepted) who is not suspended on the site. Each of the 145 operations of `SmithySchema.js` has a route in `script/PassRoutes.js` and runs through `Smithy.js` `execute`. Each other id given with a repository is matched to it (branch rule, webhook, mirror, CI secret and environment, run, job, artifact, deployment, release asset, merge request and thread, issue, label, milestone, import run), and a redirect id to the site.

**Members and roles.** `setGroupMember` and `setRepositoryMember` need Owner of the group or repository; no lower role changes another's role, and `leaveGroup` lets any member delete its own row, the last Owner excepted. A group, with the groups above it, keeps one Owner whose role has no end. Creating a subgroup, and changing, renaming, deleting, transferring or archiving a group or repository or changing its visibility, ask for Owner. A repository is no wider than its group, and a fork no wider than its parent. `transferRepository` needs Owner of the repository, which a role on that repository alone gives; a target group must be viewed and the caller a Maintainer of it, and with no target the repository goes to the caller's own namespace, so it is given to nobody else; quotas, the path and the old group's shared project are checked. It asks nothing of the group the repository leaves and does not test whether the repository is hidden, so a repository hidden only by its group's hide is shown at its own visibility once moved. It keeps the repository's own role rows, its project, webhooks, mirrors, CI secrets and environments, branch rules and forks, applies the agreement of the new place again (`keepRules`) and syncs the confidential projects. `deleteRepository` needs Owner and `confirmPath`, is refused while forks exist, and deletes through the framework last. Quotas are read by the group's Owner, the account or the site's owners, and set by the site's owners.

**Issues and conversations.** An issue is read by a viewer of a repository whose issues are on, when its task is public or the caller is a Reporter. A confidential issue is read by the repository's Owners and its reporter only; `findIssues` builds the same rule into its query and its counts, and `searchSite` asks `issueAccess` for each row. An issue's or a merge request's conversation is a `ForumTopic` of kind `record`: `ForumCore.js` `topic()` asks `SmithyScope.js` `recordAccess` for it and refuses the Forum's own operations on it.

**Code reads, raw files and archives.** `getTree`, `getBlob`, `getBlame`, `findCommits`, `getCommit`, `getCompare` and `findRefs` call `repository()` first and then the framework's `get#Git*` services with authorization disabled. `findRefs` for branches reads the open merge requests by source branch with no `hiddenDate` condition, so it answers the number of a hidden one; `getRepository` and `getCompare` leave hidden ones out. Raw (`<repository>/-/raw/<refPath>`) answers text as `text/plain`, a PNG, JPEG, GIF or WebP by its extension, and any other binary file as `application/octet-stream`, with `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, and `Content-Disposition: attachment` for anything but plain text and those images. An SVG or HTML file is sent as `text/plain`. An archive of a branch or tag of a public repository that is not hidden needs no sign-in; any other archive, and one by commit id, needs a signed-in user. No limit of archive builds by client is in Smithy. A README, a docs page, a landing page and release notes are Markdown, rendered and cleaned as under [Forum](#forum).

**Forks and merge requests.** `forkRepository` needs `writer`, and Developer when the repository is not public. A fork into a group needs Maintainer of that group. The site's `forkCreateEnumId` must be `ScpVerified` unless the caller is the site's owner. `createMergeRequest` needs `writer` and Developer in the source repository; a source in another repository is found by `repository()` in the same site, and the framework's refusal of a source outside the fork network is passed on. Naming reviewers needs Developer in the target. A merge request whose text the post gate holds is opened hidden.

**Branch rules.** `storeBranchRule` and `deleteBranchRule` need `writer` and Maintainer, and a rule id must be of the repository. `createRef` (Developer) refuses a ref a rule keeps from a direct push, and `deleteRef` (Maintainer) a ref a rule keeps from deletion. A rule pattern without `refs/` names branches only, so a tag is protected only by a `refs/tags/...` pattern. Where the agreement is required, `syncRules` forces the default branch's rule to require a merge request and `agreement/authors` after every rule change. A force push or a ref delete over git needs the delete right (Maintainer) and is still held to every rule (no role passes a rule but the rule's push group); a merge by the API passes `requireMergeRequest` but not approvals, contexts or methods; a write through a `git://` resource location moves a protected branch and is only logged.

**Pipelines.** A pipeline run, its jobs, a job's log (`getJobLog`) and its artifacts (`downloadArtifact`) are read by whoever views the repository, a visitor of a public repository included, with three limits: a run of a merge request only by who reads that merge request (a held one: its author and moderators), a hidden run only by Owners and staff, and a log or an artifact only while pipelines are on (`SmithyPipelines.js` `visible`). Run, re-run and retry need Developer; `approvePipelineRun` needs Maintainer. The run check (`check#Run`, `git-ci` `run-check-service`) lowers trust and never raises it: a run is untrusted when its commits come from a fork, a push for review or a detached merge request, or when the account that caused it, the merge request's author or the head's pusher is below Developer. An untrusted run waits for a Maintainer by `outsideRunApproval` (`first`, `always`, `never`), is refused above `outsideRunMaxJobs` jobs, and counts against the account's daily runs. `storeCiSecret`, `deleteCiSecret` and `storeCiEnvironment` need `writer` and Maintainer. `findCiSecrets` answers names, scopes and dates; no read answers a secret's value, and the receipt is made without it. An environment's `allowedRefs` made only of wildcards is refused, as is a `targetUrl` or `cloneUrl` with a user or password in it; its token is write-only (`hasToken`). `requestDeploy` needs Developer, and passes `commitId` and `refName` to the engine's `request#GitDeployment` with authorization off. `decideDeploy` needs Maintainer and refuses the account that asked for the deployment. `storePipelineSettings` needs Owner of the group; a pool must be one the operator allowed the group's owner key for that trust, and `never` only the top-level group's Owner sets. Smithy gives the engine only the run check's decision, the trust, the owner and the pool; secrets and an environment's token are written to the engine and never read back.

**Git access (`Account/GitAccess`).** `findGitAccess`, `addSshKey`, `removeSshKey`, `createAccessToken` and `revokeAccessToken` (`SmithyGit.js`) act on the caller's own account through the framework's `create#UserSshKey`, `create#UserAccessToken` and their find, delete and revoke services. Adding a key or a token needs `writer` and a fresh proof: the account's password (and second factor code) checked by `login#UserAccount`, or, for an account with no password, a sign-in within five minutes (`RECENT_SIGN_IN`, the window of `require#RecentAuth`): through a remote frontend the visitor's own, its delegation's issue (`PassAuthority.js` `passSignedInAt`, SEC-PFS-63); in local mode this session's own (`check#RecentAuth`, 300 seconds: a password, a second factor's code or a provider sign-in with its `auth_time`; never another session's or a login key's). With an account already signed in, `startSso` asks the provider to sign the user in again (`reauth: true`). An account has at most 20 keys and 20 tokens. An access token is a framework login key of scope `git` (`moqui.security.UserLoginKey` with a `description` and `scope` `git`, `crates/moqui-core/src/service/user_keys.rs` `create_access_token`): git over HTTP and the git REST take it, and the web, the rest of REST, sockets, A2A and PASS pages refuse it. It lasts until the date asked (at most 366 days), else 90 days. Only its hash is stored; the token is answered once and is not in the receipt. The authority refuses every PASS operation to a request signed in by an access token or a session's key, and all but `APP_KEY_OPERATIONS` to a device's key (`PassAuthority.js` `run`); in local mode the frontend applies the same rule (`Facade.js` `checkLoginKey`).

**Webhooks and push mirrors.** The webhook and mirror operations need Maintainer, and an id must be of the repository in the request. A repository has at most 10 webhooks. The URL and the secret go to the framework's `store#GitWebhook`; `findWebhooks` answers the URL whole and `hasSecret`, never the secret. Smithy stores a webhook with authorization disabled and records no owner of it, so a webhook stays when its maker loses the repository; a mirror is stored as the Maintainer with authorization on, and the framework pauses it once its giver loses the delete right. On a create, `storeWebhook`'s receipt row holds a hash of the input without the secret, as `storeMirror`'s (SEC-PFS-62). `testWebhook` is limited to 3 a minute for a repository and answers the status code and delivered or not. A mirror's URL must match `https://<host>[:port]/<path>` with no `@`; the credential is a field of its own and only `hasCredential` is answered. A changed URL of a mirror with a stored credential needs the credential again or its removal, and `lastError` is scrubbed of credentials. The address rules (no loopback, private or link-local address) are the framework's ([Git](Attack-Surface-Git.md)). Smithy's `check#Outbound` (`git-server` `outbound-check-service`) refuses webhook deliveries and mirror pushes of a repository whose site has no Smithy mount, of a hidden repository and of one whose owner is suspended, and refuses when the check itself fails.

**The GitHub import.** `startGitHubImport` needs `writer` and Owner of the target group; an existing target repository must be in that group and needs Owner. The source is a name `owner/name`, never a URL. The API base is the conf setting `mantle@smithy-github-api` (an attribute of `<mantle>` in mr-mantle's `MoquiConf.xml`, default `https://api.github.com`), not an input. The caller's token is sent as `Authorization: Bearer` to that base, is kept for the run in the encrypted `password` of a `SystemMessageRemote` row, and is not in the receipt. A clone address that GitHub answers is refused unless it is `https` on the API's host. Pull request heads are fetched by the framework's `fetch#GitRefs` with that address and the token as the password; no file under `service/mantle/smithy/` names `import#GitRepository`. A private source into a wider group or repository is refused without `publishPrivate`. The import is a group Owner's act, though `service/Smithy.gitecas.xml` says an import is an operator's: a repository it makes has `importedHistory` Y, where the agreement gate takes a commit that no push brought as its author's on the author address (or a noreply login) alone. An import of a public repository adds `/<owner>/<name>` to the site's redirect table (`putRedirect`). Before each step the import checks the group's ownership, the confirmed address, hidden and archived again (`claim`), not that the repository is still in the import's group.

**The GitHub identity claim at SSO sign-in.** Mantle sets `user-facade` `login` `sso-linked-service` to `mantle.smithy.SmithyImportServices.handle#SsoLinked` (`authenticate="false"`). It claims nothing unless the flow is an `OauthFlow` of type `OctGitHub` whose endpoints are empty or exactly github.com's (or one Enterprise Server host's), `providerHost` is `api.github.com` (or that host), and the account holds that `externalUserId` and `externalAuthFlowId`. It then moves, in each site where the account is an active, unsuspended member, the records of the import's placeholder with the same numeric GitHub id and host to the account (posts, issues, merge requests, assignments, reactions). No role or repository ownership is moved.

**Smithy and the framework's git REST.** For a repository Smithy keeps, `check#RestWrite` (`git-server` `rest-write-check-service`) refuses every write of the framework's git REST and allows `read` and `commitStatus.create`. Mantle's `MoquiConf.xml` sets `reserved-status-contexts="agreement/,ci/,deploy/"` and `review-start-hidden="true"`. The review threads of the framework's REST are answered by `mantle.work.GitServices.handle#GitReviewThread`: the caller must be signed in and view the repository, and a hidden merge request is its author's alone. For a repository Smithy keeps, each comment in that answer carries no `fromPartyId`, and `authorName` and `authorHandle` from the site profile when `SmithyCore.authorShown` lets the caller see it, else empty (SEC-PFS-01); another repository's comments carry `fromPartyId` and an `authorName` built from `PartyDetail`. The hook services (`check#Push`, `check#LfsUpload`, `check#Outbound`, `check#RestWrite`, `check#Run` and others) are `anonymous-all`, take `repositoryId` and a user id as parameters, and are not in `PassRoutes.js`. `check#Push` runs for the source `push` only, so writes through Moqui (page commits, merges, `create#GitRef`, `git://` resource locations) are held to neither the repository's size quota nor the gate's account rules. `get#AuthorSigned` (`SmithyHosting.js`, over the framework REST's `get_author_signed` for a viewer of the repository) answers `missing` only to the author or a Maintainer, and `signed` for any address.

**The git authorization hook.** The hook in mr-mantle's `service/mantle/work/GitServices.xml` (granted in `data/MantleSetupData.xml`) carries `SmithyCore.js` `rights` to the framework for a repository Smithy keeps: `AUTHZA_VIEW` is `canView`; `AUTHZA_CREATE` and `AUTHZA_UPDATE` need a confirmed address and rank 30 (Developer); `AUTHZA_DELETE` needs rank 40 (Maintainer); any other action, and a failed call, answer `AUTHZT_NONE`. An operator's page role is not counted there, and a site that no longer mounts Smithy caps the rank at Guest; `ADMIN` has its own `AUTHZT_ALWAYS` on `GitRepositories`. With no user it answers view when the repository is public in effect (its own, its groups' and a fork's parents' visibility), the site is published, every group is active and nothing is hidden, and never a write. A suspended party has rank 0, so view of public repositories only. A collaborator's row is read on each request, so a removed one loses access at once. The hook sees the account a git access token signs in, with all its rights on every repository: no token is read-only or for one repository. It decides only whether a caller may fetch a repository at all. Smithy's repositories are `db` by default, a fork is of its parent's kind and a `db` network keeps one set of objects, a fork may be private under a public parent, and `review-start-hidden` makes every push for review and fork merge request start hidden; so a fetcher of a public parent, anonymous included, who knows a commit id reaches the history of a private fork's commit or of a hidden merge request's head through the framework's fetch by id.

**Releases.** Drafts are a Maintainer's. `storeRelease`, `deleteRelease`, `addReleaseAsset` and `removeReleaseAsset` need `writer` and Maintainer in a repository that is not archived; the tag must be the repository's own; an artifact asset must be of a successful, trusted run of this repository, not of a merge request, at the commit the tag names now; an announcement is refused when the news category is read by more than the repository. A release of a private repository is read only by its viewers, and the group landing, the activity list and a release card list only viewable repositories. Release notes (`store#ReleaseNotes`, `service/mantle/work/ProjectServices.xml`) and release files (`SmithySite.js` `assetRoot`) are written under Mantle's `mantle@content-root` conf setting (`dbresource://mantle/content`), which a user cannot change: before SEC-PFS-82 they were written under the caller's own `mantle.content.root` preference, which any signed-in user sets at `/apps/setPreference`, and no service reads that key now (nor `mantle.content.large.root`). A release file's name is reduced to `[A-Za-z0-9._+-]` (`fileNameOf`). The resource facade refuses a write, delete, move or restore at a location holding a `#` on every storage, since a reference or a read cuts the location at the `#` (it would change the file before it, or on `dbresource://` write a file never found) (`crates/moqui-core/src/context/resource.rs` `refuse_cut_write`; the `git` provider's `writable` the same); a reference made from `location#suffix` writes the location as given and derives no child, and an uploaded file's name has its `#` made `_` (`web/multipart.rs` `safe_file_name`). A stored notes location is written again only under the content root in the release's own folder (`store#ReleaseNotes`), and `removeReleaseAsset` deletes a file only under the site's release-asset root.

**Redirects.** The `redirect` transition of `mr-pass/screen/Smithy.xml` (`method="get"`, `read-only="true"`) takes a `location` parameter and calls `redirectRoute` (`screen/Smithy/Smithy.js`). It answers 301 to the location with the request's query added when the location is a path on the site (`siteLocal`: one leading `/` not followed by `/` or `\`, no backslash or control character), or an `https` address whose host `getSiteInfo` finds among the site's `PublicSiteHost` rows and that is not the site's theme preview host. Any other location fails. The redirect table is written by the site's owners (`storeRedirect`, `deleteRedirect`, `importRedirects`) and by the GitHub import; a target is a path of the site or an `https` address of one of its hosts, never a server path.
