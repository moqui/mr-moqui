# Attack surface: administration services

The privileged groups and sealed permissions, and the administration services (`org.moqui.admin.*`) behind the System app and an application's Admin screens: access, sessions and credentials, accounts, keys and second factors, shared devices, configuration, sign-in providers, connections, protocols, system messages, jobs, imports and exports, backups, readiness, audit and owned resources. This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## Administration services

### Privileged groups and sealed permissions

`user-facade` `authz` sets the privileged groups to `ADMIN`, `ADMIN_ADV` and `SYSMSG_RECEIVE`. Creating, updating, or deleting a membership in one of those groups is allowed only when the caller is a member of that same group (`assert_privileged_group_membership`). A member of `ADMIN` who is not in `ADMIN_ADV` or `SYSMSG_RECEIVE` cannot add a member to either; a first member of `SYSMSG_RECEIVE` comes only from a data load or a call with authorization disabled, and the seed data has none (`data/SecurityTypeData.xml` defines and grants the group; no `UserGroupMember` row outside test data names it). A first member of `ADMIN_ADV` comes from the initial admin account's `joinAdvanced` check (`create#InitialAdminAccount`, [Attack-Surface-Web.md](Attack-Surface-Web.md)) or from a data load by the operator (`moqui load location=FILE`, [Run-Deploy.md](../Run-Deploy.md)); a system may have none, and then nobody holds its sealed permissions. Seed and install, and a call with authorization disabled, skip that check. `SYSMSG_RECEIVE` is there because its members call `receive#IncomingSystemMessage` as a remote system, and a party screen that adds memberships by posted `userGroupId` would otherwise let a user join it. The sealed permissions are `GROOVY_SHELL_WEB`, `SQL_RUNNER_WEB`, `SSH_SHELL`, `TERMINAL_HOST`, `LOAD_RUNNER`, `INSTANCE_ADMIN` (System › Instance: host processes, containers and databases), `ADMIN_LOGIN_AS`, `ADMIN_PASSWORD`, `SearchRemote`, `DashboardRemote`, `REST_SCHEMA`, `LlmGatewayUse`, `COMPONENT_DEPLOY`, `CONF_EDIT`, `DATABASE_ADMIN`, `DATABASE_EXTERNAL`, `ADMIN_CONSTITUTION_GLOBAL`, `GIT_CI_ADMIN` (the CI's runner pools and their tokens: a pool's runners run the jobs sent to it, with their secrets), `REPORT_SAVE_LOCATION` (a scheduled report's files written to a server location), and the delegated-administration grants that widen access, `ADMIN_IDENTITY_GLOBAL`, `ADMIN_ACCESS_MANAGE` and `ADMIN_BACKUP_DOWNLOAD`. A `UserGroupPermission` row for one of those can be written only by a caller who already has that permission, and a `UserGroupMember` row in a group that grants one (not ended) only by a caller who has each such permission, so a sealed grant is not passed on through a group that is not privileged; an update that only ends a membership sooner passes (`Security.eecas.xml` `UserGroupMemberSealed`, `assert_sealed_group_membership`). A bulk `update_all` or `delete_all` goes row by row through the value path, so each row runs these entity ECA rules; both run under the find's own authorization (`authz_guard`), so on a find built with `disableAuthz()` they write with authorization off, which the checks skip (`crates/moqui-entity/src/entity/find/bulk.rs`). A component adds to either list with `authz` child elements, `<privileged-group name="..."/>` and `<sealed-permission name="..."/>`, which the conf merge adds to every other component's and never replaces; setting the attribute in a component's conf replaces the framework's list, so it is not done (mr-boss adds its privileged Admin groups this way). The check reads the attribute, or the framework's default list when it is empty, joined with every element (`security_checks.rs`). A DataDocument field expression (a `fieldPath` with `(`) is JavaScript run as whoever reads the document (the grid, exports, feeds, reports), so creating or updating one needs `DATABASE_ADMIN`, which already allows data changes that end in code running on the server (`Security.eecas.xml` `DataDocumentFieldExpression`, `assert_document_expression` in `crates/moqui-core/src/service/security_checks.rs`). Seed and install, and a call with authorization disabled, skip that check too. Its context holds no encrypted or password fields (`expression_hidden`, `crates/moqui-entity/src/entity/field_rw.rs`). A decimal formula (a payroll component's) is not script: `org.moqui.impl.ExpressionServices` parses it into a tree of numbers, input names, operators and an allowlist of functions and computes it over a map of decimals (`moqui_lib::decimal_expr`), with no context, entity, service or I/O behind it, so writing one needs only the application's own permission ([ExpressionServices](../dev/JS-Framework-Services.md#expressionservices-decimal-formulas)).

`ec.user.hasPermission` and the sealed-permission checks read the user's own `UserGroupMember` rows in date and then `UserGroupPermission` (`user_granted`, `crates/moqui-core/src/user/preference.rs`). `ALL_USERS` is added to a user's groups for artifact authorization and preferences only. A `UserGroupPermission` on `ALL_USERS` therefore counts only for a user with a `UserGroupMember` row in `ALL_USERS`. The shared-device check `display_account_refusal` counts `ALL_USERS` among the display account's groups (`user_group_ids`, `crates/moqui-core/src/user/device.rs`).

An `AUTHZT_ALWAYS` record permits before any deny is applied (`is_permitted`, `crates/moqui-core/src/user/authz.rs`). Below a frame that holds an inheritable `AUTHZT_ALWAYS`, every service, entity and other artifact is permitted before its own records are read, a deny included. `ALL_USERS` holds three artifact groups that way, each of members with `inheritAuthz` Y: `DriveDeviceServices` (nine `org.moqui.resource.FileServices` verbs; `data/SecurityTypeData.xml`), `XmppClientServices` (`org.moqui.chat.ChatServices` and `XmppServices` verbs; `data/XmppSecurityData.xml`) and `ConstitutionServices` (`org.moqui.admin.ConstitutionServices`; `data/AgentTypeData.xml`). A deny does not close these services for a group, and everything they call runs with no artifact check, so the check inside each listed service is the only one. The other `ALL_USERS` grants under `runtime/components/base` are `AUTHZT_ALLOW`, the administration families below among them.

### Access

Delegated access administration goes through `org.moqui.admin.AccessServices` (`find#Groups`, `get#Group`, `create#Group`, `store#Group`, `store#Membership`, `end#Membership`, `preview#Grants`, `apply#Grants`, `store#GroupPreference`; bodies in `framework/service/org/moqui/admin/Access.js`) and `IdentityServices.check#AdministrationPath` (`Identity.js`). `ALL_USERS` may call them (`AdminAccessServices`, an inheritable `AUTHZT_ALLOW`, so an app's deny of the package still applies); each checks `ADMIN_ACCESS_VIEW` or the sealed `ADMIN_ACCESS_MANAGE` with `ec.user.hasPermission` and refuses without it. They write the security rows through the entity facade with authorization on, so the privileged-group and sealed-permission EECAs decide each row as for any other writer, and each write moves the authorization caches here and on every live cluster member. Before writing they refuse, with a reason code rather than an error: a membership outside a registered bundle (`moqui.security.CapabilityBundle`, seeded by each component) or a custom group of a registered purpose (a `UserGroupType` with `optionIndicator` Y); a grant that is not a registered bundle's permission or artifact binding (so no deny can be removed and no unregistered `ArtifactAuthz` added; a binding carries the bundle's filter sets), counting a privileged group's bundle only for a member of that group, so its permissions are not copied to another group; a sealed permission the caller does not hold, granted, ended, or carried by a group whose membership is given (no sealed grant smuggled through a group); a privileged group, or its members, changed by a non-member; a custom group named after a privileged or framework group; a stale revision; and any membership, group-flag or grant change that would leave no usable instance administrator where there was one. A usable administrator is a date-valid member of `ADMIN` who is not permanently disabled or terminated, can authenticate (a password, or an external identity with an enabled sign-in flow), holds a date-valid factor when any of its groups requires one, and is admitted by its own and its groups' `ipAllowed` from the caller's address, checked now and at each later date the change names. Memberships and grants are ended, never deleted; `UserGroupMember`'s and `UserGroupPermission`'s dates, `ArtifactAuthz`'s type, `UserGroup`'s `requireAuthcFactor` and `ipAllowed` and `UserGroupPreference`'s value are audit-logged with the caller's reason, and a removed binding or default gets an explicit audit row. `UserSecurityChecks.privilegedGroups()` and `sealedPermissions()` give scripts the effective lists the EECAs read, for markers and reasons; they grant nothing. An app adds organization scope above these services (IronStone Admin checks each member against the organizations its administrator works for); the framework services know no organization.

The same services read the registry as a capability matrix, the row rules and a review (Admin P9: `get#Capabilities`, `get#ScopeRules`, `get#GrantReview`; `AccessCapabilities.js`), each under `ADMIN_ACCESS_VIEW`, writing nothing and evaluating nothing: the matrix shows a launcher binding and each permission by its kind as rows of their own (a launcher is never read as a view or a change) and lists what a group holds that no registered bundle describes read only; the scope rules name each `EntityFilterSet` bound to an `ArtifactAuthz` with its source and never return a filter's `filterMap` or an `applyCond`; the review leaves sealed permissions out, counted, and holds no allowed IPs, preference values or filter expressions. A grant request may bind a row rule: a filter set a registered bundle the caller may assign names for that artifact group, added to the group's binding of the registered type (`UNREGISTERED_SCOPE`, `SCOPE_UNBOUND`), never to a binding that carries a filter set of its own (`SCOPE_CONFIGURED`: an administrator group's active-organization rule is not "completed") and never removed (`SCOPE_REMOVAL`: removing one widens what members read). The grant revision covers each binding's filter sets, and a bound rule gets an explicit audit row. Arbitrary filter sets and expressions, removing a filter and raw `ArtifactAuthz` rows stay Tools' (`ADMIN`).

### Sessions and credentials

Sessions and an account's credentials (Admin P4) are `IdentityServices.find#Sessions`, `revoke#Sessions`, `get#AccountCredentials` and `revoke#AccountAccess`, under the same `AdminAccessServices` grant. A user reads and ends their own sessions with no permission (Commons Account's "Where you are signed in"; never the current session, and a visit of another account is refused and counted); another user's need `ADMIN_IDENTITY_VIEW` to read and `ADMIN_IDENTITY_MANAGE` to end. A session is named by its visit, never by its cookie, token, user agent or contents, and credentials are metadata only (no secret, verifier, factor option or recovery code); a login key, access token or device key is named by its stored hash (`credentialId` is `UserLoginKey.loginKey`), which no login takes as a key. Ending a session deletes its web session on this server, retires the live copy and publishes the session end to every live cluster member, as `end#UserVisit` does, through `UserSecurityChecks.endUserSessions(userId, visitIds)` (`user::end_user_sessions`), which decides no authority. A user ends their own access with `revoke#OwnAccess` (Commons Account's "Sign out everywhere and end my keys and app passwords" in mr-boss, SEC-WEB-06): no permission, but a sign-in in the last five minutes (`require#RecentAuth`); every session of the account on every server, the current one at its next request through `hasLoggedOut`, its login keys and app passwords, by the same path as `revoke#AccountAccess`, with the same evidence; SSH keys and phones are left. `revoke#AccountAccess` (another user only, `ADMIN_IDENTITY_MANAGE`, and the administrator's own sign-in in the last five minutes, `require#RecentAuth`, reasonCode `reauthRequired`, as `revoke#Sessions` asks for another user's sessions) ends every session and sets the account's `hasLoggedOut` (so a session no row names yet signs out at its next request), ends the login keys (access tokens, device and sign-in keys, so a notification socket on a key closes at its next check), app passwords (XMPP's sign-in), SSH keys and SIP phones (each live SIP engine drops the phone), pauses the agent triggers that run as the user with their cron jobs and asks the user's open agent runs to cancel; it leaves the account enabled. Ending another user's sessions or access is refused for an account in a privileged group the caller is not in or holding a sealed permission the caller lacks (`Identity.js` `heldBeyond`, which Mantle's account-wide changes and IronStone's Login as also apply). The per-request session refresh and the notification socket's 60-second check sign out an account disabled for good (`disabled` with no `disabledDateTime`) or past its `terminateDate`, as login refuses it; a tarpit lock (disabled with a time) stops new logins only, so failed logins by someone else cannot sign the owner out. A ServiceJob whose run-as user is disabled for good, past its end date or gone does not run: the run is recorded with the refusal. `UserAccount`'s `ipAllowed` and `requirePasswordChange` are audit-logged. The framework knows no organization: an app checks the target first and asks for `ADMIN_IDENTITY_GLOBAL` for an account-wide change of an identity shared with an organization outside the caller's scope (IronStone Admin's `check#Record` with `accountWide`; Mantle's `IdentityServices`). `AccessServices.check#GrantProposal` and `apply#GrantProposal` take a grant proposal of registered bundles for an account an app provisions, by the same delegation rules as `store#Membership` (`ADMIN_ACCESS_MANAGE` or `ADMIN_IDENTITY_MANAGE` to apply), written with authorization on so the EECAs decide each membership. `apply#GrantProposal` refuses the caller's own account (`OWN_ACCOUNT`) unless the caller holds `ADMIN_ACCESS_MANAGE` (SEC-ADM-06, fixed); its other bounds are the bundle checks (`proposalBundles`: a registered bundle, not a privileged group's for a non-member, no sealed permission carried, the bundle's `delegablePermissionId`). `ADMIN_IDENTITY_MANAGE` is not sealed. In mr-boss, `BOSS_ADMIN`, every `BOSS_ADMIN_*` bundle and each app's administrator bundle (`BOSS_<APP>_ADMIN`) name `delegablePermissionId="ADMIN_ACCESS_MANAGE"`, so only an access administrator proposes them (`NOT_DELEGABLE` otherwise); the sub-area administrator bundles do not.

### Accounts, keys and second factors

The account services of `org.moqui.impl.UserServices` (`framework/service/org/moqui/impl/UserServices.xml`) are not among the administration families. `enable#UserAccount` and `disable#UserAccount` take any `userId` and check no permission, so the artifact authorization of the service, or of the screen or REST path above it, decides. `update#UserAccount` goes through `check#AccountAction` with no permission for another account (Mantle's party edits by staff call it): a change of another account's sign-in fields (anything but `userFullName`, `locale`, `timeZone` and `currencyUomId`) is refused when that account holds access the caller lacks (`heldBeyond`, SEC-ADM-05), and a change of an account's `emailAddress` (where `reset#Password` mails) or `externalUserId` (the provider link), a cleared one included, the user's own or by an administrator another's, needs the caller's sign-in in the last five minutes (`require#RecentAuth`; [Recent sign-in](Recent-Auth.md)). `update#UserAccount` takes every non-key field of `UserAccount` but the password, lockout and logout fields: `username`, `emailAddress`, `ipAllowed`, `externalUserId`, `externalAuthFlowId`, `displayAccount` and `terminateDate` are among its parameters. `create#UserAccount` is `authenticate="anonymous-all"` with the same field list; `POST /rest/s1/moqui/users` calls it (`tools/service/moqui.rest.xml`) under the `MOQUI_API` grant, which is `ADMIN`'s. No `allow-remote` value of these services is read ([Services and `allow-remote`](Attack-Surface-Web.md#services-and-allow-remote)). With `ADMIN_PASSWORD` (seeded on `ADMIN`) `update#Password` sets another account's password with no old password and no code, unless that account holds access the caller lacks (`heldBeyond`), and only with the administrator's own sign-in in the last five minutes (`require#RecentAuth`); a holder's own password needs the old one, as anyone's. Without it, `update#Password` refuses an account disabled for good or past its `terminateDate`, and no password change re-enables an account disabled for good: only `enable#UserAccount` does (plans/Security-Review.md SEC-ADM-01, fixed). `update#Password`'s administrator path, `update#UserAccount`'s sign-in fields and the factor services below apply the `heldBeyond` rule of `IdentityServices`: an account in a privileged group the caller is not in, or holding a sealed permission the caller lacks, is refused (SEC-ADM-05, fixed). `enable#UserAccount` and `disable#UserAccount` do not. The web paths to `update#Password`, `reset#Password` and `create#InitialAdminAccount`, the lockout and the recent sign-in check are in [Login lockout and passwords](Attack-Surface-Web.md#login-lockout-and-passwords).

The second factor services of `UserServices` (`get#UserAuthcFactorInfo`, `validate#UserAuthcFactorCode`, `create#SingleUseAuthcCodes`, `create#SingleUseAuthcFactor`, `send#AuthcCodeEmail`, `send#AuthcCodeSms`, `create#UserAuthcFactorEmail`, `create#UserAuthcFactorSms`, `create#UserAuthcFactorTotp`, `setup#UserAuthcFactorTotp`, `invalidate#UserAuthcFactorEntry`) take a `userId` or a `factorId` and need a signed-in user. Each calls `org.moqui.impl.UserServices.check#AccountAction`: the account's own user, or another user only with `ADMIN_IDENTITY_MANAGE` (`ADMIN_IDENTITY_VIEW` to read its factors) and only when that account holds no access the caller lacks (`heldBeyond`); a call with authorization disabled passes (SEC-ADM-04, fixed). Issuing single use codes, adding a factor and ending one need the caller's sign-in in the last five minutes, on the user's own account and on another's by an administrator (`recentAuth`, `require#RecentAuth`, SEC-ADM-03); a refused browser form asks the user to confirm and sends again. `create#SingleUseAuthcCodes` returns up to 21 eight-digit codes, stored as hashes, good for a year by default. `setup#UserAuthcFactorTotp` returns the secret (`qrSecret`, `qrUri`) only of a factor not yet verified and an authenticator's. `send#AuthcCodeEmail` has `code` among its out-parameters. Single-use codes count as a factor in date, so issuing them makes a second factor required for the account. A code stands in for the old password of `update#Password` only in a pre-authenticated session, never a signed-in one. The anonymous variants (`get#ExternalUserAuthcFactorInfo`, `send#ExternalAuthcCode`, `validate#ExternalUserAuthcCode`) act only on the session's `moquiPreAuthcUsername` or the signed-in user. The callers are `System/Security/UserAccount/UserAccountDetail.xml` and its `Verify*` subscreens (`ADMIN`), mr-boss `Commons/Settings/Account.xml` (passes `userId: ec.user.userId`), mr-marble `MyAccount/User/Account.xml` (no `in-map`), and Mantle's `Invitations.js` and `Identity.js`. A transition's `service-call` shortcut with no `in-map`, or with `in-map` `true` or `context`, passes the whole context. On a plain post the `userId` a screen's always-actions set wins over a posted one (the request's parameters are put in the context first). Until SEC-RTE-81 the shortcut was `multi="parameter"` unless it named a `multi` or was `async`, so a post with `_isMulti=true` made it a multi call and the call took a posted `userId_0` before the context's `userId`: mr-marble's `updateUser` (`mantle.party.PartyServices.update#Account`, `in-map="context"`, which checks no owner) reached `update#UserAccount` for another account, whose `check#AccountAction` with `permissionId` `NONE` refuses only an account that holds access the caller lacks, and for an email change asks the caller's own recent sign-in. Now a shortcut is a multi call only when it says `multi="parameter"` or a multi form of its screen posts to it, and a multi call does not let a posted row value replace a value the screen pinned (`screen/definition.rs`, `service/call.rs`; [Attack-Surface-Routes.md](Attack-Surface-Routes.md#screen-tree)); mr-marble's explicit in-map and an owner check in `update#Account` are the component halves. With an `in-map` that is a map of its own a multi call finds no row and calls nothing (mr-boss `Commons/Settings/Account.xml`). No administration transition is reached this way: each that calls an `org.moqui.admin` service passes a map of its own, and the whole-context ones (the raw entity-auto transitions of System's `JobDetail.xml` and `ConnectionDetail.xml`) fix no id.

A user's own keys are `UserServices.create#UserAccessToken`, `find#UserAccessTokens`, `revoke#UserAccessToken`, `create#UserAppPassword`, `get#UserAppPasswords`, `revoke#UserAppPassword`, `create#UserSshKey`, `find#UserSshKeys` and `delete#UserSshKey` (Rust, `crates/moqui-core/src/service/user_keys.rs`). Each acts on the signed-in user; none takes a `userId`. They write with authorization off. A token or an app password is returned once and stored as a hash. An app password names the one protocol that takes it (`scope`: `dav`, `ssh`, `git`, `xmpp` or `ai`; a row made before scopes is taken by each; SEC-COM-21). `create#UserAccessToken` takes `expireDays`: 90 by default, at most 366. `create#UserSshKey`, `create#UserAccessToken` and `create#UserAppPassword` need a sign-in in the last five minutes (`require_recent_auth`, SEC-ADM-07); `create#UserScopedKey` (the gateway key, made by a dev instance with the account's key) does not. An access token is scope `git` (`user::ACCESS_TOKEN_SCOPE`; a token made before is read as `git` too, `key_scope`): git over HTTP and the git REST take it, and the web, the rest of REST, sockets, A2A and PASS pages refuse it (SEC-PFS-61). A sign-in by a login key, an access token, an app password, an SSH key, an identity provider (`login_external_user`) or `ec.user.internalLoginUser` goes through `internal_login` (`crates/moqui-core/src/user/login.rs`), which checks the account gate (disabled, `terminateDate`), `displayAccount`, `requirePasswordChange`, password expiry and `ipAllowed`, and no second factor. A group's `requireAuthcFactor` binds password sign-ins only.

Login as is the `loginAs` transition of `System/Security/UserAccount/UserAccountDetail.xml`, under `ADMIN_LOGIN_AS` (sealed, seeded on `ADMIN_ADV`). It checks the permission, refuses the caller's own account and an account that holds access the caller lacks (`heldBeyond`), needs the administrator's sign-in in the last five minutes (`require#RecentAuth`; the hidden-form link asks and sends again), writes an `EntityAuditLog` row on the target (`changedFieldName` `loginAs`, the administrator's user and visit) and a warning line, and calls `ec.user.internalLoginUser` with the posted `loginAsUsername` (SEC-ADM-08, fixed). The login writes no `UserLoginHistory` row (`internal_login`, not `recorded_login`) and keeps the session id; a display account is refused. mr-boss Admin's `Admin/Users/UserDetail.xml` `loginAs` asks `require#RecentAuth` the same way after its own `check#Record` and logs in only when it is recent.

### Shared devices

Shared devices (Admin P18; [Shared devices](Shared-Devices.md)). A browser registered as a device opens one route group with no person signed in: `org.moqui.admin.DeviceServices` registers (`register#Device`, `issue#DeviceCode`), lists and revokes devices for a holder of `ADMIN_ACCESS_VIEW` or `ADMIN_ACCESS_MANAGE` (the `AdminDeviceServices` grant for `ALL_USERS`; each service checks its permission), and `/Device` redeems a registration code for whoever posts it (`redeem#Device`, no sign-in, the page's session token). The code is about 99 bits, returned once, kept only as its hash, good once and for 5 to 60 minutes; a wrong, used or expired one gets one answer and is counted by the web protection. Redeeming sets the cookie `moqui.device` (`HttpOnly`, `SameSite=Strict`, `Secure` on https), whose secret is kept only as its SHA-256 and is given to no script. A request with that cookie runs as the registration's display account for that request alone: the account is never written to the web session, so no session row, live session, notification or terminal socket or Assistant stream holds it, and there is no session of it to take over. Such a request reads no `api_key`, `login_key`, Basic credentials or `authUsername`, no login succeeds in it, and it is refused (403) every screen, transition, REST and service path and script servlet outside its route group's artifact group, before anything of the target runs (`user::device::check_route`); what the group admits is still authorized as the display account. A refusal or failure answered to a device's browser page is a fixed plain page with no error text, never the instance's error screen. A display account (`UserAccount.displayAccount`) is never signed in by a password, a key, an app password, an SSH key, an identity provider, a factor, a reset or `Login as`, may hold no privileged group or sealed permission, and is checked on every request of its devices, as are revocation, the end date, the idle timeout and `ipAllowed`, with no cache, so each holds from the next request on every server. The cookie is a bearer secret: it is replaced daily, and the one before it stops the device ten minutes later (a copy is the only thing left presenting it), which does not detect a copy used within the day; the device list shows the last address and client. A registrar gives a device nothing they could not give a person: every group of the display account must be one they could assign. The framework knows no organization: an app scopes the display account first (Mantle's `register#SharedDevice`, which refuses another organization's). Evidence (registered, code shown, redeemed, refused, stopped, revoked) is on the display account in the audit log, never with a code or a secret. A compromised device browser reads what its display account may read through the route group's screens until it is revoked.

### Configuration

Delegated configuration (Admin P8) is `org.moqui.admin.ConfigurationServices` (`get#EffectiveSettings`, `get#InstancePreference`, `store#InstancePreference`, `find#LocalizedMessages`, `store#LocalizedMessage`, `find#LocalizedEntityFields`, `store#LocalizedEntityField`; bodies in `ConfigurationSettings.js` and `ConfigurationLocalization.js`), which `ALL_USERS` may call (`AdminConfigurationServices` in `data/AdminConfigurationData.xml`, an inheritable `AUTHZT_ALLOW` that names each service, never the whole file): reads check `ADMIN_SETTINGS_VIEW` and changes `ADMIN_SETTINGS_MANAGE`. The group also names `validate#MessageTranslationRow`, `apply#MessageTranslationRow` and `export#MessageTranslationRows`, the row services of the `messageTranslations` import and export targets: validate and apply check `ADMIN_SETTINGS_MANAGE` (apply through `store#LocalizedMessage`) and export checks `ADMIN_SETTINGS_VIEW`. A setting is a seed row of `moqui.server.InstanceSetting`; only a registered preference is written, typed and within its allowed values and limits, and a setting marked secret or whose property name reads as one (pass, pw, key, secret, token, credential) is never returned and never a preference. `get#InstancePreference` answers any signed-in caller (the service has no `authenticate` attribute) one registered, nonsecret preference: of the framework's seed `instance.displayName`, `instance.defaultLocale`, `instance.defaultTimeZone`, `signin.newDeviceWindowDays` and `report.groupRecipientCeiling`; no other component registers an editable setting. A translation must have exactly its original's `${...}` placeholders, so a translator cannot add an expression the server would evaluate. Markup is refused by the text parameter of `store#LocalizedMessage`; the import's row services take their row as a `Map`, whose values the parameter check does not read, and `translationProblem` checks length, control characters, links and placeholders, so a translation applied through the `messageTranslations` import may carry markup. The lookup holds every translation to the same rule (`l10n.rs` `translation_adds_expression`: a translation of a text that is not a message key that adds an expression is not used, with a warning), and writing a `LocalizedMessage` that adds an expression, or a message key's template that holds one, needs `DATABASE_ADMIN` (`Security.eecas.xml`; SEC-SCR-06); a label is translated only for a `moqui.basic.LocalizedLabelTarget` that is an `enable-localization`, unencrypted field of a configuration entity with one key. The conf's own view (`get#ConfView`, file and line of each value) stays `ADMIN`'s.

### Sign-in providers and policy

Sign-in providers and sign-in policy (Admin P10). `ConfigurationServices.find#IdentityProviders`, `store#IdentityProvider` and `test#IdentityProvider` (bodies in `ConfigurationProviders.js`; the `AdminIdentityProviderServices` grant, ALL_USERS, each checking its own permission) administer `moqui.security.sso.AuthFlow` with its OpenID Connect, OAuth and SAML row, `AuthFlowFieldMap` and `AuthFlowRoleMap`. A SAML row is kept and listed; no SAML sign-in exists, and `login#User`, `check#Flow` and the enabling of a SAML provider are refused. Whoever configures a provider decides who signs in as the accounts linked to it, so the parts are held apart: reading needs `ADMIN_CONNECTION_VIEW` or `ADMIN_ACCESS_VIEW`; the configuration `ADMIN_CONNECTION_MANAGE`; the role mappings, the default group, the rule that links existing accounts and enabling `ADMIN_ACCESS_MANAGE` (sealed). A mapped or default group is one the actor may assign by the grant proposal's rules and is never a privileged group or one that grants a sealed permission, whoever asks. Enabling needs a passing test of the configuration as it is now and is refused while a linked account holds access beyond the actor's (`HELD_BEYOND`); disabling keeps the administration path. A change of the client type, client id, issuer or discovery URL, realm, an endpoint, the Apple team or key (SAML: the metadata location or entity id) needs the secret entered again in the same save, else the stored one is cleared; either way the provider is saved disabled with its test mark cleared, so nothing reaches the new endpoint with the old secret. A change of the identity mappings does neither: the provider stays enabled and no test is asked. A secret is write-only (`secretSet` on a read), never logged, and its replacement or clearing is an audit row with no value. Identity mappings are a claim name onto the full name, email address, locale or time zone, never an expression; a provider whose rows carry an expression or a mapping service (an `ADMIN`'s, in Tools) keeps them, read only. `OidcFlow.useNonce` and `preferredJwsAlgorithmEnumId` are stored, and a change of either disables the provider the same way, the secret kept; the sign-in reads the algorithm only to refuse `ES512` (`crates/moqui-host/src/sso.rs`) and does not read `useNonce`. URLs are `https` (`http` only for the server's own machine, and only when `instance@purpose` is not `production`), with no credentials or fragment; on a production instance a provider started here is saved with `AuthFlow.allowPrivateNetwork` `N`, which the service never changes: the sign-in's own HTTP client (`crates/moqui-host/src/sso.rs`: no redirect followed, 1 MiB, 30 seconds) then sends no request of that flow (discovery, token, keys, user info) to a loopback, private or link-local address, by name (the resolver `moqui_lib::http::PublicOnly`) or written out. A flow without the flag (an `ADMIN`'s in Tools, or one of an instance that is not production) may be on the instance's own network. A flow an instance administrator set to `Y` keeps it when a holder of `ADMIN_CONNECTION_MANAGE` changes its discovery URL or endpoints (the retest clears only the test mark), where a connection's endpoint change on a production instance sets `N` (below), so `test#IdentityProvider` then reads the new address from inside the network. `test#IdentityProvider` calls `org.moqui.sso.AuthServices.check#Flow` (Rust, `service/sso.rs`; `ADMIN_CONNECTION_MANAGE` or `ADMIN_ACCESS_MANAGE`), which starts a login as `login#User` does and keeps nothing: the server reads an OpenID provider's discovery document (the same outbound request a sign-in makes, to the URL an integration administrator configured), no token is asked for, nobody is redirected and no account is made; its failure text names URLs and never the secret, and a discovery document that does not parse is reported by the kind of error and its position, never by the parser's text, which quotes the body.

The sign-in itself obeys the same bounds whoever wrote the rows (`service/sso.rs`; the account sync writes with authorization off, which the security EECAs skip): an existing account with no provider id is linked only under the flow's `accountLinkEnumId` `AflVerifiedEmail` rule (an `email_verified` claim and an `email` equal to the account's address), never by the provider's username alone, and never an account in a privileged group or in a group granting a sealed permission (an administrator links it); a role map or default group naming such a group is logged and passed over; and the sync ends only memberships in the groups the flow's role maps name, so an administrator's membership and one given by hand stay. A provider's id is linked with the provider it is of (`UserAccount.externalAuthFlowId`, set when a sign-in makes or links the account): an account another provider is named on is never found by this one, whatever id it asserts, so a second provider (with other users, or run or configured by somebody else) signs in only its own accounts. An account with an id and no provider named (linked by hand, or before providers were told apart) is taken by the provider that first signs in with the id; with several providers enabled, never an account in a privileged group or in a group granting a sealed permission, where an administrator names the provider. Under the same `AflVerifiedEmail` rule a sign-in whose `email_verified` claim is true and whose `email` equals the account's address (as it is after the flow's field maps) writes a `moqui.security.public.VerifiedAddress` row for that account and address when there is none, as the registration's mail link does (after the account's transaction, in one of its own: a failure to record it is logged and never fails the sign-in): the flow's rule is the statement that the provider's verified address is trusted, so whoever may set it on a flow decides which providers confirm an address for what an application gates on one (Smithy's writes and pushes). A flow without the rule writes none. A closed account (disabled for good, or past its `terminateDate`) is refused before the sync writes anything. An `AuthFlowFieldMap.srcFieldName` that is a plain name is read as the claim of that name, never evaluated; only a `dstFieldExpression` or a source that is not a plain name (an `ADMIN`'s, in Tools) is an expression. A mapped `emailAddress` is kept only when the profile's `email_verified` claim is true, whatever claim was mapped onto it: a map of another claim (one a user sets at the provider, such as `nickname`) onto `emailAddress` writes that value, unverified, to `UserAccount.emailAddress` of a user whose `email` the provider verified, and `reset#Password` finds an account by that address. The link rule and the verified address row read the `email` claim, not a mapped field. The sync writes the account through `UserServices.update#UserAccount` and entity-auto `create#moqui.security.UserAccount`; `update#UserAccount` refuses an address another account holds with a message that names that account's username. The `HELD_BEYOND` rule above counts the accounts the provider signs in: those it is named on and those that name none. The conf's `user-facade` `login` `sso-linked-service` (none by default) is told of each real sign-in through a flow, once its transaction commits and with authorization off: the user, the flow, the host of the user info endpoint (`providerHost`), the provider's id and username (`login`), the email with whether the provider verified it, and `urlsOverridden` (the flow names an endpoint or discovery URL of its own, so a flow typed GitHub that points elsewhere is told apart). An application that ties records to the identity (Smithy's imported GitHub authors) trusts it only for the provider host and flow it expects; a failure is logged and never blocks the sign-in, and a write of `externalUserId` by hand calls nothing.

The grant behind a sign-in is huskarl's `AuthorizationCodeGrant` (0.11.10, built by `crates/moqui-host/src/sso.rs`). `state` is random, required on the callback and compared in constant time, after the session's pending sign-in is taken and removed; an OpenID flow sends a nonce whatever `useNonce` says and requires it in the ID token; PKCE is S256, `plain` only when the discovery document lists `plain` and not `S256`, and never off. The ID token is checked against the keys of the document's `jwks_uri`, with an algorithm the document lists other than `none`, an `iss` equal to the document's own `issuer` (not a configured value, and not compared with the discovery URL), an `aud` of the client id and no other audience, and `exp`, `iat` and `sub` required; an RFC 9207 `iss` on the callback is checked when the document says it is supported. So the discovery document, fetched from the configured URL with no redirect, is trusted whole (issuer, endpoints, key location, algorithms and PKCE methods), then every claim of the ID token, and every user info member the ID token lacks, added without comparing the user info `sub` with the token's. An OAuth 2 flow has no ID token: `state` and PKCE protect the code, and the identity is the user info answer for the access token.

An installed app's sign-in (`service/sso_app.rs`; the routes are in [Attack-Surface-Routes.md](Attack-Surface-Routes.md#public-and-weakly-authenticated-root-paths)) ends in a device key. The pending sign-in is a session attribute bound to the browser session and the app's challenge, state and redirect URI, good 15 minutes, and is completed only for the user its own provider round trip signed in or, at this server's login, after a sign-in since the start or the password again. The code is 43 random characters kept as a hash, bound to the user, the challenge and the redirect URI, good 60 seconds, one per sign-in, and taken once by an update of the unused row in its own transaction before any other check. It buys a device key for that user, issued through the account gate, with the life of `user-facade/login-key@device-expire-hours`.

`ConfigurationServices.get#SignInPolicyValues` (Rust, `service/sign_in_policy.rs`) answers a fixed list of nonsecret `user-facade` `password`, `login-key` and `login` attributes and the web session's timeout, as the server runs with them, to a holder of `ADMIN_SETTINGS_VIEW` or `ADMIN_ACCESS_VIEW`; `get#EffectiveSettings` shows them through the settings that name one as `confAttribute` (to an access administrator the sign-in settings only). `AccessServices.preview#GroupSignInRules` (`ADMIN_ACCESS_VIEW`) previews a group's factor and address rules as counts, naming no member.

### Connections and mail relays

Connections and mail relays (Admin P11). `ConfigurationServices.find#Connections`, `get#Connection`, `store#Connection`, `test#Connection` and `find#ConnectionConsumers` (bodies in `ConfigurationConnections.js`; the `AdminConnectionServices` grant, ALL_USERS, each checking `ADMIN_CONNECTION_VIEW` or `ADMIN_CONNECTION_MANAGE`) administer the native connection records through registered adapters (`moqui.server.ConnectionAdapter`, seed data, never a name an administrator enters): `SystemMessageRemote` (kind remote), an `EmailServer` no `EmailAccount` owns (relay), `EmailOAuthProvider` (mailOAuth) and `NetworkPrinter` (printer) here, and a component's kinds through its adapter service (Mantle's gateways), which no group may call directly and which is built with the same engine. The `AdminConnectionServices` grant is inheritable (`inheritAuthz` Y), so a component's adapter service and every connection consumer provider (called by `find#ConnectionConsumers`, which a holder of `ADMIN_CONNECTION_VIEW` reaches, and by `get`, `store` and `test` of a remote, to ask whether another kind owns it) run under it with no artifact check of their own: the check inside each is the only one, where `call#OwnerService`, `call#TargetService`, `call#ChangeSource` and `ReadinessServices` cut the grant. What they hold to:

- A secret is write-only (a read answers whether one is set), is never logged or put in a test's text, and its replacement or clearing is an audit row with no value. Only the fields a kind declares change, each validated; a send service, a gateway's service names, `disabled` and `allowPrivateNetwork` are never among them.
- The endpoint-change rule: a change of a host, port, URL, user or kind of sign-in needs the secrets entered again in the same save, else every stored secret of the connection is cleared; either way the record is saved `disabled` Y and its test mark (`moqui.server.ConnectionCheck`: a fingerprint of the endpoint fields, never a secret) is cleared, and a passing `test#Connection` of it as it is then enables it (not one an administrator had disabled before the change). The services write the audit rows the entity audit log does not (a first value, `disabled` and `allowPrivateNetwork` among them). A value saved as it was read is no change; a URL is read without credentials written into it. `disabled` is enforced by the senders, not by Admin: the SMTP transport (`moqui-mail` `smtp_transport`), `send#ProducedSystemMessage` and `send#SystemMessageRest`, the print service, and Mantle's gateways for their connection; the backup mirror is not one of them ([Backups](#backups)). While a cleared secret has not been entered again a test sends nothing.
- The relays include `SYSTEM`, the server the framework's sign-in mail templates name (`PASSWORD_RESET`, `SINGLE_USE_CODE` and the factor mails, `data/MoquiSetupData.xml`), which decides where reset passwords and emailed sign-in codes go. That relay (`SYSTEM`, and any relay one of `PASSWORD_RESET`, `SINGLE_USE_CODE`, `ADDED_EMAIL_AUTHC_FACTOR`, `EMAIL_AUTHC_FACTOR_SENT` or `ACCOUNT_SIGN_IN` names) is read only to a holder of `ADMIN_CONNECTION_MANAGE` alone: starting, changing and testing it needs the sealed `ADMIN_ACCESS_MANAGE` too, and a sign-in in the last five minutes (`ConfigurationConnections.js` `signInRelay`, the engine's `staleSignIn`; SEC-ADM-82). A relay's `webBaseUrl`, the base of the links in the mail it sends (before the instance's own root URL, `moqui-mail` `implementation.rs`), is neither an endpoint nor retested: a change of it leaves the relay enabled, and its host is not checked against the instance's (`urlText` checks the scheme, credentials and fragment).
- Only the sign-in mail's relay asks for a recent sign-in (`require#RecentAuth`, on its store and test); a sign-in provider is enabled or its access parts changed, and another connection's secret replaced, from a session of any age.
- Server-side requests: a test makes the server contact an address its administrator chose (one HEAD with no credentials and no body, an SMTP connect and sign-in, a test page). On a production instance a connection started or repointed through these services is saved `allowPrivateNetwork` N, never set back by them, and its sender then reaches no loopback, private or link-local address: the HTTP client by its resolver and redirect checks, SMTP by one lookup (`moqui_lib::net::public_addresses`) and a connection to the address found, the IPP client by the `PublicOnly` resolver with no redirect followed. An instance administrator allows a connection on the instance's own network (Tools). A test's answer is a host, a status code and one of a fixed list of failure kinds, never a response body or the remote's own words, within the clients' time limits.
- An address the server expands (`SystemMessageRemote.sendUrl`) may hold the three names the sender gives and no other `${}`; URLs are `https` (`http` only for the server's own machine on an instance that is not production).
- Inbound: `/rest/sm/{type}/{remote}` takes a message of any type from whoever satisfies the remote's `messageAuthEnumId`, so that field is never changed here, a remote started here receives only from a signed-in user authorized to receive system messages (`SmatLogin`; how it sends is `sendAuthEnumId`, which `send#SystemMessageRest` now reads first), and the shared secret of a remote that verifies received messages by it is not entered here (`SECRET_NOT_DELEGATED`). A remote that verifies by a secret that was cleared refuses what it receives (an empty key is not taken), and an empty `messageAuthEnumId` is a login (`service/system_sync/message.rs`). Binding a remote's inbound to its message type is open ([Remaining-Work](../../plans/Remaining-Work.md)).
- A remote with a send service of its own, or of a message type with a file path or a send service (the backup mirror's `EmbeddedDbBackup`, an EDI partner's), and any remote that does not post over `https`, is read only here: repointing it could send what it carries elsewhere. So is a remote that is another kind's connection (a gateway's: the owner's consumer provider answers `ownsConnection`), which is changed through that kind under its validation (a provider's hosts on a production instance); a provider that cannot be asked leaves the remote read only. An `EmailServer` a mail account owns is answered as not available on every path (it carries the account's password and token), and an `EmailOAuthProvider`'s endpoints are not changed here (its client id, tenant and secret are): `authorizeUrl` and `tokenUrl` are shown, not fields, and `revokeUrl`, `userInfoUrl` and `issuer` are not fields of the kind. A change of them by another path (the generic entity tools; the entity is in no restricted list) clears neither the stored secret nor the test mark, since the endpoint-change rule here sees only the client id and tenant.

### Protocols and the mail queue

Protocols and the mail queue (Admin P12). `ConfigurationServices.get#ProtocolReadiness` and `test#Protocol` (bodies in `ConfigurationProtocols.js`; the `AdminProtocolServices` grant) read what each protocol of the server is doing and run its checks; `OperationServices.find#MailOutcomes`, `retry#MailOutcome` and `reconcile#MailOutcome` (`OperationMail.js`; the `AdminOperationServices` grant, each checking `ADMIN_OPERATION_VIEW` or `ADMIN_OPERATION_MANAGE`) list the send outcomes of stored mail and act on them.

- The server's own answers come from fixed lists (`crates/moqui-core/src/service/protocol_admin.rs`): `get#ProtocolFacts` the startup report's entries for named listeners and integrations and a list of nonsecret conf attributes (no key, host key or key file), and `probe#ProtocolTarget` one TCP connection, closed at once with nothing written, to a target named by key, whose host and port are the conf's own properties. No address is taken from a request, so neither is a port scanner, and neither is in a group's grant: `test#Protocol` calls them, and each checks its permission again.
- A check that leaves the server (a public name looked up and connected to) runs only with the caller's confirmation, in the script and again in the Rust service; a protocol that is off or not built is sent nothing. A result names a host, a port and a kind of failure.
- SMTP reception is reported trusted only while it listens, `smtp-server@allowed-addresses` names addresses that are no range of every address and can reach the bound address, and `smtp-server@authserv-id` is set; any mismatch is reported as running without trust, never as ready.
- The mail queue returns no subject, body, header, address or attachment (no parameter asks for one), and an error's text has every address struck out. A message whose send is uncertain (`EmailMessage.sendOutcome`, kept by `send#EmailTemplate` and `send#EmailMessage` with a failed delivery) is never sent from here until a person settles it, and a person never sets a message's sent state: the settlement (reported delivered or not delivered, who, when and the reason; `EmailMessage.sendSettlement`, audit logged) is kept apart from the status and `sendOutcome`, which only a send's own result writes, so no reader of the status takes a person's word for a delivery. One reported not delivered may be sent again through the same claim. A settlement holds only for the send it was made for: `send#EmailMessage` clears it (the audit log keeps it) and marks a message known not sent uncertain when a send of a stored message begins, in its own transaction before the transport is contacted, for every caller (the queue's retry, BasicComms' MessageDetail resend, which stays `ADMIN` only and asks for no settlement first), so a send lost part way leaves the message uncertain and unsettled, never offered Send again on an old report; a send refused before it began leaves the settlement. A retry sends the same stored message, claimed first in its own transaction so a second request or a server that stops part way finds it held. A mail account's message is its sender's alone, and a message a registered owner claims (`moqui.server.MailOutcomeOwner`, seed data) is retried and reconciled only by that owner's own service, with the owner's permission; while an owner cannot be asked, nothing is retried.

### System messages and recovery

System messages, recovery and message types (Admin P13). `OperationServices.find#Messages`, `get#Message`, `preview#Recovery` and `execute#Recovery` (bodies in `OperationMessages.js` and `OperationRecovery.js`; added to the `AdminOperationServices` grant by name) read the transport outcomes of system messages and dispatch a retry, a reconciliation or a cancellation to what the message type's owner registered; `ConfigurationServices.find#MessageTypes`, `get#MessageTypeUse` and `store#MessageType` (`ConfigurationMessageTypes.js`; the `AdminMessageTypeServices` grant, `ADMIN_CONNECTION_VIEW` and `ADMIN_CONNECTION_MANAGE`) read the message types and change what an owner registered.

- Nothing is recovered without a registration. A `moqui.server.RecoveryDescriptor` (seed data of the owning component, read when used: a row naming a missing service is logged and left out) names, per kind of record and target, each action's mode: the framework's own action for that same stored message (`send#ProducedSystemMessage`, `consume#ReceivedSystemMessage`, `reset#SystemMessageInError`, `cancel#SystemMessage`), which the owner thereby says is safe to repeat, or the owner's own service. An owner's service registered for recovery, the mail queue or a job's items is called only through `OperationServices.call#OwnerService` (`OperationLib.js` `callOwner`; SEC-ADM-10), which calls only a service a `RecoveryDescriptor` or `MailOutcomeOwner` row names and whose `ALL_USERS` ALLOW (`AdminOperationCall`) is not inheritable, as `DataTransferServices.call#TargetService`, `AuditServices.call#ChangeSource` and `ReadinessServices` cut it: the `AdminOperationServices` grant does not carry into the owner's service, which is authorized for the caller as a direct call is, so an owner's service carries a grant of its own besides its own permission check (the framework's `find#MessageJobRunItems` is in `AdminOperationServices`; Mantle's five owners, `mantle.party.MessageServices.find#MailOutcomeOwners` and `recover#OwnedMailOutcome`, `mantle.forum.DeliveryWorkerServices.find#MailOutcomeOwners`, and `mantle.product.StoreChannelServices.find#MessageRecoveryTargets` and `recover#StoreMessage`, have their own `ALL_USERS` ALLOW and each checks its own permission, [Attack-Surface-Apps-BOSS.md](Attack-Surface-Apps-BOSS.md#admin); every other `RecoveryDescriptor` is a job's native retry with a `managePermission` and no service, and mr-boss, mr-pass and mr-marble register none). The framework's own steps (a claim, a send, an apply) are called as before: a native retry of a received message calls `consume#ReceivedSystemMessage` directly (`lib.callRegistered`, not `call#OwnerService`), so the type's consume service runs as the signed-in operator under the inheritable `AdminOperationServices` ALLOW, where the scheduled job runs it with no user. No service, record kind or handler name is taken from a request; the kinds and actions are own names of fixed tables. A message of an unregistered type (the backup mirror's, a gateway's webhook) is read only.
- A message whose outcome is unknown (Sending or Consuming for longer than such a call may take, or the owner's word) is never sent or consumed again from here: it is settled by a person's word, and nothing is sent by that. A message's status is the transport's alone: the settlement is kept apart (`SystemMessage.outcomeSettlement`, done or notDone, with who, when and the reason, and in the audit log), the message is never marked Sent or Consumed by it, and a settled message is its own state, out of what needs attention and never listed as done; one reported not done may be retried, through the retry's claim, which clears the settlement. A message of a remote that is `disabled` (a connection waiting for its test) is not sent. Every action names the revision it read and is claimed first, the row locked, in a transaction of its own, and the framework's send and consume take a message by a claim of their own (`claim#SystemMessage`: only a message still in the status read is set Sending or Consuming), so the scheduled job and a retry never both send or consume one message; where its owner answers per message and does not let the reader, a message's remote, references, error line, settler and status reasons are not answered; each record of a batch (at most 25) is taken on its own and has its own result; an operation key answers a repeat of the same batch by the same user with the first results.
- No list or detail returns a message's text. `get#Message` answers a payload only when asked, only when the type's descriptor names the permission that reads it, the reader holds it and, where the owner answers per message, the owner says this reader may see it; it is cut to 20,000 characters with the values of fields named like a credential struck out. An error is answered as its class and one line with what a remote answered, URL paths and queries, addresses, credentials and long tokens struck out; where an owner answers per message (its scope is a store's or an organization's, which the framework does not know), that line and the message's correlation ids are shown only with the owner's word.
- `store#MessageType` sets a type's send or consume service only to a handler its owner registered for that one type and role (`moqui.server.MessageHandler`), chosen by the registration's key; a handler is never cleared, the receive service is never chosen (it is how the instance takes what a remote posts to `/rest/sm`, as a remote's inbound sign-in is not changed in delegated administration), and a type with no registered handler is not changed at all. A send path, which the sender expands for each message, may hold only the names the sender gives; the other paths and the file pattern hold no `${}`, and no path holds a `..` segment. Each changed field leaves an audit row.

### Jobs and notification topics

Jobs and notification topics (Admin P14). `OperationServices.find#Jobs`, `get#Job`, `store#Job`, `find#JobRuns`, `get#JobRun` and `get#JobRunItems` (`OperationJobs.js`) and `find#Topics`, `get#Topic`, `store#TopicDefaults` and `store#TopicSubscription` (`OperationTopics.js`), each added to the `AdminOperationServices` grant by name, read the scheduled jobs and their runs and change what an owner registered. A scheduled job is an administrator's stored text that a service later runs with, and a subscription is how a notification reaches a person, so both are closed lists.

- Nothing is changed without a registration. `store#Job` writes only a job that has a `moqui.server.JobRegistration` (its owner's seed row), and only the controls that row names: the schedule (a cron expression of its own characters that the scheduler parses and that comes due no more often than the row's minimum interval; never cleared, never given to a job that has none), the pause, the priority and the wait after an error. The service has no parameter for the job's service, the identity it runs as, its topic, its time limits, its lock expiry or its dates, so no request names one. A job parameter is written only where a `JobParameterDefinition` registers it for that job, only when the job's service declares it, and only as a value of the registered type within its bounds; a text is letters, digits, spaces and `. , : _ -`, so it holds no expression, path, URL or address; a definition named like a secret is left out. `clean_ServiceJobRun_daily` registers `daysToKeep` from 1 to 366, so a holder of `ADMIN_OPERATION_MANAGE` can cut the job run history, from which backup coverage is read, to one day; each change leaves an audit row.
- A run outside the schedule is a registered recovery (`RecoveryDescriptor`, `targetKind` `ServiceJob`) through `execute#Recovery`. The native action starts nothing itself: in a transaction of its own, with the job's row and its lock row locked, at the revision read and only while no run holds the lock, it marks the job due (the step, `apply#JobRecovery`, checks the registration again itself, so it marks no unregistered job due whoever calls it), and the scheduler's next pass claims the lock and runs the job as it runs every run. So it never runs beside a run under way (the scheduler's claim is the one claim), and never as the person who asked: `ec.service.job(name).run()`, which runs a job as the caller and takes no lock, is not used. A paused job, one outside its dates and one with no schedule are not started this way. A lock is never cleared or deleted here; a run whose server stopped is ended by the scheduler, which takes the lock over when its lease lapsed (`leaseExpireDate`, renewed by the running instance until the run ends or passes its job timeout), when the instance is gone, or after `expireLockTime`.
- A job run carries no organization, so a holder of `ADMIN_OPERATION_VIEW` reads the runs of every organization's jobs: their times, where they ran, the class of an error and up to five lines of it with addresses, URL paths, credentials and long tokens struck out, the numbers among a run's results, and the names of its parameters with a value only where it is a number, a yes or no, or a registered parameter (a stored text counts as a number only up to nine digits, so not an account, card or phone number, and nothing named like a secret is shown as a value, a result neither). Never a run's messages, a result's text or another parameter's value; a queued call (`ASYNC_QUEUE_`, which stores its caller's parameters) is never listed. A run that ended without an error while its results or its owner's items count failures is answered as ended with failed items, never as a success. `get#JobRunItems` calls the service the job's owner registered (`itemsService`) as the caller with the artifact authorization inherited (as a recovery's owner service is), so the check inside the owner's service decides, and reads its answer as data (cut, masked, states of a fixed set).
- A job's notification carries the run's errors, parameters and results unmasked, so a recipient is added only where the registration names the permission a recipient must hold, and only an account that signs in and holds it; an unknown name and an outsider get one answer.
- `store#TopicDefaults` (`ADMIN_SETTINGS_MANAGE`) writes only the delivery settings a `moqui.server.TopicRegistration` names; whether a topic is private, its title, error title and link templates (each expanded as a script when a notification is sent), its email template, its approval services and its inbox are never written, and none is returned by a read. `store#TopicSubscription` (`ADMIN_OPERATION_MANAGE`) sets a user's choices only for a topic whose owner registered an audience, and only for an account that signs in and holds that permission, the caller's own too: nobody is subscribed to a private topic, or to any other, outside the audience its owner registered. `allNotifications` (a user who has it receives every message of a topic, a private topic's too: the notification resolution adds such users to every message that is not direct-only, which the framework's own job error and web error topics rely on; a message whose content is its named recipients' alone is sent direct-only, `NotificationMessage::direct_only` or a script's `directOnly()`, as a business alert's and IronStone People's confidential notices are) is never set by this service, only ended; setting it stays an instance administrator's, in Tools. Subscriptions are listed by name only within the registered audience and only for a holder of `ADMIN_OPERATION_VIEW`; the others are counted.

### Business imports

Business imports (Admin P15). `DataTransferServices` (`DataTransferImports.js`, `DataTransferBatch.js`, `DataTransferLib.js`; `find#ImportTargets`, `get#ImportTarget`, `stage#Import`, `configure#Import`, `validate#Import`, `apply#Import`, `get#Transfer`, `retry#ImportItems`, `get#ImportReport`, `get#ImportSample` and `find#Transfers`, granted to `ALL_USERS` by name in `AdminTransferServices`) stage a file and apply its rows through a registered target. An import is the widest write path an administrator has, so what it can reach is a closed list and every write is its owner's.

- Nothing is imported without a registration. A request names a target by its id; the `moqui.server.TransferTarget` row (its owner's seed data) names what is called: an owner's five steps for a target with its own batch, a validate and an apply service per row for a target whose batch is kept here, or nothing but the owner's place for an owner wizard. No parameter of any service is a service name, an entity name or a field map that the registration does not bound: a mapping is from the file's headers to the target's registered fields and a batch option is one the target registers, each by its own name (never a prototype's), and anything else is an error. A registration naming a service that is not defined, or one without its step's parameters, is logged and left out, and nothing is called for it.
- Mantle's `opportunities` import target (IronStone Sales) asks `SALES_IMPORT`, `SALES_OPPORTUNITY_EDIT` and `SALES_TEAM_MANAGE`, all required, and no `ADMIN_*` permission; its row services (`mantle.sales.OpportunityServices` validate#/apply#OpportunityImportRow) check `SALES_IMPORT` with `SALES_OPPORTUNITY_EDIT` and the organization in the importer's sales scope again, and write every deal through Sales' own guarded services as the importer; a repeat under a row's operation key answers the first result, and any other use of the key is refused.
- The registration adds no right. An owner's service is called only through `call#TargetService`, which reads the service from the registration by the step's name (a caller cannot name one) and passes only that step's parameters. Its `ALL_USERS` ALLOW (`AdminTransferCall`) is not inheritable, so the dispatching service's grant does not carry into the owner's service: called outside a screen it is authorized for the caller as a direct call is. An app screen's inheritable ALWAYS grant still covers it, as it covers everything below that screen (an app's import area is such a screen), so what holds on every path is the owner's service checking its own permission and scope itself: a registered service that relied on its artifact authorization alone would be open to every user of such a screen, and an owner registers only services that check the caller. A target's `importPermission` and `viewPermission` are asked besides. What a registration fixes for its row services (`fixedValuesJson`) is set from the registration at the call, never from the request.
- A file is bounded and is text. A batch kept here takes delimited UTF-8 text within the target's bytes and rows (at most 2 MiB and 5000 rows, 50 columns, 2000 characters a cell), checked by its content whatever its name says; anything else is refused before it is kept. A file with a column named like a secret (password, passphrase, secret, token, API key, private key, credential, hash, salt, PIN, OTP, factor) or like one the target refuses is refused whole with the column named, so such a value is never read, mapped, stored or echoed. A file's name is kept as its last path part with control characters and `${` taken out.
- A registered column may name a permission: a reader without it sees the column as `Restricted`, and its values are cleared from the staged row once applied. `get#ImportTarget`, `get#Transfer` and `get#ImportReport` ask only for a signed-in user at the door and leave the rest to the target's permissions inside; `get#ImportTarget` answers the target's columns with each column's permission name, and the target's `importPermission`, `exportPermission` and `viewPermission` by name, to any signed-in caller.
- A batch is read by who staged it while they still hold the target's import or view permission and its scope, and by a holder of the target's view permission whom the target's scope service admits to the batch's scope (an organization is the owner's notion, so the owner's service says which scopes a caller has); anyone else, and an unknown key, get one answer. A staged file is kept as it was read, the columns no field was mapped from too (only the mapped fields reach the owner): the refusal of a column is by its name, so a secret under a name the list does not know is kept until the retention removes it. Only who staged it changes or applies it, while they still hold the import permission and the scope: every row is written under that user's own authority. The result file writes a cell that a spreadsheet would read as a formula (`=`, `+`, `-`, `@`, a tab) as text, a plain number (`-10.00`) as it is. Staged rows are removed after the target's retention (`clean#TransferBatches`), the outcomes kept.
- A validation changes nothing of the owner's (the row service is the owner's non-mutating check, run apart). An apply names the validation's fingerprint, which covers the content's hash, the mapping, the options, the registration's revision and each row's preview, and is refused when any changed. Each row is locked, validated again (a source changed since the preview is not written), and applied apart from the others under an operation key made of the batch, the row and its values, so an owner that honors the key answers a stopped apply's repeat with what it made. An applied row is never applied again: a repeat takes the rows left, and `retry#ImportItems` only rows that failed, each only if its source is still as its preview read it (a row whose source changed is validated and reviewed again). A validation after a partial apply still counts the applied rows' keys, so a row repeating one stays refused.
- `find#Transfers` (`ADMIN_TRANSFER_VIEW`) lists every target's runs. An owner's runs are what the owner's find service answers for this caller, by the owner's permission and scope, read as data: texts cut to a line, numbers as numbers, the parameters of the owner's place as names and short values. Never a row's content, and an owner that does not answer is named while the others are listed.

### Business exports

Business exports (Admin P16). `DataTransferServices`' `find#ExportTargets`, `get#ExportFields`, `preview#Export` and `run#Export` (`DataTransferExports.js`; granted to `ALL_USERS` by name in `AdminTransferServices`) export a registered target to the caller. An export is the widest read path an administrator has, so what it can read is a closed list and every read is its owner's.

- Nothing is exported without a registration (`moqui.server.TransferTarget`, direction `export`, its owner's seed row): a request names the target's id, one of the scopes the target's scope service gives this caller, values of the selection options the registration names and names of the fields it names, each by its own name. No parameter is an entity, a field, a filter, a service, a path, an address or a recipient. The owner's one service is called as the caller through `call#TargetService`, as an import's steps are: below an app screen's inheritable ALWAYS grant the only wall is that service checking the caller's permission and scope itself, so an owner registers only a service that does. A target's `exportPermission` is asked besides.
- A registered field names the permission that reads it. A field the caller does not hold it for is left out and named in the answer, whatever the request asks: it is not in the list the owner's service is given, and of a rows target's answer only the given fields are written, by own name. A field naming a permission that does not exist is logged and left out for everyone. The name of a left-out field's permission is not answered; the target's own `importPermission`, `exportPermission` and `viewPermission` are, by `find#ExportTargets` and by `get#ExportFields`, which asks only for a signed-in user at the door, as an import column's permission is.
- The file is the service's answer and nothing else: it is not stored, and nothing sends it. One export holds at most the target's rows and bytes (never more than 50000 rows and 16 MiB) and a larger one is refused whole, never cut short. A file written here is delimited text in which a cell a spreadsheet would read as a formula is written as text (a plain number such as `-10.00` is no formula); a file target's owner writes its own format.
- Each export keeps one `TransferBatch` record (state `exported`: who, the target, the scope, the selection, the field names, the row count, the file's name and the hash of its content; never the content) and one `EntityAuditLog` row. An operation key is one export's: its repeat by the same user for the same request makes the file again and keeps no second record, with an audit row of its own (it reads the data again), and anything else under it is refused. The record and the audit row are written in `run#Export`'s own transaction, and a file's bound is counted in UTF-8 bytes. A record is read by who exported, while they hold the target's export or view permission and its scope, and by a holder of its view permission whom its scope service admits; it is removed after the target's retention (366 days when it names none).
- `find#Transfers` with direction `export` also lists, for a holder of `ADMIN_TRANSFER_VIEW`, the occurrences of scheduled business reports and the last outcomes of business alert rules, from the report engine's administrative reads (`find#ReportOccurrences`, `find#AlertDeliveries`): an occurrence's id, its owner, its state and its counters; a rule as a digest of its id (the id carries its title's words). Never a title, a recipient, a value or content, and no way to open one: a report stays its recipient's (`get#RecipientReport`).
- What the administration screens read and post of the two (System › Data and the apps that show its screens, [Admin-Screens-Down](../../plans/archive/Admin-Screens-Down.md) A5) is five more services of the same group, each over the ones above and adding no field, option or right: `find#ExportRuns`, `get#ExportContext`, `find#ImportRuns` and `get#ImportDetail` ask `ADMIN_TRANSFER_VIEW` or `ADMIN_TRANSFER_RUN` and answer what `find#Transfers`, the target catalogs, `get#ExportFields`, `preview#Export`, `get#ImportTarget` and `get#Transfer` answer the caller; `run#ExportRequest` asks `ADMIN_TRANSFER_RUN` and then is `run#Export` of a wizard form's values, called as a service for its own transaction. An owner's place is answered as the registration's key (`ownerRoute`), never a URL: the screen resolves it by its mount's routes.

### Backups

Backups (Admin P16). `BackupServices` (`Backups.js`; `get#Coverage`, `find#Archives` and `run#Backup`, granted to `ALL_USERS` by name in `AdminBackupServices`) are a view of `backup#EmbeddedDatabase`, its job `backup_EmbeddedDatabase_daily` and that job's runs. Reading needs `ADMIN_BACKUP_VIEW` or `ADMIN_BACKUP_RUN`, asking for a backup `ADMIN_BACKUP_RUN`.

- No parameter names a path, a file, a directory, a mode or a destination. The archive directory, the mode, the counts kept and the mirror are the job's stored parameters and the conf (`database-backup@dir`), which an instance administrator sets (below). An archive is answered as its name, database, kind, tier, time and size, never its path; no service, transition or REST resource downloads or restores one (an archive is the whole instance's data: its download is later, under the sealed `ADMIN_BACKUP_DOWNLOAD`; the mirror below sends it out without that permission). The mirror is answered as set or not, never its address.
- Coverage is what the job's runs recorded. A success is a run that ended without an error, was not skipped and names its archive; skipped (this process runs no embedded database), failed, partial (an archive written with a failure after it), not ended and never run are each their own state, an external database is unknown, and nothing a person does marks a backup done. The warning of what an archive does not hold (`.env`, the field-encryption key, files outside the database) is fixed text, returned with every state.
- `run#Backup` starts one run of the job with its stored parameters (anything else in a request is not read), with a reason kept in the audit log. It is refused while a run is under way, within 30 minutes of the last run or request, and after three requests in a day, taken one at a time under a ledger row: each run writes an archive and moves the kept dailies along, so asking often would push older archives out. The run is started by `start#BackupRun` (granted to no group), which has no transaction: `ec.service.job(name).run()` writes the run's row in the caller's transaction and hands the run to a worker at once, and a row not yet committed would lose the run's start and, for a short run, its end.
- One backup at a time. Two runs beside each other are not safe (each removes every unfinished archive in the directory at its start, the other's too), and a run outside the schedule takes no lock of its own: so the run `run#Backup` starts takes the job's lock (`ServiceJobRunLock`, through the internal `hold#BackupLock`) once it has its run id, and the job runner releases it at the run's end, as a scheduled run's. The schedule then starts none beside it, and a request is refused while a scheduled run holds the lock. A lock naming a run that ended is read as free. A job run from Tools takes no lock: that stays an instance administrator's care. A success with the job paused or unscheduled is answered as `unscheduled`, not as covered.
- `backup#EmbeddedDatabase` (`impl/ServerServices.xml`, `authenticate="false"`) is the service that takes parameters: `backupDir`, `systemMessageRemoteId`, `mirrorTransport`, `mirrorEncrypt` and `mirrorRecipient`. Whoever writes the job's `ServiceJobParameter` rows (the raw `createJobParameter` of System's `Operations/JobDetail.xml`), changes the mirror remote's `sendUrl` and credentials (the raw `updateMessageRemote` of `Integrations/ConnectionDetail.xml`) or calls the service by name (Tools › Service Run) chooses the archive directory, any directory the server can write, and the host the archives go to. A user who opens System by their own grant (`ADMIN` in the seed) reaches these, and none of them asks `ADMIN_BACKUP_DOWNLOAD`. The delegated services hold: `store#Job` refuses the backup job (it has no `JobRegistration`), and the connection services keep the mirror's remote read only.
- A run starts `pg_dump`, `pg_basebackup` and `pg_verifybackup` from the cluster's own `bin_dir`, with no shell and the superuser password in `PGPASSWORD`, and kills the process group on a timeout; no argument comes from a request but the backup directory and the manifest path under it (`crates/moqui-drivers/src/backup.rs`). At its start it deletes every entry of the backup directory whose name ends `.partial` (a directory whole), and it deletes the archives the retention plan drops. The directory may not hold or sit inside a cluster's data directory. The job's dump is `0600` before `pg_dump` writes it, a physical backup `0700` and `0600`.
- The mirror (`crates/moqui-core/src/service/backup.rs`, `backup_store.rs`) sends each archive to the named remote's `sendUrl` (an SFTP host, or `s3://bucket?region=&endpoint=`) with that row's `username` and `password` or key pair, under the message type's `sendPath`, plain unless `mirrorEncrypt` and an age recipient are set; its tar follows no symbolic link, and it renames and deletes the remote objects whose names parse as archive names. It reads no `disabled` or `allowPrivateNetwork` of the remote, and an S3 endpoint may be `http`. SFTP checks the host key: a pinned `sshHostKeyFingerprint`, else the first key seen (`crates/moqui-core/src/sftp.rs`).
- A dump outside the job, and every restore, are a local user's: `moqui save-db` and `moqui load-save` on the command line, and the desktop app's tray (`crates/moqui-desktop/src/backup.rs`: a settings file `backups` in the app's config directory, the folder `MR-Moqui Backups` in Documents by default, the two commands as child processes). Their dumps and the folder are made with the process umask, not `0600`. A restore loads the chosen dump into `moqui`, then every file beside it named `<name><suffix>` (`<name>` letters, digits and `_`) into a database of that name, created when missing, as the superuser; only `moqui` and `postgres` are left out, and the desktop app checks only the chosen file's name.

### Readiness and settings

Readiness, refresh and the settings index ([Admin-Screens-Down](../../plans/archive/Admin-Screens-Down.md) A6). `ReadinessServices` (`Readiness.js`; `get#Readiness`, `request#Refresh`, `get#Overview`, `get#HealthCards`, `get#SupportSummary`, `find#Settings` and `check#InstanceSetup`, granted to `ALL_USERS` by name in `AdminReadinessServices`) read three registries their owners seed: `moqui.server.ReadinessProvider`, `RefreshOperation` and `SettingsEntry`. `get#Readiness`, `request#Refresh` and `find#Settings` ask no permission of their own, only a signed-in user, and leave the rest to the registration: a provider or a refresh whose row names no `requiredPermission` is run for any signed-in user, as that user.

- No service, entity or index name comes from a request. A request names a provider's, an operation's or an entry's key, an owner app, a group, a state; the row names the service. A row naming a service or a permission that does not exist is logged and left out, and a key that is no row answers `REFRESH_UNAVAILABLE` or nothing.
- The registration adds no right. The group's ALLOW is not inheritable, so a registered service is authorized for the caller as a direct call is (below an app's screen its inheritable always-allow covers it, as everything there), and it is called as the caller, never with authorization off: a provider the caller may not call, or that refuses the caller (`PERMISSION_DENIED`, `RECORD_UNAVAILABLE` and the like), is left out; one that fails otherwise is named as not checked, without its error's text, and the others still answer. A provider's `requiredPermission` and a refresh's are asked first; `request#Refresh` answers `REFRESH_DENIED` without it and a failure of the owner's service as a safe result (`failed`), never its text.
- A scope is opaque. `scopeParameters` reach an owner's service only by the names its registration lists, as plain texts of at most 255 characters; the operation key, the reason and the registration's key are never taken from them. What a scope means (an organization, a store) and whether the caller may ask for it is the owner's check. `instanceOnly` leaves out every provider that takes a scope.
- A place is a key. A check's fix place, a card's list and a settings entry's destination are answered as route keys with an id and parameters (`fixRoute`, `route`, `destinationRoute`), which the screen resolves by its mount's routes; no URL is stored or answered, so a registration cannot send a user to an address of its choosing.
- The settings index lists an entry only to a caller who holds its `viewPermission` and whose own grants open its `screenLocation`: the caller's `ArtifactAuthzCheckView` rows for screens are read directly and counted down the location's directory as the framework counts a screen path (an always-allow, an inheritable allow above, no deny), so nothing of the frames on the stack widens it. An entry with no screen or no route is not listed. The entry grants nothing: its destination checks the user again.
- `get#Overview`, `get#HealthCards` (the overview's counts alone, no provider run) and `get#SupportSummary` ask `ADMIN_OVERVIEW_VIEW`; the summary's sections are each read with the caller's own permissions and say so when refused. It holds no environment value, host fact, listener, path, user, fix place, scope or diagnostic, and a secret setting only as set or not. Redacted (what the screen's download always is) it also names no one, writes an email address in a check's subject, message and coverage, a protocol's reason and a setting's value as `[address]`, and says of a setting that names the server's inside (a listener's bind address, the gateway addresses, a certificate file) only whether it is set. A registration's own title is not rewritten: it is its owner's seed text.
- `check#InstanceSetup` runs only the framework's own checks, by key, after `ADMIN_OVERVIEW_VIEW` (the protocols' check asks what `get#ProtocolReadiness` asks). They read the framework's records with authorization off and answer states and counts: no host, address or person. The telemetry check reads `MonitorServices.get#SourceStatus` with authorization off and answers only whether telemetry is received, lost or unknown.

### Change evidence

Change evidence (Admin P17). `AuditServices` (`Audit.js`; `find#Changes`, granted to `ALL_USERS` by name in `AdminAuditServices`, `data/AdminAuditData.xml`) is the audit log (`EntityAuditLog`) as a delegated audit reader may be shown it. The log holds the old and new value of every audit-logged field of every entity of every organization, so it is the most sensitive read of the family. The log is written only by the framework and its own services: `EntityAuditLog` has no `authorize-skip` and is a service-written entity (`sensitive.rs` `SERVICE_WRITTEN_ENTITY_KEYS`), so entity REST, Service REST, the Tools record and grid writes, ETL targets and request loads read it and never write it (plans/Security-Review.md SEC-RTE-03, fixed). Reading needs `ADMIN_AUDIT_VIEW`; the whole audit log is the instance administrator's part of System › Audit › Changes, never shown under a mount ([Tools and System](Attack-Surface-Tools.md#tools-and-system)).

- Only registered projections are answered. A projection (`moqui.server.AuditProjection`, seed data of the record's owner) names one field of one entity and whether its values may be shown; a request narrows a find by a projection's id or a category, never by an entity or a field, and a change of anything unregistered is not found, listed or counted. A registration of every other field of an entity (`*`, for a configuration record such as a connection or a job) names the field that changed and never a value, and does not cover a field registered on its own, whoever may read that one. A registration that does not read (an unknown entity or permission, a source that is not defined or lacks its contract) is logged and left out.
- A secret is never a value. A projection is a marker (set, changed, cleared) unless its registration says show; a field the entity definition encrypts, or whose name reads as a secret, is a marker whatever the registration says (the entity audit log keeps an encrypted field's values encrypted, and those are not answered either). A service's own row for a secret holds only `(set)`, `(replaced)` or `(cleared…)`, shown as it is. A shown value is plain text of at most 500 characters with control characters removed; the reason and the actor's name likewise. The screen escapes them, and the CSV render guards a cell that begins like a formula.
- Whose changes. A projection with no `sourceService` is a record of the whole instance (a group's grants, a connection, a job, a setting): a holder of `ADMIN_AUDIT_VIEW` reads it. A record that belongs to an organization (a user's account, a membership, an invitation, a lifecycle operation, an export a person made) is registered by the component that knows organizations, with its `sourceService`: that service (the contract `find#OwnedChanges`) finds the audit rows within the caller's own scope and answers their ids only, and the rows are read and masked here, each checked to be of a projection of that source. It is called through `call#ChangeSource`, whose `ALL_USERS` ALLOW is not inheritable, so the owner's service is authorized as a direct call of it is. Mantle's source (`mantle.party.IdentityServices.find#IdentityChanges`) reads views that join the audit log's rows back to an internal organization, under the organization entity filters of the authorization the call runs under. Without such a component (a framework-only instance) a user's account and memberships are not in `find#Changes` at all.
- Bounds. A find reads at most the 2,000 newest rows across its sources (a deeper page is refused with a notice), a page is at most 100 rows, an export one page of 1,000 marked truncated when more match. A source that fails is named and the others are answered.
- What is written. An administrative action that changes no audit-logged field leaves a row of its own, with the actor, the session (`changedInVisitId`) and the reason: another user's sessions ended and access revoked (`IdentityServices`, on the account; the kinds and counts, never a credential), an import applied (`TransferBatch`, counts), a mail message closed or sent again from the queue (`EmailMessage`; a message's own state rows are every send of every user and are not registered).
- Access evidence is log lines, read through a dataset. A dataset that aliases a telemetry index (`indexName`) needs a row filter in its definition, but a dataset has no field list: whoever holds its artifact reads each matching line whole (a scheduled export's recipient addresses and a runtime setting's value are attributes of the audit lines). So an application that shows such lines to a delegated reader grants the alias's artifact to no group and reads it in its own service after its own check, with authorization off, answering named fields only (mr-boss `admin-access-log`, `ironstone.admin.AuditServices.get#AccessLog`). The row filter of an alias is whatever its definition says, so the engine asks for the index's own artifact (`org.moqui.report.dataset.otel_logs`), not only the alias's: of whoever saves the definition (`save#Definition`, a copy, a restore, an import, a git pull), and at each read of the reader or of the saved definition's owner, asked as the owner then, while the owner's account is open (`crates/moqui-report/src/alias.rs`; [Monitoring](../tools/Monitoring.md#dataset-aliases)). A holder of `org.moqui.report.dataset` update who is granted the datasets they name by a pattern (mr-boss's dataset steward, `insights-.*`) is refused the save of an alias of a log index, and a row written past the save is refused when read; the same holds for a business dataset's document read without its signal, or under the signal with no registered scope policy bound, which needs the document's own update artifact of every reader. A shipped alias (a component's `report/*.json`) is its component's code and is read by its own artifact: grant it as narrowly as its filter deserves, or to no group as here.

### The new-device notice

The new-device sign-in notice (Admin P10). `IdentityServices.notify#NewDeviceSignIn` (`IdentityNewDevice.js`) is called by the EECA `UserLoginHistoryNewDevice` when a successful sign-in's history row with a visit is written (after the sign-in, by a worker; at most one row a minute for a user), with authorization off and in a transaction of its own; no group is authorized to call it, and no request reaches it. Not every sign-in writes that row (`crates/moqui-core/src/user/login.rs`): the password step of an account with a second factor is recorded as not signed in and the step that finishes the factor (`internal_login_user`) records nothing, so a password sign-in with a second factor sends no notice; and the minute's one row is claimed by a failed attempt as by a successful one, so a sign-in within a minute of any other attempt on the account (a wrong password sent first, or a key or automation that signs in every minute) sends none. It refuses a visit that names another user, compares the visit's client (the browser and system of its user agent, and the network of its address: an IPv4 /24, an IPv6 /48) with at most 500 of the visits the account's login history names and the account's other visits within `signin.newDeviceWindowDays`, sends nothing for a known client, and otherwise sends one notification on the private topic `AccountSignIn` to the account alone, in its list and by email (`ACCOUNT_SIGN_IN`), with the time, the client summary, the network and the visit's id: never the user agent, the whole address, a session id or a token. An account's first sign-in sends none.

### Owned resources

Owned resources (Admin P6). A shared drive (`FileServices.transfer#DriveOwner`) and a shared mail account (`EmailClientServices.transfer#EmailAccountOwner`) change owner by their owner, or for another user with `DRIVE_OWNER_CHANGE` or `EMAIL_ACCOUNT_OWNER_CHANGE` (granted to `ADMIN`); the new owner must be an enabled account that is not ended and not an external user (`EXTERNAL_USER`), and only a shared drive (not personal, records or mirror, not archived) or a shared mail account (`EakShared`) moves: a personal account keeps its owner's own sign-in. `find#OwnedDrives` and `find#OwnedEmailAccounts` list names only, the caller's own or another's with the same permission. All four are under `ResourceOwnerServices`' `ALL_USERS` ALLOW, and each checks its permission itself. They carry the owned-resource contract (`IdentityServices.define#OwnedResourceLookup`, `define#OwnedResourceTransfer`, `define#OwnedResourcePause`, interfaces only): a coordinator that stores the service a step calls (Mantle's account lifecycle) calls it through `IdentityServices.call#OwnedResourceService`, which refuses a service without the contract's parameters (so a stored step cannot name a service written for something else) and whose `ALL_USERS` ALLOW (`OwnedResourceCall`) is not inheritable, so the coordinator's own inheritable grant (Mantle's identity services') does not carry into the owner service: it is authorized on its own records, as a direct call is (an app screen's inheritable ALWAYS grant still covers it, as it covers everything below that screen). `call#OwnedResourceService` takes the service's name as a parameter and checks no permission of its own: a signed-in caller's call of it reaches any service whose parameters match a contract by name (`userId` in, `resourceList` out and the like). No screen transition, REST resource or script names it; its one caller is Mantle's account lifecycle coordinator (`mantle/party/Lifecycle.js`), with the service of its own step. `OperationServices.call#OwnerService` (which takes a service name, checks no permission or sign-in of its own, and calls only a service a registration names) and `DataTransferServices.call#TargetService` (which takes none) are likewise called only from the administration scripts. The framework knows no organization here either: the app scopes the user whose resources move.
