# Attack surface: DAV and SFTP

DAV (files, calendars and contacts) and SFTP. The `/resources` file manager and the upload transitions of the root screen are rows in [Attack-Surface-Routes.md](Attack-Surface-Routes.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## DAV

The routes are always registered. There is no `<dav-server>` element in `MoquiDefaultConf.xml`. The defaults are the Rust fallbacks, and `docs/interfaces/Sync.md` states the same numbers.

| Flag | Default | Effect |
| --- | --- | --- |
| `enabled` | true | `false` is 404 `the DAV server is off` for every method but OPTIONS; OPTIONS and the `/.well-known/` redirects still answer; the answer comes before the body is read |
| `allow-http` | false | otherwise credentials need a secure request: HTTPS, a believed proxy's https, or loopback |
| `account-password` | false | app password only. `true` also accepts the account password |
| `max-file` | 268435456 (256 MiB) | 413 over a PUT's body; any other method's body is at most 1 MiB (`MAX_XML_BODY`) |
| `sftp-drives` | true | SFTP to drives for a user without `SSH_SFTP` |

OPTIONS is answered with no login: `DAV: 1, 2, 3, calendar-access, addressbook, extended-mkcol`, and `Allow` lists `OPTIONS, GET, HEAD, PUT, DELETE, PROPFIND, PROPPATCH, MKCOL, COPY, MOVE, LOCK, UNLOCK, REPORT`. `MKCALENDAR` is not listed and is answered 403 after login (`dav/pim.rs`).

Every other method is HTTP Basic. No credentials is 401 `WWW-Authenticate: Basic realm="Moqui", charset="UTF-8"`. Plain HTTP while `allow-http` is false is 403 `credentials over plain HTTP are refused; use HTTPS`. A path whose user segment is not the signed-in username (case-insensitive) is 404. Writes go through the file and adapter services as that user. `docs/interfaces/Sync.md` paths: `/dav/`, `/dav/principals/<user>/`, `/dav/files/<user>/<drive>/<path>`, `/dav/calendars/...`, `/dav/addressbooks/...`. The framework keeps no calendar or contact of its own. An application serves them through adapter services, and Mantle sets those adapters.

Projected address books (Mantle's `ContactProjection`, IronStone Sales' My accounts) are read-only collections
`projected-<id>` computed per request by their owner service as the signed-in user: the collection is listed only when the
owner admits the user, its cards are the parties the owner answers for that user (Sales: the contacts of the accounts the
user manages or has deals with, in their Sales scope), and `PUT` and `DELETE` on them answer 403. No `ContactBook` row is
copied.

### Request handling

What the head decides is answered before the body is read (`moqui_dav::dav::answer_before_body`, which `serve` calls too): a path outside the server, OPTIONS, `enabled="false"`, no credentials, credentials over plain HTTP. A PUT's credentials are checked first without a login (`credentials_hold`: an app password, or the account password with `account-password="true"`). A PUT's body is then spooled to `runtime/tmp/upload` as an upload's file part, up to `max-file`, and handed to the drive without a copy (`BodySpool`, host `read_to_spool`, `DavRequest::upload`); any other method's body stops at 1 MiB (`crates/moqui-host/src/dav_http.rs`; plans/Security-Review.md SEC-FIL-04, fixed). A declared `Content-Length` over the limit is 413 before the body is read. A failed login is recorded for web protection (`Event::AuthFailure`). After login, a path segment that decodes to `.`, `..` or holds `/` is 400 (`crates/moqui-dav/src/dav/mod.rs`). The request body is parsed as XML for every method but PUT; the reader refuses a DOCTYPE and nesting past 256 (`dav/xml.rs`, `moqui_lib::node`), and counts neither elements nor attributes.

A drive is named by its folder name (case ignored) or its `driveId`, from the list `FileServices.get#UserDrives` returns for the user. GET of a file sends `Content-Type` by the file's name with `ETag`, `Accept-Ranges` and `Last-Modified`, and the headers a screen download of a user's file gets (`web::user_file_guard_headers`): `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` (not for a PDF shown inline) and `Content-Disposition: attachment` for a type that can run script (HTML, SVG, XML, JavaScript) (`dav/files.rs` `get`; SEC-FIL-03, fixed). A calendar or contact object's GET (`dav/pim.rs` `object`) gets the same headers. GET of a folder is an HTML list of escaped names. PUT calls `upload#Resource` with `conflictPolicy` `replace`. DELETE calls `trash#Resource`. COPY and MOVE take a `Destination` under `/dav/files/<the same user>/`, else 502, with the same segment rule (400), and call `copy#Resource` or `move#Resource`. Each of the services a write calls checks `canWrite` or `canUpload` itself. File content is opened with authorization off after `get#ResourceInfo` admitted the path (`open_file` in `crates/moqui-dav/src/dav/files.rs`).

LOCK and UNLOCK are served on `/dav/files/<user>/<drive>/<path>` (`dav/files.rs`, `dav/locks.rs`, `crates/moqui-core/src/resource/locks.rs`). A lock is a `moqui.resource.ResourceLock` row keyed by the SHA-256 of the resource location: exclusive write only, depth infinity unless `Depth: 0`, 600 seconds by default and at most 3600, refreshed by its owner with the token. LOCK asks only that no other user holds a lock on the path; it does not ask whether the user may write the path or whether the path exists, so any user the drive is listed for (view level included) locks any path of it, the drive's root included. Every writer keeps a lock: the resource facade refuses a write, delete or move by another user, on the Files screens, SFTP and the services. Only the lock's user with its token unlocks; no screen or service releases another user's lock. Locks are not counted for a user or a drive, the `D:owner` text of the body is stored with the row and written back escaped, and expired rows are deleted when a lock is next written.

PROPFIND serves `Depth: 0`, and 1 for anything else, `infinity` included (`dav/mod.rs`). The answer is built whole in memory: one response for each child, with every property the request names that the resource lacks in a 404 propstat. Neither the children of one answer (`list#Folder` answers them all) nor the properties asked (a 1 MiB body) are counted.

REPORT serves `calendar-multiget`, `calendar-query` (the component and `time-range` of the first nested `comp-filter` only), `addressbook-multiget` and `addressbook-query` (no filter is evaluated: every card is answered, cut by `limit/nresults`) (`dav/pim.rs`), and on a principal `principal-search-property-set`, `principal-property-search` and `expand-property`, each answering only the caller's own principal. Anything else, and every REPORT under `/dav/files/`, is 403 `supported-report`. There is no `free-busy-query`, no `sync-collection` and no scheduling inbox or outbox.

### Calendars and contacts

`crates/moqui-dav/src/dav/pim.rs` holds no calendar or contact logic of its own. It calls four services of the class named by `dav-server` `calendar-services` or `contact-services`, as the signed-in user with authorization on (`sync_checked`): `get#DavCollections`, `get#DavObjects`, `put#DavObject` and `delete#DavObject`. mr-mantle's `MoquiConf.xml` sets `mantle.work.CalendarDavServices` and `mantle.party.ContactDavServices`. A PUT or DELETE on a collection whose row has `readOnly` is 403 `need-privileges` before `put#DavObject` or `delete#DavObject` is called.

Calendars (`runtime/components/addon/mr-mantle/service/mantle/work/CalendarDavServices.xml`): the collections are the calendars `CalendarServices.get#UserCalendars` answers with `CalpView`, `CalpEdit` or `CalpManage`, a `tasks` collection, and each `projected-<id>` collection whose owner service admits the user. `get#DavObjects` calls `check#CalendarAccess` for a calendar. `put#DavObject` and `delete#DavObject` need `CalpEdit` or `CalpManage` on a calendar that is not a subscription (else 403), and `EventServices.check#EventAccess` for an existing event. An event is stored through `CalendarServices.store#CalendarFeedEvents`; a task is made with `TaskServices.create#SimpleTask` assigned to the user's own party, or changed with `update#Task` and `set#TaskStatus`. `put#DavObject` itself calls no mail service, and no mail goes to an address from the client's object: `store#CalendarFeedEvents` takes only the summary, description, location, url, status, sequence and the times of an event, so a client's ATTENDEE, ORGANIZER and VALARM are dropped, and a UID is matched only inside the calendar named. The rule (`rrule`) and the url are stored as given, with no parse of the rule first, and the writer puts both back into an object unescaped. `check#ResourceBookings` after a move tells the resource's approvers, parties read from `FacilityParty` or `AssetPartyAssignment`. A calendar shared as `CalpFreeBusy` is no collection and its objects are "not found". The object text is parsed by the `ICalendar` tool; the `data` parameter is `allow-html="any"`.

Contacts (`mantle/party/ContactDavServices.xml`): `get#DavObjects` calls `ContactBookServices.check#ContactBookAccess` with `CbpView`. `put#DavObject` and `delete#DavObject` answer 403 unless the user is the book's owner and the book is `CbvPersonal`. `get#ContactObjectTags` with a `partyIdList` (the projected books) finds those `mantle.party.Party` rows with authorization off; its only caller is `get#ProjectionObjects` in the same file, with the list the owner service answered for the user. A changed card must be the user's own private party.

The adapter services are granted by an artifact group that names exactly the four of each class (`mr-mantle/data/MantleSetupData.xml`). `get#CalendarObjectTags`, `get#TaskObjectTags`, `get#ContactObjectTags` and `get#ProjectionObjects` make no access check and are called only from inside those two files.

The parsers are in `crates/moqui-dav/src/pim`. A recurrence rule expands to at most 100000 instances (1000 for an open-ended rule) over at most 2000000 periods, 50000 of them empty (`rrule.rs`). Those limits are tested after each period is built, and one period gives at most 100000 candidates, its first (`MAX_PERIOD_CANDIDATES`; logged when a rule passes it), though a rule's times of a day (BYHOUR x BYMINUTE x BYSECOND) may be up to 86400 for each matching day; a BYxxx list keeps each value once, so its length is bounded by its range (SEC-FIL-85). `ics.rs` nests components at most 8 deep (`MAX_DEPTH`; a deeper one is left out with all it holds, logged) and reads at most 100000 components a file (`MAX_COMPONENTS`; the rest is left out, logged), so the drop of a parsed tree, which recurses a level for each, stays shallow (SEC-FIL-82). `vcard.rs`, `line.rs` and `zones.rs` have no count or size limit: unfolding has no line length or line count limit, and quoted-printable is decoded for any property. An object a client PUTs is at most 1 MiB (`dav/pim.rs` `MAX_OBJECT`), 413 before it is parsed.

DAV is not the only caller. `ICalendar.parse` also reads a subscribed feed of up to 16 MiB, the HTTP client's response limit (`CalendarServices.fetch#CalendarSubscription`, from the `fetch#CalendarSubscriptions` job every 15 minutes or `fetchNow`; any signed-in user with a party subscribes to an `https` URL through the mr-boss `Commons/Settings/Calendars.xml` transition), an imported file (`import#Calendar`), and the `.ics` part of a received mail of up to 512 KiB when the message is shown (basic-comms `InboxServices.get#InvitationCard`). `ICalendar.expand` runs on every stored rule each time a range of a calendar is read (`EventServices.get#EventInstances`), the anonymous published calendar included (`get#PublishedCalendarEvents`); a failed expansion of one event is logged and the event shows its first instance. A panic in a parser called from a script is caught and thrown as a script error; a stack overflow is not.

`login_user` does not call `finish_login` when a second factor is required. DAV requires that login to succeed and requires a non-empty current user id. The wrapper that maps a second-factor result onto the current user was not read.

## SFTP

SFTP is the SSH `sftp` subsystem. Nothing listens for it unless the SSH server is up. `docs/interfaces/Sync.md` "SFTP to the drives" is this subsystem. The outbound SFTP client dials other hosts ([The SFTP client](#the-sftp-client)).

`sftp-drives` defaults to true. `sftp-root` defaults to `runtime://sftp`. `sftp-max-file` defaults to 256 MiB. The user must already be logged in by key, password, or app password. A dialog login is refused. A login by app password (`LoginBy::AppPassword`) gets the drives backend over SFTP and nothing else, whatever the user's permissions: no `sftp-root`, admin shell or git (plans/Security-Review.md SEC-FIL-02, fixed). `SSH_SFTP` (seeded on `ADMIN`) selects the root: one resource location (`runtime://`, `file:`, `component://`, or `dbresource://`), paths normalized against `/`, and `..` that leaves the root is refused. Those calls run with authorization off. The permission checked at login is the gate. A user without `SSH_SFTP` gets the drives that user may open, when `sftp-drives` is true. `sftp-drives="false"` gives that user no SFTP. A write is an upload and a new version. A removal goes to the trash. At most 64 handles per channel.

### The SFTP handler

`crates/moqui-host/src/ssh/sftp_fs.rs` implements `realpath`, `stat`, `lstat`, `fstat`, `setstat`, `fsetstat`, `opendir`, `readdir`, `open`, `read`, `write`, `close`, `remove`, `mkdir`, `rmdir` and `rename`. It has no `symlink` or `readlink` handler. A client path is split on `/`; `.` and empty parts are dropped, `..` removes the part before it, and a `..` with nothing before it is `PermissionDenied` `outside the SFTP root`. The root cannot be removed or renamed.

With `SSH_SFTP` the target is the `sftp-root` text followed by the normalized path, and each operation runs on a worker with authorization off through the resource facade (`stat`, `list`, `get`, `open`, `write_bytes`, `delete`, `make_directory`, `rename`). Which roots take writes is the facade's rule ([Resource facade schemes](#resource-facade-schemes)). A symbolic link that is on disk under a file root is followed: `stat` and a write resolve it and act on its target, and a delete removes the link itself. The handler makes no link, so one must be put there by other means. Without `SSH_SFTP` each operation runs after `internal_login_user` of the channel's user through `moqui_dav::dav::files::tree`, the drive services as that user: `locate` picks the drive from `get#UserDrives` by folder name or id and refuses `.` and `..`, and `stat`, `list`, `open`, `read`, `write`, `make_directory`, `remove` and `rename` go through the same service calls as WebDAV. The tree neither takes nor checks WebDAV locks itself; the facade checks them on the write.

A file opened for writing is held in memory until it is closed. The bytes open files hold (writes in memory, read windows) are counted per user over all of that user's channels and connections (`ssh/sftp_fs.rs` `Held`). Writes are bounded by that count: `open` for writing and `write` refuse past the user's room, so one user's writes hold at most `sftp-max-file`. A read window is counted and not bounded: `read_window` sizes it by the larger of `READ_WINDOW` and the `len` the client sends (32 bits, passed unchanged by russh-sftp), up to the rest of the file, and checks no room; a file of up to `sftp-max-file` may be opened for reading. One connection holds at most 8 session channels waiting for a request or running `sftp` (`MAX_SESSION_CHANNELS`); one more is refused (SEC-FIL-61, fixed).

### The SFTP client

`SftpClient` in scripts (`crates/moqui-core/src/script/host/sftp.rs`) and `SystemMessageRemote` rows (`crates/moqui-core/src/sftp.rs`, `service/system_sync/sftp.rs`) dial any host and port a script or a row names; there is no private-address check. The default port is 22 (the description in `SftpMessageServices.xml` says 115). The host key is the row's pinned `sshHostKeyFingerprint`, else trust on first use in `runtime/conf/ssh_known_hosts`; a changed key and a pinned mismatch are refused (`crates/moqui-host/src/ssh/client.rs`). The credential is the row's `privateKey` (with `publicKey`), else its `password`, or what a script passes; `Debug` redacts them and they are not logged. One call may take 120 seconds and an `exec`, which runs a command on the remote, 30 minutes. Paths are any the remote allows: a script gives them, and a sync row's `sendPath`, `receivePath` and `receiveMovePath` are expanded as script templates. `poll#SystemMessageSftp` lists the remote directory and reads each matching file whole into memory, every listed file when the row has no `fileCountLimit`; a remote file's name is used only on the same remote and as `remoteMessageId`. Both the client and the sync services are refused under the read fence and in sim mode.

## Drives and public shares

### Public shares

Public shares are five services of `org.moqui.resource.FileServices`, each `authenticate="anonymous-all"`: `check#PublicShareToken`, `open#PublicShare`, `list#PublicShare`, `download#PublicShare`, `upload#PublicShare`. mr-boss serves them at `/s/<token>` through the `PublicShare.xml` transitions `open`, `files`, `download` and `upload`; `open` and `upload` are `require-session-token="false"` and name no method ([CSRF](Attack-Surface-Web.md#csrf)).

A link is a `moqui.resource.ResourceShare` row with `isLink` `Y`, made by `share#Resource`, which needs edit level on the path. The token is `ec.user.randomString(32)`: 32 characters of URL-safe Base64 from 32 random bytes. Only `singleUseCodeHash(token)` is stored, in `linkTokenHash`. A token must match `^[A-Za-z0-9_-]{16,64}$`. A revoked or expired link is not valid. The services do not check again that the link's maker still has access to the path.

A link's password is stored as a password hash and checked by `open#PublicShare`, which returns a grant: `<expiry millis>.<HMAC-SHA256>` keyed by the link's token hash and password hash, valid 3600 seconds, compared in constant time (`check_grant` in `crates/moqui-core/src/script/host/files.rs`). `list#`, `download#` and `upload#PublicShare` ask for the grant only when the link has a password. `open#PublicShare` counts each try of a link's password before it checks it, 10 in ten minutes for the link and 30 from one requester (`AccountServices.record#Attempt`), past which it answers "too many tries" with no check (SEC-FIL-05).

A path with a `..` segment is "Not found", and a link to a whole drive does not reach `.trash`. `download#PublicShare` sends a file itself with `ec.web.sendResourceResponse`; inline is asked only for PNG, JPEG, GIF, WebP, BMP and PDF. A folder is zipped to `runtime://tmp/drive-zip/<16 random characters>.zip` (at most 20000 entries, depth 32).

`upload#PublicShare` takes files on a folder link with `RspUpload` or `RspEdit`, and calls `upload#Resource` with authorization off and `asInternal` true, `conflictPolicy` `keepBoth`. Each file is named by the last segment of its own name, so it lands in the shared folder and makes no folder (an empty name or `.trash` becomes `upload`). A link's own limits hold whatever the drive's `quotaBytes` (empty unless set): 20 files and 100 MiB in one call, 30 calls an hour through one link and 60 from one requester (`record#Attempt`), and 1000 files and 2 GiB through a link in all (`ResourceShare.uploadCount`, `uploadBytes`). The uploader's name (100 characters) goes into the version note. No type or content scan is done.

### Drive services

`org.moqui.resource.FileServices` serves drives (`moqui.resource.ResourceDrive`) over the resource facade. The `DriveDeviceServices` artifact group grants `get#UserDrives`, `list#Folder`, `get#ResourceInfo`, `upload#Resource`, `create#Folder`, `rename#Resource`, `move#Resource`, `copy#Resource` and `trash#Resource` to `ALL_USERS`, `AUTHZT_ALWAYS`, with `inheritAuthz` `Y` (`runtime/components/base/framework/data/SecurityTypeData.xml`). The other services are reached through an application's screens.

Each service calls `get#DriveAccess`. The owner is level 3. A current `ResourceDriveMember` row of the user or one of their groups gives its level. A `ResourceShare` to the user, a group or their party gives view or edit on its path and below. Another user's access is answered only with authorization off. A path with a `..` segment, or with a `#` (a read stops at it, so it would reach another file), is level 0; `create#Folder`, `rename#Resource` and `save#Text` refuse a name with `#` ("may not have # in it"), an upload's `#` is made `_`, and WebDAV and SFTP refuse a path with `#` before reading or writing (`crates/moqui-dav/src/dav/files.rs`). A mirror and an archived drive are read only. On a records drive a user below manage level reaches only mapped folders of records the visibility hook admits, and a user with `EXTERNAL_USER` reaches none. `list#Folder`, `get#ResourceInfo`, `upload#Resource`, `create#Folder`, `rename#Resource`, `move#Resource`, `copy#Resource` and `trash#Resource` each clean the path, refuse a `..` segment and test `level`, `canWrite` or `canUpload` from `get#DriveAccess` at the path before they touch the storage. `move#Resource` across drives is `copy#Resource` then `trash#Resource`; `trash#Resource` moves into `.trash/<trashId>/<name>`, or deletes in a git commit. A drive's `.trash` is refused by path, as the owner's only, in `list#Folder`, `get#ResourceInfo`, `upload#Resource` and `trash#Resource`; `copy#Resource`, `move#Resource`, `rename#Resource`, `save#Text` and `create#Folder` have no such test, so through the Files screens a member reaches a `.trash` path with them at the level the service asks (DAV and SFTP ask `get#ResourceInfo` first).

`create#Drive` refuses `mirror` storage, a records drive and an explicit `rootLocation` unless the caller is in `ADMIN` or authorization is off. Its `memberList` takes any `userId` or `userGroupId` with any permission, so the maker puts a drive of any name into another user's DAV home and SFTP top; a second drive of a name that user already has shows both folders there as `name (driveId)`. `transfer#DriveOwner` and `find#OwnedDrives` need the owner or `DRIVE_OWNER_CHANGE`. `create#Drive` `localPath` (a git drive's repository on disk, stored on the `GitRepository` row, used as given) is refused the same way: only an administrator or a caller with authorization off names one. `export#Drive` of a git drive needs the view right on the drive (`get#DriveAccess` level 1); a records drive (whose viewers see only the records they may) and a folder drive need manage. With authorization on, `export#Drive` takes `targetLocation` only as a relative path of `[A-Za-z0-9._-]` segments (no `.` or `..`, no empty segment, so no scheme or leading `/`) and writes the zip at `runtime://drive-export/<path>`; anything else is refused. With no target the zip goes to `runtime://tmp/drive-export/<driveId>-<ms>.zip`, cleaned by `clean#DriveTempFiles`; with authorization disabled the location is taken as given. `targetPath` (a git drive) is a relative path under `runtime/git-export`: `export#Drive` calls `export#GitRepository` with authorization disabled and `underExportDir`, which holds it there, so the drive's view right decides, not the repository's delete right ([Git](Attack-Surface-Git.md)); with no `targetPath` the bare repository goes to the repository's `localPath`. The mr-boss wrappers (`DriveServices.create#SharedDrive`, `DriveSettings.xml`) do not pass them. `create#SharedDrive` is the one caller of `create#Drive` outside tests; it passes the name, description, storage, `memberList`, `quotaBytes` and, for a mirror, the remote fields, and no `localPath`.

### Chunked uploads

`org.moqui.edge.ClientSyncServices.upload#Chunk` (the `uploadChunk` transition that Compose and Chat include) takes one chunk of a file of the signed-in user. `uploadId` must match `^[A-Za-z0-9_.:-]{1,64}$`. A file is at most 25 MB. A chunk other than the last is at least `client-sync@upload-min-chunk-bytes` (262144). A user holds at most `client-sync@upload-max-count` (20) unfinished uploads and `client-sync@upload-max-mb` (100) MB in all. Chunks are stored under `dbresource://upload/<userId>/<token>` and rows are found by `userId` and `uploadId`.

### The drive picker

`org.moqui.comms.FilePickerServices` (`get#PickerData`, `list#PickerFolder`, `find#PickerFiles`) lists drives, a folder and search results for Compose and the Inbox through the `pickerData`, `pickerFolder` and `pickerSearch` transitions (GET, `read-only`). Every read goes through `FileServices.get#UserDrives`, `list#Folder`, `find#Recent` and `find#Resources` as the user. `pickerData` without `checkOnly` makes the user's personal drive.

## The `/resources` file manager (elFinder)

The route is a row in [Attack-Surface-Routes.md](Attack-Surface-Routes.md). `ElFinderServices.run#Command` (`crates/moqui-dav/src/elfinder.rs`) implements `file`, `open`, `tree`, `parents`, `ls`, `get`, `mkdir`, `mkfile`, `rm`, `rename`, `upload` and `put`. `resourceRoot` and `volumeId` come from the request; with no `resourceRoot` the transition uses Mantle's `mantle@content-root` setting, else `dbresource://mantle/content`. A target is the volume id (3 characters) and the URL-safe Base64 of the path under the root. A path with a `..` segment or a segment holding `:` is `errFileNotFound`. `rm`, `rename` and `put` refuse the root. `rm` of a folder removes everything under it.

In production (`instance@purpose` `production`) every command, the reads (`get`, `file`, `open`) included, answers "This resource root is not served on a production instance" unless the root starts with `dbresource://`, `content://` or `git://` (`Connector::root_refused`, before the command runs; SEC-FIL-08, fixed); `file:`, `runtime://`, `component://` and `classpath://` roots are served on a dev or test instance only. A `content://` root is an error unless a component installs a provider for that scheme. The `resources` transition is `read-only="true"`, and it runs the same commands for GET and POST ([CSRF](Attack-Surface-Web.md#csrf)).

## Resource facade schemes

`ResourceFacade::get` (`crates/moqui-core/src/context/resource.rs`) serves `dbresource`, `file`, `runtime`, `component`, `classpath`, `http` and `https`, and any scheme a provider registered (`git`, and the CI artifact scheme of `moqui-git`). `content` is an error unless a provider is installed for it. `write_bytes` writes `dbresource` rows, provider locations, and files under `file`, `runtime` and `component`; other schemes are not writable. The facade does not reject `..`: `runtime://` and `component://` join the given path onto their directory. Callers check paths. A write, delete, move, change set or restore at a location with a `#` is refused on every storage (`refuse_cut_write`), since a reference and a read cut the location at the `#` (SEC-PFS-82, SEC-BAP-82).

## Archive extraction and image decoding

The script host function `resource_extract_archive` (`crates/moqui-core/src/script/host/archive.rs`) reads a tar, gunzipped when its first bytes are the gzip magic. It writes regular files only; a link, a device or any other entry type is skipped as `not a regular file`. An entry path with a root, a prefix or a `..` component is skipped as `an absolute or parent path`. Each file is written to `<target>/<path>` through the resource facade. The expanded stream is cut at `maxBytes` (4 GiB when the script gives none) and files past `maxEntries` (1000000 when the script gives none) are skipped. `resource_gunzip` also cuts its expanded output at a byte limit.

The image services (`crates/moqui-core/src/service/images.rs`) decode with the format guessed from the bytes and refuse an input wider or taller than 30000 pixels. A resize is refused past 16383 pixels a side or 50000000 pixels in all. A rich text image is at most 8 MiB.
