# Attack surface: development tools

This file covers what loads the dev set of components, the Dev AIDE app (`/apps/dev`) and its anonymous static mount (`/devstatic`), the framework's development services and the artifact index over REST (`/rest/s1/moqui/aide`), the development commands, the demo lock-down component, the example and template components, the test-only hooks, the test client, and the load runner's targets. This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## What loads the dev components

`runtime/components/components.xml` lists four component sets in load order: `base`, `addon`, `dev` with `purpose="dev"`, and `test` with `purpose="dev, test"`. Only a set listed there loads; a directory beside the file that it does not list is named in a WARN and not loaded (`crates/moqui-core/src/context/component.rs`, `add_component_dir`).

A component with purposes loads only when the instance purpose is one of them (`Discovery::allows`). A component found by scanning a directory must be allowed by the directory's purposes and, when its `component.xml` names any, by those too (`component.rs:310-321`); a `component` element of a `components.xml` that names no purpose takes its directory's (`:266-271`). A component left out is named in a WARN. An empty instance purpose matches no restricted component.

The instance purpose used for discovery is `instance@purpose` of the conf merged before the components are found, the default and runtime confs with the environment's names applied (`effective_instance_purpose`): `moqui_conf__instance__purpose` from `-D` or the process environment, then from `runtime/.env`, then the runtime conf's `instance` element. `runtime/components/base/framework/conf/MoquiDefaultConf.xml` sets `production`. `runtime/conf/MoquiDevConf.xml` sets `dev`. A component's own conf merges after discovery.

At request time the dev tools ask again: `moqui_core::devtools::is_dev_instance()` is true only when the setting `instance@purpose` equals `dev` (`crates/moqui-core/src/devtools/mod.rs:28`). It reads `conf_env::instance_purpose()`: a process property or environment variable `moqui_conf__instance__purpose`, else the running conf (`crates/moqui-core/src/context/conf_env.rs:236-251`).

| Component | Directory | `component.xml` | Loads when |
|---|---|---|---|
| `dev-aide` | `runtime/components/dev/dev-aide` | `purpose="dev"` | The instance purpose is `dev`. The purpose is on the component itself, so a copy in another scanned directory has it too. A conf's `component` element that names a `purpose` replaces the `component.xml`'s (`component.rs:441-444`), so a runtime conf can load it with `purpose="production"`; `tier::require` still refuses every call off a dev instance (`src/tier.rs:61-62`). |
| `example` | `runtime/components/dev/example` | no purpose; `disabled="${example_disabled ?: 'false'}"` | The dev set loads (purpose `dev`) and `example_disabled` is not `true`. |
| `template` | `runtime/components/dev/template` | `name="@component@"`, `disabled="true"` | Not as it stands: it is the skeleton a new component is copied from. |
| `demo` | `runtime/components/dev/demo` | no purpose; `disabled="${demo_disabled ?: 'true'}"`; `depends-on` `tools` | A conf names it. `runtime/conf/MoquiDemoConf.xml` has `<component name="demo" location="components/dev/demo"/>` in its `component-list` and keeps the production purpose. |

A conf's `component-list` may name a `component` or a `component-dir`; each goes through the same purpose check (`discover_for`). A conf that names a component with no purpose of its own loads it on any instance purpose.

`disabled` in a `component.xml` is read only by the directory scan (`component.rs:302`, `:345-351`); `component_from_dir` does not read it (`:406-459`). A conf's `component` element (`component_from_element`, `:384-393`) loads the component whatever its `disabled` says, which is how `MoquiDemoConf.xml` loads `demo`. Of purposes, the naming element's are used, else the `component.xml`'s (`:441-444`).

`./moq archive` leaves out `components/dev` unless `--with-dev`, and `components/test` and each component's `test/`, `plan/` and `plans/` unless `--with-tests` (`moq`, `task` archive, the `excludes` list). The default conf of an archive is `conf/MoquiProductionConf.xml`. The task's help states that `--binary` builds the same file set in (`--embed production`, or `--embed all` with either option) and that the archive includes `runtime/.env`, `runtime/db` and `runtime/cert` unless `--no-data`. `--with-dev` keeps the whole dev set: `dev-aide`, `example`, `template` and `demo`.

The extend tier runs code on the server. `try#Service` with `real` calls any defined service with caller parameters and writes a `DAA_TRY` audit row. `try#Snippet` runs caller JavaScript or XML Actions in the sim. `run#Spec` runs a spec. `start#LocalRun` writes the steps of one job of the working tree's `ci.xml` to a script under the runtime's `tmp` and types `sh <script>` into a host session of the Terminal (`src/local_run.rs`). `start#LocalRun` is refused under a fence and on a request logged in by a header (`src/local_run.rs:341-347`); the host session needs `TERMINAL_HOST` and the server's own origin, and from anywhere but this machine `terminal@remote`, https and a recent sign-in (`crates/moqui-host/src/term/access.rs:325-347`).

The sim (`moqui_llm::approval::preview::run_in_sim_within`) runs a body as the current user and returns its out-parameters, messages, errors, the rows it would write and its log (`in_sim`, `src/services.rs`). A sim run of the extend tier or above runs within the calling dev-aide service's frame, so it has what `DEV_AIDE_APP` passes on. A sim run of the view tier has no such frame (`sim_within`). The sim needs embedded Postgres; without it `try#Snippet` and `eval#Condition` are refused.

The sim is `fence::enter_sim` (`crates/moqui-llm/src/approval/preview.rs:191`). Entity writes go to the overlay. An async call, a remote call, printing, mail, SQL that may write, a resource write through the ResourceFacade, a notification and a program are refused where their code calls `check_effect` (`crates/moqui-entity/src/entity/fence.rs:15-30`, `:84-101`). File and resource reads, `ec.factory.getTool`, and Rust code that writes with `std::fs` or spawns a thread are not fenced. A sim run hides the after-values of rows the user cannot read (`preview.rs:199-235`).

`eval#Condition` (extend tier, as `try#Snippet`: SEC-DEV-02) takes `condition`, an expression or a condition element, and `against`, a JSON object. It builds XML Actions around the condition (`<if condition="...">` or `<if><condition>...`), checks them and runs them in the sim.

`try#Service` in the sim may run over text the caller gives (plans/design-dev-aide.md F14 for services): `files`, a list of `{rootId, path, text}` resolved and confined as a canvas buffer's are, and `preview`, the caller's own buffer (`buffer:<id>`) or change set (`approval:<id>`, `changeset::owned`). That text is code, so it needs the extend tier, as `try#Snippet` does, and a real run over it is refused (`src/services.rs` `try_service`). The text may not define a Rust service anew or point one at another function, which would run the server's code under a name and authorization of its choosing (`ServiceOverlay::build`). While an overlay is held, the screen definitions keep none of the forms, units and templates a render makes then and use none kept before, since they may be made from its service definitions (`screen::generate` `keeps`). The service files' definitions are made over the registry as a reload of them would make them, and held on the sim's thread only (`moqui_core::service::overlay`): the registry is not changed, and no other thread or request sees them; a script file's text stands at its location for the scripts read on that thread, not kept in the script cache. The agent's `try_service` takes the same as `changeSet` (a change set of the user's) or `files` (as `propose_edit` takes them), at the extend tier, in the sim only (`src/agent/try_service.rs`). With `trace` (the extend tier: a trace shows what a service builds inside, its finds with authorization off too), the run's XML actions run a script generated with trace calls (`moqui_core::script::trace`): each element's count, the names it set read after it (bounded to 200 characters, a map at 30 keys and a list at 10 items, a secret-named field and an entity value's encrypted field `(hidden)` as the logs and the sim's rows hide them, credential assignments redacted), and the element that failed. A value copied out of an entity value under a plain name (a `set` of `from="row.secretField"` into `copy`) is shown as the plain value it now is, decrypted; the extend tier can already read it so through `try#Snippet`. The agent's `try_service` runs a worktree session's proposal with its files at the main tree's places (`session_context`), and judges `sim_refusal` on the proposal's definition. `get#ServiceView` with `files` builds the same definitions at the view tier and runs none of them.

`save#RuleFixture` (extend tier) writes a context as `test/fixtures/<name>.json` (a name of letters, digits, `-` and `_`) of the rules file's component when the user may write there, else of the site's, through `save_text`; `list#RuleFixtures` reads each fixture through `Context::resolve`, so a link out of the root is not read. `try#Rule` (extend tier) runs a rule's trigger in the sim, traced, and writes nothing. `save#RuleSpec` (extend tier) runs a rule's trigger with the fixture in the sim as the user (a SECA's service call, an EECA's entity operation; a gitECA rule's condition only), writes nothing when it fails, and otherwise writes the fixture and appends a feature to `test/<RulesFile>.spec.js`, its names and texts written as JSON string literals and its rows' XML as JSON string literals, never a template, so a value of a record runs nothing in the spec; a name in the header comment has its control characters and line terminators replaced (`src/eca_specs.rs`, `services::check_data`, `comment_text`). The spec runs only through `run#Spec`, in the sim, or `moqui test`.

`export#Records` (view tier) takes an entity name and an optional `filter` map of equalities, counts the matches, refuses a count over `MAX_EXPORT` (1000, `src/entities.rs:59`), and returns the records as entity XML text (`EntityDataWriter`). The service does not turn authorization off. It refuses a restricted entity for everyone, and below the full tier with `ADMIN` a `moqui.security` entity, `DevAideCredential`, `DevAideServer`, `DevAideTaskSource` and any entity with an encrypted field (`entities.rs` `export_refused`); its writer is never full, so the text holds no password or encrypted field (plans/Security-Review.md SEC-DEV-01, fixed). `try#Snippet` at the extend tier reads the same rows by design.

`plan#DataLoad` (view tier) and `load#ChangedRecords` (extend tier, `may_write` on the data file) compare each record of a data file the user may open (the plan: the buffer's `text`, or the file; the load: the file as saved) by entity and primary key with the base and the database (`src/data_load.rs`). The base is the `moqui.dev.DevDataLoadBaseline` row of the root and file (the text the last load committed, one row per root and file, read and written with authorization off), else `git show HEAD:<path>`. The plan reads the database row of every record the file or the base names, of any entity, with authorization on. A password or encrypted field (`GenericAccess::hidden`) is left out of the records and the rows before they are compared, so it is neither compared nor answered and no applied status confirms a guess of it; a record of an entity `export_refused` refuses the caller (restricted, `moqui.security`, the dev-aide credential entities, an encrypted field, below the full tier with `ADMIN`) is never compared with the database: it only `differs` from its base, with no fields. The load needs the plan's `baseHash` and `fileHash`, checked again inside its `ForceNew` transaction, re-plans there, refuses a conflict that `choices` does not name, writes each planned record through the entity-auto `store#<entity>` (Java's `storeEntity`, its status checks included) as the user, so the SECA rules of `store#<entity>` run, which they do not for Load this file, and deletes a record removed from the file only by the user's choice, the base's last record first. As Load this file, a data file of the extend tier may hold any record. A change only to a hidden field is not picked up, and a record that is written writes the file's values of its hidden fields too; the plan's `note` says so. The baseline moves after the commit, in a transaction of its own, unless an element (of the file or of the last load's text) or a record was passed over, or a removal or a differing record had no choice, so they are offered again; the answer says when it did not. A `DAA_LOAD` audit row records the counts, or the error.

`check#DataFile` (view tier) is a restricted check (`restrictSensitiveEntities`): an entity no generic read takes is refused and a password or encrypted field is not compared; a top-level element with a record of an entity `export_refused` refuses the caller is not checked at all (taken out of the text before the check, so no message, row or count of fields compared depends on its rows) and one line, `Entity X: not checked for you`, names it (`src/entities.rs`, SEC-DEV-01).

### File paths

A file path of a request is relative to a root and goes through `confine::resolve` (`src/confine.rs`). It refuses a NUL byte, a leading `/` or `\`, a drive letter, and any `..` part. It canonicalizes the deepest part that exists, so a symlink is followed, and refuses a result outside the root. It refuses a path with a `.git` part, a path in the root's build output (its first part under the root is `target`), and a path inside the runtime's `db`, `log`, `txlog`, `tmp`, `.env`, `cert`, `save`, `sftp`, `install` or `opensearch`, or a name at the top of the runtime that starts with `.env` (a copy of it). It refuses a path inside `runtime/worktrees` unless the root itself is there. Below the full tier a path inside `runtime/conf` is refused too (`Context::resolve`, `confine::hidden_below_full`), and `search#Files` leaves out the `git grep` lines of what an open would refuse (SEC-DEV-04).

The loaded runtime and the loaded components are never build output, though a root's `target` may hold them (a disposable runtime under the repository's `target`, whose components have no repository of their own and so take the enclosing one as their root): a path inside one of them is measured from the deepest such directory that holds it, so its own `target` is still refused, and so is the root's other build output. The path is canonical first, so a symlink from them into build output is refused, and a base that is not a plain prefix of the path counts as build output, so the check fails closed (`confine::build_output`).

The deny list (`DENIED_RUNTIME`) has those ten runtime names. `runtime/conf` is not on it; it is refused below the full tier on every resolve (`src/workspace.rs:108-117`).

`get#File` treats a file with a NUL in its first 8 KB as binary and applies `max-edit-bytes` (2097152 in the component's conf). `save#File` refuses content over `max-edit-bytes`. `get#FileAt` (view tier) resolves the path the same way and runs `git show <rev>:<path>` after `valid_rev`.

A write needs the extend tier, a root that Settings has not made read only, and passes `may_write` (`src/workspace.rs:131`). The upstream lock is lifted only for the full tier, by the user preference or the conf's `allow-upstream-edits` (false in the component's conf). A write renames a temporary file over the target, so a dangling symlink at the leaf is replaced, not followed (`src/workspace.rs:534-554`).

`rename#Path` and `delete#Path` (extend tier) are confined at both ends and pass `may_write`; `delete#Path` acts on the canonical path, so a link inside the site is followed to its target, which `may_write` checks (`src/workspace.rs:796-898`). `create#SiteComponent` and `create#Component` (full tier) write only `runtime/components/<set>/<name>`, with a `name` of letters, digits, `-` and `_` (`src/workspace.rs:1319-1478`). `clone#Repository` (full tier, network allowed) clones into the set directory, with a `name` that does not start with a dot and has only letters, digits, `-`, `_` and `.` (`src/repo.rs:937-1003`).

`search#Files` of a text is `git grep --untracked` (tracked files and untracked ones not ignored) and leaves out the lines of files an open would refuse; a regular expression, and any search of a root that is no git repository, is Rust's regex over the root's files (`git ls-files` or a walk) with the same confinement, each file at most `max-edit-bytes`, as `replace#Files` reads them (a query at most 4 KiB, a replacement 64 KiB) (`src/workspace.rs:984-1037`). `find#Files` lists the names of `git ls-files --cached --others --exclude-standard`, not filtered by the deny list, or walks a plain root skipping dot names, `target`, `node_modules`, symlinks and refused directories (`src/workspace.rs:900-950`). `list#Directory` hides only `.git` and shows other names (such as `.env`) without their content (`src/workspace.rs:391-405`).

### Roots

The roots are the git repositories that hold the loaded components (found by looking up from each component directory for `.git`), each loaded component in no repository, `runtime/conf` when no repository holds it, and the rows of `moqui.dev.DevAideRoot` (`src/roots.rs`). `store#Root` (full tier) takes `location`, canonicalizes it, needs a directory, and refuses a location inside one of the denied runtime names, or in the build output of a root that holds it unless it is the loaded runtime or a loaded component (`confine::in_build_output`), at every tier. A location outside the runtime and the current roots (`/`, a home directory) needs `ADMIN` (`confine::root_location_open`, SEC-DEV-04); an admin can make any other directory the server's OS user can read a root.

A hosted root (`rootKind` `hosted`, `src/hosted.rs`) is a `GitRepository` of this server's hosting at a branch, with no directory: its `location` is a name, `git://<repositoryId>/<branch>` (a repository id has no `/`, so no two pairs share one), its id `hosted-<rootId>` of its row, and `Context::resolve` refuses every path of it, so no file service, git command or agent tool reaches the file system through it (the `vcs` services are refused; `git_root` refuses a root that is not git; `replace#Files` refuses a hosted root). `store#HostedRoot` (extend tier) asks `get#GitRepositoryAccess` as the user and refuses a repository the user may not update or that is archived, and a branch the repository does not have; the root row is then written with authorization off; for an empty repository the branch must be its default branch, which the first commit makes. `Context::of` drops the hosted roots whose repository the user may not view (one `get#GitRepositoryAccess` each), so `get#Roots`, `get#Overview`, `list#Repositories`, `get#HostedRoot` and every lookup by id answer for them as for no root (`no root <id>`). On a hosted root `list#Directory`, `get#File`, `find#Files` and `search#Files` call `get#GitTree` and `get#GitBlob` as the user with authorization on, so `AT_GIT_REPOSITORY` view decides what each user reads (a `git://` location is not checked against it, which is why they are not used); paths with a `.`, `..` or `.git` part are refused (`clean_path`), and Go to file and search stop at 2,000 directories, 20,000 files, 5,000 files searched and Replace across files' budgets (`MAX_SCAN_TIME`, `MAX_READ_BYTES`). `save#File`, `create#File`, `create#Directory` (an empty `.gitkeep`), `rename#Path` and `delete#Path` (a folder's files and links, read whole at one commit or refused: a listing that fails, the time budget, a submodule in it, more than 2,000 paths) are each one `commit#GitFiles` as the user to the root's branch, a Save with `expectedBlobIds` the blob the file was opened at: the update right, the archive and the branch rules (a protected branch's `GitProtectedBranch`) are the hosting's, as for a push, a moved blob answers a conflict, an empty repository's first commit names no branch or blob, the write is refused under a fence (`unfenced`), and an audit row names the commit. Nothing of a hosted root is loaded, reloaded or run; `check#File` and a save's checks parse the text only.

### Git

Git runs as a child process with an argument vector, never through a shell (`src/git.rs`). The command is the conf's `git-command`. Each call adds `-c core.quotepath=off -c color.ui=false` and sets `LC_ALL=C`, `GIT_TERMINAL_PROMPT=0`, `GIT_LITERAL_PATHSPECS=1`, and empty `GIT_ASKPASS` and `SSH_ASKPASS`. The module comment states that git uses the trees' own config, hooks, signing and credentials. Paths follow `--`. A remote URL is refused when it is empty, starts with `-` or has a control character (`valid_url`, `src/repo.rs:871`). Git names refuse a leading `-` and `..`, and names and URLs follow `--` (`src/vcs.rs:1084-1099`; `src/repo.rs:871-877`, `:885`, `:899`, `:975`); a stash message is its own argument after `-m` (`src/repo.rs:564`). Network commands are refused when the `shared` setting is on and `network_git` is off (`network_allowed`).

A stored token reaches git through environment variables (`MOQUI_DEV_AIDE_GIT_TOKEN` and three numbered ones, with matching `..._USERNAME` names) and a `-c credential.<prefix>.helper=!f() {...}` argument that echoes them, after `-c credential.helper=` (`token_helper`, `src/vcs.rs`). The token is not in the argument vector.

### Settings, credentials and the group server

`moqui.dev.DevAideCredential.token`, `moqui.dev.DevAideTaskSource.token`, and `moqui.dev.DevAideServer` `gatewayKey`, `pendingVerifier` and `envPriorJson` are `encrypt="true"` (`entity/DevAideEntities.xml`).

`store#Credential` needs the full tier and `ADMIN`, turns authorization off, and stores a token for a root, optionally for one user, with the scheme, host and port of an HTTPS remote. It logs the root, the user and who stored it, not the token. `get#Credentials` returns the rows without the token.

The group server connection (`src/hosting/connect.rs`) is refused on a request logged in by a header. `start#Connect` takes `baseUrl`, stores a random 32-character `pendingState` and a 64-character PKCE verifier on the user's `DevAideServer` row, and redirects the browser to the server's authorize URL with this instance's own `/qapps/dev/Settings/serverSignedIn` as the redirect. `finish#Connect` finds the row by `pendingState`, requires its `userId` to be the current user, clears the pending fields, refuses after `PENDING_MILLIS` (15 minutes, `src/hosting/connect.rs:49`), and posts `code`, the verifier and the redirect to the server's token path (default `/sso/appToken`). The answer's `loginKey` is stored as the user's token.

The `serverSignedIn` transition has `require-session-token="false"`.

`apply#ServerSetup` writes instance files only for the full tier with `shared` off. It writes three names to `runtime/.env`: `llm-facade/endpoint[default]@url` (the server's offered gateway URL, checked by `on_server`), `llm-facade/endpoint[default]@api-key` (a key the server issues for scope `gateway`), and `llm-facade/model[default]@name` (the request's `gatewayAlias`, default `default`). The earlier values of those three lines are kept in `envPriorJson`. `moqui_lib::env::update_dotenv_file` refuses a name with `=` or a line break and a value with a line break, and writes the file with mode 0600 on Unix.

The group server client (`src/hosting/client.rs`) takes a base that is https, or http to a loopback IP literal, with no user, query or fragment (`:38-55`). A `restBase` or REST path the server offers is joined to the server's own origin, and a URL not on it is refused (`:168-182`), so the token goes only to that origin. A write is refused under a fence (`:276-279`; `src/vcs.rs:260-305`). A read under the agent's read fence passes only with a permit for that origin (`check_remote`, then `fence::lift` for that GET, `:282-286`).

`store#TaskSource` (view tier) takes a `baseUrl` that starts with `https://` or `http://`, to any host, and a `token` (`src/tasks.rs:444-487`). For a source Connect made, a new address clears the token; for a source with a typed token, an empty `token` keeps the stored one. `get#Tasks` sends the token as the `api_key` header to the source's `baseUrl` (`src/tasks.rs:180-205`); a view-tier user's reads refuse internal addresses (`deny_internal`, `:205`).

### Co-editing a file

On a shared dev server a file's tab joins the file's room on the notification socket, `DevFile:<rootId>:<path>` (moqui-collab's text rooms, `crates/moqui-collab/src/text.rs`, on the frames of [Co-editing](Attack-Surface-Tools.md#co-editing)). A join asks `get#CoeditAccess` (`src/coedit.rs`) as the socket's user (`moqui_core::user::as_user`); the service answers for the current user only, or for a caller with no user, never for another. It allows a join only in shared mode, at the extend tier or above, only for a file the user may write as Save would (`Context::may_write`: the upstream lock, a read-only root), resolved and confined as a read is and named as the root names it (one room per file), not of a hosted root, not binary and not over `max-edit-bytes`; a refused join is no member. The room is seeded from the file's text (LF) when new and kept in memory only, dropped with its last member. An update is at most `max-edit-bytes`, the document's state at most four times that, and a user co-edits at most `dev-aide@coedit-max-rooms` (20) files at once (429). Each member's answer is asked again every minute; one who may no longer write the file is dropped (`Revoked`), and one whose answer could not be renewed for three minutes has their updates refused. Nothing is written to disk from a room: Save is the user's `save#File`, by the hash of the file they read, refused on a conflict as without co-editing.

### Agent tools

The dev agent's tools are `artifact`, `source`, `check`, `propose_edit`, `try_service`, `vcs` and `hosting` (`src/agent/`). Their shared helper `context(least)` builds the same `Context` with a tier, so the dev instance check and the user's tier apply to a tool call that uses it (`src/agent/mod.rs`). In an agent session with worktrees, the session's worktree roots stand in for the main roots. A file name given to a tool, `component://` and absolute names included, goes through `roots::locate` and then `Context::resolve`, so a `..` inside a location is refused (`src/agent/mod.rs:126-157`; `src/roots.rs:310-321`).

A run gets the dev tools (the `dev` capability) when its user is a dev-aide user on a dev instance (`moqui_core::devtools::dev_aide_user`: one of the three dev-aide permissions) and its agent's tool policy pins one of `artifact`, `source`, `check` or `propose_edit` (`crates/moqui-llm/src/run/mod.rs:579-587`). The read tools `artifact`, `source` and `check` are also listed over MCP (`spec.mcp = true`, `src/agent/source.rs:53`, `artifact.rs:89`, `check.rs:54`), and the MCP surface gives the dev capability to any dev-aide user on a dev instance (`crates/moqui-llm/src/mcp/tools.rs:116-117`). `tier::require` refuses a header login only from the extend tier up (`src/tier.rs:65`), so an API key of a holder of any dev-aide permission reads workspace files with `POST /mcp` `tools/call source`.

Reads ask no approval: `artifact`, `source`, `check`, the `vcs` and `hosting` reads, and `try_service` in the sim (`Classification::Read`, `src/agent/try_service.rs:55`). Writes ask an approval: `propose_edit` a file approval, `try_service` with `real=true`, `vcs` commit and push, and `hosting` open, comment and reply. A background Job agent in Policy mode has its writes approved by the policy (`crates/moqui-llm/src/approval/mod.rs:489`, `:609-618`). `propose_edit` asks the extend tier again at accept, binds the approved arguments, and refuses a whole-text change over a moved file (`src/agent/propose.rs:365-391`). An approved `try_service` real run calls the service with the fence lifted and the bound arguments, without asking the tier again (`try_service.rs:76-88`, `:218-234`). The `vcs` and `hosting` writes go through VcsServices and HostingServices, which ask their tier themselves (for example `src/repo.rs:312`).

`try_service` without `real` refuses only the Terminal's services and dev-aide's own services that are not read-only (`sim_refusal`, `try_service.rs:95-120`), then runs the service in the sim as the user (`:141-198`). What the sim fences is above; a Rust service that acts on the host without asking the fence, such as `restart#Server`, runs from it.

`artifact` and `check` take a `project` argument, as the REST reads do (see [the artifact index over REST](#the-artifact-index-over-rest)), at the view tier (`artifact.rs:124-129`, `check.rs:74-75`). `check` with a `project` reads a file of that project's components and answers its problems (`check.rs:102-123`).

The `hosting` tool's reads run under the agent's read fence with a permit for the connected server's origin (`src/agent/hosting.rs:266`, `fence::enter_remote`), which the client checks before it lifts the fence for that GET. A successful answer reaches the model wrapped as untrusted (`hosting.rs:219`); a failure's text is the tool error's `instruction` (`hosting.rs:189`; `crates/moqui-llm/src/tools/format.rs:130`).

## Test client

`moqui test-client` (`crates/moqui-host/src/test_client/`) runs a component's client specs on the developer's machine with the developer's trust. A spec reaches HTTP and sockets to any URL (`allow` checks nothing outside a load run in a server, `test_client/mod.rs:1052-1057`), the browser to any page (a spec's `page.evaluate` can navigate it to `file://`; `goto` joins a path to the server, `test_client/http.rs:110-118`), and the component's own files through `files.*`. `--server` refuses plain http to another machine without `--allow-http` (`http.rs:72-84`). A session's own headers and its session token go with every request of the session, a full URL to another host and a followed redirect to another host included (`http.rs:593-615`). The cookie jar matches domain, path, expiry and `Secure` (`http.rs:231-287`, `:308-317`). `response.save` and screenshots take a plain file name only (`test_client/mod.rs:1412`, `browser.rs:747-758`). The SSH client takes any host key only on loopback or with `--insecure`, else needs a pinned fingerprint (`test_client/ssh.rs:331-336`).

An offline client spec's pages are served as `https://moqui.test/files/<repo-relative>` from the whole repository root, `runtime/.env` and `runtime/conf` included (`test_client/offline.rs:51-56`, `:150-151`). The offline origin refuses `..`, `.`, empty segments, `\` and NUL, and checks the canonical path is under its root (`offline.rs:106-111`, `:131-141`, `:160-176`). Every other request of such a page goes to the network (`test_client/cdp.rs:497-504`, `Fetch.continueRequest`).

The test browser (`test_client/cdp.rs:165-213`) gets `launch_args()` with the sandbox on, a DevTools port on `127.0.0.1` that any local process may open (`crates/moqui-host/src/chromium.rs:337`; the PDF engine's pipe of SEC-SCR-10's fix is not used here), a fake camera and microphone and autoplay, `--ignore-certificate-errors` with `--insecure` (`browser.rs:774-784`), its own process group (`cdp.rs:1233-1245`), and the developer's whole environment (no `limit_child_env`, `cdp.rs:185-191`). It gets no proxy (`cdp.rs:175-184`). Its profile is a new directory in the system temp directory, made by `moqui_lib::private_fs::new_dir_in` (mode 0700, a random name, never one already there; `cdp.rs` `start`), so the `DevToolsActivePort` that `devtools_url` reads there before it asks whether the browser has started (`chromium.rs`) is the browser's own. The browser is driven over that port, not a pipe. `ffmpeg` runs from the `PATH` with fixed arguments (`test_client/video.rs:379-386`).

`test-client --serve` starts `moqui test <components> --spec ... --db snapshot --serve 127.0.0.1:0 --ready-file <dir>/<n>.url`, the directory new and made as the profile's and removed when the server ends (`serve.rs` `start`), with `MOQUI_CONF` and the suite's declared properties in its environment (`test_client/serve.rs:177-192`, `:229-243`), and takes the first line of the ready file as the server's URL, plain http allowed (`serve.rs:216-217`, `:263-267`). Neither the profile nor the ready file can be one another local user made in a shared `/tmp`.

## Load runner targets

A load run needs the `LOAD_RUNNER` permission (`crates/moqui-host/src/load_runner/mod.rs:77`) and takes `targetUrl`. `TargetPolicy::of_factory` (`load_runner/targets.rs`) allows this server's own origins, loopback, and the URL prefixes and `ssh://host:port` entries of `load-runner@targets` (empty by default). On a dev instance `any` is true and a run reaches any URL and any SSH host. `DEFAULT_MAX_RUNS` is 1 and `DEFAULT_MAX_USERS` is 1000 when `load-runner@max-runs` and `load-runner@max-users` are not set.

`TargetPolicy::allow` parses a URL as reqwest does and refuses userinfo, plain http to another machine and anything off the list; loopback is the literal only (`load_runner/targets.rs:101-124`, `:199-221`). A load run's HTTP needs the plan's `uses: ["http"]` and `may_act()`, and `thread.begin` needs the run's own load and one-time token (`load_runner/run.rs:247-255`, `:292-302`). `LoadScript::read` takes only a `.load.js` file inside the component (`test_client/load/script.rs:268-291`).

A load script run in a server is the test client's script with only `__moquiTestHost.call` and the pure helpers, set at the prelude's first call, before any script line (`test_client/mod.rs:799-808`, `:1561-1568`; `crates/moqui-core/src/script/runtime.rs:493-500`). Of the host calls it keeps `files.read` and `files.list` of the script's own component (`test_client/mod.rs:1692-1698`; no `..`, no absolute path, a canonical prefix, and a walk that does not follow a symbolic link, `:1427-1466`), `ssh.*` to `TargetPolicy::allow_ssh` hosts (`:1390-1406`), and `service.call` in process (`:1577-1580`). It refuses `browser.`, `page.`, `locator.`, `load.run`, `parallel` and `response.save` (`:811`, `:1548-1550`), and its `out_dir` is never written (`:1027`). Every request and each redirect is checked before it is sent (`test_client/http.rs:555`); a raw request and a socket check both the server and the target path (`test_client/mod.rs:1143-1144`, `:1362-1363`). A `LOAD_RUNNER` holder reaches all of this by choosing a script.
