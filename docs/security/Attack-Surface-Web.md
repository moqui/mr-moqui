# Attack surface: web authentication and controls

How a web request is authenticated and authorized, the controls every request passes (session cookie, CSRF, lockout, tarpit, headers, CORS, client address, web protection), and the HTTP and HTTPS listeners with ACME. The routes themselves are in [Attack-Surface-Routes.md](Attack-Surface-Routes.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## HTTP authentication and authorization

A servlet request is signed in from the session cookie, HTTP Basic, an `api_key` or `login_key` header, or `authUsername` and `authPassword` (`docs/interfaces/Web-Scripts.md`). A key header is checked on every request, ahead of the cookie and Basic. A key for a user other than the session's, or a rejected key while a session is signed in, is a 401. A rejected key with nobody signed in leaves the request anonymous with the login error. `/notws` accepts the session cookie and, failing that, a `login_key` header. `/termws` accepts the session cookie only. `/agentws` accepts the session cookie and, failing that, a full-account `login_key` header. Notification sockets revalidate the original session or hashed login key every 60 seconds and close on logout, a changed user, key revocation or expiry, or a failed credential lookup. Revalidation does not log in again or write login history. Protocol Ping/Pong traffic cannot extend authentication.

`authenticate` (`crates/moqui-core/src/screen/mod.rs`) runs on every request the screen servlet chain serves, on any path, after the session is bound. `Authorization: Basic` is checked with the account password even when the session is signed in; a different user replaces the session's. `authUsername` and `authPassword` are read from the request parameters, the query string included, and only when nobody is signed in. Each failed check counts as a failed login of the account and as an `auth-failure` event of the client. A password login that needs a second factor returns with nobody signed in. A request that signed in from its own credentials skips the session token check ([CSRF](#csrf)), and its session is marked `moquiHeaderLogin`. A shared device's request reads none of these credentials. A login key or app password sign-in does not ask for the second factor.

Screens carry `require-authentication`. The parser maps `false`, `anonymous-view`, and `anonymous-all` to those modes, and it maps a missing attribute to required. A render requires a user when any screen in the chain is required. An anonymous login counts as a user.

Artifact authorization runs on a stack: each screen, transition, service, REST path, entity, git repository, and LLM call is pushed. A record is required of the last screen of a path when it requires authentication, of a transition when its screen requires authentication, of the last node of a REST path when its `require-authentication` is empty or `true`, of a service by its `authenticate`, and of an entity unless its `authorize-skip` covers the operation. Inheritable allow and always records cover children on that stack unless a more specific deny wins.

### Services and `allow-remote`

Nothing reads a service's `allow-remote` attribute; `runtime/components/base/framework/xsd/mr-service-definition.xsd` says it is kept for compatibility. There is no general remote service interface (no JSON-RPC or XML-RPC). A service is reached from outside only through a screen transition, a REST resource (`*.rest.xml`), a web script, a token route, the PASS authority's route table, or an agent tool exposure (`AgentToolExposure`). Each of these has its own authentication and authorization. A service's `authenticate` attribute (`anonymous-all`, `anonymous-view`, `false`) decides whether it runs with no user once one of them calls it.

### Parent frames

A render checks only the last screen of its path; the screens above it are entered without their own check (Java's `pushInternal` with authorization required of the target alone), so their always- and pre-actions run for a user who may open the target. The qvt shell loads each level of a page as its own request, and the terminal client each level between the app root and the leaf (`Party.tui`), which checks that level as a target. A level the user may not open alone answers, only when the request names in `X-Moqui-Page-Path` a page strictly below it on the same screens that the user may open (the page's screen permitted with its parents on the stack, its subscreens items' user groups, and a shared device's route group), as the page's frame (`screen/frame.rs`): a GET in qvt or tui, written from the level's widgets as its subscreens placeholders alone (up to the first active level), `private, no-store`. Nothing of the level runs: no always-, pre- or widget actions, no section, no form, no label, no transition; its shell providers are not gathered for it (the shell gathers them only from roots the user may open). Its tabs list only the subscreens the user may open: in qvt the shell's menu data fills them, in tui the frame carries them, as the menu data makes each entry of that level for the page (each subscreen authorized below the level, its `menu-include` and `disable-when` evaluated, its title expanded; nothing of the level itself runs, where the menu data also runs the levels' pre-actions). What the frame tells the user is that the level exists, its title (tui) and that it has a subscreens placeholder or a tab bar, which the page's own menu data and breadcrumb titles already showed them. The level asked for without the header, in another mode (an html page), as a transition, for a page the user may not open, that does not resolve, or is not below it, or a level with a screen on its path that grants anonymous access (whose own render may apply that grant where the check does not), is refused or rendered as before; the launcher lists only roots the user may open. Checking the page is one path resolution and one permission check of its screens, as its own request would be.

## Cross-cutting controls

These apply unless a row says otherwise.

### Session cookie

The session row is `moqui.server.HttpSession`. The cookie is `moqui.session={id}.{mac}`, then `HttpOnly`, `SameSite=Lax`, and `Path=/`. Over https it is `__Host-moqui.session` with `Secure` and no `Domain` (SEC-WEB-05), which a browser keeps only so, so no other host of the domain and no plain-http page can plant or shadow it; an https request reads only that name, and a plain `moqui.session` it brings is no session. Https is the TLS listener, or `X-Forwarded-Proto: https` from a peer `ClientAddressing` believes. A client that is not that peer cannot turn the flag on by sending the header. The visitor cookie is `moqui.visitor`, with `Max-Age` of one year. The session cookie itself has no `Max-Age`.

The MAC is HMAC-SHA256 of the session id under `webapp-list/webapp[webroot]/session-config@cookie-key`, base64 URL-safe without padding. A bad MAC is treated as no session. The session id and the session token are 20 random bytes, hex, 40 characters. `session-config` is `timeout="60"` (minutes), `flush="eventual"`, `max="10000"`.

`webapp-list/webapp[webroot]/session-config@cookie-key` ships as `CHANGEME` with `is-secret="true"`. Left so by the conf files and the environment, it is made at its first read and kept as a `SecretValue` row, which every member of a cluster reads ([Secrets](Attack-Surface-Data.md#secrets)). A value an operator sets is checked at startup and at a conf reload that sets it (`check_session_cookie_key`, `context/factory.rs`): one that still ends in `CHANGEME`, is not standard base64 or decodes to under 32 bytes stops the server, with a message that names the property and not its value (SEC-WEB-13). Forming a cluster refuses a value that ends in `CHANGEME` (`cluster/mod.rs`) too. See [Secrets](Attack-Surface-Data.md#secrets).

A password login that succeeds, or that passes the password and waits for a second factor, moves the session to a new id and a new session token (`rotate_on_password_login`); the old id is retired and its row deleted. The new session is a copy of the old one with its attributes. A password login for the user the session already holds keeps the id. Every other sign-in moves a session the client brought to a new id when it held another user or none (`internal_login`, SEC-WEB-05): `internalLoginUser` (the code that finishes a second factor, `Login/changePassword` after a password change, `/rest/verifyOtp`), a login key or `api_key` header, an app password and an SSO login; a session the server made for the request keeps its id. A password login that ends in "requires a password change" or "password must be changed" returns before the id changes; the change form's sign-in then moves it. Logout (`ec.user.logoutUser()`) sets `UserAccount.hasLoggedOut` to `Y`, retires the session id and deletes its row with every attribute in it, and goes on with a new empty session of no user and no visit (`session::renew_after_logout`, SEC-WEB-06). At each request's bind the account is read: `hasLoggedOut = Y`, `disabled = Y` with no `disabledDateTime`, or a past `terminateDate` ends the login. Only an interactive sign-in (a password, a second factor's code, SSO, an SSH key) sets `hasLoggedOut` back to `N`, so a session elsewhere that made no request in between stays signed in after it; a login key, an `api_key` header or an app password signs its request in and leaves the flag set (SEC-WEB-06), so such a request after a logout elsewhere does not undo it. The account's own `revoke#OwnAccess` ends every session with its keys and app passwords ([Admin](Attack-Surface-Admin.md)). A password change (`update#PasswordInternal`) ends the account's other sessions on every server (the one that changed it stays); it ends no login key or app password. A session expires only by idleness (`session-config` `timeout`); there is no absolute lifetime.

A request with no valid session cookie gets a new session in memory (`resolve_id`). Over `session-config` `max` live sessions, the request that crossed it drops the ones used longest ago, down to nine tenths of the cap, after writing those with changes. The `HttpSession` row holds the session token and the session attributes as JSON text. After an SSO sign-in the attributes hold the raw ID token (`moquiAuthFlowIdToken`), the flow id and `moquiAuthFlowReturnTo`, which is written back and not cleared after use (`service/sso.rs`); the ID token goes to the provider's end-session URL in the query (`moqui-host/src/sso.rs`). The session id is also stored in `moqui.server.Visit.sessionId` and in the request span attribute `session.id`. The first pair of the cookie's name in the `Cookie` header is the one read.

#### Pages without a session

A request that comes with no session cookie starts no Visit until the cookie comes back or a user signs in. Two kinds of page send no session at all, so no cookie comes back:

- A page a shared cache may keep (`Cache-Control` with `public`), for a request with no live session (no verified session cookie, or one naming a session that is gone) and nobody signed in: no `Set-Cookie`, `moquiSessionToken` or `X-CSRF-Token`, and the session made for the request is discarded unwritten, so a cache never keeps a new session's cookie to hand to others.
- A page whose screen or servlet calls `ec.web.declineSession()`, whatever its caching (a preview frame on its own host, an embed, a beacon). For a request with no session of its own and nobody signed in it is the same as the public page. A request that has a session keeps it and is sent nothing new: no cookie and no token. Either way a Visit the request started at the bind (a returning `moqui.visitor` or a session cookie with no visit yet) is deleted, with a Visitor made for it, and the session forgets it, so no Visit has a declined request as its `initialRequest`. A Visit a sign-in in the request started stays. A page that signs a user in should not decline.

```js
ec.web.declineSession()   // e.g. mr-pass Shop/ShopPreview.js, before it writes the preview
```

A public island's component is the first kind too (impl-shop F72): the `.qvue` or `.qjs` answer of a screen that says `server-static` for that mode itself (not a placeholder screen's automatic one) or declines its session is sent with the `screen-server-static` `Cache-Control` (public by default), so it makes no session, but only for a request that brought no session of its own and has nobody signed in (`render.rs` `is_public_island`). A signed-in user, a request with a session, and any other screen's component get `private, no-store`, and keep their session. A `Cache-Control` the screen set itself stands. A screen that says `server-static` for qvue or qjs must send the same component to everyone; data for one visitor comes by a later request (a transition), which keeps its session.

A `.qvue` asked for as `<path>.qvue?_qvt=bundle` (a screen's `template="false"` qvue or a `.qvue` file under a screen) is answered compiled on the server by the vendored Vue compiler (`screen/qvue_bundle.rs`, `vue_check::qvue_make`, `served_qvue`), with the screen's render and authorization as for the plain `.qvue` and its `Cache-Control`: the file's script runs once in a standalone runtime with no `ec`, under the compiler's deadline and memory cap, and the answer is `text/javascript` with `X-Moqui-Qvt: bundled-qvue`, kept by the text's hash (a failure kept as a 500; a templated qvue has none, 404). The script registers the component under the path the client asked for (the loading element's `data-moqui-bundle`, else its own URL path), so it depends on the text alone. A page on the runtime build of Vue whose `qvt.handles` lists `bundled-qvue` (PASS's islands) loads each `.qvue` this way and never compiles a template or evaluates a component in the browser.

### The system scope

`ec.artifactExecution.runAsSystem(body)` runs `body` with no user and authorization off, in a fresh execution context that shares the caller's transaction, effective time and agent origin (`user/system.rs` `as_system`; Commerce F72). It is for a service that has already checked its caller and must write what that caller has no right to write directly, such as Mantle's site page saves into a page space with `restrictUpdate` (a rule like `get#WikiPageAccess`'s `!userId && authzOff` then admits it). The caller's user, authorization and artifact stack come back when `body` returns, throws or panics; the messages and errors `body` added are moved to the caller's context. Records written inside have no `changedByUserId` or `lastUpdatedByUserId` of a user. A wiki save can still say whom it was for: `update#WikiPage` reads `historyUserId` only with no user and authorization off, for its `WikiPageHistory` row and a new page's creator (Mantle's site page saves pass the acting user), and `get#WikiPageHistory` names that user for a version that has none of its own.

Only a service's own code may call it: the top artifact frame must be a service's (`AT_SERVICE`), pushed after any screen render in progress on the thread began (`ExecutionContext::in_service_body`). Anything else is refused with an error: a screen's actions, widget expressions and transitions, a screen a service renders (the render began after its frame), a REST resource, a web script, a webapp action and a script with no frame. A remote or REST caller has no way to name it; it reaches the scope only through a service whose own code calls it, so the service decides what runs. Rust code calls `crate::user::as_system` directly. There is no XML action for it.

### CSRF

`webapp-list/webapp[webroot]@require-session-token` is `true`. `POST`, `PUT`, `PATCH`, and `DELETE` on a transition that runs actions must send `moquiSessionToken`, or a header `moquisessiontoken`, `sessiontoken`, or `x-csrf-token`. The compare is constant time. A missing or wrong token is 401 `Session token is missing or is not valid`. A transition may set `require-session-token="false"`, which turns the check off for it; `Login/login` and `rest/login` do. `require-session-token="true"` keeps the check when the webapp setting is `false`. Header authentication skips the check: a request that signed in from its own `api_key` or `login_key` header, Basic credentials, or `authUsername` and `authPassword`. A new session skips it too: a request with no valid `moqui.session` cookie, or with one that names a session that is gone, has no token to send. Responses set `moquiSessionToken` and `X-CSRF-Token` when the cookie is new or the token changed.

The rule is `csrf_rejected`, `insecure_transition` and `runs_actions` in `crates/moqui-core/src/screen/render.rs`:

- A transition runs actions when it has a `service-call` or an `actions` element, or is the implicit `formSaveFind` or `formSelectColumns`. A transition with no actions is `read-only`.
- A `GET` or `HEAD` is never checked for the token. A transition with no `method` attribute takes every method (`screen/definition.rs`); about three quarters of the `<transition>` elements in `runtime/components/base` and `runtime/components/dev` have none. The implicit `formSaveFind` and `formSelectColumns` take only `POST`.
- A transition that runs actions and is not `read-only` is refused with 400 when the request has a query parameter other than `lastStandalone` and `renderMode`, or an inline `~name=value` path segment. A `path-parameter` extra path is not counted. The path walk stops at a transition's name and keeps the names after it as an extra path, which is ignored unless a `path-parameter` binds it (`screen/url.rs`, `render.rs`), so `/Login/login/x`, `/r/<token>/submit/x` and `/call/<token>/joinGuest/x` are the same transitions as without `/x`; a transition's name with a render-mode extension is the transition too. A transition also runs through the FOP servlet at `/fop/<its path>`, with the same checks ([Routes](Attack-Surface-Routes.md)). It is also refused with 400 over plain http when `webapp-list/webapp[webroot]@https-enabled` is `true`.
- A `GET` (or `HEAD`) with no query string of such a transition is refused with 403 when another site started it and it carries no session token (`cross_site_write`, plans/Security-Review.md SEC-WEB-04 and SEC-TLS-04, fixed): its `Sec-Fetch-Site` is not `same-origin` or `none`, or, with no `Sec-Fetch-Site`, its `Referer` names another host (`web::started_by_another_site`); and so is one the browser loads as a part of a page, its `Sec-Fetch-Dest` not `document`, `iframe`, `frame` or `empty` (an image of this site in a stored rich text), or, from a browser that sends no `Sec-Fetch-Dest`, its `Accept` names an image, style, media or font type and not `text/html` (`web::loaded_as_subresource`, `web::get_write_refused`; plans/Security-Review-Medium.md SEC-CLI-82). elFinder's write commands run only from the file manager's own fetch (`Sec-Fetch-Dest: empty`) or with the session's token, so a link in a stored text that an administrator follows changes no file (`elfinder::file_change_refused`). The app's own links, a typed URL and a client that sends neither header still run it. `GET /Login/logout`, `GET /rest/logout` and `GET /sso/logout` are such transitions: a cross-site link no longer signs the user out (SEC-RTE-08, SEC-ADM-09).
- `/resources` (elFinder) is a `read-only` transition, so the rule above does not cover it; its write commands (`put`, `rm`, `rename`, `mkdir`, `mkfile`, `upload`) refuse a request another site started by the same test (`crates/moqui-dav/src/elfinder.rs`; SEC-RTE-05, SEC-FIL-01, fixed).
- `read-only="true"` exempts a transition from those two refusals, so it runs on a `GET` with URL parameters. It does not exempt it from the token: a `POST`, `PUT`, `PATCH` or `DELETE` to a `read-only` transition that runs actions must send it.
- A key-header request (and any other header authentication) skips only the token check. The URL parameter and https refusals apply to it.
- The `Sec-Fetch-Site` (or `Referer`) check is only the cross-site `GET` rule above and the `/resources` writes. The `Origin` check ([CORS](#cors)) applies only to a request that sends `Origin`.
- A script servlet gets no token check from the framework; the script decides. A render with no socket (`enforce_request_checks` false: the error page, an in-process render) runs none of these checks.

### Login lockout and passwords

`login` is `max-failures="3"` `disable-minutes="5"` `history-store="true"`. The account is disabled when `successiveFailedLogins + 1` is greater than `max-failures`, so the fourth failure starts the five-minute window. An attempt during the window counts but does not restart it, so the window ends `disable-minutes` after it began, and the next failure after that starts a new one. That window is not a substitute for an edge limit on the login URL. The per-client login rate limit in [Web protection](#web-protection) is off until per-client rules are on.

The lock is `disabled = Y` with a `disabledDateTime`; it ends `disable-minutes` after that time (`still_disabled`, `crates/moqui-core/src/user/login.rs`). `disable#UserAccount` writes `disabled = Y` with no `disabledDateTime`, which does not end by time and ends the account's live sessions at their next request. While an account is disabled either way, every sign-in attempt on it is refused without checking the credential (`gate_account`). Only an attempt that tried a password counts as a failed login (a password login, a re-authentication, a password change's old password); a login that tries no password (an internal login for jobs, queued work or XMPP service calls, a second factor's finish, the SSO device key, a valid login key or app password) never counts, and a valid key or app password the gate refuses is not noted as an auth failure (`refused_credential`). A counted failure past `max-failures` writes `disabled = Y` and `disabledDateTime = now` only when the account is not already in a lock window (`write_failed_increment`, and `increment#UserAccountFailedLogins` in `UserServices.xml`), and never on an account disabled for good (`disabled = Y`, no `disabledDateTime`), which keeps no lock time and only counts. So attempts on a locked account do not extend its window, and attempts on an account disabled by `disable#UserAccount` never turn it into a timed lock (plans/Security-Review.md SEC-WEB-01, SEC-WEB-03, fixed). A sign-in that passes the gate resets `successiveFailedLogins`, `disabled` and `disabledDateTime` (`finish_login`); an account disabled for good does not pass the gate. A past `terminateDate` refuses every sign-in and none of this changes it. A wrong `oldPassword` in `update#Password` and a wrong second factor code (`validate#UserAuthcFactorCode` with `countFailure`, through `ec.user.checkCountedCode`) count as failed logins too, by the same compare-and-set (`increment_failed`; `increment#UserAccountFailedLogins` uses it as well); a disabled account takes no code. No more password or code checks of one user run at once than the failures the account has left (`LoginCheck`, `gate_once`): a password past them waits for a place, and a code past them is counted and refused without being compared, as a code is checked in its caller's transaction (`check_counted_code`, SEC-WEB-87), so codes sent at once are each counted and the lock bounds them as it bounds passwords. A right code is taken by one conditional update in the caller's transaction (`take_factor_code`: a single-use code only while not ended, an authenticator step only after the last one taken), so of two right submissions of one code only one verifies; a caller that rolls back, as `update#Password` does when it refuses the new password, gives the code back, while the wrong codes counted stay counted. An unknown user, a locked account and a legacy hash each cost one argon2 verification (`burn_verify`). A login history row is written at most once a minute per user and kind (`save_history`, `HistoryKind`): failures get one row a minute and successes one a minute for each visit, so a wrong password or a key's login every minute keeps no new sign-in out. A password step that waits for a second factor is recorded as not logged in, and the step that finishes the factor writes the successful row (`internal_login_user`). The new-device notice is sent only from a successful row with a visit ([Admin](Attack-Surface-Admin.md)).

Lockout abuse: the lock is per account and needs no knowledge of its password, so anyone who knows a username can
keep that account locked by sending four wrong passwords every `disable-minutes`, and while it is locked its owner
cannot sign in either (`gate_account`). The design bounds what that costs: the lock lasts `disable-minutes` (five) and
attempts during it do not extend it; with per-client rules on ([Web protection](#web-protection)) one client's
attempts meet the `login` rate limit (ten a minute) and the `auth-failure` ban (twenty in ten minutes bans the client
for fifteen), so a lockout kept up from one address is slowed and then refused, while one kept up from many addresses
is not. That is the trade-off of a per-account lock: password guessing on an account is bounded at the price of this.
Second-factor codes are bounded by the lock as passwords are, those sent at once too (SEC-WEB-87, fixed).

A password login asks for a second factor when the user has a `moqui.security.UserAuthcFactor` row in date, or is in a `UserGroup` with `requireAuthcFactor = Y` (`second_factor_required`, `user/factor.rs`). The password stage leaves the user signed out and sets the session attributes `moquiPreAuthcUsername` and `moquiAuthcFactorRequired`. The code is taken by `Login/login`, `SecondFactor/verifyUserAuthcFactor`, `/rest/login` and `/rest/verifyOtp`, each through `validate#ExternalUserAuthcCode` (`anonymous-all`), which reads the user from the session attribute. A TOTP code is HMAC-SHA1, six digits, 30 seconds, one step either side, and is taken only for a step after the factor's last one (`UserAuthcFactor.lastTotpStep`, `user::totp_code_step`), so a code works once. A sent single-use code has six digits and is valid 24 hours; a printed one has eight and is valid a year. `Login/sendOtp`, `SecondFactor/sendOtp` and `/rest/sendOtp` send a code for the pre-authenticated or signed-in user; `send#ExternalAuthcCode` sends a factor at most one code every 30 seconds, whoever asks, and `send_reauth_code` allows one send per 30 seconds per session. `get#ExternalUserAuthcFactorInfo` (`anonymous-view`) answers the email addresses and phone numbers of that user's sendable factors.

New password hashes are argon2id. Legacy hashes still verify, including the conf type `SHA-256`. The password element also sets `min-length="8"`, `min-digits="1"`, `min-others="1"`, `history-limit="5"`, `change-weeks="104"`, and `email-expire-hours="48"`. A login key is hashed with `login-key` `encrypt-hash-type`, which is SHA-256, and it is not hashed with argon2id. `login-key` `expire-hours` is 144.

A sensitive action can ask for a recent sign-in (`check#RecentAuth`, five minutes): a password login, a second factor's code,
an SSO login with a recent `auth_time` or a re-authentication counts; a key, an app password or an internal login does
not, and another user's login in the session drops it. A password login includes Basic credentials (and an SSH or terminal
password), so a client that sends Basic on every request is always recent. `reauthenticate#User`
checks the signed-in user's password and code under the same lockout rules as the login form ([Recent sign-in](Recent-Auth.md)).
`/ReAuth/check`, `/ReAuth/password` and `/ReAuth/sendCode` are 401 without a user; the posts need the CSRF token.
`check#RecentAuth` is `authenticate="anonymous-all"`, answers only about the session's own user and takes `maxAgeSeconds`
from its caller (default 300); `/ReAuth/check`, the only outside path to it, passes no parameter. `require#RecentAuth`, the
form that refuses, passes a caller with authorization disabled (`service/recent_auth.rs`), so a guarded service called
inside a disabled-authorization scope does not ask. An SSO re-authentication is a POST of `/sso/reauth` with the session
token; `/sso/login` is always a plain sign-in (`webroot/sso.xml`), so a link or another site's navigation does not start
one. For an OpenID flow the callback then needs an `auth_time` after the request (`prompt=login` is sent); an OAuth 2 flow
(`AftOauth`) has no such proof, and its round trip counts as a recent sign-in only when the flow's
`OauthFlow.reauthPrompts` is Y (`service/sso.rs`). An account with no password and a verified address confirms by a code
mailed there (`send#ReauthEmailCode`; [Recent sign-in](Recent-Auth.md)).

`update#Password` is `authenticate="anonymous-all"` (`UserServices.xml`). `Login/changePassword` and `ChangePassword/changePassword` (both screens are `require-authentication="false"`), the REST resource `/rest/s1/moqui/users/{userId}/password/update` and `org.moqui.public.Account` (`manageAccount`, for the signed-in user) call it. With nobody signed in it takes any `username` or `userId`; a signed-in user without `ADMIN_PASSWORD` may change only their own password, and a holder of it changes another account only when that account holds no access the caller lacks (`heldBeyond`, SEC-ADM-05). It refuses an account disabled for good or past its `terminateDate` unless the caller has `ADMIN_PASSWORD` (SEC-ADM-01, fixed); `reset#Password` makes no reset password for such an account. The old password is checked by `ec.user.checkOldPassword` (`check_old_password`) behind the password login's gate (`gate_password`): a lock window or `terminateDate` refuses any password, one check of a user runs at a time (`LoginCheck`), an unknown or refused account costs an argon2 verify (`burn_verify`), a wrong old password counts as a failed login and is noted as an auth failure, and every refusal answers "Password could not be updated with the information provided." It checks `oldPassword` against `currentPassword`, then against an unexpired `resetPassword`. For a user who needs a second factor, a valid code stands in for `oldPassword` only in a pre-authenticated session (`moquiPreAuthcUsername`), never a signed-in one; a right `oldPassword` with no code answers `Authentication code required for user` (SEC-WEB-02, SEC-ADM-03, fixed). On success `update#PasswordInternal` writes the argon2 hash, clears `resetPassword`, and writes `requirePasswordChange` from its parameter (default `N`); `disabled` it writes when the caller gives it, and otherwise only ends a tarpit lock, leaving an account disabled for good disabled. The Rust `change_password` does the same. `Login/changePassword` then signs the user in with `internalLoginUser`.

`reset#Password` is `authenticate="anonymous-all"`. `Login/resetPassword`, the REST resource `/rest/s1/moqui/users/{userId}/password/reset` and `org.moqui.public.Account` (`requestRecovery`) call it. It finds the account by `userId`, then by exact `username`, then by `emailAddress` equal to the `username` given, and answers the same public message whether or not one was found. It makes the random password and its hash before the lookup, so an unknown, closed or recently reset account answers after the same work. For a found account with an email address it stores the argon2 hash of a 12 character random password in `resetPassword`, at most once per `login` `disable-minutes` per account, leaves `requirePasswordChange` alone (`password` `email-require-change` has no effect), and emails the password (SEC-WEB-09, fixed). The reset password is accepted only as `oldPassword` in `update#Password`, for `email-expire-hours`; a login never takes it. It does not read `disabled`. The `allow-remote` values on these two services have no effect ([Services and `allow-remote`](#services-and-allow-remote)).

`create#InitialAdminAccount` is `authenticate="anonymous-all"`. It returns an error unless `get#InitialAdminNeeded` (`authenticate="anonymous-view"`) answers `needed`: the property `user-facade/login@initial-admin-enabled` is `true`, and no `UserAccount` row exists but the seed accounts nobody logs in as (`_NA_`, the edge node's delegate `_EDGE_` and the agents' chat users). The default conf has `user-facade/login@initial-admin-enabled` false, so a production server offers the form and takes the call only while the operator sets it (a temporary line in `.env`); the dev conf and the Desktop app's node set it true. With it off and no account, `disabled` is true: the Login page shows the login form with a line saying how to turn the setup on, the startup log says the same instead of writing the setup secret, and the service refuses with that message. It takes the request only when `ec.user.initialAdminAllowed(setupSecret)` passes: the caller is on this machine (`user/setup.rs` `initial_admin_local`: a loopback peer straight to the listener, or the Desktop node in process, with no `Forwarded`, `X-Forwarded-For`, `X-Real-IP` or configured client-ip header), or it gives the one-time setup secret the server writes to its startup log while no account exists (`log_initial_admin_setup`, new at each start). It then locks the seed `_NA_` row, asks `get#InitialAdminNeeded` again, creates the account and adds it to `ADMIN` with authorization disabled, so two requests at once make one administrator (SEC-WEB-08, fixed). With `joinAdvanced` (the form's "Also join Administrators - Advanced" check, off by default) it adds it to the privileged `ADMIN_ADV` too, the same way; this is the only way in to that group other than a data load or an existing member. `get#InitialAdminNeeded` answers the password rules only while `needed` is true. The Login screen's actions use the same service, so the page and the service count accounts the same way. `Login/createInitialAdminAccount` is a transition of a `require-authentication="false"` screen, so any caller reaches the service while `needed` holds, and one from another machine needs the setup secret, which the Login form, its tui form and the terminal's login dialog ask for (`secretRequired`). The terminal's login dialog calls the same two services with no user, in process (`crates/moqui-host/src/tui.rs`) and over HTTP (`/Login/initialAdminNeeded`, then the post).

### HTML and uploads

A service parameter `allow-html` defaults to none, which rejects text that contains `<`. There is no webapp attribute of that name. `safe` cleans with ammonia and allows the span attributes `data-mention-id`, `data-record-entity`, and `data-record-id`. `app` is `safe` for app text read by signed-in users, where an image keeps only a `src` of this server (SEC-CLI-82). `any` leaves the markup.

`webapp-list/webapp[webroot]@upload-executable-allow` is `false`. An upload is refused unless that setting is `true`. The check matches a `#!` shebang and the magics `MZ`, ELF, a Java class file, and four Mach-O values. A ZIP (`PK`) is not treated as a program. `webapp-list/webapp[webroot]/web-protection/requests@max-upload` is 2147483648 bytes. A file over 256 KiB is written under `runtime/tmp/upload`. A multipart body takes `webapp-list/webapp[webroot]/web-protection/requests@max-upload` only when the request names a user before its body is read: a signed session cookie of a signed-in session, or an `api_key`, `login_key` or Basic credential that holds, checked without a login (`moqui_core::user::credential_user`, host `http.rs` `upload_has_user`; a wrong one counts for web protection). Any other upload stops at `webapp-list/webapp[webroot]/web-protection/requests@max-body`, except on the `web-protection` `requests` `anonymous-upload-paths` (`webapp-list/webapp[webroot]/web-protection/requests@anonymous-upload-paths`, default `/s/`, the public share's file drop; a path with `..` or `%2e` never matches), which take `webapp-list/webapp[webroot]/web-protection/requests@max-upload` with no user. A `servlet` may name its own `max-upload` for a multipart body (`web/servlet.rs` `max_upload_for`); mr-mantle's `PassApi` names `11m`. The spool files of all requests hold at most `webapp-list/webapp[webroot]/web-protection/requests@max-spool` (4 GiB), past which an upload is 503, and a refused or cut-short upload leaves no file (`SpoolWriting`; SEC-RTE-07, fixed).

A body that is not multipart stops at `webapp-list/webapp[webroot]/web-protection/requests@max-body`, or at the `max-body` of the `servlet` its path maps to (`web/mod.rs` `body_limit_for`): `/search/*` and `/dashboard/*` name `100m`. A body whose limit is above `max-body` stops at `max-body` for a request with no user (`web::anonymous_upload_limit`, `upload_has_user`), since the host reads the whole body into memory before the session, the sign-in and the servlet's `AuthFilter` run; `anonymous-upload-paths` exempts uploads only. `MoquiDefaultConf.xml` sets the webapp's to 10 MiB (`10485760`), the code's fallback as well (`crates/moqui-core/src/web/mod.rs`), and `MoquiDevConf.xml` does not set it. A deployment may change it in its runtime conf, or from the environment by its name (`moqui_conf__webapp_list__webapp__WEBROOT__web_protection__requests__max_body`).

Screen JSON removes credential fields at any depth, case-insensitive: `password`, `oldPassword`, `newPassword`, `newPasswordVerify`, `currentPassword`, `resetPassword`, `authPassword`, `api_key`, `login_key`, `passwordSalt`, `passwordHashType`, `passwordBase64`, `passwordVerify`.

### Response headers

Every response of the screen servlet chain (a screen, a transition, REST, a script servlet, an early error) gets the `screen-render` headers it did not set itself: `Content-Security-Policy: frame-ancestors 'none'; form-action 'self';`, `X-Frame-Options: sameorigin`, `X-XSS-Protection: 1; mode=block`, and `X-Content-Type-Options: nosniff`. `Strict-Transport-Security: max-age=31536000` (type `screen-secure`, no `includeSubDomains`) is added only to an https request whose `Host` is not `localhost` or a name under it. A stricter CSP in the conf comment is commented out. A request that resolves to a vault screen (one of `vault@screen-names`, `Vault`, `Vaults`, `VaultKey`, `VaultContacts` or `RecoveryKeys`, among the screens its path names, never an extra-path name; the `/qapps` page's document included) gets, when it set no policy of its own, that `screen-render` policy with `vault@screen-policy`'s directives added: a directive the site sets is kept, given only the worker's `blob:` and `'wasm-unsafe-eval'`; by default the added ones are `default-src 'self'`, `script-src 'self' 'unsafe-eval' 'wasm-unsafe-eval'` (no inline script), `style-src 'self' 'unsafe-inline'`, `connect-src 'self'`, `worker-src 'self' blob:`, `object-src 'none'` and `base-uri 'self'` among others, and `X-Frame-Options` stays; the shell loads a vault screen as a new document (`crates/moqui-core/src/web/vault_policy.rs`; [Vaults](Vaults.md#the-vault-screens-policy)). A user's file the engine sends from its storage (`send#RunArtifact`, `web::send_file_response`) and a PASS download the frontend forwards from the authority over gRPC carry their type only when it is inert (images, fonts, audio and video, PDF, plain text and CSV, archives; `web::is_inert_content_type`), else `application/octet-stream`, with `Content-Security-Policy: default-src 'none'; sandbox` (`web::USER_FILE_SANDBOX`; an inline PDF aside). The Assist sandbox frame uses its own policy, under [Assist](Attack-Surface-AI.md#assist).

The host routes outside the screen servlet chain get none of the `screen-render` headers (`web/mod.rs` `finish_response` is called only from the chain): `/health`, `/metrics`, `/git`, `/ci/runner`, `/dav`, `/notws`, `/termws`, `/agentws`, `/callws`, the LLM, OTLP, channel and XMPP routes, and every refusal the host writes itself (web protection's 403, 404, 405 and 429, and the 421, 414, 413, 408, 503 and 504) carry no `X-Content-Type-Options`, `X-Frame-Options`, CSP or HSTS unless the handler sets its own. The chat bridge media (`channels.rs`), XMPP uploads (`xmpp/upload.rs`), the Assist sandbox (`llm/sandbox.rs`) and DAV files (`moqui-dav`, the user-file headers above) set their own. HSTS reaches a browser only from a screen answer.

### CORS

`webapp-list/webapp[webroot]@handle-cors` is `true`. `webapp-list/webapp[webroot]@allow-origins` is empty. An origin is its scheme, host, and port, all three. The server's own origin is allowed: https over TLS or from a believed proxy, with the host and port of `Host` or of a believed proxy's forwarded host and port, and the webapp URLs from the conf. A foreign origin is 401 `Origin not allowed`, before the servlet. An `allow-origins` entry that includes a scheme is matched the same way. A bare domain allows that host and the hosts under it on any scheme and port. An IP address entry allows that address only. `*` allows every origin, but never with credentials (SEC-WEB-10): an origin only `*` allows gets `Access-Control-Allow-Origin` with no `Access-Control-Allow-Credentials`, so a browser sends it no cookie and lets it read no signed-in answer, and `/notws`, `/termws` and the Assist event stream, which a browser opens with the session cookie, do not count `*`. The dev conf sets `localhost,127.0.0.1`: this machine on any port and either scheme. The own origin and a named entry get `Access-Control-Allow-Credentials: true`, and `Access-Control-Expose-Headers` lists `X-CSRF-Token` and `moquiSessionToken`. A request with no `Origin` header is not checked.

An `OPTIONS` preflight is 204 with an empty body, before the servlet chain (`crates/moqui-core/src/screen/mod.rs`). Preflight and actual responses send `Access-Control-Allow-Credentials: true`. Preflight also sends the conf allow-headers (including `api_key`, `login_key`, `moquiSessionToken`, `X-CSRF-Token`, `Authorization`, `A2A-Version`, `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`), allow-methods `GET, PUT, POST, PATCH, DELETE, OPTIONS`, and `Access-Control-Max-Age: 3600`.

`/notws`, `/termws`, `/agentws`, `/callws`, and the Assist event stream use the same origin list and answer 403 `origin not allowed`.

### Client IP

`webapp-list/webapp[webroot]@client-ip-header` and `webapp-list/webapp[webroot]@trusted-proxies` are empty, so `X-Forwarded-For` is not trusted. `ClientAddressing` believes a peer only when a header is configured. If a header is set and the trusted-proxy list is still empty, the first hop is believed from any peer, and `X-Forwarded-Proto` uses that same gate. `X-Forwarded-Proto`, `-Host` and `-Port` are read from the hop the client address is read from: the value at that index when the header has as many values, else the last, and the first only when no trusted proxy is listed (`ClientAddressing::forwarded_value`, read everywhere through `http::forwarded`). The comment above the property still names Jetty's `ForwardedRequestCustomizer`. The listener uses `ClientAddressing`.

On every node that takes links (`instance@node-role` `front`, `front_edge`, `edge` or `all-in-one`) a header with an empty trusted-proxy list is ignored, with an error at startup: the edge node faces the internet and passes the client address to its local nodes ([Edge node](../Run-Deploy.md#a-local-server-with-an-edge-node)).

`/health` and `/metrics` check the TCP peer and, when a believed header names another client, that client too: it must be an entry of `status-ips`, and a loopback address a header or an edge node names is not this machine (`http::status_request_allowed`). `/status` uses `ec.user.getClientIp()`, which can differ.
Both take any address in 127.0.0.0/8 as loopback.

A server of `moqui test --serve` (and only that: the command sets it in code before its server starts; no property or
conf turns it on) takes a request's `X-Moqui-Test-Peer` header as its TCP peer and client address, when the peer and
the client address (a believed proxy's header included) are both loopback and the header names an IPv4 address in
127.0.0.0/8, so `moqui test-client` gives each client spec its own requester
([JS-Test-Client](../dev/JS-Test-Client.md#--serve)). The header is removed before any request is served, on every
server. A client can name only a loopback address, from loopback, on a test server; `./moq run` never reads it.

### Web protection

`web-protection` always applies connection limits, request limits, and overload. Per-client rules (client rules, the `requests` `methods` list, rate limits, bans, path rules, user-agent rules and `connections` `max-per-client`, 64 connections) are on when `webapp-list/webapp[webroot]@trusted-proxies` is set, or when `webapp-list/webapp[webroot]/web-protection@enabled` is `true`. Both default to empty, so per-client rules are off on a default install, and the `methods` list is not applied then; its default adds the WebDAV methods (PROPFIND, PROPPATCH, MKCOL, COPY, MOVE, LOCK, UNLOCK, REPORT). Whatever that list says, a screen asked by a method other than GET, HEAD, POST or OPTIONS, and a transition of method `any` asked by one outside those and PUT, PATCH and DELETE, are 405 with an `Allow` header (`render::refused_method`). A rate limit and a path rule apply when they match the request path as sent, with `%XX` decoded and without regard to ASCII case, or that path's cleaned-up names (`guard.rs` `screen_path`: empty, `.` and `~name=value` names dropped, `..` popping one, each name decoded), so a dot segment does not pass them (SEC-WEB-07, fixed). The guard runs before the screens resolve the path, so it is asked again for the screen path the request reached: before any action runs, the render asks the host's check (`moqui_core::web::reached`, `render::reached_paths`) with the screens walked and the transition under the render's link prefix (a token route's `/<name>/<token>` in front; after a transition, with its extra path too and the last name's render-mode extension removed), and `Guard::check_reached` applies the path rules and rate limits the edge-time forms did not match. A `//name` search path, a `ScreenPathAlias` rewrite and a render-mode extension are so matched by the path they reach. A transition through `/fop` is 404 (`render::refused_transition_path`), as are names after a transition that declares no `path-parameter`; read-only transitions and screens with `allow-extra-path` keep their extra path. `/ReAuth/password` is in the `login` limit. A glob is `*` within a segment and `**` across segments, lower case. An invalid `rate-limit` or `ban`, and a `client-rule` or `path-rule` with an action that is not its own, is logged and left out, and `enabled="false"` drops any of them (`GuardConf::from_node`, `read_lists`); a `rate-limit` and a `ban` merge by `name`, a rule by `name` or is appended, and only a component's conf can change them (`context/conf.rs` `merge_web_protection`). A rate limit charges nothing for a request another rule refused, and a conf reload resets the limits without dropping bans. A refusal closes the connection only for a client that came straight to the listener. Per-client state is kept for at most `max-tracked-clients` (100,000) clients, an IPv6 one by its /64 (`client-ipv6-prefix`), and an entry stays while it has a connection, a ban, or was seen within the longest ban window. When the table is full a new client takes the place of the idle client seen longest ago, else of the connection-free banned client whose ban ends soonest (`Guard::evict_idle`); it is refused (503, or the connection closed) only when every tracked client holds a connection, counted in `edge_untracked` and logged once a minute. An `auth-failure` event is a login in the request that returned the invalid-login error (a password, a login key, an app password, a shared device's credential, a re-authentication); a wrong `oldPassword` in `update#Password` is one too, and so is a wrong or refused second factor code at `Login/login`, `/rest/verifyOtp`, `SecondFactor` or a re-authentication (`check_counted_code`, SEC-WEB-87). Loopback (`127.0.0.0/8`, `::1`) is exempt when those rules are on (the `client-rule` `loopback`); the exemption is by the resolved client address, not the TCP peer, so with a `client-ip-header` and no `trusted-proxies` ([Client IP](#client-ip)) any client that names `127.0.0.1` in the header is exempt from every per-client rule, where `/health` refuses a loopback address a header names. The mr-boss limit on `POST /r/*/submit` is one of those per-client rules.

## HTTP container

The listener is hyper and axum. `webapp-list/webapp[webroot]@http-bind` empty binds `0.0.0.0`, every IPv4 address; `localhost` binds `127.0.0.1`; any other value must be an IP address. The HTTPS listener binds the same address. `webapp-list/webapp[webroot]@http-port` empty is port 8080. When `webapp-list/webapp[webroot]@allowed-hosts` is set, a request straight to a listener whose `Host` is not listed is answered 421 (`serve.rs` `host_allowed`); it is empty by default, and the Desktop node sets `127.0.0.1:<port>,localhost:<port>`. The plain HTTP listener is HTTP/1.1. The HTTPS listener offers `h2` and `http/1.1` by ALPN (`moqui_conf__webapp_list__webapp__WEBROOT__http2=false` offers only `http/1.1`). An HTTP/2 connection takes at most `http2-max-streams` (100) open streams, a request head of at most `max-header-bytes`, h2's bounds on streams a client resets before they are taken (20) and on streams reset for its protocol errors (1,024), PINGs every 30 seconds, and is closed with a GOAWAY after `header-timeout` with no request, or when web protection refuses its client with a closing refusal (HTTP/1.1's `Connection: close`). An HTTP/2 request is given `Host` from `:authority`; a WebSocket over extended CONNECT is checked by web protection as the GET of an HTTP/1.1 upgrade. Over HTTP/2 a `content-type: application/grpc` call goes to the gRPC services that are on (OTLP ingest, PASS authority; the rows below) before web protection's per-request rules and the router, as on their own port, except a call for an edge node's terminate host, which is forwarded as any request. There is no separate servlet descriptor: filters and servlets are the webroot `<webapp>` children in `MoquiDefaultConf.xml`, run by the screen chain. Neither hyper nor axum normalizes a path. The router matches the raw path, so `/git/../x` is git's and `/x/../git/y` is the fallback's, and the fallback gives the raw path to the core. `match_servlet` and `filters_for` (`web/servlet.rs`) compare that raw string with no decoding and no dot handling: exact, then the longest prefix on a segment boundary (`/searchx` is not `/search`), then extension, then the default; a servlet and its filters are chosen from the same string. So `/fop/../apps/x` is the FOP servlet with path info `/../apps/x` (the screen `/apps/x` as PDF, with its checks), and `//search/x`, `/%73earch/x` and `/apps/../search/x` are the screens servlet, which drops `.`, `..` (popping a name) and `~name=value` names and resolves `//name` as a search path. Web protection runs before all of it, on the raw path and its cleaned-up names. The session is the database row above.

`webapp-list/webapp[webroot]@https-enabled` is `false`. `webapp-list/webapp[webroot]@https-listen-port` empty is 8443 when the listener is used. The value `off` starts none. With no usable certificate in `runtime/cert` the listener does not bind, whether or not the port was set, until a name is set up with ACME ([ACME](#acme)), a certificate is added, or while a set-up check runs; it then answers only the challenges of names set up and refuses every other handshake until a certificate is there. An edge node that started so takes no links (`edge_link` is not given the listener's certificates) until it restarts with one. `moqui_conf__instance__purpose=dev` tries to generate a development certificate first. `webapp-list/webapp[webroot]@https-port` is the port clients see in generated URLs, which can differ behind a proxy.

The HTTPS listener's `rustls::ServerConfig` uses the `aws_lc_rs` provider with rustls's default protocol versions and cipher suites, and asks for no client certificate (`server_config`, `crates/moqui-host/src/tls.rs`). The certificate is chosen by server name from `runtime/cert`: the name, then `_wildcard.<parent>`, then the parent, then `default`. With `moqui_conf__instance__purpose=dev` and no pair, a self-signed certificate for `localhost` is written as `localhost` and `default`. The TLS handshake has the `header-timeout` (30 seconds).

Some example confs under `runtime/conf/` open more than the default. `MoquiDevConf.xml` sets `moqui_conf__webapp_list__webapp__WEBROOT__allow_origins=localhost,127.0.0.1` and turns the tarpit off for screens, transitions and services. `MoquiLoadTestConf.xml` turns the same tarpit off and sets `login` `history-store="false"`. `dev-group/MoquiGroupConf.xml` binds the SSH server on `0.0.0.0:2222` and turns the LLM gateway on, with `moqui_conf__instance__purpose=production`. The edge, front, all-in-one, multi-domain, full-stack and PASS confs set `moqui_conf__webapp_list__webapp__WEBROOT__web_protection__enabled=true`. The listeners these confs open are in [Process](Attack-Surface-Process.md).

### ACME

Certificates from an ACME authority, only for a name an administrator sets up on System › Certificates (`moqui.server.AcmeName`, `org.moqui.admin.CertificateServices`, `crates/moqui-host/src/acme/`, [plan](../../plans/Edge-Node2.md) §4.8). Nothing is requested for any other name, and nothing a client sends starts an order. The checks are in `setup#AcmeName`: a DNS name of letters, digits, hyphens and dots with two labels or more (`services.rs` `valid_host`), an `https://` directory, and not another tool's directory; `remove#`, `renew#` and `update#AcmeName` act only on a name that has a row. The four entities (`AcmeName`, `AcmeChallenge`, `AcmeCertificate`, `AcmeOrderLock`) are in none of the lists of `crates/moqui-entity/src/entity/sensitive.rs`, so whoever writes entities through the generic tools (Tools › Data, entity REST, a data load) writes these rows past those checks; the items below say what the code does with such a row.

- **The services** (`org.moqui.admin.CertificateServices`) have no `authenticate` attribute and check no permission in their bodies, so each needs an authorization record; the only grant that covers them is `SYSTEM_APP`'s, to `ADMIN`, through the five transitions of `tools/screen/System/Certificates.xml`, and mr-boss denies its Admin groups the mounted System screens. `renew#AcmeCertificates` is the service of a paused job. Every store function runs with authorization off in its own transaction (`store.rs`).
- **The order** (`order::run`) marks the name in the process, reads its row and takes the cluster lock with the row locked for update and a 15-minute lease; then it gets the account from the derived key at `directoryUrl`, makes a new order for the one DNS name, writes the TLS-ALPN-01 digest of each pending authorization as challenge rows for ten minutes, waits 1.2 seconds, polls, makes a new key and request, finalizes and takes the certificate; the challenge is closed whether the order worked or not. The chain the authority sends is stored and written as received; only its first certificate's expiry and issuer are read.
- **The challenge** (TLS-ALPN-01, RFC 8737) is answered on the HTTPS listener: a ClientHello that offers ALPN `acme-tls/1` gets a self-signed certificate carrying the SHA-256 of the order's key authorization, only when its server name has a challenge open (`moqui.server.AcmeChallenge`), and is refused otherwise. An order writes the challenge for ten minutes and closes it when the order ends; the reader (`store.rs` `read_challenges`, `refused_challenge`) takes a row whose `expireDate` is still ahead only when its name has an `AcmeName` row and it closes within ten minutes and one of now, or when it is the reachability check's own (`probe` Y, a digest the node drew at random, before the name is set up) and closes within a minute and one, and logs and leaves out any other; it is never served HTTP. The four ACME entities are written only by their own services, never a generic tool, REST or request load (`SERVICE_WRITTEN_ENTITY_KEYS`, SEC-OUT-81). The open challenges are read from their rows again when the last read is a second old, and at most once a second per process, so `acme-tls/1` handshakes cost at most that; an order waits past that second before the authority looks, so every member answers the challenge as it is now. On an edge node the passthrough check comes first, so a local node's passthrough name's challenge goes down its tunnel and the local node answers it; the edge node answers only for names it ends TLS for itself.
- **The set-up check** opens a challenge of its own with a random digest, for at most a minute and closed when the check ends, and connects to the name on 443 as the authority would, taking any certificate (it checks no signature, only that its digest is in the certificate), for at most 20 seconds. It reaches whatever address the name's DNS has; an administrator chooses the name. On a node with no certificate the listener binds for the check and closes after it.
- **Calls to the authority** have a time limit (a minute for the account and the order, three for the validation and the certificate), well under the 15-minute order lock.
- **The account key** is a P-256 key derived from `acme@account-key`, a generated secret kept as a `SecretValue` row ([Secrets](Attack-Surface-Data.md#secrets)), so the members of a cluster share it through their database. Whoever has it can act as the account at the authority: revoke its certificates, and order for a name whose challenge they can answer.
- **The certificate's key** is new for each order. It is kept in `moqui.server.AcmeCertificate` (`privateKeyPem` encrypted at rest), and every member of a cluster serves it from memory (`tls::hold_key`); no file holds it, and a `privkey.pem` or `.privkey.pem.new` an earlier build wrote is removed (`acme/store.rs` `write_files`; `the_certificate_is_written_where_the_listener_reads_it`). `fullchain.pem` and the marker are written with the default mode, and the name's directory with `private_fs::create_dir_all`. Every member writes the files again from the rows each minute (`store.rs` `sync_files`), for each `AcmeCertificate` row whose name has an `AcmeName` row; `write_files` and `remove_files` take only a name `valid_host` passes (a DNS name an authority issues for), so no row puts a certificate under `default`, `localhost`, a wildcard's file name or a path outside `runtime/cert` (SEC-OUT-81). A `runtime/cert/<name>/` directory that exists without the `.moqui-acme` marker is another tool's and is never written over or removed.
- **The authority** is reached over HTTPS checked by the operating system's trust store (`instant-acme` on hyper-rustls), or by the one root `acme@directory-ca` names for a company's own authority; the directory URL is the administrator's choice (`acme@directory-url` by default). Only `https`: no redirect is followed, no proxy is used and no address guard applies, to the directory or to the URLs it names; a response body is read whole with no cap, bounded by the step's time limit. The authority's error text is kept in `AcmeName.lastError` and shown on the screen. An order, the renewal job's included, takes `AcmeName.directoryUrl` only when it is `https://` (`order.rs` `directory_url`), as `setup#AcmeName` does.

The request deadline is `request-timeout`, code default 300 seconds, and the answer is 504. Exempt paths are `/notws`, `/termws`, `/agentws`, `/xmpp-websocket`, `/callws`, paths starting with `/xmpp-upload/`, `/git/` (and git at a page's URL on a public-site host, which is served as its `/git/` request: [Git hosting](../interfaces/Git-Hosting.md#repository-paths)), `/ci/runner/`, `/dav/`, and `/llm/v1`, and any request whose `Content-Type` starts with `multipart/` (a multipart request to the screens has the deadline again once its body has arrived). An upload is held to a pace instead: past `body-timeout` each chunk is waited for only while the average rate stays above `requests@upload-min-rate` (1024 bytes a second), then 408; at most `max-uploads` (1024) arrive at once, an upload with no user taking at most three quarters of them and at most `requests@max-uploads-per-client` (16) for one client address (`crates/moqui-host/src/http/upload.rs`); on an edge node, a request it forwards to a member, which applies its own deadline (the forward's waits bound it on the edge node: [Edge](Attack-Surface-Cluster-Edge.md#edge-node)). The exemption is by path prefix (`serve.rs`), whoever serves the path: where no host route takes a prefix (`/xmpp-upload/` while XMPP is off, `/git/` and `/ci/runner/` in a build without `git`), a path such as `/xmpp-upload/../apps/...` falls to the screens with no 504 deadline; the worker runs to its end either way, so only the answer differs. When a request's worker is lost the answer is a 500 with the worker's error text (`http/admission.rs` `Refusal::Lost`), where the other host 500s give an error id. A screen response past the `screen-facade` `stream-threshold` (64 KiB) is sent as it renders ([Screen output](../ui/Screen-Output.md)): the deadline covers it up to its head, and after that it holds its request worker and its transaction while the client reads. A client that takes nothing for `write-timeout` ends the render, so one that stops reading holds a worker for at most that long.
