# Attack surface: clients

The desktop and mobile apps and the other clients: the commands a page can call in the apps (Tauri IPC), the apps' URL schemes and OS links, the node the desktop app runs, the device keys and the offline store, and how the browser shell puts untrusted content into a page. This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## The desktop app's own node

A node the desktop app runs in its own process may have no HTTP or cluster port (`moqui_host::start_embedded_with`, `crates/moqui-host/src/in_process.rs`). Its window's requests and sockets reach the router in process, through the same checks as a listener's, from the loopback address, as a sidecar window's do over loopback HTTP. The app keeps the node's session cookie for the window, sets `Host` and `Cookie` itself, and does not pass on the page's `Cookie`, `Host`, `login_key`, `api_key`, `Forwarded`, `X-Real-IP`, `X-Forwarded-*`, `X-Moqui-Edge*` and `X-Moqui-Tunnel` headers (`HOST_HEADERS` and `passed_on` in `crates/moqui-desktop/src/node/scheme.rs`). Nothing outside the app's process reaches that path.

The node in process answers a request that another site started (`Origin` not `http://moqui-node.localhost`, or `Sec-Fetch-Site` not `same-origin` or `none`) only when it is a `GET` or `HEAD` for a document; any other is answered 403 before it reaches the router (`cross_site`, `navigation`). The cookie jar is the file `node-cookies` in the app config directory, opened with mode `0600` (`crates/moqui-desktop/src/node/cookies.rs`). A `Content-Security-Policy` of the node with no `script-src`, `script-src-elem` or `default-src` is not passed to the window (`has_script_policy`). An attachment, or a document that is not HTML and is over 16 MiB, that a window opens is answered 204 to the page and saved by the host through the save dialog, to the path the user picks, written to `<name>.part` and then renamed (`crates/moqui-desktop/src/download.rs`).

## The desktop app's modes

The desktop app (`crates/moqui-desktop`, identifier `org.moqui.desktop`, Chromium through `tauri-runtime-cef`) runs in one of three modes, kept in the file `node-mode` in the app config directory and switched from the tray menu (`crates/moqui-desktop/src/node/mod.rs`, `crates/moqui-desktop/src/lib.rs`).

| Mode | What listens | Window origin |
|---|---|---|
| Node in process (the default) | Nothing, unless the tray's ports item wrote `on` to the file `node-ports`; then HTTP on `127.0.0.1:<port>` | `http://moqui-node.localhost` (scheme `moqui-node`) |
| Sidecar (the `moqui` binary as a child process) | HTTP on `127.0.0.1:<port>`; the cluster listener on `127.0.0.1` at a port the kernel picks | `http://127.0.0.1:<port>` |
| Client of a remote server | Nothing | `http://moqui-shell.localhost` (main window), `http://moqui-app.localhost` (windows `remote-<n>`) |

Both node modes set `moqui_conf__webapp_list__webapp__WEBROOT__http_bind=127.0.0.1`, `moqui_conf__webapp_list__webapp__WEBROOT__http_port=<port>`, `moqui_conf__webapp_list__webapp__WEBROOT__https_listen_port=off`, `moqui_conf__cluster_member__bind_address=127.0.0.1`, `moqui_conf__cluster_member__https_port=0` and `moqui_conf__search_facade__cluster__run=false` (`listen_properties`); the sidecar gets them as `-D name=value` arguments with `moqui_stop_on_stdin_close=true`. The port is the one in the file `node-port` when it is free, else one the kernel picks (`choose_port`). The loopback listener is plain HTTP and is the node's ordinary web listener: every local process and every local user of the machine reaches the same routes a remote caller of a server reaches, the sign-in and the first-administrator form (`createInitialAdminAccount` in `runtime/components/base/webroot/screen/webroot/Login.xml`) among them; the first administrator is taken only from this machine or with the setup secret of the startup log ([Login lockout and passwords](Attack-Surface-Web.md#login-lockout-and-passwords)). Both node modes set `webapp-list/webapp[webroot]@allowed-hosts` to `127.0.0.1:<port>,localhost:<port>`, so a request whose `Host` names anything else (a page that rebinds a DNS name to loopback) is answered 421 before the router (`serve.rs` `host_allowed`; plans/Security-Review.md SEC-CLI-01, fixed), and the own origin the server takes from `Host` (`request_own_origins`, `crates/moqui-core/src/web/origin.rs`) is one of those two names, which only a page that listener served sends. The node starts with `user-facade/login@initial-admin-enabled` true on every start and offers the first-administrator form while no account exists (`crates/moqui-desktop/src/node/mod.rs`); both modes set `user-facade/login@initial-admin-local` to `in-process`, so only a request of the node's own process takes it without the setup secret (`crates/moqui-core/src/user/setup.rs`): in process the app's window, through the scheme; a caller of the tray's ports needs the secret. In sidecar mode the app makes the secret, gives it to the sidecar as `user-facade/login@initial-admin-secret` in its environment (not its arguments) and to its window's Login form through the bridge (`node_setup_secret`, `bridge.js`), and the sidecar's log does not show it (plans/Security-Review.md SEC-CLI-101). The tray's "Developer tools" item writes the file `node-purpose` and starts the node with `moqui_conf__instance__purpose=dev` (`purpose_properties`); see [Attack-Surface-Dev.md](Attack-Surface-Dev.md) for what a dev instance adds. `tauri.conf.json` of both apps has `"csp": null`, `"withGlobalTauri": false` and no windows; the windows are built in code.

The DevTools protocol listens on `127.0.0.1:<MOQUI_DESKTOP_DEVTOOLS_PORT>` only in a development run (`tauri::is_dev()`) with that variable set (`cef()` in `crates/moqui-desktop/src/lib.rs`). Media autoplay needs no gesture in every window. Camera and microphone requests are allowed for a page on the node's origin or a client's shell or app origin and denied for any other page (`on_permission`, `media_allowed` in `crates/moqui-desktop/src/bridge.rs`).

The node's runtime is, in order: `MOQUI_RUNTIME`; in a development run the repository's; then the first of `runtime` in the working directory, `runtime` beside the executable (the AppImage file's folder) and the executable's own folder that has a `components/base` directory; and only then the runtime bundled with the app (`crates/moqui-desktop/src/runtime_dir.rs`, `find_runtime_dir` in `crates/moqui-host/src/lib.rs`). Nothing checks the owner or mode of a folder found this way, so whoever can write one of those folders gives the node the components it loads.

`bridge.js` defines the page adapter on the node's, the shell's and the app's origins only and holds no secret. After a sleep the app asks the node's `/health` and refreshes the backup label (`wake.rs`). Autostart writes a LaunchAgent or an XDG autostart file for the running program (`os/autostart.rs`), and the login items and the handler entry quote the program's path (`os/entries.rs`). The edge pairing wizard opens once, after a `/qapps` page first loads on the node (`os/first_run.rs`).

### Where a window may go

| Window | Rule | Code |
|---|---|---|
| Main window, node modes | Stays on the app's own pages (`tauri.localhost`, the development server), and the node's origin. An `http` or `https` URL elsewhere, and a `mailto:`, `tel:` or `sip:` link, is handed to `xdg-open` (`open` on macOS) and the window stays. A URL of any other scheme is not refused by this check and is left to Chromium. A new window follows the same rule. | `stays_in_app`, `is_external`, `crates/moqui-desktop/src/lib.rs` |
| Main window, client mode | Only `/` and `/index.html` on the shell's origin, and `about:`, `data:` and `blob:` URLs. Another path on the shell's origin or a URL on the app origin opens in an app window. `http`, `https`, `mailto`, `tel` and `sip` go to `xdg-open`. Anything else is refused. A new window is always denied. | `goes`, `stays_on`, `crates/moqui-desktop/src/client/windows.rs` |
| App window `remote-<n>`, client mode | Stays on the app origin, and `about:`, `data:` and `blob:` URLs. The shell's origin is refused. The web goes to `xdg-open`. | same |
| The one webview of the mobile app | The shell's page only when the page shown is the shell or the host itself shows the shell; the app origin only with an account signed in; `about:blank`. `http` and `https` to a host that is not `localhost` or `*.localhost`, and `mailto`, `tel`, `sip`, open outside the app. Anything else is refused. | `goes`, `crates/moqui-mobile/src/host.rs`; `navigation`, `crates/moqui-mobile/src/lib.rs` |
| The hidden PDF window `pdf` (desktop) | No capability names it. It goes only to `about:` URLs, downloads and new windows are refused, and every request its page makes is failed through the DevTools `Fetch` domain. | `crates/moqui-desktop/src/pdf.rs` |

A page's navigation to a web URL, or to a `mailto:`, `tel:` or `sip:` link, starts the OS handler with no question to the user; the URL is one argument of the opener.

## Commands a page can call (Tauri IPC)

A page calls a command through Tauri's IPC. Which page may call which command is set by capabilities: `crates/moqui-desktop/capabilities/splash.json`, `crates/moqui-mobile/capabilities/main.json`, and three the desktop app adds at run time (`capability` in `crates/moqui-desktop/src/bridge.rs`, `add_capabilities` in `crates/moqui-desktop/src/client/windows.rs`). Tauri counts a page of the app's own schemes (`moqui-node`, `moqui-shell`, `moqui-app`) as local, so a local capability names a window, and some commands check the calling page themselves.

| Capability | Granted to | Commands |
|---|---|---|
| `splash` (desktop, file) | Local pages of window `main` | `restart_node` |
| `node-bridge` (desktop, sidecar) | Remote origin `http://127.0.0.1:<port>` in window `main`, not local pages | `notify`, `set_counts`, `set_presence`, `open_external`, `set_comms_root`, `notification:allow-is-permission-granted` |
| `node-bridge` (desktop, node in process) | Local pages of window `main` | the same, and `socket_open`, `socket_send`, `socket_close` |
| `client-shell` (desktop, client mode) | Local pages of window `main` | the twelve `client_*` commands, `socket_*`, `outbox_*`, `draft_*`, `file_save`, `notify`, `set_counts`, `set_presence`, `open_external` |
| `client-app` (desktop, client mode) | Local pages of windows `remote-*` | `socket_*`, `outbox_add`, `outbox_list`, `outbox_kinds`, `outbox_retry`, `outbox_discard`, `draft_*`, `file_save`, `open_in_shell` |
| `main` (mobile, file) | Local pages of the one webview `main` (the shell and the server's pages alike) | every command of the mobile app |

No command takes a path on the user's file system, reads a file outside the offline store, returns a device key, or starts a process other than the OS link opener.

The shell-page check differs by app. On the desktop `is_shell_page` is the trait default and returns true; the `client-shell` capability and the main window's navigation rule are the check. On the mobile app the one webview shows server pages too, so `is_shell_page` requires the webview's URL to be on the shell's origin and the `nonce` argument to equal the nonce of the shell's current load. The host makes a new nonce when a load of the shell finishes, evaluates it into the document, and clears it when any navigation or load starts (`PageState` in `crates/moqui-mobile/src/host.rs`). Four commands (`chat_room_shown`, `push_check`, `push_check_fix`, `push_test`) use `shell_only` instead, which asks only whether the last load begun is on the shell's origin, so a server page reaches them through IPC it posts while a navigation to the shell is starting (which `client_show_shell` lets it start). In the client crates no command looks at the calling frame's origin: the outbox, the drafts, `file_save` and the sockets know the caller only by `webview.label()`. On the mobile app `client_show_shell`, `open_in_shell`, `notify`, `open_external`, `scheme_fetch`, the sockets, the outbox and the drafts have no shell check: a server's page calls them.

## The app schemes and what reaches the server

In client mode the pages are on two schemes registered by the app (`crates/moqui-client-tauri/src/scheme.rs`, `crates/moqui-client/src/proxy.rs`).

- `moqui-shell` (`http://moqui-shell.localhost`): the shell's own files (`/`, `/shell/`, `/js/`, `/libs/`, `/css/`) are answered from the app's staged files or 404, never from the server. The shell's page gets the shell's `Content-Security-Policy` (`assets::configured_shell_csp`, not read). Any other path is forwarded to the current account's server only when `Sec-Fetch-Dest` is `empty`, `image`, `audio`, `video`, `track` or `font` (or absent on a request that is not a document); a document, frame, script, style or worker of the server is answered 403. A forwarded answer carries `X-Content-Type-Options: nosniff`.
- `moqui-app` (`http://moqui-app.localhost`): every request is forwarded to the server of the window's account, documents and scripts among them, but a worker's script (`Sec-Fetch-Dest` `worker`, `sharedworker` or `serviceworker`, or a `Service-Worker` header) is refused, 403 (`scheme::worker_request`; plans/Security-Review-Medium.md SEC-CLI-81), so no page of one server can leave a service worker on the origin to answer another account's requests. The server's HTML and scripts run on this origin. It is one origin for every account and every server, on the desktop and the phone (`APP_ORIGIN`, `crates/moqui-client-tauri/src/lib.rs`). The pages keep their browser storage apart only by a key prefix they choose to use, the account id the host writes into the window (`moqui.scopedKey` in `MoquiLib.js`, `window.__moquiStorageScope` in `crates/moqui-desktop/src/client/windows.rs`), and the host never clears the origin's storage, caches or service workers between accounts (only a removed account's data is cleared). A page of one server therefore reads and writes what another account's pages keep there. When a comms page starts with the host's outbox, the chat sends and drafts it finds under its keys in `localStorage` are dropped, never moved into the host (`dropBrowserOutbox` in `WebrootChat.js`, `drafts.dropLocal` in `MoquiLib.js`; SEC-CLI-81), so another server's page cannot plant a send the host would post as this account or a draft Compose would show as the user's; it can still read and clear what this account's pages keep on the origin, which only an origin or profile per account would end.

The proxy adds the account's device key as the `login_key` request header; the page never receives the key. Of the page's request headers only fifteen pass: `accept`, `accept-language`, `content-type`, `range`, `if-range`, `if-none-match`, `if-modified-since`, `x-requested-with` and seven `x-moqui-*` headers (`REQUEST_HEADERS`); a page cannot send `Cookie`, `Authorization`, `Origin`, `login_key`, `api_key` or an edge link header. A request whose `Origin` is not the scheme's origin, or whose `Sec-Fetch-Site` is neither `same-origin` nor `none`, is refused before the key is added (`cross_site`). The path must start with one `/` and hold no `\`, `#` or control character, so the target is always the account's server (`upstream_url`). Only seven methods pass. The client follows no redirect and keeps no cookie (`crates/moqui-client/src/http.rs`), so the key goes to no other host; a redirect to the account's server is rewritten to the same path on the scheme's origin, matched by host and port with `http` and `https` alike, and any other `Location` is passed as it is. No setting turns TLS verification off: the requests use reqwest's rustls and the sockets the OS trust store. From the answer ten headers are dropped (`set-cookie`, `set-cookie2`, `connection`, `keep-alive`, `transfer-encoding`, `content-length`, `content-encoding`, `strict-transport-security`, `alt-svc`, `www-authenticate`) and every `access-control-*` one; every other header of the server's answer reaches the page, on both origins, `Clear-Site-Data`, `Service-Worker-Allowed`, `Refresh`, `Link` and a CSP with a script directive among them (`DROPPED_RESPONSE_HEADERS` in `proxy.rs`, `answer` in `scheme.rs`). The request signs in from its `login_key` header and carries no cookie, and the server checks no session token for a request that signs in from a key header ([CSRF](Attack-Surface-Web.md#csrf)); the proxy's cross-site refusal is the check. On the mobile app `scheme_fetch` takes the request's headers from the page, `Origin` and `Sec-Fetch-*` among them.

A `POST` to `/ChatKeys/storeKey` returns the passphrase of the page's chat store. The host keeps the server's answer in the key store, and when the server cannot be reached it answers the kept passphrase to a request on the shell's origin only. The offline answers and the passphrase are given for the page's account with or without a key, so a personal account that signed out keeps both until it is removed (its chat store keys go only with the account, `remove_account`).

## Links from the OS

The desktop app registers the schemes `mailto`, `tel`, `sip` and `org.moqui.desktop` (`plugins.deep-link` in `crates/moqui-desktop/tauri.conf.json`); `mailto`, `tel` and `sip` become the user's default only after the tray item "Make default for email and calls", which runs `xdg-mime default` with fixed arguments (`crates/moqui-desktop/src/os/handlers.rs`). Any local program or web page that opens such a link reaches the app.

| Link | What the app does | Code |
|---|---|---|
| `mailto:` | Opens `<comms root>/Inbox/Compose` with `to`, `cc`, `bcc`, `subject` and `body` from the link as query parameters. Other headers of the link (`attach`, `in-reply-to`) are dropped | `route`, `mail_params`, `crates/moqui-desktop/src/os/links.rs` |
| `tel:`, `sip:` | Opens `<comms root>/Calls/Dialer?number=<number>` | `route`, `call_number` |
| `org.moqui.desktop:/sso?code=…&state=…` | Taken only when an SSO sign-in is waiting and the link's `state` equals its state; otherwise logged and dropped | `sso_returned`, `crates/moqui-client-tauri/src/commands.rs` |
| `org.moqui.mobile:/sso?…` (mobile) | The same | `on_event`, `crates/moqui-mobile/src/lib.rs` |
| `org.moqui.mobile:/join?host=…&token=…` (mobile; browsable, so any web page or app sends one) | With an account on that host that is not the current one, makes it current (a reload of the shell); keeps `/join/<token>` for the shell, which shows the join page of that token; the person still presses Join | `crates/moqui-mobile/src/host.rs`, `join.rs` |
| A call link (mobile) | Taken only when it carries a nonce the native code made for the user's Answer or Hang up, once | `calls::link_of`, `native::take_link` (not read) |
| A dial link (mobile, `org.moqui.mobile:/dial?nonce=…`) | Taken only when it carries a nonce the native code made, once and within two minutes, for a number that came through Telecom to the app's calling account (`DialAccount.dialed`, from Telecom's binding of `CallConnectionService`, which only Telecom may bind: `BIND_TELECOM_CONNECTION_SERVICE`). The nonce stops a link sent to the activity by itself; it does not stop another app from choosing the number, since any app may place a call with that account (`placeCall`, `ACTION_CALL`). So the number (digits, `+`, `*`, `#` only) is only filled in on the Dialer, and the user presses Call once, which places it through the server's `place#PhoneCall` and its checks (for cost and fraud safety). The current account's Dialer, or the one account that can call; when several can and the current one cannot, the user picks which (`call_dial_choice`), and no account is switched without that pick. Numbers Android treats as emergency numbers never reach it (Telecom keeps them on the SIM) | `dial::nonce_of`, `native::take_dial_link`, `host::open_dial` |
| A room link (mobile, `org.moqui.mobile:/room?account=…&chatRoomId=…&eventSeq=…&sig=…`, a chat notification's tap) | Taken only when its `sig` is this app's: an HMAC-SHA256 of the account, room and message with a 32-byte key the app keeps in its key store (`app.link-key`), compared in constant time. It then opens the comms Chat screen at the room for an account signed in here (switching to it); another app's link opens nothing | `calls::room_link_of`, `native::room_link_taken`, `host::open_room_link` |

The comms root is, in order: a client account's server's; the file `comms-root` a node page wrote with `set_comms_root`; `comms@app-root`; `/qapps/BasicComms`. The page opens on the node's origin or, in client mode, in the shell or an app window of the current account.

A second launch of the desktop app sends its links to the first over the Unix socket `<config>/org.moqui.desktop/instance.sock`. The first instance sets the socket to mode `0600` after `bind`. A message is at most 64 KiB, must start with the line `moqui-desktop launch 1`, and each other line is used only when it parses as a URL of one of the four schemes (`crates/moqui-desktop/src/os/instance.rs`). What a local process of the same user can send is therefore the same links the OS hands over.

## Sign-in of an installed app

Password sign-in: the shell calls `client_sign_in`; the app posts to the server through `moqui_lib::remote_login` and keeps the device key, and sign-out calls the server's `revokeLoginKey` (`crates/moqui-client/src/login.rs`). SSO: `client_sso_start` makes a 48-byte random PKCE verifier and a 24-byte random state, opens the system browser at the server's `/sso/appLogin` with the S256 challenge, the state and the redirect `org.moqui.desktop:/sso` or `org.moqui.mobile:/sso`, and keeps one pending sign-in. The hand-back link is matched on its state, refused when stale, and its code is sent with the verifier to `/sso/appToken` (`crates/moqui-client/src/sso.rs`). The verifier stays in the app. The server's `/sso/appLogin` and `/sso/appToken` routes are in [Attack-Surface-Routes.md](Attack-Surface-Routes.md).

The server address the user types decides where the password and the device key go. `base_url` accepts `https` to any host and `http` only to `localhost`, `127.0.0.1` and `[::1]`.

## The terminal client

`moqui tui --server <base>` (`crates/moqui-host/src/tui_remote.rs`) is a client on the user's machine; how it signs in and keeps its key is in [The `moqui tui` command](Attack-Surface-SSH.md#the-moqui-tui-command). Its requests go through reqwest's rustls, and its `/notws` socket through rustls with the web PKI roots and a check of the server's name. It keeps cookies in memory only, follows no redirect, and reads a response body whole, with no size limit. `moqui tui --server` and `moqui tui` in process share the TUI's local loop (`crates/moqui-tui/src/ui/run.rs`). What the server, or whoever writes the server's data, reaches there:

- A file on disk. A screen or transition answered as an attachment, the first screen of a session included, is saved with no question into `XDG_DOWNLOAD_DIR` or `~/Downloads`, by the local loop and by `--agent` (`save_download`). The name keeps only letters, digits, `.`, `-` and `_`, and never replaces a file; with no name left the file is `export.` and the second part of the `Content-Type` when that is one to ten ASCII letters and digits, else `export.bin`, so no name holds a separator, a Windows `\` included (`download_name`, SEC-CLI-84). A report export is saved only as CSV, XLSX, PDF or PNG. The SSH and browser-terminal sessions never save.
- The user's terminal. The TUI drops controls from every string of a screen model as it is parsed (`clean_value`), not from option labels, menu titles, transition messages, notification titles, palette search hits, a component's JSON, server error text or the Assist thread, nor, in `moqui tui` with `--serve`, from the log pane, which holds every log line of the serving process (`crates/moqui-host/src/tui_cmd.rs`). The painter puts a control character in a cell. The local loop writes the screen through Revue's writer, which prints each cell's character as it is, with a cursor move before the next cell; only the SSH `apps` channel and the browser terminal go through the encoder, which writes a space instead ([Escape sequences](Attack-Surface-SSH.md#escape-sequences-from-application-data)). The text answers of `agent-apps`, `moqui tui --agent` and the LLM screen tool, and `--snapshot`, join the cells' characters with nothing between them (`crates/moqui-tui/src/ui/agent.rs`); the agent's JSON answer escapes C0 but not DEL or C1. OSC 8 is written only for an `http`, `https` or `mailto` link of the model, and Revue percent-encodes its control characters.
- The clipboard. A drag, a double or triple click, Ctrl+C or Ctrl+X copies the selected cells' characters as they are, control characters included, as OSC 52 (`selected_text`, `copy_text`); no text from the server starts a copy, and the TUI never reads the clipboard.
- Memory: the calc grid draws and reads only the frozen rows that leave the terminal five rows of the others (at most 200 of a sheet's `frozenRows`) and the frozen columns that fit half its width (at most 100 of `frozenColumns`; one not drawn scrolls as the others do) on every frame, whatever the workbook says (`frozen_counts`, `crates/moqui-tui/src/components/calc.rs`, SEC-CLI-83); the server's layout passes the workbook's counts on as they are.
- Navigation. A link a component takes from its data (a timeline item's `url`, a tree row's `_open`, a calendar event's `open`, a board card's `open` with `{id}` and each `{name}` replaced by the row's value, not encoded, a report panel's `link` with encoded values) ends in `follow_url`, which goes to a path of the server or only shows a URL that holds `://` or starts `mailto:` (`crates/moqui-tui/src/session/mod.rs`). "Open in browser" opens nothing (`take_open` has no caller), so no program is started.

## `moqui-browser` and `moqui-embedded`

`crates/moqui-browser` is a library and a WebAssembly module that `scripts/wasm-build.sh` stages into a directory for a page to load; no route of the server serves it. ### The service worker

`/sw.js` (`runtime/components/base/webroot/screen/webroot/sw.js`) answers a `GET` on its own origin with no `Authorization` header from the cache `moqui-shell-v2` first, and otherwise fetches and keeps the answer, when the path starts with `/libs/`, or is a static file by its extension (script, style, map, font, image, wasm) with a `v` query parameter outside `/rest/`, `/rpc/`, `/apps/`, `/qapps/`, `/dav/`, `/git/`, `/xmpp-upload/`, `/s/`, `/u/` and `/r/` (`cacheable`). It keeps an answer only when it is a 200 of type `basic` whose `Cache-Control` names `public` and none of `private`, `no-store` or `no-cache` (`keepable`; SEC-CLI-02). Activating the worker deletes every other cache, `moqui-shell-v1` among them. A screen render carries `no-cache, no-store, must-revalidate, private` and is not kept. The server marks `public` its static files, versioned `.qvue` bundles and a page whose script sets it, none of them per user by the framework (`screen/static_files.rs`, `screen/mod.rs`), so the cache holds nothing private; it is not cleared at sign-out. A kept answer is not asked for again. A push shows a notification; a click on it focuses or opens a window at the notification's link when that link is on the worker's origin, else at `/qapps`. `WebrootPush.js` registers `/sw.js` with scope `/` when push is on, which it is not in the desktop app (`pushOn` is false under `moquiDesktop`, `WebrootVue.qvt.js`); the shell's CSP allows one worker, by its exact path. On the apps' `moqui-app` origin nothing refuses a service worker a server's own script registers ([The app schemes](#the-app-schemes-and-what-reaches-the-server)).
