# Attack surface: git hosting and pipelines

Git over HTTP and SSH, Git LFS, repository hosting, and pipelines with their runners. This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## Git

`ANY /git/{*rest}` when `git` is compiled; on a `<public-site>` host, git's smart HTTP and LFS requests at a page's URL (`/<path>/info/refs?service=...`, `/<path>/git-upload-pack`, `/<path>/git-receive-pack`, `/<path>.git/info/lfs/...`, the first segment not a framework route) are served as the same request under `/git/`. Web protection checks such a request by the path it came with (client rules, methods, path rules, rate limits) and its path rules again by the `/git/...` path it is served at, so `<path-rule action="deny" path="/git/**"/>` stops git at page URLs too; a rate limit whose path is only `/git/**` does not count them, which is why `git-anonymous` names the page forms. `git-server` defaults: `allow-http="false"`, `max-concurrent="4"`, `max-queued="16"`, `max-request="67108864"`, `max-push-size="2147483648"`, `max-object-size="536870912"`, `idle-timeout="120"`, `lfs-max-object-size="5368709120"`, `webhook-private-network="false"`. The route is exempt from the webapp request timeout.

From `docs/interfaces/Git-Hosting.md`: HTTP Basic with the username and the password, or an access token or an app password as the password. An account with a second factor needs the token or the app password. The account password cannot finish that login. `Authorization: Bearer` and the `api_key` header also work. A request with no credentials is checked as no user: it reads (clone, fetch, LFS download) only a repository an `ALL_USERS` authorization record lets anyone view, which the framework's own data never does (Mantle's check does, for a public repository), and is 401 for everything else: a repository that is not there, a path that is not one, a push (refused before any record is asked), an LFS upload or verify, and every LFS locks request. The 401 is the same, status, headers and body, whatever the reason. It is not an `auth-failure` event; a header that is there and is not usable credentials (another `Authorization` scheme, Basic that does not decode, an empty `api_key`, a bad LFS token) is one, and is 401 on a public repository too, so a made-up header does not pass the `git-anonymous` limit for free. Requests with no credentials run at most `git-server` `anonymous-max-concurrent` git jobs at once (half of `max-concurrent`, at least 1); one more is 503 with `Retry-After`. Credentials are accepted only over HTTPS (the TLS listener, or `X-Forwarded-Proto: https` from a believed proxy), from loopback, or when `allow-http="true"`.

Authorization is artifact type `AT_GIT_REPOSITORY`, name `repositoryId`; a URL names a repository by its id (one segment, exact), its `repositoryPath` (segments of letters, digits, `.`, `_`, `-`, none starting with `.` or `-`; unique and looked up without case, by `repositoryPathKey`), or a path it had before a rename, until another repository takes that path. A path of one segment is only ever a repository's own id, so no path shadows an id. The framework has no namespace ownership: `set#GitRepositoryPath` needs the update right on the repository and nothing more, and the application decides who may rename and when a left path may be retaken. The server refuses to serve when that type's authorization is not enabled. VIEW is clone and fetch. CREATE is a new branch or tag. UPDATE is a fast-forward. DELETE is a force-push, a deleted ref, or settings. No view is 404 with credentials (401 without). View without push pushes only `refs/for/<branch>` (below), each other ref refused; it is 403 for the whole push with `review-push="false"`, and for a drive's viewer. Only `refs/heads/`, `refs/tags/` and `refs/for/` can be pushed. The default branch cannot be deleted. Seed `GitRepositories` is always-all for `ADMIN`. A `remote` repository is a read-only mirror. LFS is under `/git/<path>.git/info/lfs`; with `git-server` `lfs-upload-check-service` set, that service is asked before objects new to a repository are accepted (an application's quota) by the batch, by each upload and by a write of an LFS-tracked file through Moqui, and its errors refuse with 403; it is asked again once an object is stored, and a refusal then takes the object back, so uploads that run at once do not pass a limit together. Webhooks are not sent to loopback, private, or link-local addresses unless `webhook-private-network="true"`.

Outbound pushes and fetches (`docs/interfaces/Git-Hosting.md`, Push mirrors and Fetching refs): a `GitRepositoryMirror` is stored, read, pushed and deleted with the delete right on its repository, as its webhooks and branch rules are (or authorization off), and `fetch#GitRefs` needs the same. A mirror's URL carries no credential (one with a user or password in it is refused; an SSH URL may name only a user); the credential is a field of its own, kept encrypted, never returned (`hasCredential`), sent only as basic authorization to the host the URL names (no redirect is followed) or as the SSH login, and taken out of every error, `lastError`, problem and notification (as is any `Basic` header value). A change of where it goes (the URL's scheme, host or port, the user, the host key) needs the credential again in the same call, or `clearCredential`, so an editor does not send a stored credential to a host of their own; the credential rides on the right of who gave it (`createdByUserId`), and a push of a mirror whose giver no longer has the delete right pauses it (`enabled` N, `lastError` says why) without using the credential, unless it was stored with authorization off (`storedAuthzDisabled`). The same holds for `fetch#GitRefs`'s password, which is not stored. Both follow the webhooks' address rules: no loopback, private or link-local address (written out or resolved) and no plain `http://` unless `webhook-private-network="true"`; an SSH mirror needs a pinned host key and connects to an address the one public-address check resolved (no second resolution, so no DNS rebinding). A mirror's patterns cover branches and tags only, so a hidden merge request's head or a framework ref is never pushed out; each push and each fetch asks `outbound-check-service` (`push-mirror`, `fetch`), so an application that hides or suspends a repository stops them. A fetch writes only `refs/heads/`, `refs/tags/` and `refs/merge-requests/` (never `refs/moqui-*`), its objects held to `max-object-size` and checked whole as a push's, a branch or tag through the branch rules and the pre-receive rules. With authorization on it is held to a push's reachability rules: its haves are the refs a reader reads (never a hidden head or a framework ref, whose ids are not told to the remote), a ref's new value it did not bring is the caller's (an id the store holds that is not is asked of the remote as one it does not, and refused when the remote does not send it, so the answer tells nothing of the store), and the pack's parents, entries and thin bases are what the caller reads; a merge request's head is set only as the first head of an imported merge request, which records it. An imported merge request's `headCommitId` is a commit its administrator reads, and its importer (`importedByUserId`) counts as its author for approvals. Limits: 32 MiB of refs, a 1 MiB push report, an 8 GiB fetched pack, 30 minutes a transfer; one push of a mirror at a time across a cluster; failures back off from 1 minute to 6 hours.

The services an application's code pages call check the same type: `get#GitBlame` and `get#GitArchive` need view, read trees and history that whoever may push made, and are refused past their `git-server` limits. Blame: `blame-max-bytes` (1 MiB), `blame-max-lines` (50,000), `blame-max-commits` (10,000), `blame-max-diffs` (2,000 comparisons, each parent of a merge one) and `blame-max-seconds` (10, which cuts each comparison off). Archive: `archive-max-bytes` (256 MiB of content), `archive-max-files` (50,000 entries, every tree read counted, so a tree naming one subtree many times ends), 64 directories deep with no recursion, `archive-max-concurrent` (2 at once on a node) and `archive-max-disk-bytes` (2 GiB kept). An archive is one file for each (repository, commit, path, format) under `runtime/tmp/git-archive`, written under another name and renamed, shared by the callers that ask for it, kept six hours from its last use. A pushed tree's names are not trusted: an entry named `.`, `..`, `.git` (any case), empty, with `/`, `\` or NUL, or not UTF-8, and a name twice in one directory, refuses the archive; a link is stored as a link entry and never followed, and one whose target is absolute or climbs out of the archive is left out. Neither service is capped by client: a page that offers them to visitors rate limits its route. `get#GitRepositoryUsage` needs view, leaves out what the caller may not view, and is for an application's quota code (it reads object rows or walks a directory per repository). `delete#GitRepository` needs delete, the right that also forces a push, so an application wraps it in its own rule; with authorization off it deletes for any caller. It marks the repository as going in a committed step that every push and write reads again before storing, deletes the rows in its transaction, and after the commit removes the directory and deletes the id's rows once more. The directory goes only when, with links followed, it is under the runtime directory, is a bare repository (`HEAD` and `objects/`) and is no other repository's directory, parent or child. It cannot be undone. `find#UserSshKeys` and `find#UserAccessTokens` answer the current user's rows only, with no public key, token or stored hash.

Push to review, forks and reads by id (`docs/interfaces/Git-Hosting.md`): with `git-server` `review-push` (default `true`) an account that may only view a repository pushes `refs/for/<branch>`, which stores its commits in that repository and opens or updates its own merge request; it writes no ref a reader reads but the merge request's head (`refs/merge-requests/<n>/head`), uploads no LFS object, and is capped by `review-max-push-bytes` (50 MiB a push; no more than that is read from such an account's connection) and `review-max-account-bytes` (200 MiB an account a day over all repositories, from `GitUpdate.packBytes`). A pre-receive gitECA rule sees `forReview`, the target branch, the user and `packBytes`, and is where an application puts its own gate (a confirmed address, a daily count); `commit#GitFiles` with `asProposal` is the same by a service, under the same caps and the same pre-receive rules. With authorization disabled only: `fileLocationMap` (reads a resource location as the server), `authorName` and `authorEmail`, `bypassBranchRules`, `propose#MergeRequest`, `sync#MergeRequestHead`, and the `mergeRequestNum`, `pushedForReview`, `headCommitId`, `reviewTopic` and `hidden` of `create#MergeRequest`, the `localPath` of `fork#GitRepository`. A fork (`fork#GitRepository`, view of the source) shares its network's objects: one set of `GitObject` rows for a `db` network, the parent's directory through `objects/info/alternates` for a `local` one. Because a store then holds what its repository's readers may not read (another fork's commits, a merge request held for moderation, hidden by `set#MergeRequestHidden` or from the start with `review-start-hidden`), no read goes by what the store has. A commit is read by id through the `get#Git*` services, wanted by id in a fetch, restored or checked out by id, only when a branch, a tag or the head of a merge request that is not hidden reaches it; the start of an id is looked up among those commits alone. The one exception is a repository in no fork network, none of whose merge requests is or ever was hidden (`GitRepository.reviewHiddenDate`, kept from the first one on), on a server without `review-start-hidden`: there a user with the update right (or a service with authorization disabled) also reads the commits its refs have left. The row is read when asked, so a first fork or a first hidden merge request made on another node counts at once. A push is checked for everything it names and does not bring: a ref's new value, a parent (also one a client declares shallow, which must be there), a tag's target must be such a commit, or a tag object a readable tag names; a tree, a blob (also as a ref's new value, for an account with a push right) and the base of a thin pack's delta must be a file of a commit the pusher reads (for an account with no push right: of the branch the review is for, of its own review heads, or of a commit the push builds on). An id that is not in the store and one that is another's are refused alike (the same words, report and push log row, before the ref's name and the account's rights are looked at), and a fetch acknowledges a `have` only for a commit the readable refs reach, so neither tells which ids a store holds. For an account with no push right the server's work is bounded: `review-max-commands` (8) commands, shallow lines and options in `review-max-request-bytes` (64 KiB), `review-max-built-on` (8) commits built on, `review-max-trees` (20,000) trees read, and `review-max-refused` (30) refused pushes for review or proposals an hour per node before the next are refused unread (`GitReviewRefusals`); an account that may push sends at most `push-max-commands` (100,000) commands in `push-max-request-bytes` (16 MiB). `commit#GitFiles` builds its objects in memory and stores them only once the change may be made, so a refused proposal stores nothing. The heads are not advertised and a hidden one is not fetched. `find#GitUpdates` gives an account without the update right no remote address, no object id that no ref reaches, no rule error, no text of a refusal, and no count of the log. A hidden merge request is changed and reviewed (`update#`, `close#`, `reopen#MergeRequest`, `set#MergeRequestReviewers`, `submit#MergeRequestReview`, `get#MergeRequestApprovals`) by its author or with authorization disabled only, and a repository's webhooks are sent nothing of it until it is shown (then `opened`). `get#GitCommitStatuses` and `create#GitCommitStatus` (the two git services under `/rest`) answer for a commit only when the caller reads it by id; `includeHidden` is honoured with authorization disabled only. The reached commits are a set in memory per repository and node (`reach-max-commits`, 1,000,000; at most 128 repositories, least recently used first out), read from the refs again at most every two seconds for a hit and always for a miss. A merge request from a fork needs the update right on the fork, follows its branch only while its author has that right, and is detached by the fork's owner (`detach#MergeRequestSource`) or by the fork's deletion; the LFS objects it brings pass the target's upload check. `create#GitCommitStatus` refuses the contexts under `reserved-status-contexts` (none by default; mr-mantle sets `agreement/,ci/,deploy/`) unless called with authorization disabled. `merge#MergeRequest` needs the update right and merges exactly the commit whose approvals and checks it counted, by its id (not a branch or tag of that name; `expectedHeadCommitId` refuses a head the caller did not see), and deletes a fork's source branch only for a caller with the delete right on the fork (or `forceDeleteSourceBranch` with authorization disabled). The gitECA pre events run, with the new commits, their authors and the calling user, for every way a branch moves (a push, a merge, `commit#GitFiles`, `create#GitRef`, a `git://` write, an import, a mirror's fetch), so an application's rule on them cannot be passed by choosing another way in; a rule names `source="push,fetch,import,write"` to hold for all. `queue#GitWebhookEvent` and `queue#MergeRequestEvent`, whose events are signed with the webhooks' secrets, need the update right on the repository or authorization disabled. A repository with forks is not deleted. The head ref of a merge request closed unmerged is deleted after `review-ref-retention-days` (30). `get#GitCommitRefs` reads at most `contains-max-commits` (200,000) commits a call, and `get#GitCommitPushers` at most 500 ids by key, of commits the caller reads.

SSH git is a channel on the SSH server, not this route. See [SSH and the TUI](Attack-Surface-SSH.md#ssh-and-the-tui).

## Pipelines

From `docs/interfaces/Pipelines.md`. The CI engine never runs a step on the server: a job is a container the server starts on another machine through an `InstanceHost` (the Docker Engine API over a Unix socket, HTTP, or HTTPS with a client certificate whose key is an encrypted field), or a registered runner's. What it adds to the surface:

- **The pipeline file** (`ci.xml`) is read from a pushed commit, by whoever may push or open a merge request. The reader is strict and bounded (`git-ci` `max-file-bytes`, `max-pipelines`, `max-jobs`, `max-matrix`, `max-steps`, `max-timeout-minutes`); names are letters, digits, dot, dash and underscore; paths cannot leave the checkout. Nothing of the file is run or expanded on the server: a step's command, an image name and a cache key are text handed to the runner. The image must match a pattern of the pool's `allowedImages` (none by default).
- **The runner REST**, `ANY /ci/runner/{*rest}` when `git` is compiled. No session, cookie or user credential: a bearer token, taken only where git takes credentials (HTTPS, a believed proxy's, loopback, or `git-server` `allow-http`). A **job token** (32 random bytes, stored as its SHA-256, good while its job run is `running` and until the job's time limit, dead once the job ends) reaches only `jobs/<its job run>/...`: the job, log lines, step results, uploads, cache downloads and the result. The job run in the path must be the token's (403); the token of a job that ended or passed its time is 410 Gone, which is no authentication failure (a runner retrying after a cancel, on any cluster member), and a malformed or unknown token is 401, counted for web protection (an unknown well-formed one toward the `ci-token-failure` ban, a malformed one toward `auth-failure`'s). A **pool token** only registers a runner (counted per pool, `runner-max-registrations-per-minute`, and at most `max-runners-per-pool` active runners, so a leaked one mints only so many runner tokens for the list of good CI tokens) and a **runner token** only asks for a job of its pool. Requests are counted per job and per runner once the token is found good (`runner-max-requests-per-minute`), and then pass the per-client rate limits ([web protection](Attack-Surface-Web.md#web-protection) `ci-token-failure`); a JSON body is at most `max-log-batch-bytes`; an upload streams to a content blob and is cut at its kind's limit (`max-artifact-bytes`, `max-report-bytes`, `max-cache-bytes`), at most `max-artifacts` of a job. Exempt from the request deadline, as git is. A host whose root screen refuses the framework's routes answers 404 here too.
- **A job token on the git server** reads its job's repository at its job's commit and nothing else: upload-pack only, one advertised ref at that commit, every `want` that commit, a shallow fetch of at most `max-fetch-depth`. The token of a job that ended is 410, no authentication failure, as on the runner REST; an unknown one is 401 and counted. The repository is the run's (the target of a fork's merge request, never the fork), and the commit must still be the repository's to give: one the head ref of the run's merge request reaches (`refs/merge-requests/<n>/head`; a hidden merge request's head is fetched by its job's token and by nothing else), or for another run one a ref the repository's readers read reaches. A commit its ref has left (a forced branch, an amended push for review, a released head) is refused in a fork network and in a repository that has had a hidden merge request (elsewhere every commit of the store was once a reader's), and the only `have` acknowledged is that commit, so the token is no way to read, or to probe for, what else a fork network's store or a store with a hidden merge request holds. It logs no user in, so it reaches no service, screen or other route, and it cannot push. A step runs as the runner's user and could read the token from the runner's process: it gives the step nothing the job did not have.
- **What queues a run.** The framework's post-receive gitECA rule (a branch or a tag moved by a push or a write; a push to `refs/for/<branch>` and a merge request's head ref queue no push pipeline) and its service ECA rule on `queue#MergeRequestEvent`, which does not run after a refused event (a caller without the update right). `queue#PushRuns` and `queue#MergeRequestRuns` are refused without authorization disabled, so no caller names the user or the commit of a run. The file is read at the event's commit as the system reads, a hidden merge request's head too; in a fork network, and in a repository that has had a hidden merge request, a commit no ref of the repository reaches any more has no pipeline, so a run (or a re-run of an old one) is no way to read it.
- **Hidden runs.** The run of a hidden merge request's head is hidden (`GitPipelineRun.hidden`): its log, artifacts and reports, which are that head's files, are read by the user who pushed it and with authorization disabled and `includeHidden`, not by a user with the update right, who therefore does not approve it either (the application does). `set#MergeRequestHidden` hides and shows a merge request's runs with it.
- **Untrusted code.** A run for a merge request from a fork, one pushed for review or one detached from its source, whoever opened it, or caused by an account without the update right, is untrusted: no secrets, caches read and never written (so it cannot poison a later trusted run), and only those no protected run wrote (which a build with secrets may have filled), only a pool marked for untrusted runs (a trusted run never shares its hosts), whose images are never pulled on demand, and it waits for `approve#PipelineRun` unless the application's `run-check-service` allows it. That service may lower a run's trust and never raise it, and is asked again before a job of an ended run runs again; a refused or never approved run is not run again. A re-run of an untrusted run stays untrusted whoever asks for it. A server whose accounts sign themselves up sets `run-check-service`: with none, any account's push to its own repository is a trusted run.
- **Secrets** (`GitCiSecret.secretValue`, encrypted) are given only to a job of a trusted run whose scope is met (a protected branch or tag: one a branch rule keeps to a push group or to merge requests; or the job's environment, when the environment allows the run: a protected ref or a branch of its `allowedRefs`, never a merge request's run, an approved one with `approvalRequired`), only over the runner REST and never in a container's definition, and are masked in the log as it is stored. They are managed by a repository's maintainers (the delete right), not by a developer who pushes, and a secret moved to another scope or environment needs a new value. No service reads a value back. A step that has a secret can still send it elsewhere: the protection is that only reviewed files run with one.
- **The container**, and each of its service containers (at most `max-services`, their images allowed by the pool as the job's is), has no privilege, no capabilities, `no-new-privileges`, no host path or socket, no published port, a non-root user (root in no form; with `container-user="image"` only an image whose USER is a numeric uid other than 0, since a name may be uid 0 in the image), an init that reaps orphans, a read-only root with sized tmpfs mounts (the working directory on one, or on the root filesystem the pool's `diskMb` sizes), and the pool's CPU, memory and swap, pid and disk limits and network mode. What it may reach on the network is the host's to limit (`egressRule` names a network, never the host's or another container's; the engine makes no rules): it must reach the server's URL, and should reach nothing else of the server's network. A job with services gets a network of its own, internal unless the pool's egress is `bridge`, with the job also on the pool's network: a service reaches nothing outside. Names carry the server's id and removals touch only containers with the server's label, so servers sharing a host do not touch each other's; the cleanup leaves a container made after it read the running jobs. A registered runner keeps its machine between jobs: its pool is one owner's on a server with tenants, and `moqui ci-run poll` kills what a job left running of the runner's user. The server holds the host's API credentials, which are root on that host: a compromised server owns its runner hosts, not the other way round, as long as runners are other machines.
- **Statuses** `ci/<pipeline>/<job>` are written by the engine through `create#GitCommitStatus`, with authorization disabled and `includeHidden` (so a service ECA rule on it runs for them, and a hidden head has its checks); their description is plain text, with `<` and `>` left out of what a pipeline file's error, a runner or the application's check said. A user with a push right can still post a status of any context unless the application reserves `ci/` (`git-server` `reserved-status-contexts`), which a branch rule that requires a `ci/` check needs.
- **Artifacts and reports** are a job's output, whatever its commit's scripts wrote, so they are never the application's own pages: `send#RunArtifact` sends one as an attachment, and inline (`inline`) only a passive type; an HTML, SVG, XML or JavaScript file only with `inlineActive` as well, and every inline one with `Content-Security-Policy: sandbox` (no `allow-same-origin`, no `allow-scripts`) and `X-Content-Type-Options: nosniff`, as `ec.web.sendResourceResponse` and a PASS download send every inline file that is not the application's own, and either sends a file of an active type as an attachment even when asked inline (a PDF is not sandboxed: browsers do not show one in a sandbox). Their `ci-artifact://` locations are read with `get#RunArtifact`'s check; a PASS authority download opens a `ci-artifact://` location its authority service answered with authorization off (that service checked the caller, the client never names a location, and a hidden run's file is read only so), and any other answered location with the call's own authorization.
- **Deployments** (`request#`, `decide#`, `cancel#`, `find#GitDeployments`, `get#GitDeployment`). Asking needs the update right, a branch that is protected or in the environment's `allowedRefs`, and its head; the environment's pipeline runs with the `deploy` event through the run check like any run. The pipeline file is read from the deployed commit, so whoever pushes to the branch chooses the tests that pass it: a branch no rule protects (named by `allowedRefs` only) therefore always waits for an approver, whatever the environment's `approvalRequired`. Approval is `decide#GitDeployment` only, by the environment's approver group (or a maintainer), never the requester; an approval of the run (a job in the environment) does not approve the deployment. The environment's token is the secret its target issued: encrypted, at least 32 characters, never read back (`hasToken`), never sent (it signs the attestation, [Component deploy](Attack-Surface-Tools.md#component-deploy-and-conf-reload)) and never in `errorText`, a status or a notice. Only maintainers (the delete right) store an environment, so a developer cannot point one at a host of their own, and only they read its `targetUrl` and `cloneUrl` (`find#CiEnvironments`); a `cloneUrl` with a user or password in it is refused. The deploy step posts to `<targetUrl>/rest/s1/moqui/components/deploy` only: `https`, or `http` to a loopback IP literal; a loopback, private or link-local target (written out or resolved) only with `git-ci` `deploy-private-network="true"`; no redirect; `deploy-timeout-seconds`; 1 MiB of answer; the outbound check (`deploy`) asked first. What the target answered on a failure is in `errorText`, which `get#` and `find#` answer to a maintainer only; the public status `deploy/<environment>` says only how it ended. A repository the caller does not view is not found, with its deployments. Statuses `deploy/<environment>` are the engine's; reserve them with `reserved-status-contexts="ci/,deploy/"`.
- **Delete.** `delete#GitRepository` removes the engine's rows of the repository with it (runs, jobs, logs, uploads, secrets, environments, deployments, schedules) and stops its running jobs, so no job token or secret outlives its repository; a fork's runs are its own.
- **Services** (`org.moqui.git.GitCiServices`): reads follow view of the repository, and a hidden merge request's run only with authorization disabled; cancel, retry, run and approve need update; a repository's secrets and environments need delete (a maintainer); an owner's, and `includeHidden`, need authorization disabled. The runner pool services (`find#`, `store#`, `delete#RunnerPool`, `create#RunnerPoolToken`, `revoke#Runner`) need the `GIT_CI_ADMIN` permission or authorization disabled. Pool tokens expire (`pool-token-days`), a new one can revoke the runners the old one registered, and a revoked runner's token is refused.
