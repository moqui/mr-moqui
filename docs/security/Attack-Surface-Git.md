# Attack surface: git hosting and pipelines

Git over HTTP and SSH, Git LFS, repository hosting, and pipelines with their runners. This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## Git

`ANY /git/{*rest}` when `git` is compiled; on a `<public-site>` host, git's smart HTTP and LFS requests at a page's URL (`/<path>/info/refs?service=...`, `/<path>/git-upload-pack`, `/<path>/git-receive-pack`, `/<path>.git/info/lfs/...`, the first segment not a framework route) are served as the same request under `/git/`. Web protection checks such a request by the path it came with (client rules, methods, path rules, rate limits) and its path rules again by the `/git/...` path it is served at, so `<path-rule action="deny" path="/git/**"/>` stops git at page URLs too; a rate limit whose path is only `/git/**` does not count them, which is why `git-anonymous` names the page forms. `git-server` defaults: `allow-http="false"`, `max-concurrent="4"`, `max-queued="16"`, `max-request="67108864"`, `max-push-size="2147483648"`, `max-object-size="536870912"`, `idle-timeout="120"`, `lfs-max-object-size="5368709120"`, `webhook-private-network="false"`, `max-webhooks="20"`, `max-mirrors="10"`, `queue-pass-seconds="300"`, `queue-pass-gap-seconds="300"`, `merge-requests-max-page="100"`, `merge-requests-max-repositories="500"`. `max-request` (upload-pack) and `max-push-size` (receive-pack) bound the HTTP request body as sent and as inflated, and an SSH command's input ([Pushed packs and request limits](#pushed-packs-and-request-limits)). The route is exempt from the webapp request timeout.

From `docs/interfaces/Git-Hosting.md`: HTTP Basic with the username and the password, or an access token or an app password as the password. An access token is scope `git` (`UserLoginKey.scope`): git over HTTP (`authenticate_with`, `login_user_key_for(key, "git")`) and the git REST (`/rest/s1/moqui/git/...`, `/rest/s1/moqui/hosting/...`) take it, and the web, the rest of REST, sockets, A2A and PASS pages refuse it (plans/Security-Review.md SEC-PFS-61, fixed). An app password opens no git over SSH ([SSH](Attack-Surface-SSH.md)). An account with a second factor needs the token or the app password. The account password cannot finish that login. `Authorization: Bearer` and the `api_key` or `login_key` header also work. A request with no credentials is checked as no user: it reads (clone, fetch, LFS download) only a repository an `ALL_USERS` authorization record lets anyone view, which the framework's own data never does (Mantle's check does, for a public repository), and is 401 for everything else: a repository that is not there, a path that is not one, a push (refused before any record is asked), an LFS upload or verify, and every LFS locks request. The 401 is the same, status, headers and body, whatever the reason. It is not an `auth-failure` event; a header that is there and is not usable credentials (another `Authorization` scheme, Basic that does not decode, an empty `api_key`, a bad LFS token) is one, and is 401 on a public repository too, so a made-up header does not pass the `git-anonymous` limit for free. Requests with no credentials run at most `git-server` `anonymous-max-concurrent` git jobs at once (half of `max-concurrent`, at least 1); one more is 503 with `Retry-After`. Credentials are accepted only over HTTPS (the TLS listener, or `X-Forwarded-Proto: https` from a believed proxy), from a client on this machine, or when `allow-http="true"` (`crates/moqui-host/src/git_http.rs` `secure`, the host's `http::secure_transport`). Behind a believed proxy the client is the address the proxy names in `client-ip-header`, never the loopback socket peer, and a loopback client an edge node names is not local. A request that is not secure gets no login challenge: what would be a 401 (git, LFS) is 403 "this needs a sign-in, which is taken only over HTTPS", with no `WWW-Authenticate` or `LFS-Authenticate`, so git does not send a password over plain HTTP; an anonymous clone of a public repository over plain HTTP still works. Credentials over plain HTTP (403), an `Authorization` header in no form the server takes, or an empty `api_key` (401, a failed sign-in) are answered by the host before the request takes a git pool worker (`moqui_git::server::early_refusal`, `git_http.rs` `early_answer`), even when the git server is off.

Authorization is artifact type `AT_GIT_REPOSITORY`, name `repositoryId`; a URL names a repository by its id (one segment, exact), its `repositoryPath` (segments of letters, digits, `.`, `_`, `-`, none starting with `.` or `-`; unique and looked up without case, by `repositoryPathKey`), or a path it had before a rename, until another repository takes that path. A path of one segment is only ever a repository's own id, so no path shadows an id. The framework has no namespace ownership: `set#GitRepositoryPath` needs the update right on the repository and nothing more, and the application decides who may rename and when a left path may be retaken. The git server (smart HTTP, SSH, LFS) refuses to serve when that type's authorization is not enabled, and so do the `org.moqui.git` services and the REST over them for a call with authorization on (`provider_and_id`). The default conf sets it on. When the type gives a signed-in user no right, a drive that holds the repository is asked ([A drive's members](#a-drives-members)). VIEW is clone and fetch. CREATE is a new branch or tag. UPDATE is a fast-forward. DELETE is a force-push, a deleted ref, or settings. No view is 404 with credentials (401 without). View without push pushes only `refs/for/<branch>` (below), each other ref refused; it is 403 for the whole push with `review-push="false"`, and for a drive's viewer. Only `refs/heads/`, `refs/tags/` and `refs/for/` can be pushed. The default branch cannot be deleted. Seed `GitRepositories` is always-all for `ADMIN`. A `remote` repository is a read-only mirror. LFS is under `/git/<path>.git/info/lfs` ([Git LFS](#git-lfs)); with `git-server` `lfs-upload-check-service` set, that service is asked before objects new to a repository are accepted (an application's quota) by the batch, by each upload and by a write of an LFS-tracked file through Moqui, and its errors refuse with 403; it is asked again once an object is stored, and a refusal then takes the object back, so uploads that run at once do not pass a limit together. Webhooks are not sent to loopback, private, or link-local addresses unless `webhook-private-network="true"` ([Webhooks](#webhooks)).

Outbound pushes and fetches (`docs/interfaces/Git-Hosting.md`, Push mirrors and Fetching refs): a `GitRepositoryMirror` is stored, read, pushed and deleted with the delete right on its repository, as its webhooks and branch rules are (or authorization off), and `fetch#GitRefs` needs the same. A mirror's URL carries no credential (one with a user or password in it is refused; an SSH URL may name only a user); the credential is a field of its own, kept encrypted, never returned (`hasCredential`), sent only as basic authorization to the host the URL names (no redirect is followed) or as the SSH login, and taken out of every error, `lastError`, problem and notification (as is any `Basic` header value). Any change of the URL (its path too), of `username` or of `hostKeyFingerprint` needs the credential again in the same call, or `clearCredential`, so an editor does not send a stored credential to a host of their own; the credential rides on the right of who gave it (`createdByUserId`), and a push of a mirror whose giver no longer has the delete right pauses it (`enabled` N, `lastError` says why) without using the credential, unless it was stored with authorization off (`storedAuthzDisabled`). The same holds for `fetch#GitRefs`'s password, which is not stored. Both follow the webhooks' address rule (no loopback, private, link-local, shared or reserved address, written out or resolved) and, unlike a webhook, also refuse plain `http://`, unless `webhook-private-network="true"`; an SSH mirror needs a pinned host key and connects to an address the one public-address check resolved (no second resolution, so no DNS rebinding). A `GitRepositoryMirror`'s patterns cover branches and tags only, so it never pushes a hidden merge request's head or a framework ref; the older `pushMirrorRefs` maps any ref it names ([The older push mirror](#the-older-push-mirror)). Each push of a mirror and each `fetch#GitRefs` asks `outbound-check-service` (`push-mirror`, `fetch`), so an application that hides or suspends a repository stops them. `fetch#GitRepository`, `import#GitRepository` and a component deploy's fetch use gitoxide's client instead: the URL's scheme and address are not checked, `outbound-check-service` is not asked, and `GitRepository.accessToken` is given to the host that asks for a credential ([Fetches through gitoxide](#fetches-through-gitoxide)). A fetch writes only `refs/heads/`, `refs/tags/` and `refs/merge-requests/` (never `refs/moqui-*`), its objects held to `max-object-size` and checked whole as a push's, a branch or tag through the branch rules and the pre-receive rules. With authorization on it is held to a push's reachability rules: its haves are the refs a reader reads (never a hidden head or a framework ref, whose ids are not told to the remote), a ref's new value it did not bring is the caller's (an id the store holds that is not is asked of the remote as one it does not, and refused when the remote does not send it, so the answer tells nothing of the store), and the pack's parents, entries and thin bases are what the caller reads; a merge request's head is set only as the first head of an imported merge request, which records it. An imported merge request's `headCommitId` is a commit its administrator reads, and its importer (`importedByUserId`) counts as its author for approvals. Limits over HTTPS: 60 seconds and 32 MiB for the refs, a 1 MiB push report, an 8 GiB fetched pack, 30 minutes a transfer. An SSH push reads the refs and the report within the same caps, has a 30-minute deadline for the whole command with at most 120 seconds for each wait, and keeps at most 64 KiB of the remote's stderr ([Push mirror transport](#push-mirror-transport)); one push of a mirror at a time across a cluster; failures back off from 1 minute to 6 hours. A repository has at most `max-mirrors` (10) mirrors (`service::mirror::store_mirror` refuses one more). A pass of the mirror queue (`run#GitRepositoryMirrors`, `mirror::push_due_mirrors_until`) starts pushes for `queue-pass-seconds` (300), leaves the rest due for the next run, and starts at least `queue-pass-gap-seconds` (300) after the last pass on the node (`moqui_git::queue_pass_may_start`); a push's own mirror is pushed at once.

The services an application's code pages call check the same type: `get#GitBlame` and `get#GitArchive` need view, read trees and history that whoever may push made, and are refused past their `git-server` limits. Blame: `blame-max-bytes` (1 MiB), `blame-max-lines` (50,000), `blame-max-commits` (10,000), `blame-max-diffs` (2,000 comparisons, each parent of a merge one) and `blame-max-seconds` (10, which cuts each comparison off). Archive: `archive-max-bytes` (256 MiB of content), `archive-max-files` (50,000 entries, every tree read counted, so a tree naming one subtree many times ends), 64 directories deep with no recursion, `archive-max-concurrent` (2 at once on a node) and `archive-max-disk-bytes` (2 GiB kept). An archive is one file for each (repository, commit, path, format) under `runtime/tmp/git-archive`, written under another name and renamed, shared by the callers that ask for it, kept six hours from its last use. A pushed tree's names are not trusted: an entry named `.`, `..`, `.git` (any case), empty, with `/`, `\` or NUL, or not UTF-8, and a name twice in one directory, refuses the archive; a link is stored as a link entry and never followed, and one whose target is absolute or climbs out of the archive is left out. Neither service is capped by client: a page that offers them to visitors rate limits its route. `get#GitRepositoryUsage` needs view, leaves out what the caller may not view, and is for an application's quota code (it reads object rows or walks a directory per repository). `delete#GitRepository` needs delete, the right that also forces a push, so an application wraps it in its own rule; with authorization off it deletes for any caller. It marks the repository as going in a committed step that every push and write reads again before storing, deletes the rows in its transaction, and after the commit removes the directory and deletes the id's rows once more. The directory goes only when, with links followed, it is under the runtime directory, is a bare repository (`HEAD` and `objects/`) and is no other repository's directory, parent or child. It cannot be undone. `find#UserSshKeys` and `find#UserAccessTokens` answer the current user's rows only, with no public key, token or stored hash.

Push to review, forks and reads by id (`docs/interfaces/Git-Hosting.md`): with `git-server` `review-push` (default `true`) an account that may only view a repository pushes `refs/for/<branch>`, which stores its commits in that repository and opens or updates its own merge request; it writes no ref a reader reads but the merge request's head (`refs/merge-requests/<n>/head`), uploads no LFS object, and is capped by `review-max-push-bytes` (50 MiB a push; no more than that is read from such an account's connection) and `review-max-account-bytes` (200 MiB an account a day over all repositories, from `GitUpdate.packBytes`). A pre-receive gitECA rule sees `forReview`, the target branch, the user and `packBytes`, and is where an application puts its own gate (a confirmed address, a daily count); `commit#GitFiles` with `asProposal` is the same by a service, under the same caps and the same pre-receive rules. With authorization disabled only: `fileLocationMap` (reads a resource location as the server), `authorName` and `authorEmail`, `bypassBranchRules`, `propose#MergeRequest`, `sync#MergeRequestHead`, the `hidden` of `create#MergeRequest`, the `localPath` of `fork#GitRepository`. With authorization disabled, or with `imported` and the delete right on the repository: the `mergeRequestNum`, `pushedForReview`, `headCommitId` and `reviewTopic` of `create#MergeRequest`, and the import's `statusId`, dates and `authorUserId` (another account as the author). A fork (`fork#GitRepository`, view of the source) shares its network's objects: one set of `GitObject` rows for a `db` network, the parent's directory through `objects/info/alternates` for a `local` one. Because a store then holds what its repository's readers may not read (another fork's commits, a merge request held for moderation, hidden by `set#MergeRequestHidden` or from the start with `review-start-hidden`), no read goes by what the store has. A commit is read by id through the `get#Git*` services, wanted by id in a fetch, restored or checked out by id, only when a branch, a tag or the head of a merge request that is not hidden reaches it; the start of an id is looked up among those commits alone. By name a revision reads only a branch, a tag or the head of a merge request that is not hidden, and `get#GitRefs` lists only branches and tags; the store's other refs (a mirror's fetch staged under `refs/moqui-incoming/` before its gate passes it) are neither read nor listed (SEC-GIT-12; `browse.rs`). The one exception is a repository in no fork network, none of whose merge requests is or ever was hidden (`GitRepository.reviewHiddenDate`, kept from the first one on), on a server without `review-start-hidden`: there a user with the update right (or a service with authorization disabled) also reads the commits its refs have left. The row is read when asked, so a first fork or a first hidden merge request made on another node counts at once. A push is checked for everything it names and does not bring: a ref's new value, a parent (also one a client declares shallow, which must be there), a tag's target must be such a commit, or a tag object a readable tag names; a tree, a blob (also as a ref's new value, for an account with a push right) and the base of a thin pack's delta must be a file of a commit the pusher reads (for an account with no push right: of the branch the review is for, of its own review heads, or of a commit the push builds on). An id that is not in the store and one that is another's are refused alike (the same words, report and push log row, before the ref's name and the account's rights are looked at), and a fetch acknowledges a `have` only for a commit the readable refs reach. A fetch's `shallow <id>` lines are held to the same rule: `Request::check` (`crates/moqui-git/src/server/upload.rs`) keeps only those a ref names or the readable refs reach and drops the others, as it would an id the store lacks, before `plan::shallow` reads them, so a commit the caller may not read is never unshallowed, its parents are not added to the wants, and the answer does not tell whether the store holds it (plans/Security-Review-Medium.md SEC-GIT-82, fixed). In a v0 negotiation with `multi_ack` each `have` that is not common walks each want's history back to the date of the oldest common have (`ok_to_give_up`), wants are not deduplicated, and nothing bounds the walks but the line budget; v2 walks once a request. For an account with no push right the server's work is bounded: `review-max-commands` (8) commands, shallow lines and options in `review-max-request-bytes` (64 KiB), `review-max-built-on` (8) commits built on, `review-max-trees` (20,000) trees read, and `review-max-refused` (30) refused pushes for review or proposals an hour per node before the next are refused unread (`GitReviewRefusals`); an account that may push sends at most `push-max-commands` (100,000) commands in `push-max-request-bytes` (16 MiB). `commit#GitFiles` builds its objects in memory and stores them only once the change may be made, so a refused proposal stores nothing. The heads are not advertised and a hidden one is not fetched. `find#GitUpdates` gives an account without the update right no remote address, no object id that no ref reaches, no rule error, no text of a refusal, and no count of the log. A hidden merge request is changed and reviewed (`update#`, `close#`, `reopen#MergeRequest`, `set#MergeRequestReviewers`, `submit#MergeRequestReview`, `get#MergeRequestApprovals`) by its author or with authorization disabled only, and a repository's webhooks are sent nothing of it until it is shown (then `opened`). `get#GitCommitStatuses` and `create#GitCommitStatus` answer for a commit only when the caller reads it by id; `includeHidden` is honoured with authorization disabled only. The reached commits are a set in memory per repository and node (`reach-max-commits`, 1,000,000; at most 128 repositories, least recently used first out), read from the refs again at most every two seconds for a hit and always for a miss. A merge request from a fork needs the update right on the fork, follows its branch only while its author has that right, and is detached by a user with the delete right on the fork, by the merge request's author (`detach#MergeRequestSource`), or by the fork's deletion; the LFS objects it brings pass the target's upload check. `create#GitCommitStatus` refuses the contexts under `reserved-status-contexts` (none by default; mr-mantle sets `agreement/,ci/,deploy/`) unless called with authorization disabled. `merge#MergeRequest` needs the update right and merges exactly the commit whose approvals and checks it counted, by its id (not a branch or tag of that name; `expectedHeadCommitId` refuses a head the caller did not see), and deletes a fork's source branch only for a caller with the delete right on the fork (or `forceDeleteSourceBranch` with authorization disabled). The gitECA pre events run, with the new commits, their authors and the calling user, for every way a branch moves (a push, a merge, `commit#GitFiles`, `create#GitRef`, a `git://` write, an import, a mirror's fetch), so an application's rule on them cannot be passed by choosing another way in; a rule names `source="push,fetch,import,write"` to hold for all. `queue#GitWebhookEvent` and `queue#MergeRequestEvent`, whose events are signed with the webhooks' secrets, need the update right on the repository or authorization disabled. A repository with forks is not deleted. The head ref of a merge request closed unmerged is deleted after `review-ref-retention-days` (30). `get#GitCommitRefs` reads at most `contains-max-commits` (200,000) commits a call, and `get#GitCommitPushers` at most 500 ids by key, of commits the caller reads.

SSH git is a channel on the SSH server, not this route. See [SSH and the TUI](Attack-Surface-SSH.md#ssh-and-the-tui).

Smithy, the application over these services (groups, confidential issues, the forks policy, access tokens), is in [Smithy](Attack-Surface-Apps-PASS-Forum-Smithy.md#smithy).

### Git LFS

Git LFS is `/git/<path>.git/info/lfs/` on the git pool (`crates/moqui-git/src/server/lfs.rs`): `POST objects/batch`, `GET` and `PUT objects/<oid>`, `POST verify`, and the locks API (`locks`, `locks/verify`, `locks/<id>/unlock`). A JSON body is at most 1 MiB. A batch is at most 1000 objects. An object is at most `git-server` `lfs-max-object-size`. An object is read only through a `GitLfsObject` row of the request's repository, and the rows are made only by an upload, by a `git://` write of content the writer supplied (`lfs_files.rs`), by a fork, which is given every row of its source (`fork.rs` `copy_lfs_rows`; view of the source), and by a merge request from a repository that holds the object (`share_lfs`); so an oid alone does not reach another repository's file. An upload must be the content of its oid (the blob writer refuses another hash), and an oid is 64 lowercase hex digits, never a path: the content is a database blob looked up by id. The upload body is read only after the write check, the size limit and the application's check. A read goes by the row and never by reachability: an object whose pointer is only in a commit no readable ref reaches (a removed branch, a hidden merge request that brought it) is sent to any viewer who names its SHA-256, without credentials on a repository anyone views. An object's size is tested on `Content-Length`, on the body as sent and in the writer, and the stored size must equal `Content-Length` when one was sent; the framework has no quota on a repository's count or total, which is the application's `lfs-upload-check-service`; a `git://` write of an LFS-tracked file is not held to `lfs-max-object-size`; the bytes of a refused or mismatched upload stay in blob storage until `gc#ContentBlobs`. Every LFS request opens the repository as an upload-pack does, and the write check (`may_write`) tests the token, the mirror kind and the push right, not `archived`: an archived repository still takes LFS objects and locks, and an upload does not read the repository's row again before it writes its own, as a push does.

Locks are per repository and unique by path. `GET locks` needs a signed-in user who views the repository and answers every lock's path and its owner's username; the page size is the caller's, with no ceiling. A user with a push right makes and removes locks, another user's only with `force` and the delete right. There is no limit on a repository's or a user's locks or on the length of a path, and each locks request lists every lock row of the repository.

Over SSH, `git-lfs-authenticate` and `git-lfs-transfer` are handled in `serve_ssh` before the git command is parsed; `git-lfs-transfer` is refused. When `git-server` `public-url` is not set, the batch answer's `href`s and the SSH answer are built from the request's own URL (`moqui_core::web::request_url`), and each `href` is paired with the `MoquiLfs` token. An entity error is answered to an LFS client as its text (500).

An action of a batch answered to a signed-in user carries `Authorization: MoquiLfs v1.<payload>.<signature>`. The payload is the username, the repository id, the operation, an expiry and a nonce. It is signed with HMAC-SHA256 under `git-server@lfs-token-key` (`git-server` `lfs-token-key`); a token signed under `git-server@lfs-token-key-previous` is accepted too. A batch token lasts 15 minutes. `git-lfs-authenticate` over SSH answers one for 60 minutes. A key that is empty or ends in `CHANGEME` issues and accepts none. A request with a token logs the token's user in with no password or second factor (`moqui_core::user::internal_login_user`, which refuses a disabled, locked or terminated account, one that must change its password and a display account; `gate_account` in `crates/moqui-core/src/user/login.rs`), must name the token's repository, and is authorized again as that user: view to read, a push right and an upload token to write. A request with no credentials reads a repository anyone may view and gets actions with no token. The token is not tied to the credential that obtained it: after an access token, an app password or an SSH key is revoked, a token it obtained is good until it expires, authorized as the user each time.

### A drive's members

When `AT_GIT_REPOSITORY` gives a signed-in user no right on a repository, the git server and the git services ask the drive that holds it (`ResourceDrive.repositoryId`): `org.moqui.resource.FileServices.get#DriveAccess` is called with authorization disabled (`crates/moqui-git/src/server/mod.rs`). Level 1 is view. Level 2 with `canWrite` is create and update. Level 3 with `canWrite` is delete. The answer is kept in the execution context by user and repository. A push for review (`refs/for/`) is by the repository's own rights only. The drive's levels are in [Drive services](Attack-Surface-Files.md#drive-services).

### Pushed packs and request limits

A pushed pack is indexed by gix-pack into a quarantine directory: `objects/incoming-<pid>-<n>` of a repository on disk, `runtime/tmp/git-<repositoryId>-incoming-<pid>-<n>` for a `db` one (`crates/moqui-git/src/server/pack_in.rs`). The pack's checksum and entries are verified and each object is hashed. One object and one delta result are held to `git-server` `max-object-size` (512 MiB). The indexer runs on `pack-threads` threads (2 when empty). Each pushed commit, tree and tag is parsed, and every object one names must be in the pack or readable in the store. Tree entry names, modes and `.gitmodules` are not checked, and blobs are not read. Each entry's header is read once, its kind and depth kept by offset (`pack_in::read_entries`), and a delta chain deeper than `git-server` `max-delta-depth` (4095) is refused (`GitDeltaTooDeep`); an account with no push right is held to `review-max-object-size` (32 MiB) and `review-max-delta-depth` (250) (`PackLimits::of`). There is no limit on the object count (plans/Security-Review.md SEC-GIT-05, fixed). An accepted pack is renamed into `objects/pack` or stored row by row (`db`), where an object over `db-large-object` is inflated into a content blob. A refused push removes its quarantine directory. Git gc makes a scratch directory in a repository on disk (`objects/gc-<pid>-<millis>`, `crates/moqui-git/src/gc/local.rs`), removed on drop. Nothing removes a quarantine, import (`git-import-*`) or scratch directory that a killed process left: gc lists only `objects/pack` and the two-hex object directories, and the only sweep at start is the archives'.

`max-request` (upload-pack) and `max-push-size` (receive-pack) bound the body as sent (`crates/moqui-host/src/git_http.rs`) and, for a `Content-Encoding: gzip` body, as inflated (`serve_http` wraps the decoder in `server::limited::Capped`, an error past the limit), and over SSH they bound a push's whole input (`serve_ssh`) and each round of an upload-pack conversation (`upload_v0`: the want phase and each flush of haves; `serve_v2`: each command), as HTTP bounds each request, so a long negotiation is answered and no round is larger than a request. Upload-pack counts its request lines (`upload::LineBudget`: `fetch-max-lines`, 1,000,000, each capability on a want line one, in `fetch-max-request-bytes`, 64 MiB; per round, as the bytes), else `GitFetchRequestTooLarge` (SEC-GIT-03, fixed). A v0 negotiation takes each want once, asks the readers about a stored commit they do not read once however often it is a have, walks the wants' history again only when a have adds a common commit, and reads at most `MOST_COMMITS_WALKED` (200,000) commits in those walks, past which it answers ready and sends the pack for the commits acknowledged (`upload::Negotiation`, SEC-GIT-83, fixed). The pack of an account with a push right is written to the quarantine directory with no limit on its inflated total. A push of an account with no push right counts the larger of its pack and inflated bytes toward `review-max-push-bytes` and, as `packBytes`, `review-max-account-bytes`. `idle-timeout` bounds a stalled HTTP body and a client that stops reading; a silent SSH client ends with the SSH connection's 600 second inactivity timeout. A job token's fetch request is at most 1 MiB after gzip is undone.

### Where a repository is on disk

A `local` or `remote` repository's directory is `GitRepository.localPath`, else `runtime/git/<repositoryId>` (`crates/moqui-git/src/lib.rs`). An absolute `localPath` is used as written. A relative one is joined to the runtime directory, with `..` not removed. The framework has no service that creates a `GitRepository` row except `fork#GitRepository`; an application or the System screens write the row. `fork#GitRepository` takes the new `repositoryId` only as one segment that passes `server::path::check_path` (SEC-GIT-10, fixed), and with no `localPath` joins it onto `runtime/git/`. `export#GitRepository` needs the delete right, or authorization disabled, and, with authorization on, writes a bare repository at a `targetPath` that is a relative path of safe segments under `runtime/git-export` (`EXPORT_DIR`); any path only with authorization disabled, and `underExportDir` holds the target under `runtime/git-export` even then, for a caller that checked its own right (SEC-GIT-07, fixed). When the directory there has a `HEAD`, it opens the repository already there and sets its branch to the exported head. `org.moqui.resource.FileServices.export#Drive` checks the view right on a git drive itself and passes its caller's `targetPath` with authorization disabled and `underExportDir`, so a viewer of the drive exports it under `runtime/git-export` ([Drive services](Attack-Surface-Files.md#drive-services)); the System `GitRepositoryDetail` screen and mr-boss Code settings call `export#GitRepository` directly and need the delete right. An error of opening or reading a repository's directory carries the path (`fs.rs`: `"{what} {path}: {err}"`), and the git server sends an error's text to a client that may view the repository (`ERR ...`, "repository ... cannot be opened: ...").

### Fetches through gitoxide

The git server runs no hook file and no `git` binary: a hook is a gitECA rule. `Command::new` in `crates/moqui-git` is only in `ci/runner/` (the runner's side). Three fetches go through gitoxide's client (`fetch` in `crates/moqui-git/src/fs.rs`), not through the smart HTTP client of the push mirrors:

- A `GitRepository` of `repositoryKind` `remote` is fetched from its `remoteUrl` by `fetch#GitRepository`, by `init#GitRepository`, and by the `fetch_AllGitRepositories_frequent` job every five minutes.
- `import#GitRepository` copies a branch into a `db` repository from `source`, or from `remoteUrl` when `source` is empty. `source` is `git://<otherRepositoryId>` (another repository of this server, read from its store), a directory on the server (a repository, bare or not), or a URL to fetch. The service checks the source for its caller (`import_source_allowed` in `crates/moqui-git/src/service/mod.rs`; plans/Security-Review.md SEC-GIT-01, fixed): another repository needs the view right on it, a directory or a scheme other than http(s) the sealed `TERMINAL_HOST` or authorization disabled, and a `source` URL must be https (http with `webhook-private-network`), with no credential in it, to a host whose addresses are all public unless `webhook-private-network`, whoever calls. The repository's own `remoteUrl` (no `source`) is not checked: an administrator set it. mr-boss's `create#Repository` takes only an http(s) `importUrl` from a project manager.
- A component deploy's `GitProvider::fetch_branch` fetches a URL ([Component deploy](Attack-Surface-Tools.md#component-deploy-and-conf-reload)).

Past the `source` check above, this path has no size or time limit and no `outbound-check-service` call; the fetch of an http(s) `source` connects only to a public address unless `webhook-private-network` (`moqui_git::deny_internal`: the public-only resolver, no proxy, an internal address literal refused) and follows no redirect (the guard sets gitoxide's `configure_request`, and gitoxide refuses every redirect once request headers were configured), so a name that changes its address between the check and the fetch is refused. A remote mirror's fetch (`GitProvider::fetch`, `fetch#GitRepository`, a drive mirror's included, whose `remoteUrl` a drive manager may change through `update#Drive`) runs under the same guard unless `webhook-private-network` is on: an https or http host's addresses must be public and an ssh host is pinned to a public address (SEC-BOS-90). A `file://` or local-path `remoteUrl` is not a network address and the guard does not refuse it. `find#GitRepositories` answers `remoteUrl` only to who may delete the repository, with its user, password and query left out; `FileServices.create#Drive` (mirror) and `WikiServices.make#WikiSpaceStorage` (remote) refuse a `remoteUrl` with a password, or with any user for http(s) (an ssh user such as `git@` is kept). The Tools `GitRepositoryDetail` entity form (ADMIN's) still stores one as given. `GitRepository.username` and `accessToken` (encrypted) are given to gix's credential callback, which answers every request for a credential without looking at the URL it is asked for (`fs.rs`); `import#GitRepository` gives it the repository's credentials also when the URL is the caller's `source`, so a `source` host that answers 401 is offered the token stored for `remoteUrl`. `fs::fetch` redacts the URL it prints itself and appends gitoxide's own error text as it is; that text is `GitRepository.lastFetchError` and the service's error. The framework's callers gate the `remote` kind on the `ADMIN` group (`WikiServices.make#WikiSpaceStorage`, `FileServices` drive creation with storage `mirror`). The pre events of source `fetch` and `import` run before a branch or tag moves. A `remote` repository's fetch stages the remote's branches under `refs/moqui-incoming/` before those events pass them.

What gitoxide's client does with a URL (`gix-transport` 0.62.0 `client/blocking_io/connect.rs`, built with `blocking-network-client` and `blocking-http-transport-reqwest-rust-tls`): `ext::` and remote helpers are refused. `file://` and a plain path spawn `git-upload-pack` (or `git upload-pack`). `ssh://` and the scp form spawn `ssh`. `git://` is a TCP connection made in process. `http://` and `https://` use reqwest. `fs::fetch` itself applies no rule on the scheme or the host: the address guard is on only inside `fs::deny_internal()`, which `import` takes for a caller's http(s) `source`; a `remoteUrl` fetch and an import from `remoteUrl` never take it. The guard does not cover `file://` and `git://`, which `import_source_allowed` keeps to `TERMINAL_HOST` or authorization disabled; with it an ssh fetch is pinned to a checked address. Without the guard (a `remoteUrl`) gitoxide follows redirects of the first request only, up to 50, never to another scheme except http to https, and to another host only when the redirected URL keeps the request's tail; later requests go to the redirected base. A URL's own `user:password` is the first identity, sent as basic authorization on the first request with no 401 first, and is dropped when a redirect changes host or port or downgrades. After a 401 the credential callback is asked with the transport's current URL, the redirected one, and answers the stored token whatever that URL is: a host a `remoteUrl` redirects to receives `GitRepository.accessToken` if it answers 401, over https (or over http when the `remoteUrl` is http).

### The older push mirror

A repository with `pushMirrorRemoteId` is pushed over SSH to the `SystemMessageRemote` it names (`sendUrl`, `username`, `privateKey` and `publicKey` or `password`, `sshHostKeyFingerprint`). The framework's post-receive rule (`Git.gitecas.xml`) calls `push#GitMirror` async after each push, fetch, import or write. `pushMirrorRefs` maps any local ref (`from:to`, a trailing `*`); empty is every branch and tag. The local refs offered to the map are all of `refs/`. Without `sshHostKeyFingerprint` the host key is trusted on first use and recorded in `runtime/conf/ssh_known_hosts`. No internal-address rule applies. `outbound-check-service` is asked (`push-mirror`). The service checks no repository right. The fields are set from the tools screen `System/Resource/GitRepositoryDetail` ([Tools and System](Attack-Surface-Tools.md#tools-and-system)).

### Push mirror transport

An HTTPS push mirror and `fetch#GitRefs` use `crates/moqui-git/src/server/smart_http.rs` on `moqui_lib::http::RestClient`: internal addresses are denied in the resolver, no redirect is followed, and the TLS roots are the system's. An SSH push mirror uses the server's russh client (`crates/moqui-host/src/ssh/client.rs`). Both read the server's refs within `MAX_ADVERTISEMENT` (32 MiB) and its report within `MAX_REPORT` (1 MiB), refused past them, a report cut at its cap included; over SSH the whole command has a 30-minute deadline (each wait what is left of it, at most 120 seconds) and at most 64 KiB of stderr is kept (`push::push`, `RusshExec`; SEC-GIT-06, fixed). The mirror's own `credential` logs in: a private key when it contains `PRIVATE KEY`, else a password. `hostKeyFingerprint` is required. No agent is used. A mirror's `credential` is at most 16 KB. `run#GitRepositoryMirrors` is `authenticate="anonymous-all"` for its job, which runs each minute and pushes up to 500 due rows one after another. It takes an optional `mirrorId`, the one mirror to push. No REST resource names it.

### Webhooks

`store#GitWebhook`, `delete#GitWebhook`, `find#GitWebhooks`, `find#GitWebhookDeliveries` and `test#GitWebhook` need the delete right on the repository. A webhook URL follows a mirror's rule (`smart_http::check_url`): `https://`, plain `http://` only with `webhook-private-network="true"`, and no user or password in it; `store#GitWebhook` checks it (`check#GitWebhookUrl`) and so does each delivery (`webhook_url_allowed`), so a stored webhook that breaks the rule fails each delivery with the reason. The `url` field is not encrypted, and `find#GitWebhooks` answers it to who may delete the repository. The `secret` is the caller's text with no minimum length, stored encrypted, kept when left empty on an update (a changed URL too), and answered only as `hasSecret`. A repository has at most `max-webhooks` (20) webhooks: `store#GitWebhook` refuses one more (`get#GitWebhookLimits`).

A delivery is a `SystemMessage` of type `GitWebhook`, POSTed by `send#GitWebhookDelivery` with `X-Moqui-Event`, `X-Moqui-Delivery`, the trace headers and, with a secret, `X-Hub-Signature-256` and `X-Moqui-Signature-256` (`sha256=` HMAC-SHA256 of the body). The client denies internal addresses unless `webhook-private-network="true"` ([the internal-address guard](Attack-Surface-Outbound.md#the-internal-address-guard)); the check is in the resolver, on the addresses connected to. It follows no redirect, times out at 10 seconds and reads at most 64 KiB of the answer, which is not stored. A pass of `retry#GitWebhookDeliveries` starts sends for `queue-pass-seconds` (300), leaves the rest for the next run, and starts at least `queue-pass-gap-seconds` (300) after the last pass on the node. The delivery log gives a maintainer the body sent, the HTTP status and each attempt's error text. A push body carries the last 20 commits (id, message, author and committer name and e-mail) and the pusher's user id and username. Nothing is sent of a hidden merge request.

`retry#GitWebhookDeliveries` (`authenticate="anonymous-all"`, the job each minute, 200 pending a run, sent one after another) retries after 1, 2, 4 ... minutes and gives up after 8 failures. `outbound-check-service` is asked when a delivery is queued, not when it is sent or retried, and not for a ping. `send#GitWebhookDelivery` checks no right, and `queue#GitWebhookPush` refuses a caller unless authorization is disabled (`internal_call`); no REST resource names them. `queue#GitWebhookPush` takes `userId`, `source` and `refUpdates` from its parameters.

### The hosting REST resources

`/rest/s1/moqui/git/{repositoryId}` is in `runtime/components/base/tools/service/moqui.rest.xml`; the path's authorization is in [Parent frames](Attack-Surface-Web.md#parent-frames). Every method needs a signed-in user. No GET maps to a write service.

- GET: `get#Repository` (the resource itself), `cloneUrls`, `refs`, `branchRules`, `tree`, `blob`, `compare`, `commits`, `commits/{commitId}` with `diff`, `refs` and `statuses`, `agreement`, `writeCheck`, `mergeRequests` and `mergeRequests/{mergeRequestNum}` with `approvals`, `diff` and `threads`, `pipelines`, `pipelines/definitions`, `pipelines/{runNum}`, `jobs/{jobRunId}` and its `log`, and `artifacts/{artifactId}`.
- POST: `refs`, `commits/{commitId}/statuses`, `mergeRequests`, a merge request's `close`, `reopen`, `reviews`, `merge`, `threads` and `threads/{threadId}/resolve`, `pipelines`, a run's `rerun`, `cancel` and `approve`, and `jobs/{jobRunId}/retry`.
- PATCH: a merge request. PUT: its `reviewers`. DELETE: `refs`.

The pipeline and job GETs call `org.moqui.git.GitCiServices` directly; each reads a run only when the caller views the run's repository. `jobs/{jobRunId}`, its `log` and `artifacts/{artifactId}` find the row by its id alone and check view on the run's own repository, so they answer under any `repositoryId` in the path; no right comes from the path. `pipelines/definitions` (`get#PipelineDefinitions`, view) reads the pipeline file at a commit; the file's blob is read whole, with no size passed to `file_at`, before `max-file-bytes` is tested, as it is on each push and merge request event (`ci/queue.rs` `read_at`). A write checks view first (a caller without it is told the repository is not found), then `rest-write-check-service`, then calls the framework service, which checks its own right (`crates/moqui-git/src/service/rest.rs`). A read asks no `rest-write-check-service`. A merge request is named by its number; the REST replaces any `mergeRequestId` the caller sent with the id of that number in that repository. `find#MergeRequests` through REST drops `includeHidden` and gives at most `merge-requests-max-page` (100) a page; naming no repository, it looks in the first `merge-requests-max-repositories` (500) repositories the caller may view, by id, and stops there (`rest::first_visible`), so a caller who sees more names them (`repositoryId`, `repositoryIdList`).

Sizes of the reads: `get#GitBlob` reads the file's size first (`GitProvider::file_at`, an LFS file's content counted) and answers a file over `git-server` `blob-max-bytes` (16 MiB) with its `size` and `tooLarge` only; such a file is read from a `git://` location, which streams it (`crates/moqui-git/src/browse.rs`, `lfs_files.rs`). `get#Blob` answers a file that is not text whole, as base64 in the JSON, within that limit. `get#GitCommitDiff` and `get#GitCommit` diff the first `commit-max-diff-files` (300) files a commit changed and list the rest as too large, as `compare` does. `get#GitLog` answers at most 500 commits a call, and with `path` compares at most `log-max-commits` (10,000) commits a page (SEC-GIT-04, fixed).

`/rest/s1/moqui/hosting`: `GET offer` needs no credentials (`anonymous-view` on the resource, the method and the service). It answers the public base URL, whether the caller is signed in and the caller's own username, the git HTTPS base, the SSH host and port, whether push to review is on, the REST and sign-in paths, whether the LLM gateway is enabled and needs a client, and whether an agreement service is set. With `git-server` `offer-service` set, that service is called with authorization disabled, also for a caller with no credentials, and its `offer` replaces the framework's. `GET repository?url=` resolves a clone or page URL and answers `found` false for a repository that is not there and for one the caller may not view. `GET mergeRequests` (`find#MergeRequests`) lists merge requests of the repositories the caller names or, naming none, of the first `merge-requests-max-repositories` (500) the caller may view, by id (`rest::first_visible`, which stops there), at most `merge-requests-max-page` (100) a page. `GET agreement` answers `get#AuthorSigned` (`signed`, `message`, `signUrl`) for the `authorUserId` or `authorEmail` the caller names, to a caller who views the repository. `hosting/gatewayKey` and `hosting/keyRevoke` are under the same resource and are in [Routes](Attack-Surface-Routes.md).

The application hooks of these calls are `git-server` `rest-write-check-service`, `offer-service`, `agreement-check-service` and `review-thread-service`, all empty by default. The first three are called with authorization disabled. `rest-write-check-service` receives the `operation` text of `verify#Write` as the caller sent it. With no `rest-write-check-service` every write is allowed; with one, only an answer of `allowed` true allows. `agreement-check-service` receives the `authorUserId` or `authorEmail` the caller sent. `review-thread-service` is called as the caller, with authorization as it is, and receives the caller's `threadId` unchecked.

### Repository settings, refs and branch rules

By service (`crates/moqui-git/src/service/hosting.rs`): `create#GitRef` needs create and writes only `refs/heads/` and `refs/tags/` names. `delete#GitRef` needs delete and deletes a branch or a tag only: `write_refs` applies the branch-or-tag name check (`valid_ref_name`, `GitBadRefName`) to a delete too, so a merge request's head is not deleted (SEC-GIT-11, fixed). With authorization on, every service refuses when `AT_GIT_REPOSITORY` `authz-enabled` is off, as the server does (`provider_and_id`; SEC-GIT-14, fixed); a call with authorization disabled (rules, jobs) still runs. `archive#GitRepository`, `unarchive#GitRepository`, `update#GitRepository`, `store#GitBranchRule` and `delete#GitBranchRule` need delete. `set#GitRepositoryPath` and `setup#GitLfs` need update. `merge#GitRefs` needs update, and view with `checkOnly`. `find#GitRepositories` answers the repositories the caller may view, each with its `remoteUrl` as stored; with `pageNoLimit` it has no page size. `fork#GitRepository` needs view of the source only. A `revision` that starts with `refs/` is read as that ref by the reads (`resolve_commit` in `crates/moqui-git/src/browse.rs`), a hidden merge request's head left out.

### Services that check no repository right

`export#GitRepository`, `fetch#GitRepository` and `push#GitMirror` need the delete right (`hosting::allowed`), and `init#GitRepository` with `contentRepository` the update right (it commits `.gitattributes`, as `setup#GitLfs` does). `queue#GitWebhookPush`, `run#GitRepositoryMirrors`, `clean#GitUpdates`, `check#MergeRequest`, `sync#MergeRequest` and `refresh#MergeRequests` take internal calls only: they refuse a caller unless authorization is disabled, as `queue#PushRuns` does, and their framework callers (gitECA rules, jobs) call them so (plans/Security-Review.md SEC-GIT-07, fixed). These `org.moqui.git` services still check no `AT_GIT_REPOSITORY` right in the service: `fetch#AllGitRepositories`, `init#GitRepository` without `contentRepository`, `import#GitRepository` (whose source is checked: SEC-GIT-01), `gc#GitRepositories`, `fsck#GitRepository`, `process#GitUpdate`, `process#PendingGitUpdates`, `queue#GitRepositoryMirrorPushes` and `send#GitWebhookDelivery`. A caller needs authorization for the service itself ([Services and `allow-remote`](Attack-Surface-Web.md#services-and-allow-remote)). The checks on who starts them are in their callers: the `System/Resource` screens `GitRepositoryList.xml` and `GitRepositoryDetail.xml` ([Tools and System](Attack-Surface-Tools.md#tools-and-system)), `Git.gitecas.xml`, `WikiServices.xml`, service jobs, and an application's screens. No resource of `moqui.rest.xml` names them. No route lets a user who is not `ADMIN` name a service to call: Tools `ServiceRun` is under the Tools grant and calls as the caller with authorization on; the load runner's `service.call` needs `LOAD_RUNNER` (seeded to `ADMIN_ADV`); an agent tool exposure is a row only `AgentAdmin` stores, and a tool call runs as the caller with authorization on; a ServiceJob whose `serviceName` an `ADMIN` edits runs with authorization disabled, as do SystemMessage send services and the `InstanceHostType` run services; there is no generic call-by-name REST or RPC route. No seed `AT_SERVICE` record names `org.moqui.git.*`: a user reaches a git service only under a screen or REST frame that lets it inherit (`/moqui/git` for `ALL_USERS`, mr-boss `Projects.xml` for its two groups). So these services, `fork#GitRepository` and the run services are reached by `ADMIN`, by the seeded jobs and rules, and by two fixed application calls (mr-boss `RepositoryDetail/Activity.xml` `process#GitUpdate` after a `canDelete` check, with authorization disabled; Smithy's fork with fixed keys). The nine transitions of `GitRepositoryList.xml` and `GitRepositoryDetail.xml` (fetch, push mirror, init, export, import, gc, fsck, LFS setup) pass the whole context to the service with authorization on; `repositoryId` is the request's own parameter.

- `update#MergeRequest` (its author, or a user with update) that moves a merge request to another target branch sets its approvals back to requested: each was given for the merge into the branch it named, under that branch's rules (SEC-GIT-13).
- `check#MergeRequest`, `sync#MergeRequest` and `refresh#MergeRequests`, run internally, take any `mergeRequestId` and call the inner services with authorization disabled: they move the head and status, set approvals back to requested and queue a `synchronize` event.
- `clean#GitUpdates` is `authenticate="false"` and deletes the push log older than `daysToKeep`. `run#GitRepositoryMirrors` and `retry#GitWebhookDeliveries` are `authenticate="anonymous-all"` and take `mirrorId` and `retryLimit`. These three need no service authorization; `clean#GitUpdates` and `run#GitRepositoryMirrors` refuse in their bodies unless authorization is disabled.
- `get#GitRepositoryAccess` answers the caller's own rights as booleans, and another user's (`userId`) with authorization disabled only.
- `process#GitUpdate` signs the calling context in as the user of the update (`internal_login_user`, `crates/moqui-git/src/events.rs`), runs the post-receive rules, and signs the caller back in; no guard restores the caller if a rule unwinds between the two, and when the update's user does not pass the account gate the rules run as the caller, with a warning.
- `sync#MergeRequestHead`, which `get#MergeRequest` and `get#MergeRequestDiff` (REST GET) call with authorization disabled after their own view and hidden checks, writes for a merge request that is not open only a missing head ref, only from the row's recorded `headCommitId`, only when that is a commit of the store, and for a closed one only inside the retention time (`service/review.rs`); `set_merge_request_head` (`fork.rs`) takes the repository's lease and lock, checks it is still writable and sets that one ref with a compare of its current value. `headCommitId` is written by the merge request services and by an import, whose head must be one the importer reads.
- `commit#GitFiles` adds the `Moqui-User-Id` trailer only when the message has none (`merge.rs`), so a trailer the caller wrote is kept and `get#GitTree` answers it as `moquiUserId`; a pushed commit can say the same. `propose#MergeRequest` updates a named merge request only when it is the caller's own open proposal for that target. Merges read no `.gitattributes` and configure no driver or filter command.

## Pipelines

From `docs/interfaces/Pipelines.md`. The CI engine never runs a step on the server: a job is a container the server starts through an `InstanceHost` (the Docker Engine API over a Unix socket, HTTPS with a client certificate whose key is an encrypted field, or plain HTTP to this machine only; plain HTTP to another host is refused, SEC-OUT-08), or a registered runner's. Nothing requires the host to be another machine: a Unix socket and a loopback address are accepted, and the seed data has a host `LocalDocker` at `http://127.0.0.1:2375`. What it adds to the surface:

- **The pipeline file** (`ci.xml`) is read from a pushed commit, by whoever may push or open a merge request. The reader is strict and bounded (`git-ci` `max-file-bytes`, `max-pipelines`, `max-jobs`, `max-matrix`, `max-steps`, `max-timeout-minutes`); names are letters, digits, dot, dash and underscore; paths cannot leave the checkout. Nothing of the file is run on the server: a step's command, an image name and a cache key are text handed to the runner. `${matrix.NAME}` is replaced by the matrix values, as text, in the image, the variables and each step's command when a job is planned; a cache key's `${hash:...}` is the runner's. The image must match a pattern of the pool's `allowedImages` (none by default).
- **The runner REST**, `ANY /ci/runner/{*rest}` when `git` is compiled. No session, cookie or user credential: a bearer token, taken only where git takes credentials (HTTPS, a believed proxy's, a client on this machine, or `git-server` `allow-http`). A **job token** (32 random bytes, stored as its SHA-256, good while its job run is `running` and until the job's time limit, dead once the job ends) reaches only `jobs/<its job run>/...`: the job, log lines, step results, uploads, cache downloads and the result. The job run in the path must be the token's (403); the token of a job that ended or passed its time is 410 Gone, which is no authentication failure (a runner retrying after a cancel, on any cluster member), and a malformed or unknown token is 401, counted for web protection (an unknown well-formed one toward the `ci-token-failure` ban, a malformed one toward `auth-failure`'s). A **pool token** only registers a runner (counted per pool, `runner-max-registrations-per-minute`, and at most `max-runners-per-pool` active runners, so a leaked one mints only so many runner tokens for the list of good CI tokens) and a **runner token** only asks for a job of its pool. Requests are counted per job and per runner once the token is found good (`runner-max-requests-per-minute`), and then pass the per-client rate limits ([web protection](Attack-Surface-Web.md#web-protection) `ci-token-failure`); a JSON body is at most `max-log-batch-bytes`; an upload streams to a content blob and is cut at its kind's limit (`max-artifact-bytes`, `max-report-bytes`, `max-cache-bytes`), at most `max-artifacts` of a job. An upload's `name` (200 characters, no slash), `path` (500 characters, any text) and `retentionDays` are the runner's query parameters, stored as sent and answered by `get#JobRun`, so a job chooses its report's file name and with it its served type. The server stores an upload's body as it came, with no knowledge of which file the runner read. `git-ci` `max-repository-upload-bytes` and `max-owner-upload-bytes` are 0 by default, which is no cap: a job then stores `max-artifacts` (100) uploads of `max-artifact-bytes` (1 GiB) each; the count is read before a body and not again after it, so uploads sent at once each pass it. The only GETs are `job` and `caches`: there is no artifact download for a runner. Exempt from the request deadline, as git is. A host whose root screen refuses the framework's routes still serves `/git/` and `/ci/runner/` (`SERVED_ON_REFUSING_HOSTS` in `crates/moqui-core/src/web/reserved.rs`), each behind its own authentication and web protection. Git, LFS and the runner REST run on one pool (`git-server` `max-concurrent`, `max-queued`), and a request takes a worker before its token or credentials are read.
- **A job token on the git server** reads its job's repository at its job's commit and nothing else: upload-pack only, one advertised ref at that commit, every `want` that commit, a shallow fetch of at most `max-fetch-depth`. The token of a job that ended is 410, no authentication failure, as on the runner REST; an unknown one is 401 and counted. The repository is the run's (the target of a fork's merge request, never the fork), and the commit must still be the repository's to give: one the head ref of the run's merge request reaches (`refs/merge-requests/<n>/head`; a hidden merge request's head is fetched by its job's token and by nothing else), or for another run one a ref the repository's readers read reaches. A commit its ref has left (a forced branch, an amended push for review, a released head) is refused in a fork network and in a repository that has had a hidden merge request (elsewhere every commit of the store was once a reader's), and a `have` or a client's `shallow` commit is answered only for that commit and its ancestors within `max-fetch-depth`, what a fetch of it gives; any other shallow line is dropped ([Git](#git)). The token's request check (`job_fetch::check_request`) refuses `want-ref`, `deepen-since`, `deepen-not` and `deepen-relative` (as an argument or a v0 capability), which counts the depth from the client's shallow commits and so could go deeper a request at a time (plans/Security-Review-Medium.md SEC-GIT-82). A job token gets nothing from LFS: `serve_lfs` has no job-token branch, a `Bearer mqcj_...` header goes to the user key login and is refused as an unknown key, so a job's checkout of a repository with LFS files gets the pointers and each `git lfs` attempt is a failed sign-in. It logs no user in, so it reaches no service, screen or other route, and it cannot push. A step runs as the runner's user and could read the token from the runner's process: it gives the step nothing the job did not have.
- **What queues a run.** The framework's post-receive gitECA rule (a branch or a tag moved by a push or a write; a push to `refs/for/<branch>` and a merge request's head ref queue no push pipeline) and its service ECA rule on `queue#MergeRequestEvent`, which does not run after a refused event (a caller without the update right). `queue#PushRuns` and `queue#MergeRequestRuns` are refused without authorization disabled, so no caller names the user or the commit of a run. A schedule (`queue#ScheduledRuns`, a job) is taken from the default branch's pipeline file and runs for the first plain branch the pipeline names, else the default branch (`ci/queue.rs`): the file is read at that branch's head when the schedule is due, the run has no user, and `trust::is_trusted` answers true for every schedule run, whoever pushed that branch. The file is read at the event's commit as the system reads, a hidden merge request's head too; in a fork network, and in a repository that has had a hidden merge request, a commit no ref of the repository reaches any more has no pipeline, so a run (or a re-run of an old one) is no way to read it.
- **Hidden runs.** The run of a hidden merge request's head is hidden (`GitPipelineRun.hidden`): its log, artifacts and reports, which are that head's files, are read by the user who pushed it and with authorization disabled and `includeHidden`, not by a user with the update right, who therefore does not approve it either (the application does). `set#MergeRequestHidden` hides and shows a merge request's runs with it.
- **Untrusted code.** A run for a merge request from a fork, one pushed for review or one detached from its source, whoever opened it, or caused by an account without the update right, is untrusted: no secrets, caches read and never written (so it cannot poison a later trusted run), and only those no protected run wrote (which a build with secrets may have filled), only a pool marked for untrusted runs (a trusted run never shares its hosts) and, from a pool of registered runners, only a runner started with `--step-user`, which says `stepUser` in each claim (`registered::claim_for`; any other gets no such job and the run waits queued, the claim's `notice` saying why), whose images are never pulled on demand, and it waits for `approve#PipelineRun` unless the application's `run-check-service` allows it. That service may lower a run's trust and never raise it, and is asked again before a job of an ended run runs again; a refused or never approved run is not run again. A re-run of a merge request's run from a fork, pushed for review or detached stays untrusted whoever asks for it. A re-run of a run that was untrusted only because its account had no update right (a push of a new branch or tag by an account with the create right alone) is decided again by the caller's update right and the run check. A server whose accounts sign themselves up sets `run-check-service`: with none, any account's push to its own repository is a trusted run.
- **Secrets** (`GitCiSecret.secretValue`, encrypted) are given only to a job of a trusted run whose scope is met (a protected branch or tag: one a branch rule keeps to a push group or to merge requests; or the job's environment, when the environment allows the run: a protected ref or a branch of its `allowedRefs`, never a merge request's run, an approved one with `approvalRequired`), only over the runner REST and never in a container's definition, and are masked in the log as it is stored. The mask is applied to each `POST jobs/<id>/log` batch and across a batch boundary (a start of a secret at a batch's end, an end of one at the next batch's start when it goes on the line the last chunk left open; `trust::mask_batch`), to values of 4 characters or more; a log batch is not stored while the job's secrets cannot be read (the runner gets an error and sends it again). A result's `message` (500 characters) is masked, and left out when the secrets cannot be read. Not masked: the content of artifacts and reports, and a secret cut across three batches. They are managed by a repository's maintainers (the delete right), not by a developer who pushes, and a secret moved to another scope or environment needs a new value; the environment a secret is scoped to is edited (`allowedRefs`, `approvalRequired`, by the same maintainers) with no new value, as a branch rule is for the `protected` scope. A trusted merge request's run from a branch of the repository receives none either; a scheduled run on a branch an environment's `allowedRefs` names does. The value goes only in `GET jobs/<id>/job` to the job's token. No service reads a value back. The service facade logs no parameter value (its log lines carry the service name and an error text), and none of the services that take a secret is a seeded job, whose parameters `ServiceJobRun.parameters` would keep; `ec.web.getRequestDetails()` leaves out the names `secret_parameter` knows (`password`, `secret`, `token`, `credential`, `code`, names ending in `key`), which does not cover the `value` of `store#CiSecret`; its one user is the System home's dialog of the viewer's own request. A step that has a secret can still send it elsewhere: the protection is that only reviewed files run with one.
- **The container**, and each of its service containers (at most `max-services`, their images allowed by the pool as the job's is), has no privilege, no capabilities, `no-new-privileges`, no host path or socket, no published port, a non-root user (root in no form; with `container-user="image"` only an image whose USER is a numeric uid other than 0, since a name may be uid 0 in the image), an init that reaps orphans, a read-only root with sized tmpfs mounts (the working directory on one, or on the root filesystem the pool's `diskMb` sizes), and the pool's CPU, memory and swap, pid and disk limits and network mode. What it may reach on the network is the host's to limit (`egressRule` names a network, never the host's or another container's; the engine makes no rules): it must reach the server's URL, and should reach nothing else of the server's network. A job with services gets a network of its own, internal unless the pool's egress is `bridge`, with the job also on the pool's network: a service reaches nothing outside. Names carry the server's id and removals touch only containers with the server's label, so servers sharing a host do not touch each other's; the cleanup leaves a container made after it read the running jobs. A registered runner keeps its machine between jobs: its pool is one owner's on a server with tenants, and `moqui ci-run poll` kills what a job left running of the runner's user. The server holds the host's API credentials, which are root on that host: a compromised server owns its runner hosts, not the other way round, as long as runners are other machines.
- **Statuses** `ci/<pipeline>/<job>` are written by the engine through `create#GitCommitStatus`, with authorization disabled and `includeHidden` (so a service ECA rule on it runs for them, and a hidden head has its checks); their description is plain text, with `<` and `>` left out of what a pipeline file's error, a runner or the application's check said. A user with a push right can still post a status of any context unless the application reserves `ci/` (`git-server` `reserved-status-contexts`), which a branch rule that requires a `ci/` check needs.
- **Artifacts and reports** are a job's output, whatever its commit's scripts wrote, so they are never the application's own pages: `send#RunArtifact` sends one as an attachment, and inline (`inline`) only a passive type; it is answered by its type only when that is inert (images, fonts, audio and video, PDF, plain text and CSV, archives; `web::is_inert_content_type`), else as `application/octet-stream`, with `Content-Security-Policy: default-src 'none'; sandbox` (an inline PDF aside); an HTML, SVG or XML page is shown by its own type only with `inlineActive` as well, sandboxed, and a script never is; every inline one has `Content-Security-Policy: sandbox` (no `allow-same-origin`, no `allow-scripts`) and `X-Content-Type-Options: nosniff`, as `ec.web.sendResourceResponse` and a PASS download send every inline file that is not the application's own, and either sends a file of an active type as an attachment even when asked inline (a PDF is not sandboxed: browsers do not show one in a sandbox). The `Content-Disposition` of a sent file keeps of the name, in the quoted `filename`, only ASCII graphic characters other than `"`, `\` and `;` (anything else, CR and LF included, is `_`), and percent-encodes `filename*` byte by byte (`attachment_disposition` in `crates/moqui-core/src/web/mod.rs`). A cache is never served by the artifact reads. Their `ci-artifact://` locations are read with `get#RunArtifact`'s check; `open` streams (`send#RunArtifact` and `ec.web.sendResourceResponse` use it), and `read_bytes` reads the whole artifact into memory with no cap of its own (`ci/location.rs`), which every generic whole-file read of a resource location calls; a PASS authority download opens a `ci-artifact://` location its authority service answered with authorization off (that service checked the caller, the client never names a location, and a hidden run's file is read only so), and any other answered location with the call's own authorization.
- **Deployments** (`request#`, `decide#`, `cancel#`, `find#GitDeployments`, `get#GitDeployment`). Asking needs the update right, a branch that is protected or in the environment's `allowedRefs`, and its head; the environment's pipeline runs with the `deploy` event through the run check like any run. The pipeline file is read from the deployed commit, so whoever pushes to the branch chooses the tests that pass it: a branch no rule protects (named by `allowedRefs` only) therefore always waits for an approver, whatever the environment's `approvalRequired`. Approval is `decide#GitDeployment` only, by the environment's approver group (or a maintainer), never the requester; an approval of the run (a job in the environment) does not approve the deployment. The environment's token is the secret its target issued: encrypted, at least 32 characters, never read back (`hasToken`), never sent (it signs the attestation, [Component deploy](Attack-Surface-Tools.md#component-deploy-and-conf-reload)) and never in `errorText`, a status or a notice. Only maintainers (the delete right) store an environment, so a developer cannot point one at a host of their own, and only they read its `targetUrl` and `cloneUrl` (`find#CiEnvironments`); a `cloneUrl` with a user or password in it is refused. The deploy step posts to `<targetUrl>/rest/s1/moqui/components/deploy` only: `https`, or `http` to a loopback IP literal; a loopback, private or link-local target (written out or resolved) only with `git-ci` `deploy-private-network="true"`; no redirect; `deploy-timeout-seconds`; 1 MiB of answer; the outbound check (`deploy`) asked first. What the target answered on a failure is in `errorText`, which `get#` and `find#` answer to a maintainer only; the public status `deploy/<environment>` says only how it ended. A repository the caller does not view is not found, with its deployments. Statuses `deploy/<environment>` are the engine's; reserve them with `reserved-status-contexts="ci/,deploy/"`.
- **Delete.** `delete#GitRepository` removes the engine's rows of the repository with it (runs, jobs, logs, uploads, secrets, environments, deployments, schedules), its push mirror rows, and cancels its webhooks' queued deliveries (`storage::delete_rows_of`; SEC-GIT-15, fixed), and stops its running jobs, so no job token or secret outlives its repository; a fork's runs are its own.
- **Services** (`org.moqui.git.GitCiServices`): reads follow view of the repository, and a hidden merge request's run only with authorization disabled; retry, run and re-run need update; cancel needs update or to be the user who triggered the run; approve needs update, and for a run with a job in an environment that requires approval the delete right and another user than who triggered it; a repository's secrets and environments need delete (a maintainer) to store, list or delete, but `find#CiEnvironments` needs view: a viewer reads each environment's name, `allowedRefs`, `requiredPipeline`, `approverGroupId`, `approvalRequired` and `hasToken`, and the URLs only with delete; `set#RunArtifactKeep` needs update, `delete#RepositoryRuns` delete, `get#PipelineDefinitions` and a repository's `get#RunnerUsage` view; an owner's, and `includeHidden`, need authorization disabled. `queue#ScheduledRuns`, `start#QueuedJobRuns`, `end#OverdueJobRuns` and `expire#RunData` are the jobs' and check nothing in their bodies. The runner pool services (`find#`, `store#`, `delete#RunnerPool`, `create#RunnerPoolToken`, `revoke#Runner`) need the `GIT_CI_ADMIN` permission or authorization disabled. Pool tokens expire (`pool-token-days`), a new one can revoke the runners the old one registered, and a revoked runner's token is refused. `store#RunnerPool` accepts a pool of `poolKind` `registered` that is not `trusted`.

### When pipelines are on, and the built-in pipeline

`git-ci@enabled` is empty in the default conf. With it empty the engine queues runs only while an enabled `GitRunnerPool` row exists, and the framework seeds none. A push or a write through Moqui that moves a branch or creates a tag queues runs (the rule's `source="push,write"`: not a mirror's fetch and not an import). Merge request events queue theirs.

With `builtin-enabled="true"` (the default) a commit whose root has a `component.xml` and no `ci.xml` gets one pipeline, `component`, on push and merge-request, with one job `test`. Its image is `builtin-image` (`moqui-build`; `{frameworkVersion}` is the version the `component.xml` names) and must match the pool's `allowedImages` like any job's. Its one step is `crates/moqui-git/src/ci/builtin-component.sh`, run by the runner in the container: it copies the checkout into an MR Moqui tree of the image and runs `./moq component-get <name>` and `./moq test <name>`. The built-in run follows the same trust rules as a `ci.xml` run.

With no `run-check-service` a trusted run is allowed and an untrusted one waits. `start-inline="true"` (the default) starts queued jobs on a thread named `git-ci-start` once the queuing transaction commits, instead of waiting for the start job; the thread calls the host type's start service and runs no step. `runner-command` (`moqui ci-run`) is split on whitespace and is the container's command.

### What a job's container and its steps are given

A job's container is created with `MOQUI_CI_SERVER_URL`, `MOQUI_CI_TOKEN` (the job token), `MOQUI_CI_JOB_RUN_ID` and `CI` in its environment, so the job token is in the container's definition on the host. `GET jobs/<id>/job` answers the job's plan, clone URL and, for a trusted run, its secrets, on every call while the job runs. The runner (`moqui ci-run`) starts each step with no runner credential in its environment (every `MOQUI_CI_` name that ends in `_TOKEN` or `_TOKEN_FILE` is removed; `crates/moqui-git/src/ci/runner/mod.rs`), and adds the job's variables, the `MOQUI_CI_*` variables and the secrets. It checks the commit out with the system `git`; the token is passed as `http.extraHeader` in `GIT_CONFIG_*` environment variables, not in arguments.

Job, runner and pool tokens are a prefix (`mqcj_`, `mqcr_`, `mqcp_`) and 32 random bytes in hex, stored as their SHA-256 and looked up by it. A runner token expires (`runner-token-days`); `revoke#Runner` ends it sooner. A registered runner (`moqui ci-run poll`, `crates/moqui-host/src/ci_run.rs`) reads its token from `--token-file` or `MOQUI_CI_RUNNER_TOKEN_FILE`, else from `MOQUI_CI_RUNNER_TOKEN` with a warning, and runs steps as its own user with no container. A step starts from a cleared environment: `PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `LANGUAGE`, `TZ`, `TMPDIR`, `SHELL`, `TERM`, the `LC_` variables and the `--pass-env` names, then the job's own variables; no runner, pool or job token in any mode (`step_base_env` in `crates/moqui-git/src/ci/runner/mod.rs`; plans/Security-Review.md SEC-GIT-02, fixed). A step can still read what the runner's user can: the token file, and a token kept in the runner's starting environment (`/proc/<pid>/environ`). With `--step-user USER` (unix) the runner runs as root and each step as USER (`CommandExt::uid`/`gid`), who owns the checkout and the steps' home but not the root-only token file; USER's processes a job left are killed after it. The runner's own process, root in this mode, restores caches before the steps; after the steps it kills USER's processes of the job, and the reports, artifacts and caches it uploads are found and read by a child of the binary that runs as USER (`ci-run collect`), which `poll` checks USER can run before it takes a job; as that kill takes every process of USER from the job, `poll` holds USER for itself alone (an exclusive lock on `/run/moqui-ci-step-user-<uid>.lock`) and refuses to start when another runner holds it ([The runner's archives](#the-runners-archives)). The rotated token file is made `0600` and renamed over the old one (`ci_run.rs`). A runner token expires `git-ci` `runner-token-days` (90) after it was made, a runner registered before that counting from its `registeredDate`; a claim answers `rotateAfter`, and `POST /ci/runner/rotate` gives a new token and ends the old one at once (an expired token is 401). A pool's `allowedAddresses` (CIDRs) refuses a register, claim or rotate from another address with 403, noted as a failed sign-in; a list that reads as no range takes no address, and `store#RunnerPool` refuses an entry that is not one. `GitRunner.lastAddress` keeps where a runner was last heard from. `POST /ci/runner/claim` with a runner token answers the next queued job of the pool, with its job token, when the runner has no job running.

A registered runner works in a directory of its own (`runner::work_dir` in `ci/runner/mod.rs`, called by `ci_run.rs`; plans/Security-Review-Medium.md SEC-GIT-98, fixed). Without `--work` it is a new `<system temp>/moqui-ci-<16 random hex>` made at the start (a `create_dir` that fails on a name that is there, so no other local account can have made it first). A `--work` directory is made when missing; one that is there must be a directory, not a link, of the runner's user (`geteuid`), that no group or other user may write, and each directory above it must be root's or the runner user's, and sticky when other users, or a group other than the runner's own effective group, may write it (as `/tmp`; a group-writable directory of the runner's own group, a umask 002 user's, is taken), or `poll` refuses to start (`parents_safe`, `parent_refusal`). The random directory is removed when the runner ends (`WorkDir`'s drop) and when SIGINT, SIGTERM or SIGHUP ends it (`remove_on_signal` in `ci_run.rs`). Either is set to mode 0700, or 0711 with `--step-user`, through which the step user (and the collect child) reaches what was handed to it and lists nothing. Each claimed job's directory is `<work>/<jobRunId>` (`runner::job_dir`): a `jobRunId` that is not an id (letters, digits, `_`, `-`) is not run; what was there is removed and the directory made new with the same mode, and the checkout `src` and the steps' `home` in it are made 0700 (`moqui_lib::private_fs::create_dir_all`) before they are handed to the step user. The runner's scratch files there (cache archives, reports, the collect children's input, output and errors) are made with `create_new`, `O_NOFOLLOW` and mode 0600 (`runner::create_new`), never through a file or link at the name. So no other local account reads a job's checkout, caches or `home`, or can swap a job's directory under the steps, the cache archive or `chown -R`; runners of two pools on one machine each have their own directory.

### The run services of a host type

The container driver is four services of `org.moqui.dev.InstanceServices` (`start#RunDocker`, `inspect#RunDocker`, `remove#RunDocker`, `cleanup#RunsDocker`) that the engine calls with authorization disabled. They check no permission in their bodies; a caller needs authorization for the service. `InstanceHost.hostProtocol` is `unix`, `http` or `https`, and `http` when empty; `http` is taken only to a loopback `hostAddress` (`localhost`, 127.0.0.0/8, `::1`, `::ffff:127.x`), and to any other host `DockerHost::of` refuses it before anything is sent, for a CI run and for the hosted-instance services' `call#DockerApi` (SEC-OUT-08). The entity seed data makes an `InstanceHost` `LocalDocker` at `http://127.0.0.1:2375` and the host types `docker` and `fake`. A container's network mode is the pool's `egressRule`, `bridge` when empty; `host` and `container:...` are refused and nothing else is (`docker.rs`), so a Podman mode `ns:<path>` (the host's network namespace by `ns:/proc/1/ns/net`), `slirp4netns:...` and `pasta:...` pass; the rule is a `GIT_CI_ADMIN` holder's to store. The container is created with `Binds: []` and its tmpfs mounts and nothing about the image's declared volumes; no image's `Config.Volumes` is inspected, so an image's `VOLUME` path is the engine's to make as an anonymous volume, which the pool's `diskMb` (`StorageOpt`, the root filesystem's) and the tmpfs sizes do not bound. A trusted pool's image that the host does not have is pulled; an untrusted pool's is not. The CPU, memory, pid and disk limits are set only when the pool has them. `inspect#RunDocker` and `remove#RunDocker` take `instanceRef` only as 1 to 64 hex digits (`container_ref`, `crates/moqui-git/src/ci/driver/docker.rs`). `remove#RunDocker` removes the container `instanceRef` names only when it carries this server's `moqui.ci.server` label (`DockerHost::ours`), and the containers with the job's and the server's labels; every label listing carries this server's label whatever `filterLabels` says (`own_filters`; SEC-GIT-17, fixed).

### The runner's archives

`moqui ci-run` restores a cache by unpacking a `tar.gz` into the workspace with the `tar` crate's `unpack_in`, overwriting files (`crates/moqui-git/src/ci/runner/archive.rs`); it downloads caches only, and the runner REST has no artifact download. An entry whose path would leave the workspace is skipped. Links are stored and restored as links. There is no limit on the unpacked size or the entry count. The archive is what an earlier job of the same repository uploaded for the cache key: a trusted run's, and an untrusted run reads only what no protected run wrote. The unpack runs as the runner's user, before the workspace is handed to the step user.

After the steps the runner collects the reports and artifacts the pipeline file names, and a trusted job's caches (`ci/runner/mod.rs` `find`, `copy_regular`, `open_regular`; `ci/runner/collect.rs`; `archive.rs` `pack_into`). The pattern's text cannot hold `..`, `.git` or an absolute path (`ci/file.rs` `valid_path`), and what is on disk is held to the workspace: a path is kept only when `canonicalize` puts it under the canonical workspace, at each segment, so a link out (of the last name or of a directory on the way, `d -> /root` with `d/x`) is left out and a `*` never lists a directory out of it; each path left out is named in the job's log. A report must be a regular file by `symlink_metadata` (a link is refused and named in the log, even one to a file of the workspace) and is read with `O_NOFOLLOW` and `O_NONBLOCK`, the opened file checked to be a regular file; the upload opens its file the same way (`ci/runner/http.rs`). `pack_into` refuses a named path that resolves outside the workspace; under a directory it walks by `symlink_metadata`, stores a link as its text and never follows it, reads a file through `open_regular`, and leaves out a FIFO, socket or device. With `--step-user` the runner, root, first kills the step user's processes that started during the job (`end_leftovers`, up to five passes, so one that left its group with `setsid` cannot stop or feed what follows), and then neither lists, resolves nor reads the workspace the steps wrote: each pattern is matched, each report copied and each artifact or cache packed by `moqui ci-run collect` (`find`, `report`, `pack`), a child of the same binary (by `/proc/self/exe` on Linux) with the step user's uid and gid, no environment and `/` as its directory, given absolute paths in a file as its input and writing to a file the runner made. A link that a step swaps in therefore reads only what the step user can read, and a refusal names only what the step user could see. The whole collection has one 30-minute limit, after which a child is killed and no other starts. `poll --step-user` runs a `collect probe` as the step user at its start and refuses to start when that fails (plans/Security-Review.md SEC-GIT-81, fixed). Without `--step-user` the steps run as the runner's user and read what it reads anyway, and the runner does the same work itself. The server stores an upload's body as sent, which the run's readers download ([The hosting REST resources](#the-hosting-rest-resources)). A cache key's `${hash:FILE}` is read before the steps, while the checkout is still the runner's, by `copy_regular` (a regular file of the workspace, not a link); a file that is there but not read is said in the log, as it leaves that part of the key constant. The key puts 16 hex digits of the file's SHA-256 in the log. The runner's scratch files beside the workspace have names made from its process id (SEC-GIT-98).
