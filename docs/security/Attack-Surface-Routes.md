# Attack surface: routes, screens and REST

The host routes and servlets, the root screen tree and its public paths, token routes, and REST. A row for another area (telemetry, XMPP, git, DAV, the LLM routes) stays in the host table here and links to that area's file. This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

`search_backend` defaults to `postgres`, so both proxies answer 404 on a default install after authentication. Each proxy's `max-body` is `100m`. Hop-by-hop headers are stripped, and so are `host`, `authorization`, `cookie`, and `content-length`. The client's `Authorization` and cookies are not forwarded. Upstream Basic is the servlet's user and password init-params (`elasticsearch_user` / `elasticsearch_password` for search; the dashboard init-params for Kibana). The proxy timeout is 120 seconds. HTTP request spans are recorded by the factory-scoped telemetry middleware.

The host reads the whole request body before the request reaches a worker, a sign-in check or a screen (`dispatch_screen`, `crates/moqui-host/src/http.rs`). This holds for any path of the screen fallback, a path that does not exist included. A body that is not multipart stops at `webapp_max_body`. A `multipart/form-data` body stops at `webapp_max_upload` when the request names a user before its body is read, else at `webapp_max_body` but on the anonymous upload paths (`/s/`), is spooled under the runtime directory as it arrives, within `webapp_max_spool` for all requests, and is cut off when nothing arrives for `webapp_upload_idle_timeout` (60 seconds). The sizes are in [HTML and uploads](Attack-Surface-Web.md#html-and-uploads). A JSON object body (`application/json`, `text/json`, `+json`) becomes request parameters whose values may be objects and lists; a name the query already set keeps the query's value.

A `<public-site>` may name a `host-check-service`, called with the site, host and path for a request to a framework route on its host: a path whose first segment is reserved in `moqui_core::web::reserved` (`/apps`, `/qapps`, `/rest`, `/Login`, `/sso`, `/status`, the token routes `s`, `u`, `cal` and `r`, and the others listed there), or a servlet's path. The token routes `i` and `call`, the root transitions of `webroot.xml` (`/menuData`, `/shellData`, `/resources`, `/email` and the rest) and the `find` screen are not in that list, and this check does not refuse them. When it answers `restricted` true the route is 404 there, before any servlet, token route, screen or `before-request` action runs, so the framework's sign-in routes and its apps are 404 on that host (a site's theme preview host, Commerce F87: the operator's `<public-site>` for that host names Mantle's `mantle.public.ThemeServices.get#PreviewHost`, as mr-pass's `docs/Deployment.md` shows; no shipped conf names one). The request logins (an `api_key` or `login_key` header, Basic credentials, `authUsername` and `authPassword` parameters) are still read on every request before the check, so a request to a site page can start a signed-in framework session on that host. A path another servlet takes (`/fop`, `/search`, `/dashboard`, an app's own) is refused the same way, and the refusal makes no session. The static routes a page there loads (`/js`, `/css`, `/libs`, `/images`, `/static`, `/assets`) are not checked while the screen path stays under them: `/libs/../apps` is the apps, and is checked. A check that fails refuses the route and is logged. The host routes above (`/health`, `/metrics`, `/notws`, `/termws` and the others) are answered before this check: the probes keep their IP list, and the sockets need a session cookie or a `login_key`; on such a host a session has a user only through a site page's own sign-in (PASS in local mode) or a request login.

Root screens by host name ([Run-Deploy](../Run-Deploy.md#several-sites-by-host-name), plans/Edge-Node2.md §4.2): a `root-screen` whose host pattern matches the `Host` header (its port left off, lower case) gives that host its own root screen; any other host gets the `.*` root, `webroot.xml`. A host is not trusted by being sent: an unknown one is the default root's. With `framework-routes="refuse"` the host serves its root's screens and the shared static files only: the token routes and the servlets are 404 there before they run, as on a public site's restricted host but with no service call, and so are the host routes above (`/health`, `/metrics`, the sockets, `/dav`, the LLM and channel routes), by a layer on them, and the gRPC services of the HTTPS listener (the OTLP receiver, the PASS authority), whose calls go to the router instead. Left to such a host, each behind its own authentication and web protection: git over HTTP and Git LFS under `/git/` (git at a public site's page URL too, when it is also a `public-site` host, served at its `/git/` path) and the CI runner REST under `/ci/runner/` (`moqui_core::web::reserved::SERVED_ON_REFUSING_HOSTS`), so a site's own host can be its clone and runner URL. The first path segments the framework reserves on every host are one list, `moqui_core::web::reserved` (`ec.web.reservedPaths` to scripts, which adds the first segment of each servlet the conf declares, enabled or not: `/search`, `/dashboard`, PASS's `/trk` and `/trk-o`): a public site's routes never take one, git at a page's URL never starts with one, and a test fails for a host route that is not under it. `.well-known` and `ci` are reserved for pages only under the host's own sub-paths (`ec.web.reservedSubPaths`: `ci/runner`, `.well-known/caldav`, `carddav`, `agent-card.json`, `mcp.json`, `ai-catalog.json`), so a site serves its own `/.well-known/security.txt` or a page at `/ci`; a public site's route is checked by the path as written and as the screens resolve it (`..`). As a name that owns everything under it (a repository group, a mount, git at a page's URL) each stays reserved whole. The gRPC listener on its own port (`grpc-port`, `pass_authority_grpc_port`) is not by host and is not affected. A `root-screen` conf that cannot be read (an invalid host pattern) refuses the framework's routes on every host. With `include` the host gets `webroot.xml`'s screens and routes beside its own. A link made in a request (`ec.web.getWebappRootUrl`) uses the request's host only when the whole `Host` header is a plain host name (letters, digits, `-` and `.`) with at most a numeric port, a `root-screen` pattern other than `.*` names it and that root does not refuse the framework's routes; the one normalized value is checked and written, with the conf's scheme and port. Else the conf's `webapp_http_host`, as always outside a request. A public site whose root is also its host's root screen is still routed and bound by its `public-site`, and a request that no public-site route takes has no bound site: a `resolvedSiteId` parameter it sends is dropped.

There is no axum route for `/groovysh`, `/rpc`, `/elastic`, `/kibana`, `/htmlr`, `/vapps`, or `/h2`. `/fop`, `/search`, and `/dashboard` are servlet patterns on the fallback. `/status` is a screen transition. The conf has no `/groovysh` endpoint, and the obsolete Groovy Shell screen has been removed. The browser's Terminal UI runs the applications; the privileged SSH admin shell provides the JavaScript executor ([SSH and the TUI](Attack-Surface-SSH.md#ssh-and-the-tui)).

## Screen tree

The root screen `component://webroot/screen/webroot.xml` sets `require-authentication="false"` so subscreens decide. The default subscreen item is `qapps`. There is no `vapps` item. Schema documents are the REST transitions, which require a user and `REST_SCHEMA`.

Because the root screen does not require a user, static files served as that screen's content are reachable without a login. The shell references `/js` and `/libs`, and the root names `/favicon.ico`. The root's files are those of `webroot/screen/webroot/`: `css/`, `images/`, `js/`, `libs/`, `favicon.ico`, `MoquiLogo100.png`, `manifest.webmanifest`, `sw.js` and `README.md`. The rules for a file are in [Static files under a screen](#static-files-under-a-screen).

`qapps` is `require-authentication="false"` with extra path allowed, and its pre-actions redirect to `/Login` when there is no `userId`. The Assist drawer flag is `ec.llm.isEnabled()` and `hasPermission('AgentUse')`. `terminalUrl` is `/qapps/Terminal` only when `webapp_terminal_endpoint` is set.

### How a path is resolved and checked

A request path is resolved to its screens before any check (`ScreenUrlInfo::parse`, `crates/moqui-core/src/screen/url.rs`). The path is split on `/` first, and each name is then percent-decoded on its own, as a servlet decodes its path (`Getting%20started` is `Getting started`; a `+` is itself; an encoded `%2F` stays inside its name, and a name that does not decode to UTF-8 is kept as written). `.` and empty segments drop, `..` pops and never goes above the root, and a `~name=value` segment becomes a parameter, each read as written, so `%2E%2E` is a name and not a pop. The public-site route checks read the first names the same way (`/%61pps` is the apps). A link built back from the names encodes each once (`encode_path_name`: a space is `%20`, a `%` is `%25`). A path that starts with `//` is a search for the named screen anywhere under the root screen, to a depth of 24: `//tools` is `/apps/tools`. A `moqui.screen.ScreenPathAlias` row for the path replaces it; the row is read with authorization disabled. A name that is neither a subscreen nor a transition ends the walk at a file under the screen's directory, or at the screen when it allows an extra path.

The screens that render are the path's screens from the render start (`render_defs`). The render start is the root, unless the request's `lastStandalone` parameter (`true`, a positive N for the last N screens, a negative N), an always-standalone render mode, or a `standalone="true"` screen on the path moves it down. `check_authentication` and the login redirect look at every screen of the path, from the root (`path_requires_authentication`, `crates/moqui-core/src/screen/render.rs`, SEC-RTE-09): a screen under a parent that requires a user needs one, as a fragment too, whatever it says itself. A parent's `allow-web-request="false"` refuses a web request for a screen below it the same way, as a fragment too (`check_web_settings`), and a shared device's route check exempts a file only when no screen of the whole path needs a user (`device.rs` `check_route`). `lastStandalone` is one of the two query parameters a transition with actions accepts ([CSRF](Attack-Surface-Web.md#csrf)).

Artifact authorization is required only of the last screen of the path, and only when that screen requires authentication; the screens above it are pushed without a required record. A transition's frame requires authorization only when its own screen requires authentication. A subscreens item limited to a user group (`SubscreensItem.userGroupId`) refuses the path for a user outside the group. What a level above the last screen answers is in [Parent frames](Attack-Surface-Web.md#parent-frames).

Every request parameter is put in the screen context under its name, except `context`.

A screen with a `condition` and no `fail-widgets` is left out of menus when the condition fails (`menu::offered`). Asked for by its path it is authorized as any screen, then writes `<title> is not offered here.` in place of its widgets and does not run its actions. The condition is not part of authorization: the screen's transitions and the screens below it do not evaluate it.

A failed request answers JSON `{errorCode, errors}`, or the webapp's `error-screen` for the status when the client accepts `text/html` and the first path segment is not `rest`, `rpc`, `status`, `error`, `health` or `metrics`. In production a 500 carries only an error id; any other status carries the error's message. A 404 of the screen walk says `screen path not found: <name> under <screen location>` to a signed-in user, and only `screen path not found` to nobody signed in (`url.rs` `not_found`, SEC-RTE-13). The path is resolved before the user is checked, so a path that does not exist is 404 and one that exists is a login redirect or 401. The error screens escape what they show; `showErrorDetail` is true only outside production for a signed-in user. `ec.web.sendError` writes the request path and message html-escaped.

### Transitions every screen has

Every screen has five transitions it does not declare: `actions`, `formSaveFind`, `formSelectColumns`, `screenDoc` and `scanResolve` (`crates/moqui-core/src/screen/definition.rs`). `actions` takes any method, is `read-only` and is not checked for the session token. It answers only for a screen eligible as a server-static template (`statics.rs` `sends_package`: its eligibility with the qvt macro module of the path, or a forced static report); for any other screen it answers 404 and runs no actions (plans/Security-Review.md SEC-RTE-02). For an eligible screen it runs the pre-actions of the path, the screen's actions and its sections' actions, and answers as JSON only the context names the screen's compiled template reads (recorded when the template is built, and the template built for an `actions` request that comes first; none when it cannot be built), `hideNav` and the names the actions that ran list in `client-context` (the always-actions of every screen on the path, the pre-actions that ran, the screen's actions and its sections'), each sent whole, with the credential parameter names of `web::CREDENTIAL_PARAMETER_NAMES` removed as a second line (`run_actions_transition`, `screen_package`). `actions/<form>` (one form-list's rows) and a tree's nodes are served for every screen: rows to the qvt static form-list and list views (a board's rows, a calendar's range, a tree's children), tree nodes to the html and tui clients too. Each row keeps only the template's names (for a server-static screen; none for another), the form's fields and their display texts, the fields its row-selection and views name, what the client reads of a row and its `row-actions` `client-context`. `formSaveFind` and `formSelectColumns` are `POST` with the session token and write the caller's saved finds and columns. `screenDoc` and `scanResolve` are `read-only`. Each is authorized as a transition of its screen: with no required record when the screen does not require authentication. For such a screen `actions` answers a caller with no user when the screen is server-static; `/Login` is not, so `/Login/actions` is 404.

`webroot/template/screen/BasicTransitions.xml` is a library a screen takes transitions from with `transition-include`; an included transition keeps its attributes and is authorized as a transition of the including screen. `emailScreenAsync` (not `read-only`, so it takes a POST with the session token) calls `org.moqui.mail.EmailServices.send#ScreenRenderEmail` asynchronously with a fixed set: the request's `toAddresses`, `title`, `screenRenderMode` and `fileName` (no template, Cc or Bcc from the request); the screen rendered is the including screen. The screens that include it and what the service does are in [Send services](Attack-Surface-Mail.md#send-services). `emailScreenUserAsync` sends to the user's own address. `getEnumRelatedByTypeList` reads `moqui.basic.Enumeration`.

### Static files under a screen

A file under the directory beside any screen on the path (`X.xml` and `X/`) is sent when the next path name is not a subscreen or a transition (`crates/moqui-core/src/screen/static_files.rs`). A file is sent after `check_authentication` of the screens that render and with no artifact authorization, so a file under a screen that requires authentication goes to any signed-in user. A file is refused when a name is empty, starts with `.`, or holds `/`, `\`, NUL, `:` or a control character, as the walk decoded it or percent-decoded once more; when its extension is `xml`, `ftl`, `fancy`, `fancy-locked`, `groovy`, `java`, `kt`, `properties` or `sql`; when it is a screen's source (`X.qvue` beside `X.xml`, `X.tui.json`, a file a `render-mode` text names); or when its canonical path is outside the screen's directory. Only `GET` and `HEAD` are served. A `?v=` query or `.min.` in the name gives `Cache-Control: public, max-age=31536000, immutable`.

### Token routes

Token routes are not framework-default paths. `runtime/components/addon/mr-boss/MoquiConf.xml` adds them on the `webroot` webapp, and `runtime/components/base/basic-comms/MoquiConf.xml` adds `call`. `screen/mod.rs` sends a match to token-route dispatch before the ordinary screen and before the public-site route of the request. A path is under a token route only when the segment after the route's name is 8 to 128 letters, digits, `-` or `_` (with `.qvt`, `.qvue` or `.qjs` allowed after it); any other path falls to the ordinary screens. The token service runs first, with `token` and `routeName`. A token it does not accept, or a service that fails, answers 404 with `Cache-Control: no-store`: a short html page for a browser, `{"errorCode":404,"errors":"This link has expired or was not found."}` otherwise. Nothing of the screen runs. The dispatch (`crates/moqui-core/src/screen/token_route.rs`) does not count the refusal as a failed sign-in: it does not call `web::note_auth_failure`. A `token` or `tokenRoute` request parameter is replaced. A route named `apps`, `qapps`, `rest`, `rpc`, `status`, `error`, `health`, `metrics`, `fop`, `js`, `css`, `libs`, `images`, `Login`, `sso`, `notws` or `Device`, or with a `/` in its name, is left out with an error log. A shared device's request never reaches a token route.

mr-boss also adds per-client rate limits: `request-form` on `POST /r/*/submit`, 5 requests in 60 seconds, burst 5; and
`invitation-accept` on `POST /i/*/*` (an invitation's account and factor steps), 10 requests in 60 seconds, burst 5.
They apply when per-client web protection is on.

A route's token is its credential, so it is kept out of what the server records. The request log (each request's SERVER
span) has `/i/:token/...` for `url.path`, and for a path or URL under a token route in the `Referer` header and in a
query value such as a sign-in step's `returnTo` (`screen::token_route::redact_url`). The log lines that name a request
path (a refused origin, the public-site host check) are redacted the same way, and so are a Visit's `initialRequest`
and `initialReferrer`. Browser telemetry (`/rum/traces`, `/rum/logs`, `/rum/replay`) has every string redacted before
it is stored, a replay's `url` and the links its rrweb snapshot holds included (`token_route::redact_json`). The routes
are read per conf generation, so a route a conf reload adds is redacted from then on. The route name and the rest of
the path stay (`/u/:token/oneClick`). A component may also declare a path segment that holds a bearer
token with a `token-path` of the webroot webapp (`/preview/{token}` at the root, `/**/held-mail/{token}` after any
segments, such as a mount's; the components' `token-path`s are merged): that segment is recorded as `:token` in the
same places, as for a token route (`token_route::TokenPath`, `redact_path`). mr-pass declares its held mail, held
report and preview paths. `http.route` is the screen's location, which holds no token. The session keeps a
sign-in step's `returnTo` with its token (it is where the user goes next); a session is not a record.

While a token route's screen renders it is the root of its links (`web::set_link_prefix`): a form's action, a link and a
transition's redirect to a screen go to `/<name>/<token>/...`, not to `/<transition>` outside the route. A plain URL
(`/Login`) is not prefixed, and no request parameter or header sets the prefix: only the token route's dispatch does,
after its token check. A server-static qvt template is cached for every visitor, so it is made with no prefix
(`screen::statics::serve_template`) and its paths, an alias transition's target included, are still from the screen; a
token route's screen that needs links under the route should not be server-static. A `screen-last` path the session
saves (the page before a login) is from the screen as well.

Entity REST (`entity/query_rest.rs`): a find of a restricted generic entity is unauthorized. Writes of identity-admin entities, of `UserAccount`, of the audit entities (`DatabaseAudit`, `SqlRunToken`, `DatabaseConnection`, the ETL entities) and of the service-written entities (`sensitive.rs` `SERVICE_WRITTEN_ENTITY_KEYS`: `EntityAuditLog`, the Monitor recovery, drain and ingest-key rows, scrape targets and synthetic checks) and the hosted-instance configuration entities are refused (`is_generic_write_refused`). Secret-config entities are writable only when the caller is in `ADMIN`. Results pass through `strip_user_account_secrets`, whose names are `currentPassword`, `resetPassword`, `passwordSalt`, `passwordHashType`, and `passwordBase64`, and each encrypted field is answered as `<field>IsSet` (true or false), never its value (`RecordGuard::Answer`; plans/Security-Review.md SEC-DAT-03, fixed). A request takes no condition or order on a password or encrypted field ([Finds from request parameters](Attack-Surface-Data.md#finds-from-request-parameters)). `pageNoLimit` is removed from the parameters. `entity-facade` `rest-max-page-size` is 1000. With no `pageIndex` or `pageSize` a list is 100 rows. A `pageSize` above `rest-max-page-size` is replaced by it, and the offset is `pageIndex` times it.

The entity REST transitions do not require authorization, because the REST screen does not require authentication. Each entity operation needs its own `AT_ENTITY` record, or an `authorize-skip` on the entity that covers the operation ([Entity authorization and row filters](Attack-Surface-Data.md#entity-authorization-and-row-filters)). In the base components `authorize-skip="view"` is on `LocalizedMessage`, `LocalizedEntityField` and the four `DbViewEntity*` entities. A write runs the implicit entity-auto service, which has no service authorization of its own. `EntityAuditLog` has no `authorize-skip` and is in the write refusal list, so `/rest/e1` never writes it (SEC-RTE-03, fixed). `orderByField` names are kept only when they are fields of the entity, and are written as quoted identifiers. Conditions are made from the entity's own field names, a fixed set of `_op` operators and bound values. `dependents=true` (two levels), `dependentLevels=N` and `master=name` add the related records of each row. The restricted-entity rule is applied to the entity the path names and to each related entity the expansion reads: one the generic read rule refuses (`UserLoginKey`, `UserAuthcFactor`, `UserPasswordHistory` below `UserAccount`) is skipped, and each nested record is concealed as the top one (`push_related`; SEC-RTE-06, fixed). Extra path names after the key are relationship names; the entity they end at is the one checked.

A `POST` with `X-HTTP-Method-Override` runs as the named method, for the path authorization and the operation, on `/rest/e1`, `/rest/m1`, `/rest/v1` and `/rest/s1` (`screen/dispatch.rs`). The session token check uses the real method.

Service REST (`crates/moqui-core/src/service/rest.rs`): REST files are the `*.rest.xml` of each component's `service/` directory. A later file with the same root name replaces an earlier one, with a log line. A `<service>` of a method runs after the path's check and the user check, under the service's own `authenticate` and its `AT_SERVICE` authorization. The path grant is inheritable, so the service a path names runs under it. Naming a service in a REST file is what makes it reachable here; the service's `allow-remote` attribute is not read ([Services and `allow-remote`](Attack-Surface-Web.md#services-and-allow-remote)). The whole request parameter map (query, body, path ids) is the service's input. A JSON array body of objects runs the operation once per element, each with the request's other parameters; the number of elements is bounded only by the body limit. An unknown child resource answers 404 with the names of the resources at that level to a signed-in caller, and `Resource not found` to nobody signed in (SEC-RTE-13). A resource or method with `false`, `anonymous-all` or `anonymous-view` needs no user and no `AT_REST_PATH` record; the `anonymous-*` modes log the anonymous user in and mark the path frame inheritable.

An `<entity>` operation of a REST file (`list`, `one`, `count`, `create`, `update`, `store`, `delete`) refuses identity-admin and audit entities. A secret-config entity (`EmailServer`, `SystemMessageRemote`) is readable on a declared resource and writable only by a caller in `ADMIN`. A `UserAccount` write drops the password fields, and the identity fields unless the caller is in `ADMIN`. A result omits the five `UserAccount` password fields and answers each encrypted field as `<field>IsSet`, in masters too (`GenericAccess::conceal`, `guarded_master_value`). A `list` drops `pageNoLimit` from the request, returns 100 rows when no page is asked for, and caps a page at `rest-max-page-size` (SEC-RTE-14).
