# Attack surface: data and stored secrets

The database, field encryption, generated secrets, and the threat model for stored secrets. This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## Database

The transactional datasource's `database-conf-name` `embedded` (the default; also empty and `h2`) selects the embedded Postgres cluster. There is no H2 driver and no H2 TCP server.

Embedded Postgres is on when the entity datasource is embedded and the build has `embedded-postgres` (Dev, Lite, Maximal). The cluster directory is `runtime/db/embedded` and the data directory is `runtime/db/embedded/data`, mode `0700`. On Unix there is no TCP: `listen_addresses` is empty. The socket directory is the data directory, or `moqui-pg-<FNV-1a hash of the data directory path>` under the temp directory (`/tmp` when the temp path is not shell-safe) when the data directory path has a character outside `[A-Za-z0-9/._+@%:,-]`. That directory is created with mode `0700` when it is missing; the start refuses one that is not a directory of this user with mode `0700` (`embedded::socket_dir_private`; `crates/moqui-drivers/src/embedded.rs`, `launch`, `socket_dir_for`). `PORT` 5432 names the socket file `.s.PGSQL.5432`. A second postmaster (search, or the sim overlay) uses the same socket recipe. The client uses the bootstrap superuser and the password in the cluster `pgpass` file, over the Unix socket with no TLS. No other role is made: every entity group's pool on the cluster connects as that superuser (`crates/moqui-drivers/src/entity_facade.rs`; `embedded.rs`, `driver_for`), so the Tools SQL runner, a grid SQL source and an ETL SQL source run as it, and a read-only run is only `SET TRANSACTION READ ONLY` (`crates/moqui-entity/src/driver.rs`). This tree does not set `unix_socket_permissions`. `pg_hba.conf` is what `initdb --auth password` writes (`postgresql_embedded` 0.22): method `password` for local and loopback connections. On Windows the same default listens on `127.0.0.1` and an ephemeral port.

The superuser password is the text of `runtime/db/embedded/pgpass`. MR Moqui writes it with mode `0600` before the setup (which then leaves it), or makes it `0600` when it is there (`embedded::private_password_file`), and each start reads it back. The wire client (`crates/moqui-drivers/src/pgwire.rs`, `authenticate`) answers a cleartext, an MD5 and a SCRAM-SHA-256 request with the same password, and uses no channel binding. `pg_dump`, `pg_restore`, `pg_basebackup` and `pg_verifybackup` get the password in `PGPASSWORD` of the child process. A `pg_dump` writes into a partial file made `0600` before it runs (`backup::private_partial`); a published backup directory is `0700` and its files `0600` (`crates/moqui-drivers/src/backup.rs`).

External Postgres or MySQL is off unless the transactional datasource's `database-conf-name` is `postgres`, `mysql`, or `mysql8`. This process is a client: nothing in the tree listens on the Postgres protocol (`pgwire.rs` is a client only). Omitted ports default to 5432 and 3306. TLS is on unless the datasource's `sslmode` is `disable` or `disabled`, or a `jdbc-uri` has `useSSL=false`, and there is no fallback from TLS to a plain connection. On Postgres an empty `sslmode`, `verify-full`, `allow`, `prefer` and any unknown value check the certificate's authority and host name. `verify-ca` checks the authority only, and without the datasource's `sslrootcert` the authorities are the whole `webpki-roots` set, so a certificate any public authority issued, for any name, passes (`pg_tls.rs`, `AnyName`); libpq's `verify-ca` trusts only the root file and refuses to run without one. `require` encrypts and accepts any certificate (the handshake signatures are still checked), unless the datasource's `sslrootcert` is set, and then it checks as `verify-ca`. A MySQL datasource takes only on or off from `sslmode`: `entity_db::mysql_driver` passes the driver no TLS options, so `require`, `verify-ca` and `sslrootcert` have no effect and the certificate is always checked, host name included, against the `webpki-roots` set; a server with a private authority connects only with `disable` (`crates/moqui-entity/src/entity/datasource.rs`, `tls_verify`; `crates/moqui-drivers/src/pg_tls.rs`; `crates/moqui-drivers/src/entity_db.rs`, `mysql_driver`; `crates/moqui-drivers/src/mysql.rs`, `ssl_opts`).

A connection made from a conf map (`crates/moqui-drivers/src/lib.rs`, `conf_driver`: the Tools external connections of `crates/moqui-tools/src/ext.rs`, and a script's conf map, InstanceServices) takes the same modes, with these differences. With an empty mode a MySQL connection has no TLS, and neither has a Postgres connection to `localhost`, `127.0.0.1` or `::1`; an external connection's own empty mode is `verify-full` for a host that is not loopback (`ext.rs`, `ssl_mode_of`). On MySQL the `sslrootcert` file is trusted beside the `webpki-roots` set, not instead of it (the `mysql` fork, `rustls_io.rs`), and `verify-ca`, or `require` with a root file, skips the host name. A host that starts with `/` is a Unix socket directory. Over plain TCP, MySQL's `caching_sha2_password` full authentication asks the server for its public key and encrypts the password to the key it gets; over TLS it sends the password itself.

Whatever the mode, the Postgres client answers a server's cleartext, MD5 or SCRAM request with the password (`pgwire.rs`, `authenticate`; there is no `require_auth`), so on a connection that is not `verify-full` a man in the middle that passes the certificate check asks for the cleartext password and gets it. What a database server sends back (the server of an external connection, which its owner names; a man in the middle; a compromised server): its values decode with bounds checks, and a notice is logged at info level as it was sent. A message has no size limit: `Message::parse` (`postgres-protocol` 0.6.12) reserves the length the header gives before the bytes arrive, so one header asks for up to 4 GiB, and an allocation that fails aborts the process; the MySQL fork reserves a result's column count as the server sends it, before it reads a column. A reply's rows are kept with no row or byte limit until `ReadyForQuery`: the read timeout bounds one read, and the SQL tools' row limit is applied after the rows came. The Postgres connect, TLS and startup must finish in 10 s and a cancel in 5 s; MySQL's connect is 10 s, a read 600 s (or `read-timeout`) and a write 60 s (`mysql.rs`). The crates that parse a server's bytes are `postgres-protocol` 0.6.12, the `mysql` fork `moqui/rust-mysql-simple` with `mysql_common` 0.37.3, and `rustls` with `rustls-webpki`; the fork is a git dependency, outside what the `cargo deny` advisory check covers.

A database error's text: a Postgres `ErrorResponse` is `postgres <context>: <message>`, with the server's error as its source, whose text adds a `DETAIL:` and a `HINT:` line (`pgwire.rs`); MySQL's is `mysql request failed` with the server's error. The `DETAIL` of a key violation is `Key (<column>)=(<value>) already exists`, and of a not-null or check failure `Failing row contains (...)`, every column of the row as written. An error that leaves a request as a 500 answers an error id in production and `client_text` of its message on any other instance purpose (`crates/moqui-core/src/web/mod.rs`, `error_text`). A failure inside a service is added to the message facade with the text of every cause (`crates/moqui-core/src/service/call.rs`, `record_failure`) on any instance purpose; `client_text` drops only the lines that start with white space, so the `DETAIL` line stays, and Service REST and a screen's JSON answer return the facade's errors to the caller with 400 or 500 (`crates/moqui-core/src/screen/dispatch.rs`). A data load's failure goes into the load's messages with its whole cause chain, which Data Load shows its user on any instance purpose (`crates/moqui-core/src/script/host/tools.rs`, `load_data`).

## Field encryption

`entity-facade@crypt-pass` ships as `MoquiDefaultPassword:CHANGEME`, a generated secret of the conf schema. The algorithm is `PBEWithHmacSHA256AndAES_128`, salt `20201202`, 10 iterations. The same secret encrypts an OAuth refresh token and a client secret stored on `EmailOAuthProvider`, the SSO client secrets (`OauthFlow.secret`, `OidcFlow.secret`), the SAML keystore and private key passwords, and a calendar publish link's token (`CalendarShare.publishToken`, still found by value since the encryption is deterministic). Alternate decrypt still tries `PBEWithMD5AndDES` with the current pass and with `entity-facade@crypt-pass-old`, and the AES algorithm with the old pass. The old pass ships as the same `CHANGEME` sentinel and is not replaced by the generator. What this encryption protects, and its known gaps, are in [Threat model: stored secrets](#threat-model-stored-secrets).

## Secrets

Startup, before listeners, replaces each conf attribute the conf schema marks a generated secret (`Secret::Generated` in `crates/moqui-core/src/context/conf_schema.rs`) whose value still ends in `CHANGEME` after the environment and `runtime/.env` are applied (`crates/moqui-core/src/context/conf_env.rs`, `generate_secrets`). The value is 32 CSPRNG bytes, base64, written into `runtime/.env` under the attribute's environment name (`moqui_conf__entity_facade__crypt_pass`). Each write replaces the file through a sibling of mode `0600`, so the file is `0600` after any write. An unwritable `.env` fails startup. `entity-facade@crypt-pass-old` is kept, not generated: its sentinel stays. `cluster-member@tls-cert` and `cluster-member@tls-key` are generated as a pair when `cluster-tls` is on, which it is in every server package. The generated secrets are `entity-facade@crypt-pass`, `acme@account-key`, `ssh-server@host-key`, `git-server@lfs-token-key`, `chat@store-key-secret`, `media-server/turn-server@auth-secret`, `channels@media-key`, `xmpp-server/upload@secret`, `xmpp-server@scram-decoy-key`, `webapp-list/webapp[webroot]/session-config@cookie-key`, `push/web@vapid-key` and `edge@link-key`. The key is then on the same host as the data it protects; see [Threat model: stored secrets](#threat-model-stored-secrets). Three of their consumers were read: `ssh-server@host-key` must be the base64 of exactly 32 bytes, an Ed25519 seed (`crates/moqui-host/src/ssh/server.rs`); `push/web@vapid-key` is the seed of the VAPID key (`web_push.rs`), and its bytes are also the key of the chat push collapse keys (`chat_push.rs`), one secret for two uses; `acme@account-key` is a seed (`crates/moqui-host/src/acme/order.rs`).

A conf attribute holds a secret when the conf schema marks it (generated or kept, such as `push/fcm@service-account` and `pass-authority/client[id]@secret`), or when its name is or ends in `password`, `pass`, `secret`, `api-key`, `token-key`, `state-key` or `private-key` (`conf_schema::attribute_secret`). An override or a generated value is applied into the merged conf, so the running conf holds secrets: the boot log names a secret override without its value, and System › Conf (`crates/moqui-core/src/context/conf_reload/view.rs`) and a conf reload's report (`conf_reload/diff.rs`) mask each secret attribute. A script reads the conf with `ec.factory.getConfValue(selector)`, which answers null for a secret; `System.getProperty(name)` refuses every `moqui_conf__` name and every name that reads as a secret (`crates/moqui-core/src/context/identity.rs`, `script_refused_property`). No Tools or System screen lists the properties or the environment: the screens have no `getProperties` or `getenv`, and nine System screens read named properties with `System.getProperty`. The LLM endpoints' keys (`llm-facade/endpoint[anthropic]@api-key` and the others) are secrets by their name.

## Entity authorization and row filters

A find adds `EntityFilter` conditions only when all of these hold (`crates/moqui-core/src/user/filter.rs`): an execution context is entered, the entity name does not start with `moqui.`, authorization is not disabled on the context, `AT_ENTITY` authorization is enabled, and the artifact frame on top of the stack was authorized by an `ArtifactAuthz` record that has `ArtifactAuthzFilter` rows. So these finds get no filter:

- a find with authorization disabled (a service or job that disables it, a data document feed, an edge replication read);
- a find of a `moqui.*` entity;
- a find whose authorizing frame has no record, or a record with no filter set.

For a find that qualifies, each filter set of the record is taken in turn:

- A set whose `applyCond`, on `ArtifactAuthzFilter` or on `EntityFilterSet`, evaluates false is skipped, and its filters are not applied.
- An `EntityFilter` applies to a find of its `entityName`, and to a find of a view that has that entity as a direct member. Other finds do not evaluate its `filterMap`.
- On a view the condition goes on the alias of the filtered member field (`map_conditions`). With two members of the filtered entity aliased (two `Party` members), each member is held to the whole map on its own and the members' conditions are ANDed (`conditions_for`): `MANTLE_PRIVATE_CONTACT` becomes `(from is null or from = me) and (to is null or to = me)`, so a row with one shared party and one of the caller's own personal contacts is its owner's (SEC-DAT-11, fixed). With no such alias the find gets `1 = 0`, unless the set has `allowMissingAlias="Y"`, and then that field's condition is left out, logged as a warning the first time for each view and field (`filter.rs` `note_missing_alias`, SEC-DAT-11).
- An error while evaluating an `applyCond` or a `filterMap`, an unknown comparison, or a missing alias without `allowMissingAlias` adds `1 = 0` to the find and logs `entity filter failed closed`.
- A null value in a `filterMap` is `IS NULL`. An empty list is `1 = 0`.

The conditions are added by `one`, `list`, `count` and `iterator`, and so by the read of `updateAll` and `deleteAll` (`crates/moqui-entity/src/entity/find.rs`, `combined`). A create, update or delete of a value by its primary key is not filtered. A find that a filter may change is not read from the shared entity cache. A view that is not in the entity model (a data document's view) is filtered through its own definition (`apply_view_filters`).

The filters are those of the one `ArtifactAuthz` record in the top frame's `AuthInfo`; the sets of two matching records are never combined. A new frame takes its record in this order (`crates/moqui-core/src/user/authz.rs`, `is_permitted`): the frame below, unchanged, when that is an inheritable `AUTHZT_ALWAYS` for the action; else the user's first matching `AUTHZT_ALWAYS` record; else the last matching `AUTHZT_ALLOW` record, since each match replaces the one before; else the frame below when it is inheritable. The user's records are read group by group in group-id order (`load_group_checks`), so of two matching allow records, one with a filter set and one without, the one of the later group id decides.

The seeded sets: `MANTLE_USER_ORG` has no `applyCond`. `MANTLE_ACTIVE_ORG` has `applyCond="activeOrgId"` and `allowMissingAlias="Y"`. `MANTLE_PRIVATE_CONTACT` has `allowMissingAlias="N"` (`runtime/components/addon/mr-mantle/data/MantleSetupData.xml`), and the views over `Party` alias `privateOwnerUserId`. `COMMERCE_STORE` has `applyCond="ec.user.context.commerceStoreIds != null"` and `allowMissingAlias="Y"` (`runtime/components/addon/mr-boss/data/BossSetupData.xml`). `BOSS_PROJECT_CLIENT` has `allowMissingAlias="N"`.

`filterOrgIds` is set by `mantle.party.PartyServices.setup#UserOrganizationInfo`, which returns without setting it when the account has no `partyId`. An unset name is null (`docs/dev/JS-Globals.md`), so a `MANTLE_USER_ORG` map written `({organizationPartyId: filterOrgIds})` (`AcctgTrans`, `FinancialAccount`, `Facility`, `ProductStore`, `Agreement` and others) is `IS NULL` and reads the rows with no organization, and the `Invoice` and `Payment` maps (`joinOr="Y"`) the rows where either party is null; a map written `filterOrgIds || []` gives `1 = 0`.

## Finds from request parameters

`EntityFind::search_form_map` (`crates/moqui-entity/src/entity/search_form.rs`) turns a parameter map into conditions, order and paging. For every field of the entity, and every alias of a view, it reads `<field>`, `<field>_op` (`equals`, `like`, `contains`, `begins`, `empty`, `in`), `<field>_not`, `<field>_ic`, `<field>_period` with `_poffset` and `_pdate`, and `<field>_from` and `<field>_thru`. `orderByField` is a comma list of field names. `pageIndex` and `pageSize` page the find; the default page is 20 rows and a request's `pageSize` is held to `rest-max-page-size` (1000). `pageNoLimit=true` (a screen's CSV, XLSX, print or text export) removes the offset and reads at most `entity-facade` `screen-max-rows` (100,000). A limit the caller's code set on the find is its own (SEC-DAT-09, fixed). Values are bound parameters. Request input takes no condition and no order on a password field (by name or origin), and no order, pattern, range or period on an encrypted field (`GenericAccess::hidden`); an `equals` on an encrypted field stays for a screen's or script's own find (its bound value is encrypted before SQL, so it matches the stored value) and is refused on a generic find (`EntityFind::generic_input`: entity REST, Service REST entity resources, the data grid, `searchFormMap`'s `genericInput`, an `entity-find` whose entity name is expanded). A field in a screen's `skip-fields` is refused as an `orderByField` from the input too. The caller's own defaults and default order still may name any field (plans/Security-Review.md SEC-DAT-01, fixed).

Its callers:

- A screen's `<search-form-inputs>` (`searchFormInputs`, `crates/moqui-core/src/script/host/entities.rs`). The default input is the whole script context, request parameters included, and no skip list is passed.
- Entity REST (`crates/moqui-entity/src/entity/query_rest.rs`): [REST](Attack-Surface-Routes.md#rest). It removes `pageNoLimit`, reads 100 rows when no page is asked for, and replaces a `pageSize` above `rest-max-page-size` (1000) with it.
- A Service REST entity resource (`crates/moqui-core/src/service/rest.rs`, `find_entity`, `count_entity`). It drops `pageNoLimit` from the request, reads 100 rows when no page is asked for and caps a `pageSize` at `rest-max-page-size` (SEC-RTE-14). A screen's `pageSize` is held to it as well, through `search_form_map`.
- The Tools data grid (`crates/moqui-tools/src/grid.rs`). It refuses a sort, filter or condition on a `UserAccount` password field or an encrypted field (`hidden_value`).

## Entity definitions from database rows

An entity name the file model does not have is looked up as a `moqui.entity.view.DbViewEntity` row or as `DataDocument.<dataDocumentId>` (`crates/moqui-entity/src/entity/derived.rs`). The definition rows are read with authorization disabled and outside the caller's transaction. A find of such a view is not read from the entity cache. A `DbViewEntityAlias` row gives the alias name, member alias, field and `functionName`; a `DataDocumentField` row gives a `functionName` too. A `DbViewEntityAlias` or `DataDocumentField` `functionName` must be one of `derived.rs` `ROW_VIEW_FUNCTIONS` (min, max, sum, avg, count, count-distinct, upper, lower); another refuses the view (logged, not found) or the document (`check_row_function`, SEC-DAT-04). The report dataset services take the same list (`crates/moqui-report/src/business.rs` `FUNCTIONS`). A view defined in XML is code, and its function is checked only as one word of ASCII letters, digits and `_` (`crates/moqui-db/src/sql/view.rs`, `check_word`). The Tools screens that write these rows are in [Tools and System](Attack-Surface-Tools.md#tools-and-system).

## Export, snapshots and EntitySync

`ec.entity.makeDataWriter()` (`crates/moqui-entity/src/entity/data_writer.rs`) writes entities as XML, JSON or CSV to text, a file, a directory or a zip. Without `full(true)` it skips the restricted entities (one message naming them) and writes no password or encrypted field, in dependents and masters too (`RecordGuard::File`); with it, it writes every field as the facade reads it, encrypted fields decrypted and `UserAccount` password hashes. The script host's `makeDataWriter` sets `full` only for a holder of the sealed `ADMIN_BACKUP_DOWNLOAD` (`ADMIN` in the seed), so Tools Export and Snapshots are whole for such a holder and carry no secrets for anyone else (SEC-TLS-05, fixed). A target file is created new (`File::create_new`) with the mode the process umask gives, and a zip target's missing parent directories are created.

`org.moqui.impl.EntityServices.export#EntityDataSnapshot` writes `runtime/db/snapshot/<baseFilename>.zip`; with no entity list it writes every entity. The service refuses a `baseFilename` that is not one safe path segment (`WebUtilities.isSafeSinglePathSegment`, SEC-TLS-07). `import#EntityDataSnapshot` checks `zipFilename` with `isSafeSinglePathSegment`. A zip data file is read entry by entry; a nested zip is at most 256 MiB and four levels deep. Only when `restrictSensitiveEntities` is set does the data loader refuse, before any write, a record of an entity a generic write refuses (`crates/moqui-entity/src/entity/sensitive.rs`, `is_generic_write_refused`: the identity-admin, secret-config, audit, host-config and service-written entities, by canonical name, on the XML, JSON and CSV paths) and every service element (`crates/moqui-entity/src/entity/load_feed/loader.rs`); `UserAccount` is not on those lists. A check or a list by the loader (`check`, `checkInfo`, `list`) applies that refusal first too, and a check compares no password or encrypted field and refuses an entity, or a view over one, that a generic read refuses (`check_tree`, `load_feed/check.rs`), so it answers no stored value of one. `put#EntitySyncData` sets `restrictSensitiveEntities`. A snapshot import does not: it writes a record of any entity, by default with entity ECA rules and the audit log off, and calls a service element (a defined service or any `verb#noun`) with authorization disabled (`crates/moqui-core/src/service/eca.rs`), as a seed load and `moqui load` do. The Tools screen that starts, downloads, uploads and imports snapshots is in [Tools and System](Attack-Surface-Tools.md#tools-and-system).

The data loader (`crates/moqui-entity/src/entity/load_feed/`) takes as a location any host path, or a `file:`, `classpath:` or `component://` location (`..` kept), and never a URL; a directory loads every `.xml`, `.csv`, `.json` and `.zip` in it, and another extension is refused (`loader.rs`; `crates/moqui-core/src/context/locate.rs`). A record's values are bound field values, a service element names a defined service or a `verb#noun`, and entity ECA rules come only from the components' `*.eecas.xml` files, never from a data file. The XML reader takes no DOCTYPE in an element and no entity beyond the five and character references (a prologue DOCTYPE is skipped) and nests at most 256 deep; JSON nests at most 128. One streamed element of an `entity-facade-xml` file, or one JSON value, is at most 64 MiB, but a file whose root is another element is read whole and parsed as one tree, a zip entry inflates as it streams, and the CSV reader has no record or field limit (`xml.rs`, `csv.rs`, `pull.rs`). A load's `disableEntityEca`, `disableAuditLog` and `disableDataFeed` switch those off for the writes of the thread that runs it, in a scope that puts back what was set before when it ends, by an error or a panic too, so loads that overlap or nest leave nothing off (`WriteSwitches`, `crates/moqui-entity/src/entity/facade.rs`; `load_data`, `crates/moqui-core/src/script/host/tools.rs`); another thread's writes keep their entity ECA rules, audit rows and feed. Under a load's `disableEntityEca` every rule that calls a `UserSecurityChecks` assert still runs (`is_security_check`, `load_feed/eca.rs`): the privileged-membership and sealed-grant checks of `Security.eecas.xml`, and the stored script, template, expression and translation checks. They pass when authorization is off, so a snapshot restore, an administrator's whole-database operation, runs with authorization off: the `ImportEntityDataSnapshot` job, and the wrapped import of `run#LoadWrap` after its own `DATABASE_ADMIN` check (`DatabaseLoadServices.xml`). The facade's own flags, which a boot or a test sets, turn every rule off for every thread. Each service element a load calls is kept, with its parameters, in a list on the facade that only tests read and nothing clears.

`org.moqui.impl.EntitySyncServices.get#EntitySyncData` and `put#EntitySyncData` are reached at `/rest/s1/moqui/entity/syncs/data/get` and `.../put` (`runtime/components/base/tools/service/moqui.rest.xml`), under the `/moqui` REST path authorization, which the seed gives to `ADMIN`. `get` takes `entityIncludeList` from the caller, with entity names and filter maps, skips a restricted entity (logged), and returns the records as `entity-facade-xml` text built in memory with no password field and no restricted related record (`RecordGuard::Replica`); encrypted fields are decrypted, as a replica needs them, and `recordThreshold` is at most 10,000. `put` loads `entityData` with the restricted-entity check, refuses the service-written entities, a password field (`LoadOptions::refuse_password_fields`), `moqui.service.job.*` and service elements (`crates/moqui-core/src/service/system_sync/entity_sync.rs`; SEC-DAT-08). An outbound sync posts JSON to `<targetServerUrl>/rest/s1/moqui/entity/syncs/data/<op>` with `Authorization: Basic` of `targetUsername` and the decrypted `targetPassword`; the target is held by the row rule of `allowPrivateNetwork` ([The internal-address guard](Attack-Surface-Outbound.md)).

## Search index

`ec.search` (`crates/moqui-core/src/script/host/search.rs`) gives every script every search store by name: the target is the `documentType` or `indexName` the script passes, and only the browser replay store is refused. The telemetry stores (`otel_spans`, `otel_logs`, `otel_metrics`, `otel_errors`, `monitor_annotations`) are targets with no `DataDocument` row (`crates/moqui-core/src/search/mod.rs`). The facade checks no user and no authorization. A row filter is there only when the caller passes `request.filter`, and that trusted filter is ANDed into every statement: the count, the page, the semantic and each hybrid branch, and OpenSearch. Values are bound parameters, a field name reaches SQL only through the store's mapping (an unknown name is `FALSE`; `search/postgres/compile.rs`, `locate`), and `LIKE` patterns escape `\`, `%` and `_`. A query cannot name another store: the target is the caller's list, and an OpenSearch index name is in the URL path.

`org.moqui.search.SearchServices.search#DataDocuments` checks nothing of its caller: no authorization of the document's primary entity, and no row filter unless the caller passes `filter`. Given a `documentType` it drops `indexName` and searches the type named (`runtime/components/base/framework/service/org/moqui/search/SearchServices.xml`). It is reached by `POST /rest/s1/moqui/dataDocuments/indexes/{indexName}/search` (under the `/moqui` REST path), the Marble search screens and lookups, `mantle.GeneralServices.search#MantleFiltered`, `mantle.party.PartyServices.search#Party` (`GET /rest/s1/mantle/parties/search`), `mantle.work.ProjectServices.get#ProjectParties`, and the shop (`ShopCatalog.js`, which escapes the visitor's text and keeps published products only). Marble's `Search.xml` and `QuickSearch.xml` pass their whole context, request parameters included, to `search#MantleFiltered`, and its party and product lookups take `documentType` from the request first (`mr-marble/template/party/PartyForms.xml`, `template/product/ProductTransitions.xml`); `search#MantleFiltered` adds an organization filter only when the type is empty, `MantleParty` or `MantleProduct`. These callers read the organization limit from the first filter set of the user's authorization only (`findFilters[0]`), and Marble's product lookup and Catalog Search write it into the query text as `ownerPartyId:(<ids>)`.

`mantle.search.UniversalSearchServices.search#Universal` is mr-boss `Commons/Search` and the palette, which fix `indexName`, and `GET` and `POST /rest/s1/mantle/search` under the `/mantle` REST path (`ADMIN` in the seed), where the caller sets `indexName`, `filters`, `near`, `limit`, `offset`, `facets` and `linkSet`; it does not check that `indexName` is `mantle`, bound `limit`, or limit the field names of `filters`. It shows a type only with a `DataDocument` row and view authorization on its primary entity. Under an organization limit (`MANTLE_USER_ORG` or `MANTLE_ACTIVE_ORG` on a `Party` find) a type's organization, user and party fields must hold one of the user's organizations or the user's party, and a type with no such field is left out, wiki pages excepted; without that limit a type is not limited by organization. Each hit is read again by primary key through the entity facade, with its filters, and then the per-record hide rules drop the hidden ones. `total` and the facet counts come from the index, recounted from the rows shown only for bound mailboxes, one-sided finance and payroll. A hit's answer is the index's copy of the document (title, subtitle, every scalar root field), not the row just read.

The query string (`crates/moqui-core/src/search/parse.rs`) takes `field:value`, prefixes and wildcards on any indexed field, and groups nested at most 64 deep; it has no regular expression, numbered fuzziness or slop. An empty group, `()` or `field:()`, is no clauses, which matches every document. A contains or wildcard term compiles to a scan of every row's words that no index serves, and a statement timeout is set only inside a report's limits (`search/limits.rs`); a page ends within 10,000 results, and `pageNoLimit=true` asks for 10,000. On OpenSearch a wildcard term is sent as a `query_string` with only `*`, `?` and `\` escaped again, so a character the user escaped with a backslash reaches OpenSearch as syntax. Highlight fragments are HTML-escaped around the `<em>` tags. The read-your-writes wait is at most 60 s. `POST /find/rank` (`webroot/find.xml`) answers 401 without a user and takes at most 5000 texts of 2000 characters.

`index#DataDocuments` stores the documents it is given, less four control fields. An encrypted or password field is left out where the document is defined ([Where a decrypted value goes](#where-a-decrypted-value-goes)), and a script that calls `ec.search.indexDocuments` with documents it built stores what it built. A change of a document's definition rebuilds its store: the mapping's signature covers every field, and at the next index call the Postgres backend drops and recreates a table whose signature differs (`search/postgres/mod.rs`, `ensure_index`), as OpenSearch does its index; the documents must then be indexed again. `index#DataDocuments`, `index#DataFeedDocuments`, `delete#DataDocument`, `delete#Documents` and `embed#PendingDocuments` have `authenticate="false"` or `anonymous-all`; the one outside route to them found is `POST /rest/s1/moqui/dataDocuments/feeds/{dataFeedId}/index` (`index#DataFeedDocuments`, `moqui.rest.xml`), and no transition or REST resource names the delete services. The feed (`search/feed.rs`) runs with authorization disabled and calls the service a `DataFeed` row's `feedReceiveServiceName` names; `ec.search.processFeedPending` and `ec.search.rebuildFeed` reach it from any script. A `DataDocumentField` whose last path element starts with `(` is an expression, run by the server's script engine when a document is built (`document.rs`; `crates/moqui-core/src/entity_hooks.rs`), with the document's fields and its parents' as names, in the context that builds the document (the feed's has authorization disabled). Writing or changing one needs `DATABASE_ADMIN` (`Security.eecas.xml`, SEC-SCR-06, fixed); a data load with authorization off, or with entity ECA rules off, is not checked.

The OpenSearch client sends `Authorization: Basic` of `search-facade/cluster@user` and `@password` on every request to `search-facade/cluster@url`, http or https as configured, with no request timeout unless a report's limit is active (`search/opensearch.rs`). Document ids are percent-encoded in a path.

## Caches

The entity cache (`crates/moqui-entity/src/entity/cache.rs`) keeps one list cache and one count cache for each entity, 10,000 entries each, which the shared evict thread enforces every 30 s, so a cache can pass its limit between passes; one cached list has no row limit, a key no length limit, and an entry no expiry. A find that the user's row filters may change is neither read from nor stored in the shared cache, and a shared hit is still authorized as a view of the entity. A key holds the whole condition, order, limit and offset; a select-field, distinct, aggregate or locking find is not shared; a write evicts every list that held the row or whose condition may match, every count and every view of the entity, and a read made before a concurrent write commits is not stored after it. The transaction cache is per thread and frame, a rollback drops the frame's held writes, and a frame holds at most 10,000 writes. A cluster invalidation carries the entity name and primary key fields only, and a peer's message can only evict. The conf's `entity.record.*` `max-elements` and every cache's `type` are read by nothing (`crates/moqui-core/src/context/cache.rs` reads `expire-time-idle`, `expire-time-live` and `max-elements`): `distributed` means nothing, and every conf cache is its own process's. The HMAC replay cache `moqui.security.hmac.replay` is one of them, so each cluster member keeps its own set of the signatures it has seen (`crates/moqui-core/src/service/system_sync/message.rs`).

`ec.cache` (`crates/moqui-core/src/script/host/cache.rs`) is one namespace for every script: a script reads, writes and clears any conf cache by name, the replay cache and PayTrace's token cache included, and a name not in the conf makes a cache with no size limit and no expiry. System › Cache › `CacheElements` lists conf caches only; the entity and screen caches give counts. The screen caches (`crates/moqui-core/src/screen/cache.rs`): `screen.definition` has no limit, `screen.url` and `screen.theme.icon` hold 20,000, the `//` screen path search map has no limit, and the shell providers hold 2000 keys of session, user, locale and theme for 600 s.

## Logs and spans

`crates/moqui-host/src/logging.rs` writes each event as given; it has no redaction of its own. `moqui.log` and `moqui-error.log` are created `0600`, and a new log directory `0700` (`logging::Rolling`, `moqui_lib::private_fs`); an existing file keeps its mode until it rolls. SQL text in a span (`db.query.text`) and in the slow-statement warning goes through `redact_sql` (`crates/moqui-entity/src/entity/exec.rs`): quoted literals become `?` and the text is cut near 4 KiB. Entity values are bound parameters and are not in the SQL text. A span's error text is cut at 4,096 characters and passed through `redact_text` (`crates/moqui-core/src/telemetry/mod.rs`), which replaces the value after `password`, `authorization`, `api_key`, `access_token`, `refresh_token`, `token` or `secret` followed by `:` or `=`. A decrypt failure logs the entity name, the field name and the error, not the value.

A service job's run keeps its parameters as given, as JSON in `ServiceJobRun.parameters` (`text-long`, not encrypted), and the job's notification message carries the same map and the results (`crates/moqui-core/src/service/jobs.rs`, `create_run`); a Data Load with `wrapForeignKeys` passes its whole load text there as a parameter of the `DatabaseLoadWrap` job.

## Threat model: stored secrets

This section says what a stored secret is protected from, and what it is not protected from. Each claim names its test; [Proof-Tests, Stored secrets](Proof-Tests.md#stored-secrets) lists them all. A test whose name starts with `known_gap_` pins a weakness: when the weakness is fixed, the test fails, and this section must change with it.

The short answer: field encryption keeps secrets out of a stolen database dump or a database backup that does not include `runtime/.env`. It does not protect them from anyone who has that file, the host, or code that runs in the server. It is not suitable as a personal password manager.

### Controls that hold

- Field encryption with the wrong pass, salt or iteration count does not give the plaintext (`wrong_or_empty_pass_fails`, `only_the_same_pass_salt_and_iterations_decrypt`).
- An empty pass is refused by `encrypt` and `decrypt`, and a pass that is not printable ASCII is refused (`crates/moqui-entity/src/entity/crypto.rs:104`; `wrong_or_empty_pass_fails`, `a_pass_phrase_that_is_not_ascii_is_an_error`).
- `CryptConfig`'s `Debug` does not show the pass (`crypto.rs:50`; `debug_leaves_out_the_pass`).
- Every bound value of an encrypted field in a query is encrypted before SQL (`every_bound_value_of_an_encrypted_field_is_sealed`).
- Startup replaces each generated secret attribute still at `CHANGEME` with 32 CSPRNG bytes, a new value each time, written to `.env` under its environment name with mode `0600` (`crates/moqui-core/src/context/conf_env.rs`, `generate_secrets`; `crates/moqui-lib/src/env.rs`, `update_dotenv_file`). An attribute is a secret by the conf schema or by its name (`conf_schema::attribute_secret`). Tests: `generated_secrets_are_32_random_bytes_and_secret_names_are_known`, `generated_secret_is_stable_and_unwritable_env_fails`, `update_dotenv_file_replaces_in_place_appends_and_removes`, `a_report_masks_secrets_and_a_components_element_is_live`.
- Password hashes are argon2id, and a legacy hash becomes argon2id at the next sign-in (`a_legacy_hash_verifies_and_the_stored_value_becomes_an_argon2_string`).

### Inspiration

Two designs show what MR Moqui does not do yet.

**HashiCorp Vault** (server-side secrets):

- A barrier encrypts all storage with AES-256-GCM. A random nonce on each write gives different ciphertext for equal values, and the GCM tag detects a change.
- The keyring is versioned. `vault operator rotate` adds a key term; old terms still decrypt, and new writes use the new term.
- A root key encrypts the keyring. Shamir's secret sharing (k of n unseal keys) or a KMS or HSM (auto-unseal) seals the root key. The key is not on the disk beside the data.
- Leases and dynamic secrets: Vault makes a short-lived credential on request and revokes it when its lease ends.
- Transit encrypts as a service: the application never holds the key. A rewrap moves ciphertext to the newest key version without exposing the plaintext. Convergent encryption is an opt-in for lookup by value.
- Response wrapping hands a secret over through a single-use token.
- Audit devices log each request with secret values as HMAC-SHA256. A request fails when no audit device can write it (fail closed).
- `mlock` keeps secret memory out of swap.

**Bitwarden** (client-side, zero-knowledge):

- The client derives a master key from the master password with PBKDF2-SHA256 (600,000 iterations by default) or Argon2id.
- HKDF stretches the master key into an encryption key and a MAC key.
- A random user key encrypts the vault. The stretched master key wraps the user key, so a password change rewraps one key, not every item.
- Each field is AES-256-CBC with HMAC-SHA256, encrypt-then-MAC, with a random IV.
- An organization key is shared by encrypting it to each member's RSA public key.
- The client sends only a hash of the master key, and the server hashes it again with a random salt. The server never sees the master password or a plaintext item.

**What MR Moqui can take from them** (also in [Remaining-Work](../../plans/Remaining-Work.md#sessions-notifications-and-security)):

| Improvement | From | Closes |
| --- | --- | --- |
