# Attack surface: processes and build

Processes the server starts, the startup port check, and the build features that decide what is compiled in. This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](Attack-Surface.md).

## Child processes

Each row is a program the server starts. A program named without a path (`git`, `gcc`, `ldconfig`, `lsof`, `su`, `id`, `kill`, `pkill`) is found through the server's `PATH`. Unless a row says so, the child gets the server's whole environment, with any secret that was given to the server as an environment variable.

## Other local processes

The `pdf` feature, which every server package includes, starts headless Chromium when a binary is found, with DevTools on a pipe (`--remote-debugging-pipe`) on Unix, so there is no socket another local process could open (SEC-SCR-10); on Windows on `--remote-debugging-port=0` at `127.0.0.1`, with no authentication of its own. The test client's browser (`moqui test-client`) keeps a loopback port. If no Chromium binary is found, the server still starts and PDF is unavailable.

An OpenSearch child starts only when `search-facade@backend` is opensearch, `search-facade/cluster@url` is loopback (the property default is `http://127.0.0.1:9200`), nothing is already answering, `runtime/opensearch/bin` exists, `search-facade/cluster@run` is not `false` (default `true`), and there is no pid file. The default `search-facade@backend` is `postgres`, so the child stays off. `search-facade/cluster@user` and `@password` default to empty. The child is given only `-Epath.data` and `-Epath.logs`; its network and security settings are its install's, which `moq` downloads as `opensearch-min`, the distribution without the security plugin, binding loopback by default (`scripts/moq/opensearch.sh`; the install's `config/opensearch.yml` was not read). So any local user or process of the host reads, rewrites and deletes every index on port 9200 with no sign-in; the server's own authorization holds only for what it searches. Run-Deploy (Programs) says so, and that a shared host keeps the Postgres backend or an OpenSearch with the security plugin and credentials (SEC-OUT-88).

The server never starts `moqui ci-run` on its own host. The CI engine asks the container driver for the job's image with its `runner-command` (`moqui ci-run`) and `MOQUI_CI_SERVER_URL`, `MOQUI_CI_TOKEN`, `MOQUI_CI_JOB_RUN_ID` and `CI=true` (`crates/moqui-git/src/ci/engine.rs`), so the runner runs as the image's user. A registered runner (`moqui ci-run poll`, `crates/moqui-host/src/ci_run.rs`) is started by an operator, as any user, as root with `--step-user`, with its token from `--token-file`, and works under `--work` ([Git](Attack-Surface-Git.md#what-a-jobs-container-and-its-steps-are-given)).

`moqui operator` (`crates/moqui-host/src/operator/client.rs`) is the operator socket's client: it reaches `/run/moqui-operator/moqui.sock` (always, as root), `runtime/db/operator.sock` for another user when that one is not there, or `--socket`, never a socket a conf, `runtime/.env` or the environment names; it reads passphrases, shares and secret values with the terminal's echo off and prints the recovery shares `init` issues once. `moqui vault` (`crates/moqui-host/src/vault_cmd/`) is a vault client over REST to `--server` (https, or http only to this machine), signing in with the password and second factor at each run and keeping nothing of the sign-in; the key passphrase and every key stay in its process, and it keeps only `~/.config/moqui/vault/state.json` (0600, no keys) ([Vaults](Vaults.md#the-moqui-vault-command)).

`systemd_notify` sends one datagram of at most 256 bytes to `NOTIFY_SOCKET` (a path, or `@name` on Linux), and a failure is ignored (`crates/moqui-host/src/systemd_notify.rs`); Chromium and OpenSearch do not get the variable. SIGHUP reloads the conf files when stdin is not a terminal, logs what applied and what waits for a restart, and keeps the running conf when the files do not merge; SIGINT and SIGTERM stop the server gracefully (`crates/moqui-host/src/http.rs`).

The desktop app (`crates/moqui-desktop`) starts the sidecar `moqui` with the app's whole environment plus `MOQUI_RUNTIME`, in a process group of its own with its descriptors marked close-on-exec (`node/sidecar.rs`); `moqui save-db` and `load-save` (`backup.rs`); `open` or `xdg-open` of an http, https (not the app's or the node's own), mailto, tel or sip URL (`lib.rs`) or of the backup folder; `xdg-mime default` and `update-desktop-database` (`os/handlers.rs`); and `hostname` (`client/mod.rs`). Its single-instance socket is `<config dir>/<identifier>/instance.sock`, made 0600 after `bind`, and a message on it is read with a header and at most 64 KiB (`os/instance.rs`).

The development tools start `ffmpeg` from the `PATH` with fixed arguments (`crates/moqui-host/src/test_client/video.rs`); the test client's browser (`test_client/cdp.rs`) with `launch_args`, DevTools on a loopback port, a fake camera and microphone, autoplay, `--ignore-certificate-errors` with `--insecure`, a process group of its own, the developer's whole environment (no `limit_child_env`) and its profile in a new directory of the system temp directory (`private_fs::new_dir_in`: mode 0700, a random name, never one already there); test workers, which are this binary with their output in `runtime/tmp/test-workers-<pid>` (`test_cmd/workers.rs`); and, for `test-client --serve`, `moqui test <components> --spec ... --db snapshot --serve 127.0.0.1:0 --ready-file <dir>/<n>.url`, the ready file in a new directory made the same way and removed when the server ends, with `MOQUI_CONF` and the suite's declared settings in its environment (`test_client/serve.rs`).

No code sets the mode of `runtime/tmp`: each user of it makes its part with `create_dir_all` (PDF profiles, `test-client/<run>`, `test-workers-<pid>`, the upload spool), except the terminal holder, whose directory is 0700. The image makes `/var/lib/moqui/tmp` with `install -d` (`podman/entrypoint.sh`). Whether another local user reads these depends on the modes of `runtime/tmp` and its parents.

The log subscriber (`crates/moqui-host/src/logging.rs`) writes each event's message and fields as given, with no redaction and no control character stripped, to stderr, the log files, the taps (the TUI's log pane and an SSH session's) and, for INFO and above, the telemetry log with the user id and visitor id; DEBUG and TRACE lines do not go to the telemetry log, and the queues before attach are bounded. What reaches a log is each caller's choice: the outbound, ACME and PASS client code logs host names, redacted URLs, the ACME contact email, an authority's error text, a PASS endpoint as written and the first line of a PASS service error, and no key, secret or header.

## Startup port check

`/metrics` is on the public HTTP listener. It is not its own port. `port_check` probes HTTP, HTTPS, cluster, and SSH before the database opens. It does not probe SMTP.

## Build features

Default Cargo features are `maximal` and `devtools` (`crates/moqui-host/Cargo.toml`). `maximal` includes `enterprise`, which includes `git`, `llm`, `tui`, and `ssh`. `lite` includes `llm` and `tui`. `git` and `ssh` are on the `enterprise` and `maximal` sets. A default `cargo build` therefore compiles `/git`, `/termws`, and the LLM routes. `inbound-smtp` is on Enterprise and Maximal. `embedded-postgres` is on Lite and Maximal. Enterprise leaves that feature out and uses an external database.

The sets in `crates/moqui-host/Cargo.toml` are these. No `dev` set exists; its line is commented out.

`./moq build` makes one of four packages, each with `--no-default-features`. Maximal, the default, is `--profile release -F maximal,devtools` and gives `target/release/moqui`. Debug is `--profile dev -F maximal,devtools` and gives `target/debug/moqui`. Lite is `--profile lite -F lite` and gives `target/lite/moqui`. Enterprise is `--profile enterprise -F enterprise` and gives `target/enterprise/moqui`. The default release build therefore has `devtools`; Lite and Enterprise do not. `--embed production|all`, `--embed-opensearch` and `--embed-chromium` add the `embed-*` features.

## Packaging

`podman/Containerfile` builds on `debian:13-slim`. It makes the user `moqui` (uid 1000, shell `nologin`), copies the binary, the confs and the components to `/opt/moqui`, and gives the directory `/opt/moqui` itself to `moqui`; the binary is mode 755. It declares the volume `/var/lib/moqui` and exposes 8080 and 8443. It has no `USER` line. `podman/entrypoint.sh`, when it starts as root, makes the data directories under `/var/lib/moqui`, creates `/var/lib/moqui/env` with mode 600 and links it as `/opt/moqui/.env`, and then, still root, makes the operator socket with `moqui operator bind /run/moqui-operator/moqui.sock -- ...`, which runs the server with `setpriv --reuid=moqui --regid=moqui --init-groups --inh-caps=-all`; with no group given, only root in the container (`podman exec -u 0`) runs operator commands. When it starts as another user it runs the server directly. The health check is `curl http://127.0.0.1:8080/health`. The image installs no Chromium. `podman/build.sh` builds the binary with `./moq build --release`, the Maximal package with `devtools`, where Run-Deploy's production checklist says a production image leaves the dev tools out.

`podman/quadlet/moqui.container` publishes 8080 and 8443 on every host address and sets `moqui_conf__instance__purpose=production`. The four compose files publish the same two ports and set `instance@purpose: production`. The three with a database give the server and the database container `${MOQUI_DB_PASSWORD:?set MOQUI_DB_PASSWORD in podman/.env}` (and the MySQL one `MOQUI_DB_ROOT_PASSWORD` the same way), so there is no default password and a start without one fails; `podman/env.example` leaves both empty. They set `moqui_conf__entity_facade__datasource__TRANSACTIONAL__sslmode: disable` (the compose network only) and do not publish the database port; a commented line publishes it on `127.0.0.1` of the host (plans/archive/Security-Review.md SEC-OUT-07, fixed). The two with OpenSearch run it as `user: "0:0"` with `DISABLE_SECURITY_PLUGIN: "true"` and `network.host: 0.0.0.0` inside the compose network, publish no OpenSearch port, and name the image `docker.io/opensearchproject/opensearch:3.4.0` by tag, not digest.

`systemd/moqui.service` runs `/opt/moqui/moqui` as user and group `moqui` with `Type=notify`, `NotifyAccess=main`, `EnvironmentFile=-/etc/moqui/environment`, `KillMode=mixed`, `LimitCORE=0`, a reload that sends SIGHUP, and `Sockets=moqui-operator.socket` (required), whose socket `systemd/moqui-operator.socket` makes as root; `systemd/moqui.sysusers` makes the group `moqui-operator` for it. A server waiting sealed sends `READY=1` with `STATUS=sealed` ([Sealed start](../Run-Deploy.md#sealed-start)). Its sandbox settings are `NoNewPrivileges=true`, `PrivateTmp=true`, `ProtectSystem=strict`, `ProtectHome=true`, `ReadWritePaths=/opt/moqui /opt/moqui/components` and `ReadOnlyPaths=/opt/moqui/moqui -/opt/moqui/MoquiConf.xml -/opt/moqui/conf`: the runtime's data and components are writable, the binary and the confs are not, whoever owns them (SEC-OUT-13), and the install steps (docs/Run-Deploy.md) make them root's. The image (`podman/Containerfile`) has the binary and the confs root's and not writable to uid 1000, `components/` uid 1000's, and `/opt/moqui` root's, group `moqui` and sticky, which the entrypoint no longer hands to the moqui user. It does not set `PrivateDevices`, `ProtectKernelTunables`, `ProtectKernelModules`, `ProtectControlGroups`, `RestrictAddressFamilies`, `RestrictNamespaces`, `CapabilityBoundingSet`, `SystemCallFilter`, `LockPersonality` or `UMask`. The drop-ins `postgres.conf` and `mysql.conf` only order the unit after the database service. `systemd/moqui.sysusers` makes the user `moqui` with home `/opt/moqui` and shell `nologin`.

The `moq` script downloads OpenSearch (`opensearch-min`) from `artifacts.opensearch.org` with `curl` and checks it against the SHA-512 file published beside it at the same address, and against the SHA-256 recorded at its first download; when the published file cannot be read the archive is removed and the task stops (`scripts/moq/opensearch.sh`, SEC-OUT-91). `scripts/pg-payload.sh` checks a Postgres archive against the sum published beside it and against the SHA-256 the repository pins (`scripts/pg-payload.sha256`), and refuses one with no pin; the desktop build checks tauri's `quick-sharun.sh` against the SHA-256 recorded at its first use for that tauri-cli. The CI image's build fetches `rustup-init.sh` from `sh.rustup.rs` and checks nothing (`podman/Containerfile.build`). It downloads a Chromium snapshot (the revision from chromiumdash and the storage listing) and an add-on's zip with `curl -fL`, and checks a snapshot of a revision and a `release` or `binary` add-on zip against the SHA-256 recorded at its first download (`check_download_sum`; plans/archive/Security-Review-Low.md SEC-OUT-14, fixed); an add-on zip's URL has no scheme limit. It clones an add-on with `git clone -- <url>`. Nothing it fetches runs at once: a component with a `Cargo.toml` is linked into the next build, and a component loads at the next start.

`moq` looks a component, a component set or a repository up in `myaddons.xml`, then in `addons.xml`, then in each `addons.xml` a server serves that `myaddons.xml` names, and the first match wins (`scripts/moq/components.sh` `ADDONS_FILES`). So a served file adds names and replaces none of the official ones, and a component name must pass `template_name` (a letter, then letters, digits, `-` and `_`) before it becomes a path. Zip downloads use `curl --proto '=https,file' --proto-redir '=https' --url`. Only its components and repositories are read, never its root's `default` or `default-repository`, and it is fetched over https, `file` or loopback http, with https redirects only, at most 4 MiB in 30 seconds. On an MR PASS server the served file lists a group's public repositories by slug (mr-mantle `SmithySite.js`).

Other downloads: `scripts/pg-payload.sh` downloads the embedded Postgres archive that `embedded-postgres` puts in the binary and checks it against the `.sha256` of the same GitHub release; `podman/Containerfile.build` downloads `rustup-init.sh` and runs it with no sum; `scripts/moq/desktop.sh` runs `~/.cache/tauri/quick-sharun.sh`, which tauri downloaded, with no check; `scripts/nasm.sh`, `scripts/cmake.sh` and `scripts/ninja.sh` (Windows only, through `scripts/win-tool.sh`) pin the SHA-256 of NASM, CMake and Ninja.

## Test-only hooks

- `HttpFixtures` (`crates/moqui-core/src/service/http_fixtures.rs`) answers every request of `outbound::send` when it is on. `set_enabled(true)` fails unless `http_fixtures::allow()` ran in the process, and only the `moqui test` runner calls it (`crates/moqui-host/src/test_cmd/mod.rs`). A server of `moqui run` cannot turn it on.
- The `X-Moqui-Test-Peer` header (`crates/moqui-host/src/http/test_peer.rs`) is read only after `test_peer::allow()`, which only `moqui test --serve` calls (`crates/moqui-host/src/test_cmd/serve.rs`). It is taken only when the TCP peer and the client address are both loopback, and only for an IPv4 address in `127.0.0.0/8`.
- Mail capture (`crates/moqui-core/src/service/mail_capture.rs`) keeps a send in memory in place of sending it, up to 500 messages for a factory. It is on only after `mail_capture::allow()` ran in the process, which the `moqui test` runner calls beside `http_fixtures::allow`, and then when the setting `email-client@capture-sends` is `true` or a script turns the `MailCapture` tool on: `is_enabled` answers `allowed()` and `set_enabled` asks `may_enable(enabled, allowed())` (plans/archive/Security-Review.md SEC-DEV-05, fixed).
- `moqui test --serve` keeps `http_fixtures::allow`, `mail_capture::allow` and `test_peer::allow` set for the server it serves after the specs, on any address `--serve` names (`0.0.0.0:8080` is taken), and with `--db existing` on the runtime's own database (`crates/moqui-host/src/test_cmd/mod.rs`, `test_cmd/serve.rs`). Whoever reaches that address reaches a server with the test hooks on.
- `chat@link-preview-service` names a service asked in place of the network for a chat link preview, and `mail-delivery@mx-override` sends a recipient domain's mail to a named `host:port`; both are read with no check of the instance's purpose in the lines read (`crates/moqui-core/src/service/chat_link.rs`, `crates/moqui-mail/src/mx.rs` `override_for`).
